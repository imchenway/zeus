# 通用发布前门禁

## 目标

把本地提交前检查、GitHub 普通 CI 和 macOS Release 收敛到同一个验证入口，避免本地认为可发布、推送后 Actions 才暴露必然失败的问题。

## 问题事实

- 既有 CI 在每次 `main` 推送后执行全仓 `pnpm format:check`。
- 最近多次失败都停止在格式检查，尚未进入 lint、typecheck、build 和安全审计。
- 当前仓库存在 78 个历史未格式化文件；为修正文档或发布脚本而批量改写这些业务文件会扩大变更范围，也不符合“能运行、能发布”的当前目标。
- 既有 `verify:release` 与普通 CI 分别维护门禁命令，长期存在本地、CI 和正式发布口径漂移的风险。

## 实现

新增唯一普通发布入口：

```bash
pnpm verify:publish
```

该入口执行：

1. 扫描工作区、暂存区和本次未跟踪文件中的 Git 冲突残留；
2. 检查本次变更范围内的 Git 空白错误；
3. 只对本次变更中的 TypeScript、JavaScript、JSON 和 YAML 文件执行 Prettier；
4. 执行 lint；
5. 执行 TypeScript 类型检查；
6. 执行生产构建。

变更范围的来源：

- 本地：未提交、已暂存、未跟踪以及相对上游尚未推送的文件；
- GitHub push / PR：`ZEUS_VERIFY_BASE..ZEUS_VERIFY_HEAD`；
- 干净工作区或 Release tag：最近一次提交范围。

正式发布入口保持为：

```bash
pnpm verify:release
```

它先调用 `verify:publish`，再执行设计验收矩阵、AI CLI adapter 探针、macOS 打包、Homebrew Cask、摘要、清单和包内健康检查。普通 CI 也只调用 `verify:publish`，不再复制多条独立命令。

## 优缺点

优点：

- 本地、普通 CI 和 Release 使用同一份门禁实现，减少口径漂移；
- 即使冲突标记已经被当成普通文本提交，门禁也会在编译前给出精确文件和行号；
- 失败会在推送前被本地发现；
- 不需要为一次小改动批量格式化 78 个历史文件；
- 不引入或恢复单元测试体系。

缺点：

- 每次正式推送前都会执行生产构建，比单独 lint 更慢；
- 文档若需要演示完整 Git 冲突标记，不能把标记单独放在行首；
- 只阻止新增或本次触及文件的格式问题，不会自动偿还全仓历史格式欠账；
- 依赖安全审计不放入每次普通推送和实用发布的自动门禁，已知风险保留在任务记录中，并另行安排依赖升级。

## 验证记录

本地结果：

- `node --check scripts/verify-publish.mjs`：通过。
- 本次变更文件 Prettier、GitHub workflow YAML 解析和 `git diff --check`：通过。
- `pnpm verify:publish`：通过；变更文件格式、Git 空白错误、lint、typecheck 和生产构建均成功。
- `pnpm verify:release`：通过；共同门禁、12 个章节 / 139 项验收矩阵、Codex / Claude / Gemini 探针、macOS App / DMG / ZIP 打包、codesign 磁盘校验、Electron 加载和包内健康检查均成功。
- 本地产物仍为 ad-hoc 签名且未 Apple 公证；该结果不等同于 Developer ID 正式分发。
- `pnpm audit --audit-level=moderate` 报告 20 条既有依赖风险（2 low、4 moderate、13 high、1 critical），因此移出每次自动门禁；本任务不夹带依赖树升级。

远端结果：

- 推送后的 GitHub CI：待提交推送后核对。

## 变更边界与回滚

- 本任务不修改业务功能、版本号、Release tag 或 Homebrew Cask。
- 未跟踪的 `docs/TASK_20260729_002_新增项目入口定位.md` 属于其他工作，不纳入本任务提交。
- 回滚时恢复 `package.json`、CI / Release workflow、`scripts/verify-release.sh` 和发布文档，并删除 `scripts/verify-publish.mjs`；回滚后会恢复本地与远端门禁分离及全仓格式检查固定失败的问题。
