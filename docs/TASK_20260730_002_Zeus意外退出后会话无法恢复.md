# Zeus 意外退出后会话无法恢复

## 当前状态

- 阶段：源码分析与修复方案
- 实施状态：尚未实施
- 运行验证：尚未执行修复后的打包应用验证
- 分析基线：本任务开始时工作区为干净状态，正式包中的 Renderer、Main、local-server 和 storage 构建产物与当时仓库构建产物一致。分析过程中工作区出现了其他并行修改，本任务未覆盖、回滚或吸收这些修改。

## 用户现场

用户在计划模式的 `request_user_input` 最后一个问题中点击“其他回答”自由输入入口后，Zeus 退出。重新打开后：

- 原 turn 已被记为 `interrupted`；
- 用户新发送的“继续”同时显示为“发送中”和“待发送”；
- 队列没有“继续队列”操作，消息也不会自动派发；
- 当前用户数据库执行 `PRAGMA quick_check` 返回 `database disk image is malformed`。

## 源码事实

### 自由输入控件没有显式退出调用

`apps/desktop/src/renderer/session/PendingRequestSurface.tsx` 中，“其他回答”点击只执行以下状态变化：

1. 计算内部 Other 控制值；
2. 更新当前问题的 `answers`；
3. 让原本禁用的输入框进入可输入状态；
4. 普通单选才自动进入下一题，Other 分支不会立即提交。

`apps/desktop/src/renderer/session/PlanImplementationRequestSurface.tsx` 中，计划完成后的“告诉 Codex 应该如何做得不同”也只执行 `setFeedbackOpen(true)` 并聚焦 textarea。

因此，源码不能证明这两个点击处理器自身会直接退出应用。缺少当次 Renderer 的真实异常消息和组件栈，不能编造具体的 React 异常类型。

### 可恢复的 Renderer 异常会被放大成整应用退出

退出链由源码完整证明：

1. `apps/desktop/src/preload/index.cts` 捕获全局 `error` 和 `unhandledrejection`。
2. `apps/desktop/src/preload/rendererBootstrapState.cjs` 在首次渲染完成后，将任意上述异常发送到 `zeus:renderer-runtime-failed`。
3. `apps/desktop/src/renderer/ErrorBoundary.tsx` 捕获 React 错误后调用同一 fatal 上报；存在 `onFatalError` 时反而返回空页面，不渲染已经实现的恢复界面。
4. `apps/desktop/src/main/main.ts` 收到 `zeus:renderer-runtime-failed` 后调用 `startupCoordinator.fail(...)`。
5. `startupCoordinator` 将运行期异常送入 `handleFatalStartupError`。
6. `fatalStartup.ts` 最终调用 `app.quit()`。

这解释了为什么 macOS 将当次退出记录为 `voluntary`，而不是原生崩溃：Zeus 自己执行了正常退出。

### 中断恢复状态被误判并形成队列死锁

`packages/local-server/src/codexNativeConversationCoordinator.ts` 中存在以下状态组合：

1. turn 被 provider 确认为 `interrupted` 后，conversation 的 `providerState` 被持久化为 `paused`。
2. 只有当中断发生时已经存在 queued submission，源码才把这些 submission 转为 `paused/interrupted`。
3. 本次退出前没有 queued submission，因此重启后不存在可证明 `interrupted` 原因的 paused submission。
4. `inferRunState()` 在没有 active turn、没有 `paused/interrupted` submission 时，只要看到 `providerState === 'paused'`，就返回 `paused/recovery_required`。
5. 用户重启后发送“继续”，`submitMessage()` 先持久化 queued submission，但仅在 run state 为 `idle` 时派发，因此消息停留在 queued。
6. `drainQueuedSubmissions()` 同样只派发 `idle` conversation。
7. `resumeInterruptedQueue()` 只接受 `paused/interrupted`，当前状态却是 `paused/recovery_required`。
8. Renderer 只为 `interrupted` 显示“继续队列”，不会为 `recovery_required` 显示该操作。

最终形成稳定死锁：

`providerState=paused` → `runState=recovery_required` → 新消息只入队 → 队列不能派发 → UI 没有恢复按钮。

### 当前持久化方式不能保证异常退出后的数据库完整性

`packages/storage/src/index.ts` 的 `save()` 直接执行：

1. `this.db.export()` 导出整个 sql.js 内存数据库；
2. `writeFile(this.filePath, ...)` 覆盖正式数据库文件。

该实现没有临时文件、原子 rename、文件同步和 save 串行队列。多个并发 `save()` 可能交叠写入；进程在覆盖写期间退出，也可能留下半写文件。

`codexNativeConversationCoordinator.ts` 对 provider 事件逐条调用 `persist()`，并把最多一万条 processed event identity 作为一个 JSON settings 值反复写入。当前数据库约一百兆，意味着流式事件期间可能高频全库导出和覆盖。

源码证明该持久化方式不具备异常退出安全性；当前数据库已经损坏。但没有日志能证明损坏恰好发生在本次自由输入点击对应的某一次写入，因此这里只能将两者标记为强关联风险，不能写成已证明的单点因果。

## 领域边界

恢复逻辑必须区分四类事实：

| 领域事实 | 含义 | 是否允许自动继续 |
| --- | --- | --- |
| Provider thread 已恢复且最后 turn 已终止 | 同一 thread 可以开始新 turn | 允许 |
| 旧 turn 为 interrupted，退出前没有待发消息 | 不重放旧 turn，下一条新消息开启新 turn | 允许 |
| 旧 turn 为 interrupted，退出前已有持久化待发消息 | 保留原队列，等待用户显式继续 | 不自动 |
| Provider 结果未知、thread 无法读取或身份不确定 | 可能重复写 provider | 禁止，保持 recovery required |

`providerState=paused` 只能描述 provider 层表象，不能单独代表 `recovery_required`。恢复原因必须来自 turn、submission、request 和 provider snapshot 的可核对事实。

## 推荐修复方案

### 阻止 Renderer 异常终止整个应用

修改范围：

- `apps/desktop/src/preload/rendererBootstrapState.cjs`
- `apps/desktop/src/preload/index.cts`
- `apps/desktop/src/main/main.ts`
- `apps/desktop/src/renderer/ErrorBoundary.tsx`
- `apps/desktop/src/renderer/main.tsx`

方案：

1. 保留首次 commit 前的 bootstrap fatal；只有应用确实无法启动时才进入 fatal startup termination。
2. 首次 commit 后的 `error`、`unhandledrejection` 和 React Error Boundary 只上报运行期诊断，不再调用 `startupCoordinator.fail()`。
3. Error Boundary 始终渲染现有恢复界面，提供“刷新窗口”；不能因为存在上报回调就返回空页面。
4. Main 对运行期错误写入本地诊断并保持 local-server、Codex app-server 和数据库进程存活。
5. 会话交互区域增加局部错误边界时，只暂停当前交互面板，不影响项目树、历史消息和恢复操作。

优点：

- 即使自由输入仍存在未知 Renderer 缺陷，也不会再导致整应用退出和中断 provider turn。
- 用户可以刷新界面，后台会话与队列继续保留。
- 后续能拿到真实错误信息，而不是只留下 shutdown interrupted。

缺点：

- 这是异常隔离，不等于已经修复自由输入控件的具体异常。
- 若错误发生在全局状态层，刷新前当前窗口可能只能显示恢复页。

### 修正 interrupted 与 recovery required 的推导

修改范围：

- `packages/local-server/src/codexNativeConversationCoordinator.ts`
- 必要时同步 `packages/local-server/src/index.ts` 的快照推导
- `apps/desktop/src/renderer/session/ConversationComposer.tsx`
- `apps/desktop/src/renderer/session/sessionReducer.ts`

推荐语义：

1. 已中断的旧 turn 永不自动重放。
2. 中断发生前已经持久化的 queued submission 转为 `paused/interrupted`，重启后继续要求用户显式“继续队列”。
3. 如果中断发生时没有 queued submission，provider snapshot 已确认旧 turn 终止后，将 conversation 归一为 `providerState=ready`、`runState=idle`。
4. 用户重启后新输入的消息直接在同一 provider thread 开启新 turn。
5. 只有 provider snapshot 无法确认、dispatch 窗口未知、thread 身份不一致等情况才进入 `recovery_required`。
6. `inferRunState()` 不再用 `providerState === 'paused'` 单点推断 recovery required；优先使用显式 paused reason、active turn、pending request 和已核对的 provider snapshot。

优点：

- 当前“继续”入队死锁会被直接消除。
- 不重放旧 turn，也不静默发送退出前已排队的内容。
- 与现有 archived/provider_archived 的显式恢复模式一致。

缺点：

- 需要统一实时 `turn/completed` 和启动 `reconcileConversationSnapshot` 两条状态转换，漏改任一条都会再次产生不一致。
- 必须用真实 app-server snapshot 验证 interrupted thread 确实可继续开启新 turn。

不推荐仅把 `recovery_required` 映射成 `interrupted`。该方案改动小，但会把真正的未知 provider 写窗口伪装成安全中断，存在重复发送风险。

### 让数据库保存具备异常退出安全性

修改范围：

- `packages/storage/src/index.ts`
- 高频 provider event 的持久化调度位置

方案：

1. 为 `save()` 增加单一串行保存链，禁止同一数据库文件并发覆盖。
2. 每次保存先导出稳定 Buffer，写入同目录唯一临时文件。
3. 临时文件写完并同步后通过同目录 rename 原子替换正式文件；必要时同步目录。
4. 保存失败时保留旧正式文件，清理对应临时文件，不把半写内容提升为正式库。
5. 保留最近一次通过完整性校验的恢复副本；启动发现正式库损坏时停止写入并进入恢复流程。
6. 将流式 delta 的数据库保存合并为短时间窗口批量刷新；submission acceptance、request response、provider turn identity、terminal state 等权威边界仍立即保存。
7. processed provider event identity 不再作为不断扩大的单个 settings JSON 高频重写，改为有界结构或批量快照。

优点：

- 强制退出期间至少保留旧的完整数据库或新的完整数据库。
- 消除并发 save 的乱序覆盖风险。
- 降低流式输出期间全库导出和磁盘写入压力。

缺点：

- sql.js 仍然需要全库导出，数据库越大保存成本越高。
- 批量持久化需要明确哪些事件允许短暂延迟，不能削弱用户消息和 provider 写入幂等边界。
- 已损坏的当前数据库不会因代码修复自动恢复，仍需单独备份和迁移可读数据。

长期更稳妥的方向是使用具备事务日志和崩溃恢复能力的原生 SQLite 驱动；代价是迁移范围、原生依赖和打包风险显著更大，不建议与本次恢复缺陷一次性混合。

## 建议实施顺序

1. 先隔离 Renderer 运行期错误，避免继续制造整应用退出。
2. 修正 interrupted 状态归一和队列恢复语义。
3. 将数据库保存改为串行原子替换，再处理保存频率。
4. 基于只读备份单独恢复当前损坏数据库，禁止直接覆盖唯一现场。
5. 最后执行正式打包应用的强制退出与同 thread 续接验收。

## 验证方式

静态与构建：

- `pnpm lint`
- `pnpm typecheck`
- `pnpm build`
- `pnpm package:mac`
- `codesign --verify --deep --strict dist/mac-arm64/Zeus.app`
- `scripts/verify-packaged-app-health.mjs`

真实运行检查必须使用测试数据库副本和测试会话：

1. 点击 request user input 的 Other，自由输入框启用，Zeus 进程不退出。
2. 人为触发局部 Renderer 异常，窗口显示恢复界面，Main、local-server 和 app-server 继续存活。
3. 在等待用户输入时强制结束测试应用，重启后旧 turn 标记 interrupted，不重放旧 turn。
4. 退出前没有 queued submission 时，重启后的新消息在同一 provider thread 创建新 turn。
5. 退出前存在 queued submission 时，消息保持 `paused/interrupted`，只有用户点击“继续队列”后才按原顺序发送。
6. Provider snapshot 无法确认时仍保持 recovery required，不能自动发送。
7. 强制退出前后对测试数据库执行 `PRAGMA quick_check` 和 `PRAGMA integrity_check`，结果均为 `ok`。
8. 核对 conversation、submission、turn、request 和 provider thread identity，确认没有重复用户消息、重复 turn 或错误新建 thread。

静态检查、构建成功或隔离页面成功都不能替代上述正式打包应用运行验收。
