# TASK_20260730_003 应用菜单检查更新弹窗

## 1. 任务目标

让 macOS 应用菜单中的 `Check for Updates...` 不再只跳转设置页，而是立即执行真实更新检查并显示结果弹窗，由用户决定是否进入升级路径。

## 2. 真实现状

- `apps/desktop/src/main/appShellPolicy.ts` 已定义 `Check for Updates...` 菜单项和 `CommandOrControl+U` 快捷键；
- `apps/desktop/src/main/main.ts` 当前把该菜单动作映射到 `#settings-about`，没有触发更新检查；
- Renderer 已通过 `POST /api/release/check-update` 执行真实 GitHub Release manifest 检查；
- `packages/release-core` 只有在产物同时签名并公证时才返回 `download_and_install`，否则返回 `open_download_page`；
- 当前下载和安装 API 仍是明确拒绝的预留接口，本任务不把预留接口伪装成已能自动替换应用。

## 3. 已确认边界

用户确认采用以下安全边界：

- 菜单点击后立即检查，并对“检查中、已是最新、发现更新、检查失败”提供明确反馈；
- 已是最新时显示当前版本；
- 发现已签名且已公证的更新时，弹窗允许进入下载并安装路径；
- 未签名或未公证的更新只允许用户选择“打开下载页”或“取消”，不自动替换本机 App；
- 外部下载页继续通过 Electron Main 的 HTTPS 白名单桥接打开，不允许 Renderer 直接打开任意 URL。

## 4. 领域模型

当前可用技能中缺少项目规则要求的 `domain-modeling`，本任务以真实类型完成等价建模：

- 更新检查请求：由 macOS 原生菜单发起，经 Main → preload → Renderer 单向事件进入现有检查链路；
- 更新检查状态：`checking | result | failed`；
- 结果状态：沿用 `ReleaseUpdateStatusSnapshot.status` 的 `up_to_date | available | unavailable`；
- 用户决策：`dismiss | retry | open_download_page | download_and_install`；
- 安全能力：以 `automaticInstallEnabled` 和 `recommendedAction` 为唯一事实源，不从按钮文案推断。

## 5. 实施记录

- 将根包与桌面包版本从 `0.1.1` 同步提升到 `0.1.2`，避免新二进制继续占用既有公开版本号；
- `AppShellMenuActions.openReleaseStatus` 收敛为 `checkForUpdates`，菜单动作不再执行 hash 跳转；
- Main 在 Renderer 已就绪时发送 `zeus:native-check-for-updates`；尚未就绪时按窗口保留一次请求，
  收到 `zeus:renderer-bootstrap-ready` 后投递，窗口关闭时清理；
- preload 只暴露 `onNativeCheckForUpdates` 单向订阅，不向 Renderer 暴露任意 IPC 发送能力；
- App 收到菜单事件后调用现有 `onCheckReleaseUpdate`，并以请求编号防止用户关闭弹窗后迟到结果重新打开；
- 新增 `ReleaseUpdateDialog`，覆盖检查中、已是最新、发现更新、检查失败和安装准备状态；
- 未签名或未公证时，主动作只打开 `releasePageUrl`；URL 继续经过 Renderer 与 Main 两层 HTTPS 校验；
- 已签名且已公证分支复用现有 download/install API；任一接口拒绝时显示真实 `reason`，不伪造成功；
- 设置页原有“检查更新”按钮仍保持原位内联刷新，不被菜单弹窗行为改变。
