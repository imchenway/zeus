# Zeus 代码图谱工作台设计与实现记录

## 当前结论

2026-07-31 已按“代码页就是看图谱”的确认口径完成 Renderer 重构，并使用仓库本地生成的 `dist/mac-arm64/Zeus.app` 完成无截图真实运行复核。设计稿不再只是提案，当前实现以本文件“实现结果”和“交付与验证”两节为准。

## 产品边界纠正

用户已明确：“代码”页的目的就是查看代码图谱。

因此本稿撤回“源码优先、图谱按需”的方向，并恢复以下硬约束：

1. `CodeMapView` / `GraphCanvas` 是代码页首屏唯一主舞台。
2. 页面内部不增加文件树、源码编辑器或第二套常驻导航。
3. 节点、边、搜索、问答、导出和运行诊断都围绕图谱服务，不能与图谱争抢首屏。
4. 源码仍是图谱节点的次级动作，由外部应用打开，不在代码页内嵌阅读器。

## 现状证据

源码核对范围：`apps/desktop/src/renderer/App.tsx`、`apps/desktop/src/renderer/styles.css`、桌面端 API 客户端与图谱引擎。

- 当前存在七类真实视图标签：系统架构图、模块图、表关系图、模块详情图、接口时序图、模块流程图、方法逻辑图。
- 当前主画布最终固定裁剪为八个节点、五条边，搜索结果也经过相同裁剪。
- 一跳、两跳操作只改变检查器中的邻居文字，没有驱动画布展示真实邻域。
- 当前静态 SVG 不具备缩放、平移、适配视口、聚焦和小地图。
- 节点支持选择、打开源码、图谱问答、创建任务、隐藏和恢复；边支持关系类型、置信度、来源与目标详情。
- 搜索、问答、Mermaid / PlantUML、节点与边清单及运行时预览均为现有入口，但被同时放进检查器后造成拥挤。
- “打开源码”通过 macOS 默认应用打开文件，尚不能在 Zeus 内精确定位到具体行。

以上是进入实现前的现状证据。缩放、平移、适配、聚焦邻域、语义聚合和小地图现已落入产品代码；静态扫描仍不等于运行时调用轨迹，超大图谱也仍受当前前端切片与 SVG 渲染上限约束。

## 视觉命题

“低噪音空间地图，而不是图谱后台。”

- 冷中性连续画布占据工作区剩余空间。
- 节点主体保持中性，只用窄色条区分界面、模块、包和运行时。
- 选中节点使用单一蓝紫强调色，相关路径提高对比度，其他对象降低权重。
- 不使用卡片矩阵、指标胶囊、多层状态横幅或常驻底部动作带。
- 小图按内容边界适配；大图通过聚合、语义缩放和局部聚焦处理，不能静默裁切。

## 内容规划

首屏只保留四层：

1. 外层项目导航：任务、代码、会话。
2. 图谱命令栏：视图选择、节点搜索、扫描状态、询问和图谱工具。
3. GraphCanvas：运行时接入真实节点与方向关系；设计稿用明确标注的结构示例表达图例、画布控制和小地图。
4. 状态栏：运行时展示当前视图、可见数量、真实总量与扫描状态；设计稿只显示示例数量。

节点或边被主动选择后，才出现浮动详情。搜索、问答、导出、节点与边清单、运行时诊断和重新扫描统一收进命令栏次级入口。

## 交互命题

默认路径是“查看全图 → 定位对象 → 聚焦关系 → 采取动作”。

- 查看全图：进入代码页即可看到图谱主体，不需要滚动或切换模式。
- 定位对象：通过节点搜索、视图选择或直接点击图谱对象定位。
- 聚焦关系：选择节点后查看入边、出边与置信度；一跳、两跳必须真实改变可见子图。
- 采取动作：打开源码、询问节点、创建任务或隐藏节点。

设计稿支持：

- 展示七类现有视图入口；本稿只交互展开系统架构图，避免用同一示例拓扑冒充其他视图；
- 搜索并定位节点；
- 点击或键盘选择节点；
- 按需打开、关闭节点详情；
- 画布缩放与适配；
- 打开图谱工具菜单；
- 窄屏底部详情面板与焦点恢复。

## 状态覆盖

- 初次加载：画布中央显示正在读取真实图谱，不绘制假节点。
- 后台扫描：保留上一份图谱，命令栏显示更新状态。
- 未扫描或空图：解释原因并在画布中央提供“扫描项目”。
- 扫描失败：有旧快照时继续展示并标记过期；无快照时提供重试。
- 权限不足：说明需要当前项目目录权限。
- 项目不匹配：阻断旧项目图谱，不能展示其他项目缓存。
- 超大图谱：明确进入聚合层，并区分真实总量与当前渲染量。
- 搜索无结果：只影响搜索浮层，不清空当前画布。
- AI Runtime 不可用：只影响问答，GraphCanvas 继续可用。

## 优缺点

优点：

- 代码页目标单一，首屏直接回答“项目代码如何连接”。
- 详情和工具按需出现，图谱面积稳定。
- 现有搜索、问答、导出、创建任务和运行诊断能力仍然可达。
- 窄屏不再把 Inspector 堆到画布下方形成超长页面。

缺点与成本：

- 浮动详情会遮挡局部画布，需要自动把选中节点移到未遮挡区域。
- 低频工具的发现性低于常驻标签，需要可靠的命令栏和快捷键提示。
- 取消八节点、五条边硬裁不能直接把全量 SVG 塞进 Renderer，需要聚合、虚拟化或 WebGL 渲染策略。
- 真正的一跳、两跳聚焦需要接通 neighborhood API，不是纯 CSS 返修。

## 实施计划（已执行）

1. 先重构渲染结构，使 GraphCanvas 占满工作区并移除常驻空 Inspector。
2. 把七个平铺视图入口收成分层选择器，并保留各视图的视口和选择状态。
3. 把搜索、问答、导出、实体清单和运行时诊断迁移到互斥浮层。
4. 接通真实邻域查询，再实现一跳、两跳聚焦和图谱返回路径。
5. 为中大型图谱加入语义缩放、聚合和渲染性能策略。
6. 最后完成键盘、焦点、窄屏面板和错误状态。

## 实现取舍

优点：

- 代码页目标收敛为“直接看图谱”，进入页面无需二次切换。
- Inspector 和工具不再常驻占位，图谱面积与布局保持稳定。
- 一跳、两跳、搜索和缩放会真实改变或控制当前画布，不再只更新说明文字。
- 聚合节点和聚合边可以追溯到原始来源，统计不把关系组冒充原始关系。
- 后台扫描和并发请求不会轻易清空已有图或回写过期结果。

缺点与后续成本：

- 当前聚合发生在 Renderer，适合先解决可用性与语义问题，但超大仓库的最终性能仍需要服务端聚合或 WebGL 主画布。
- 一跳、两跳只覆盖当前已加载、已过滤视图，不是仓库全量邻域查询。
- “已加载总量”是当前后端返回的视图快照，不是仓库全局节点与关系总数。
- 静态扫描只能表达源码结构，不能证明运行时真实调用顺序。
- 浮动详情仍可能遮挡局部对象；当前通过保持画布宽度、移动控件和关闭后恢复焦点降低影响，没有实现自动把选中节点移到空白区。

## 渲染器大包告警修复（2026-07-31）

### 原因与方案

Source map 量化确认，原始 Renderer 构建的主要体积来自：

- `App.tsx` 单模块源码约 821KB。
- React DOM、Framer Motion、Phosphor Icons 和会话工作区静态进入主依赖图。
- 样式全部跟随 Renderer 主入口，最终形成 542.61KB 的单一 CSS 资产。
- 原始主 JavaScript 为 1,321.92KB，触发 Vite 默认 500KB 告警。

本次没有提高 `chunkSizeWarningLimit`，也没有关闭压缩体积报告，而是在 `apps/desktop/vite.config.ts` 使用 Rolldown 原生 `codeSplitting`：

- 目标分块尺寸为 360KB。
- React、Motion、图标和普通第三方依赖按运行时职责拆分。
- 会话、任务、设置/更新和 Renderer 代码按产品功能域拆分。
- CSS 跟随对应功能域分块，仍由生成后的相对 `modulepreload` 和 stylesheet 链接加载。
- `base: './'` 保持不变，确保所有分块在打包后的 `file://` 环境离线加载。

优点：

- Vite 默认阈值下不再出现大包告警，配置没有掩盖体积问题。
- React、Motion、图标、会话、任务和设置形成可识别的缓存及诊断边界。
- JavaScript 和 CSS 都有明确的小于 500KB 的构建证据。
- 不引入新的运行时依赖，也不依赖网络资源。

缺点与边界：

- 输出资产数量增加，启动时会读取更多本地文件；Electron 本地 `file://` 场景没有网络往返，但仍需保持打包健康检查。
- `App.tsx` 仍是大型源码模块；本次通过构建图切分消除交付告警，没有把整个组件物理拆成多个源码文件。
- 分组名称和路径规则依赖当前目录结构，未来移动会话、任务或设置模块时需要同步更新 Vite 配置。

### 构建结果

| 资产 | 修复前 | 修复后最大值 |
| --- | ---: | ---: |
| JavaScript | `index` 1,321.92KB | `renderer-runtime` 385.58KB |
| CSS | `index` 542.61KB | `renderer-runtime` 411.07KB |

最终 `pnpm build` 和 `pnpm package:mac:test` 均在 Vite 默认 500KB 阈值下退出码为 0，输出中不再出现 `Some chunks are larger than 500 kB`。

### 打包运行验收

- `Zeus Test` 从 `dist/test/mac-arm64/Zeus Test.app` 正常启动，窗口和辅助功能树没有白屏或框架错误覆盖层。
- 首屏项目列表正常显示 `tc-app-core`，证明 React、会话、图标和基础样式分块均能从 `file://` 加载。
- 点击“代码”后系统架构图正常显示 17 个节点、19 个关系组和 19 条原始关系。
- 图谱仍能显示 `tc-app-service-wms` 与 `WmsApplication`，证明拆包没有破坏代码页数据和交互。

## 当前系统架构图未达预期审查（待确认）

2026-07-31 对 `Zeus Test` 中 `tc-app-core` 的系统架构图重新做视觉与语义审查。数据污染已经消除，但当前图仍不能高效回答“系统如何分层、服务如何组织、模块依赖指向哪里”。

确认的问题：

- 17 个真实节点全部使用近似同权样式，Maven 聚合模块、业务服务模块和 Spring Boot 启动类没有形成清楚的层级。
- `tc-app-core`、`tc-app-api`、`tc-app-common`、`tc-app-sdk`、`tc-app-service` 被自动布局成一条横向链，容易被误读为运行调用顺序。
- 6 个服务模块和 6 个启动类分成两层散点，模块与启动入口需要用户自行配对。
- 16 条“包含”关系仍然使用连线表达，画布重复显示“包含 1.00”，掩盖了真正重要的 3 条模块依赖。
- 全部确定性结构关系都显示 `1.00`，没有为阅读提供额外价值。
- 图形只占画布中央小部分，节点字号、边标签和箭头在正常窗口下仍然偏小。
- 既有设计稿只规定了连续画布、三列示例和交互工具，没有定义 Maven 聚合、模块包含和依赖关系应如何映射为视觉层级，因此不是单纯的实现偏差，设计模型本身也需要补齐。

推荐方向：

- 把 `tc-app-core` 和 `tc-app-service` 从普通节点改为架构边界，不再为“包含”关系绘制连线。
- 系统架构图改为自上而下的逻辑分层：业务服务工作负载、共享契约与 SDK、公共基础模块。
- 每个业务服务使用一个组合节点，内部直接展示对应 Spring Boot 启动类，例如 `tc-app-service-wms / WmsApplication`，不再拆成两个散点。
- 主画布只保留真实模块依赖箭头；关系类型和置信度默认隐藏，选择边后再进入详情。
- 点击业务服务组合节点后钻取模块详情图，系统架构图负责建立全局心智模型，模块图负责展示类与源码依赖。
- 少量节点时隐藏小地图并把内容适配到主要可视区域，避免大量无意义留白。

优点：

- “包含”通过空间边界表达，“依赖”通过箭头表达，两种关系不再混淆。
- 6 个可运行服务及其入口能一眼配对，系统结构比 Maven 文件树更接近架构阅读习惯。
- 系统级与源码级细节分层，默认图不会再次退化为节点云。

缺点与成本：

- Graph View 需要新增容器/组合节点语义，不能只调整 SVG 坐标。
- 模块详情钻取需要把当前对象传给二级视图，现有视图选择器和返回路径需要同步改造。
- Maven 聚合关系、依赖关系和运行入口归属必须继续保留真实证据，不能为追求图形完整而臆造业务调用链。
