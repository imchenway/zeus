# Zeus 长任务无损升级设计

## 任务目标

解决长时间执行轮次阻止用户及时升级 Zeus 的问题。用户确认的目标不是“会话记录不丢”，而是：

> 正在执行的轮次不受计划内升级影响；旧界面退出后仍继续执行，新版界面自动重开并重新接管同一轮次的展示、审批与回答。

本任务先完成当前能力取证、产品口径、领域模型、架构决策、实施边界与真实验收矩阵。用户确认继续后，实施阶段在保留现有未提交改动的前提下完成了独立执行宿主、界面重连、退出选择、多运行时世代，以及应用内下载、校验、原子替换、自动重开和失败回滚。正式 Apple 分发产物与 Codex/BrowserHost 全场景仍按文末边界继续验收。

## 已确认口径

1. 应用内升级由用户主动点击“升级并重启”；允许自动检查、下载和校验，不在任务运行时静默重启界面。
2. 升级前已经开始的执行轮次继续绑定原运行时世代，禁止中断、迁移、重跑或重复产生副作用。
3. 新版界面立即生效；升级后新提交的执行轮次由新运行时世代承载。
4. 旧运行时世代不再接收新轮次，只完成存量轮次和待处理交互，排空后自动退出。
5. 多次连续升级允许多个排空世代并存，不使用会强制结束执行轮次的世代数量上限。
6. 新版与既有执行宿主不兼容时拒绝立即切换，保留已下载版本，待安全窗口自动安装。
7. 命令审批、文件审批、普通用户询问和其他待处理请求不阻止升级；新版重开后恢复同一请求，原超时继续计时。
8. 普通未发送草稿跨升级恢复；敏感回答不落盘，存在未提交敏感内容时要求提交、清空或取消升级。
9. 普通 `Command+Q` 与升级切换不是同一个领域事件。存在执行中轮次时，普通退出提供“退出界面并继续”“停止并退出”“取消”。
10. 计划内升级、界面重启和 Electron 界面进程崩溃属于无损保证；后台宿主崩溃、系统重启和断电进入恢复确认，禁止未知状态自动重跑。
11. 应用内升级提供完整自动重开体验；Homebrew 和 DMG 共享不中断执行宿主的能力，但不承诺由外部安装器自动重开。

## 实施前源码事实（设计基线）

### 更新能力

- `packages/local-server/src/index.ts` 的 `/api/release/check-update` 会读取真实发布清单。
- `/api/release/download-update` 与 `/api/release/install-update` 当前固定返回 `accepted: false`，下载和安装只是预留能力。
- `docs/release.md` 明确记录当前公开包未完成 Developer ID 签名和 Apple 公证，不启用静默自动安装。
- `apps/desktop/src/renderer/release/ReleaseUpdateDialog.tsx` 已具备检查中、发现更新、手动下载和安装准备等界面状态，但没有真实安装事务。

### 退出与执行生命周期

- `apps/desktop/src/main/main.ts` 的 `before-quit` 会关闭 BrowserHost、Local Server 和系统通知桥，然后调用 `app.exit`。
- `apps/desktop/src/main/localServerRuntime.ts` 的 `close()` 会执行 Local Server 最终关闭，并关闭应用级 Codex app-server manager。
- `packages/ai-runtime/src/codexAppServerManager.ts` 当前使用 `stdio://` 启动单个 Codex app-server；关闭时先发 `SIGTERM`，超时后发 `SIGKILL`。
- `packages/local-server/src/index.ts` 在 Zeus 正常退出时调用 Coordinator 的 `final` 关闭模式，而不是保留执行所有权的升级交接。
- 因此当前只能恢复持久化会话与 thread，不能保证退出后的活跃执行轮次仍在继续。

### 恢复能力

- Coordinator 启动时会 `thread/resume`、`thread/read` 并对账已绑定会话。
- 已完成、已中断和已失败的 provider turn 可以据真实 snapshot 收敛。
- 无法确认的 dispatch/active 窗口会进入 `recovery_required`；这符合避免重复副作用的安全边界，但不等于无损继续。
- 当前 Local Server、Coordinator、数据库写入和 app-server manager 都由 Electron Main 进程拥有，界面进程与执行宿主尚未分离。

## 问题定义

当前架构的根因不是缺少“重启后刷新会话”按钮，而是执行所有权绑定错误：

```text
Electron Main
  ├─ Renderer / BrowserHost
  ├─ Local Server / SQLite 写入
  ├─ Conversation Coordinator
  └─ 单个 stdio Codex app-server

Electron Main 退出
  └─ 上述所有执行边界同时关闭
```

`thread/resume` 能恢复一个已持久化 thread，但不能把已经被本机进程终止的工具、命令和流式执行恢复成“从未中断”。在未知窗口自动重发输入还会重复文件修改、命令或远程操作。

## 目标架构

### 边界

```text
Zeus 界面进程
  ├─ 窗口、菜单、草稿与升级确认
  ├─ BrowserHost 可视交互
  └─ 连接执行宿主，不直接拥有执行轮次

本机执行宿主
  ├─ 唯一业务数据库写入者
  ├─ 会话 Coordinator 与全局调度
  ├─ 升级事务与运行时世代注册表
  ├─ 待处理交互与事件持久化
  └─ 一个或多个运行时世代
       ├─ 当前世代：接收新轮次
       └─ 排空世代：只完成既有轮次

升级安装器
  ├─ 下载与摘要校验
  ├─ 签名、公证和兼容检查
  ├─ 请求执行宿主进入升级切换
  ├─ 替换应用并自动重开
  └─ 失败时回滚应用，不触碰执行轮次
```

### 执行宿主

执行宿主是唯一拥有以下责任的本机边界：

- SQLite 和持久化事件写入；
- conversation、turn、submission、pending request 的状态机；
- 项目级与全局并发调度；
- 运行时世代创建、租约、排空和回收；
- UI 连接租约、升级切换意图和普通退出意图；
- 新旧界面协议握手；
- 普通草稿恢复；敏感答案不持久化。

它不能依赖 Zeus 窗口存在，也不能位于升级时会被直接删除且无法继续读取的临时路径。

### 运行时世代

每个世代至少拥有：

- 稳定世代 ID；
- Zeus 应用版本、Codex binary version、协议版本和二进制摘要；
- 不可变运行目录；
- 进程 PID、端点与健康状态；
- `active`、`draining`、`stopped` 或 `recovery_required` 状态；
- 绑定的 conversation、turn 与 pending request 租约；
- 创建、最后活动、排空开始和结束时间。

执行轮次开始后固定绑定世代。升级只切换“新轮次默认世代”，不迁移已开始的执行轮次。

### 单一写入原则

不能让新旧 Local Server 同时直接写同一个 `zeus.db`。多世代只适用于 Codex 执行引擎；业务状态仍由一个执行宿主串行持久化。否则会出现：

- SQL.js 内存快照互相覆盖；
- submission 与 turn 状态倒退；
- pending request 被两个进程同时响应；
- 同一项目并发限制失真；
- 升级失败无法判断哪个进程拥有最终事实。

## 状态模型

### 升级事务

```text
discovered
  → downloading
  → verified
  → compatibility_checked
  → prepared
  → ui_handoff
  → installing
  → relaunching
  → reattached
  → completed
```

安全分支：

- `compatibility_checked → waiting_for_drain`：新版无法连接当前执行宿主；
- 任意安装前阶段 `→ cancelled`：用户取消；
- `installing / relaunching → rollback`：替换或启动失败；
- `rollback → reattached`：旧界面恢复连接；
- 后台宿主失联 `→ recovery_required`：禁止继续宣称无损。

### 运行时世代

```text
starting → active → draining → stopped
    │         │         │
    └─────────┴─────────┴→ recovery_required
```

- `active`：当前新轮次默认世代。
- `draining`：不接收新轮次，但继续执行、等待交互和发送事件。
- `stopped`：没有任何活跃或等待租约，可以回收。
- `recovery_required`：无法证明进程与轮次状态，需要用户确认。

## 升级事务顺序

1. 检查 Release manifest，选择当前架构产物。
2. 下载到本机升级暂存目录，不覆盖当前 App。
3. 验证 SHA-256、Developer ID 签名、公证票据、bundle id、架构、最低系统版本和目标版本。
4. 让执行宿主检查：
   - 新界面协议是否兼容当前执行宿主；
   - 新运行时是否可以登记为当前世代；
   - 新版运行目录是否已经完整物化；
   - 是否存在未提交敏感回答；
   - 是否存在未保存但可恢复的普通草稿。
5. 创建持久化升级事务，冻结重复安装请求。
6. 将当前世代切换为 `draining`，登记新世代为 `active`；此时旧轮次继续运行，新轮次只能进入新世代。
7. 保存窗口和普通草稿，通知界面进入升级切换。
8. 退出旧界面进程，但不关闭执行宿主或任何仍有租约的运行时世代。
9. 安装器原子替换 App；失败时恢复旧 App。
10. 启动新版界面，并通过升级事务 ID、宿主实例 ID 和协议版本重连。
11. 新界面恢复会话、流式状态、pending request、普通草稿和窗口状态。
12. 宿主确认新界面已接管后将升级事务标为完成。
13. 每个排空世代的最后一个租约结束后，宿主正常关闭进程并回收对应不可变运行目录。

## 交互请求和草稿

### 待处理请求

- 命令、文件、权限、普通用户询问和 MCP 请求由执行宿主持久化。
- 升级切换只断开视图订阅，不改变请求身份、状态或原截止时间。
- 新界面必须用宿主实例 ID、世代 ID、request ID 和 payload identity 重新绑定。
- 请求在界面离线期间自动解决或超时时，新界面只显示最终真实状态，不重新创建请求。

### 草稿

- 普通 composer 文本、非敏感选项和已物化附件引用可以进入本机恢复草稿。
- 密钥、token 和标记为 secret 的回答不得进入升级事务、日志或恢复文件。
- 检测到未提交敏感回答时不开始退出；用户只能提交、清空或取消升级。

## 普通退出语义

普通退出不能借用升级切换：

- 没有活跃或等待轮次：正常退出界面和执行宿主。
- 存在活跃或等待轮次：
  - “退出界面，任务继续运行”：界面退出，执行宿主按工作租约存活；
  - “停止任务并退出”：显式 interrupt，等待真实终态后关闭；
  - “取消”：不退出。
- 下次打开 Zeus 时连接仍存活的宿主；若宿主已经退出，则启动当前版本宿主并按持久化事实恢复。

## 连续升级与资源回收

- 不按数量强杀排空世代。
- 同一世代没有执行中、等待交互、未落库事件或未完成变更集写入时才可停止。
- 不可变运行目录只在进程退出且无租约后删除。
- 设置页展示排空世代、关联轮次数、运行时长、CPU/内存和安全风险。
- 安全更新可以警告旧世代风险，但不能自动终止；用户可显式停止关联轮次。

## 兼容策略

### 界面与执行宿主

- 执行宿主协议必须显式版本化并进行双向能力握手。
- 新界面至少兼容当前正式版执行宿主；发布门禁必须用上一正式版宿主连接候选新版界面。
- 不兼容时在旧界面内停止切换，升级事务进入 `waiting_for_drain`。
- 新界面不能用“尝试连接失败后新建数据库宿主”作为兜底，以免形成双写。

### 执行宿主与运行时世代

- 执行宿主以 adapter 能力表路由，不用应用版本字符串猜测协议。
- 旧世代只处理已经绑定的 turn 和 request。
- 新世代不接管旧世代 request ID，也不把旧活跃 submission 再次 dispatch。
- 若世代失联，关联轮次进入 `recovery_required`，不能自动迁移。

## BrowserHost 边界

当前 BrowserHost 位于 Electron Main。无损升级后需要明确处理升级窗口中的浏览器工具调用：

- 可视浏览器继续属于界面进程；
- 执行宿主持有可重连的 Browser Automation broker；
- 界面断开期间，新浏览器动作进入短暂等待，不返回伪失败；
- 新界面重连后恢复 broker 租约和会话浏览器状态；
- 如果等待超过明确上限，执行轮次进入真实待恢复状态，不自动重放可能产生副作用的动作。

这条链路必须做真实浏览器场景验证，不能只用 Local Server 静态状态替代。

## 应用内、Homebrew 与 DMG

### 应用内升级

完整保证：

- 自动检查、下载和校验；
- 用户主动确认；
- 执行宿主世代切换；
- App 替换、失败回滚和自动重开；
- 新界面自动重连。

启用真实自动安装的前置条件是 Developer ID 签名和 Apple 公证。当前 ad-hoc 发行只能继续提供手动升级，不能伪装成完整链路。

### Homebrew 和 DMG

- 执行宿主位于可跨 App 替换存活的稳定位置。
- 外部安装器退出界面时不能终止执行宿主。
- 用户打开新版后自动发现并重连宿主。
- 外部安装器不承诺自动重开。
- 如果外部替换导致新界面不兼容，旧宿主继续执行，界面显示明确恢复说明；不得启动第二个数据库写入者。

## 安全要求

- 宿主端点只允许本机连接，并使用权限为 `0600` 的随机凭据或等价本机身份校验。
- rendezvous 文件不得包含 Telegram token、API Key 或其他业务密钥。
- 运行目录必须验证真实路径、所有者、权限、二进制摘要和签名，拒绝符号链接替换。
- 升级产物先写临时文件，校验通过后原子移动。
- 安装失败回滚只回滚 App，不回滚已经发生的执行事件或文件修改。
- 新旧世代共享统一并发和项目写入冲突控制，不能因跨版本绕过权限。
- 宿主日志记录升级事务 ID、世代 ID、PID、状态变更和错误分类，不记录 secret 回答正文。

## 建议实施顺序

### 宿主事实与只读状态

1. 增加宿主、运行时世代和升级事务只读模型。
2. 暴露真实活跃/等待轮次计数和当前世代。
3. 在设置页显示“当前不支持无损安装”，不改变退出行为。
4. 验证现有正式包行为没有变化。

优点：先建立可观测事实和迁移基础。
缺点：用户体验尚未改善。

### 执行宿主独立

1. 将 Local Server、SQLite 唯一写入和 Coordinator 移出界面生命周期。
2. 实现本机单实例宿主、rendezvous、心跳和新界面重连。
3. 普通退出增加三选一语义。
4. 验证关闭窗口、普通退出继续和 Electron 界面进程崩溃。

优点：长任务第一次真正不依赖界面。
缺点：仍只有一个运行时世代，升级后新轮次暂时不能使用新 Runtime。

### 世代路由

1. 物化不可变运行目录。
2. turn/submission 绑定世代。
3. 新世代激活、旧世代排空和多世代资源展示。
4. pending request 与自动解决计时跨界面恢复。

优点：满足新旧任务分流。
缺点：调度、恢复和磁盘生命周期复杂度上升。

### 应用内安装

1. 接入下载、签名、公证、摘要和系统版本校验。
2. 实现安装 helper、App 替换、回滚和自动重开。
3. 实现新版界面兼容握手和失败时 `waiting_for_drain`。
4. 补齐 Release notes、manifest 和发布门禁。

优点：形成完整用户闭环。
缺点：依赖真实 Apple 分发凭据，无法用 ad-hoc 产物宣称完成。

## 真实验收矩阵

所有场景必须使用仓库生成的 `dist/mac-arm64/Zeus.app` 或任务专用正式包副本，不使用 `/Applications/Zeus.app` 代替开发验收。

| 场景 | 必须观察到 | 禁止结果 |
| --- | --- | --- |
| 长模型轮次正在流式输出时升级 | 旧世代持续产生事件；新版重开后同一 thread/turn 继续收敛 | 新 turn、重发用户消息、`recovery_required` |
| 长命令正在执行时升级 | 原 PID/进程组继续；输出序列连续；只产生一次副作用 | 命令重启、双 PID、输出断裂后伪完成 |
| 文件修改中升级 | 旧世代完成原工具调用；变更集仍归属原 turn | 新世代重复应用补丁 |
| 等待命令或文件审批 | 新版显示同一 request identity；回答只提交一次 | 请求重建、默认允许、自动取消 |
| 等待普通用户询问 | 原截止时间继续；新版恢复同一问题 | 超时重置、重复问题 |
| 正在填写普通草稿 | 新版恢复草稿和附件引用 | 草稿丢失或自动发送 |
| 正在填写敏感回答 | 升级被阻止并要求提交或清空 | secret 落盘或日志泄漏 |
| 浏览器工具调用跨越重启 | broker 等待并在新界面重连后继续 | 工具伪失败或重复点击 |
| 两次连续升级 | 两个排空世代各自完成原轮次，新轮次只进最新世代 | 因世代上限强杀 |
| 新版协议不兼容 | 保留下载并等待排空，旧任务继续 | 强行切换或双数据库写入者 |
| 安装失败 | 旧 App 回滚并重新连接原宿主 | 回滚执行数据、停止旧轮次 |
| 普通退出选择继续 | 界面退出，宿主和轮次继续 | 被当作 final quit |
| 普通退出选择停止 | 明确 interrupt 并观察真实终态后退出 | 直接 SIGKILL |
| Homebrew/DMG 替换 | 旧宿主继续，新版手动打开后重连 | 外部替换清理宿主 |
| 后台宿主崩溃 | 标记恢复确认，不自动重发 | 宣称仍在执行或自动重跑 |

## 交付门禁

实现阶段每个阶段都必须至少执行：

1. `pnpm lint`
2. `pnpm typecheck`
3. `pnpm build`
4. `pnpm package:mac`
5. 正式包真实启动健康检查
6. 对应阶段的真实升级场景

静态检查、类型检查和构建成功不能替代正式包的进程、PID、thread/turn、请求身份、数据库和副作用对账。

本项目不新增或恢复单元测试、组件测试、DOM/CSS 契约测试及其发布门禁。真实验收脚本只负责启动正式包、采集进程与持久化事实、执行升级切换并输出可复现证据。

## 风险与回滚

### 主要风险

- 新旧进程同时写数据库；
- 升级时丢失 pending request transport authority；
- 旧运行目录被 App 替换删除；
- BrowserHost 断开导致工具误失败；
- 新界面不兼容旧宿主；
- 安装器在未签名、未公证时绕过 Gatekeeper；
- 自动恢复重复执行文件、命令或远程副作用。

### 回滚原则

- 在执行宿主提取完成前，不启用自动安装入口。
- 每个阶段保留旧的单进程启动路径作为显式开发回退，但正式无损模式不能静默退回双写。
- 安装失败只回滚 App bundle；执行宿主和运行时世代保持原状。
- 世代失联只进入恢复确认，不跨世代自动 dispatch。
- 协议不兼容时留在旧界面或等待排空，不启动新的数据库拥有者。

## 实现进展（2026-07-31）

### 已实现

- 新增独立执行宿主入口。Electron Main 启动或发现宿主后只持有界面租约，不再直接拥有 Local Server、SQLite 和 Codex app-server。
- 宿主通过权限为 `0600` 的 rendezvous 文件发布 PID、回环端点、协议版本和随机控制凭据；文件所有者、权限、协议和回环 URL 均需通过复验。
- 宿主进程使用 Electron Node 模式脱离 Main。界面心跳失效后，有活跃工作时继续存活；无活跃工作时经过空闲宽限再自行回收。
- Local Server 新增真实宿主状态，统计活跃 Codex 轮次、待处理交互、其他 Runtime、命令运行和当前 transport generation。
- BrowserHost 增加本机临时桥，执行宿主持有可重连代理；界面离线时调用等待新租约，不立即返回伪失败。
- 普通退出在存在活跃工作时提供“退出界面，任务继续运行”“停止任务并退出”“取消”。无法读取宿主状态时默认保护后台执行。
- 更新弹窗展示宿主是否独立、活跃轮次、待处理交互和其他 Runtime 数量；未签名、未公证产物仍只允许手动安装。
- Codex 运行时在进入执行宿主前会复制到用户数据目录的内容地址路径；宿主复验真实路径、所有者、权限和 SHA-256，App bundle 被替换后旧二进制仍可用。
- 新增多世代 Codex 管理器。新线程和已经空闲的旧线程进入当前世代；正在执行或等待交互的线程固定在原世代，完成后旧进程自然排空。
- 协调器不再把“不是最新 generation”直接视为失效，而是向多世代管理器确认该 generation 是否仍存活；旧世代的审批和普通询问仍可按原 request identity 回答。
- 新界面登记 BrowserHost 租约时同时提交已物化运行时描述；宿主先激活新世代，再完成界面租约连接。更新弹窗可展示当前世代总数和排空世代数。
- Release manifest 增加执行宿主协议版本并进行严格解析。只有产物已签名、已公证且协议兼容时才启用自动安装；协议不兼容或字段非法时继续 fail-closed。
- packaged App 的下载与安装由 Electron Main 的受限 IPC 承担，不再让 Renderer 直接执行文件系统替换。下载采用临时文件、大小上限、SHA-256 和原子改名，生产地址只允许 GitHub Release 及其受信任产物域名。
- 安装准备会挂载 DMG、复制目标 App、执行严格 codesign 校验；生产模式额外校验目标版本、Gatekeeper 和公证票据。仅任务专用 `Zeus Test.app` 且显式测试开关允许回环清单和 ad-hoc 产物。
- 脱离 Main 的安装辅助进程等待旧 Main 退出，原子交换当前 App 与暂存 App，启动新版并等待其以预期应用版本重新连接原执行宿主；新版不能启动或不能回连时先确认新版进程已终止，再恢复旧 App，并等待新的旧版界面租约重新连接后才提交回滚完成。
- 升级切换真实使用 `upgrade_handoff`：旧 Main 只释放界面租约和 BrowserHost，不关闭执行宿主。旧 App 备份在旧宿主仍存活时保留，最终退出并关闭宿主后由新版 Main 按受控名称清理。

- Local Server 的 `/api/release/download-update` 与 `/api/release/install-update` 继续作为浏览器/开发环境的 fail-closed 入口；packaged App 已改由受信任 Main IPC 完成真实下载和安装。

- 更新弹窗尚未在真实 Electron 窗口中完成截图级视觉验收。

## 当前结论

计划内无损升级的代码闭环已经实现：执行宿主独立、多世代路由、下载校验、兼容门禁、敏感回答门禁、原子替换、自动重开、版本握手、重新连接、失败回滚和旧包延迟清理都已进入真实 packaged App。任务专用 App 证明：界面从 0.1.2 的 PID 11191 切换为 0.1.3 的 PID 11436 时，本机宿主和真实长 Runtime 保持原 PID，运行中的 session 未被重建，宿主后续更新检查也已使用新 UI 的 0.1.3 版本事实；隔离失败场景证明旧 App 能恢复并重新打开。

这证明计划内升级主链路已完成，但不证明正式发布已经上线：真实 Apple 签名与公证产物、Codex 长轮次/审批/普通询问、BrowserHost 跨切换、连续多次升级和机器级异常仍是明确的外部或扩展验收项。整个过程没有操作 `/Applications/Zeus.app`，也没有退出用户正在运行的仓库产物。
