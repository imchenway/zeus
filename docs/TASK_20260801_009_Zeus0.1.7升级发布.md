# Zeus 0.1.7 升级发布

## 任务目标

把 Fast/service-tier 全链路作为新的不可变公开稳定版 `v0.1.7` 发布，完成源码版本、完整 Release notes、本地发布门禁、仓库制品、GitHub Release、更新清单和 Homebrew Tap 的一致交付。

## 已确认口径

- 目标版本：`v0.1.7`。
- 发布类型：公开稳定版，不覆盖已经公开的 `v0.1.6`。
- 发布范围：任务推送、项目对话、任务会话首轮、已有会话后续轮次、项目档位偏好、provider 实际档位展示，以及 Runtime、Local Server、存储和 Renderer 的 `serviceTier` 三态链路。
- 已授权动作：用户明确确认重新升级发布，因此允许创建发布分支、提交、推送、合入 `main`、创建不可变标签、GitHub Release 和 Homebrew Tap。
- 发布分支：`zeus/release-0.1.7`。
- 不执行强推、历史改写或同版本二进制替换。

## 领域与发布边界

- “公开稳定版”继续以不可变 Git 标签、GitHub Release、更新清单和 Homebrew Cask 的一致事实为完成口径。
- “实用发布”继续表示 ad-hoc 签名且未完成 Apple 公证，只支持用户确认后的手动安装。
- “跟随 Codex”省略 `serviceTier`，“标准”显式发送 `null`，Fast 发送模型目录返回的真实档位 ID。
- 用户选择、项目档位偏好和 Codex 实际生效档位是三个不同事实，界面不能用前两者冒充实际状态。
- Fast 不改变模型身份或推理强度；模型目录没有对应档位时不能伪造 Fast。
- 正常退出 Zeus 仍会中断活动执行轮次，本次发布不宣称无损后台升级已经实现。

该方案的优点是让 Zeus 与 Codex app-server 的真实服务档位协议一致，并在所有会话入口保持统一选择；缺点是可用档位依赖运行时模型目录，provider 未返回实际状态时只能显示“未同步”，且当前 ad-hoc 包仍不能提供 Apple 已认证的自动安装体验。

## 发布步骤

1. 同步根包与桌面包版本为 `0.1.7`，完成用户向 Release notes 与发布任务记录。
2. 执行 `pnpm verify:release`，生成真实 App、DMG、manifest 和 Homebrew Cask。
3. 只使用仓库生成的 `dist/mac-arm64/Zeus.app` 做必要的版本、签名、健康与运行边界验收。
4. 核对 DMG、manifest、Cask、版本、大小、摘要和 ad-hoc 签名事实。
5. 提交并推送发布分支，通过远端 CI 后合入 `main`。
6. 创建 annotated tag `v0.1.7`，发布 GitHub Release 的 DMG 与 manifest，并同步 Homebrew Tap。
7. 反查 Release、公开资产、摘要、Release notes、manifest、tag、main 和 Tap，把最终事实写回本任务文档与 `docs/release.md`。
