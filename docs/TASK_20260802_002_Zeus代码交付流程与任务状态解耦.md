# Zeus 代码交付流程与任务状态解耦

## 任务目标

代码交付中的提交、推送、远端校验、worktree 回收和目标分支合入应由真实 Git 生命周期驱动，不应只在任务切换到“已完成”或“已取消”时出现。

用户确认的行为：

1. 只要任务存在开发分支，任何任务管理状态都可以打开代码交付。
2. 开发中的分支可以从代码交付进入完整提交审查，完成提交、推送、校验和回收。
3. 准备完成后返回代码交付，继续合入来源分支或主工作区当前分支。
4. 已交付和已放弃分支继续展示真实结果，不泄漏内部工作区标识。

## 现场根因

ZEUS-000013 的真实分支 `zeus/ZEUS-000013-task-01` 已经干净并与远端提交一致，但 TaskWorkspace 仍是 `ready`，worktree 也尚未由 Zeus 回收。

原代码交付弹窗存在两套不一致门禁：

- 选中逻辑在没有 `reclaimed` 分支时回退到第一个 `ready` 工作区。
- 下拉选项只包含 `reclaimed / merged`，导致选中值没有标签，通用 Select 回退显示 `task_workspace_*` 内部 ID。
- 主按钮仍允许点击；服务端随后以 `ZEUS_TASK_BRANCH_NOT_REMOTE_BACKED` 拒绝 `ready` 状态并展示英文错误。

这不是 Git 合并冲突，而是提交准备入口只绑定任务终态、代码交付入口又提前开放造成的流程断裂。

## 领域决策

### 任务管理状态不是 Git 权限

任务管理状态只表达工作推进阶段。它不授权也不禁止提交、推送、回收或合入。Git 操作仍由活动会话、工作区变更、远端提交和 TaskWorkspace 生命周期执行真实门禁。

### 代码交付按分支状态给出下一步

| 分支状态 | 代码交付展示 | 主操作 |
| --- | --- | --- |
| `ready` | 待准备、真实分支名、准备步骤 | 审查并准备交付 |
| `failed` | 上次错误、真实分支名、恢复步骤 | 重新审查并准备交付 |
| `reclaimed` | 已推送并回收、目标与方式 | 合入并推送 |
| `merged` | 已交付记录 | 已交付；其他目标存在时允许再次交付 |
| `discarded` | 已放弃事实 | 无写操作 |

TaskWorkspace ID 是内部关联键，不是用户领域中的任务分支名称。

## 方案取舍

采用“代码交付编排已有提交审查弹窗”的方案：

- 优点：复用现有变更选择、双栏差异、活动会话停止、提交、推送和回收安全校验；任务状态不发生隐式变化。
- 优点：准备完成或用户取消后回到同一代码交付上下文，继续读取服务端真实状态。
- 缺点：准备与合入仍是两个清晰步骤，不能压缩成一次无审查的自动写操作。

未采用直接在代码交付按钮中自动推送并回收：

- 优点：点击次数少。
- 缺点：可能在用户没有审查变更时提交，或静默删除仍可写的 worktree，不符合显式 Git 写操作边界。

未采用只禁用合入按钮并提示“先完成任务”：

- 优点：改动最小。
- 缺点：继续错误耦合任务管理状态，无法处理任务进行中或手工推送后的真实分支。

## 实现范围

- `TaskGitMergeModal` 列出全部任务开发线，选项始终使用真实 `branchName` 和生命周期标签。
- `ready / failed` 分支的主操作打开 `TaskGitReviewModal` 的交付准备模式。
- 交付准备模式完成推送、远端校验和 worktree 回收后关闭，不修改任务管理状态。
- 应用壳关闭交付准备弹窗后恢复代码交付弹窗，并刷新任务工作区与事件上下文。
- 合入竞态错误在中文界面映射为可操作说明；服务端真实状态门禁保持不变。
