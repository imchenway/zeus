# Zeus 升级发布一键能力审计

## 当前阶段

截至 2026-08-02，Zeus 已形成“发布内容草稿 → 发布候选准备 → 本地发布门禁 → 公开发布与回验”四阶段受控脚本，并已用这套链路完成 `v0.1.10` 公开稳定发布。各阶段都可由 Zeus 命令管理单独配置和执行；Release notes 审阅、候选提交进入 `main` 与最终公开确认仍保留人工责任边界。

## 术语边界

- 本文的“发布”指把新版本形成不可变标签、GitHub Release、更新清单和 Homebrew Cask 的公开稳定版流程。
- 用户侧“升级”目前仍是 Homebrew 或 DMG 手动安装；当前 ad-hoc、未公证制品不能启用静默应用内自动安装。

## 当前已自动化范围

- `pnpm verify:release` 串联发布前检查、验收矩阵、AI CLI 探针、macOS 打包、Homebrew Cask 和公开更新清单生成，并继续校验包内 Electron、Renderer、Main、Preload 与 Codex Runtime 完整性。
- `pnpm release:notes:draft` 基于 Git 范围、任务文档和版本事实生成 Release notes 草稿及证据，不修改仓库。
- `pnpm release:prepare` 在显式写入开关下同步根包、桌面包版本和已审阅 Release notes。
- `pnpm release:gate` 执行同一候选提交的完整本地门禁，输出可供公开发布阶段校验的摘要与快照。
- `pnpm release:publish` 默认只做只读前置检查；显式远程开关与精确确认值齐备后，创建不可变标签、触发 Release Workflow，并回下载公开资产完成一致性对账。
- `pnpm release:commands:sync` 依据仓库声明向指定 Zeus 项目幂等同步上述四条命令，同时保留项目权限与逐次高风险确认。
- `.github/workflows/release.yml` 支持手动输入既有标签；在 `publish_release=true` 时运行完整门禁、创建或幂等核对 GitHub Release，并把生成的 Cask 同步到 `imchenway/homebrew-tap`。
- Workflow 对标签与包版本不一致、Release notes 缺失、同版本 DMG 不可变、Tap token 缺失等情况执行 fail-closed。

## 分阶段保留的责任边界

- 计算并确认下一个版本号。
- 审阅 AI 生成的 Release notes，并确认发布范围、用户影响和已知限制。
- 创建发布分支、提交、推送、PR、等待 CI 和合入 `main`。
- 对存在桌面功能变化的版本完成对应真实交互验收。
- 自动写回任务文档与 `docs/release.md` 的最终事实。

因此，当前能力是“每个阶段一条命令、阶段之间显式确认”，不是从任意脏工作区直接无人值守发布。优点是机械步骤已收口且失败可幂等续跑；缺点是仍需维护者对内容、候选提交和桌面交互证据负责。

## 已实施方案与取舍

当前采用四阶段受控发布入口，把发布内容生成、候选准备、本地门禁、标签、Workflow 触发和发布后反查分开执行，并通过候选提交、门禁摘要和精确确认值约束阶段衔接。

优点：入口统一、步骤不易遗漏、失败可定位、同版本不可变和凭据检查可以集中执行。

缺点：脚本将拥有提交、推送、PR 合入、标签、Release 和 Tap 等高影响权限；Release notes 与真实桌面交互不适合无人工判断地自动生成或跳过；失败恢复和幂等设计必须覆盖每个远端阶段。

当前落实为“每阶段单入口、阶段间确认”的受控流程：脚本自动完成可重复机械步骤，在发布范围确认、Release notes 确认和最终公开发布前保留明确门禁。这样既能直接配置到 Zeus 命令管理，也不会把不可逆远端写入伪装成无人值守操作。

## 发布内容生成原则

发布脚本不应在 CI 中临时编造 Release notes。推荐把内容准备分为“事实采集、用户向整理、确定性发布”三个阶段：

1. 脚本以最近公开标签到候选提交的 Git 变更、已完成任务文档和当前版本配置为输入，生成发布内容草稿。
2. 草稿中的制品大小、SHA-256、签名、公证、最低系统版本和验证结果必须在真实构建完成后从产物与命令结果回填，不允许由文字推断。
3. 用户向正文收敛为 `docs/releases/v<version>.md`，固定包含主要新增或修复、交互变化、升级方式、系统要求、已知限制和发布验证。
4. 发布前展示该文件和实际资产清单；确认后把它与版本变更一起提交，使目标标签内包含最终 Release notes。
5. GitHub Release 只读取标签内的该文件，不在远端重新生成；公开后再逐字节反查 Release 正文、DMG、manifest 和 Homebrew Cask。

不推荐仅根据 commit subject 自动拼接 Release notes。其优点是实现简单，但提交信息面向开发者，无法可靠覆盖用户影响、升级方式、已知限制和真实验证边界。Zeus 已有任务文档和完整发布记录，应以任务事实与实际产物为主，Git 提交只用于确定变更范围。

## 可配置的发布内容草稿命令

已新增 `pnpm release:notes:draft`，它只生成候选 Release notes 和对应证据，不修改项目文件、版本、Git 历史或远端发布状态。

建议在 Zeus 命令管理中创建项目命令：

- 名称：`zeus-release-notes`
- 标题：`生成 Zeus 发布内容草稿`
- 命令：`pnpm release:notes:draft`
- 超时：`1800` 秒
- 启用命令：是
- 允许 Telegram：否
- Git 写入：否
- 项目外写入：是，草稿、证据和隔离的 Codex 临时目录位于项目外的受控命令产物或系统临时目录。
- 外部服务写入：是，因为候选变更会交给本机 Codex CLI 分析。

声明式参数：

| 环境变量 | 类型 | 必填 | 默认值 | 用途 |
| --- | --- | --- | --- | --- |
| `RELEASE_VERSION` | string | 是 | 无 | 目标稳定版本，例如 `0.1.10` |
| `BASE_TAG` | string | 否 | 最新稳定标签 | 发布内容的 Git 基线，例如 `v0.1.9` |
| `INCLUDE_WORKTREE` | boolean | 否 | `true` | 是否把未提交工作区线索交给 Codex |
| `RELEASE_CONTEXT` | string | 否 | 无 | 本次发布的补充边界，最多 2000 字符 |
| `RELEASE_MODEL` | string | 否 | Codex 默认模型 | 特殊情况下覆盖生成模型 |

运行前需要在终端完成 `codex login`。脚本只在权限为 `0700` 的临时目录中复用现有登录信息，不读取用户 Codex 配置，不接受或输出 API Key。Codex 以 `read-only` 沙箱和临时会话运行；命令结束后，草稿和证据通过 `ZEUS_ARTIFACT_FILE` 注册为 Zeus 命令产物。

优点：输入范围由 Git 标签和候选提交锁定，草稿与证据成对产出，并对标题、升级命令、DMG 名称、必要章节和待验证边界做确定性检查。

缺点：仍会消耗 Codex 配额并将候选变更发送给外部 AI 服务；草稿只是候选内容，仍需人工审阅；未提交工作区会降低范围的可复现性，正式发布准备时建议关闭 `INCLUDE_WORKTREE` 并基于已确定的候选提交重新生成。

## 可配置的本地发布门禁命令

第二阶段新增 `pnpm release:gate`，把现有 `pnpm verify:release` 收口为 Zeus 命令产物。它要求目标版本高于最新稳定标签、根包与桌面包版本一致、已审阅 Release notes 存在，且默认拒绝脏工作区和已存在标签。

建议在 Zeus 命令管理中再创建一条项目命令：

- 名称：`zeus-release-gate`
- 标题：`执行 Zeus 本地发布门禁`
- 命令：`pnpm release:gate`
- 超时：`3600` 秒
- 启用命令：是
- 允许 Telegram：否
- Git 写入：否
- 项目外写入：是，门禁摘要与快照会写入 Zeus 提供的本次命令产物目录。
- 外部服务写入：否。

声明式参数：

| 环境变量 | 类型 | 必填 | 默认值 | 用途 |
| --- | --- | --- | --- | --- |
| `EXPECTED_VERSION` | string | 是 | 无 | 待验证的新稳定版本 |
| `ALLOW_DIRTY_WORKTREE` | boolean | 否 | `false` | 仅用于本地非正式试跑；正式候选不应开启 |
| `REQUIRE_APPLE_DISTRIBUTION` | boolean | 否 | `false` | 开启后强制 Developer ID 签名与 Apple 公证 |
| `REGISTER_DMG_ARTIFACT` | boolean | 否 | `false` | 是否把大体积 DMG 也注册到 Zeus 产物列表 |

门禁通过后会生成门禁摘要，并快照 Release notes、manifest 和 Homebrew Cask；DMG 默认只保留在 `dist/`，避免命令产物无意复制数百 MB 文件。脚本会额外执行 `hdiutil verify`，并逐项核对 DMG 字节数、SHA-256、manifest 和生成的 Cask。

该命令会在项目的 `dist/` 与 `.tmp/` 生成或刷新本地构建产物，但不修改受 Git 跟踪的源码，不创建提交、标签、GitHub Release 或 Tap 变更。它也不能代替真实桌面交互验收；摘要会继续把这些项列为公开发布前的待完成边界。

当前仓库版本 `0.1.9` 已有同名公开标签，因此本次仅验证静态语法和“已发布版本不可重新打包”的前置拒绝，没有为 `0.1.9` 重新生成正式制品。`run-release-gate.mjs` 的 Node 语法检查、定向 ESLint 和 Prettier 已通过，新增命令后的全量 `pnpm lint`、`pnpm typecheck`、`pnpm build` 与 `git diff --check` 也已通过。完整运行必须等待根包、桌面包和 Release notes 都进入新的候选版本。

## 可配置的发布候选准备命令

第三阶段新增 `pnpm release:prepare`，把已审阅草稿收敛为仓库 Release notes，并同步根包与桌面包版本。它默认仅生成计划；只有显式设置 `APPLY_CHANGES=true` 才会写入受 Git 跟踪的文件。

建议在 Zeus 命令管理中创建项目命令：

- 名称：`zeus-release-prepare`
- 标题：`准备 Zeus 发布候选`
- 命令：`pnpm release:prepare`
- 超时：`300` 秒
- 启用命令：是
- 允许 Telegram：否
- Git 写入：否，脚本不执行 `git add` 或其他 Git 写命令。
- 项目外写入：是，候选计划与审阅快照会写入 Zeus 本次命令产物目录。
- 外部服务写入：否。

声明式参数：

| 环境变量 | 类型 | 必填 | 默认值 | 用途 |
| --- | --- | --- | --- | --- |
| `RELEASE_VERSION` | string | 是 | 无 | 新的稳定版本 |
| `RELEASE_NOTES_FILE` | string | 是 | 无 | 上一阶段产出且已人工审阅的草稿绝对路径 |
| `APPLY_CHANGES` | boolean | 否 | `false` | 是否真正写入两个包版本和 `docs/releases/v<version>.md` |

写入模式不提供“允许脏工作区”开关；如果发现任何既有变更就直接拒绝，避免版本准备夹带其他工作。写入过程只允许改变 `package.json`、`apps/desktop/package.json` 和目标 Release notes；Prettier 或 Git 空白检查失败时会恢复写入前内容。

候选准备完成后不会自动执行提交。用户必须审阅 Git 变更，在形成可复现的候选提交后，才能执行 `pnpm release:gate`。这个边界避免“修改版本”和“对外发布”在一次无人工审阅的脚本中连续发生。

## Zeus 命令管理声明与同步

为避免在命令管理界面逐字段手抄，现已新增声明文件 `scripts/zeus-release-command-definitions.json` 和同步入口 `pnpm release:commands:sync`。声明文件完整记录四条项目命令的名称、别名、说明、参数、超时、启停状态和三类风险；同步脚本复用 Zeus 共享层的命令定义校验器，再通过本机命令管理 API 做差异预览和幂等写入。

同步脚本只接受带端口的 loopback HTTP 地址，要求显式提供 API token 和项目 ID，并回读项目的真实 `localPath`；只有目标项目目录与当前仓库物理路径一致时才继续。API token 不会写入计划、日志或声明文件。脚本只创建或更新这四条项目命令，不创建全局命令、不删除其他命令、不修改项目的 Shell 或 Git 写入权限；全局或同项目名称／别名冲突会在写入前阻断。

首次使用先只验证声明文件：

```bash
VALIDATE_ONLY=true pnpm release:commands:sync
```

拿到当前 Zeus 执行宿主的本机 API 地址、token 和 Zeus 项目 ID 后，先生成只读差异计划：

```bash
ZEUS_API_BASE_URL=http://127.0.0.1:<port> \
ZEUS_API_TOKEN=<token> \
ZEUS_PROJECT_ID=<project-id> \
pnpm release:commands:sync
```

审阅计划后，真实同步还必须同时开启写入并提供绑定项目 ID 的确认值：

```bash
ZEUS_API_BASE_URL=http://127.0.0.1:<port> \
ZEUS_API_TOKEN=<token> \
ZEUS_PROJECT_ID=<project-id> \
APPLY_COMMANDS=true \
SYNC_CONFIRMATION=SYNC_RELEASE_COMMANDS_<project-id> \
pnpm release:commands:sync
```

该同步方式的优点是声明可审阅、字段不会遗漏、重复执行只产生差异；缺点是本机 API token 仍必须由操作者在运行时显式提供，且网络中断可能造成部分命令先完成写入。脚本不做破坏性回滚，而是依赖回读和幂等重试收敛，避免覆盖用户同期修改。
