# 脏工作区隔离发布

## 目标

- `zeus-release` 检测到暂存、未暂存或未跟踪内容时，不再要求用户先清空工作区。
- 发布内容只取本地 `main HEAD` 的已提交快照，未提交内容不得进入 Release notes、版本提交、正式 App、DMG 或远端。
- 原工作区的文件内容、暂存状态和本地 `main` 引用保持原样，不自动 stash、恢复、提交、重置、合并或变基。

## 已确认领域边界

- **发布源**：执行命令时本地 `main HEAD` 指向的已提交快照；工作树中的暂存、未暂存和未跟踪内容不属于发布源。
- **隔离发布副本**：按发布源创建、只承载发布编排和恢复状态的持久干净仓库；目录按发布源提交固定，重跑复用同一副本。
- **本地同步债务**：隔离副本创建并推送版本提交后，原工作区因保持原样而不会自动前移到该提交；用户处理完未提交内容后再显式同步 `origin/main`。

`CONTEXT.md` 当前由并行任务暂存修改，本任务不插入上述术语，避免污染该任务的暂存内容；本文件作为本次边界记录。

## 实现契约

- 干净工作区继续在当前仓库执行原发布主链路。
- 脏工作区从当前本地 `main HEAD` 创建 `.tmp/zeus-release-isolated/<source-head>` 隔离副本；同一发布源重跑时复用该目录和其中的发布状态。
- 隔离副本的 `origin` 必须重新绑定受控 GitHub 仓库，并强制刷新副本自己的 `origin/main` 跟踪引用；该动作不修改原仓库引用。
- 隔离副本必须确认分支为 `main`，且当前提交等于发布源或是发布源的可恢复后继提交；不自动删除或覆盖不可信副本。
- 隔离副本先执行冻结锁文件的依赖安装，再执行相同的 `pnpm release`；内部环境标记只用于避免递归创建副本，不提供跳过发布门禁的能力。
- 发布产物继续透传到 Zeus 命令运行目录。发布成功后明确提示原工作区未同步，避免用户误认为未提交内容已经发布。

## 优缺点

### 优点

- 用户可以保留并行任务现场，同时发布已经进入本地 `main` 的提交。
- 未提交内容不被 stash、复制、打包或提交，发布源仍可由提交 SHA 完整追溯。
- 隔离副本保留发布恢复状态，失败重跑不需要破坏性清理。

### 缺点

- 发布成功后原本地 `main` 会比远端少一个版本提交，用户必须在处理当前工作区后显式同步。
- 首次创建隔离副本需要安装依赖，占用额外磁盘并增加少量启动时间。
- 如果用户长期不处理本地同步债务，下一次发布会因远端领先或分叉而阻断。
