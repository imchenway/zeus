# Zeus 代码交付差异与脏工作区合入修复

## 任务目标

修复任务代码交付链路中三个相互关联的问题：

1. 点击任务分支后看不到任务已经提交的代码差异。
2. 查看、提交、推送和合回目标分支之间缺少清晰、可信的操作结果。
3. 目标分支所在工作区存在未提交代码时，代码交付被错误阻断。

## 用户确认

- 交付窗口采用同窗分步方式，依次展示“查看代码、提交、可选推送、合入”。
- 四个动作彼此独立，完成当前动作后只解锁下一步，不自动替用户执行后续 Git 写操作。
- 默认代码对比展示任务分支相对来源分支的全部已提交成果；本机未提交变化单独分组。
- 任务分支提交完成后即可合入；推送任务分支只是可选的远端备份或协作动作，不是合入门禁。
- 合入在隔离工作目录完成并推送目标分支。目标分支所在本地工作区有未提交代码时，不修改、不暂存也不覆盖这些代码。
- 远端目标分支校验成功即算交付完成；本地同名分支暂时不能安全前移时，明确展示“本地待同步”。
- 任务详情中的“提交代码”和“推送代码”独立入口继续保留，并与交付窗口使用同一套真实能力。

## 现场证据与根因

### 代码对比读取错了范围

当前交付弹窗的文件列表只汇总 `stagedFiles / unstagedFiles / untrackedFiles`，文件差异也只读取任务 worktree 相对 `HEAD`
的未提交变化。任务分支已经完成提交且工作区干净时，页面必然显示“0 个变更”，即使该分支相对来源分支存在完整代码成果。

ZEUS-000036 的真实任务记录显示：

- 来源提交为 `051c6e5ae6dc064aee8236c5dc4adaf69c30aa68`。
- 任务分支提交为 `b2e0297452f8b7fc65f9951b3bcc6e38687f2c97`。
- 任务分支与远端提交一致，工作区已经回收。
- 现有界面展示的“领先 / 落后”是任务分支相对它自己的远端分支，而不是相对来源分支的代码差异。

因此左侧分支按钮虽然实际已经选中，点击后也没有新的数据可展示，用户看到的是“没反应”。

### 提交、推送和合入反馈断裂

当前“准备代码交付”会把提交、推送、验证和 worktree 回收放在同一动作中；成功后弹窗关闭，真正的合入入口需要用户重新进入代码交付。ZEUS-000036
的事件记录证明推送和回收已经成功，但页面没有连续展示这两个结果，用户无法判断代码到底处于哪一步。

### 合入错误依赖主工作区

服务端启动合入前强制要求项目主工作区：

- 当前正检出目标分支；
- 工作区完全干净。

最终完成合入时又重复校验相同条件，并在主工作区执行快进和推送。这虽然避免覆盖本机修改，但把“远端能否安全完成交付”错误绑定到了“主工作区当前是否干净”。

## 方案设计

### 同窗四步工作台

交付窗口保持一个上下文，按真实状态展示四个步骤：

1. **查看代码**：选择任务分支，默认查看已提交代码成果；可切换查看本机未提交变化。
2. **提交**：只有存在本机未提交变化时可选择文件并创建本地提交；成功后展示新提交号。
3. **可选推送**：只推送任务分支当前提交，不携带本机未提交变化；用于远端备份、协作或审查，不阻塞后续合入。
4. **合入**：本机任务分支已经提交且工作区干净后，选择目标分支和合入方式，显式执行合入并推送目标分支。

优点：操作边界清楚，用户能看到每一步输入和结果，不会误把“工作区干净”当成“没有代码”。

代价：界面状态比当前两个弹窗更复杂，需要同时处理工作区存在、已回收、已合入和本地待同步等状态。

### 两类差异分开读取

- 已提交成果使用来源分支与任务分支共同起点到任务分支当前提交的对比，表达“这个任务带来了什么代码”。
- 本机未提交变化继续使用工作区相对任务分支当前提交的对比，表达“还有什么没有进入提交”。
- worktree 已回收后，仍可直接通过仓库中的任务分支读取已提交成果。
- 二进制文件保留文件级变化信息；没有文本内容时明确说明，不伪装成无变化。

优点：符合代码评审和交付心智，已提交代码不会因工作区干净而消失。

代价：同一文件可能同时存在已提交成果和本机未提交变化，必须通过分组和标签避免混淆。

### 脏工作区下的隔离合入

1. 读取目标分支当前提交并保存为并发校验基线。
2. 在 detached integration worktree 中完成 merge 或 squash。
3. 推送前重新确认本地目标分支提交没有变化，并使用非强制推送更新远端；远端不再接受快进时安全失败。
4. 远端提交校验成功后记录交付完成。
5. 如果本地目标分支没有被任何工作区检出，安全更新本地分支引用。
6. 如果本地目标分支正被干净工作区检出，可在不覆盖文件的前提下同步；如果工作区有未提交代码，则保持其分支引用和文件现场不动，记录“本地待同步”。

优点：目标工作区有未提交代码时不再阻塞远端交付，也不需要自动 stash 或恢复用户现场。

代价：远端与本地目标分支可能短时间不一致；用户在处理完本机变化后需要显式同步。

未采用自动暂存再恢复：冲突可能同时来自任务合入和用户本机变化，失败恢复复杂，容易让用户误以为现场完全未动。

## 实现范围

- Git 核心增加任务分支已提交差异快照与文件级差异读取。
- 任务工作区接口同时返回已提交成果摘要、本机未提交摘要和可选的任务分支远端状态。
- 代码交付界面合并现有准备与合入上下文，保留四个独立按钮和逐步状态。
- 合入完成逻辑改为隔离结果直接安全推送，并返回本地同步状态。
- 任务事件和审计记录区分“远端已交付”和“本地待同步”。
- 单独提交、单独推送入口复用相同状态反馈，不改变任务管理状态。

## 验收要求

- 任务分支工作区干净但存在已提交成果时，点击分支可看到文件列表和文本差异。
- 多个任务分支切换时，选中态、文件列表和差异内容同步更新。
- 提交只写入用户选中的文件；可选推送只同步当前提交；不推任务分支也可以进入合入；每一步都有明确成功或失败结果。
- 目标工作区有未提交代码时，隔离合入和远端校验可以成功，本地文件与索引保持不变，并展示“本地待同步”。
- 目标分支在合入期间变化时安全停止，不覆盖或强推。
- 使用隔离 Git 仓库完成真实提交、推送、干净工作区合入、脏工作区合入和竞态拒绝验证。
- 完成 `pnpm lint`、`pnpm typecheck`、`pnpm build`、`pnpm package:mac` 和仓库生成隔离桌面包的真实界面验收；静态检查或构建成功不等于界面验收完成。

## 实现结果

- 交付窗口改为同窗四步工作台，左侧任务分支具有真实选中态；重复点击当前分支也会给出“已选择”反馈。
- 默认读取任务分支相对来源分支共同起点的已提交成果，文件级文本差异不再依赖 worktree 是否干净或已经回收。
- “已提交成果”和“本机未提交”使用独立页签、文件列表和差异读取范围，不再把提交后的干净工作区误写成没有代码。
- 提交、任务分支推送和目标分支合入使用三个独立按钮。任务分支推送明确标记为可选；合入只要求任务分支当前内容已经提交且工作区干净。
- 目标分支合入在隔离 worktree 中完成，成功后直接推送并反查目标远端提交。本地目标分支有未提交代码时保持分支引用、文件和索引不动，并保存
  `pending` 本地同步状态。
- 交付完成后回收干净任务 worktree，不要求任务分支存在远端副本；同时兼容 macOS `/tmp` 与 `/private/tmp` 指向同一路径的情况。
- 交付窗口重新打开或提交后，即使仍选中同名文件也会重新读取差异，修复真实桌面复验发现的旧差异失效问题。

## 真实验证记录

### 隔离 Git 核心链路

在隔离裸远端、项目主 worktree 和任务 worktree 中完成以下断言：

1. 任务分支只有本地提交、远端分支不存在时，已提交成果仍能列出 `feature.ts` 并读取文本差异。
2. 项目主 worktree 的 `base.txt` 保留未提交修改，任务分支仍可合入并推送远端 `main`。
3. 远端 `main` 推进到合入结果；本地 `main` 提交不动、`base.txt` 差异不动，结果记录为 `localSyncStatus=pending`。
4. 未被工作区检出的 `release` 分支能够自动同步本地引用，结果记录为 `localSyncStatus=synced`。
5. 合入准备后本地目标分支被推进时，完成阶段返回 `ZEUS_TARGET_HEAD_CHANGED`，没有覆盖目标分支。
6. macOS 路径别名修复后，使用 `/tmp/.../task-worktree` 记录能够匹配 Git 返回的 `/private/tmp/.../task-worktree` 并完成回收。
