# Zeus 会话误分流、排队卡死与工作区回退修复

## 任务边界

- 用户确认图二是在图一会话发送消息后由 Zeus 自动产生，并非手动新建或切换。
- 诊断阶段只读取正式应用现场、数据库和源码；用户确认完整闭环后进入修复阶段，不执行 Git 历史或远端动作。
- 正式应用版本为 `0.2.0`，数据目录为 `/Users/david/Library/Application Support/@zeus/desktop`。

## 修复阶段确认

- 用户确认继续修复，并选择完整闭环范围。
- 明确未发送的 steer 失败必须留在原会话，按普通下一轮队列消息继续；未知副作用仍保持安全锁定。
- 恢复状态不得静默把原 composer 替换为新会话 composer；创建承接会话必须由用户显式触发。
- 任务承接会话必须继承来源会话的持久任务环境与 worktree；证据缺失、环境已回收或仍被活动轮次占用时拒绝创建，不能回退项目主目录或 `main`。
- 轮次变更集以会话执行现场为授权根，Undo、Reapply 和中断恢复使用同一根目录。

优点：消息身份、会话身份、工作区身份和变更记录使用同一事实源，消除输入最终在 `main` 执行的风险。

代价：真实的不可恢复场景会多一次用户确认；原任务环境不可用时不能便捷兜底，只能回到任务工作区选择流程。

## 结论

这不是 Provider 主动创建新会话，而是 Zeus 在一次续发失败后，把原会话底部输入区静默替换成了新会话输入区。用户继续发送时，Renderer 明确提交 `mode: create`；服务端又把这条恢复会话落到项目主目录而不是原任务 worktree。新会话随后被项目并发上限拦在本机队列中，没有创建 Provider thread，因此表现为“新建后卡死”。

## 源码根因链

### 1. 续发失败被扩大成整会话恢复门禁

当前会话续发支持 `queue` 和 `steer_now`。本次 `steer_now` 的目标轮次已在 Provider 结束，最终落库为 `recovery_required`。前端控制器把任何发送失败转换为可粘滞的恢复错误，导致原会话进入不可继续状态。

### 2. 原输入框被静默替换为新会话输入框

`SessionWorkspace` 在 `state.error.recoveryRequired === true` 时设置 `freshStartRequired`，并在原输入区位置挂载 `NewConversationComposer`。该组件对任务所有者固定调用：

```text
mode: create
```

因此后续发送不是续接原会话，而是创建新任务会话。两个输入区外观和位置接近，界面没有把这次语义切换解释清楚，用户无法预见会创建新会话。

### 3. 恢复新会话丢失原任务工作区

普通 `mode: create` 任务会话不走 `source: task_push`，服务端固定使用 `project.localPath`，没有传入原会话的 `workspaceId / environmentId / worktreePath`。结果是任务会话从 `ZEUS-0043` worktree 退回 `/Users/david/hypha/zeus` 主工作区。

这与现有领域口径冲突：任务会话缺少持久工作区证据时应显示“不可用”，不能回退到项目主目录。

### 4. 新会话被并发门禁留在本机队列

正式配置为：

- 每项目最多 1 个活动轮次；
- 全局最多 2 个活动轮次。

15:54:42 时，同一项目至少已有两个未终止的原生轮次。任务首发使用 `bypassConcurrency`，可以形成超过普通上限的活动现场；本次普通恢复新会话不带该标记，所以 `startTaskConversation` 只创建本机会话和 `queued` submission，未创建 Provider thread。

当时同项目还有两条创建时间更早的普通队列提交。容量释放后，队列按创建时间先派发较早提交；最新现场中 `conversation_77e8083bd733bd0722d823d8` 已占用该项目唯一普通并发槽，本次 `conversation_21edc4c758b807cf60dae5a3` 仍保持 `unbound / queued / turnCount=0`。因此它不是线程创建后执行卡死，而是一直没有获得创建 Provider thread 的资格。

只要前面的普通轮次没有结束，它就不会进入模型。当前界面只显示“排队中”，没有展示“前面还有几条、被哪个并发上限阻塞、何时才会获得容量”，因此产品体验等同卡死。

## 截图中的路径错误

`ZEUS_TURN_CHANGE_SET_PATH_FORBIDDEN` 来自轮次变更集记录器。Provider 修改的两个文件实际位于当前 `ZEUS-0043` worktree 内，但记录器用项目主目录 `/Users/david/hypha/zeus` 作为授权根；worktree 位于其同级 `.zeus-worktrees`，因此被错误判定为“项目外路径”。

该错误没有让上一轮失败，上一轮最终仍是 `completed`；它是独立缺陷，但说明同一处“任务会话执行现场”和“项目主目录”混用还同时影响了变更记录。

## 建议修复顺序与取舍

### 第一优先：续发失败留在原会话

- 建议：Provider 返回“轮次已结束”时，把原输入恢复为原会话的普通下一轮草稿或队列消息；只有无法确认是否产生副作用的未知结果才进入 `recovery_required`。
- 优点：不会因无副作用的时序竞争拆分会话，上下文和工作区身份都保留。
- 代价：服务端必须区分“明确未接收”和“结果未知”，不能继续把所有 steer 失败统一处理。

### 第二优先：禁止恢复输入区静默创建

- 建议：确需新建时先明确显示“原会话不可继续，将创建新会话”，并要求一次显式确认；普通 Enter 不能跨会话发送。
- 优点：用户能预见会话身份变化，不会把外观相同的输入框误认成原会话。
- 代价：真正需要恢复时会多一次确认操作。

### 第三优先：新会话必须继承或重新选择任务执行现场

- 建议：从任务会话恢复创建时继承原 `environment/workspace`，或者重新走任务推送工作区选择；缺少证据时拒绝创建，不能退回项目主目录。
- 优点：避免在 `main` 上误写，工作区、分支和变更记录保持一致。
- 代价：原 worktree 已回收或不可用时，需要增加重新选择或重新创建工作区的流程。

### 第四优先：排队展示真实阻塞原因

- 建议：队列记录保存并展示并发阻塞范围、当前计数、上限和预计恢复条件；容量长期不释放时提供进入占用会话、停止占用轮次或取消消息的操作。
- 优点：用户能判断是在等待还是异常，不再表现为无解释卡死。
- 代价：队列快照需要增加并发原因字段，并保持实时更新。

### 同步修复：轮次变更集以会话执行现场为根

- 建议：变更集路径校验使用会话持久执行目录及其受信工作区身份，不使用项目主目录代替。
- 优点：任务 worktree 内的真实修改可以正常记录、审核和撤销。
- 代价：历史缺少工作区身份的会话只能保持变更集不可用，不能猜测授权根。

## 实现结果

- `steer_now` 收到 Provider 明确返回 `no active turn to steer` 时，清除旧轮次绑定，把同一条输入留在原会话并按普通下一轮重新排队；其他无法判断副作用的错误仍进入 `recovery_required`。
- 恢复门禁不再自动挂载新会话输入框。用户必须先点击恢复提示中的按钮，之后才能创建承接会话，普通 Enter 不会跨会话发送。
- 任务承接请求携带来源会话 ID。服务端校验同项目、同任务和持久任务环境，复用或恢复原 worktree；环境缺失、已回收或仍被活动轮次占用时直接拒绝，不回退项目主目录。
- 会话执行目录统一由持久提交上下文、任务工作区和任务环境解析。任务会话没有这些证据时返回不可用，不以项目主目录猜测。
- 轮次变更集的捕获、Undo、Reapply 和中断恢复全部使用会话执行目录作为授权根；路径错误文案同步改为“会话执行目录之外”。
