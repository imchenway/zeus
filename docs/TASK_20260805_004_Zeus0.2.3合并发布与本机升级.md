# Zeus 0.2.3 合并发布与本机升级

## 任务目标

把 `codex/always-visible-composer` 中已经完成的输入区常驻能力，与当前工作区完成的冲突处理修复一起交付到 `main`，随后发布 Zeus 0.2.3，并把本机 `/Applications/Zeus.app` 升级到公开稳定版。

## 用户确认

- 发布版本为 `0.2.3`。
- 本次只包含两个业务范围：输入区始终可见，以及冲突处理对齐 IDEA、AI 辅助和大文件性能修复。
- 不带入数据库修复、依赖升级或其他任务分支。
- Git 历史保留为：现有输入区提交、独立冲突修复提交、`main` 合并提交、0.2.3 发布提交。
- 真实桌面窗口尚未复验不阻断本次发布，但必须在交付结论中明确披露，不能写成 GUI 已验收。
- 公开发布验证完成后，升级并重新启动用户日常安装的 `/Applications/Zeus.app`。

## 当前事实

- `codex/always-visible-composer` 基于公开 `main` 的 0.2.2，仅多出一个已推送的输入区常驻提交。
- 冲突处理修复当前位于同一工作区的未提交改动中，范围已核对，不包含其他任务分支。
- 冲突修复已经通过 `pnpm lint`、`pnpm typecheck`、`pnpm build` 和 `pnpm package:mac`；生成的是独立身份 `Zeus Test.app`。
- 真实桌面窗口点击和滚动体验因 macOS 锁屏未完成；浏览器页面缺少 Electron 本地桥接，不能代替真实桌面验收。
- 日常数据库健康问题与本次代码交付无关，已由用户明确排除，不进入 0.2.3。

## 合并与发布方案

1. 把冲突处理代码和本任务文档作为独立提交写入 `codex/always-visible-composer`，并推送该分支。
2. 同步本地 `main` 到远端最新状态，使用显式合并提交纳入整个功能分支。
3. 在合并后的干净 `main` 上重新执行发布门禁，确认源码、类型、构建和测试身份安装包均正常。
4. 通过仓库正式发布编排生成 0.2.3 发布提交、标签、GitHub Release、安装资产和 Homebrew 稳定版入口。
5. 分别核对公开版本号、Release notes、下载资产和 Homebrew 清单；签名、公证和真实 GUI 状态单独报告。
6. 公开稳定版验证完成后，通过 Homebrew 升级 `/Applications/Zeus.app`，重新启动并核对本机应用版本与服务健康。

## 优点与代价

### 保留独立功能提交后再合并

优点：输入区能力与冲突修复边界清楚，出现问题时容易定位；`main` 上能明确看出整个任务分支的合入点。

代价：提交数量比压缩成一个提交更多，但不会把两个不同目的的改动揉成一团。

### GUI 未复验但继续发布

优点：不因当前锁屏条件阻塞已由静态检查、构建、真实冲突数据和测试身份打包支撑的交付。

代价：真实窗口中的点击、滚动手感和最终视觉状态仍有残余风险；发布后如发现界面问题，需要追加修复版本。

### 发布后立即升级日常应用

优点：公开资产与本机实际安装形成完整交付闭环，可以确认用户真正拿到 0.2.3。

代价：升级会结束并重新启动当前正式 Zeus；未保存的运行中界面状态可能受影响。

## 验收口径

- 功能分支和 `main` 远端历史包含两个已确认业务范围，不混入其他任务改动。
- 合并后的源码重新通过 `pnpm lint`、`pnpm typecheck`、`pnpm build` 和正式发布门禁。
- 仓库版本、0.2.3 发布文档、Git 标签、GitHub Release 和 Homebrew 稳定版版本一致。
- GitHub Release 中具备可下载安装资产，并核对签名、公证实际状态。
- `/Applications/Zeus.app` 的安装版本升级到 0.2.3，重新启动后本地服务可用。
- GUI 未实机复验继续明确标记为未覆盖项。
