# Zeus 升级后执行宿主迁移失败修复

## 任务目标

修复正式应用升级到 `0.2.4` 后，执行宿主因任务工作区唯一索引迁移失败而无法启动的问题。修复必须保留现有多仓任务工作区数据，并使用独立身份 `Zeus Test.app` 和正式数据副本完成真实启动验收。

## 用户确认口径

1. 修复代码并验证，不采用删除重复记录的一次性恢复方案。
2. 保留现有任务、会话、任务环境和全部仓库任务工作区记录。
3. 验收只使用数据库副本和 `dev.hypha.zeus.test` 身份的 `Zeus Test.app`，不修改或替换 `/Applications/Zeus.app`。
4. 不执行 Git 提交、推送、合并或发布。

## 现场证据

- `/Applications/Zeus.app` 的实际版本为 `0.2.4`，bundle ID 为 `dev.hypha.zeus`。
- Main 进程和 Renderer 已启动，但没有存活的 execution-host 进程。
- `execution-host/host-startup-error.log` 的直接错误为 `UNIQUE constraint failed: task_workspaces.project_id, task_workspaces.branch_name`。
- 失败调用链为 `createZeusDatabase` → `migrateTaskGitWorkspaceSchema` → 创建 `idx_task_workspaces_project_branch`，随后宿主退出；界面等待二十秒后才显示宿主未就绪。
- 正式数据库 `PRAGMA quick_check` 返回 `ok`，共包含 67 条任务工作区记录。
- 两组同项目同分支名记录各有 3 条，分别对应多仓任务中的不同仓库；数据库已有正确的 `idx_task_workspaces_repository_branch(repository_id, branch_name)` 唯一索引。
- 首轮测试包启动越过索引迁移后，又暴露一条早期 submission 缺少 `context.projectId`；Plan 实施请求恢复无条件解析完整执行上下文，因 `Missing submission projectId` 再次终止宿主启动。

## 根因

旧单仓模型要求任务分支名在项目内唯一。多仓模型已把唯一性边界改为“同一项目仓库内唯一”，并允许同一项目的不同仓库使用相同任务分支名。

数据库启动时仍先执行旧迁移函数。该函数无条件重新创建已经废弃的项目级唯一索引，随后多仓迁移函数才准备删除它。只要数据库已经存在合法的跨仓同名分支，启动流程就会在抵达删除步骤前失败。

界面展示的二十秒超时是二次错误，不是根因；执行宿主实际在数据库迁移阶段立即退出。

迁移修复后暴露的第二个阻塞同样属于旧数据兼容问题。该 submission 已绑定到具有真实 `project_id` 的会话，并且其项目路径、模型等其他执行上下文完整；恢复逻辑却只读取 submission 内的重复字段，没有使用会话归属作为兼容来源。

## 修复设计

`migrateTaskGitWorkspaceSchema` 在处理旧项目级唯一索引前先读取 `task_workspaces` 的真实字段：

- 尚无 `repository_id` 时，数据库仍处于旧单仓结构，临时保留项目级唯一索引，后续同一次启动由多仓迁移替换。
- 已有 `repository_id` 时，数据库已经进入多仓结构，直接移除可能残留的项目级唯一索引，不再尝试重新创建。
- 多仓迁移继续创建并维护仓库级唯一索引，不删除、不合并任何业务记录。

优点：兼容旧数据库的升级路径，同时允许多仓合法同名分支，避免通过删数据掩盖迁移缺陷。

缺点：旧迁移函数需要感知后续结构是否已经存在；长期应把数据库迁移收敛为只执行一次、严格按版本前进的迁移序列，避免每次启动重复执行已过时结构。

恢复旧 submission 时，优先使用 submission 中明确保存的 `projectId`；仅当该字段缺失时，回退到 submission 所属会话的真实 `projectId`。会话归属本来就是持久化的权威业务关系，因此该兼容不猜测项目、不改写历史 submission，也不会跨项目恢复。

优点：保留历史记录并恢复旧会话可读性，所有依赖执行上下文的恢复路径使用同一项目归属口径。

缺点：若 submission 和会话都缺少项目归属，仍然按损坏状态拒绝恢复，不会静默选择其他项目。

## 领域口径

- 项目容器可以包含多个项目仓库。
- 仓库任务工作区对应一个项目仓库的隔离开发现场。
- 任务分支名只在同一项目仓库内唯一；跨仓同名是合法状态，不属于重复脏数据。

## 验收条件

1. 当前正式数据库副本在修复代码下可以完成迁移，67 条任务工作区记录保持不变。
2. 两组跨仓同名分支记录全部保留，项目级唯一索引不存在，仓库级唯一索引存在。
3. 数据库副本迁移后 `PRAGMA quick_check` 返回 `ok`。
4. 缺少 submission `projectId` 的旧记录从所属会话恢复项目归属，不删除或改写原记录，并且不会阻断宿主启动。
5. `pnpm lint`、`pnpm typecheck`、`pnpm build`、`pnpm package:mac` 通过；这些结果只证明对应静态和打包门禁。
6. 独立 `Zeus Test.app` 使用正式数据库副本启动时，execution-host 写出 ready，Main 能取得本机服务配置，界面不再出现二十秒超时。
7. 验收不启动、替换或修改 `/Applications/Zeus.app`，不写回正式数据库。
