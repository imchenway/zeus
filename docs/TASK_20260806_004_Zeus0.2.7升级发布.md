# Zeus 0.2.7 升级发布

## 任务目标

把远端公开稳定版 `0.2.6` 之后的当前全部工作区改动交付为 `0.2.7`，完成 GitHub Release、公开安装资产和 Homebrew
稳定入口对账，再升级并重启本机 `/Applications/Zeus.app`。

## 已确认边界

1. 本次采用完整升级发布：提交并推送 `main`、完成公开发布和资产回验，再升级并重启本机正式 Zeus。
2. 发布范围包含当前全部未提交内容：旧数据目录恢复文档及领域术语、Codex 登录门禁代码、对应领域术语和任务文档。
3. 真实 `Zeus Test.app` 尚未走完“登录并继续、浏览器完成登录、自动创建会话”的 GUI 链路。用户明确接受其作为发布例外继续，但发布记录和最终结论必须披露，禁止表述为
   GUI 已验收。
4. 目标版本按最新公开稳定版补丁位递增为 `0.2.7`。
5. 当前本地 `main` 比 `origin/main` 少一个 `0.2.6` 发布提交；必须先把已确认改动建立在远端 `0.2.6` 之上，禁止从本地 `0.2.5`
   快照直接发布。

## 发布方案

1. 在隔离的干净发布工作区中以 `origin/main@0.2.6` 为基线应用当前全部改动，避免破坏原工作区和已有运行现场。
2. 复核候选差异，只暂存本次用户确认的全部文件，形成独立功能提交并推送到 `main`。
3. 在同一候选提交上执行仓库端到端发布编排，由脚本生成 `0.2.7` 发布正文和版本提交，完成发布门禁、`main` 推送、CI、不可变标签、GitHub
   Release、DMG、manifest 与 Homebrew 对账。
4. 公开发布回验完成后，正常升级 `/Applications/Zeus.app`，重新启动并核对应用版本、bundle ID、执行宿主和 `/health`。
5. 分别报告源码门禁、正式包、公开资产、签名与公证、本机升级和 GUI 未覆盖项，不把任一阶段结果夸大为其他阶段完成。

## 优点与代价

### 以远端 0.2.6 创建隔离候选

优点：不需要在原脏工作区执行拉取、变基或暂存恢复，当前现场保持可回退；候选天然包含最新公开提交。

代价：发布完成后原工作区仍可能落后远端，需要在当前改动处理完后显式同步，不能假设原目录已经自动前移。

### 披露 GUI 缺口后继续

优点：不因锁屏环境阻塞已经通过源码、协议和测试包门禁的修复交付。

代价：真实窗口中的登录跳转、等待反馈和自动创建仍有残余风险；如果公开后暴露问题，需要追加修复版本。

## 验收口径

- 候选提交基于 `v0.2.6`，包含全部确认文件，不夹带发布编排生成物之外的未知改动。
- `pnpm lint`、`pnpm typecheck`、`pnpm build` 和正式发布门禁在同一候选提交上通过。
- 仓库版本、`v0.2.7` 标签、GitHub Release、DMG、manifest 与 Homebrew Cask 版本及摘要一致。
- 签名与公证按公开 manifest 的真实值报告；如果仍为 ad-hoc、未公证，不描述为 Apple 正式签名分发。
- `/Applications/Zeus.app` 升级到 `0.2.7`，bundle ID 保持 `dev.hypha.zeus`，重启后本机服务健康。
- GUI 登录链路继续明确标记为发布例外，不计为已通过。
