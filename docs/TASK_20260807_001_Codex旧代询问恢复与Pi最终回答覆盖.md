## 方案与取舍

### Codex 交互恢复

旧世代请求不直接回写已经退出的 RPC 通道，而是转为“交互恢复检查点”。用户答案仍先经过原请求结构校验，再在同一 provider thread 创建幂等续接轮次，并把旧轮次收束为已中断。

优点：

- 用户可以继续回答同一问题，不需要丢弃会话或重新描述上下文。
- 不伪造新世代 requestId，也不自动重放旧轮次已经产生的副作用。
- 审批类请求继续要求新轮次重新发出明确操作，旧批准不能跨操作复用。
- 兼容旧实现已经写成 `ZEUS_CODEX_REQUEST_GENERATION_STALE` 的最近一次失败请求，启动恢复后可重新展示。

代价：

- 续接会形成一个新的 provider turn，而不是恢复已经退出的原 turn。
- app-server 切换瞬间若上游另行重放相同请求，需要继续依靠请求身份和幂等键避免重复提交；不能把两个世代的请求视为同一个原生 RPC。

### Pi 回答投影

停止原因为 `toolUse` 的 assistant 消息改写为 `in_progress / prework`，继续显示为阶段回答；正常最终消息使用同一个 item 标识写成 `completed / final_answer`，覆盖阶段文本。

优点：用户执行期间仍能看到模型说明，最终结果到达后界面与持久消息一致。

代价：阶段说明不是一条永久独立消息，最终回答出现后会被替换；这正是本任务确认的产品口径。
