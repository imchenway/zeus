# Zeus 历史任务附件推送恢复

## 任务目标

修复数据目录迁移后，历史任务附件实际存在但“推送到新会话”仍提示附件不可用的问题；完整恢复可验证历史引用，真正缺失的附件继续明确阻断。

## 用户确认口径

- 完整修复全部历史任务附件，不只处理本次截图中的 `ZEUS-0079`。
- 旧目录保持原样，不删除、不改写。
- 当前托管目录没有可验证副本时继续阻断，并提示用户重新添加附件。
- 本次不执行 Git 提交、推送或正式发布。

## 现场证据与根因

- 截图中的失败任务是 `ZEUS-0079`，附件记录仍指向旧目录
  `/Users/david/Library/Application Support/@zeus/desktop/task-attachments/...`。
- 当前正式应用使用 `/Users/david/.zeus`，任务附件受信根为 `/Users/david/.zeus/task-attachments`。
- 当前数据库共有 74 个未删除历史任务、83 个附件仍指向旧正式目录；另有 5 个附件已经指向当前正式目录。
- 83 个旧引用对应的文件在旧目录和当前目录均存在，逐个 SHA-256 核对一致。
- 推送前校验会先解析旧绝对路径，再检查它是否位于项目目录或当前附件受信根；旧路径虽然存在，但不在当前受信根，因此被误判为不可用。

结论：这是托管附件引用没有随数据目录迁移而归一化，不是附件文件丢失，也不是 Codex 接收附件失败。

## 修复设计与取舍

Local Server 启动时扫描任务附件记录。历史路径只有满足以下条件才重定向到当前托管目录：

1. 原引用的直接父目录名为 `task-attachments`；
2. 当前托管目录存在同一“时间戳 + UUID + 原文件名”稳定资源名，避免把项目中碰巧名为 `task-attachments` 的普通目录误认成
   Zeus 托管目录；
3. 资源真实路径仍位于当前受信根；
4. 文件或目录类型一致；文件存在已保存大小时必须一致；
5. 旧副本仍存在时，旧副本与当前副本的内容摘要一致。

修复只更新 `source_context_json` 中的存储路径，不刷新任务业务 `updated_at`
，不新增任务事件，也不碰旧目录。推送时复用同一解析规则作为兼容兜底，避免迁移未落盘或后续导入旧任务时再次失败。

优点：一次恢复全部可验证历史任务，后续再次搬迁完整数据目录也能自动归一化；安全边界仍只信任当前托管目录。

代价：首次启动会读取历史资源做一致性校验；缺失、类型不符、大小不符或内容不一致的资源不会自动恢复，仍需用户重新添加。

不创建 ADR：这是托管附件路径归一化和迁移缺口修复，没有引入新的长期架构选型。

## 验收口径

- 使用正式数据库副本启动最终构建的 Local Server，83 个旧引用全部改为当前托管目录，74 个任务的业务更新时间保持不变。
- `ZEUS-0079` 的附件能够通过同一推送前规范化逻辑，且文件名、大小和图片签名保持真实。
- 构造当前目录缺少资源的历史引用时，不改写数据库，推送仍返回 `ZEUS_TASK_PUSH_ATTACHMENT_UNAVAILABLE`。
- 执行 `pnpm lint`、`pnpm typecheck`、`pnpm build` 和必要的测试身份打包检查；静态检查或构建成功不等于正式应用真实推送完成。

## 实施记录

- `packages/local-server/src/index.ts`
    - Local Server 启动时准备当前任务附件受信根，并扫描未删除任务中的附件引用。
    - 只识别直接位于历史 `task-attachments` 目录、且文件名符合“13 位时间戳 + UUID + 原文件名”的 Zeus 托管资源。
    - 当前副本必须位于当前受信根，文件或目录类型一致；文件核对已保存大小，目录核对递归总大小。
    - 旧副本仍存在时递归计算 SHA-256 摘要，内容不一致不迁移；符号链接和非普通文件直接拒绝。
    - 自动修复只改 `source_context_json`，不更新任务业务时间，不新增事件，不改旧目录。
    - 推送前附件规范化复用同一解析规则，作为启动修复之外的兼容兜底。
- `CONTEXT.md`
    - 明确任务附件关联指向 Zeus 托管资源，资源身份不由历史绝对目录决定。
- `DESIGN.md`
    - 记录自动迁移、失败阻断、安全校验及优缺点。
