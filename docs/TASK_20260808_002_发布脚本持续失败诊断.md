# 发布脚本持续失败诊断

## 结论

本次 `pnpm release` 的直接失败原因不是依赖安装警告，也不是 DeepSeek 生成 Release notes 失败，而是候选范围内的
`docs/diagrams/ZEUS-0135_升级后完整目录结构.html` 末尾多了两个空行。`git diff --check` 在第 2384 行报
`new blank line at EOF`，退出码为 `2`，因此端到端发布中断。

这不只是一个 HTML 空行问题，还暴露了发布编排顺序不合理：脚本先安装整个工作区依赖、自动改写候选代码并在隔离副本创建格式化提交，然后并行启动
Release notes 生成和便宜的空白检查。结果是一个几毫秒就能发现的问题，要等到大量无效工作后才报错。

## 证据

- 失败日志明确指向 `docs/diagrams/ZEUS-0135_升级后完整目录结构.html:2384: new blank line at EOF.`
- 该 HTML 由提交 `8a2ed3242dfcf9087552e8e40f43b5175d2e5a22` 引入，文件末尾实际有两个空行。
- ZEUS-0135 任务文档记录了 `lint`、`typecheck`、`build`、`package:mac` 和 `codesign`，但没有记录 `git diff --check` 或
  `format:check`，所以这个问题在交付前没有被发现。
- `scripts/release-all.mjs` 的自动整理扩展名只包含 TypeScript、JavaScript、JSON 和 YAML，不包含 HTML，所以“自动整理候选”不会修复该文件。
- 自动整理在隔离副本中改写了 16 个文件，并创建了 `283c9c1ccf56e61d374bae597c3b898ae3bad50f` 格式化提交；这个提交只存在隔离发布副本，没有写入原工作区的
  `main`。
- 候选前置检查和 Release notes 生成被 `Promise.all` 并行启动；因此空白检查已经失败时，DeepSeek
  请求仍在运行并成功产生草稿，造成额外等待和混乱的日志顺序。
- 安装阶段的 `zeus-code-indexer` 和 `zeus-graph-engine` `ENOENT` 是 pnpm 创建未构建 workspace bin
  的警告；安装最终返回成功，不是本次的阻断点。AI Runtime 把这些警告文本标成 `error`，又增加了噪音。

## 影响范围

- `v0.2.15` 状态停在 `notes_generated`，`releaseCommit=null`。
- 远端不存在 `v0.2.15` 标签，GitHub 不存在 `v0.2.15` Release。
- 没有执行 main push、公开发布、Homebrew 更新或安装正式应用。
- 原工作区没有被隔离副本中的格式化提交改写。

## 为什么容易反复失败

1. 发布入口承担了“清理候选代码”的职责，而不是只发布已通过检查的不可变候选。
2. 自动格式化只覆盖部分扩展名，但后面的 Git 空白门禁覆盖全部文件，两者范围不一致。
3. 最便宜、最确定的候选检查不在最前面，而与外部模型请求并行。
4. 普通任务交付门禁没有保证执行与发布相同的全范围空白检查，问题被推迟到发布环节。

## 建议改法

### 首选：发布脚本只接受已验证候选

把自动 `Prettier --write` 和自动格式提交移出 `pnpm release`，先在任务交付或合入前运行变更范围的 Prettier 检查和
`git diff --check`。发布入口一开始只做读检查，任何问题立即失败。

- 优点：发布候选不会在发布过程中被改写；失败快，日志和恢复状态更简单。
- 缺点：普通任务的交付门禁必须真正落实，发布命令不再替上游擦屁股。

### 最小修补：重排现有阶段

保留自动整理，但在进入依赖安装、自动提交和 Release notes 前，先检查标签冲突、候选祖先关系和全范围 Git
空白错误；自动整理后再执行一次全范围检查，通过后才允许提交和请求模型。

- 优点：改动较小，仍能自动修复部分格式问题。
- 缺点：发布过程仍会生成额外提交，恢复路径和候选 SHA 继续复杂。

## 本轮边界

本轮不重跑 `pnpm release`，不执行提交、推送、标签或公开发布。

## 2026-08-08 实施修复

1. `scripts/release-all.mjs` 在判断脏工作区、创建隔离副本或安装依赖前，先对最近本地稳定标签到当前 HEAD 执行
   `git diff --check`。
2. 候选前置检查改为 Release notes 之前串行完成，不再与外部模型请求并行。
3. 发布候选的 Prettier 阶段从 `--write` 改为 `--check`，删除自动 `git add` 和自动格式化提交。
4. 删除 `docs/diagrams/ZEUS-0135_升级后完整目录结构.html` 末尾多余空行。
5. 使用当前 Prettier 配置整理 v0.2.14 之后变更范围内的 16 个历史格式欠账文件，让新的只读门禁可以通过。

改动的优点是便宜问题会在发布起点立即暴露，发布脚本不再悄悄改写业务代码或改变候选 SHA；缺点是上游任务如果没有经过格式检查，发布会直接拒绝，不再自动代为修改。

## 2026-08-08 首次重试失败与纠正

用户提交 `b2d11b351d13` 后执行 `pnpm release`，快速空白检查和候选前置检查通过，但候选范围 Prettier 发现 17 个文件未按仓库 Prettier 3.8.4 格式提交，因此在任何 Release notes、版本写入、推送或公开发布前退出。

本次纠正不放宽只读门禁，而是对 v0.2.14 之后的 34 个受管候选文件执行同一版本 Prettier `--write`，然后用完全相同的文件集合执行 `--check`。结果为 34 个文件全部通过，`git diff --check v0.2.14^{commit} --` 通过。

这次失败证明发布脚本改为只读检查的方向是对的：它没有悄悄改写候选或创建新提交，也没有将未通过格式门禁的代码推向远端。问题在于上一次交付没有核对最终提交对象的真实内容，本次改为直接对 `HEAD` 候选范围重新整理和检查。
