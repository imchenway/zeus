# 代码交付提交前自动格式化

## 背景

代码交付页此前只负责把选中的文件执行 Git 提交和推送，没有执行仓库声明的 Prettier，也没有执行 Git
空白检查。页面显示“提交成功”或“推送成功”只能证明 Git 动作完成，不能证明提交内容满足发布门禁。因此，格式问题会一直留在提交中，直到
`pnpm release` 或远端 CI 才暴露。

## 本次处理

1. 代码交付创建提交前，先判断任务仓库根目录的 `package.json` 是否显式声明 Prettier。
2. 如果声明了 Prettier，优先使用任务工作区安装的本地版本；Git worktree 没有独立 `node_modules`
   时，复用同一仓库主工作区安装的版本。对本次选中且仍存在的普通文件执行 `--write`，随后立即执行 `--check`。
3. 格式化完成后再暂存选中文件，并对暂存内容执行 `git diff --cached --check`；存在行尾空格、文件末尾多余空行等问题时拒绝提交。
4. 删除文件仍正常进入提交；符号链接不会交给格式化器，避免跟随链接改写工作区外文件。
5. 提交结果记录实际被 Prettier 改写的文件路径，代码交付页会显示自动格式化数量，审计事件也会保留该结果。
6. 仓库没有声明 Prettier 时保持原有通用 Git 提交流程，不把 Zeus 的 Node 工具链强加给其他项目。
7. 同时整理本次发布已经发现的 3 个格式欠账文件，避免新机制生效前的旧内容继续阻断下一次发布。
8. Git 提交命令也限定为本次选中的路径；其他预先暂存但未选中的内容继续留在暂存区，不能绕过格式和空白门禁混入提交。

## 失败策略

- 项目声明了 Prettier，但任务工作区和同仓库主工作区都没有安装本地 Prettier：拒绝提交，并提示先安装项目依赖。
- Prettier 无法解析或检查文件：拒绝提交，并返回格式化器的实际错误。
- Git 空白检查失败：拒绝提交，并返回具体文件和行号。
- 上述失败均不会创建 Git 提交，也不会触发推送。

## 优缺点

优点：格式问题在代码进入提交前被处理，页面成功状态与发布门禁更一致；只改写用户选中的文件，不会顺手整理无关历史文件；固定使用仓库本地版本，避免开发机全局版本差异。

缺点：首次进入尚未安装依赖的任务工作区时，提交会被明确拦截；Prettier 使用 `--write`
，如果同一批文件中后续文件解析失败，先处理的文件可能已经留在工作区，但不会被提交，用户可以直接查看和继续修正。

## 验证边界

本任务使用项目规定的静态检查与构建验证，不新增或恢复单元测试。本任务不执行当前仓库的 Git 提交、推送、合并、标签或发布。

## 验证结果

- 本次涉及的受管文件执行 Prettier `--check`：通过。
- `git diff --check`：通过。
- `pnpm lint`：通过。
- `pnpm typecheck`：通过。
- `pnpm build`：通过。
- `pnpm verify:publish`：通过，包含本次变更文件的 Prettier、Git 空白、冲突标记、ESLint、类型检查和生产构建门禁。
- `pnpm package:mac`：通过，生成并校验独立身份的 `Zeus Test.app`；这只证明测试包可以生成，不代表真实界面操作已经验收。

## v0.2.16 首次发布重试

提交 `d9762faf24bd7f511b9d9844c03988b26eec4841` 后，`pnpm release` 在候选范围 Prettier 检查处发现 6 个文件不符合仓库 Prettier 3.8.4，发布状态保持 `phase=initialized`，没有生成发布提交、标签或公开 Release。

这次不是新门禁执行后失效，而是代码交付动作仍由已安装的旧版 Zeus 执行。旧版运行时尚未包含本任务新增的提交前格式化逻辑，因此它不能在自身升级前使用新逻辑完成这次自举提交。候选提交中的 TypeScript 实际采用了 4 空格和紧贴花括号的另一套排版，与仓库 `prettier.config.js` 不一致。

已使用仓库同一份本地 Prettier 3.8.4 对报错的 6 个文件执行 `--write`，并按发布脚本列出的 10 个候选文件重新执行 `--check`。后续需要把这次纯格式修复单独提交，再由 `pnpm release` 将未写入的 v0.2.16 状态安全重新绑定到新候选提交。新版本安装后，后续代码交付才会实际执行本任务新增的提交前门禁。
