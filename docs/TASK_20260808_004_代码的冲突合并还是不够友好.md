# 代码的冲突合并还是不够友好

## 根因

旧实现把 Git 返回的冲突文本直接交给中间文本编辑器。`<<<<<<<`、`=======`、`>>>>>>>` 因而成为用户可见内容，冲突块的选择、编辑和未处理数量也只能依赖原始字符串扫描。

本次把 Git 冲突标记限定为内部传输格式。渲染层读取冲突文件后立即建立 `ConflictDocument`，中间编辑器只接收无标记的可见草稿。

## 交互依据

交互按 JetBrains IDEA 三栏合并工具的定义实现：左、右两侧只读，中间是基于共同基线的可编辑结果；两侧差异旁提供指向中间的选入操作和忽略操作，全部处理后再应用结果。

- [Resolve Git conflicts](https://www.jetbrains.com/help/idea/resolve-conflicts.html)
- [Differences viewer](https://www.jetbrains.com/help/idea/differences-viewer.html)

当前界面对应关系：

- 左侧是目标分支，只读；右侧是任务分支，只读。
- 中间以共同基线作为未处理块的起点，已自动合并的非冲突内容保留，并可直接编辑。
- 左侧箭头选入目标分支内容，右侧箭头选入任务分支内容；两侧的 `X` 只忽略对应侧，不移除侧栏代码。
- 两侧都选入时调用确定性的三方组合；重叠修改不能安全组合时保留未处理状态，并提示在中间手工调整。
- 冲突导航条只显示块位置和状态，不再承担直接替换原始 marker 的职责。

## 内部模型

`apps/desktop/src/renderer/task/taskConflictModel.ts` 定义 `ConflictDocument` 和 `ConflictBlock`：

- 冲突块保存共同基线、目标分支内容、任务分支内容、中间可见文本、稳定指纹和出现序号。
- 两侧独立保存 `pending / accepted / ignored` 状态；中间直接编辑后块状态为 `manual`。
- 侧栏定位使用稳定指纹、出现序号和扫描得到的范围，不再用重复代码片段的 `indexOf` 作为块身份。
- `serializeConflictForAi` 只在请求 AI 前为仍未处理块恢复隐藏 marker，保持现有 AI 接口兼容。
- `serializeConflictForGit` 只返回中间无 marker 的纯文本，写文件和 `git add` 仍只发生在“保存结果并继续”入口。

## 草稿和保存边界

`TaskGitMergeModal` 按文件保存 `fingerprint + ConflictDocument` 快照。切换冲突文件不会丢失未保存编辑；目标分支变化重建候选后，只恢复指纹完全匹配的快照，冲突内容变化时不自动套用旧草稿。

未点击“保存结果并继续”前，不调用解决冲突接口，也不写文件、不暂存。保存按钮仍要求当前模型没有 `pending` 冲突块；后端目标 HEAD 校验、全部冲突解决后才能完成合入、最终推送独立执行等安全边界保持不变。

完整文件视图继续使用原生文本框，中间只显示无 marker 的结果；冲突控制层只为冲突块生成少量按钮，不把大文件拆成整份 React 行节点。
