# 发布失败与高能耗诊断

## 任务背景

用户在 Zeus 正式应用的 AI Runtime 中执行 `sh -lc pnpm release`，遇到两个现象：

1. 首次发布失败。
2. 命令执行期间整机能耗异常升高，风扇高速运转，机器持续发热。

本轮先完成只读跟踪和隔离复现；用户随后明确授权修复，并允许在需要时重新执行 Zeus 发布命令。代码修复、静态检查、打包、测试包运行回归、v0.2.18 正式升级发布，以及用户日常安装的正式 Zeus 升级后能耗复验现已全部完成。

## 结论

- v0.2.17 已于 `2026-08-09T03:29:19Z` 正式公开，DMG 和发布清单均已上传，Homebrew 同步步骤成功。
- 因此首次失败属于 GitHub Actions 产物服务的瞬时故障，不是代码编译失败，也不是 DMG 打包失败。

### 高能耗首要根因

高能耗发生在 Zeus 自身的命令详情读取与渲染链路，不是远端 GitHub 打包消耗本机 CPU。隔离复现已经证明：命令本身不需要是 `pnpm release`，任意命令完成后只要命令详情保持选中，就会触发持续循环。

直接证据：

- 第二次 Runtime 已在 `2026-08-09T03:29:34.762Z` 以退出码 0 结束，日志只有 66 行、约 31 KB。
- 命令结束数分钟后，正式 Zeus 的 execution host 仍约占 44% CPU，Renderer 仍约占 48% 至 52% CPU，Network Service 仍约占 18% 至 19% CPU。
- 本机回环 HTTP 连接在命令结束后仍持续传输，5 秒内继续增加约 14 MB；应用启动约 8 分钟时累计读取已超过 4.7 GB。
- 应用启动约 15 分钟、发布命令结束约 11 分钟后，三个进程仍分别约占 47.5%、46.7% 和 19.4% CPU，本机累计读取已增长到约 10.5 GB，证明异常循环不会随发布子进程退出而退出。
- execution host 的进程采样显示大量时间消耗在 HTTP 回调和 `node::sqlite::StatementSync::All`，与远端构建进程无关。
- Zeus 项目当前有 188 个未归档任务、24 个未归档会话、33838 个会话项，数据库约 483 MB。
- 使用正式数据库的一致性只读副本启动 `Zeus Test.app`，页面空闲时 execution host 与 Renderer 均约 2% 至 4%。
- 通过命令中心执行只输出一行 `ZEUS_ENERGY_PROBE_OK` 的 `printf` 命令后，execution host 立即升到约 46.9%，Renderer 升到约 49.8%，Network Service 升到约 18.0%。这排除了 pnpm、GitHub CLI、远端打包和大日志是必要条件。
- `CommandCenterPanel` 的命令详情 effect 依赖 `activeRuns` 数组；每次详情加载又无条件 `map` 出新的 `runs` 数组。即使选中执行已经结束、内容也完全没变，新的数组仍会让 effect 再次立即加载详情，形成“HTTP 详情请求 → SQLite 查询 → setRuns 新数组 → effect 重跑”的无限循环。
- 服务端每次详情请求还会查询 Runtime 会话和日志，因此该循环同时解释了 SQLite `StatementSync::All`、本机 HTTP 流量、Renderer 重绘和命令结束后仍不停止的现象。发布日志比一行探针更大，只会进一步放大每次循环的传输量。

同时存在但不是本次启动条件的放大链路：

1. `apps/desktop/src/renderer/App.tsx` 在进入“会话”或“任务”区域时，会对当前项目的每一个任务同时调用 `loadTaskConversationChoices`。Zeus 项目当前一次会创建 188 个任务请求，另加 1 个项目请求。
2. `packages/local-server/src/index.ts` 的 `listTaskConversationHistory` 没有使用已有的按任务查询，而是每个任务请求都分页读取整个项目的全部会话，然后在 JavaScript 中按 `taskId` 过滤。
3. `packages/storage/src/index.ts` 的 `listByProject` 还会为分页命中的每个会话读取消息。仓储层实际上已经存在 `listByTask(taskId)`，但上述接口没有使用。
4. 每个任务请求完成后，Renderer 又分别更新任务会话状态，带来大量独立 React 更新和重复渲染。

任务会话扇出会加重大项目的 SQLite 读取和 Renderer 更新，但隔离复现表明它不是“执行任意命令后立刻持续飙高”的首要根因。根据本机回环累计流量，当前问题也不能被简化为 `gh run watch` 输出过多；第二次发布 Runtime 的全部日志只有约 31 KB，远小于数 GB 的本机 HTTP 流量。

## 触发关系的校正

- 已确认：每次 Runtime 输出都会被 Zeus 写入 SQLite、终端日志文件并广播实时事件。
- 已确认：修复前的发布脚本等待 GitHub Workflow 时，每 10 秒执行一次 `gh run watch` 状态刷新，因此发布期间会稳定地产生 Runtime 输出事件。
- 已确认：第二次发布原始终端日志只有约 35 KB，且只有 2 个 ANSI ESC 控制字符，不支持“终端控制字符或日志体积直接把电脑压满”的解释。
- 已确认：异常 HTTP/SQLite/Renderer 循环在 Runtime 退出后仍持续至少 11 分钟。
- 已通过对照回归确认：使用同一份隔离数据库，命令中心空闲时 CPU 保持低位；执行只输出一行的无害命令后立即复现。触发器是命令详情状态更新，不是打开会话页，也不是发布脚本自身。
- 已完成：先切断命令详情自触发循环和重叠轮询，再收口项目会话批量读取、实时摘要刷新、Runtime 日志内存与持久化放大；发布侧低噪声轮询和上传重试作为可靠性补强一并完成。

## 实施阶段记录

- 命令详情轮询只依赖“所选执行是否仍在运行”这个稳定布尔值；详情未变化时保持原状态对象，请求进行中时禁止重叠。运行中最多每秒读取一次，进入终态后停止轮询。
- 终态存在日志积压时，不再无间隔补拉完整历史，而是只做一次受 2000 条和约 4 MB 限制的尾部重定位。完整日志仍保留在 Runtime 中，需要时可以分页查看或导出。
- Runtime 日志分页改为数据库持久序号游标，不再使用实时追加时会漏行或重复的偏移量分页；同一毫秒产生的日志也能保持稳定顺序。
- 日志正文查询先读取字节长度，再在数据库层按约 4 MB 预算取正文。即使出现单条 5 MB 日志，也只把轻量省略标记交给 Node 和 Renderer，避免先把巨块读进内存再截断。
- Runtime 内存日志设置单会话 2000 条、约 4 MB、缓存会话数和总会话数上限；SQLite 仍保留完整历史。数据库保存与日志文件写入按 100 毫秒合并，移除每块日志一个小文件的写放大。
- 每个 stdout/stderr 数据块不再复制成一条会话消息；绑定任务的 Runtime 结束时只写入一次有界终态摘要。实时事件按 100 毫秒真正批量合并，只更新 sessionId 匹配的会话，避免对全部会话和 4 MB 窗口反复编码、复制。
- Runtime 的完成边界从子进程 `exit` 改为标准输出、标准错误均排空后的 `close`。macOS 下按进程组发送 TERM/KILL 并确认整棵进程树退出；发现孤儿进程时保留管理权并允许再次强杀，不能把仍存活的子进程误报为已完成。
- Runtime 在 spawn 前生成随机进程身份，先持久化再注入子进程环境；spawn 后立即把真实 PID 单独提交到数据库，完成前不向调用方报告启动成功。这个内部身份不进入 Runtime API、命令详情、审计日志或终端输出，并自动纳入日志脱敏。
- Zeus 异常退出后恢复 Runtime 时，只有确认原进程组已不存在才记为 `lost`；进程组仍存在但身份无法核验时保留 `orphan_detected` 并拒绝发信号，避免 PID 复用导致误杀无关进程。身份可核验时才按进程组 TERM、限时等待、KILL 并再次确认。
- 未确认终态的 Runtime 不得归档或软删除，启动恢复会重新显示历史上被隐藏的活动会话。任务终态操作只发出停止请求并立即返回“待清理”冲突，用户在进程树确认结束后重试；不再让一个 HTTP 请求同步等待最长约 11 秒。
- local-server 关闭前先等待 Runtime 管理器完成；强制关闭时阻断晚到的日志回调，避免数据库关闭后仍有后台写入。如果进程树仍未确认退出，local-server 保留数据库并低频重试，execution host 也保留控制面；只有安全收口后才退出。非 Codex 图谱调用也改为等待真实完成或按配置超时后停止、强杀并再次确认。
- 项目会话选择改为一次 metadata-only 批量查询并按任务分组，Renderer 只合并一次状态；实时列表、执行主机状态、待处理请求和旧会话迁移也全部改为轻量记录或有界查询，不再把长会话消息历史读入内存后丢弃。
- 发布脚本改为每 10 秒读取 Workflow JSON，只在状态、作业或步骤变化时输出；连续三次状态读取失败才终止。Release Workflow 的 artifact 上传先正常执行，外部服务失败时再条件重试一次，重试仍失败会继续阻断发布。

上述边界的代价是：命令详情只保留最新约 2000 条、约 4 MB 的终端投影，完整历史需要进入 Runtime 分页查看；文件和数据库实时落盘最多增加约 100 毫秒延迟；无法核验身份的跨重启孤儿进程会保持可见并要求人工处理，而不是冒险强杀；GitHub artifact 只自动重试一次，不能掩盖持续性外部故障。换来的收益是命令结束后不再持续轮询、长日志不会无限占用 Renderer/Node 内存、发布等待日志更短，并且后台子进程不会因 PID 复用被误判或在终态前被隐藏。

## 建议修复方案

### 方案一：项目级批量加载任务会话摘要，推荐

一次查询项目会话的紧凑摘要，在服务端按 `taskId` 分组，再由一个接口返回所有任务的会话选择结果；Renderer 只进行一次请求和一次状态合并。

优点：

- 从根本上消除 188 个并发请求和 188 次独立渲染。
- 服务端只扫描一次，项目任务数量增加时性能仍可控。
- 最符合会话树一次展示整个项目数据的真实使用方式。

缺点：

- 需要新增批量接口和对应数据结构，改动范围比单点替换更大。
- 需要明确单次响应的大小上限，避免以后项目会话过多时形成另一个大响应。

### 方案二：先把任务接口改成已有的 `listByTask`

将 `listTaskConversationHistory` 改为直接调用仓储层已有的 `conversations.listByTask(taskId)`。

优点：

- 改动小，能立即消除“每个任务都扫描整个项目”的数据库浪费。
- 风险相对较低，现有接口形状不变。

缺点：

- Renderer 仍会同时发出 188 个 HTTP 请求，并产生大量独立状态更新。
- 只能缓解，不能彻底解决大项目下的能耗和渲染问题。

### 发布可靠性补强

可为 GitHub Actions 的产物上传增加工作流级重试，并把本机 `gh run watch` 改为只在状态变化时输出的低噪声轮询。

优点：

- GitHub 产物服务瞬时超时时，不必重新走完整打包。
- Runtime 日志更短，更容易看清真正失败节点。

缺点：

- 重试只能提高容错，无法保证 GitHub 外部服务永不失败。
- 低噪声轮询只能减少次要开销，不能代替会话列表数据链路修复。
