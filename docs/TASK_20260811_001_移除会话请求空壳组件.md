# 移除会话请求空壳组件

## 任务背景

会话收到 `conversation.request.created` 后，Renderer 会先创建一个 `payload: {}` 的待处理请求，并立即展示“需要你的回答 /
正在读取请求详情”。完整问题再通过第二次接口读取。

该设计会产生三个直接问题：

- 用户看到“需要回答”，却没有任何问题、选项或可执行动作。
- 普通输入区被空请求替换，用户无法继续当前会话。
- 请求详情读取失败时异常被吞掉，空壳会永久停留，Provider 与用户互相等待。

用户在 2026-08-11 明确要求移除该空壳界面并修复会话阻塞。

## 产品规则

- 请求发现只是内部同步过程，不是用户待办，不能展示“需要你的回答”。
- 只有完整、可校验、可回答的请求才能进入待回答或待审批界面。
- 新请求事件直接携带完整请求，Renderer 不再创建空 `payload` 占位。
- 二次请求接口只用于旧事件、断线和状态修复，不作为正常展示前置步骤。
- 兜底读取失败后自动重试；失败不能留下不可操作的空壳组件。

## 方案与取舍

### 采用方案：完整事件投影 + 后台补拉兜底

优点：

- 正常链路一次事件即可展示真实问题，没有空框闪现。
- 断线恢复仍可通过持久化请求接口校准，不丢失请求。
- Renderer 不再根据请求 ID 猜测用户待办，状态来源更真实。

代价：

- 实时事件载荷会增加完整请求内容。
- Codex 与 Pi 两条运行内核都需要统一事件结构。

### 不采用：保留空壳并增加加载动画

优点：实现改动较小。

缺点：仍然把内部同步暴露成用户待办；读取失败时仍需要额外错误态，无法消除错误信息架构。

## 实施范围

1. `conversation.request.created` 携带完整持久化请求投影。
2. Renderer 只接纳完整请求，不再生成 `payload: {}` 占位。
3. 请求详情补拉失败后自动重试，并在请求解决或连接销毁时停止。
4. `PendingRequestSurface` 不再渲染“正在读取请求详情”的空壳分支。
5. 会话工作区只把具备完整详情的请求当作阻塞交互。

## 2026-08-11 真实会话复查

用户反馈 ZEUS-0173 与 ZEUS-0174 仍分别停在 “Preparing single user question” 和 “Planning to ask product decision
question”。只读核对正式数据目录后确认：

- 两个会话均处于 `waiting_user`，Provider 已经发出 `request_user_input`。
- `conversation_server_requests` 已完整保存问题、选项和请求标识，请求状态仍为 `pending`。
- 实际请求比 Renderer 的旧白名单多出合法可选字段 `isBlocking: false`。
- 服务端校验明确接受 `isBlocking`，Renderer 却要求载荷只能恰好包含五个固定字段，因此把真实问题误判为详情不完整并从工作区过滤。

这次卡死不是图片解码、模型仍在思考或请求补拉失败，而是前后端各维护一套协议白名单后发生了规则漂移。

## 修正方案

把 `request_user_input` 的问题读取器移动到 `@zeus/shared`，服务端接收、答案校验和 Renderer 展示统一调用同一入口。该入口只读取提交回答所必需的
`questions`，完全忽略信封中的未知元数据，不再维护请求信封字段白名单。浏览器验收页使用与现场一致的 `isBlocking: false`
，并额外加入未知元数据，只有真实问题卡出现才算通过。

优点：

- 已落库的 ZEUS-0173、ZEUS-0174 请求无需重发，升级后即可被正确识别和显示。
- Provider 协议以后增加已支持字段时，不会再出现服务端接收而前端隐藏的问题。

代价：

- 仍保留问题 ID、问题正文、敏感标记和可提交选项等必要检查；这些字段缺失时无法构造安全且可对应的回答。信封元数据不再参与显示判断。
