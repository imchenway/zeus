# Zeus 发布命令界面假死根因修复

## 当前结论

- 修复状态：已定位并修复代码级根因，未停止或重启正式 Zeus。
- 发布失败的直接原因：公网访问失败。发布日志明确记录 DeepSeek `fetch failed`，随后 GitHub `443` 连接失败。
- 整个 Zeus 界面无响应不是同一问题：该次发布命令已在约 20 秒内退出，但前台界面心跳随后中断约 3 分 30 秒。
- 当前存在版本混跑：已安装和前台 Zeus 是 `0.3.0`，独立执行宿主仍是 `0.2.38`。
- 旧执行宿主仍报告真实活动工作，现有安全交接规则不会强行终止它；优点是不打断会话和命令，代价是旧宿主的性能与稳定性问题会继续影响新前台。

## 代码级根因

- 前台每秒执行一次租约维护，但旧实现把“查询宿主状态、执行版本交接、发送 UI 心跳”串在同一个异步任务中。
- 版本不一致且存在待回复项时，交接会读取整个 Dashboard，再按项目分页读取会话，并逐会话读取详情，形成大量串行本机 API 请求。
- 交接扫描没有结束时，同一个租约任务不会再次发送心跳；超过 15 秒后旧宿主判定 UI 租约过期。
- 交接扫描产生的本机请求同时加重 Local Server 压力，于是出现 UI 心跳过期、本机健康检查超时和整窗无响应的同一条故障链。
- 发布命令只是促使版本混跑现场持续存在的触发条件，不是这条 UI 假死链的实现根因。

## 修复内容

- UI 心跳与版本交接拆成两个独立周期任务；交接再慢也不会占用 1 秒心跳。
- Local Server 新增一次性只读交接快照，直接读取持久化待回复请求表，不再经过 Dashboard、项目会话列表和逐会话详情。
- 新前台连接不支持一次性快照的旧宿主时，如果仍有待回复项就安全等待，不再退化成全量扫描；待回复项归零后仍可正常完成交接。
- Renderer 配置刷新不再等待长时间交接，避免交接反向阻塞前台初始化与本机 API 配置读取。

## 方案取舍

- 优点：从机制上保证版本交接不能饿死 UI 心跳；把交接读取从多次本机请求降为一次数据库查询和一次 API 响应。
- 优点：继续保留待回复项和活动工作的安全边界，不通过强杀旧宿主换取表面流畅。
- 代价：新前台面对不支持快照的旧宿主时，存在待回复项就延后交接；这比丢失待回复项或重新触发全量扫描更安全。

## 用户确认的现象

- 用户所说的“假死”是整个 Zeus 窗口无法点击或滚动，不只是发布终端暂时没有新输出。
- 本文统一使用“Zeus 界面无响应”描述该现象；“发布外部等待”只描述等待 GitHub、模型服务等外部结果。

## 根因分层

### 已确认

- 发布失败：公网连接失败。
- 界面无响应：前台 UI 心跳中断，本机执行宿主/本机服务也曾无法及时响应。
- 生命周期异常：`0.3.0` 前台仍连接 `0.2.38` 执行宿主。

### 高概率放大因素

- 网络差延长发布的外部等待时间，使旧执行宿主更久处于命令运行状态，延迟安全交接。
- 旧执行宿主同时承载会话、Runtime、命令与大体量 SQLite，任何同步重活都会放大前台失联感受。

### 排除项

- 数据库和 WAL 体量会放大旧全量扫描成本，但不是必须依赖的根因解释；修复不以清理用户数据库为前提。
- 公网连接失败只解释发布失败，不能解释命令退出后的 UI 租约过期和本机服务超时。
