# TASK_20260814_003 发布脚本反复失败诊断

## 结论

本次 `pnpm release` 的直接阻断点是 `docs/ZEUS-0260_会话Markdown列表换行诊断.md` 第 20、23 行各有两个行尾空格，
`git diff --check v0.3.5^{commit} d1e0bc374ec7...` 因此以退出码 `2` 失败。

发布脚本本身也存在确定的编排缺陷：起始空白检查已经知道完整候选存在 Git 空白报告，却只把它解释为“可由自动格式化修复”；随后
Prettier 自动整理只覆盖 TypeScript、JavaScript、JSON 和 YAML 等受管扩展名，既不覆盖 Markdown，仓库的 `.prettierignore` 也显式排除了
`*.md`。脚本仍先创建纯格式提交，最后才重新执行覆盖全部候选文件的 `git diff --check`，所以形成“自动提交成功后又被已知但不可修复的问题阻断”的
半成品现场。

这不是本次业务代码编译、macOS 打包、GitHub Actions 或 Homebrew 发布失败。脚本尚未进入这些阶段。

## 为什么会反复出现

仓库在 2026-08-08 已诊断过同一类范围错位：自动格式化只覆盖部分扩展名，而 Git 空白门禁覆盖全部候选文件。当时一度把发布入口收紧为
“先做全范围只读检查，不在发布中改写候选”；后续为了让发布门禁自动修复 Prettier 格式，又恢复了自动写入和自动提交，但没有同步解决
Markdown、HTML 等非 Prettier 受管文件与全范围 Git 空白检查之间的差异。

历史上的“发布失败”还包含另一类外部故障，例如 GitHub Actions `CreateArtifact` 超时。外部服务故障无法由本地脚本彻底消除，只能通过恢复状态、
条件重试和事实回验降低重复工作；本次不属于这一类。

## 行尾两个空格的实际影响

- 本次两处空格位于 Markdown 的 `text` 代码块中，只是在文件中保留原始模型输出的字节，不参与 Zeus 源码、构建、打包或运行。
- 在普通 Markdown 正文中，行尾两个空格还可能表示强制换行；无条件删除会改变文档排版语义。
- Git `diff --check` 不理解代码块或 Markdown 语义，只按通用空白规则报告 `trailing whitespace`，因此它能发现格式差异，但不能单独判断是否应阻断发布。
- 发布门禁应继续阻断未解决的冲突标记和真实候选错误；Markdown、HTML 等文档中的无害行尾空格或文件末尾空行更适合作为警告，不能与源码格式、类型错误、构建失败和产物错误使用同一阻断级别。

优点：不会再让不影响制品的文档空白阻断发布，同时仍保留真正危险内容的发布保护。

缺点：需要把冲突标记检查与普通空白提示拆开，不能再直接把 `git diff --check` 的非零退出码整体当成发布失败。

## 修复方向与取舍

### 推荐：安全错误阻断，文档空白只警告

在创建恢复状态、运行 Prettier 或创建格式提交前，先读取完整候选检查明细并按影响分级：未解决冲突标记、源码格式无法修复、类型、构建和产物错误继续阻断；
Markdown、HTML 等文档中的行尾空格和文件末尾空行只输出警告。受 Prettier 管理的文件仍可自动整理；整理后必须在创建格式提交前重新执行安全检查。

优点：不会再让无制品影响的文档空白阻断发布，也不会先生成提交再暴露已知错误；真正危险的候选问题继续保持失败关闭。

缺点：需要把 Git 的冲突标记报告和普通空白报告拆开处理，并明确维护源码与文档的分级规则。

具体执行顺序：

1. 保留 `docs/ZEUS-0260_会话Markdown列表换行诊断.md` 中记录原文的两个空格，不为通过发布而改写证据。
2. 把 `scripts/release-all.mjs` 的候选检查拆成“安全阻断项”和“文档空白警告”；不能再直接用 `git diff --check` 的整体退出码决定发布失败。
3. 在任何 `Prettier --write` 和格式提交之前先完成分级检查；自动整理后、格式提交前再次检查，避免留下新的半成品提交。
4. `ensureCandidatePreflight` 和发布提交快速门禁复用同一分级规则，避免前面放行、后面再次被原始 `git diff --check` 阻断。
5. GitHub Release Workflow 中现有 `git diff --check` 只检查生成的 Homebrew Cask 仓库变更，不检查 Zeus 候选 Markdown，本次无需同步放宽远端候选门禁。
6. 使用脚本语法检查、`pnpm lint`、`pnpm typecheck` 和只读候选检查验证；不通过真实发布来试错。
7. 修复进入新的本地提交后，保留现有 `d1e0bc3` 格式提交和 `v0.3.6` 恢复目录。脚本会在 `phase=initialized`、`releaseCommit=null` 的安全阶段把候选重新绑定到新 HEAD，不需要删除状态或重做已经完成的格式整理。

### 更稳但更严格：发布入口只接受不可变、已验证候选

恢复 2026-08-08 的只读发布职责：`pnpm release` 不执行 `Prettier --write`、不创建格式提交，只在第一阶段检查并拒绝不合格候选；自动格式化放在任务交付或
合入提交阶段。

优点：发布脚本不再改变候选提交，恢复状态和审计最简单，失败最快。

缺点：上游交付门禁必须可靠执行；遗漏格式时需要先修正并重新运行发布。

### 不建议：只删除当前两个空格后继续

优点：可以最快排除这一次阻断。

缺点：这两个空格位于保留模型原文的代码块中，直接删除可能改变诊断证据；更重要的是脚本的范围错位仍在，下一次遇到 Markdown、HTML 或其他未受管文件时会按同一路径再次失败。
