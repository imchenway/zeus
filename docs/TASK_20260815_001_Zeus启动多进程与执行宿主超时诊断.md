# Zeus 启动多进程与执行宿主超时诊断

## 任务状态

- 日期：2026-08-15
- 用户决策：明确要求移除第四个同名 Zeus execution-host 进程，接受关闭或升级界面时后台执行不能继续的代价。
- 实施范围：正式启动链改为主进程直接持有 Local Server、SQLite 和 Agent 调度；同时停止已经完成的 Agent 身份迁移在每次启动重复全量回填。
- 当前结论：独立 execution-host 不再由正式启动链拉起；Electron 主进程及其 GPU、网络、渲染 Helper 仍保留。未替换或启动 `/Applications/Zeus.app`，运行验证只使用独立 `Zeus Test.app`。

## 用户现场

活动监视器显示：

- PID `60926`：Zeus 主进程；
- PID `60927`、`60928`：两个 `Zeus Helper`，对应 Chromium/Electron 的渲染、GPU 等隔离子进程；
- PID `60929`：Zeus 独立执行宿主。该宿主通过同一个 Zeus 可执行文件配合 `ELECTRON_RUN_AS_NODE=1` 启动，因此活动监视器仍显示为“Zeus”；
- PID `60929` 瞬时 CPU 为 `102.6%`，表示占用约一个 CPU 核执行同步启动工作，不是四份界面应用同时启动。

四个进程本身不是故障。Electron 使用多进程隔离界面、渲染和 GPU；Zeus 额外把 Local Server、SQLite 和 Agent 调度放进可脱离界面的 execution-host，以便界面重启时长任务仍可继续。优点是界面与长任务解耦；代价是活动监视器会出现多个同名进程，并且宿主启动门禁必须正确处理慢启动和并发拉起。

### 执行宿主时间线

`~/.zeus/runtime/execution-host/host-startup-error.log` 在本地时间 `00:05:34` 写入：

```text
Error: Zeus execution-host is already running with PID 60929.
```

`~/.zeus/runtime/execution-host/host.log` 随后显示：

```text
00:06:34  PID 60929 才写出 execution_host.ready，版本为 0.3.10
00:07:14  PID 60929 因 detached_idle 关闭
```

因此，在 `00:05:34` 发生下一次宿主拉起时，PID `60929` 已经持有单实例锁，但至少又过了约 60 秒才发布可连接的 rendezvous。界面侧只等待 20 秒；宿主未就绪时 `connectOrLaunchExecutionHost()` 直接抛出 `Zeus execution-host did not become ready within 20 seconds.`。该异常进入 `handleFatalStartupError()` 后显示用户截图中的“Zeus 无法启动，请重新打开应用”，随后界面退出。失去界面租约且没有活动工作后，已经晚到的宿主按 30 秒空闲规则自动退出。

日志中的“already running”是慢启动之后重复拉起产生的二次错误，不应误判为同时正常运行了两套数据库写入者。真正需要先解决的是为什么 PID `60929` 在 ready 之前耗时超过 20 秒，以及为什么发现活锁但尚无 rendezvous 时仍尝试创建新宿主。

## 慢启动的已确认代码热点

当前 `~/.zeus/data/zeus.db` 的只读检查结果：

| 指标 | 现场值 |
| --- | ---: |
| 数据库逻辑大小 | 1470.0 MiB |
| freelist 空闲页 | 547.9 MiB |
| `conversation_items` 数据 | 674.6 MiB |
| `conversation_items` 行数 | 92,102 |
| Codex 原生会话数 | 352 |
| 启动时需要联机恢复的非归档会话 | 121 |
| 每次启动 UPDATE 命中的会话明细 | 92,093 |
| 已经完成同样回填的命中行 | 92,093 |
| `20260803_0001_agent_runtime_framework` 迁移记录 | 已存在 |
| `PRAGMA quick_check` | `ok` |

`createZeusDatabase()` 每次打开数据库都会调用 `migrateAgentRuntimeSchema()`。该函数虽然写入了迁移记录，但没有先检查迁移是否已经完成，并且每次都执行：

```sql
UPDATE conversation_items
SET agent_kind = COALESCE(agent_kind, 'codex'),
    native_item_id = COALESCE(native_item_id, provider_item_id)
WHERE conversation_id IN (
  SELECT id FROM conversations WHERE agent_kind = 'codex'
);
```

现场 92,093 条目标记录已经全部符合目标值，但仍会在每次启动进入大范围 UPDATE。由于 `conversation_items` 同时携带较大的正文与 JSON 负载，这会重写大量 SQLite 页面、产生 WAL 和检查点开销，符合 PID `60929` 单核满载、数据库在宿主退出时仍被写入以及 ready 明显晚于 20 秒的现场表现。

除此之外，Local Server 启动还会对全部原生会话逐项读取 `conversation_items`、解析 `payload_json` 并重新归一化会话资源；该循环没有“历史回填已完成”的迁移门禁。随后 `codexNativeCoordinator.recover()` 会在 execution-host 写出 ready 之前恢复 Codex 世代，并逐个续接、读取非归档线程。现场有 352 条 Codex 原生会话，其中 121 条属于非归档恢复候选。

所以，本次可以确认的是“执行宿主被启动前的历史数据处理拖过了 20 秒”，并能确认无效全量 UPDATE 是确定存在的高开销缺陷；由于当前启动代码没有阶段耗时日志，未启动隔离测试包做计时前，不能把 PID `60929` 的全部耗时只归因于这一条 SQL。全量资源归一和 121 条会话恢复也需要分别计时后收口。

数据库本身通过完整性检查，当前证据不支持“数据损坏”判断。freelist 达到约 548 MiB 说明文件还存在明显膨胀，但压缩数据库不是首要修复；如果启动代码继续全量 UPDATE，单纯 `VACUUM` 只能暂时缩小文件，后续仍会重复产生写放大。

## 建议修复顺序与利弊

### 1. 先停止重复全量回填与全量资源归一

迁移完成后直接跳过一次性字段回填；同时把兼容修复限制为字段缺失的记录，例如只处理 `agent_kind IS NULL OR native_item_id IS NULL`。会话资源历史归一也需要用迁移记录或待处理集合驱动，不能每次启动重新解析全部历史消息。

- 优点：直接消除 92,093 条无效重写，是本次启动超时的根因修复；保留对部分迁移现场的修复能力。
- 缺点：仍需明确“迁移记录存在但数据部分缺失”的恢复策略，不能只依赖一个迁移标记后无条件跳过所有检查；资源归一规则升级时还需要新的迁移编号。

### 2. 修正“活锁存在、rendezvous 尚未写出”的并发语义

发现 execution-host 锁对应进程仍存活时，把它识别为“宿主正在启动”，在同一受限等待流程中观察该进程或 rendezvous；不要立刻再 spawn 一个必然撞锁的宿主。

- 优点：消除二次错误，避免重试把真实慢启动污染成“宿主已存在”；也能保护 SQLite 单写入者边界。
- 缺点：需要处理持锁进程卡死、PID 复用和最大等待时间，不能无限等待。

### 3. 把 20 秒硬超时改为带阶段反馈的安全上限

数据迁移、资源归一、历史会话恢复和 Provider 恢复应分别记录开始、结束和数量；界面应区分“宿主正在迁移/恢复”与“宿主已经失败”。修复无效 UPDATE 后再根据真实基线设置上限。

- 优点：大数据现场不会被一个固定数字误判为失败，用户能看到真实进度。
- 缺点：只把 20 秒改成更长时间会掩盖性能退化，不能作为单独修复。

### 4. 根因修复后再评估数据库回收空间

在数据库副本上验证 `VACUUM` 或受控重建，再决定是否对正式数据执行。

- 优点：可回收约 548 MiB 的空闲页并改善后续 I/O。
- 缺点：需要额外磁盘空间和较长独占时间，属于数据维护动作；未修复重复 UPDATE 前收益不持久。

## 2026-08-15 实施记录

### 移除第四个同名 Zeus 进程

`apps/desktop/src/main/main.ts` 的正式启动入口由 `startDesktopLocalServer()` 切换为主进程内嵌的 `startEmbeddedDesktopLocalServer()`：

- BrowserHost、Local Server、SQLite 和 Agent 调度直接位于 Electron 主进程；
- 正式启动链不再执行 `spawn(process.execPath, executionHost.js)`，因此不会再出现同名的第四个 Zeus execution-host；
- Renderer、GPU 与网络 Helper 仍由 Electron 按安全隔离模型创建，不在本次删除范围内；
- `/api/execution-host/status` 等内部接口名称暂时保留，它们表达运行状态协议，不再代表一定存在独立操作系统进程。
- 升级时如果发现旧版留下的独立宿主，先停止其活动工作并等待完全退出，再由主进程打开 SQLite，避免出现两个写入者。
- 对“旧宿主已持有锁、但尚未发布就绪文件”的慢启动窗口也做了保护：最多等待 45 秒进入可控状态；仍不可控则取消启动，不冒险并发打开数据库。

优点：消除 execution-host 锁、rendezvous、20 秒就绪超时和重复拉起竞争；活动监视器不再出现第二个同名 Zeus。缺点：Local Server 与界面重新绑定，主进程退出或升级时，数据库服务和 Agent 调度也会结束。

### 收紧退出语义

有活动工作时，退出弹窗不再提供“退出界面，任务继续运行”；只允许“停止活动工作并退出”或“取消”。如果运行状态无法读取，退出会被取消并保持应用打开，不再伪造后台继续执行。

优点：界面承诺与真实进程模型一致，不会让用户误以为第四个进程仍在后台托管任务。缺点：用户不能关闭界面后继续长任务，升级也需要先结束当前执行。

### 停止重复迁移写放大

`packages/storage/src/index.ts` 现在只在 `20260803_0001_agent_runtime_framework` 迁移尚未登记时执行 Agent 身份历史回填，并且 UPDATE 只命中缺失字段的记录。当前正式数据库已经登记该迁移，升级后的启动不会再重写 92,093 条已完成记录。

优点：直接消除当前现场已经确认的无效大表 UPDATE、WAL 和检查点写放大。缺点：首次处理真正的旧数据库时仍需执行一次必要回填；会话资源归一与 Provider 历史恢复仍有独立的性能优化空间。
