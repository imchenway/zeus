# Zeus 工具生成图片未进入最终回答诊断

## 结论

本轮三张原型图均已成功生成并写入 Provider JSONL，但它们被外层 `exec` 包装为 `custom_tool_call_output` 中的 `input_image` 内容块，没有成为 Zeus 已支持的顶层 `imageGeneration` 条目，也没有进入最终 assistant 消息。Zeus 因而把外层调用投影为工具活动，并在最终回答到达后按既有规则折叠到处理摘要中。

这不是图片生成失败或客户端刷新延迟，而是“嵌套工具图片”与“助手生成图片”之间缺少提升规则。

## 证据链

1. 本轮 JSONL 第 140 行附近记录了三次外层 `exec` 调用。对应输出均包含 `type=input_image` 的 data URL，图片生成成功。
2. 最终 assistant 消息只包含选择方案的文字，没有图片内容块、受信资源或可见文件链接。
3. Renderer 只把顶层 `imageGeneration` 映射为图片角色；`dynamicToolCall`、`toolCall` 等映射为工具角色。
4. 工具角色进入 `SessionActivityGroup`，最终回答到达后按“轮次最终回答收口”折叠。
5. 既有生成图资源归一化明确要求条目或负载类型为 `imageGeneration`，并从当前 Provider 会话的 `generated_images` 目录读取受信 `savedPath`；嵌套 `input_image` 不满足该条件。

## 为什么会重复

ZEUS-0164 修复的是 Provider 原生顶层 `imageGeneration.savedPath` 链路。本次走的是 `exec -> image_gen -> generatedImage` 的嵌套编排链路，协议形态不同，所以没有命中旧修复。只要 Agent 把需要交付的图片留在工具输出中、最终回答又没有显式资源引用，同类问题就会再次出现；`view_image` 等工具图片也存在相同风险。

## 责任边界与修复方向

### 即时交付约定

生成完成后把最终图片保存到任务目录，并在最终回答中提供受信文件链接。

优点：不改协议即可避免用户找不到交付物。

代价：依赖 Agent 每次遵守，只能提供链接，不能保证图片直接内联显示。

### Zeus 产品修复

在 Provider 投影层识别带明确交付语义的工具输出图片，将其持久化为受控的“助手生成图片”资源；Renderer 独立展示，不归入普通工具活动。

优点：从产品层消除重复漏显，历史恢复和权限校验可以沿用现有生成图链路。

代价：不能把所有工具截图都自动提升，否则调试截图、页面截图和临时预览会污染会话正文；必须有明确的交付标记、文件生命周期和受信路径。

### 推荐方案

采用双层防线：当前 Agent 交付约定立即生效；Zeus 后续只对带 `generatedImage` 交付标记与受控本地路径的图片做顶层提升，不对普通 `input_image` 自动提升。

## 附件类型影响范围

| 来源 | 当前是否受本问题影响 | 原因与边界 |
| --- | --- | --- |
| 用户主动上传的图片、文件、文件夹 | 通常不受影响 | 走独立的附件数组、受信目录和提交链路，不依赖工具活动是否折叠；历史上的发送后延迟显示属于另一类乐观消息同步问题。 |
| Provider 原生顶层 `imageGeneration` | 通常不受影响 | 已有专用条目、受信 `savedPath` 和图片资源归一化链路。 |
| Assistant 正文中的本地文件或网页链接 | 通常不受影响 | 正文 Markdown 链接会被资源归一化；本地文件仍需位于允许目录。 |
| 工具生成且明确要交付的图片 | 受影响 | 若只存在于 `custom_tool_call_output` 的富内容块中，会被当作工具过程折叠。 |
| 工具截图、页面截图、`view_image` 预览 | 技术上同样受影响 | 默认应继续作为过程证据折叠；只有 Agent 明确声明为交付物时才提升。 |
| 工具返回的 PDF、普通文件、网页资源 | 条件性受影响 | 只埋在工具富输出中会折叠；最终回答给出受信链接后可进入现有资源链路。 |
| 工具返回的音频、视频 | 受影响且缺少专用展示 | 当前会话资源预览只有图片和文本/文档，没有音视频播放器；短期只能作为受信文件卡交付。 |
| 工具文本、命令日志 | 不属于附件丢失 | 内容仍保留在可展开的处理过程里；若文本本身是最终交付物，仍应在最终回答中摘要或链接。 |

## 产品修复协议

### 一、由编排层显式声明交付物

工具输出不能仅依赖 `input_image`、`audio` 或 `resource_link` 这类内容类型判断是否展示。编排层需要增加明确的交付语义，例如：

```text
presentation: deliverable
kind: generated_image | file | website | audio
savedPath/resourceRef: 受控本地引用
displayName: 用户可见名称
mimeType: 实际媒体类型
```

优点：可准确区分最终原型图与调试截图，避免正文污染。

代价：工具编排协议、Provider 投影和客户端都需要识别这组字段。

### 二、Provider 投影层持久化并提升

对带交付标记的完整工具输出执行以下步骤：

1. 将内容落到当前 Provider 会话或任务的受控附件目录，不把 base64 存入数据库或发送给 Renderer。
2. 校验真实路径、允许目录、普通文件、文件头、大小上限和当前会话归属。
3. 生成稳定资源编号并关联来源工具调用、轮次和条目，避免重放时重复。
4. 投影为独立的会话资源条目，不再归入普通 `SessionActivityGroup`。

优点：可以复用现有受信文件与历史恢复机制，解决刷新、折叠和重放后的可见性。

代价：需要新增数据迁移与兼容逻辑；历史记录只能安全迁移具备明确交付标记和合法文件路径的条目，不能从所有 data URL 猜测。

### 三、Renderer 独立展示交付资源

普通工具活动继续折叠；交付资源作为正文条目展示，并与对应的最终回答相邻。图片可内联预览，文件显示资源卡，网页显示链接卡；音视频需新增预览类型，未实现前退化为文件卡。

优点：既保留过程区的整洁，又保证真正的交付物一直可见。

代价：新增音视频预览会扩大资源模型、内容读取接口和安全校验范围，可以在图片与普通文件稳定后再做。

### 四、最终回答保底

即使已经生成独立交付资源，Agent 的最终回答仍应引用资源编号或受信文件链接，避免出现“图在上面”但无法定位的回答。

优点：旧客户端或提升失败时仍有可恢复入口。

代价：这是保底契约，不能替代产品层修复。

## 实施结果

2026-08-15 已完成产品修复，不再只依赖 Agent 在最终回答中补链接：

1. 会话资源新增 `delivery=assistant` 交付身份。显式 `payload.deliverables`、`payload.presentation.deliverables`，以及结构化资源中的 `delivery=assistant` 或 `presentation=deliverable` 都会进入助手交付资源。
2. 兼容本轮真实 `generatedImage` 输出：外层工具结果同时具备图片内容块和“Generated images are saved … as … by default.”稳定回执时，才读取其中的生成图路径。
3. 兼容路径必须属于当前 Provider 线程自己的 `generated_images/<providerThreadId>` 目录，并通过真实路径、普通文件和 PNG/JPEG/GIF/WebP 文件头校验；任意绝对路径、伪扩展名或其他线程目录都不会被提升。
4. 图片和音频富内容块的 base64/data URL 在持久化前递归移除，只保留条目类型、文字回执和交付元数据。
5. Renderer 将助手交付资源排除出工具活动与轮次处理折叠。纯图片交付沿用生成图内联预览；文件、网页或混合交付显示资源卡。
6. 同一工具条目中的普通资源不会跟随交付物一并进入正文；图片条目也只展示带交付身份的图片。旧的顶层生成图历史没有该字段时仍走兼容回退。

该方案不需要数据库迁移：交付身份写入既有资源 `displayJson`，资源稳定编号、目标授权和历史恢复继续复用原表。

## 当前附件边界

- 用户上传图片、文件和文件夹：原链路不变。
- Provider 顶层生成图：原链路不变，并带助手交付身份。
- `generatedImage` 嵌套生成图：符合回执和线程目录校验时自动显示在正文。
- 普通工具截图、网页截图、`view_image`：没有显式交付身份，继续留在可展开处理过程，防止正文被调试证据污染。
- PDF、普通文件、网页：编排层显式放入 `deliverables` 后显示资源卡。
- 音频、视频：可以作为受信文件卡交付；当前仍没有专用播放器，这是明确的展示限制，不属于再次丢失。
