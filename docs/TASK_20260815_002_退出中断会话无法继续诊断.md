# 退出中断会话无法继续修复

## 结论

退出只应中断当前执行轮次，不应废弃整条会话。用户重新打开 Zeus 后，应当能够在原 Codex thread 中发送下一条消息；旧轮次不会从中断位置继续生成，而是以
`interrupted` 终结，新消息创建下一轮。

2026-08-15 的正式现场违反了这个口径。根因不是 `interrupted` 不可续，而是旧运行时把一批 thread 写入了系统默认 Codex
Home；Zeus 0.3.14 固定使用专属 Codex Home 后，没有兼容迁移这批错位历史。

当前源码已补上安全、幂等的历史 thread 迁移。应用启动时会先处理精确错位记录，再创建会话协调器和 Codex app-server。迁移只复制不删除；真正
`thread/resume` 并验证旧轮次已终结后，才会把会话恢复为可用状态。

## 受影响范围

正式数据库当前共有 386 条 Codex 原生会话记录，并非全部都是同一问题。

| 存储情况                  |  数量 | 当前列表内 | 暂停态 | 处理        |
|-----------------------|----:|------:|----:|-----------|
| 已在 Zeus 专属 Codex Home | 254 |    83 |  89 | 不迁移       |
| 错位到系统默认 Codex Home    |  41 |    38 |  38 | 本次迁移      |
| 历史记录没有持久化路径           |  86 |     8 |  10 | 不扫描、不猜测文件 |
| 其他历史路径                |   5 |     0 |   0 | 不在本次迁移范围  |

41 条错位记录对应的 JSONL 文件全部存在，缺失数为 0，合计 87,730,813 字节，最大单文件 11,986,036
字节。因此本次使用流式摘要校验，不会把全部历史正文一次性载入内存。

86 条没有路径的历史记录不能由此推导为“全部不可续”。Provider 可能仍能按 thread ID 在正确 Home 中恢复；源码遵守“不扫描文件猜测
Provider 身份”的边界，只在真实 `thread/resume` 结果中裁决。

## 正式现场只读证据

本轮只读检查当前正式应用、正式数据库和对应 JSONL，没有停止正式 Zeus，没有写正式数据库，也没有移动或复制正式 Provider 文件。

- `/Applications/Zeus.app` 当前版本为 `0.3.14`，bundle ID 为 `dev.hypha.zeus`。
- `/Users/david/.zeus/data/zeus.db` 的 `PRAGMA quick_check` 返回 `ok`，可排除数据库损坏导致本次不可续。
- 最近由退出终结的三条非归档 Codex 会话仍为 `status=open`，但当前 `provider_state=paused`。
- “计划模式确认消息错误”会话在重开后分别于 15:16、15:27、15:41 三次提交新消息，全部失败；“codex 里可打开的文件、链接等都是有颜色的样式”会话也失败一次。
- 四次失败均为 `no rollout found for thread id ...`，新提交没有取得 `providerTurnId`，说明请求没有进入新的 Provider turn。
- 受影响会话数据库中持久的 `provider_thread_path` 位于 `/Users/david/.codex/sessions/`，对应文件真实存在，但不在
  `/Users/david/.zeus/providers/codex/sessions/`。
- 代表性 JSONL 的最后事件是 `turn_aborted`，时间与 14:35 的强制退出一致。Provider 已明确终结旧轮次，具备开启下一轮的语义前提。

## 根因链

1. 受影响会话由旧运行时创建，当时没有把 Zeus 专属 `CODEX_HOME` 固定传给内嵌 Codex app-server。
2. Codex 因此把 rollout 写进系统默认 `/Users/david/.codex`；Zeus 数据库也如实记录了该真实路径。
3. 用户选择停止活动工作并退出。Zeus 把本地轮次持久化为 `interrupted`，JSONL 同时落下 `turn_aborted`。
4. 0.3.14 修正后续 app-server 的 `CODEX_HOME`，当前运行时只在 Zeus 专属目录查找 thread。
5. 用户再次发送时，当前 app-server 无法在专属 Home 找到旧 thread，于是返回 `no rollout found`；Zeus 将会话保持为 `paused`。

因此这是“运行目录修正缺少历史兼容迁移”，不是“退出中断会话设计上不可继续”。

## 实现

### 启动顺序

`packages/local-server/src/index.ts` 在创建 Codex 运行时与会话协调器之前执行错位 thread 迁移。这避免启动后先触发一轮必然失败的
`thread/resume`。

### 文件迁移

`packages/local-server/src/misplacedCodexThreadMigration.ts` 执行以下约束：

1. 只枚举 Zeus 数据库中已持久 `provider_thread_id + provider_thread_path` 的主记录，不加载全部消息正文。
2. 只接受精确路径位于允许的旧 `sessions` 根目录下的普通 `.jsonl` 文件；符号链接、越界路径和非普通文件全部拒绝。
3. 从 JSONL 首条 `session_meta` 复验 `payload.id` 与数据库 thread ID 一致。
4. 目标保留原有年、月、日目录和文件名，但必须仍位于 Zeus 专属 `sessions` 根内。
5. 复制到目标目录内的随机临时文件，权限设为 `0600`；流式计算源和目标的 SHA-256，同时复验源文件大小、修改时间和文件身份没有变化。
6. 文件同步后使用不覆盖的原子发布；目标已存在时，只有 thread 身份和完整摘要都一致才接纳，冲突时保留双方并失败关闭。
7. 源文件永不移动、不删除。只有文件校验成功后，才在数据库事务中把 `provider_thread_path` 和 `native_session_path` 切换到专属
   Home。
8. 迁移成功、已有相同目标、跳过原因和源目标路径都写入本地审计日志；成功或幂等接纳的记录同时保存摘要。

### 状态恢复

文件迁移本身不会将 `paused` 直接改成 `ready`。用户再次发送时，现有协调器会：

1. 使用 Zeus 专属 Codex Home 恢复原 thread ID。
2. 读取 Provider 快照并对齐历史轮次。
3. 确认 Provider 当前空闲，且上一轮已在安全边界终结。
4. 恢复为 `ready`，再把新消息作为下一轮提交。

这会保留原 thread 身份和上下文，也不会重放之前已失败、没有 `providerTurnId` 的消息。

## 方案取舍

### 当前方案：受控复制后恢复原 thread

优点：

- 恢复原 thread、原上下文和原消息历史。
- 继续保持 Zeus 账号、配置、技能和会话目录隔离。
- 源文件保留，中途崩溃时可通过相同摘要幂等接纳已发布目标。
- 冲突时不覆盖任何一方，可通过审计日志精确定位。

缺点：

- 首次启动需要复制和计算摘要，受影响文件越大，该次启动越慢。
- 文件迁移成功只代表存储身份已修复；会话仍需真实 Provider 恢复验证后才能标记可用。

### 不采用：临时切回系统默认 Codex Home

优点：无需复制 rollout，旧 thread 可以直接在原目录查找。

缺点：会重新混用系统 Codex 的账号、配置、历史、插件和远程状态，破坏 Zeus 专属运行身份；同一 app-server 世代也不能安全地在两个
Home 间热切换。
