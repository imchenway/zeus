## 2. 已采纳且不再反复摇摆的架构决策

1. 采用“本地优先模块化单体 + 独立持久执行核心 + Provider 适配器 + 分层存储 + CQRS-lite”。
2. 不为了形式上的高可用改成云端微服务；同一台 Mac 上的多个服务不能消除设备级单点。
3. 不把主业务库从 SQLite 迁往 PostgreSQL；本地单用户场景继续使用原生 SQLite、WAL 和唯一写入者。
4. 不因当前性能问题整体改写为 Rust；先消除全量读取、重复事实、同步阻塞和巨型模块。
5. Provider 原生会话继续作为模型上下文、原始工具事件和 Provider 恢复协议的事实源。
6. Zeus 业务库继续作为项目、任务、产品会话、提交、审批、授权、变更和统一产品状态的事实源。
7. Zeus 不新增第三份完整会话 JSONL，也不直接改写 Provider 原生 JSONL。
8. 采用小型事务状态账本、Inbox/Outbox 和可重建投影，不采用“所有原始事件永久重放”的完整 Event Sourcing。
9. 先保持一个可靠的业务 SQLite；只优先物理拆分大型资产和可重建索引，不按领域创建大量数据库。
10. 产品会话、运行分段、原生会话、提交、轮次和模型请求使用根目录 `CONTEXT.md` 中的固定语义。

### 总体收益

- 保留本地低延迟、隐私和离线可读能力。
- 让会话切换、启动恢复和数据库增长不再与全部历史线性绑定。
- Renderer、Main、Provider 和重型后台任务形成独立故障域。
- 数据权威、恢复、备份和升级交接拥有可审计边界。

### 总体缺点

- 需要进行多阶段数据迁移、协议演进和旧投影退役，不能一次性大爆炸切换。
- Inbox/Outbox、资产生命周期、投影版本和进程租约会增加实现复杂度。
- 读投影可能短暂落后于写事实，界面需要明确展示同步状态。
- 单机架构不能消除整机损坏这一故障域；多设备同步属于独立产品能力，需求未定义前本轮不接入 iCloud 或 Google，也不把恢复包复制冒充同步。

## 3. 目标运行拓扑

```text
Electron Renderer ─────┐
Electron Main Shell ───┼─ 本机认证协议 ─ Zeus Core / Execution Host
远程控制入口 ──────────┘                    │
                                  ┌─────────┼──────────┐
                                  │         │          │
                              业务 SQLite  Provider   后台 Worker
                                  │         │          │
                              资产存储    Codex/Pi   索引/图谱/Git
                                  │         │
                              大型内容    原生会话
```

- Renderer 只管理交互、当前视口和有界缓存。
- Electron Main 只管理窗口、系统能力、升级和 Browser Host。
- Zeus Core 是唯一业务写入者，管理状态机、调度、恢复和本机 API。
- Provider Worker 管理 Codex、Pi 等运行时及其原生身份。
- Heavy Worker 管理代码索引、图谱扫描、大型 Git 分析和其他 CPU/磁盘密集工作。

## 4. 性能与可用性目标

以下是待现场校准的产品 SLO，不是当前已达到的事实：

| 指标 | 目标 |
| --- | --- |
| 会话点击后的目标身份反馈 | P95 不超过 16ms |
| 已缓存会话的首个真实内容帧 | P95 不超过 100ms |
| 冷会话首个历史分页 | P95 不超过 300ms |
| Provider 事件接收到 Renderer 可见 | P95 不超过 100ms，不含 Provider 网络时间 |
| Zeus Core 异常重启后的业务可读恢复 | P95 不超过 5s，且不扫描全部历史 |
| 会话首屏返回体 | 默认不超过 1MiB，超限内容改为句柄或分页 |
| 正文内存 | 与当前视口和有界缓存相关，不随全部会话历史无界增长 |
| 未知 Provider 结果 | 永不自动重发，恢复后继续核对原身份 |
