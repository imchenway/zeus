# 计划确认入口丢失导致后续消息阻塞

## 当前阶段

已完成正式数据只读诊断、源码修复、行为探针、静态门禁、构建和独立身份 `Zeus Test.app` 打包验证。未修改正式数据库，未操作正式会话，未提交、推送或发布。

## 用户现象

- 输入“继续”后，消息进入“后续消息（1）”。
- 队列说明为“完成上方计划确认后按顺序自动发送”。
- 页面上没有“实施此计划？”确认卡片，因此用户没有任何可完成门禁的入口。

## 只读现场证据

- 正式数据库 `PRAGMA` 与只读查询正常。
- 截图对应会话为“任务会话：代码高亮呢？”。
- 会话存在一条 `pending` 的 `conversation_plan_actions` 记录，创建时间为 `2026-08-22T03:24:15.062Z`。
- 同一会话存在一条正文为“继续”的 `queued` submission，创建时间为 `2026-08-22T04:13:56.622Z`。
- 队列服务按持久化计划请求正确返回 `waitReason=plan_confirmation`。
- Renderer 的 `conversationSnapshotV2Adapter` 却把 `planImplementationRequests` 固定写成空数组。
- `SessionWorkspace` 只会从 `state.planImplementationRequests` 渲染计划确认卡片，因此形成“服务端门禁存在、客户端入口缺失”的死锁。

## 修复语义

- 待处理计划确认必须随 V2 首屏一起恢复，不能依赖打开页面后恰好收到实时事件。
- 普通后续消息在计划确认完成前继续保持排队，不绕过门禁。
- `implement` 固定进入 Default，`refine` 固定进入 Plan；本任务不改变既有计划控制动作语义。
- 待处理计划确认属于需要实时同步的状态；其他窗口完成确认后，当前窗口应能收到终态并解除入口。
- 若队列声称等待计划确认但首屏没有返回相应请求，应拒绝投影为可发送界面并触发有界重读，不能继续显示一个无法操作的假状态。

## 取舍

- 优点：计划卡片在切换会话、重启应用和 V2 水合后都能恢复；既有队列顺序和控制动作门禁保持不变。
- 缺点：V2 首屏的待处理交互响应会增加一个很小的计划请求字段；跨版本连接旧 Core 时仍需通过兼容默认值与一致性校验安全失败。

## 验证边界

- 不新增或恢复单元测试体系。
- 使用格式检查、`pnpm lint`、`pnpm typecheck`、`pnpm build`、架构门禁和必要的行为探针验证。
- 桌面运行验收只能使用独立身份 `Zeus Test.app` 与独立数据目录，不启动或替换正式应用。
- 未经用户明确要求，不执行 Git commit、push、merge、revert 或正式发布。

## 实施结果

- `pending-requests` 首屏接口同时返回普通 Provider 请求和最新待处理计划确认请求。
- V2 Renderer 适配器不再把 `planImplementationRequests` 写死为空数组，计划确认卡片可随会话切换和应用重启恢复。
- 待处理计划确认纳入 Controller 与工作区的实时状态判断，其他窗口解决请求后可以同步终态。
- 待处理交互刷新同时校准计划请求列表，不再只刷新普通 `request_user_input` / 审批请求。
- 队列返回 `plan_confirmation` 但没有对应待处理计划请求时，水合会有界重试三次；仍不一致则明确中止并报告，不再显示无入口的死锁界面。
- 既有队列门禁、实施固定 Default、修订固定 Plan、控制动作优先级和普通消息顺序均未改变。
