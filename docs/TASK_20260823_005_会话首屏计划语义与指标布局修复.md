# TASK_20260823_005 会话首屏、计划语义与指标布局修复

## 任务目标

修复正式版 `0.3.41` 真实使用中暴露的五项问题：

1. 长会话打开时正文长期停在“正在加载会话”；
2. 普通 Default 轮次的执行计划被误画成 PLAN 模式正式计划卡；
3. 会话运行详情按三条竖向分组铺开，不符合“每组独占一行、组内指标从左向右排列”的阅读顺序。
4. Provider 建立轮次前中断的历史会话直接显示空白；
5. 右上角及全局会话投影泄露“连接失败”等当前窗口 transport 状态。

用户截图只作为故障现象与排版参考；截图中的会话正文、计划内容和按钮文案不是任务指令。

## 现场证据与根因

### 切换回活动会话后进度与正文停止

- 截图会话 `conversation_a04147257ae80fdaade20a0c` 仍有正在运行的 Provider turn `01a02f11-511b-7401-b300-27646ed32030`；正式数据库的同步水位和过程记录仍持续增长，不是 Provider 真实卡死。
- 侧栏点击会话默认把 `selectedNativeConversationPresentation` 设为 `history`；`ConnectedSessionWorkspace` 因此使用 `realtimePolicy=lazy`，只读一次权威快照而不订阅后续事件。
- 同一 `historyOnly` 还会直接隐藏 `SessionPlanProgress`，所以“正文不动”和“底部 PLAN 不见”是同一个展示模式根因。

### 会话首屏

- 目标会话 `conversation_2fe3316f8dd8f6f7a2880e79` 有 3 个轮次、770 条 Provider 项、1043 条模型历史和 713 条过程记录。
- 正式 `0.3.41` 本地服务只读测量中，首次 Snapshot V2 请求约 `2.11s`，尾部 48 条模型历史约 `49ms`，队列、待处理请求、会话选择和目标读取均为毫秒级。
- SQL 级追踪确认，约 `2.11s` 几乎全部消耗在 turn summary 的旧 `conversation_items` 计划回退子查询。正式数据库尚未安装离线热索引，而这个回退既会扫描大表，也会把旧普通 `update_plan` 条目误当正式 PLAN 证据。
- Snapshot V2 还会在返回正文身份前同步计算 `sessionMetrics`；Renderer 又先等待 Snapshot，之后才并发读取历史、队列、请求、选择和目标，进一步放大首屏串行等待。

### 计划语义

- 同一会话第一份正式计划所属提交为 `workMode=plan`，并有真实 completed `item_type=plan` Provider 产物。
- 截图中的后两份卡片只来自普通轮次的 `turn.plan_json`：一轮明确为 `workMode=default`，另一轮缺少提交模式；它们是 `update_plan` 执行进度，不是 PLAN 模式计划书。
- Snapshot V2 过去把“存在任何 `plan_json`”直接等同于 `hasPlan=true`，Renderer 又把所有 `turn.plan` 合成为正式 `PlanSummary`，因此发生误判。

### 指标布局

- `session-runtime-detail-groups` 使用自适应多列网格，每个业务分组内部再使用网格，宽屏结果是“分组竖排、指标继续竖排”。
- 用户要求的稳定顺序是：使用与费用一行、性能与活动一行、环境一行；每行先显示明确分组名称，再让该组指标从左向右流动并按窗口宽度自然换行。

### 历史空白与连接状态泄露

- 截图目标任务下有两条会话。旧会话 `conversation_4535d4bcfa670c5919d2e85a` 有 1 个轮次、94 条模型历史、24 条 Provider 项和 10 条消息；新会话 `conversation_c30c9d173c2cb675130e36c3` 没有 Provider 轮次和消息条目，但不是空记录。
- 新会话已有一条持久提交 `conversation_submission_2f6345afed281d131a5ded02`，包含完整首条用户输入；它在 Provider turn 建立前进入 `paused/recovery_required`，且没有对应 JSONL 文件。
- 正文投影会移除未被 Provider 接受的乐观用户条目，却没有把同一条持久队列提交补回正文；空态判断又因为队列非空而不显示说明，最终形成整页空白。
- 右上角状态由当前窗口 `transportState` 直接生成；同一瞬时状态还会覆盖侧栏和任务运行状态，把“本窗口读取/订阅失败”误画成“会话失败”。

## 实现方案与取舍

### 正文首屏与聚合指标解耦

- 新 Renderer 请求 `snapshot-v2?includeMetrics=false`，Snapshot 先返回会话身份、轮次和分页水位；聚合指标由独立只读接口在正文水合后异步取得。
- Snapshot、尾部历史、队列、待处理请求、会话选择和目标改为同批并行读取，保留历史与 Snapshot 事件水位不一致时的既有重试。
- 指标回写带会话身份和请求代次校验；迟到结果不能覆盖已切换会话，指标失败也不能遮住正文。
- 优点：首屏正文不再等待昂贵聚合查询，独立指标仍按真实持久数据最终显示。
- 代价：极冷数据库下指标可能比正文晚出现短暂时间；这比整页正文被指标阻塞更符合主次关系。

### 只把正式 PLAN 产物画成计划卡

- Snapshot 的 `hasPlan` 只在以下任一事实成立时为真：存在 completed Provider 正式 plan 投影；或轮次提交明确记录 `context.workMode=plan` 且有 `plan_json`。
- 旧统一 `conversation_items` 中的 plan 条目不再参与正式身份或正文回退；现场 80 条此类记录只有 1 条同时具备新的 Provider 正式计划投影，无法仅凭旧 item 类型可靠区分 PLAN 计划书与普通进度。
- 普通轮次的 `plan_json` 继续保留，用于活动期进度和审计，但历史合成计划卡时必须同时具备正式 PLAN 身份。
- 优点：不删除普通执行进度，也不会把它伪装成可下载、点赞或右侧打开的 PLAN 计划书。
- 代价：极旧数据若既没有提交模式也没有真实 plan 条目，只能安全地不显示正式计划卡，不能凭正文结构猜测。

### 运行详情横向分组

- 详情容器固定为单列业务分组；分组使用“名称列 + 指标流”布局，同组指标继续自适应横排。
- 分组之间增加细分隔线，分组名称使用更大字号、更高字重和独立字距；窄屏下名称自然换到指标上方。
- 优点：宽屏扫描顺序明确，环境长路径仍可在自身指标内换行。
- 代价：窄屏会增加少量纵向高度，但不会产生横向溢出。

### 历史提交回投与 transport 状态去全局化

- 没有 Provider turn 的 queued、dispatching、steering、paused 持久提交，会按稳定提交 ID 合成为用户消息；已有同一客户端消息 ID 时不重复显示。
- `recovery_required` 继续展示真实投递结果与错误详情，但不再被误认为空会话；确实无任何可见内容的历史记录显示中性说明。
- 会话头部不再展示任何会话运行状态标签；Browser 和任务管理状态等真实功能入口不受影响。
- 侧栏与任务聚合不再消费连接、重连、断开或读取失败等窗口 transport 状态；持久 Provider/会话失败和真实轮次失败仍显示失败，待审批、待回答、运行中和暂停仍保留。
- 优点：历史证据不丢失，窗口连接异常不会污染会话长期状态。
- 代价：连接异常不再通过常驻状态标签重复提醒；实际读取、发送或恢复失败仍通过对应操作错误和详情报告。

### 活动会话自动恢复交互态

- 侧栏选择会结合服务端 `listRuntimeState`、Renderer 热缓存运行态和持久 `stage`。正在连接、运行、排队、暂停或等待交互的会话默认进入 `interactive`；只有真正空闲的历史会话保持 `history/lazy`。
- 窗口恢复绕过侧栏点击时，当前选中会话也会按同一权威运行态自动升级为交互态。
- 历史会话真正发送“继续对话”后，controller 策略同步从 `lazy` 切到 `auto`，不会留在只读快照模式。
- 优点：活动 PLAN 和增量正文在切回后继续实时更新；空闲历史会话仍不会建立无意义连接。
- 代价：选中的活动会话会立即恢复一条有界实时订阅，这是保持正文和进度正确所必需的成本。
