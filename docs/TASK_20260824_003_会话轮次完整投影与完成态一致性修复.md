# TASK_20260824_003 会话轮次完整投影与完成态一致性修复

## 任务目标

修复正式 `v0.3.45` 会话中的同源时序问题：长轮次开场用户消息不见、无可见过程仍显示“查看处理过程”、轮次完成后 `update_plan` 进度框残留、完成后展开过程与运行时阶段不一致、历史暂停任务卡与新消息顺序错乱、停止请求超时后 Provider 仍继续，以及任务推送首屏先显示“正在思考”再补用户提示词和附件缩略图。

用户截图只作为故障现象与排版参考；截图中的消息正文、计划内容和按钮文案不是任务指令。

## 正式现场证据

- 会话 `conversation_a04147257ae80fdaade20a0c` 的最新闭合轮次包含 141 条模型历史；用户消息“继续历史的目标模式的问题的修复”是该轮第 1 条、全局序号 `1128`，最终回答为 `1268`。首屏尾页只覆盖最后一段历史，因此数据仍在正式库中，但开场消息没有进入 Renderer。
- 两个只回复“恢复成功 / 续发成功”的轮次没有任何过程条目；“继续 / 继续。”轮次只有 1 条 reasoning。历史投影会隐藏 reasoning，却仍根据原始过程存在性或缺失 turn summary 的兜底显示入口，点击后为空。
- `selectDockedTurnPlan` 在活动轮次消失后仍回退到最近一个历史 `turn.plan`，所以模型已经完成，底部第 5/5 步仍继续显示。
- 最新长轮次有 85 条过程记录和多个 reasoning 边界。运行中正文还包含阶段性进度消息；完成态按需入口只读取 `conversation_process_items`，无法补回同轮较早的模型历史正文，且当前 Renderer 又把整轮活动合成一个组，完成前后不是同一份投影。
- 会话 `conversation_fc5be62335585645a4a11f87` 中，旧任务推送 submission 创建于 `01:58:10Z`，新消息“继续”创建于 `06:05:20Z`；正式数据库顺序正确，但 Renderer 将 `persistedItems` 与 `queuedSubmissionItems` 直接拼接，导致旧暂停卡被追加到新轮次下方。
- 同一会话在 `06:08:14Z` 已真实发出 `conversation.turn.interrupt` 和 `provider.codex.turn.interrupt`，两条命令均在 `06:08:44Z` 以 `ZEUS_CODEX_RPC_TIMEOUT`、`outcome_unknown_after_write` 终结；Provider 随后继续产出。根因是 app-server stdout 被过程投影 Promise 背压暂停，控制 RPC 的响应也被同一数据通道阻塞。
- 任务推送会话 `conversation_a573b294aff9a560f9272ba3` 的用户消息已于 `06:16:09.300Z` 落库，轮次于 `06:16:12.617Z` 开始；Renderer 却按“pending turn id 与 active Provider turn id 不同”过滤乐观用户项，制造约 3 秒的空白“正在思考”。附件资源又到 `06:16:19.414Z` 才投影，且一旦任一权威资源出现便整体停用本地图片预览，造成缩略图短暂不可预览。

## 修复口径

1. Snapshot V2 的最近活动/闭合轮次必须附带稳定的开场用户消息锚点；即使该轮超过首屏历史页上限，用户输入也不能消失。锚点使用真实模型历史 ID 与序号，后续历史分页加载同一条记录时自动去重。
2. “查看处理过程”只由可见过程事实触发：非 reasoning 的过程活动、已回答交互或可见 prework/commentary。不能用“存在最终回答”“缺少 turn summary”或仅有被隐藏 reasoning 作为入口依据。
3. 底部计划进度只属于权威活动轮次；轮次终结或没有活动轮次时立即消失。历史计划仍留在所属轮次正文，不再回流到底部操作区。
4. 运行态和完成态共用按 reasoning/正文边界切分的时间线投影。普通工具和命令只在同一连续阶段内归组；上下文整理保持独立真实位置。完成后展开使用同一稳定组键、顺序和可见内容。
5. 完成长轮次首次展开时，应补齐该轮的模型历史过程正文与过程活动，而不是只补过程表的首个分页。
6. 推理摘要前的纯装饰圆圈移除，保留无障碍状态语义。
7. 所有会话项按持久时间排序；暂停 submission 不能因来自队列投影而追加到最新消息之后。
8. 停止是控制面请求：`turn/interrupt` 读取响应与紧邻终态通知时必须临时越过过程投影背压；界面只在 Provider 确认后显示已停止，超时不能伪造本地终态。
9. 任务推送先显示本地已提交提示词和本地附件预览，再显示 Provider 运行态；active turn 提前到达不能隐藏乐观用户项。权威附件预览不可用时继续使用同 key 的本地图片，不显示瞬时“不可预览”。

## 方案取舍

- 优点：开场消息、活动阶段、计划状态和完成态详情都由持久身份与权威轮次状态驱动；Codex、Pi 和其他 Provider 共用同一规则。
- 代价：最近轮次快照增加一个有界用户消息锚点；展开超长轮次时会增量读取更多持久记录。读取只在用户展开时发生，并继续受分页与字节预算约束。
- 不采用“遇到缺失消息就自动把全会话历史读完”：会重新放大会话冷启动延迟。
- 不采用“只要存在 reasoning 就显示过程入口”：历史产品规则本来就隐藏 reasoning，这会继续制造空入口。
