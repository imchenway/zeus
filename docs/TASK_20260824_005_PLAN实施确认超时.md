# PLAN 实施确认超时

## 用户现象

- PLAN 完成后点击“是，实施此计划”，控制消息先长期显示“排队中”。
- 约 30 秒后变为“发送结果待确认”，错误为 `Codex app-server request timed out: thread/read`。
- 本任务只读核对正式 SQLite、Provider JSONL 与运行日志；没有修改正式数据，也没有自动重发失败消息。

## 现场证据

- 正式会话 `conversation_a573b294aff9a560f9272ba3` 的实施提交创建于 `2026-08-24T07:37:41.402Z`，在 `2026-08-24T07:38:11.519Z` 进入 `paused/recovery_required`。
- 提交没有 `provider_turn_id`、没有 `dispatched_at`，错误精确为 `ZEUS_CODEX_RPC_TIMEOUT: thread/read`。
- 对应 Provider JSONL 中不存在实施控制消息，证明请求在 `turn/start` 前失败，不能自动重放，也不能写成模型已收到。
- 计划动作记录为 `implemented` 只表示用户已经选择“实施”；实际发送结果仍由 submission 独立记录。当前界面显示“发送结果待确认”是失败关闭结果，但两个状态名称容易造成理解冲突。

## 根因

v0.3.47 已让 `turn/interrupt` 临时越过异步事件投影造成的 stdout 背压，但派发前的 Provider 权威 `thread/read` 仍使用普通读取。长轮次事件投影未完成时，app-server stdout 会暂停；权威读取请求虽已写出，响应却无法被当前进程消费，最终在 30 秒超时。PLAN 控制动作必须先通过该读取确认线程真实空闲，因此停在队列阶段。

## 修复

- 为 `readThread` 增加显式 `priority: 'control'`，只允许控制面调用选择优先读取。
- Provider 线程权威检查使用控制优先级；历史分页、普通详情读取继续服从现有背压。
- `turn/interrupt` 继续保留 2 秒终态通知窗口；权威 `thread/read` 在响应后的下一轮事件循环立即恢复普通背压，避免扩大无界事件读取窗口。
- 删除“Zeus 不会自动重发，避免模型收到重复消息”的用户界面说明；保留“发送结果待确认”、错误详情和底层禁止自动重放的安全策略。
- 未确认投递统一使用黄色“发送结果待确认”，只有明确 `failed` 才使用红色失败态；`thread/read`、错误码和原始信息收入“技术详情”。
- 持久记录确认收敛为“正在确认发送结果”；有“修改后重发”按钮时不再重复解释输入内容已保留。
- 通用错误弹窗不再默认显示重复的操作指导；业务传入的具体摘要、折叠详情和操作按钮仍保留。

## 取舍

- 优点：PLAN 实施、普通队列派发和恢复前的权威空闲判断不会再被同一进程的慢正文投影反向阻塞。
- 缺点：控制读取期间会短暂恢复 stdout；若投影本身长期失败，读取成功后仍会重新进入背压，不能掩盖投影故障。
- 仍然禁止自动重放超时提交；只有 Provider 精确接纳证据才能把 submission 写成已发送。
