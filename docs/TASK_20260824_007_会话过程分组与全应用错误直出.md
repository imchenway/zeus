# TASK_20260824_007 会话过程分组与全应用错误直出

## 任务目标

统一修复三类会话与错误交互：同一 Provider 轮次的操作反复拆成多个顶层组；操作失败显示标题、友好解释、恢复建议和“技术详情”等重复层；失败消息又被自动回填到输入框，可能覆盖用户后来输入。

本任务以用户当前实施计划为准，覆盖并取代 TASK005 中“发送结果待确认 + 技术详情 + 修改后重发”的旧界面口径。底层禁止未知结果自动重放的安全规则继续保留，但不再把解释性句子显示给用户。

## 实施口径

### 1. 同轮过程只生成一个活动组

- `projectTranscriptRows` 先按 `turnId` 收集该轮所有命令、文件、搜索、网页和工具活动，再在首个操作位置只发出一次 `activity:${turnId}`。
- reasoning、commentary、失败状态、超过 32 条和分页增量都不能刷新或拆分该顶层身份；新增操作只更新组内明细。
- 组内明细保持原始时间线顺序；摘要类别通过集合去重。最新 reasoning 仍是该轮唯一灰色状态行并固定在过程底部。
- 运行态、完成态和历史分页共用相同的活动行投影；不同 `turnId` 仍各自独立。

### 2. 全应用错误只显示原始一行

- `ApplicationErrorOptions` 只保留语言与必要主操作，类型层删除标题、摘要、来源、发生时间和详情字段。
- `formatVisibleApplicationError` 统一读取结构化 `code`/`error` 与 `message`，避免重复错误码前缀，把多行空白压成一行，并继续执行密钥、token 和密码脱敏。
- `ApplicationErrorDialogHost` 只渲染一段错误代码文本；关闭、刷新、重试或存储恢复等必要按钮保留，不渲染图标说明和折叠详情。
- 会话失败、轮次失败、分页、工具结果、资源、Browser、Git、设置、启动与错误边界复用同一格式。捕获异常的入口尽量保留原始对象，避免先转换成“操作失败，请重试”而丢失错误码。
- Provider 错误行不再显示角色标题、payload、stack、时间或 source；即使异常对象携带资源或上下文，也只渲染错误行。

### 3. 失败后不回填 Composer

- `send_failed`、`send_uncertain` action 不再携带 draft、附件、Browser 内容或上下文，Reducer 只更新消息状态和错误。
- 启动读取持久 pending envelope 时使用 `preserveComposer` 投影失败气泡；Composer 保持自身已持久草稿，不从失败 envelope 合并内容。
- 删除 `user_confirmation` 队列恢复、附件合并、Browser 评论合并和上下文合并路径；失败记录不再被删除后搬回输入框。
- 用户输入新草稿、附件、Browser 内容或上下文后，才清除没有接纳证据的本地 pending 账本；迟到失败不能覆盖当前 Composer。
- Provider 写入前无法派发的 submission 收敛为持久 `failed`，保存原始错误和 submission outcome；缺少错误时使用 `ZEUS_NATIVE_SUBMISSION_NOT_DISPATCHED: The submission was not dispatched to the provider.`。
- 写出后结果未知继续保留 `outcome_unknown`，既不自动重发，也不开放 retry API 重放。

## 数据与兼容边界

- 外部 API 和 SQLite 表结构不变。
- `ConversationSubmissionRepository.updateStatus` 新增仅供内部协调器使用的“保留原错误”和“保留 submission outcome”选项，避免失败收敛破坏既有审计和安全结果。
- 旧版本留下的 `paused/user_confirmation` 记录仍能投影为失败气泡；Renderer 提供缺省错误，但不会恢复输入框。

## 方案取舍

- 优点：同轮结构稳定，长轮次不会因 reasoning 或分页出现十几个“运行了命令”；错误信息可直接复制用于排障；失败消息不再污染新草稿。
- 代价：错误界面不再提供友好原因和恢复说明；复杂活动组展开后可能较长。活动组默认折叠且按需读取，必要恢复动作仍以按钮保留。
- 不采用自动重发：Provider 是否已接收在超时场景不可安全推断，自动重放会制造重复用户消息。
- 不采用“失败后自动回填但检测草稿冲突”：附件、Browser 评论和上下文的合并语义仍可能重复或覆盖，且与用户明确要求相反。

## QA 夹具

- 同一轮插入多段 reasoning/commentary 与 40 条混合活动，增量追加第 41 条；运行态应只有一个 `.session-activity-group`，节点身份保持不变，唯一灰色 reasoning 位于过程底部。
- 切换为完成态后展开“查看处理过程”，仍只允许一个活动组，明细顺序不变。
- `account/read`、`thread/read`、PLAN、队列、转向和恢复错误全部使用共享一行原语；全局弹窗和模拟致命错误只保留一行与必要按钮。
- Reducer 真实组件夹具覆盖迟到失败与重启恢复：前者保留用户后来输入的新草稿和附件，后者保持空输入框且不恢复旧附件；失败气泡仍可见。

## 最终验证

- 真实 `ConversationTranscript` QA 中，同一轮 40 条混合活动只有一个活动组；增量追加第 41 条后仍为同一个组。运行态、完成态展开过程和历史投影展开过程均为 1 个活动组、41 条明细和 1 条最新 reasoning。
- `account/read`、`thread/read`、PLAN、队列、转向和恢复六类夹具均只渲染一行 `错误码: 原始消息`；全局错误与模拟致命错误也只保留同一行及必要的关闭、刷新操作。
- 迟到失败后 Composer 仍为用户后来输入的新草稿和 1 个新附件；重启恢复后的 Composer 为空且有 0 个附件。失败消息气泡与原始错误仍保留，没有自动回填或自动重发。
- 额外扫清底层错误 message 中的“不会自动重发”“文本已保留在输入框”等解释句；禁止重放仍由状态机、审计结果和代码约束保证，不再作为可见错误文案重复出现。
- `pnpm lint`、`pnpm typecheck`、`pnpm build`、`pnpm package:mac` 和 `git diff --check` 全部通过；未新增 Vitest、单元测试或测试依赖。
- 最终 `Zeus Test.app` 使用显式临时数据根真实启动，bundle ID 为 `dev.hypha.zeus.test`；Renderer 与 Execution Host 正常就绪，窗口没有框架错误覆盖层。验收实例已单独退出，两份隔离数据根已移入 macOS 废纸篓，可恢复。隔离空数据不具备真实 Provider 历史，分组、错误和不回填的业务断言由同一 Renderer 的真实组件 QA 完成。
- 实施阶段结束时尚未获得远端写入授权；用户随后明确要求“升级发布”，因此进入 v0.3.49 的提交、推送、标签、GitHub Release 与 Homebrew 闭环。
