# AI 处理冲突会话重复投影诊断

## 结论

点击“AI 处理冲突”后，当前会话里的用户提示词和部分助手过程消息都会在界面中重复显示；但本次现场并没有启动两轮
Provider，也没有发现重复执行命令或重复计费的证据。问题属于同一轮会话内容被前端以两套身份重复投影。

## 现场证据

- 会话：`conversation_14a8ce34f8993e0d1c57ceb5`
- Provider 线程：`01a0346b-dc8a-7851-85c6-1fe07837e1c6`
- Provider 轮次：`01a0346b-dde2-7200-82ac-cca21e80fd76`
- `conversation_turns` 只有一条运行中轮次。
- `task_integration_attempts` 只有一个活动尝试。
- 原始 Provider rollout 只有一个 `turn_context`；每条助手消息和过程事件各出现一次。
- `conversation_messages` 中存在两条正文完全相同的用户消息：一条来自本地暂存提交，另一条来自 Provider 回显；助手消息在数据库和
  rollout 中各只有一条，重复只发生在渲染投影层。

## 根因

### 用户提示词重复

冲突会话先以 `holdDispatch` 创建本地占位消息，工作树准备完成后再通过 `release_hold` 生成 replacement
submission。replacement 使用新的 `client_message_id`，而原本地占位消息仍保留旧 ID。

`ConversationTranscript` 当前主要按 client message ID、submission ID 或 provider item ID 合并用户消息。旧占位消息和
Provider 回显的身份互不相同，虽然正文一致，也不会被合并，因此显示成两条。

### 助手响应重复

助手消息在数据库、Snapshot API 和 Provider rollout 中各只有一份，因此不是模型生成了两遍。活动轮次中，实时流投影与 Snapshot
V2 历史投影同时进入前端状态；历史合并路径仍可按本地 item ID 保留记录，没有在所有路径上统一按 `providerItemId` 收敛，导致同一
Provider 消息在页面上以两个本地 item 展示。

## 影响

- 缺点：会话中输入、过程说明和思考分组出现重复，滚动位置和处理进度容易被误判。
- 当前未发现的影响：没有证据表明本次触发了双 Provider 轮次、双命令执行或双计费。

## 修复方向与取舍

1. 在 `release_hold` 时继承原 submission 的 `client_message_id`，或显式建立旧占位消息与 replacement 的关联。
    - 优点：从身份源头消除用户消息双显，语义最清晰。
    - 缺点：需要核对 replacement、重试和历史恢复对 client ID 唯一性的依赖。
2. Snapshot V2 与实时流统一使用 `providerItemId` 作为已落地 Provider 内容的主去重键。
    - 优点：能够同时覆盖助手消息、思考过程和重连后的重复投影。
    - 缺点：必须保留尚未获得 provider identity 的本地临时项，避免错误吞掉真实内容。
3. 仅按相同正文和邻近时间去重。
    - 优点：改动较小。
    - 缺点：会误合并用户或模型有意重复发送的内容，不建议作为主方案。

## 推荐实施方案

### 1. 解除 hold 时保持逻辑消息身份

在 `packages/local-server/src/codexNativeConversationCoordinator.ts` 的 `releaseHeldSubmissions` 中，仅对 `release_hold`
replacement 显式传入：

```ts
clientMessageId: submission.clientMessageId
```

`conversation_submissions.client_message_id` 没有唯一索引，因此原 submission 与 replacement
共用该逻辑身份不会违反数据库约束。编辑、重试和改路由仍保持各自的新 client ID，避免把真正不同的投递错误合并。

### 2. Snapshot 分页按 Provider 身份合并

在 `apps/desktop/src/renderer/session/conversationSnapshotV2Adapter.ts` 中，让 `mergeConversationHistoryV2`
与现有过程页、轮次历史页采用相同规则：

- 首选 `providerItemId`；缺失时才退回本地 `id`。
- 同一 Provider item 出现不同本地 ID 时删除旧 ID，只保留一项。
- `process_detail` 比 `model_history` 信息完整，二者冲突时保留过程项。

### 3. 修正实时状态与分页状态的最终合并

`apps/desktop/src/renderer/session/sessionReducer.ts` 的 `mergeSnapshotV2Page` 当前按 local key 查找；找不到就把旧实时项直接加回。该逻辑会撤销
`hydrateSnapshot` 已经完成的 Provider 去重。

应先为水合结果建立 `providerItemId -> canonical key` 映射，再处理旧实时项：

- Provider 身份相同但 key 不同时，合并到 canonical key，并删除旧 key。
- 终态优先于进行中状态，`process_detail` 优先于 `model_history`。
- 时间线位置保留较早的 `timelineAt`，内容和资源保留较完整的一侧。
- `itemOrder` 先把旧 key 映射为 canonical key，再做集合去重与排序。

这一步是助手回复双显的主修复点。现场同步事件中，同一回复始终使用唯一的 `msg_*` Provider item ID；重复是在分页状态与实时状态按
local key 合并时产生的。

### 4. 兼容修复前已生成的会话

新逻辑只能阻止以后生成不同 client ID。对于数据库里已经存在的 `release_hold` replacement，读取时应沿
`replacement_of_submission_id` 解析原 submission 的 client ID，作为用户消息的 canonical client ID；不需要修改历史正文，也不按正文做模糊去重。

## 验收场景

- 首次点击“AI 处理冲突”，提示词从 hold、release 到 Provider 接纳始终只有一个气泡。
- 回复流式生成、加载过程详情、轮次完成、会话刷新和应用重启后，每个 Provider item 始终只显示一次。
- 连续两轮故意发送完全相同的正文仍显示两条，证明没有采用正文去重。
- 数据库保持一个活动 attempt、一个 Provider turn；Provider rollout 与界面各 Provider item 一一对应。
- 按项目规则执行 `pnpm lint`、`pnpm typecheck`、`pnpm build`、`pnpm package:mac`，并只启动独立身份的 `Zeus Test.app`
  做真实冲突会话回归。
