# 任务推送提示词重复与引导消息消失诊断

## 当前阶段

已完成正式 Zeus 现场、Provider JSONL、SQLite 持久事实、Snapshot V2 与 Renderer 投影代码的诊断，
并已完成源码修复与行为探针。正式数据库和 Provider 会话保持只读，没有重放任何历史用户消息。

## 现场对象

- 会话：`conversation_19f0fc80ca9e3456dd587612`
- 标题：`任务会话：引入数字员工`
- Provider thread：`01a034ab-3587-7ca1-9c55-ca50ac4f5f8a`
- JSONL：`/Users/david/.zeus/providers/codex/sessions/2026/08/25/rollout-2026-08-25T00-47-10-01a034ab-3587-7ca1-9c55-ca50ac4f5f8a.jsonl`

## 权威事实

1. JSONL 中原始任务提示词只有一条，时间为 `2026-08-24T16:47:19.577Z`。
2. 第一条引导消息 `zeus/ZEUS-0351-skill-skill-03 ...` 也只有一条，时间为
   `2026-08-25T09:47:29.628Z`。
3. 第二条引导消息 `zeus/ZEUS-0263-task-02 ...` 当时仍是本地 `queued` submission，尚未派发到 Provider，
   因此不应出现在 JSONL 中。
4. 正式数据库仍完整保留第一条引导消息：
   - `conversation_messages.id=conversation_message_Rh6tAdOicXwk`
   - `conversation_model_history.sequence=1204`
   - `clientUserMessageId=0e0aa557-41db-45f0-82c8-698774c8fcd0`
5. 第二条引导消息仍保存在队列：
   - `conversation_submission_0ZdWmEiWNoMt`
   - `status=queued`

因此，这不是用户重复发送，也不是消息持久数据丢失，而是活动会话的投影正文被错误覆盖。

## 直接触发证据

正式 `conversation_sync_events` 的序号 `20923` 为第二轮的 `conversation.item.completed`：

- `turnId=01a03851-5310-7040-9902-d05d3aafadde`
- 兼容 item 身份为 `item-1`
- `clientId=0e0aa557-41db-45f0-82c8-698774c8fcd0`，即第一条引导消息
- 但 `textContent` 和 `itemPayload.content[0].text` 都错误地变成最初的“引入数字员工”任务提示词

Renderer 依据 `clientId` 找到第一条引导消息后，用这条陈旧的兼容事件覆盖其正文。最终同时表现为：

1. 最初任务提示词在第二轮位置再次出现；
2. 第一条引导消息的气泡仍是同一身份，但正文已经被替换，因此看起来“消失”。

第二条排队消息触发了新一轮队列与会话对账，但不是数据丢失源头。

## 根因

Provider 历史兼容投影使用 `item-1`、`item-2` 这类每轮可复用的合成身份。Zeus 当前存在三层不一致：

1. `conversation_provider_item_states` 以 `(provider_thread_id, provider_item_id)` 唯一，错误地把兼容 `item-1`
   当作整个 thread 内唯一；第一轮已经保存的 `item-1` 会与第二轮的 `item-1` 碰撞。
2. `ConversationProviderItemRepository.upsertCompleted()` 发现同类型的旧 `completed` item 后直接返回旧记录，
   没有拒绝 `turnId/providerTurnId` 已变化的跨轮碰撞。
3. `codexProviderHistoryProjection` 随后把旧 `item-1` 的任务正文与当前轮 submission 的 `clientId` 组合后广播；
   `sessionReducer.reduceItemEvent()` 又按该 `clientId` 覆盖当前用户消息。

现有 `filterCompatibilitySnapshotItemAliases()` 只能在兼容项正文与同轮真实 item 正文完全相等时抑制别名，
无法处理“兼容 ID 已跨轮碰撞并读到旧正文”的情况。

## 实际修复边界与取舍

### 1. 兼容别名冲突时按轮次定域

`item-N` 只能使用 `(providerThreadId, providerTurnId, providerItemId)` 识别，不能沿用普通 Provider item 的
thread 全局身份。

- 实现：首个已经持久化的旧 `item-N` 继续沿用原身份；只有另一轮再次复用相同 `item-N` 时，才解析为
  `compat:<providerTurnId>:item-N`。兼容事件同时保留原生 `nativeItemId` 和
  `compatibilitySnapshotItemId` 标记。
- 优点：从摄取层消除跨轮碰撞，同时不重写正式库中既有消息、模型历史和资源引用。
- 缺点：兼容身份存在“首个旧身份 + 后续定域身份”两种格式；调用方必须统一经过解析函数，不能手拼。

### 2. 仓储遇到跨轮同 ID 必须失败关闭

`upsertProgress/upsertCompleted` 若查到相同 thread/item ID、但 `turnId/providerTurnId` 不同，应拒绝复用旧记录，
而不是返回旧完成项。

- 优点：即使 Provider 再返回不可靠兼容身份，也不会静默污染当前轮。
- 缺点：若没有同时完成兼容 ID 定域，历史恢复会出现显式警告，需要上层降级处理。

### 3. 用户消息正文以 submission/client 身份为稳定锚点

兼容别名事件不得用与 submission 持久正文不一致的内容覆盖已确认用户消息。Renderer 可保留一道防御：
对 `item-N` 且正文与同 client 的权威模型历史不一致时忽略正文更新。

- 优点：旧数据和旧 Provider 仍能避免界面再次篡改用户消息。
- 缺点：这是防御层，不能替代服务端和仓储根修复。

### 4. 排队消息自动发送不得被旧暂停记录遮挡

正式现场同时证明：更早的 `paused/recovery_required` 审计记录排在队列位置 1，后来的第二条引导消息为
`queued`、位置 2 且已有冻结执行快照。统一排空器此前只取第一条 `queued/paused/failed`，发现它不是
`queued` 后直接返回，导致真正可发送的第二条消息永远没有被选中。

- 实现：自动排空只选择队列顺序中最早的 `status=queued AND providerTurnId IS NULL` 记录；
  `blocked_by_head` 后续项本身会被置为 `paused`，因此不会绕过真正阻塞的队首。
- 优点：旧的暂停/失败审计事实继续保留，但不再遮挡后来可发送的消息；上一轮 `turn.completed` 后仍由原有
  microtask 触发同一排空器。
- 缺点：如果最早的 queued 记录自身缺少执行快照，仍按队列顺序停住而不会跳过；这是避免乱序发送的必要边界。

## 已完成的代码验收

- 行为探针确认：第一轮 `item-1` 保持旧身份，第二轮同名项得到 `compat:turn-2:item-1`，稳定 Provider ID
  不改写；仓储收到未经定域的跨轮复用时返回 `ZEUS_PROVIDER_ITEM_IDENTITY_CONFLICT`。
- 同一探针确认：较早暂停记录之后的 queued 引导消息会被选中；全部为暂停态时不发送；两个 queued 之间仍保持原顺序。
- Renderer 在兼容快照事件正文与同一 `clientUserMessageId` 的耐久用户正文不一致时保留耐久正文，避免旧客户端再次被改文。
- 正式数据库只读复核：第一条引导消息仍完整保存在 `conversation_messages`；第二条原提交保留为
  `paused/interrupted`，之后的 replacement 已完成，说明历史数据没有被本次修复改写。

## 验收要求

1. 同一 thread 连续两轮都返回 `item-1` 时，两条用户消息分别保留且顺序稳定。
2. 首条任务推送只显示一次。
3. 第一条引导消息在第二条排队消息发送前后均不消失、不改文。
4. 第二条消息在 queued、dispatching、active、completed 四阶段保持同一客户端身份。
5. 冷开、热切换、Snapshot V2 尾页水合、实时事件回放和重新展开历史结果一致。
6. 正式 JSONL、SQLite 模型历史与 UI 可见用户消息逐条一一对应。
