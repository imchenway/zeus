# TASK_20260825_006 会话处理过程按阶段摘要分组

## 用户问题

普通会话和子智能体会话把整轮命令、工具、文件操作和思考摘要压成一个处理过程。用户实际需要按每次可见的
中间摘要分段：A 摘要之后到 B 摘要之前是一组，B 到 C 是一组，C 之后是下一组；子智能体不能再维护另一套
扁平展示算法。

## 根因

- `projectTranscriptRows()` 只使用 `turnId` 建立 `activity:${turnId}`，因此整轮所有操作在第一次操作位置就被合并。
- `projectTranscriptTurnRows()` 再把整轮所有过程行包成单个 `turn_work`，中间 `agentMessage/commentary`
  也只是该大组中的普通行，不能形成阶段边界。
- 子智能体虽然已经复用 `ConversationTranscript`，旧投影算法仍会把其大量 reasoning 和文件操作整轮展开或整轮折叠。

## 实现

1. 阶段边界只认用户可见、非最终答复的 assistant/commentary 摘要；内部 reasoning、计划、交付物和最终正文
   不会误切新阶段。
2. 命令、工具、文件、网页和上下文活动按“当前阶段身份”聚合，活动 key 同时包含 turn 与阶段，不再按整轮聚合。
3. 每个阶段生成独立 `turn_work`：摘要始终可见，摘要后的 reasoning 和操作放入该阶段的“查看处理过程”。
4. 活动轮次只让最后阶段实时展开；前面已经结束的阶段折叠。最后活动阶段仍只显示最新 reasoning，避免恢复旧的
   英文思考列表；完成轮次展开后可以逐阶段查看完整过程。
5. 只有最后阶段负责 Snapshot V2 后续分页，避免三个阶段同时请求相同尾页。
6. `SubagentWorkspace` 不增加分组逻辑，继续把只读线程投影为 `NativeSessionState` 后直接复用
   `ConversationTranscript`。

## 取舍

- 优点：阶段语义来自真实可见摘要，普通会话和子智能体永久一致；完成态默认简洁，用户仍可逐段审计命令和思考。
- 缺点：没有中间摘要的旧轮次仍只有一个过程组；这是忠于历史事实，不能靠时间间隔臆造阶段。

## 验收记录

- 纯行为探针构造 A/B/C 三条摘要、三类操作和一条 reasoning，得到 3 个独立阶段；A 与 B 之间的 reasoning
  只属于 A，每个阶段各有一个活动组，只有 C 标记为后续分页入口。
- 浏览器组件真实 DOM：运行态显示 A/B 两个可折叠阶段和实时 C 阶段；完成态显示 3 个独立“查看处理过程”。
  逐一展开后得到 3 个 reasoning、3 个活动组，处理时长仍位于最终正文下方。
- 子智能体 Zeno 使用同一组件显示 A/B/C 三条摘要和 3 个独立过程入口；任务指令位于转录上方，最终审查正文和
  处理时长保持在本轮末尾。
- 组件现场无 console error；窄分栏中摘要、折叠入口和活动组均无横向溢出。
