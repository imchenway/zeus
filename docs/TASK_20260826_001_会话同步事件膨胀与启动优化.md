# TASK_20260826_001 会话同步事件膨胀与启动优化

## 任务目标

修复耐久会话同步流把累计文件变更全文反复写入 SQLite，导致正式数据库从约 4.8 GB 增长到约 24 GB、启动明显变慢的问题。交付必须同时满足：

1. 新版本不再把完整 change set diff 写进每一条实时事件；
2. 同步事件只保留用于断线追赶的有界尾部，越过尾部时回到 Snapshot V2 权威快照；
3. 现有正式数据库在隔离副本完成清理、压缩和一致性校验后再离线晋升；
4. 使用独立身份 `Zeus Test.app` 对正式数据副本完成真实 GUI 回归；
5. 用户已明确授权提交、发布、升级，并要求在正式 `/Applications/Zeus.app` 完成现场验证。

## 2026-08-26 正式现场基线

- 当前源码：`main` 与 `origin/main` 均为 `121b906`，工作区干净；公开稳定版与正式安装版为 `0.3.61`。
- 正式 SQLite：`/Users/david/.zeus/data/zeus.db`，文件大小 `25,448,878,080` 字节，所在卷可用空间约 `57 GiB`。
- 上一阶段只读盘点：`conversation_sync_events` 约 119 万条、载荷约 17.3 GB；其中约 8.5 万条 `conversation.turn.change_set.changed` 占约 15.5 GB。
- 约 57 个真实 change set 被累计快照重复写入约 8.5 万次，平均每个 change set 约 1491 份；事件默认随机 UUID，因此相同实体修订不能幂等去重。
- 正式应用成功启动时，execution-host 取得锁后仍需约 42 秒完成 Core/Local Server 初始化。当前证据不支持数据库损坏，问题是无界耐久事件及其大载荷放大了打开、迁移校验和恢复成本。

## 根因边界

1. `turnChangeSets` 的实时广播携带完整 `TurnChangeSet`，其中同时包含总 `unifiedDiff` 和每个文件的 `unifiedDiff`。
2. 2026-08-22 接入耐久同步后，广播 payload 被原样写入 `conversation_sync_events`；单事件 1 MiB 上限只能限制单条，不能限制同一实体反复累计写入。
3. `conversation.turn.change_set.changed` 被登记为 `critical_fact`，绕过了过程事件合并；每次更新又生成随机 event ID。
4. 同步流只有连续序号和显式 baseline，没有尾部保留策略；Snapshot V2 已是权威读模型，但旧同步事件仍永久保留。

## 实施设计

### 1. 协议流 V2 与轻量 change set 投影

- 协议代次升级到 `zeus-conversation-sync-v2`；升级迁移只退役旧流并为现有会话建立空 V2 baseline，不扫描或删除 17 GB 旧事件，避免再次把冷启动变成全表维护。
- 实时 change set 只携带身份、状态、文件路径、行数、可逆性和摘要字段；总 diff 与逐文件 diff 留在 `turn_change_sets`、`turn_change_files` 和 ArtifactStore，按现有读取接口获取。
- `capturing` 更新登记为可合并过程事件；同一 change set 在短窗口内只持久化最后一次投影。终态到达后 Renderer 通过现有 change set 读取接口补齐完整 diff。
- change set 事件使用实体身份与修订生成稳定 event ID，同一修订重试只能命中幂等记录，不能再生成第二份随机副本。

### 2. 有界同步尾部

- V2 每个会话最多保留固定数量和固定字节的连续尾部；达到检查水位后只删除已被 Snapshot V2 覆盖的前缀，并同步推进 `base_sequence`。
- 客户端请求早于 baseline 时沿用现有 `baseline_required` 语义，重新读取 Snapshot V2 后从新水位继续；业务事实仍由会话、轮次、过程、交付物、请求和审计表拥有。

### 3. 现有数据库离线压缩

- 正式源先用 SQLite Backup API 生成一致候选，候选应用全部新迁移；只在候选删除已退役协议流事件，再执行受控 `VACUUM` 重建。
- 晋升前核对 `quick_check`、外键、关键业务表计数、关键摘要、V2 当前流、文件大小和无 WAL/journal；使用同卷原子替换保留原 24 GB 数据库作为可回退副本。
- 候选或真机验收任一不通过时不晋升；正式源数据库保持原样。

## 方案优缺点

优点：

- 从源头停止累计 diff 的近二次写放大；实时 UI 仍能立即看到文件数、路径和行数。
- 同步流恢复为“短期追赶日志”，长期事实回到 Snapshot V2 和业务表，存储职责清晰。
- 协议升级不在普通冷启动执行大表删除或 `VACUUM`；现有大库通过独立候选和回退窗口收口。

缺点：

- 终态 diff 第一次展开需要一次本地按需读取；本机 loopback 请求通常为毫秒级，但不再是零请求。
- 一次性正式压缩需要约数十 GB 临时空间和离线窗口；保留 24 GB 回退副本期间不会立即释放全部磁盘。
- V2 baseline 前的逐条 UI 同步事件不再长期保留；长期审计必须读取对应业务事实和审计表，不能把临时追赶日志当审计总账。

## 验收目标

- 新 change set 同步事件平均载荷不超过 8 KiB，且不包含 `unifiedDiff` 正文。
- 单会话 V2 同步尾部不超过 4096 条且不超过 16 MiB；越界恢复走 Snapshot V2。
- 正式数据候选的 `conversation_sync_events` 旧 V1 事件归零，正式数据库目标体积不超过 8 GB，`PRAGMA quick_check` 与外键检查通过。
- `Zeus Test.app` 使用正式数据副本启动到可操作界面不超过 8 秒，历史会话、处理过程、文件变更卡、Markdown 预览和会话继续可用。
- 发布升级后的正式 Zeus 启动到可操作界面不超过 8 秒；正式库体积、同步事件代次、尾部预算和关键业务计数达到上述目标。

## 正式目录补充盘点与 Markdown 预览密度

### 现场根因

- `.zeus` 显示约 17 GB 并不等于正式数据库仍有 17 GB。补充盘点时正式数据库约 5.0 GB，另外还存在 1.9 GB 历史数据库备份、约
  3.6 GB 变更集恢复快照、3.8 GB Provider 数据、0.9 GB Electron Profile，以及附件与工具结果。
- 两份遗漏的历史数据库备份均为单链接普通文件且无进程占用，已按精确路径永久删除；`backups` 从约 1.9 GB 降至约 17 MB，`.zeus`
  从约 16 GB 降至约 14 GB。
- 变更集目录有 21,186 个恢复 blob；数据库当前引用 13,000 个，其余 8,186 个、共 `1,393,510,293` 字节没有任何引用。根因是同一
  Provider fileChange 多次更新时数据库覆盖了 pre/post 引用，但旧捕获文件未回收。
- Markdown 右侧预览同时应用了最多 64px 的横向内边距和 48rem 正文上限。在已经只有半屏宽度的右侧上下文面板中再次固定限宽，形成截图中的大面积双侧空白。

### 修复方案及权衡

- 捕获同一 fileChange 后，立即按该变更集数据库中的全部 pre/post 引用建立保留集，只删除变更集自身 `blobs`
  目录内未被保留的普通候选文件。优点是无需削弱 Undo/Reapply 历史能力即可停止孤儿增长；代价是每批 fileChange
  捕获结束后多一次小范围引用读取。
- 现存孤儿只在正式写入者停止后依据正式数据库引用离线清理；仍被引用的约 2.42 GB 恢复数据全部保留。
- Markdown 分栏预览横向内边距改为 20–36px，正文上限提高到 64rem 并填满可用宽度。优点是右侧分栏空间利用明显提高；代价是宽面板单行更长，因此全宽模式仍保留
  64rem 上限，没有改成无限宽。
