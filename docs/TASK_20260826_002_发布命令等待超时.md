# 发布命令等待超时

## 问题

Zeus `v0.3.64` 发布命令在等待 GitHub Release Workflow 时持续约 35 分钟，没有结束，也没有持续输出进度。

2026-08-26 现场核对结果：

- GitHub 官方状态为 `Partial System Outage`，Actions 为 `major_outage`；官方说明数据库主节点故障，正在切换到副本。
- Release Workflow `32984021773` 自 `2026-08-26T15:05:09Z` 起一直处于 `queued`，没有分配任何 job。
- 本地发布脚本的 `waitForWorkflowRun()` 使用无限循环。只要 GitHub API 仍能返回合法的 `queued`，脚本就不会退出。
- 原实现只在状态或 job 发生变化时输出；持续 `queued` 时没有心跳，因此表现为命令卡死。

GitHub 故障是本次排队的外部诱因；缺少等待上限和心跳是 Zeus 自身的可靠性缺陷。

## 目标语义

- 对同一个远程 Release Workflow，从 GitHub 记录的 `createdAt` 开始累计，最多等待 15 分钟。
- 状态没有变化时，每分钟输出一次等待进度、当前状态、累计时长、上限和运行链接。
- 达到上限后，本地发布命令明确失败退出，不再无限等待。
- 不自动取消远程 Workflow。GitHub 恢复后，远程运行仍可能继续；重新执行发布命令时继续识别并回验同一运行。
- 15 分钟限制只约束外部 Workflow 等待阶段，不强行终止本地构建、打包等本身有限且可能正常超过 15 分钟的阶段。

## 方案取舍

优点：

- GitHub 故障或长期排队不再让本地发布命令无限卡住。
- 重跑不会重新获得一段新的 15 分钟窗口，避免对同一远程运行反复等待。
- 心跳让排队与进程假死可以直接区分。
- 不取消远端运行，避免超时瞬间与 GitHub 恢复竞态而误删一次有效发布。

缺点：

- GitHub 只是缓慢但没有故障时，超过 15 分钟的远端发布也会让本地命令先退出。
- 本地退出后远端仍可能完成，使用者需要在 GitHub 恢复后重跑命令完成公开资产回验。

## 实现

- 新增 `scripts/release-workflow-wait-policy.mjs`，集中定义 15 分钟上限、10 秒轮询、1 分钟心跳和累计时间计算。
- `scripts/publish-release.mjs` 使用 Workflow `createdAt` 建立不可重置的等待窗口。
- 每次状态读取的单次超时不超过当前剩余窗口，防止一次 GitHub CLI 读取把等待时间大幅拖过上限。
- 达到上限后的错误明确说明本地命令已停止、远程 Workflow 未取消以及恢复方式。

## 验收

- 边界探针通过：14 分 59 秒不超时，15 分 00 秒立即超时；同一运行在 35 分钟后重跑仍立即超时，不会重置窗口。
- 异常或缺失的 `createdAt` 会从当前观察时间开始计时，不会产生无效截止时间。
- `node --check scripts/publish-release.mjs` 通过。
- `node --check scripts/release-workflow-wait-policy.mjs` 通过。
- `pnpm lint` 通过。
- `pnpm typecheck` 通过，架构治理检查同时通过。
- `pnpm build` 通过。
- `git diff --check` 通过。
- `RELEASE_VERSION=0.3.64 APPLY_REMOTE=false pnpm release:publish` 只读计划演练通过；因工作区存在本次未提交修复而正确报告 1 个阻断项，没有执行 Git 或远程写操作。
