# 发布命令等待超时

## 问题

Zeus `v0.3.64` 发布命令在等待 GitHub Release Workflow 时持续约 35 分钟，没有结束，也没有持续输出进度。

2026-08-26 现场核对结果：

- GitHub 官方状态为 `Partial System Outage`，Actions 为 `major_outage`；官方说明数据库主节点故障，正在切换到副本。
- Release Workflow `32984021773` 自 `2026-08-26T15:05:09Z` 起一直处于 `queued`，没有分配任何 job。
- 本地发布脚本的 `waitForWorkflowRun()` 使用无限循环。只要 GitHub API 仍能返回合法的 `queued`，脚本就不会退出。
- 原实现只在状态或 job 发生变化时输出；持续 `queued` 时没有心跳，因此表现为命令卡死。

GitHub 故障是本次排队的外部诱因；缺少等待上限和心跳是 Zeus 自身的可靠性缺陷。

## 目标语义

- 对同一个远程 Release Workflow，从 GitHub 记录的 `createdAt` 开始累计，最多等待 15 分钟。
- 状态没有变化时，每分钟输出一次等待进度、当前状态、累计时长、上限和运行链接。
- 达到上限后，本地发布命令明确失败退出，不再无限等待。
- 不自动取消远程 Workflow。GitHub 恢复后，远程运行仍可能继续；重新执行发布命令时继续识别并回验同一运行。
- 15 分钟限制只约束外部 Workflow 等待阶段，不强行终止本地构建、打包等本身有限且可能正常超过 15 分钟的阶段。

## 方案取舍

优点：

- GitHub 故障或长期排队不再让本地发布命令无限卡住。
- 重跑不会重新获得一段新的 15 分钟窗口，避免对同一远程运行反复等待。
- 心跳让排队与进程假死可以直接区分。
- 不取消远端运行，避免超时瞬间与 GitHub 恢复竞态而误删一次有效发布。

缺点：

- GitHub 只是缓慢但没有故障时，超过 15 分钟的远端发布也会让本地命令先退出。
- 本地退出后远端仍可能完成，使用者需要在 GitHub 恢复后重跑命令完成公开资产回验。

## 实现

- 新增 `scripts/release-workflow-wait-policy.mjs`，集中定义 15 分钟上限、10 秒轮询、1 分钟心跳和累计时间计算。
- `scripts/publish-release.mjs` 使用 Workflow `createdAt` 建立不可重置的等待窗口。
- 每次状态读取的单次超时不超过当前剩余窗口，防止一次 GitHub CLI 读取把等待时间大幅拖过上限。
- 达到上限后的错误明确说明本地命令已停止、远程 Workflow 未取消以及恢复方式。

## 验收

- 边界探针通过：14 分 59 秒不超时，15 分 00 秒立即超时；同一运行在 35 分钟后重跑仍立即超时，不会重置窗口。
- 异常或缺失的 `createdAt` 会从当前观察时间开始计时，不会产生无效截止时间。
- `node --check scripts/publish-release.mjs` 通过。
- `node --check scripts/release-workflow-wait-policy.mjs` 通过。
- `pnpm lint` 通过。
- `pnpm typecheck` 通过，架构治理检查同时通过。
- `pnpm build` 通过。
- `git diff --check` 通过。
- `RELEASE_VERSION=0.3.64 APPLY_REMOTE=false pnpm release:publish` 只读计划演练通过；因工作区存在本次未提交修复而正确报告 1 个阻断项，没有执行 Git 或远程写操作。

本次仅修改发布编排脚本和任务文档，不影响桌面应用运行时代码，因此不生成或启动 `Zeus Test.app`。

## 发布执行

- 2026-08-27，用户明确授权升级发布。
- 昨日遗留的 Release Workflow `32984021773` 仍投影为 `queued`，但普通取消和强制取消接口均返回 `409 Cannot cancel a workflow run that has not been queued yet`；GitHub Actions 同期仍处于性能下降事件。
- 为避免脏工作区隔离发布忽略本次修复，先把本任务的脚本与文档作为正式候选提交。
- 新候选推送前不触发第二个同标签发布，先利用 Workflow 的 `origin/main` 精确提交校验让旧候选失去公开写入资格。
- 修复提交推送到 `main` 后，旧运行即使苏醒，也会因候选提交不再等于 `origin/main` 而在公开写入前失败。
- GitHub 控制面无法取消这条“尚未真正入队”的幽灵运行，因此恢复规则只隔离忽略同时满足以下条件的运行：超过 15 分钟、仍为 `queued`、没有任何 job、候选正是被替代提交、远程 `main` 已精确指向替代提交。其他活动运行继续阻断发布。
- Release Workflow 并发键加入候选提交。同一标签、同一提交的重复运行仍互斥；同一标签的修复提交不再被已安全失效的旧候选幽灵组阻塞。

## 2026-08-28 历史幽灵运行再次阻断发布

### 现场事实与根因

- `pnpm release` 在把失败的 `v0.3.69` 候选重新绑定到修复提交 `2b62084017a9` 时，被 Release Workflow
  `32984021773` 阻断。
- GitHub 当前仍把该运行投影为 `queued`，创建和最后更新时间均为 `2026-08-26T15:05:09Z`，`jobs=[]`；它绑定的是已经被替代的
  `8b61cf008eb5`。在它之后已有多条 Release Workflow 成功完成，因此它不是当前仍在执行的发布，而是 GitHub 控制面遗留的幽灵记录。
- 当前提交链为 `8b61cf008eb5 → 8a33545e90d1（origin/main）→ 2b62084017a9（本地新候选）`。Release Workflow
  的公开写入预检要求候选必须精确等于 `origin/main`，所以该旧运行即使恢复，也无法再创建标签、Release 或改写 Homebrew。
- 脚本已有幽灵运行隔离逻辑，但只允许忽略“当前失败发布提交”对应的幽灵运行；更早、同样已经被 `main` 安全替代的幽灵运行仍会永久阻断所有后续恢复。

### 修复语义与取舍

- 幽灵隔离不再要求运行提交必须等于当前失败发布提交，而是要求同时满足：运行仍为 `queued`、超过 15 分钟、没有任何 job、运行提交已经被
  当前远程 `main` 替代、远程 `main` 是本地新候选的祖先、运行提交不等于远程 `main` 或本地新候选。
- 当前新候选自己的排队运行、已经创建 job 的运行、`in_progress`/`waiting` 运行、分叉提交、Git 对象不可验证或远程 `main`
  尚未指向新候选时，继续阻断发布。
- 优点：GitHub 无法取消的历史幽灵记录不会永久封死发布恢复；缺点：恢复检查增加一次本地 Git 祖先关系核验。无法证明安全时仍按阻断处理。
