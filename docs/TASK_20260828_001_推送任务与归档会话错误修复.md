## 用户现象

1. 推送任务弹出 `ZEUS_CONVERSATION_SYNC_EVENT_IDENTITY_CONFLICT`。
2. 对推送失败后留下的会话点击归档，弹出 `ZEUS_CONVERSATION_COMMAND_OUTCOME_UNKNOWN`。
3. 其他归档动作可能弹出 `ZEUS_CONVERSATION_NOT_FOUND`。
4. 其他会话回答交互问题时弹出 `ZEUS_CONVERSATION_DISPATCH_COMMAND_OUTCOME_UNKNOWN`，底层仍是同一个同步事件身份冲突。

## 现场证据

- 失败的 `conversation.task.create` 命令在外部写入前被同步事件冲突阻断，回执中的原始错误为
  `ZEUS_CONVERSATION_SYNC_EVENT_IDENTITY_CONFLICT`。
- 同一进程随后在多个会话、多个 Provider 事件方法上持续记录相同同步冲突，说明单个增量失败被进程级失败状态扩散。
- 本次推送已留下一个 `provider_state=unbound`、`stage=queued` 的本地会话和一条未绑定 Provider 回合的排队提交。
- 两次归档命令都被记录为 `outcome_unknown_after_write`，但底层原始错误实际是本地前置条件
  `ZEUS_NATIVE_CONVERSATION_IN_PROGRESS`，没有证据证明 Provider 归档写入已经发生。
- 截图中的 `ZEUS_CONVERSATION_NOT_FOUND` 没有带出会话 ID；当前推送失败留下的目标会话仍真实存在，因此不能把该 404
  归因为数据已被删除。现有证据只支持“客户端选择与稳定预留状态失配”，精确触发路由仍需在测试包复现。
- 新增现场中的两条 `conversation.server_request.respond` 命令虽然被记成 `outcome_unknown_after_write`，但对应请求均已持久化为
  `resolved`，对应 Provider 回合也仍为 `running`。这证明交互回答已经被业务链接受，随后 UI 增量发布失败反向污染了命令结果；两条回答都不得重放。

## 根因

### 1. 变更集事件身份只使用毫秒时间

变更集增量的稳定 `eventId` 只包含会话、变更集和 `updatedAt`。Provider 可以在同一毫秒内产生内容不同的 pre/post
投影，导致不同内容获得同一个事件身份，触发存储身份冲突。

### 2. 单个增量失败污染整个进程

增量刷新失败被保存到全局失败变量。之后任何会话发布任何事件都会直接抛出旧错误，因此一个会话的可重建过程投影会阻断其他任务推送。

### 3. 未外发队列没有可归档路径

尚未绑定 Provider、也没有 Provider 回合的本地排队消息仍被通用“会话进行中”校验拦截。命令框架又在进入协调器前就标记“外部写入已开始”，最终把明确的本地拒绝误报为外部结果未知。

### 4. 业务接受结果被可重建投影错误覆盖

Provider
写入或本地业务状态已经成功后，同步增量发布仍位于命令调用栈内。进程级旧错误从发布函数抛出，会让命令框架把已经接受的回答记成“外部结果未知”。任务推送的准备阶段也会先留下稳定会话预留，再因同一个发布错误返回失败，客户端随后可能持有与真实预留状态不同步的会话选择；这是当前对
`ZEUS_CONVERSATION_NOT_FOUND` 的最强推断，但还不是已复现根因。

### 5. 未绑定会话归档后的恢复投影不完整

真实测试包发现，首次提交在归档时被安全取消后，归档列表仍沿用“已取消提交等于空壳”的筛选规则，导致归档条目不可见；恢复时又错误要求不存在的任务
worktree。即使纯本地恢复成功，旧筛选也会继续隐藏仍保留用户消息的会话。

## 修复设计与取舍

### 变更集事件身份

- 做法：稳定事件身份增加规范化变更集投影的 SHA-256 指纹。
- 优点：相同内容重放仍幂等；同一毫秒内内容不同的投影不再碰撞。
- 缺点：事件身份计算增加一次小型投影哈希，但投影本身已受事件大小预算约束，成本可控。

### 增量失败隔离

- 做法：移除永久进程级失败闩锁；批量遇到身份冲突后逐条重放，只丢弃可由 Snapshot V2 重建的冲突过程投影，保留其他会话事件。
- 优点：单个会话不会继续阻断任务推送；非冲突存储错误仍会抛出并重排，不会被静默吞掉。
- 缺点：发生旧版身份冲突时会少一条过程增量，但客户端可从权威快照恢复完整状态。

### 未绑定会话归档

- 做法：仅当会话未绑定 Provider、没有未完成回合或待处理请求，且所有非终态提交都从未获得 Provider 回合时，取消本地队列并归档；侧边栏对
  `providerState=unbound` 且没有 Provider 线程身份的本地队列开放归档按钮。未绑定归档会话恢复时只恢复本地归档标记，不要求
  Provider 或 worktree；历史投影以真实消息判断是否为空壳。
- 优点：推送失败留下的本地会话可以安全清理并可见地恢复，不会产生未知的 Provider 结果；恢复后仍回到原任务。
- 缺点：恢复该会话后不会自动重发旧消息；这是避免用户未确认重放的必要约束。历史投影需要额外读取一次目标会话消息，但范围只限未绑定原生会话。

### 命令结果与生命周期

- 做法：同步身份冲突只在可重建投影层隔离，不再作为永久进程错误进入后续命令调用栈；真实进行中拒绝明确归类为
  `explicitly_rejected`。
- 优点：已经接受的交互回答不会被 UI 投影失败反报为未知；明确拒绝不再伪装为外部结果未知；任务推送的稳定预留可以按原幂等身份恢复。
- 缺点：旧冲突发生当下可能缺少一条过程增量，需要依靠权威快照补齐 UI；不能用自动重放来修复历史未知回执。

## P0 事故最终复盘（覆盖上文早期推断）

以下结论以运行日志、数据库、当前源码和独立测试包真实操作交叉核对为准。其中 `ZEUS_CONVERSATION_NOT_FOUND`
的早期“服务端归档后回读不到”判断已在本节更正。

### 1. 推送任务报同步事件冲突，并扩散到其他会话

- 直接根因一：旧版事件 ID 只使用会话、事件类型、变更集 ID 和毫秒级更新时间。同一毫秒内的前后两份不同内容会获得同一个
  ID，存储层因此拒绝第二份内容。
- 直接根因二：一次增量发布失败被保存成进程级永久错误。之后任何会话发布事件都会继续抛出第一次的旧错误，所以故障从一个会话扩散到全部会话。
- 解决方案：事件 ID 加入规范化内容的 SHA-256 指纹；移除进程级永久错误闩锁；可重建的过程增量失败只影响本事件，权威 Snapshot
  V2 负责补齐界面。
- 取舍：冲突当下可能少一条过程动画，但不会再阻断业务写入和其他会话。

### 2. 回答交互已经成功，却显示“结果未知”

- 直接证据：两条 `conversation.server_request.respond` 对应请求在数据库中均已是 `resolved`，但命令回执被同步投影错误改写为
  `outcome_unknown_after_write`。
- 直接根因：业务状态已经提交后，UI 增量发布仍在同一个命令调用栈内；投影失败反向覆盖了成功结果。
- 解决方案：业务提交和 UI 投影彻底分层。业务成功后固定返回成功；投影失败只写运行日志并触发快照重建，禁止自动重放用户回答。
- 取舍：界面可能短暂刷新一次，但不会欺骗用户“业务结果未知”。

### 3. 点击归档报“结果未知”

- 直接证据：相关归档回执的底层错误是本地 `ZEUS_NATIVE_CONVERSATION_IN_PROGRESS`，没有发生 Provider 归档写入。
- 直接根因：框架在真正调用 Provider 前就标记“外部写入已开始”，后续本地前置条件拒绝被误分类成外部结果未知。
- 解决方案：所有本地前置条件先执行；只有紧邻真实 `archiveThread` 调用时才标记外部写入开始。未绑定
  Provider、从未发送、没有活动回合和待处理请求的本地会话允许安全归档。
- 取舍：从未发送的内容归档后不会自动重发，避免未经用户确认产生副作用。

### 4. 点击归档报 `ZEUS_CONVERSATION_NOT_FOUND`

- 更正早期误判：`ConversationRepository.getById()` 并不排除已归档记录，“归档后服务端必然回读不到”不是事实。
- 已验证的稳定触发链：当前被选中的会话在归档请求返回前仍保持正文读取和刷新；归档成功后侧边栏先移除条目，旧选择又继续发起读取，预期的过期请求或本地错误再被全局
  `ApplicationErrorDialog` 提升为阻塞弹窗。
- 解决方案：归档被选中的会话时，先卸载正文和选择状态，再执行归档；归档失败才恢复选择。同时取消全局运行期错误弹窗，技术细节只记入运行日志。
- 取舍：归档请求期间正文会立即卸载；如果归档失败再恢复，但不再允许过期正文请求欺骗用户。

### 5. 升级/重启后 PID 45740 仍遗留，新界面连接旧 Core

- 直接证据：新 Main/Renderer 在 10:44 重新连接了 2026-08-27 21:09 启动的 Core PID `45740`，旧 Core 版本为 `0.3.67`，界面版本已是
  `0.3.68`。
- 直接根因：现有架构把 UI 退出和 Core 退出分开；只要 Core 报告还有活动工作就无限存活。新 UI
  又只校验协议兼容，不校验应用版本；检测到真实活动工作时，版本交接函数直接放弃交接。
- 解决方案：把“关闭窗口但后台继续”和“完整重启 Zeus”定义为两个动作。完整重启必须先把不可恢复工作持久化为中断/暂停，限时关闭或交接旧
  Core，确认旧 PID 和数据库写租约释放后，才能启动新 Core。新 UI 不得连接不同应用版本的旧 Core。
- 取舍：真实 Provider 回合无法保证无损替换；完整重启必须明确告诉用户“当前工作会停止”，不能使用 generation、eventId、副作用等内部术语。

### 6. 交接失败后白屏，随后 Core 以 code=1 退出

- 直接证据：失败交接账本没有 checkpoint、没有迁移请求，却停在恢复状态；启动错误日志明确记录
  `ReferenceError: Cannot access 'toNativeQueueApiSnapshot' before initialization`。
- 直接根因一：渲染层把 `recovery_required` 错当成 `draining`，静默重试最多两分钟，同时不渲染任何内容，所以用户只看到白屏或
  Logo。
- 直接根因二：Core 启动恢复早于队列快照序列化函数初始化；恢复一旦发布 queue.changed 就进入 JavaScript 暂时性死区并崩溃。
- 解决方案：空交接账本自动安全终止；`recovery_required` 和 `draining` 使用不同状态；前者直接显示唯一的启动失败页，后者只做有上限的短等待。Core
  必须先完成全部路由/序列化器初始化，再执行恢复。
- 取舍：空账本可直接终止；有真实 checkpoint 的账本仍必须保守恢复，不能强行清除。

### 7. 点击退出/重启后应用卡死

- 直接证据：多个 Core 日志只有 `closing`，没有 `closed`。
- 直接根因：关闭流程无限等待运行时和控制服务的 Promise；只要其中一个不返回，进程就永远到不了退出兜底。
- 解决方案：运行时关闭最多等待 20 秒，控制服务最多等待 5 秒；超时后记录日志并让进程退出。重启使用独立接力进程，等旧 Main 和
  Core 退出、单实例锁释放后，再按相同可执行文件、参数和环境启动新 Main。
- 取舍：极端情况下会跳过非关键清理，但操作系统能够释放端口、文件描述符和数据库写租约，避免整套应用永久卡死。

### 8. 重启后会话已经不运行，侧边栏和正文仍显示“正在思考”

- 直接证据：两条会话的 Provider 状态和提交状态都已是 `paused`，但数据库里的 turn 仍是 `running`；Snapshot V2 仅凭 turn
  状态把它们继续投影为 active turn。
- 直接根因：`markConversationRecoveryRequired()` 只暂停提交、Provider 状态和内存运行状态，没有把已失去宿主的
  `running/dispatching/waiting` 回合终结。数据库因此同时保存“已暂停”和“仍运行”两套互相矛盾的事实。
- 解决方案：不可恢复时在同一个事务中暂停提交、把当前回合标记为 `interrupted`/`failed`、把 Provider 状态设为 paused；Snapshot
  V2 的 active turn 还必须匹配当前 execution host 的运行身份证据，不能只看旧数据库状态。用户界面只显示“上次运行已中断，可以继续”。
- 取舍：无法确认 Provider 是否仍在远端运行时，本地保守显示“已中断”；以后收到权威事件再更新历史，不能继续用假转圈欺骗用户。

### 9. DeepSeek 旧会话正文被折叠进“处理过程”

- 直接证据：“项目的排序”对应 assistant 历史记录没有 reasoning 来源，完整正文在普通 `content_json`；旧消息又没有 phase 字段。
- 直接根因：适配器把“没有明确 final_answer 标记”的所有 assistant 消息一律标成 `prework`；Transcript 又把所有非 final
  内容折叠进处理过程。正常答案因此被误分类，不是数据损坏。
- 解决方案：只有明确的 reasoning/reasoningSummary 才进入处理过程；旧 assistant 消息没有 phase、不是 plan、也没有 reasoning
  证据时，默认按普通正文/final answer 展示。
- 取舍：极少数旧版未标记的过程文字可能会直接展示，但这比隐藏用户真正的答案更安全。

### 10. 报错弹窗、全屏蒙层和内部术语不可接受

- 直接根因：全局 `ApplicationErrorDialog` 把所有运行期异常排队为模态弹窗；格式化函数直接拼接内部错误码和原始消息；启动
  catch 又先渲染维护背景，再叠加全屏蒙层。
- 解决方案：取消全局运行期错误模态框。运行期技术细节经脱敏后只写本地运行日志；业务界面在原位置显示可执行的人话。只有 Core
  确实无法启动时显示一个平面的全窗口“启动失败”页面，只提供“重新启动”和“退出”，不再叠弹窗或背景蒙层。
- 取舍：用户不会被技术错误轰炸；排障人员需要从运行日志查看完整细节。

### 11. “Computer Use 缺少 NODE_REPL_TRUSTED_SERVICES”

- 这不是 Zeus 产品故障，而是一次错误的交付说明。现场实际可使用 Computer Use，也已经完成独立测试身份应用的真实界面检查。
