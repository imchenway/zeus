## 2026-09-01 外部实现对照与收缩边界修正

### 修正结论

上文第 69–70 行“删掉 Zeus 便携上下文”的口径过度收缩，不符合 Zeus 已确认的产品能力：同一个用户可见会话必须能在 Codex、Pi
及后续其他
Provider 之间继续。此处修正为：

- 保留最小的“产品会话 + Provider 原生分段 + 已确认事实交接”；
- 删掉的是与 Provider 原生压缩、原生历史和运行状态重复的第二套压力计算、重复投影和重复状态机；
- 跨 Provider 时新建原生分段，只从 Zeus 已确认的用户/助手消息、已验收交付物、明确决策、待处理交互和工具结果引用编译一份有界交接；
- 隐藏推理、Provider 私有工具内部状态和不兼容的原生上下文不能无损迁移，必须明确承认这一能力损失。

因此，推荐的不是“把 Zeus 会话降成 Provider 会话的皮肤”，而是“保留必需的产品级连续性，每个 Provider 事实只翻译一次”。

### 开源项目源码对照

本次按固定提交阅读，避免用 README 宣传语反推实现：AionUi `dc47f4a`、aionrs `f711174`、t3code `0bfb6df`、Buzz
`571c190`。

#### AionUi：借产品分层，不照搬内部实现

- 普通会话主表只保留会话、模型和状态，消息另表存储；Team 才额外增加 `teams`、`mailbox`、`team_tasks`。这说明普通会话与多 Agent
  协作不应共用一套巨型状态机。[源码](https://github.com/iOfficeAI/AionUi/blob/dc47f4a0173ff506b08f13c97b10944d61e422d5/packages/desktop/src/process/services/database/schema.ts#L45-L133)
- Aionrs 会话切模型时，若当前有活动 turn，先停止 Agent，再更新会话模型，下次发送时重建运行时。它并不是把一个正在运行的原生会话直接改造成另一个
  Provider。[源码](https://github.com/iOfficeAI/AionUi/blob/dc47f4a0173ff506b08f13c97b10944d61e422d5/packages/desktop/src/renderer/pages/conversation/components/ChatConversation.tsx#L153-L166)
- aionrs 的 Provider 在引擎创建时由配置选定，运行期更新的是 model、thinking、effort 和 compaction 等配置；换 Provider
  仍需重建引擎/运行时。[创建 Provider](https://github.com/iOfficeAI/aionrs/blob/f7111746015d8e6f960e1568a805ceef975022d3/crates/aion-providers/src/provider.rs#L16-L62) [更新模型](https://github.com/iOfficeAI/aionrs/blob/f7111746015d8e6f960e1568a805ceef975022d3/crates/aion-agent/src/engine.rs#L1339-L1365)
- ACP
  的模型切换把“更改运行时”和“持久化选择”收口为一次后端请求，前端不再追加第二次写入。[源码](https://github.com/iOfficeAI/AionUi/blob/dc47f4a0173ff506b08f13c97b10944d61e422d5/packages/desktop/src/renderer/components/agent/AcpModelSelector.tsx#L96-L108)
- Team 中每个成员都有独立 `conversation_id`、backend、model 和上下文重置能力，团队层只负责
  Leader、邮箱、任务板、共享工作区和每成员权限。[成员结构](https://github.com/iOfficeAI/AionUi/blob/dc47f4a0173ff506b08f13c97b10944d61e422d5/packages/desktop/src/common/types/team/teamTypes.ts#L41-L74)
- AionUi 可以借的产品组合是“ACP 外部 Agent + Aionrs 多模型 Runtime + 并行普通会话 + 可选 Team 壳”；不应照搬的是它在未收到正常完成信号时用“15
  秒无新内容”判定回复完成的启发式降级；Zeus
  的任务、计费和数字员工不能把静默冒充成功终态。[会话生命周期说明](https://github.com/iOfficeAI/AionUi/blob/dc47f4a0173ff506b08f13c97b10944d61e422d5/docs/prds/conversations/acp/session.md#L283-L304)
- 缺点：AionUi 的关键会话业务边界还依赖独立的 `aioncore`，不能仅根据 AionUi 仓库证明跨 Provider 历史交接的完整细节；Team
  本身也有 Run、SlotWork、ChildTurn 等多组状态，它是“限定在 Team 域内的必要复杂度”，不是无状态方案。

#### t3code：借 Provider 能力合同和原生子 Agent 投影

- Provider Driver/Instance 是普通值，同类 Driver 可有多个互不共享可变状态的实例；原生续接能力用
  `driverKind + continuationKey`
  显式表达。[源码](https://github.com/pingdotgg/t3code/blob/0bfb6df34b26dfe0162db6c09dca00bc8c5a5ec4/apps/server/src/provider/ProviderDriver.ts#L1-L89)
- Adapter 只做 Provider 行为：启动会话、发送 turn、中断、响应批准/用户输入、停止、读取、回滚和输出标准事件；模型切换能力明确标为
  `in-session | unsupported`。[源码](https://github.com/pingdotgg/t3code/blob/0bfb6df34b26dfe0162db6c09dca00bc8c5a5ec4/apps/server/src/provider/Services/ProviderAdapter.ts#L28-L134)
- 已绑定会话要切到不同 Driver 时，t3code 直接拒绝；即使是同 Driver，`continuationKey` 不兼容也拒绝。它没有宣称 Codex→Claude
  可作为同一原生 thread
  继续。[源码](https://github.com/pingdotgg/t3code/blob/0bfb6df34b26dfe0162db6c09dca00bc8c5a5ec4/apps/server/src/orchestration/Layers/ProviderCommandReactor.ts#L630-L651)
- 当 Provider 不支持原会话内切模型时，t3code 会重启 session，并且不带不兼容的 resume
  cursor；能力支持时则沿用会话。[源码](https://github.com/pingdotgg/t3code/blob/0bfb6df34b26dfe0162db6c09dca00bc8c5a5ec4/apps/server/src/orchestration/Layers/ProviderCommandReactor.ts#L703-L756)
- Codex 原生 `collabAgent/*` 只在 Adapter 中翻译为通用 `task.*` 活动；子 turn 完成后是可续接的 `idle`
  ，不是再创建一套数字员工运行。[源码](https://github.com/pingdotgg/t3code/blob/0bfb6df34b26dfe0162db6c09dca00bc8c5a5ec4/apps/server/src/provider/Layers/CodexAdapter.ts#L506-L638)
- 缺点：t3code 本身使用 Effect、命令回执和投影，并不“轻”；Zeus 应借其边界，不应照搬其框架。

- `buzz-agent` 明确无持久化、无路由、无 Agent 编排；Provider 只是 Rust enum 上的一次 `match`。这证明它适合作为最小
  Runtime，但不能直接替代 Zeus
  的产品会话、恢复、任务和交付物。[边界声明](https://github.com/block/buzz/blob/571c1902d0ca55cfd4ccf6b91eeb731909cc10be/crates/buzz-agent/README.md#L337-L343) [Provider 实现](https://github.com/block/buzz/blob/571c1902d0ca55cfd4ccf6b91eeb731909cc10be/crates/buzz-agent/README.md#L235-L262)
- `session/set_model` 只给现有 session 写入一个模型 override，下一轮生效；Provider 仍是进程配置选定的同一个
  Provider。[协议定义](https://github.com/block/buzz/blob/571c1902d0ca55cfd4ccf6b91eeb731909cc10be/crates/buzz-agent/src/wire.rs#L95-L103) [实现](https://github.com/block/buzz/blob/571c1902d0ca55cfd4ccf6b91eeb731909cc10be/crates/buzz-agent/src/lib.rs#L615-L661)

  同时处理。[设计](https://github.com/block/buzz/blob/571c1902d0ca55cfd4ccf6b91eeb731909cc10be/VISION_AGENT.md#L13-L32) [并行队列](https://github.com/block/buzz/blob/571c1902d0ca55cfd4ccf6b91eeb731909cc10be/crates/buzz-acp/README.md#L214-L235)

### 三个项目对 Zeus 的共同答案

“在同一界面里选不同模型”不等于“同一个 Provider 原生会话可以无损换内核”。实现上必须分成四种能力：

| 能力                           | 语义                           | Zeus 行为                                     |
|------------------------------|------------------------------|---------------------------------------------|
| `in_session`                 | 原生运行时支持同 session 修改模型        | 下一 turn 使用新模型，记录会话默认选择与本 turn 实际选择          |
| `restart_with_native_resume` | 同 Driver 需重启，但原生 resume 身份兼容 | 在安全边界停止并用原生 cursor/thread 续接                |
| `new_segment_with_handoff`   | 不同 Provider/内核，原生身份不兼容       | 创建 provisional 分段，编译已确认交接，真实接纳后才提升为 current |
| `unsupported`                | Provider 既不支持切换也不能安全恢复       | 明确拒绝，不用伪续接隐藏能力缺口                            |

### 全量简化的功能影响矩阵

| 功能点                       | 去留/改造                                         | 收益                                          | 缺点与主要风险                                                     |
|---------------------------|-----------------------------------------------|---------------------------------------------|-------------------------------------------------------------|
| 统一产品会话                    | 保留                                            | 标题、任务归属、搜索、导出、Telegram 绑定和用户时间线有稳定身份        | 仍需 Zeus 持久化，不能完全交给 Provider                                 |
| 同 Provider 切模型            | 改为能力驱动                                        | 支持时原会话续接，代码路径最短                             | 模型的上下文窗口、思考参数、工具能力可变，必须重算有效配置                               |
| 跨 Provider 继续             | 保留分段和最小交接                                     | 满足 Zeus 的核心差异化能力                            | 隐藏推理、原生工具状态不能无损迁移；切换首轮更慢、可产生额外 Token/费用                     |
| 历史恢复与冷启动                  | Provider 原生历史 + Zeus 产品投影                     | 不再复制完整原生 item，减少假恢复                         | Provider 历史被删除时只能降级为产品时间线，不得冒充原生可续接                         |
| 队列、steer、replacement、未知结果 | 保留最小 submission/attempt/receipt               | 保证幂等、不重复计费和不误重发                             | 不能只看当前 Provider 状态删掉已派发证据                                   |
| 批准与用户输入                   | 收敛成一个 PendingInteraction 投影                   | 直接推送、页面和数字员工都得到同一结果                         | 不同 Provider 的表单/批准类型仍需保留原生 payload 引用                       |
| 上下文压缩                     | 分段内原生化，跨分段仅保留交接编译器                            | 删掉 Zeus 对 Codex/Pi 压力和压缩状态的重复模拟             | 跨 Provider 交接仍可能需要独立压缩请求，不能零成本                              |
| 附件、媒体、Artifact、工具结果       | 保留受管资产与引用                                     | 避免在多张会话表重复存大正文                              | 目标 Provider 不支持媒体/工具时必须呈现能力损失                               |
| Plugin、Skill、MCP、权限       | 保留冻结投影，集中预检                                   | 一处验证 namespace/schema/能力，避免任务接纳后才失败         | 各 Provider 的原生表达不同，不能强行统一为最大公约数                             |
| Codex/Pi 原生子 Agent        | 只由 Adapter 投影为 roster/activity                | 不再误建 TaskWorkRun 或 DigitalEmployeeExecution | 只能提供 Provider 原生支持的子 Agent 能力                               |
| 数字员工指派                    | 保留业务 WorkAssignment/Deliverable，执行引用普通会话      | 岗位、冻结能力、验收和返工仍可审计                           | 数字员工不得再从 `conversation.stage/providerState` 反猜运行结果，迁移需要仔细对账 |
| 阶段式多员工交付                  | 保留 StageAttempt/AcceptedDeliverable，每阶段关联普通会话 | 只把人工验收的交付物传给下一阶段                            | 比 AionUi Team 更强的审计要求意味着不能把阶段表全删掉                           |
| 互动 Team Mode              | 若确实保留，用“团队壳 + 每成员普通会话 + 邮箱/任务板”               | 成员可独立模型、权限、上下文和失败隔离                         | 这是显式新产品域，会增加合理复杂度；不应与原生子 Agent 或阶段员工混成一个概念                  |
| Fork、Rollback、Resume      | 按 Adapter capability 提供                       | 能力语义真实                                      | 页面功能不再对所有 Provider 对称，需要显示 `unsupported`                    |
| Token、费用、上下文用量            | 收敛成逐请求账本 + Provider 证据                        | 不再在会话、turn、segment 多处各算一次                   | Provider 不回传精确值时只能呈现未知/估算                                   |
| Telegram、Automation、外部推送  | 只订阅统一会话事件/outbox                              | 网页、直接推送、数字员工不再各走一条会话启动路径                    | 旧 cursor 和已发送回执迁移错误会导致重发或漏发                                 |
| Renderer 会话状态             | 删掉整份服务端投影缓存，仅保留草稿、附件和未回执乐观身份                  | 减少“后端已失败，前端仍运行”                             | 冷启动和事件断线必须有权威快照重建，不能只靠实时事件                                  |
| 数据迁移                      | 阴影读模型对账后单次切换，旧结构转只读过渡                         | 避免永久双写和双事实源                                 | 是全量重构的最高风险项；任何身份、顺序、回执、绑定错位都可能损坏历史会话                        |

### 推荐的目标边界

#### 1. 普通会话只保留七类必需事实

1. `ProductConversation`：用户可见的稳定身份、任务归属、标题、默认路由。
2. `NativeSegment`：Provider、原生 session/thread 身份、实际模型、`provisional/current/sealed/abandoned`。
3. `Submission`：不可变用户意图、队列、replacement/steer 关系。
4. `DispatchEvidence`：派发 attempt、是否写出、Provider 接纳/拒绝/结果未知回执；优先复用已有 Command
   Outbox/Receipt，不再为每条路径新建证据表。
5. `CanonicalTimeline`：已确认消息、处理过程、警告和资产引用的唯一产品投影。
6. `PendingInteraction`：批准、表单型用户输入和对应原生请求身份。
7. `ModelRequestLedger`：本次实际 Provider/模型/参数、Token、费用、缓存及原生证据引用。

这七类是概念边界，不代表必须新建七张表。正式实施时应先复用现有表的不可重建证据，再根据写入 owner 决定物理合并，避免为“简化”再造一套新架构。

#### 2. 所有发送入口只走一条命令链

`UI / 直接推送 / Telegram / Automation / 数字员工 / Team member`
→ `ConversationService.startOrSend`
→ 冻结 submission 与能力快照
→ 投影预检（包括 deferred tool namespace、schema、模型/工具/媒体能力）
→ 按 capability 选择原会话/可恢复重启/新分段
→ Provider Adapter
→ 持久化接纳或失败事实
→ 工作编排只订阅该事实。

数字员工不再启动“另一种会话”，也不再轮询 `conversation.stage/providerState` 猜测运行结果。Provider 明确拒绝必须在同一个耐久事务中终结
submission、放弃候选分段，并把失败传给 WorkAssignment/StageAttempt；这正是本次“直接推送报错、数字员工无反应”的必要修复边界。

#### 3. 三类“多 Agent”严格分开

- **Provider 原生子 Agent**：Provider 事实，Adapter 翻译为可见 roster/activity；不创建产品员工执行记录。
- **交互 Team**：每成员是一个普通会话，Team 只增加 Leader、邮箱、任务板、共享工作区和权限。
- **数字员工/阶段交付**：Zeus 业务事实，保留责任、冻结能力、验收、返工和已接受交付物，执行过程复用普通会话。

三者不能因为 UI 上都叫“Agent”就共用一个状态机。

### 全部按推荐目标实施的收益与缺陷

#### 收益

- 同一个 Provider 拒绝只翻译一次，直接推送、数字员工、Telegram 和页面不再出现四种结果。
- 会话、分段、队列、回执、工作指派的 owner 清晰，修复缺陷时不需同步修改多个相互反猜的状态机。
- 同 Provider 切模型走原生能力，跨 Provider 切换走显式分段，能力和失真边界都可见。
- Renderer 只保留有限乐观状态，冷启动、重连和多窗口都回到同一后端快照。
- 新 Provider 主要实现 Adapter 和 capability，不必复制整个 Zeus 会话引擎。
- 存储、迁移、恢复和 GUI 验收面明显缩小，静态检查之外也更容易建立真实 Codex/Pi 协议验收。

#### 缺陷和不可消除的代价

- 这仍是最高风险数据与运行链重构；不宜一次性改表、改命令链、改 Renderer 和改数字员工。
- 产品界面可以统一，Provider 能力不会因重构而对称；Fork、Rollback、Steer、批准、媒体、子 Agent 仍可能显示不支持。
- 跨 Provider 交接必然只能传递显式、已确认事实，不能携带隐藏推理和所有工具内部状态。
- 切换新 Provider 的首轮需要新建运行时、投影工具/权限并可能整理历史，延迟与费用会高于原会话内切模型。
- 收缩后仍需保留产品时间线、派发回执、未知结果、资产和业务验收等不可重建事实；不可能降到 AionUi 普通会话的两张表。
- AionUi 的 `aioncore` 边界没有在当前对照仓库中完整展开，t3code 的 Effect/投影体系也很重，Buzz 则故意不做持久化与编排；三者都不能整体搬进
  Zeus。
- 上文“再净删 25000 行”的估算不再作为决策依据。保留跨 Provider 交接、未知结果和已验收交付物后，可安全删除的数量必须在新写入
  owner 落定后重新计算。

### 推荐实施顺序

1. **先止血**：修复 deferred tool namespace 预检，让直接推送与数字员工对同一个 `thread/start` 拒绝得到相同终态；完成真实
   Codex/Pi 协议检查。
2. **先定合同，不改表**：定义 Runtime Adapter capability 和单一运行事件词汇，各入口改走同一 `startOrSend`。
3. **收敛状态翻译**：Provider 原生事件只在 Adapter 翻译一次，工作编排改为消费耐久接纳/拒绝/终态事实。
4. **建阴影读模型**：用旧事件生成新的最小会话快照，在真实会话、冷启动、断线、未知结果和跨 Provider 切换中对账；暂不双写两套权威业务状态。
5. **单次切换普通会话**：迁移产品会话、分段、submission、回执、PendingInteraction 和时间线，旧路径变为只读导入边界。
6. **再迁数字员工和阶段工作**：只保留业务责任、冻结能力、验收和交付物，所有执行引用普通会话终态。
7. **最后删旧实现**：只在历史数据干跑、真实 Codex/Pi、GUI、完整退出重启、Telegram/Automation 和多窗口几何都通过后，才删除重复表、缓存、协调器和迁移围栏。

最终推荐是“**目标架构全量收缩，实施分阶段单路切换**”，不是在一个版本中全部推倒。这样才能同时得到简化收益，又不牺牲 Zeus
相对三个开源项目更难、也更有价值的跨 Provider 产品会话连续性。

## 2026-09-01 一次性优化交付蓝图

### “一次性”的精确含义

- 一个候选版本完成代码、数据、Renderer、数字员工和外部入口收敛。
- 内部允许分波实现、对账和运行验收，但最终只有一个新写入 owner、一次 schema generation 切换、一次发布。
- 不接受“一次大改、没有对账、没有回退边界”的理解；那不是优化，是一次性放大故障面。

### 十条不得破坏的结构不变式

1. 一个用户可见会话始终只有一个稳定 `conversationId`。
2. 一个会话最多一个 `current` 分段和一个未决的 `provisional` 分段。
3. submission 的“本地入队”、“已写出”和“Provider 已接纳”是三个不同事实。
4. Provider 明确拒绝必须终结当次派发；写出后无回执必须保持 unknown，不自动重发。
5. UI、任务直接推送、Telegram、Automation、数字员工和 Team member 只能调用同一个会话命令入口。
6. Provider 原生事件只能在对应 Runtime Adapter 翻译一次。
7. 工作指派/数字员工状态只消费耐久会话接纳、等待和终态事实，不读取 `stage/providerState` 反猜。
8. 同模型系续接、同 Driver 重启续接、跨 Provider 交接和不支持必须是四种显式 capability。
9. Provider 原生子 Agent、交互 Team 和 Zeus 数字员工是三个不同领域。
10. Renderer 从不拥有服务端运行真相；本地只保留草稿、附件和尚未回执的乐观消息身份。

### 一次候选版本内的实施波次

#### 波次 A：冻结现场与验收基线

- 暂停会话、Provider、数字员工和外部推送的并行功能修改。
- 对真实数据库副本、Provider 原生身份和受管资产做只读清单、数量和摘要对账。
- 固定现有缺陷基线：新建会话 namespace 拒绝、直接推送通用错误、数字员工假 active。

#### 波次 B：建立唯一命令核心

- 使用一个 `ConversationService` 提供 `startOrSend`、`switchModel`、`interrupt`、`respond`、`archive`、`restore`。
- 现有 Codex/Pi coordinator 先收回为两个 Runtime Adapter，不增加新框架或中间件。
- 所有动态工具、MCP、Skill、附件、模型和权限投影在 Provider 启动前集中预检，其中 namespace 违约在注册时即拒绝。

#### 波次 C：收缩耐久事实

- 保留 `conversations`、`conversation_runtime_segments`、`conversation_submissions`、`command_outbox`、
  `command_delivery_receipts`、`conversation_timeline_events`、`conversation_server_requests`、
  `conversation_model_requests` 及真正的资产/业务表。
- `conversation_switch_operations` 改由 submission + provisional segment + command receipt 表达；
  `conversation_model_history`、`conversation_process_items`、持久警告和恢复日志收敛到唯一 timeline 事件流。
- 交接上下文只保留一份可定址的 handoff artifact，其水位、能力损失和使用请求关联在目标 segment；删掉第二套压力/压缩状态机。
- `conversation_messages/items/turns` 在迁移对账期仅作旧投影，新快照只从 canonical timeline、pending
  interaction、submission 和 Provider 有界摄取状态构建。
- 本波次不盲目合并目标不同的资产、变更集、Plan、Goal、审计和安全表。

#### 波次 D：重接业务编排

- `task_work_runs` 成为一次工作执行的通用记录；`digital_employee_executions` 停止作为第二运行事实，数字员工模板/自动化仅创建工作项和普通会话。
- 阶段式工作保留 `task_stage_attempts/deliverables`，但 attempt 关联通用 work run 和普通会话；下一阶段只读取已验收交付物。
- Provider 原生子 Agent 只投影活动；若保留 Team，每个 Team member 是独立普通会话。

#### 波次 E：替换 Renderer 真相模型

- 后端输出一份有代次、有水位的权威会话快照，实时事件只做快照之后的增量。
- 删掉整份 `NativeSessionState` 磁盘缓存和与服务端重复的运行 reducer；保留必要的显示 fold、草稿、附件和 optimistic client
  message id。
- 错误详情、等待批准/输入、未知结果、切换能力损失和不支持能力都是一级 UI 状态，不用通用“请重试”遮蔽。

#### 波次 F：单次数据与写入 owner 切换

- 候选版本先在真实数据库副本上干跑迁移，校验表数量、关联身份、时间线顺序、分段唯一性、派发回执和资产摘要。
- 正式升级先关闭外部入口并建立可恢复数据库/资产快照，完成迁移和完整性检查后才开启新 writer。
- 新 writer 开启前失败则保持旧数据不变；开启后禁止旧版本再写新库，失败时进入维护/对账态，不用双写或自动降级破坏新事实。
- 切换完成后删掉所有旧 writer、过渡 feature flag 和双路运行代码，仅保留显式离线导出/导入工具。

### 放行前必须全部通过的真实验收

- **Codex**：新建、续聊、同 session 切模型、中断、steer/replacement、批准、用户输入、工具、附件/图片、子 Agent、归档/恢复。
- **Pi**：新建、续聊、模型配置、中断、批准/输入、工具、原生压缩、完整退出后恢复。
- **跨 Provider**：Codex→Pi→Codex 与 Pi→Codex→Pi，切换被拒绝、写出后断连、交接超窗口和能力损失均有真实证据。
- **入口一致性**：UI、任务直接推送、数字员工、Telegram 和 Automation 对同一接纳/拒绝得到同一终态和同一错误详情。
- **数字员工**：成功交付、等待人工、明确拒绝、结果未知、重新指派、阶段验收/返工。
- **恢复与 GUI**：空闲/运行/等待/未知四种状态下完整退出重启，多窗口、错误详情弹窗、会话切换、不抢焦点和不遮挡。
- **数据**：真实历史副本迁移、重复干跑幂等、`PRAGMA quick_check`、无孤儿关联、无多 current segment、无已失败会话对应 active
  work run。
- **工程与包**：`pnpm lint`、`pnpm typecheck`、`pnpm build`、`pnpm package:mac`、`git diff --check`；仅启动独立身份和独立数据根的
  `Zeus Test.app`。

任意一项不通过，都不进入正式发布。“一次机会”不改变证据标准。

### 明确不做

- 不引入新状态机、Event Sourcing 框架、Effect 或新数据库。
- 不复制 AionUi、t3code 或 Buzz 的框架，只借它们已证明的边界。
- 不重写 App Server 或 Pi 已有的 session、turn、压缩、中断和子 Agent 能力。
- 不为保持“所有 Provider 功能对称”伪造不可保证的续接、Fork、Rollback 或 Team 能力。
- 不保留长期双写、旧 writer 或“以后可能用到”的兼容层。
