## 用户现场

1. 已有会话 Provider thread：`01a05a8a-5293-7e92-a0e7-f40f96cc548d`，界面提示“Codex 模型能力尚未就绪，这条消息未发送”。
2. 新任务推送临时导航身份：`task-push:7810e609-af47-4b96-956b-e9db7ef1788e:thread`，界面仅提示“当前操作未完成，请稍后重试”。
3. Zeus 没有升级或重启，故障前几秒仍能正常工作。

## 修正后的结论

两个现场是同一个运行根因，不是两个独立故障，也不是附件损坏。Zeus 主进程没有重启，但 Codex Remote Control 的后台 app-server
子进程在升级切换中被替换；Zeus 在原管理器对象内自动连接新守护进程时，没有从 `zeus/0.152.0`
识别真实版本，而是复用了旧进程启动时探测到的回退版本。随后精确版本门禁把 `0.152.0` 模型目录判为不兼容，运行世代
`601e1d3f-7f70-4440-96b2-1a5ebbee0c41` 因而冻结了空模型预算。

两个发送入口都读取该空预算，所以均在 Provider 正文写入前以 `ZEUS_CONTEXT_MODEL_WINDOW_UNAVAILABLE` 失败。

## 现场时间线

- 10:21:43：最后一笔成功 Provider 派发开始，10:22:03 正常完成。
- 10:22:07：Codex `0.152.0` release 目录出现。
- 10:22:58：旧 app-server 进程最后留下日志；Zeus 主进程没有退出。
- 10:23:09：同一个常驻更新守护进程拉起 `0.152.0` app-server。
- 10:23:14：Zeus 建立新运行世代 `601e1d3f-7f70-4440-96b2-1a5ebbee0c41`。
- 10:32:51、10:34:56：普通会话和任务推送先后以相同世代、相同错误码在写入前失败。

这条时间线解释了“Zeus 没有升级或重启，错误却突然出现”：发生切换的是 Zeus 连接的后台 Codex 子进程，不是 Zeus 主应用。

## 代码根因

1. `providerVersionFromInitialize` 只识别 `codex/*`、`codex-cli/*` 和 `codex desktop/*`，不识别 Remote Control 实际返回的
   `zeus/<版本>`。
2. `createCodexAppServerManager` 会在 Remote Control 连接退出后原地自动重连，但 `providerVersionFallback` 只在外层
   Runtime entry 创建时探测一次。
3. 因此热切换后的新守护进程继续继承旧回退版本；`resolveCodexModelBudgetSnapshot` 的精确 `client_version` 门禁正确地拒绝了不匹配目录。
4. 模型预算按 generation 一次性冻结，空预算不会在发送热路径随文件变化而漂移。
5. 发送前预算解析此前读取 `getState()` 的全局活动 generation，而不是提交或 Provider thread 已绑定的
   generation；这不是本次两个会话同时失败的直接触发点，但在多世代并存时会造成另一类串代风险。
6. 新会话此前先调用 `thread/start`，再执行完整上下文预算编译，因此预算失败可能留下没有正文的 Provider thread。

## 已实施修复

### Remote Control 版本与预算快照

- 初始化握手现在识别 `zeus/<版本>`。
- Remote Control 不再把命令路径探测值当作真实守护进程版本；握手没有版本时保持未知并失败关闭，避免伪造兼容性。
- generation 初始化时如果模型目录正处于升级写入窗口，最多进行 `100ms + 400ms` 的有界重读；成功后仍只冻结一次，不让发送路径读取可变文件。

优点：修复后台子进程热替换的直接根因，同时覆盖升级瞬间的小型文件时序窗口。缺点：极端情况下新世代就绪最多增加
500ms；握手缺失版本时会明确失败，而不是冒险沿用旧版本。

### 会话世代隔离与写入前门禁

- `CodexAppServerManager` 新增按 generation 只读能力查询。
- 模型预算按提交或 Provider thread 绑定的 generation 解析，不再用全局当前 generation 代替。
- 新会话在 `thread/start` 前检查该 generation 的模型窗口；失败时不会创建 Provider thread，也不会写入正文。

优点：多世代并存时不会串用模型窗口，新会话的预算失败点前移到第一笔 Provider 写之前。缺点：找不到精确 generation
能力时仍会失败关闭，需要用户先恢复运行世代。

### 用户恢复语义

- 普通会话与任务推送统一显示：消息尚未发送、需要重新连接 Codex、之后逐条重试。
- 模型窗口错误卡片新增“重新连接 Codex”，调用现有 generation 热激活接口并刷新会话连接。
- “重新连接 Codex”只刷新运行世代，不会重发历史消息；原消息仍须用户逐条点击“重试”。

优点：避免含糊错误和重复发送。缺点：为了保持外部写入安全，恢复后需要一次显式人工重试。

## Ponytail 审查后的结构收缩

- 将派发租约、预算预检、Provider thread/turn 写入、降级重试和写入结果归类集中到具体的
  `codexNativeDispatchPipeline.ts`。协调器只保留一个派发门面，不增加接口层、工厂层或依赖。
- 将交互恢复和 turn 结果恢复合并为一个恢复所有者，删除只做转发的
  `codexTurnResultRecoveryApplication.ts`。
- Provider 事件投影、历史投影和恢复模块不再接收 `Record<string, any>` 依赖袋，所有实际依赖都有明确类型。
- 生产调用方始终提供的仓储、时钟、执行上下文、模型预算和投影服务改为必选，删除不可达的空仓储回退和可选分支。
- 将单导出的 `codexNativeConversationCoordinatorPorts.ts` 合并进现有契约文件；删除从未配置的
  `operationId`、`turnResultTimeoutMs`，分别固定使用 `randomUUID` 和 `60_000ms`。
- 协调器由 3941 行降至 3352 行，减少 589 行。相关模块合计反而增加 221 行，原因是删除 `any`
  后补齐了真实依赖契约；这是用少量声明换取编译期边界，不把“拆文件”伪装成总代码量下降。

优点：派发状态、恢复状态和投影职责各有唯一所有者，协调器风险明显下降，错误接线可由 TypeScript 直接拦截。缺点：事件投影
仍有 1526 行、历史投影仍有 932 行；本轮没有继续机械拆分，以免产生更多只转发的模块和接口。
