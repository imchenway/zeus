## “发送已暂停”的精确含义

“发送已暂停”是一个总括状态：消息已经保存为 Zeus submission，但当前没有可靠进入 Provider
turn；是否能够自动恢复要看具体暂停原因。它不是模型主动暂停，也不表示模型仍在思考。

截图中的两条重复正文不是 Renderer 把同一记录画了两遍。正式账本存在两次独立接纳：

- `conversation_submission_ae3a34ef6c4ad75f8c9d63b0`：`2026-09-02T14:50:51.413Z`
- `conversation_submission_74e0201dcfca4d6ec4f5770c`：`2026-09-02T14:52:14.948Z`

两条记录都是 `status=paused`、`paused_reason=preflight_failed`、`provider_turn_id=null`，错误码均为
`ZEUS_CONTEXT_INPUT_BUDGET_EXCEEDED`。因此两条消息都没有发送给模型，也不会自行继续；本次现场不是连接断开或 Provider 拒绝。

修复前 Renderer 仅为连接、归档、停止确认等少数暂停原因提供专用文案，其他原因统一回退成“发送已暂停”，导致用户看不到“上下文超过模型窗口”及下一步。

## 排队与错误引导的正式现场

目标会话为 `conversation_22c6414bd2434c2def1ba25c`，Provider turn 为 `01a062ad-bf33-7b40-ada5-37e97c0a830d`。

关键时间线：

1. `15:13:36.033Z`，后续问题被保存为普通 `queue` submission；`15:13:38.165Z` 点击“引导”后改为 `dispatching`，绑定当前
   Provider turn。
2. `15:14:58.014Z`，同一 Provider turn 已经持久化一条 `phase=final_answer` 的正式正文。
3. `15:16:29.871Z`，用户再次发送 Pi 问题。队列仍认为同一 Provider turn 活动，因此消息先显示“排队中”。
4. `15:17:05.381Z`，点击“引导”后，该 submission 同样绑定旧 Provider turn；`15:17:09.097Z` Provider 用户项进入该
   turn，随后继续产生思考、工具和最终正文。
5. `15:22:26.783Z`，整个 Provider turn 才最终完成。

所以“排队”来自 Zeus 的既有规则：活动 turn 中普通发送先入下一轮队列；“引导”则把队首提交注入当前活动 turn。问题不在数据丢失，而在
Zeus 把 Provider turn 生命周期直接当成用户可理解的一轮对话。

## 根因

### 1. 送达门禁仍允许向已经出现正式正文的 turn 引导

- 修复前 Renderer 的 `canSteerActiveTurn()` 同时允许 `active_prework` 与 `active_final_answer`。
- 修复前 Local Server 的 `sendQueuedNow()` 只校验 run state 为 `active/waiting`，没有拒绝已经持久化正式 `final_answer`
  的目标 turn。
- 因此只要 Provider 尚未发出 `turn/completed`，用户即使已经看到正式正文，仍可把新消息塞进旧 turn。

### 2. 展示层主动把同 turn 的后续用户消息塞入处理过程

`ConversationTranscript.projectTranscriptTurnRows()` 当前明确把同一 turn 的第二条及后续用户消息视为 `midTurnUserRow`，并放入
`turn_work` 折叠过程。于是送达层一旦把引导消息绑定旧 turn，Renderer 就会按设计将它显示在旧处理过程内部，而不是新的顶层对话轮次。

这不是偶发 CSS 错位，而是 Provider turn、用户可见回复周期和处理过程分组被合并成同一个身份。

### 3. Zeus 把 Provider 自己的上下文职责重复实现了一遍

- 同一路由续聊会根据 Zeus 的估算主动调用 Codex `thread/compact` 或 Pi `AgentSession.compact`。
- 同一分段完成两次原生压缩，或 Pi 压缩后估算仍为负数时，Zeus 又会擅自创建新分段。
- Codex 能力列表只读取 app-server 模型目录中的窗口字段，派发却读取同代际 `modelBudgets`，导致交接预检和真实派发可能使用不同窗口。
- 固定输入的粗略字节估算一旦超过窗口，就会在 Provider 看到消息前写成 `preflight_failed`；这正是截图中“发送已暂停”的来源。

这套逻辑既没有 Provider 的精确请求计数，也不能比 Provider 更可靠地决定原生压缩时机。Zeus 真正需要控制的只有换 Provider
或换运行路由时的有界交接内容。

## 已实施方案

本次只保留一个清晰边界：

1. 同一 Provider 会话：删除 Zeus 的主动压缩触发和“压缩两次就换段”策略，由 Codex app-server 或 Pi SDK 自己管理原生上下文。
2. 换 Provider 或真实换路由：保留有界便携上下文及唯一交接容量规划；Codex 能力列表优先复用同代际 `modelBudgets`
   的窗口值，与派发事实源一致。
3. 普通续聊：Zeus 的 token 估算只削减可选应用上下文，不再以 `ZEUS_CONTEXT_INPUT_BUDGET_EXCEEDED` 抢先拒绝核心用户消息。
4. 正文送达边界：当前 turn 已有完成的正式正文或正式计划后，Renderer 关闭“引导”；共用消息入口把陈旧 `steer_now`
   自动降级成普通队列，Codex 队列“立即发送”边界再次复验并保持原提交不变。
5. 暂停文案：`preflight_failed` 优先显示持久化的真实错误；没有错误详情时明确写成“发送前检查未通过，消息尚未发送”。
6. 历史展示：不重排、不迁移已经发生的历史 steer。送达关系修正后，新消息自然进入新 turn；历史投影另立任务处理，避免把展示改造混进本次根因修复。

优点：职责边界更短；同一会话不再维护第二套压缩状态机；普通消息不会被不精确估算吞掉；界面、远程入口和服务端竞态得到同一结果；无需迁移历史数据。

缺点：Provider 仍在收尾但已经产出正文时，新消息会短暂排队到 `turn/completed`；跨 Provider 的交接容量仍需 Zeus 管理；历史中已经错误进入旧
turn 的消息仍按原始事实展示。

没有采用“只改按钮文案”“只移动气泡”或新增轮询观察器。前两者不能阻止错误送达，后者会扩大状态竞争面且没有本次现场证据支持。
