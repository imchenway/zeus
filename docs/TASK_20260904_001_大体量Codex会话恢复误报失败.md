# 大体量 Codex 会话恢复误报失败

## 结论

指定 Codex 会话文件没有损坏，最后一轮也已经正常结束。Zeus 在发送下一条图片消息前恢复 Provider 会话时，把超过固定 120 秒仍未返回的
`thread/resume` 当成失败，导致一条尚未写入 Provider 的本地提交进入“需要恢复”状态。

本次修复移除 `thread/resume` 的固定等待上限：只要 Provider 进程仍然存活，Zeus 就等待它给出明确结果；执行宿主退出或交接时，Zeus
主动取消本地等待，随后由既有关闭流程终止 Provider 进程。不会自动重试 `thread/resume`，也不会重复发送用户消息。

## 现场证据

- 会话文件：
  `/Users/david/.zeus/providers/codex/sessions/2026/09/03/rollout-2026-09-03T12-02-38-01a0656e-d72f-78b0-9e90-954749c46fed.jsonl`。
- 文件大小为 37,752,115 字节，共 519 条 JSONL 记录。最后一轮 Provider turn 为 `01a06a97-25db-7d52-b3cf-f805990aacd2`
  ，已有最终回答和 `task_complete`，不是未结束轮次。
- Zeus 状态库中的会话为 `conversation_6e596e5e4428542bda40476d`。新提交 `conversation_submission_VZzHVBOm-WO0` 没有
  `provider_turn_id`，说明图片消息还没有写入 Provider，可以安全保留在本地队列。
- 该提交在 2026-09-04 15:39:16（Asia/Shanghai）进入 `paused / recovery_required`，错误为
  `ZEUS_CODEX_RPC_TIMEOUT: Codex app-server request timed out: thread/resume`。
- 截图中的“当前操作未完成，请稍后重试”与“重新恢复”正是上述暂停状态的通用展示，并非 JSONL 损坏提示。

## 根因

`thread/resume` 会加载完整历史，耗时会随会话体积增长。旧实现无论历史大小都只等待 120 秒；超时后删除本地 RPC 等待项，Provider
稍后返回的真实结果也无法再交给原恢复流程。

单纯继续调大超时时间只能把问题推迟到更大的会话。自动重试也不安全，因为首次请求是否已经在 Provider 内完成并不明确。

## 实现

- `CodexThreadResumeInput` 增加只用于宿主关闭的取消信号。
- 通用 RPC 允许明确关闭超时，同时保留其他 RPC 原有的 30 秒默认超时和只读 RPC 重试边界。
- `thread/resume` 不再使用固定超时，等待 Provider 明确成功、明确失败或进程退出。
- Provider 会话权威模块在关闭时触发取消信号，使正在加载大体量历史的恢复不会阻塞 Zeus 交接和退出。

## 优缺点

优点：

- 不再用历史体积无关的数字误判失败。
- 不重放恢复请求和用户消息，保留现有的防重复边界。
- 只有 `thread/resume` 改为无固定上限，其他 RPC 的超时与重试策略不变。
- 关闭时可以收口等待，不会为了修复慢恢复而制造退出死锁。

缺点：

- 如果 Provider 进程存活但永远不返回，界面会继续保持恢复中，直到执行宿主退出或 Provider 进程退出。协议没有取消单次
  `thread/resume` 的能力，在“慢”和“挂死”无法区分时，这是比伪造失败更安全的取舍。
