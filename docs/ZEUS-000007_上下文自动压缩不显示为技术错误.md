# ZEUS-000007 上下文自动压缩不显示为技术错误

## 任务目标

修复 Codex 自动整理长会话上下文时，被 Zeus 错误显示为红色“本轮错误”和原始技术详情的问题。正常整理过程应提供低噪音反馈，完成后归入工作活动；只有真实失败才使用错误语义。

## 现场与根因

- 用户截图中的条目原始类型为 `contextCompaction`，状态为 `in_progress`，没有失败状态或错误正文。
- app-server 通过 `item/started` 与 `item/completed` 发送该条目。
- Zeus 的会话条目白名单不包含 `contextCompaction`，未知类型统一被映射为 `error`。
- Renderer 因持久化类型为 `error`，显示红色“本轮错误”，并把原始负载放进“技术详情”。
- 因此这是正常过程事件被错误分类，不是上下文整理失败，也不是执行轮次失败。

## 用户确认的产品边界

1. 正常整理进行中显示“正在整理较早对话以继续工作”。
2. 正常整理完成后显示“已整理较早对话”，并收进工作活动。
3. 正常整理不使用红色错误样式，不展示原始 JSON 技术详情。
4. 真正失败的条目仍保留失败状态和错误表达，本任务不隐藏真实错误。
5. 历史上已被误分类、且原始负载明确为 `contextCompaction` 的条目需要精确修正；其他错误记录保持不变。

## 方案与取舍

### 采用短暂过程提示并归入工作活动

优点：用户能理解短暂停顿原因；不会把系统自我维护误解为任务失败；完成后不占据消息主线。

缺点：相比完全静默，会多一条可展开的历史活动。

### 未采用完全静默

优点：会话最简洁。

缺点：长会话整理期间可能暂时没有新输出，用户无法判断是正常等待还是卡住。

### 未采用长期独立消息

优点：过程最容易被追溯。

缺点：内部维护活动会与用户消息、回答争夺主线注意力，长会话中噪音明显。

## 实现范围

- Storage 与 Coordinator 正确认识 `contextCompaction` 条目类型，不再降级成 `error`。
- 历史迁移只修正负载类型明确匹配的误分类记录。
- Renderer 把该类型归入工作活动，并提供中英文进行中、完成文案。
- 不新增或恢复单元测试体系；按项目当前规则执行代码规范、类型、构建及必要的测试应用真实运行检查。

## 验收要求

- `contextCompaction + in_progress` 显示为“正在整理较早对话以继续工作”。
- `contextCompaction + completed` 收进工作活动并显示“已整理较早对话”。
- 正常整理不出现“本轮错误”“技术详情”或红色错误样式。
- 真实 `error` 条目和真实 `failed` 状态仍按错误展示。
- 历史误分类只按原始负载类型精确修正。
- `pnpm lint`、`pnpm typecheck`、`pnpm build` 与 `git diff --check` 通过；构建成功不冒充真实运行验收。
