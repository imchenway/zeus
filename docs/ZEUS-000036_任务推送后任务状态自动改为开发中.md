# ZEUS-000036 任务推送后任务状态自动改为开发中

## 当前阶段

实现与本地验证已完成，用户已明确授权提交并推送当前任务分支。真实 provider 任务推送会创建外部 Codex 执行轮次，本轮未代替用户触发，运行态行为仍待隔离现场验收。

## 任务目标

任务从“待开始”首次成功推送到新会话后，任务管理状态自动改为“开发中”，减少用户重复维护状态的操作。

## 用户确认的规则

1. 自动迁移只允许 `todo`（待开始）变为 `in_development`（开发中）。
2. `in_testing`、`awaiting_acceptance`、`blocked`、`completed`、`cancelled` 等其他管理状态保持原值，推送不会使其回退或重开。
3. “推送成功”必须同时满足：真实会话已经持久化，首条消息对应的执行轮次已经进入 `active`。
4. 仅点击推送、只创建会话、首轮发送失败或等待重试都不修改任务管理状态。
5. 推送过程中如果用户已把任务改为其他状态，完成回调不得覆盖用户的新状态。
6. 自动迁移需要写入任务事件、审计记录并发布实时任务更新，使列表和详情读取同一事实。

## 源码事实

- 权威推送链路位于 `packages/local-server/src/index.ts` 的任务会话接收流程，前端只负责提交和读取服务端结果。
- `nativeOperation.status === 'active'` 表示真实会话与首轮执行已经建立；只有 `providerThreadId` 表示可能只建立了会话，首轮仍可能失败。
- 现有实现会在任务推送时把 `completed` 或 `cancelled` 自动改为 `in_development`，且发生在首轮成功判断之前；这与本次确认规则相反。
- 任务管理状态和内部任务运行状态是两套独立事实；本次不改变 `TaskStatus` 的既有运行迁移。

## 领域决策

### 迁移范围

采用“仅待开始自动进入开发中”。

- 优点：符合首次开工语义，不覆盖用户已经维护的测试、验收、阻塞或终态。
- 缺点：用户在其他阶段推送新会话时仍需自行决定是否调整任务阶段。

不采用“任意非终态都进入开发中”：

- 优点：所有活跃推送看起来都处于同一阶段。
- 缺点：会把测试中、待验收和已阻塞错误回退，丢失项目管理事实。

不采用“已完成或已取消自动重开”：

- 优点：减少手工重开步骤。
- 缺点：一次补充询问就能隐式推翻终态，风险不可接受。

### 成功边界

采用“首轮执行已进入 active 后迁移”。

- 优点：状态变化与真实开发启动一致，不把点击、排队或半成功误记为开工。
- 缺点：会话已创建但首轮失败时，任务仍保持待开始，需要用户重试。

不采用“点击推送即迁移”或“会话创建即迁移”：

- 优点：界面反馈更早。
- 缺点：服务端失败后会留下错误的开发中状态，还需要补偿回滚并处理竞态。

## 实现范围

1. 删除推送时自动重开已完成、已取消任务的旧逻辑。
2. 在服务端确认首轮 `active` 后重新读取任务最新状态。
3. 仅当最新管理状态仍为 `todo` 时原子更新为 `in_development`。
4. 记录自动状态迁移事件、系统审计和 `task.updated` 实时事件。
5. 不新增或恢复已退役的自动化单元测试体系。
