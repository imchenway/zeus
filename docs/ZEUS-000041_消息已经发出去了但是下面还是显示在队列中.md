# ZEUS-000041 消息已经发出去了但是下面还是显示在队列中

- 阶段：实现与真实界面验收已完成。
- 用户现场：上一轮仍在生成时发送新消息，上方立即出现用户气泡，底部又显示同一条“待发送”队列记录。

## 现场归因

当前界面在用户点击发送时先创建临时用户气泡；若上一轮仍在执行，服务端会把同一提交保存为队列消息。临时气泡与真实队列随后同时展示，因此用户看到两份相同内容，并把临时气泡误认为模型已经收到。

同时，自动派发成功后服务端此前没有立即广播队列变化；即使 Provider 已经接管，旧队列快照仍可能继续留在界面。截图中的问题因此包含“同一提交被两个表面投影”和“接管后队列快照未及时清除”两层原因。

截图中临时气泡还会被后续新增的上一轮活动项包围，导致对话时间顺序看起来已经进入下一轮，实际模型仍在处理上一轮。

## 已确认的领域与交互口径

### 状态语义

- “队列消息”是 Zeus 已保存、模型尚未接收的用户输入。
- 气泡出现只代表 Zeus 已接收；必须常驻显示“排队中”。
- 只有模型端确认接收后，队列消息才转为普通用户消息并移除排队状态。

### 展示与顺序

- 同一条队列消息只显示一次，不再保留底部独立队列面板。
- 队列消息以待发气泡形式固定在当前正在生成的回答之后，不得插入上一轮回答中间。
- 多条队列消息继续按真实队列顺序排列；上一轮结束后沿用现有逐条自动派发机制。

### 操作

- “排队中”始终可见。
- 编辑、删除、立即发送、上移和下移在鼠标悬停或键盘焦点进入待发气泡时显示。
- 拖动不是唯一排序方式，保留上移和下移按钮，保证键盘用户可以完成同样操作。
- 图标按钮必须有可访问名称、可见焦点，并满足最小命中尺寸。

## 方案取舍

优点：同一内容只出现一次；对话时间顺序与真实模型轮次一致；用户能区分“Zeus 已接收”和“模型已接收”；既有队列操作不丢失。

代价：队列状态和操作需要进入会话气泡组件；待发气泡必须同时响应实时回答增长、队列排序和 provider 确认，状态同步比独立底部面板更复杂。

不采用“仅保留底部队列”：虽然领域边界最清楚，但不符合用户确认的气泡式交互。

不采用“两处保留”：即使补充状态文案，仍会重复展示并破坏时间顺序。

## 已完成的实现

- Local Server 的队列快照只包含尚未取得 `providerTurnId` 的 `queued/paused` submission；失败轮次不再进入队列表面。
- submission 进入 provider 轮次或派发转入恢复状态时立即广播队列变化，避免其他窗口保留旧快照。
- Renderer 在收到轮次开始事件时同步移除对应队列记录，作为实时广播之外的顺序保护。
- 临时气泡按 `clientUserMessageId` 与队列 submission 对账；排队内容从普通 transcript 行中移出，固定渲染在当前回答之后。
- queued 临时项在 provider 用户消息到达时移动到真实事件位置，避免恢复为普通气泡后跳回上一轮回答中间。
- 新增待发气泡组件，保留编辑、删除、立即发送、上移、下移、继续和恢复能力；操作在 hover/focus-within 时显示。
- 编辑队列消息时同时更新实际派发文本和正式气泡展示文本，避免队列里显示新内容、接管后又恢复旧内容。
- Composer 删除独立底部队列面板，只保留输入职责。
- `DESIGN.md` 已新增本任务队列消息气泡契约。
