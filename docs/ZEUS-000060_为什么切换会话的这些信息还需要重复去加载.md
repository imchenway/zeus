# ZEUS-000060 为什么切换会话的这些信息还需要重复去加载

## 用户现场

用户每次切换已有会话时，标题区显示“正在加载会话”，正文区域退回骨架占位和大面积空白。即使会话刚刚查看过，切回时仍需等待整份会话重新读取，影响在多个会话之间连续工作的体验。

## 根因证据

- 父层以会话 ID 作为 `ConnectedSessionWorkspace` 的 React `key`；切换会话会卸载旧会话控制器并创建新控制器。
- 新控制器只接管尚未落盘的乐观消息，不接管刚刚成功读取的完整会话快照，因此初始正文为空。
- 新控制器每次都会重新建立事件连接并读取权威会话快照；这是保证状态一致性的后台校准，但不要求在校准前清空已经读取过的真实内容。
- 父层现有缓存只记录会话列表所需的运行状态，没有保存可直接展示的正文快照。

## 已确认产品口径

1. 首次打开且没有热缓存时，继续等待权威会话快照并显示加载状态。
2. 切回本次应用运行期间已经成功读取过的会话时，立即显示上次真实正文，后台读取权威快照并校准。
3. 正在处理、等待用户回答、等待审批、正在停止、排队或需要恢复的关键会话全部保留，不参与普通缓存淘汰。
4. 除关键会话外，按最近使用顺序额外保留十个会话。
5. 后台刷新失败时保留已有正文，在顶部显示轻量失败提示并允许重连，不能退回空白页。
6. 热缓存不跨应用重启持久化，避免把磁盘旧数据冒充当前权威状态。

## 方案取舍

### 采用：内存热缓存加后台权威校准

优点：

- 已查看会话切回时不再白屏，阅读和上下文连续。
- 关键会话不会因普通数量上限而丢失界面现场。
- 后台仍读取权威快照，不改变服务端、数据库和原生会话身份。

缺点：

- 本次应用运行期间会增加一部分内存占用。
- 同时存在大量关键长会话时，实际保留数量可能超过十个普通会话的上限。
- 热缓存只改善重复切换，应用重启后的首次打开仍需加载。

### 不采用：只缩短或美化整页加载态

优点是改动较小；缺点是用户仍需等待，而且已经读取过的真实内容仍会被主动清空，因此不采用。

### 不采用：把全部会话正文长期写入磁盘缓存

优点是应用重启后也能更快显示；缺点是需要处理过期、结构升级、隐私和磁盘占用，超出本任务范围，因此不采用。

## 实施记录

- 新增本次应用运行期的会话热缓存。缓存只接收已经成功取得权威快照的会话状态，不把首次加载中的空状态写入缓存。
- `ConnectedSessionWorkspace` 创建会话控制器时接管对应热缓存；控制器立即展示缓存消息、运行信息和交互现场，同时重新建立事件连接并读取权威快照。
- 有缓存时，连接和读取阶段只在顶部显示“正在刷新会话”，不再展示正文骨架；没有缓存时仍保留首次加载状态。
- 后台刷新失败且已有快照时，保留正文并显示紧凑错误提示和重连入口；没有任何快照时仍展示完整连接失败状态。
- 关键会话包括正在处理、等待用户、等待审批、正在停止、排队、暂停和恢复中的会话；关键会话全部保留，其他会话只保留最近十个。
- 全局实时事件读取到后台会话快照时也会更新热缓存，使后台活动会话在切入前即可获得最新可展示状态。
- 按用户追加授权解决了当前分支原有的三处代码冲突标记：删除输入框内已经无引用的旧队列变量，并统一本地服务队列 DTO 与映射的完整字段。该附带处理不改变本任务的缓存口径。
- 阶段：代码、静态门禁、构建和测试身份打包已完成；真实 GUI 切换验收未执行。
- 未执行 git commit、push、merge、revert 或其他历史与远端操作。
