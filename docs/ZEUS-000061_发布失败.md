# ZEUS-000061 发布失败

## 当前阶段

冲突残留清理、发布前门禁保护、静态检查、构建和测试身份打包验证均已完成。

## 现场现象

- 当前工作区显示干净，Git 索引中也没有未解决冲突。
- 4 个源码文件和 `CONTEXT.md` 的正文仍存在 Git 冲突标记。
- `CONTEXT.md` 还完整重复了一次领域词汇表。
- 新任务 worktree 初始没有 `node_modules`，首次 `pnpm typecheck` 停在 `tsc: command not found`，尚未进入源码解析。

## 根因

冲突文件曾在保留标记的情况下被加入暂存区并完成合并提交。Git 只根据索引是否仍有多阶段条目判断“冲突是否解决”，不会理解文件正文中的标记。因此后续工作区可以保持干净，而无效正文继续随提交传播。

最早污染点：

- 会话协调器、会话协议和输入框：合并提交 `bcc0a02546623f76d00c442785d784540fc3f97f`。
- 领域词汇表：合并提交 `fb5b023f7c3a147dd074caeb6dc64ca1afaf9cf5`。
- 当前任务起点提交 `15b2cfefc55a1ce12a1c65b8d2cc2137a2cdc716` 已经包含上述内容。

## 处理口径

- 会话队列按 `ZEUS-000041` 已完成验收的语义处理：只投影尚未取得 Provider 轮次的排队或暂停消息，并保留真实派发方式和预期轮次。
- 输入框删除已经失去展示职责的旧队列变量，队列消息继续由会话气泡组件负责。
- 领域词汇表同时保留“上下文整理”与“活动计划进度”、“自定义答案入口”与答案布局术语，不丢弃任一已确认概念。
- 领域词汇表去除整份重复内容，并补回“运行状态入口”等只存在于另一份副本的有效术语。
- `pnpm verify:publish` 在格式、lint、类型检查和构建之前扫描工作区、暂存区及本次未跟踪文件中的冲突残留。

## 方案优缺点

优点：

- 修复当前无法解析的源码，同时保留各历史任务已经验收的业务语义。
- 冲突残留会在发布门禁最前面以文件和行号失败，不再依赖编译器间接暴露。
- 扫描同时覆盖已提交正文和本次本机变化，能够处理“Git 状态干净”的漏检场景。

代价：

- 门禁会把行首完整冲突标记视为错误；文档若要演示标记，需要改成行内写法。
- 本次只阻止冲突文本进入发布，不改变历史合并方式；后续仍需在合并操作中正确审查每个冲突块。

## 0.1.20 发布说明误报修复

### 现场

端到端发布已成功调用 Codex 生成结构化 Release notes，返回 `confidence=high`、`uncertainties=[]`。草稿中的真实产品说明写明：恢复后的未发送内容会回到草稿，等待用户确认发送。旧校验使用“`待` 加最多六个字符再加 `确认` 或 `验证`”的宽泛规则，把正常语句中的“待用户确认”误判成未解决占位，流程因此在版本写入前退出。

本次失败前，发布编排已经为 `TaskGitMergeModal.tsx` 的格式变化创建本地提交 `5af3fb2d8af32b7c892acc9a90c71edef1b7e583`；本地 `main` 比 `origin/main` 领先一个提交。版本号、发布提交、push、标签、GitHub Release 和 Homebrew Tap 均未写入，恢复状态仍为 `initialized`。

### 修复口径

- 明确拦截独立出现的“待确认”“待验证”“待发布门禁确认”“尚未确认”“尚未验证”“TODO”和“TBD”。
- 占位词前后若紧邻中文、字母或数字，则按自然语句处理，不再截取其中一段误报。
- “等待用户确认发送”“进入等待确认状态”等真实产品行为允许进入发布说明。
- 结构化 `confidence` 与 `uncertainties` 校验保持不变，不能用自然语言绕过真实不确定性检查。

优点是正常产品语义不会阻断自动发布，明确占位符仍会在版本写入前失败。代价是刻意把占位词嵌入连续长句可能绕过文字扫描；该边界继续由结构化置信度、空不确定项和发布说明提示词共同约束。

### 验证边界

- 使用本次失败保存的真实 `release-notes-response.json` 验证正常语句不再命中。
- 使用独立占位词样例验证明确占位仍被识别。
- 执行 `node --check scripts/generate-release-notes-draft.mjs` 与 `pnpm verify:publish`。
- 修复验证阶段不重新执行 `pnpm release`，不写版本号、标签、GitHub Release 或 Homebrew 公开资产。

### 同步发现并修复的源码污染

首次重跑完整门禁时，冲突残留检查已经通过，但类型检查继续暴露另一类污染：部分并行任务的整份文件被前后拼接在同一个文件中。因为这类内容没有 Git 冲突标记，旧门禁和新增的冲突标记扫描都无法识别。

本次按各任务已经确认的领域口径合并并重建以下能力：

- 会话输入框同时保留活动轮次排队和下一轮模型、权限、协作模式配置。
- 会话记录同时保留排队消息投影和最新推理摘要展示。
- 会话工作区同时保留断线未发送内容恢复、会话热缓存和下一轮配置持久化。
- Git 合入弹窗同时保留新版冲突编辑器和冲突全部处理后的最终确认页。
- 任务列表同时保留运行状态会话入口和中英文分支状态文案。
- 领域词汇表只保留一份完整定义，并合并各副本中独有的有效术语。

同时补齐了任务优先级无障碍文案类型、轮次耗时的等待请求输入，以及独立推送工作区下的来源分支偏好保存。`react-markdown` 和 `remark-gfm` 已存在于清单与锁文件中，本机依赖目录通过 `pnpm install --frozen-lockfile` 恢复，未改动依赖版本。
