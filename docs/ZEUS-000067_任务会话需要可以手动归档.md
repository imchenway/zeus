# ZEUS-000067 任务会话需要可以手动归档

## 当前阶段

已完成需求确认、实现、工程门禁、测试身份打包和真实桌面交互验收。

## 任务目标

- 任务会话结束使用后，用户可以手动归档，让普通会话列表只保留仍需关注的会话。
- 归档保留全部消息、任务关联、工作目录和执行历史，不等同于删除。
- 已归档会话可在设置中查看并恢复到原项目、原任务位置。

## 用户确认

- 产品语义和交互动线参考 Codex App。
- Zeus 会话记录与底层 Codex 线程同步归档和恢复，不采用仅隐藏 Zeus 列表的降级方案。
- 正在响应、排队、等待批准或等待用户输入的会话不可归档。
- 归档不改变任务管理状态，不清理任务工作区，也不执行任何 Git 操作。

## Codex 基准事实

- Codex 把归档用于收纳已经完成的会话；普通会话列表默认不展示已归档会话。
- 归档保留会话正文，恢复入口位于设置的已归档会话区域。
- Codex App Server 通过 `thread/archive` 和 `thread/unarchive` 改变原生线程状态，并广播对应生命周期事件。
- Codex 在任务运行中不允许归档当前会话。

## Zeus 源码事实

- `conversations.archived`、会话仓储的 `archive/restore` 以及本机接口已经存在，但现有归档接口只改变 Zeus 本地记录。
- 现有归档和恢复界面只服务代码图谱问答历史，任务会话侧栏没有手动归档入口，设置中也没有已归档会话列表。
- Codex 管理器已有 `thread/unarchive`，但尚未暴露 `thread/archive`。
- 任务会话选择接口默认只读取未归档记录，因此本地记录归档后会自然从普通会话列表消失。

## 实现设计

1. 为 Codex 管理器和运行代际管理器补齐原生线程归档能力。
2. 新增任务会话归档编排：先确认会话没有活动轮次、排队消息或待处理请求，再归档 Codex 线程；成功后归档 Zeus 记录并写入审计。
3. 恢复时先恢复 Codex 线程和权威快照，再恢复 Zeus 记录；任一步失败都保持可解释、可重试的状态。
4. 在任务会话行提供低频归档操作；当前选中会话归档成功后关闭该会话现场并刷新普通列表。
5. 在设置中新增已归档会话区域，展示任务、项目和归档时间上下文，并提供恢复操作。
6. 通过实时事件和请求后的定向刷新保持会话树、任务详情和设置列表一致。

## 实现结果

- Codex App Server 管理器与运行代际管理器已补齐 `thread/archive`，恢复继续使用 `thread/unarchive`；归档成功后会清理旧代际的线程路由，恢复时由当前代际重新接管。
- 原生会话协调器在归档前和 Provider 对账后各检查一次活动轮次、排队消息、待处理批准和待处理用户输入，避免对账期间状态变化导致误归档。
- Provider 归档成功后才写入 Zeus 本地归档状态；失败不会退化成仅隐藏列表。恢复按 Provider 恢复、读取权威快照、本地恢复的顺序执行。
- 任务会话行新增“更多会话操作 → 归档会话”；运行中、排队中或等待交互时动作不可用，服务端仍保留最终拒绝保护。
- 旧版只读会话无法证明底层线程同步，因此明确禁用归档并说明原因，不退化为只改变 Zeus 本地记录。
- “设置 → 缓存与数据”新增已归档任务会话列表，覆盖普通项目和已归档项目中的会话，并支持恢复。
- 归档和恢复会广播独立生命周期事件，普通会话树、当前选中会话和设置列表会同步刷新。

## 取舍

- 优点：用户心智与 Codex 一致；Zeus 和底层线程不会一边显示活跃、一边已经归档；消息和任务现场可恢复。
- 缺点：归档依赖 Codex App Server 可用，底层失败时不能退化成只隐藏 Zeus 记录。
- 不采用运行中自动中断后归档：会把收纳操作扩大为执行控制，可能丢失正在产生的结果。
- 不采用任务状态联动：任务管理阶段与单条会话生命周期不同，一个任务可以关联多个会话。

## 验收口径

- 非活动任务会话可以从会话列表手动归档，成功后立即从普通列表消失。
- 正在响应、排队、等待批准或等待用户输入的会话不提供可执行的归档动作，并说明原因。
- 已归档会话的消息、任务关联和工作目录信息保持不变。
- 设置中的已归档会话可以恢复；恢复后回到原项目、原任务的普通会话列表。
- Zeus 本地记录和 Codex 原生线程归档状态一致，失败时不显示虚假成功。
- 归档和恢复不改变任务管理状态，不删除工作区，不执行 Git 写操作。
- 静态检查、构建、测试身份打包和真实界面验收分别记录，不互相冒充。

### 真实桌面交互

目标路径：任务会话列表 → 更多会话操作 → 归档会话 → 设置中的已归档会话 → 恢复 → 返回原任务会话列表。

- Browser 插件可用，但其安全策略拒绝加载打包应用的本地 `file://` 页面，没有绕过限制；实际验收改用 macOS 界面控制直接操作最终 `Zeus Test.app`。
- 在约 `1226 × 768` 的真实窗口中，“测试”任务会话显示低频更多操作菜单，菜单中的“归档会话”可正常聚焦和点击。
- 归档成功后该会话立即从普通列表消失；设置的“缓存与数据”页面出现“已归档会话”，同时展示任务标题、项目、任务编号和时间。
- 点击“恢复”时按钮进入“正在恢复…”状态；完成后设置列表显示空态，返回应用后会话重新出现在原项目、原任务位置。
- 核心链路重新打包后再次完整执行归档和恢复，结果一致；最后的旧会话边界收紧重新通过完整工程门禁与测试身份打包，干净重启后又在最新包完整通过归档、设置页展示、恢复和回到原任务。验收结束时测试会话已恢复，没有遗留归档状态。

### 数据与 Provider 状态证据

- 归档后同一会话记录为 `provider_state=archived`、`archived=1`，并产生 `conversation.archived` 审计记录。协调器只有在 `thread/archive` 成功返回后才写入该状态。
- 恢复后同一记录回到 `provider_state=ready`、`archived=0`，并产生 `conversation.restored` 审计记录；这表示 `thread/unarchive`、线程恢复和权威快照读取均已成功。
- 最终 `PRAGMA quick_check` 返回 `ok`。

### 验收边界

- 隔离 `ZEUS_USER_DATA_DIR` 没有被首次打包进程采用，因此没有把错误目录当作隔离验收成功；后续只在独立测试身份已有的 QA 数据中选取一个已就绪测试会话做归档后立即恢复。最终业务状态已还原，但测试数据库保留验收产生的归档/恢复审计和更新时间变化。
- 最新包第一次冷启动时，界面先报“Zeus 无法启动”，执行宿主随后才就绪；本轮遗留宿主已通过 `SIGTERM` 正常关闭。再次干净启动时界面控制连接也先超时，但应用约二十秒后完整加载并通过目标交互。该冷启动时序不是本次归档功能造成的稳定故障，但仍是独立的启动可靠性风险，未隐瞒为全程无告警。
- 没有启动、关闭或修改 `/Applications/Zeus.app`，没有生成任务目录中的生产身份应用，也没有执行 commit、push、merge 或 revert。
- 没有为了制造忙碌态而向 Provider 新增消息；运行中、排队中和等待交互时的拒绝由双重服务端状态检查、前端禁用映射、静态检查和构建覆盖，不冒充真实忙碌态交互验收。
- macOS 界面控制不提供 Renderer 控制台读取；真实画面未出现错误边界，目标交互和数据库状态均正常，但这不等同于独立的控制台零告警证明。
