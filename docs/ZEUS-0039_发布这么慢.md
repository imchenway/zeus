# ZEUS-0039 发布这么慢

## 任务信息

- 类型：需求
- 标题：发布这么慢
- 用户问题：现有发布步骤是否都必须执行；一键发布长期耗时 20 分钟以上。
- 当前阶段：已完成快速发布主链路开发与静态验证，尚未提交、推送或执行真实公开发布。

## 用户确认

- 发布说明改用 Zeus 已配置的 DeepSeek Flash 模型，真实模型 ID 为 `deepseek-v4-flash`。
- 不把 `v4-flash` 当作 Codex CLI 模型名传入；发布说明生成需要迁移到 Zeus 模型连接。
- 模型 API Key 继续由 Zeus SecretStore 管理，不进入发布脚本参数、命令日志或产物。

## 结论

现有发布链路的安全目标基本合理，但不是每个动作都必须在每次发布中串行、重复执行。

必须保留的是四类结果：候选内容可追溯、代码检查通过、正式制品由可信环境构建、公开资产与清单一致。当前实现为了取得最强证据，把同一提交的代码检查执行三次，并在远端已经校验和发布 DMG 后，再把完整 DMG 下载回本机做一次字节级复核。后者受网络速度影响最大，是 20 分钟以上耗时的首要原因。

实现已按快速迭代口径收敛：公开发布完成后只下载体积很小的 manifest，通过 GitHub 资产的服务端 SHA-256 与字节数、manifest、Homebrew Cask 三方对账，不再默认回下载完整 DMG；完整 DMG 回下载和 `hdiutil verify` 改为显式深度校验。本地完整门禁和 main CI 串行等待也已移出默认主链路，目标耗时约 5～8 分钟。

## 改造前真实链路

`pnpm release` 当前按以下顺序执行：

1. 自动整理候选文件；有变化时形成独立提交。
2. 调用 Codex 生成 Release notes。
3. 写入版本与发布正文，创建发布提交。
4. 本机执行完整 `release:gate`，其中包含 `verify:publish`、验收矩阵、AI CLI 探针、正式打包和产物校验。
5. 推送 `main`，等待普通 CI；普通 CI 再执行一次 `verify:publish`。
6. 创建标签并触发 Release Workflow；Workflow 再执行一次完整 `verify:release`，重新检查并重新打包。
7. Workflow 创建 GitHub Release、上传 DMG 与 manifest、同步 Homebrew Cask。
8. 本机再次下载公开 DMG 与 manifest，对 DMG 执行 `hdiutil verify`，并复核 SHA-256、字节数、Release notes 和 Cask。

因此，同一候选提交的 lint、typecheck 和 build 会在本机门禁、普通 CI、Release Workflow 中各执行一次；正式 DMG 会在本机和 Release Workflow 中各构建一次；远端 DMG 又会完整下载回本机一次。

## 五个步骤的真实作用

### 公开 DMG 回下载与重复复核

目的不是再次构建，而是证明用户从 GitHub Release 下载到的公开文件，与 Workflow 上传前验证的文件、manifest 和 Homebrew Cask 指向的是同一份字节内容。它可以发现上传不完整、同版本资产被替换、旧资产残留、manifest 写错摘要或 Cask 指错版本等问题。

优点：证据最强，覆盖了公开下载链路本身。

缺点：每次都要重新传输约 157 MB，速度完全受网络影响；GitHub 已提供资产服务端 SHA-256 和字节数，默认全量回下载的收益与时间成本不匹配。

结论：对账必须保留，但默认使用 GitHub 服务端摘要、字节数、manifest 和 Cask 对账；完整下载挂载复核改为显式深度校验。

### Release Workflow

这是正式发布工厂，不只是一次重复检查。它从不可变标签在干净的 GitHub macOS 环境中检出源码，校验发布输入和凭据，生成生产身份 `Zeus.app` 与 DMG，上传 GitHub Release，并同步 Homebrew Cask。

优点：正式资产不依赖开发者本机的未提交内容、历史缓存和本机环境；发布过程可审计、可复现。

缺点：启动远端 macOS 环境、安装依赖和正式打包有固定成本；当前还重复执行了普通 CI 已完成的代码检查。

结论：必须保留。可以拆掉其中与同提交普通 CI 重复的 lint、typecheck 和 build，但正式打包、产物校验、Release 上传和 Cask 同步不能删。

### AI 生成发布说明

它把 Git 提交、变更文件和任务文档整理成用户能理解的更新说明，避免直接把开发提交标题当成 Release notes。

用户已经确认改用 Zeus DeepSeek 连接中的 `deepseek-v4-flash`。当前脚本直接执行 Codex CLI，并显式忽略用户模型配置，因此不能只改一个模型字符串；正确实现需要让发布编排通过 Zeus 本机服务调用已配置连接，同时保持密钥不离开 SecretStore。

优点：Flash 模型适合结构化整理，预期能明显降低生成等待；模型连接和凭据继续由 Zeus 统一管理。

缺点：发布说明生成会依赖正式 Zeus 执行宿主及对应 DeepSeek 连接可用；连接未配置、模型目录不存在该 ID 或请求失败时必须阻断并给出真实原因。

结论：需求已确认，实施时使用精确模型 ID `deepseek-v4-flash`，不再依赖 Codex 登录作为默认路径。

### 本地门禁

门禁就是“在发生远端写入前先拦住必然失败的候选”。当前它检查版本和正文是否一致，并执行格式、lint、typecheck、build、验收矩阵、AI CLI 探针、正式打包、签名状态、DMG 和 manifest 校验。

优点：问题在推送 `main`、创建标签和占用远端发布资源前暴露；失败恢复成本低。

缺点：它在本机完整打包一份最终不会直接公开的正式 DMG，并与后续远端检查重复。

结论：保留轻量本地门禁，优先检查候选结构、格式和低成本问题；完整正式打包改为显式深度门禁，默认交给 Release Workflow 执行一次。

### main CI

它在独立的 GitHub 环境中检查已经推送到 `main` 的精确提交，证明结果不是由本机缓存、脏工作区或本机依赖状态制造的。发布脚本只有在该提交 CI 成功后才创建标签，避免给失败提交留下稳定版标签。

优点：保护 `main`，给分支合入和发布提供同一份远端权威代码检查结果。

缺点：当前 Release Workflow 随后又把同一套代码检查执行一次，产生重复等待。

结论：必须保留一个远端权威代码检查。可以继续独立保留 main CI，并让 Release Workflow 复用其结果；也可以将两者合并为一个远端发布流水线，但不能在没有替代门禁时直接删除。

## 推荐改造

### 第一阶段：取消默认完整 DMG 回下载

发布完成后：

1. 读取 GitHub Release 资产元数据中的 `digest` 与 `size`。
2. 只下载 `zeus-release-manifest.json`。
3. 校验 GitHub 资产的服务端 SHA-256、字节数与 manifest 完全一致。
4. 校验 Homebrew Cask 的版本、SHA-256 和架构与 manifest 一致。
5. 保留 `DEEP_VERIFY_PUBLIC_DMG=true` 开关；开启时才下载完整 DMG 并执行 `hdiutil verify`。

优点：不削弱发布前的正式打包和 DMG 完整性校验；默认节省约 6～20 分钟，并消除网络速度对完成时间的主要影响。

缺点：默认链路不再证明“用户从公开下载地址取回的每一个字节都可在本机重新挂载校验”。这一证据仍可由显式深度校验、定时任务或重要版本抽检补充。

### 第二阶段：去掉同一提交的重复代码检查

1. 本机发布门禁默认改为快速前置检查，发现低成本问题后再推送。
2. 普通 CI 对候选提交执行完整 `verify:publish`，作为代码检查权威结果。
3. Release Workflow 在确认同一提交的 CI 成功后，只执行验收矩阵、AI CLI 探针、正式打包和产物校验，不再重复 lint、typecheck 和 build。

优点：同一提交的代码检查从三次降为一次远端权威检查；职责更清楚。

缺点：本机不再提前执行所有检查时，少数问题会到 CI 才反馈；需要保证 Release Workflow 精确绑定已通过 CI 的同一提交，不能只按分支名判断。

### 后续增强：收敛为单个远端发布流水线

由一个 Release Workflow 接收固定候选提交，内部先执行代码检查，再执行正式打包；全部通过后才创建不可变标签、GitHub Release 和 Homebrew Cask。本机命令只负责生成正文、创建候选提交、触发 Workflow 和展示进度。

优点：CI 与 Release 不再串行重复启动环境，目标耗时可进一步下降到约 6～8 分钟；发布事实集中在一个远端运行中。

缺点：需要重构标签创建时机、失败恢复和权限边界，改动风险高于前两项，不适合和快速优化一起完成。

## 产品建议

默认“发布成功”的口径应为：同一候选提交通过远端代码检查，Release Workflow 完成正式打包和本地制品校验，GitHub Release 资产的服务端摘要与 manifest、Homebrew Cask 一致。

“完整下载复验”应作为更高强度的可选动作展示，而不是所有版本都阻塞主流程。界面可以在发布成功后显示“深度校验未执行”，并提供单独入口；这比让用户面对 20 分钟无差别日志更符合真实风险和时间成本。

## 快速迭代阶段的风险取舍

用户已经明确：发布后出现普通功能缺陷可以接受，只要求默认链路阻止会导致“无法构建、无法形成安装包、无法发布、无法升级”的致命阻塞问题。因此，发布门禁不再以尽可能完整地证明质量为目标，而以最短时间形成可安装、可回退的公开版本为目标。

### 五个步骤移除后的风险

| 步骤 | 完全移除后的风险 | 是否可能造成发布阻塞 | 快速迭代建议 |
| --- | --- | --- | --- |
| 公开 DMG 回下载与重复复核 | 无法证明 GitHub 下载链路返回的完整文件与上传前文件逐字节一致；极端情况下可能漏掉 CDN、上传或同版本资产替换异常 | 可能，但 GitHub 服务端摘要、manifest 和 Cask 对账仍能覆盖主要错误 | 从默认链路移除，重要版本或异常时手工深度复核 |
| Release Workflow | 失去干净远端 macOS 环境中的正式生产构建、GitHub Release 上传和 Homebrew Cask 同步；若没有替代发布器，版本将根本无法公开 | 是，属于致命阻塞 | 不能直接删除，只能由另一条正式发布路径替代；内部收敛为只构建一次、只发布一次 |
| AI 生成发布说明 | Release notes 可能简陋、遗漏用户影响或已知限制；不会影响 App 构建与安装 | 否 | 改用 `deepseek-v4-flash`；失败时回退到确定性模板，不阻断发布 |
| 本地门禁 | 明显的格式、类型、构建或打包问题会到远端才发现，浪费一次远端运行；按现有标签时序还可能增加恢复成本 | 间接可能，远端仍可拦截 | 移除完整门禁，只保留十秒级前置检查；本地正式打包改为手工深度模式 |
| main CI | 失去发布标签创建前的独立远端代码检查；按当前流程可能先给坏提交创建标签，再由 Release Workflow 失败 | 是，但 Release Workflow 已有重复能力 | 不再串行等待独立 CI；把最小代码检查并入 Release Workflow，并在检查通过后才创建标签 |

### 哪些风险可以接受

- 可以接受：普通界面问题、非关键交互缺陷、Release notes 不够精致、公开 DMG 未逐次回下载验证、远端运行失败后重新发布。
- 不应接受：源码无法编译、正式包无法生成、DMG 无法校验、版本或标签错配、GitHub Release 缺资产、manifest 指错文件、Homebrew 安装入口指向错误摘要、同一版本静默覆盖不同二进制。

### 推荐的快速发布主链路

1. 本机执行十秒级前置检查：工作区与分支关系、版本递增、冲突标记、发布凭据状态和目标标签不存在。
2. `deepseek-v4-flash` 与只读候选检查并行生成发布说明；失败时使用确定性模板，不阻断。
3. 推送固定候选提交并触发一个 Release Workflow，不再串行等待独立 main CI。
4. Workflow 只执行阻塞级检查：安装依赖、typecheck、生产 build、正式 DMG 打包、包内容健康、`hdiutil verify`、manifest 生成与摘要一致性。
5. 检查通过后再由 Workflow 创建不可变标签、GitHub Release 和 Homebrew Cask。
6. 本机只读取 GitHub 资产服务端摘要、manifest 和 Cask 做轻量对账，不下载完整 DMG。

目标耗时为约 5～8 分钟。lint、完整验收矩阵、AI CLI 全量探针、本机正式打包和公开 DMG 回下载进入手工深度发布或定时巡检，不阻塞每次快速版本。

优点：只保留会导致“版本根本交付不了”的检查，普通缺陷可以通过后续小版本快速修复；正式二进制仍由单一干净远端环境构建，不牺牲版本和资产不可变性。

缺点：更多问题会在用户安装后暴露；远端构建失败时反馈晚于本机完整门禁；需要调整标签创建时机和 Release Workflow 职责，不能只删除现有步骤而不改编排。

## 串并行依赖结论

五个步骤不需要全部串行。当前串行主要来自发布脚本按阶段逐个 `await`，以及 `release:publish` 强制要求本地门禁和 main CI 已通过，并不是 GitHub 或打包工具要求必须这样执行。

真正不能打乱的只有三段因果关系：

1. 必须先固定版本号、Release notes 和候选提交，才能证明后续检查针对的是最终发布源码。
2. 必须先完成阻塞级代码检查、正式打包和产物校验，才能创建不可变标签并公开 Release。
3. 必须先有公开资产，才能检查 GitHub 资产元数据、manifest 和 Homebrew Cask 是否一致。

除这三段外，其余工作都可以并行、合并或移出阻塞主链路。

### 五个步骤的并行空间

| 步骤 | 可以和什么并行 | 不能提前到哪里 | 建议 |
| --- | --- | --- | --- |
| 公开 DMG 回下载与重复复核 | Release notes 核对、manifest 下载、Cask 获取可并行；完整 DMG 深度下载可在发布成功后异步执行 | 公开资产创建之前无法执行 | 默认不阻塞；深度校验作为后台或手工任务 |
| Release Workflow | 候选提交推送后可与 main CI 同时启动 | 正式包公开必须等待阻塞级检查和打包成功 | 不再等待 main CI 后才启动；用 Workflow 内的汇合作业控制最终公开 |
| AI 生成发布说明 | 可与工作区、分支、冲突、凭据、目标版本和标签占用等只读前置检查并行 | 发布提交必须等待 Release notes 产出或确定性回退完成 | 使用 `deepseek-v4-flash`，与十秒级前置检查同时启动 |
| 本地门禁 | 拆出的只读静态检查可与 AI 说明生成并行 | 生产身份打包必须绑定最终版本和候选提交 | 默认只保留快速前置检查；完整本地门禁移到手工深度模式 |
| main CI | 可与 Release Workflow 的正式打包并行 | 如果仍把它作为发布阻断条件，最终公开必须等它完成 | 快速发布不再单独串行等待；将唯一必要的 `typecheck` 放入 Release Workflow |

### 推荐并行拓扑

```text
本机阶段
├─ 快速前置检查 ─────────────┐
└─ DeepSeek 生成发布说明 ────┤
                              └─ 固定版本与候选提交 → 推送固定 SHA

远端阶段
├─ 阻塞级 typecheck ─────────┐
├─ 正式 DMG 打包与产物校验 ──┼─ 全部通过 → 创建标签 → GitHub Release → Homebrew Cask
└─ 发布凭据与目标占用检查 ───┘

发布后阶段
├─ GitHub 资产摘要与 manifest 对账
├─ Release notes 与 Cask 对账
└─ 完整 DMG 下载复核（默认异步，不计入发布完成时间）
```

这里的 `typecheck` 与正式打包应使用两个独立 GitHub Actions 作业并行运行，而不是在同一台 macOS Runner 上同时启动多个高负载进程。独立作业按两者中较慢的一个计时；同机并行会争抢 CPU、磁盘和 pnpm 缓存，时间更不稳定。

### 为什么不保留“main CI 通过后再启动 Release Workflow”

当前 main CI 运行 `verify:publish`，Release Workflow 的 `verify:release` 内部又运行一次 `verify:publish`。先等 main CI，再运行 Release Workflow，是同一提交的重复检查串行叠加。

快速发布模式应让 Release Workflow 直接接收精确候选 SHA，并在内部并行执行：

- 作业 A：只保留会导致源码无法交付的 `typecheck`。
- 作业 B：正式构建、DMG 打包、包内容健康检查、`hdiutil verify`、manifest 与 SHA-256 对账。
- 作业 C：检查发布凭据、版本、目标标签和同名 Release 不存在。
- 作业 D：仅在 A、B、C 都成功后创建标签、上传资产并更新 Homebrew Cask。

普通 main CI 仍可由 push 自动触发并提供观察信号，但不再阻塞这一轮快速发布。PR 合入前的 CI 也不受影响。

优点：main CI 的约两分钟可被正式打包完全覆盖；AI 说明生成也不再独占前置时间；关键路径由“所有步骤相加”变为“每组并行任务取最慢者”。结合本次历史耗时，默认发布仍以约 5～8 分钟为合理目标。

缺点：并行作业会增加 GitHub Actions Runner 用量；如果 `typecheck` 很快失败，已经启动的打包作业可能浪费几分钟算力。快速迭代阶段更看重墙钟时间，这个成本可以接受；若后续更看重运行费用，可恢复为先检查再打包。
