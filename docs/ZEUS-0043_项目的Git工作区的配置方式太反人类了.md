# ZEUS-0043 项目的 Git 工作区配置优化

## 任务信息

- 类型：优化
- 现状：新增项目后，用户仍需进入项目配置，逐个勾选扫描到的 Git 仓库；共享可写目录可以自定义 `docs` 等真实目录，这部分方向正确。
- 预期：已完成需求澄清，并按本文“确认后的完整预期”实施。

## 澄清阶段事实

### 当前产品行为

1. 新增项目接口只创建项目和默认配置，不会登记扫描到的 Git 仓库。
2. 项目配置页并行读取已登记仓库和扫描候选，但复选框只回显已登记仓库，不会默认选中候选。
3. 未登记任何仓库但扫描到候选时，任务推送会被阻断，要求用户返回项目设置确认仓库。
4. 共享可写目录独立登记，每行一个项目容器内的真实目录，不参与 Git 隔离。

### 真实 PIM 目录证据

`/Users/david/cckg/tcapp/Back-End/pim` 不是简单的平铺多仓目录，而是三层 Git 仓库嵌套结构：

- 根仓库 `pim` 把 `tc-app-goods`、`web-base` 记录为 Gitlink。
- `tc-app-goods` 又把 API、Common、Doc、Feign、Service 等目录记录为 Gitlink。
- API、Feign、Service 下仍有叶子仓库；`web-base` 也记录多个 Gitlink。
- 根仓库没有远端，其余当前扫描到的业务仓库通常有 `origin`。

当前保存接口禁止登记路径互相包含的仓库。因此，直接增加“全选”会同时选中父仓和子仓，并触发路径重叠错误，不能真正解决问题。

## 当前领域边界

- **扫描候选仓库**：Zeus 在项目容器内发现的真实 Git 根，仅是事实候选。
- **项目纳管仓库**：Zeus 为任务分支、独立工作区和逐仓交付负责的仓库集合。
- **任务涉及仓库**：某一次任务实际需要修改的纳管仓库；它不应等同于项目的永久配置。
- **共享可写目录**：允许任务直接写回真实路径的非 Git 目录，例如项目级 `docs`。

## 用户修订后的目标模型

### 项目创建

- 项目创建后天然拥有唯一真实工作目录，即项目容器 `localPath`。
- 项目创建和项目配置不维护 Git 仓库清单；截图中的“发现的 Git 仓库”复选列表及其保存、重新发现操作整体删除。
- 优点：项目概念回到真实目录，非 Git 项目也能完整工作。
- 代价：仓库发现必须移动到任务推送的 worktree 模式中按需执行。

### 直接目录模式

- 用户推送任务时可以选择不用 worktree，会话直接在项目真实目录中工作。
- 该模式不要求 Git；存在 Git 时自然使用当前目录和当前分支，不创建新分支、不创建隔离目录。
- 优点：路径直接、启动快、兼容非 Git 项目和用户现有现场。
- 代价：AI 修改直接落在真实目录中，没有 worktree 隔离；界面必须如实说明影响。

### Worktree 模式

- 用户选择 worktree 模式后，Zeus 在推送时自动发现项目目录下全部真实 Git 仓库，不再读取项目级勾选结果。
- 没有发现 Git 仓库时停止创建 worktree，并提示用户先自行初始化仓库；Zeus 不代替用户执行初始化。
- 每个仓库的来源分支默认是该仓库当前检出的分支，用户仍可在推送时调整来源分支和新任务分支。
- 每个扫描到的 Git 根作为独立仓库创建分支、审查和交付，不做父子仓自动提交或推送联动。
- 优点：多分支隔离只在用户需要时启用，且不再重复配置仓库归属。
- 代价：现有项目级仓库持久化门禁、父子路径禁止重叠和任务环境创建协议都需要重构。

### 共享可写目录

- 项目设置继续保留共享可写目录，用户可以配置项目根内的 `docs` 等持久记忆目录。
- 直接目录模式天然使用真实目录；worktree 模式在隔离任务环境中引用这些真实目录，不复制内容，也不把它们纳入 Git 隔离和回收。
- 优点：任务分支可以隔离代码，同时继续读写跨任务持久化文档。
- 代价：共享目录中的并发写入不会随 worktree 回滚，需要继续明确其非隔离属性。

### 首次默认方式

- 推送弹窗发现至少一个 Git 仓库时默认选择 worktree 模式。
- 完全没有发现 Git 仓库时默认选择直接目录模式；用户若主动切到 worktree，则提示先初始化仓库。
- 优点：Git 项目默认获得分支隔离，非 Git 项目无需理解不可用能力。
- 代价：默认值依赖一次真实仓库扫描，弹窗需要在扫描完成后稳定呈现，不能先显示错误选项再跳变。

### 工作方式记忆

- 用户手动切换工作方式后，Zeus 按项目记住上次选择，并在后续任务推送中恢复。
- 新项目没有历史选择时，才使用“有 Git 默认 worktree、无 Git 默认直接目录”的首次规则。
- 优点：默认安全策略与项目实际使用习惯兼容。
- 代价：直接目录模式可能长期生效，弹窗必须始终清楚展示当前方式及其影响。

### 直接目录并发

- 同一项目已有可写会话时，直接目录模式允许启动另一条并发可写会话，但必须先明确警告用户。
- 用户确认后继续，不强制改用 worktree，也不把并发现场描述成已隔离。
- 优点：保留用户对真实目录的完整控制，不人为限制并行工作。
- 代价：会话可能互相覆盖文件，变更归因、Review、Undo 和 Reapply 的可靠性下降，相关界面必须如实降级。

## 确认后的完整预期

1. 删除项目配置中的 Git 仓库发现、逐项勾选、重新发现和“保存任务工作区”组件；项目创建后只以真实 `localPath` 作为天然工作目录。
2. 项目设置单独保留共享可写目录配置；worktree 模式通过目录引用继续读写原项目中的 `docs` 等持久目录，不复制、不随 worktree 回收。
3. 任务推送提供“直接目录”和“worktree”两种正式工作方式；直接目录不要求 Git，直接使用项目真实路径和当前现场。
4. Worktree 模式在推送时自动扫描项目目录下全部 Git 仓库；没有仓库时提示用户自行初始化，Zeus 不自动初始化。
5. Worktree 模式默认从每个仓库当前检出的分支创建新任务分支，用户可以逐仓调整来源分支和新分支。
6. 扫描到的每个 Git 根独立创建、审查和交付，不做父子仓自动提交或推送联动。
7. 新项目首次推送时，有 Git 默认 worktree、无 Git 默认直接目录；用户切换后按项目记住上次选择。
8. 直接目录模式允许并发写入同一项目目录，但第二条可写会话启动前必须警告；确认后继续并如实降低变更归因与撤销保证。
9. 直接目录模式不创建任务 worktree，不出现 worktree 提交、回收或交付门禁，任务管理状态继续与代码交付解耦。

## 实施结果

### 项目配置

- 删除项目配置中的仓库候选、逐项勾选、重新发现和仓库清单保存协议。
- 项目配置接口只读写共享可写目录；共享目录继续限制在项目真实目录内，且共享目录之间不能互相包含。
- 项目配置界面把该能力独立命名为“共享可写目录”，明确说明它会被 Worktree 直接引用、不会复制或随任务目录回收。

### 任务推送

- 推送协议新增 `direct` 与 `create` 两种工作区选择；前端分别呈现“直接使用项目目录”与“Worktree”。
- 直接目录模式使用项目 `localPath`，不创建任务环境或任务仓库工作区；只读会话不触发并发警告，可写会话存在并发时必须明确确认。
- Worktree 模式在读取推送能力与正式接受推送时重新扫描项目目录，扫描结果直接形成本次全部仓库清单，不再依赖项目设置。
- 新项目按“发现 Git 则 Worktree，否则直接目录”选择首次默认值；成功推送后按项目记住用户选择。
- 每个仓库的来源分支默认当前本地分支；仓库处于 detached 状态时不会伪造当前分支，用户必须选择真实本地分支。
- Worktree 模式没有发现仓库时停止创建，并提示用户自行初始化或改用直接目录。

### 嵌套仓库与共享目录

- 父仓和子仓分别创建任务分支、Review、提交、推送和交付，不做自动联动。
- 父仓 Review、提交和本地改动迁移会排除其内部独立子仓，避免把子仓 Gitlink 或文件误计入父仓成果。
- Worktree 创建完毕后，共享目录位置替换为指向项目真实目录的符号链接；父仓 Review 与提交同时排除共享路径。
- 物理目录回收遵循“子仓先、父仓后”。若父仓先完成交付，Zeus 保留其目录并在子仓回收后自动补收；任务终态清理也按目录深度从里到外执行。
