# ZEUS-0078 没看懂，这是在排什么队？

## 任务信息

- 类型：缺陷
- 问题：待发消息以聊天气泡显示“排队中”，用户看不出在等待什么、何时发送，也容易误以为消息已经发出。
- 用户确认：确有等待条件时继续等待；等待条件解除后自动发送。实现前对照 Codex App 的真实交互，不再追问可以从产品和代码中直接确认的问题。

## 需求澄清与领域口径

### 已确认事实

- 队列不是一个需要用户手工启动的独立任务队列，而是当前会话中尚未交给模型的后续消息。
- 消息需要等待的原因包括：当前回复仍在执行、当前回复正在等待用户选择或审批、同项目或全局并发名额暂时占满，以及会话被中断或需要恢复。
- 除中断、恢复确认等明确暂停场景外，等待条件解除后由现有协调器按顺序自动发送。
- 用户仍可在等待期间编辑、删除、调整顺序；当前回复活跃时可以把某条后续消息“引导”给当前回复。

### Codex App 对照结论

- 本机 ChatGPT/Codex App `26.730.61309` 将后续消息放在输入区上方的紧凑列表，而不是放进对话记录伪装成已发送气泡。
- 普通列表项不重复显示含糊的“排队中”；产品用列表位置和上下文表达这是下一轮消息。
- “引导”表示把消息补充给当前执行，不中断当前回复；列表支持编辑、删除和调整顺序。
- 中断导致队列暂停时，列表级提示会明确说明暂停原因。

### 领域决定

“队列消息”统一定义为：用户在当前会话尚不满足发送条件时保存、等待下一轮执行的后续消息。界面必须说明当前等待原因和后续动作，不能再把“排队中”本身当成解释。

## 方案与取舍

### 采用方案

1. 将队列从对话记录底部移到输入区附近，以紧凑列表呈现。
2. 列表顶部只显示一次真实等待说明：当前回复结束后自动发送、完成上方选择或审批后自动发送、等待其他会话释放名额，或明确的中断与恢复原因。
3. 移除每条消息上的“排队中”标签，保留内容、附件、编辑、删除、排序和恢复操作。
4. 将“立即发送”改为“引导”，并说明它会补充给当前回复，不会新开一轮或中断当前回复。
5. 等待用户选择或审批时，先展示待处理交互，再展示后续消息列表，让“完成上方操作后自动发送”的指向成立。

### 优点

- 用户能直接理解“为什么等”和“接下来会发生什么”。
- 待发消息与已经进入对话记录的消息视觉分层，避免误判发送状态。
- 沿用现有真实队列和自动派发机制，不改变并发与恢复安全边界。

### 代价

- 输入区附近会增加一块紧凑状态区，多条长消息需要限制高度并允许内部滚动。
- 当前界面只能判断正在等待并发名额，无法进一步区分是项目名额还是全局名额；若未来需要精确到名额来源，服务端快照还需增加等待原因字段。

## 实现与验证记录

### 已实现

- `QueuedConversationMessages` 改为输入区附近的紧凑后续消息列表，不再复用对话气泡样式。
- 根据会话和队列真实状态生成列表级说明；用户选择或审批状态优先于可能短暂滞后的队列运行快照。
- 正常等待时保留“引导、编辑、删除、上移、下移”；等待选择或审批时隐藏不可用的“引导”，其他队列管理操作继续可用。
- `ConversationTranscript` 只保留已经进入执行轮次的消息；队列列表由 `SessionWorkspace` 放置在输入区或待处理交互下方。
- 样式限制列表高度并支持内部滚动，操作始终可见；窄窗口不再套用旧聊天气泡宽度。

### 真实界面验证

使用独立 `ZEUS_USER_DATA_DIR` 启动本任务生成的 `Zeus Test.app`，未触碰正式 `Zeus.app`。

1. 当前回复通过只读 `sleep 15` 命令保持执行时发送后续消息：列表出现在输入区上方，显示“当前回复结束后按顺序自动发送”，并显示“引导、编辑、删除、上移、下移”。
2. 当前回复结束后：后续消息自动进入下一执行轮次，列表消失，消息与回复进入对话记录。
3. 当前回复通过只读 `sleep 10` 后发起 A/B 选择，并提前加入后续消息：选择面板在上，后续消息列表在下，最终测试包显示“完成上方选择后按顺序自动发送”。
4. 选择 A 后：后续消息自动发送，模型回复“已收到”，列表消失。
5. 真实验收中曾发现队列快照短暂仍为活跃状态，导致选择面板出现后提示仍写“当前回复结束后”；现已改为优先采用用户可见的等待选择或审批状态，并通过保留现场重启新测试包复验。

### 未覆盖边界

- 未单独构造审批、连接中断、会话归档和并发名额占满的真实 GUI 场景；对应文案由现有权威状态映射，静态检查与构建已覆盖。
- 服务端当前没有区分“项目并发名额”和“全局并发名额”，因此空闲但仍有队列时统一说明“等待其他会话完成”。
