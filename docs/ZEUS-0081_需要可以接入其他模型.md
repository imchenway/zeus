# ZEUS-0081 需要可以接入其他模型

## 当前阶段

需求澄清中。当前只记录已确认边界和待决策项，尚未进入设计或功能实现。

## 原始需求

- 在系统设置中配置 API Key、接口域名和模型。
- 任务“推送到新会话”和会话输入框都可以选择已配置供应商的模型能力。
- 典型供应商包括阿里云百炼和 DeepSeek API。

## 已核对的现状

- Zeus 已区分 Agent、模型供应源和具体模型，Pi 已登记为默认隐藏的公共框架状态。
- 当前 Pi 没有真实进程启动、供应商认证或模型调用，普通用户目录不会显示 Pi。
- 现有 `external.apiKey` 只是通用密钥槽位，没有与模型供应源、模型目录或会话路由建立关系。
- Codex 的模型调用与工具循环由 Codex App Server 提供；普通模型 API 本身不等于完整编码 Agent。

## 已确认的产品决策

### 普通模型 API 通过 Pi Agent 使用

阿里云百炼、DeepSeek 等普通 API 不作为独立 Agent。Zeus 保存用户配置的模型供应源，Pi 负责模型调用、工具循环、上下文和原生会话，界面按“Pi Agent · 模型供应源 · 具体模型”表达真实身份。

优点：可以复用 Zeus 的项目、任务、工作区、产品会话、排队、权限、审计和代码交付能力，同时避免为每家模型供应商重写 Agent 内核。

缺点：Pi 与 Codex 的原生能力并不天然一致，必须分别完成工具、安全、停止、恢复和模型兼容性验收。

### 不提供只能聊天的旁路直连

任务推送与会话输入统一进入 Agent 主路径，不增加绕过 Pi、只向模型 API 发送文本的旁路模式。

优点：用户选择其他模型后仍处于可执行、可审计的 Zeus 工作流中，不会出现“看起来能推送任务，实际上只能聊天”的入口。

缺点：首个可用版本必须先完成 Pi 纵向接入，无法用一次聊天请求快速冒充多模型支持完成。

### Pi 工具动作由 Zeus 安全接管

Pi 提出的文件读写、命令执行和项目外访问必须在执行前经过 Zeus 的权限判断与用户审批。Pi 的项目可信状态不能替代 Zeus 授权，也不允许 Pi 直接全权限运行后再补审计。

优点：Codex 与 Pi 共用一致的产品安全口径，用户可以理解和追溯每次高风险动作。

缺点：需要实现 Zeus 专用 Pi 安全扩展、交互请求路由和失败关闭机制，并通过真实工具调用验证。

### 开放任意 OpenAI 兼容供应商

首版允许用户创建任意 OpenAI 兼容供应商，填写供应商名称、服务地址、API Key 和模型配置；阿里云百炼与 DeepSeek 作为快捷模板提供预填值，但不形成两套专用执行链路。

优点：新增兼容供应商不需要等待 Zeus 发版，模板与自定义配置共用同一套保存、校验和 Pi 路由能力。

缺点：不同平台对 OpenAI 协议的实现程度不一致，连接成功不能直接证明流式输出、工具调用、推理参数和用量统计都兼容；必须保存并展示逐项能力验证结果。

### 通用适配一次，厂商只作为模板和验收样本

Zeus 不为 DeepSeek、阿里云百炼、Kimi、GLM 分别开发四套执行链路。首版只实现一次“用户配置的 OpenAI Chat Completions 兼容连接”能力，用户填写服务地址、API Key、模型 ID 和必要的兼容字段后，统一复用 Pi Agent、Zeus 工具、安全审批、会话与任务能力。

常见厂商模板只提供服务地址、认证方式、模型目录地址和已知参数映射的预填值，本质仍是同一种用户配置模型连接。真实厂商用于证明通用链路可以处理直连平台和托管平台的差异，不代表代码中按厂商写分支。

只有某个平台不符合共同协议、必须使用专有字段或专有接口才能实现某项能力时，才把差异做成可选兼容配置或能力插件；不能把专有能力冒充为所有 OpenAI 兼容连接都支持。

优点：通用功能完成后，新供应商通常可以由用户自行配置，不需要等待 Zeus 发版。

缺点：协议兼容只解决“怎么调用”，不能自动证明每个模型支持工具调用、思考等级、图片或服务档位；这些仍需由模板、用户声明或运行探针形成逐模型能力档案。

### 真实外部验收需要用户自有凭据

当前开发环境没有 DeepSeek、阿里云百炼、Kimi 或 GLM 的可用 API Key，因此需求调研和后续构建通过都不能表述为已经完成真实厂商验收。

功能实现后，用户应在 Zeus 系统设置中自行录入凭据，明文只进入系统安全存储。连接诊断和能力探针由 Zeus 使用该连接发起，界面及日志只展示脱敏连接身份、请求结果、能力证据和错误分类，不回显或写入文档中的明文凭据。

如果没有任何外部厂商凭据，可以用本地 OpenAI 兼容服务验证通用配置、Pi 路由、工具审批和错误处理，但该结果只能证明本地兼容链路，不能证明 DeepSeek、百炼或其他外部平台已经兼容。

优点：凭据不离开用户设备，验收结果来自用户实际要使用的账号、地域和模型。

缺点：在用户提供安全配置并授权发起实际调用前，只能完成实现、静态检查、构建和本地链路验证，不能把它们合并报告为外部 API 端到端完成。

本任务已经确认：本次交付完成通用功能及不依赖外部 API Key 的功能验收；用户后续在 Zeus 设置界面配置自有凭据后，再单独授权并执行真实外部 API 验收。本次完成条件不得包含或冒充真实厂商调用成功。

### 模型目录自动获取并允许手工补充

保存供应商配置时尝试从供应商模型目录接口获取模型，用户可以手工新增模型，也可以修正自动获取结果中缺失的展示信息和能力声明。自动发现失败时保留供应商配置与用户输入，不把供应商误判为整体不可用。

优点：兼顾常见平台的低配置成本和不提供标准模型目录的平台，也允许使用尚未进入目录的新模型。

缺点：模型目录通常只能证明模型 ID 存在，不能单独证明推理等级、服务档位、工具调用、图片输入或用量统计可用。

### 每个模型保存独立能力档案

任务推送弹窗和会话输入框只能根据当前所选模型的能力档案展示并启用控制项。能力至少区分已支持、不支持和未验证，并记录来源、检查时间及真实生效结果；供应商级配置不能无证据覆盖全部模型。

快速模式属于服务档位，不与模型、推理等级或普通请求速度混为一谈。Codex 的 Fast 继续使用 Codex 模型目录返回的服务档位；Pi 模型只有在供应商存在明确请求字段且 Zeus 已完成真实验证时，才能显示对应服务档位。

优点：任务推送和会话输入使用同一能力事实，不会出现界面允许选择、运行时却忽略参数的假开关。

缺点：需要为目录声明、用户配置、兼容模板、运行探针和真实响应建立证据优先级，并处理能力过期和降级。

### 全局保存连接，项目选择多个可用模型

模型连接配置放在系统设置中全局保存，API Key 只配置一次；同一供应商需要使用多个账号、地域或 API Key 时，分别创建多个有名称的连接。项目从这些全局连接中选择多个允许使用的模型，并指定一个默认选中项。

默认模型只负责打开“推送到新会话”和新建项目会话时的初始选择，不是项目唯一模型。用户可以在当前项目允许的模型范围内改选，模型变化后必须重新计算推理等级、输入类型和服务档位等开关。

优点：密钥和连接不需要在每个项目重复维护，项目又可以收窄实际可用范围；多个模型可以按任务特点选择，不会被默认模型锁死。

缺点：全局连接被停用、删除或失效时会影响多个项目；系统需要在删除前展示引用项目，并为项目默认模型失效提供明确降级状态，不能静默换成其他模型。

### 同一 Pi 会话允许逐轮切换模型

已有 Pi 会话在没有活动执行时，可以为下一条消息改选项目可用模型。模型选择在消息真正派发时冻结，每一轮分别保存实际使用的连接、模型和能力档案；正在执行或排队派发时不得改变该轮模型。

Pi 原生协议提供 `set_model` 和可用模型查询，可以承载同一原生会话中的模型切换。Zeus 仍需判断不同模型对历史思考内容、工具调用消息和输入类型是否兼容；无法安全转换时必须阻止原会话切换并提示新建 Pi 会话，不能丢弃或伪造历史内容。

Codex 与 Pi 属于不同 Agent 身份，二者之间的改变仍然创建新的 Zeus 产品会话，不使用逐轮模型切换。

优点：用户可以根据下一步任务选择更合适的模型，并继续使用已有会话上下文。

缺点：同一段历史可能经过不同模型处理，问题复盘和成本归因更复杂；Zeus 必须保存逐轮模型事实，并建立历史兼容判断与明确的失败提示。

## 实现边界说明

正常的 OpenAI 兼容供应商优先使用 Pi 的自定义模型或自定义供应商配置，不修改 Pi 核心。Zeus 仍需实现 Pi 进程管理、Keychain 凭据注入、供应商配置投影、RPC 事件映射、工具安全接管、会话恢复和能力证据。

只有供应商协议无法通过 Pi 兼容配置或扩展适配，或者 Pi 缺少完成安全接管所需的协议钩子时，才重新评估是否需要修改 Pi；不得把 fork Pi 作为默认方案。

### Pi 采用官方 SDK 内嵌

Zeus 与 Pi 都运行在 Node/TypeScript 环境，本任务采用官方 `@earendil-works/pi-coding-agent` SDK，把 Pi 作为 Zeus 的运行内核依赖接入，不要求用户另外安装全局 Pi CLI，也不启动语言无关的 RPC 子进程。用户界面和持久数据仍只表达“Pi Agent”，不暴露 SDK 为新的 Agent 身份。

Zeus 使用 Pi 的运行时凭据覆盖把 Keychain 中的 API Key 注入内存，使用自定义供应商注册承载用户配置的 OpenAI Chat Completions 连接，并使用自定义工具替换 Pi 默认写文件和命令工具。Pi 不得读取自己的 `auth.json` 或把 Zeus 凭据写入 Pi 配置目录。

优点：官方明确建议同进程 Node/TypeScript 集成使用 SDK；Zeus 可以直接访问会话、事件、模型切换和工具定义，安全接管不依赖解析子进程输出。

缺点：Pi 及其依赖会进入桌面应用包，版本升级必须重新验证模型兼容和工具事件；同进程故障隔离弱于独立 RPC 子进程，需要由 Zeus 在会话边界捕获错误并失败关闭。

## 2026-08-05 官方 API 调研

### 调研口径

本节只依据各平台当前官方公开文档。模型目录和能力变化较快，以下结果是 2026-08-05 的设计快照，不作为永久硬编码目录。

“快速”需要拆成三种不同事实：

1. **服务档位**：同一个模型通过请求字段选择更高优先级资源，并能从响应确认实际生效档位。
2. **高速模型变体**：通过另一个模型 ID 使用 Flash、Turbo、High-Speed 或 Fast 模型。
3. **降低思考开销**：关闭思考或降低推理等级，以延迟换取推理深度和成本。

后两种都不能映射成 Codex Fast。

### 结论总览

| 接入渠道 | 可选服务档位 | 高速方式 | 推理控制 | Agent 关键能力 | 主要特殊点 |
|---|---|---|---|---|---|
| DeepSeek 官方 API | 未发现可请求的 `service_tier` | `deepseek-v4-flash` 是独立模型 | 思考开关；`low / high / max`，且各模型支持范围不同 | 流式、工具调用、思考中工具调用、JSON Object、用量、自动上下文缓存、模型目录 | strict 工具模式仍是 Beta；Responses 当前按模型分别开放 |
| 阿里云百炼 | 未发现面向普通调用的快速档位；PTU 响应会返回 `ptu-standard`，表示容量/计费路径 | Qwen Flash、Coder Flash、`glm-5.2-fast-preview` 等均为独立模型 | Chat 使用 `enable_thinking`；Responses 推荐 `reasoning.effort`，支持范围按模型和地域变化 | OpenAI Chat、Responses、Anthropic 兼容、工具调用、结构化输出、多模态、用量、显式或隐式缓存 | 同一平台可托管 Qwen、DeepSeek、Kimi、GLM；能力还受地域、工作空间、计费计划和部署来源影响 |

### DeepSeek

DeepSeek 当前 `/models` 返回 `deepseek-v4-flash` 和 `deepseek-v4-pro`。两者支持思考与非思考、JSON Output、工具调用和 Anthropic 兼容；Responses API 当前按模型分别开放。Chat Completion 提供 `thinking.type` 与 `reasoning_effort`，但不同模型接受的等级不同。

官方 Chat Completion 参数中没有 `service_tier`。因此 `deepseek-v4-flash` 必须作为具体模型选择，不能在 `deepseek-v4-pro` 上显示“Fast”开关。

### 阿里云百炼

百炼同时提供 OpenAI Chat、OpenAI Responses、Anthropic 兼容和 DashScope 原生接口。Responses 文档提供从 `none` 到 `max` 的推理等级，但地区和模型支持范围不同；Chat 仍广泛使用非标准的 `enable_thinking`。平台支持工具调用、结构化输出、多模态和缓存，但具体能力按模型变化。

百炼 PTU 的响应字段 `service_tier=ptu-standard` 只说明请求实际消耗了预购买吞吐容量；超额时会自动回退按量付费并返回 `default` 或省略字段。它不是用户在每次任务推送时选择的快速档位。Flash、Coder Flash 和 Fast Preview 仍按独立模型 ID 处理。

百炼还是模型托管平台：同一个 DeepSeek、Kimi 或 GLM 模型通过百炼调用时，其真实能力由“百炼端点 + 地域 + 计费计划 + 部署来源 + 模型 ID”决定，不能复用模型发行方官方 API 的能力结论。

### Kimi

Kimi 提供 OpenAI 兼容 Chat Completion 和模型目录。当前模型能力不是统一形状：K3 固定思考并支持 `low / high / max`，K2.6 支持思考开关，K2.7 Code 固定思考；Kimi 的工具调用、结构化输出、视觉输入和思考保留规则也按模型变化。

官方没有提供可请求的 `service_tier`。`kimi-k2.7-code-highspeed` 是独立高速模型，旧的 K2 Turbo / Thinking Turbo 已废弃。因此 Zeus 只能把 High-Speed 作为模型标签和模型选择，不能显示成当前模型的 Fast 开关。

### GLM / Z.AI

GLM Chat Completion 提供思考开关、流式输出、工具调用、JSON Object、用量和缓存；GLM-4.6 及以上还支持流式工具调用。GLM-4.5 及以上支持交错思考，编码场景可以保留历史思考，但要求完整、原样且按顺序回传 `reasoning_content`。

官方没有提供可请求的 `service_tier`。GLM-4.7-FlashX、GLM-4.5-X、GLM-4.5-AirX、GLM-5-Turbo 等是独立模型；高速来自模型选择，不是同一模型的服务档位。

## Zeus 统一适配建议

### 首版统一主协议

首版以 Pi 的 `openai-completions` 适配为共同基线，不同时把 Responses、Anthropic 和各厂商原生接口都变成主路径。百炼、DeepSeek、Kimi 和 GLM 模板只负责提供兼容字段映射；供应商专有内置搜索、代码解释器、MCP 和托管 Agent 不纳入首版统一能力，Zeus 继续使用 Pi 工具与自身安全审批。

该范围已经确认。首版的新建供应商、能力探针、任务推送和会话执行只对 OpenAI Chat Completions 主链负责；其他协议即使供应商支持，也必须显示为当前未接入，不能从文档能力推断为 Zeus 已支持。

优点：四家都有可落地的共同协议，Pi 已提供自定义供应商、模型兼容字段和思考格式扩展点。

缺点：首版不能使用 Responses 的服务端会话或百炼内置工具等平台专属能力；后续要通过能力插件单独开放。

### Agent 可用的最低门槛

一个模型只有以下能力通过真实探针后，才允许出现在任务推送和可写会话中：

1. 流式文本可以稳定结束并返回明确终态。
2. 可以生成函数工具调用，并能接收工具结果继续完成同一轮任务。
3. 多轮消息、工具调用 ID 和思考内容能够按供应商规则正确回传。
4. 中断、超时、限流、余额不足和模型不存在能够映射成稳定错误。
5. Token 用量至少能读取输入、输出和总量；缺失项显示未提供，不能伪造为零。

未通过工具闭环的模型可以保存在设置和诊断目录中，但不能作为“Pi Agent 可执行模型”推送正式任务。

### 统一模型能力档案

每个“模型接入渠道 + 模型 ID”保存独立能力档案，至少包含：

| 能力组 | 建议字段 |
|---|---|
| 身份 | 模型发行方、接入渠道、地域、计费计划、模型 ID、展示名、生命周期 |
| 协议 | Chat / Responses / Anthropic、基础地址、认证方式、兼容模板版本 |
| 上下文 | 上下文窗口、最大输出、文本/图片/音频/视频/文件输入 |
| 思考 | `locked_on / on_off / effort_levels`、支持等级、默认值、是否必须保留历史思考、请求映射 |
| 工具 | 普通函数、strict、并行调用、流式参数、工具结果格式、工具数量限制 |
| 输出 | 文本流、reasoning 流、JSON Object、JSON Schema |
| 缓存与用量 | 自动/显式缓存、缓存命中字段、输入/输出/思考/缓存 Token、价格元数据 |
| 速度 | `standard / high_speed / flash / turbo` 模型标签；不得替代服务档位 |
| 服务档位 | 可请求档位、请求字段映射、响应实际档位；三者不完整时不显示开关 |
| 证据 | 声明来源、探针版本、检查时间、支持/不支持/未验证、最后真实生效结果 |

### 界面开关生效规则

- 模型、推理等级和服务档位必须是三个独立控件，不能相互冒充。
- 高速模型通过模型下拉框选择，并显示“高速模型”标签；不显示 Fast 开关。
- 思考开关或推理等级只在当前模型存在明确请求映射时展示。
- 服务档位只有在同一模型上存在可请求档位，并且响应能返回或事件能确认实际档位时展示。
- 每次会话保存请求值与实际值；供应商不返回实际值时只显示“已请求”，不能写成“已生效”。
- 切换模型后重新计算全部控件；旧模型的推理等级、图片能力或服务档位不得带到新模型。

### 模型目录与探针

`GET /models` 只负责发现模型 ID 和可用性，不作为完整能力来源。能力证据优先级建议为：

1. 当前模型的真实运行响应与闭环探针。
2. Zeus 内置且带版本的官方供应商模板。
3. 供应商模型目录返回的字段。
4. 用户手工声明。

高优先级证据与低优先级声明冲突时，以高优先级为准并保留诊断，不静默覆盖用户配置。

## 2026-08-05 实现结果

本阶段已经完成首版通用接入，不按 DeepSeek、百炼、Kimi、GLM 逐家写独立执行链。供应商模板只提供默认地址和思考格式；用户新增其他 OpenAI Chat Completions 兼容连接后，可以复用同一套模型目录、能力档案、项目授权、任务推送和 Pi Agent 执行链。

已经落地的产品能力：

1. 系统设置新增“模型供应商”，可以创建多个连接，配置连接名称、服务地址、模型目录、API Key 和多个模型。API Key 只写入 macOS 钥匙串，普通设置和接口响应不返回明文。
2. 项目设置可以从全局连接中选择多个允许模型，并指定一个默认预选模型；默认项不限制用户改选其他已授权模型。
3. 任务推送和已有会话输入区统一使用组合模型身份，展示连接来源、模型名称、速度标签、可用状态、推理等级和服务档位。
4. Pi 连接首版统一走 OpenAI Chat Completions，通过官方 `@earendil-works/pi-coding-agent` SDK 内嵌运行，不要求用户安装 Pi CLI，也不修改 Pi 源码。
5. Pi 默认工具被关闭，文件读取、搜索、写入、编辑和命令统一经 Zeus 工具代理执行；只读模式拒绝写操作，自动模式进入 Zeus 审批，完全访问按现有权限选择执行。
6. 同一 Pi 会话空闲时允许逐轮切换同一项目已授权的模型；正在执行时支持插话和中断。Codex 与 Pi 之间切换会明确要求新建会话，避免混淆原生会话身份。
7. 模型 ID 中的 Flash、Turbo、High-Speed 或 Fast 只识别为高速模型标签。Pi Chat 首版不提供 Codex Fast 服务档位开关，避免把模型变体误报成服务优先级已经生效。
8. 无 API Key 的连接和模型仍可配置、查看并分配给项目，但在任务推送和会话模型选择中显示不可运行原因，不允许正式派发。

### 实现优缺点

优点：新增兼容供应商不需要改执行代码；连接、模型和项目授权边界清楚；Pi 能复用 Agent 会话与工具循环，同时由 Zeus 保留权限、审批、状态和凭据控制。

缺点：首版只统一 Chat Completions，不包含各厂商 Responses、Anthropic 兼容或原生托管工具；用户手工声明的能力在真实探针前只能标记为未验证；不同供应商对思考内容和工具消息的细节差异，仍需使用真实 API Key 逐个做运行验收。
