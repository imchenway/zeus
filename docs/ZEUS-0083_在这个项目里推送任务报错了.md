# ZEUS-0083 在这个项目里推送任务报错了

## 任务目标

修复 CSS 多仓项目使用包含中文和 `#` 的真实本地来源分支推送任务时，被 `Git source ref contains unsafe characters` 错误阻断的问题，并保证同一分支在后续差异查看、推送和代码交付链路中继续可用。

## 现场证据

- 推送弹窗中的三个项目仓库为 `backend-java`、`dwt-miniapp`、`frontend-miniapp-sdk`。
- 三个仓库都真实存在本地分支 `feature/#6594-AI-Agent智能体客服`。
- 本机 Git `2.39.5` 执行 `git check-ref-format --branch 'feature/#6594-AI-Agent智能体客服'` 成功，说明该名称符合 Git 分支规则。
- `packages/local-server` 已先确认来源值存在于仓库返回的 `localBranches`，但 `packages/git-core` 随后又用仅接受英文、数字和少量符号的正则校验 `sourceRef`，因此把 Git 合法名称误报为不安全。
- Git 操作通过参数数组调用 `execFile`，来源分支不会经过 Shell 字符串拼接；中文和 `#` 本身不构成命令注入。

## 已确认边界

1. 来源分支必须是项目仓库真实存在的本地命名分支，名称合法性以 Git 自身规则为准。
2. 来源分支允许中文、`#` 及其他 Git 合法字符，不再套用 Zeus 自造的 ASCII 字符白名单。
3. 任务分支继续强制使用 `zeus/` 前缀；前缀后的名称同样以 Git 自身规则为准。
4. 通用高风险 Git 操作继续保留原有 ref 防护，本次不粗暴删除整个安全校验函数。
5. 修复必须覆盖工作区创建、分支差异、远端推送和合入目标读取，不能只让推送弹窗越过第一道门禁。

## 方案与取舍

### 采用 Git 原生分支校验与本地分支存在性双门禁

来源分支和任务分支先通过 `git check-ref-format --branch`，需要读取或写入既有分支时再用完整 `refs/heads/<分支名>` 检查真实存在性。任务分支额外保留 `zeus/` 前缀。

优点：Zeus 规则不会继续与 Git 漂移；中文和 `#` 分支可以完成完整任务生命周期；完整 ref 可以减少短名称歧义。

缺点：任务工作区相关的多个 Git 入口都要统一迁移，不能只改一处正则；验证范围需要覆盖创建、比较、推送和合入。

### 不采用仅给正则增加中文和 `#`

优点：单点改动最小。

缺点：仍会漏掉其他 Git 合法名称，后续还会重复出现同类缺陷；差异、推送和合入链路中的同一白名单也会继续报错。

## 实施记录

- `packages/git-core/src/index.ts`
  - 新增 Git 原生分支格式校验，来源分支、任务分支和远端目标分支统一调用 `git check-ref-format --branch`。
  - 新建任务工作区时，来源分支还必须通过本地 `refs/heads/<分支名>` 存在性校验；恢复既有工作区时只接受已持久化的精确来源提交 ID。
  - 分支比较、分支提交读取和合入统一使用完整本地 ref，避免短名称歧义，同时允许 Git 合法的中文和 `#`。
  - 任务工作区提交、独立推送和远端结果校验允许 Git 合法任务分支名；任务分支创建继续由 `assertValidGitBranchName` 强制 `zeus/` 前缀。
  - 通用高风险 Git 操作的 `requireSafeGitRef` 保持原样，没有把本次任务扩大为所有任意 ref 输入的放宽。
- `CONTEXT.md`
  - 固化“来源分支”和“任务分支”领域定义，明确二者都不等于 ASCII 分支名，任务分支仍保留 `zeus/` 前缀。
- `DESIGN.md` 与任务 Git 工作区主设计文档
  - 明确来源分支使用 Git 原生规则和本地分支存在性双门禁，禁止继续新增 ASCII 字符白名单。
