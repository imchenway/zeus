# ZEUS-0090 有两个会话无法归档

## 当前阶段

已完成现状核对、根因修复、工程门禁、测试身份打包与隔离 API 往返验证。独立 GUI 点击验收受同路径并发测试实例限制，未冒充为已通过。

## 用户反馈

- 两个会话无法归档。
- 截图中的会话标题为 `This is a confirmed packag...` 与 `Zeus 20260717 PROJECT_...`。
- 任务未提供预期、复现步骤或界面报错。

## 只读数据证据

在正式数据的只读查询中，两条记录均满足以下条件：

- `task_id IS NULL`，属于项目对话，不是任务会话；
- `transport_kind = codex_native`，具有真实 Codex 原生线程身份；
- `provider_state = archived`，底层 Codex 线程已经归档；
- `archived = 0`，Zeus 本地记录仍未归档。

本次只读取正式数据库，没有修改、归档或恢复正式数据。

## 根因

既有手动归档实现把入口和设置列表限定为任务会话：

- 会话树仅在 `taskId` 非空时显示“更多会话操作”；
- 归档处理函数在 `taskId` 为空时直接返回；
- 设置页接口只收集带任务关联的已归档会话。

服务端归档路由和协调器本身已经支持项目对话，也能在底层线程已归档时跳过重复 Provider 操作并补齐 Zeus 本地归档状态。因此真实缺口是前端入口、刷新分支和已归档列表的领域范围不一致。

## 修复设计

1. 项目对话与任务会话共用同一归档菜单和运行状态门禁。
2. 归档成功后按归属刷新：任务会话刷新任务分组，项目对话刷新项目直属会话。
3. 设置页返回全部可见的已归档会话，并明确区分项目对话与任务会话上下文。
4. 保留原有双重安全保护：运行中、排队中、等待批准或等待用户输入时仍不可归档；Provider 失败时不退化成只隐藏 Zeus 记录。

## 方案取舍

- 优点：两类正式会话使用一致的收纳能力；底层已归档、Zeus 未归档的记录可通过同一操作重新收敛；恢复入口完整。
- 代价：设置页已归档列表不再只展示任务会话，需要增加“项目对话”上下文文案。
- 不采用自动批量修正正式数据：这会在用户未操作时改变会话可见性，也无法替代长期产品入口修复。
- 不移除运行状态门禁：归档不应隐式中断执行或丢弃排队和交互请求。

## 验收口径

- 非活动项目对话与任务会话都显示归档入口。
- 项目对话归档成功后从项目直属会话列表消失，并出现在设置的已归档会话列表。
- 项目对话恢复后回到原项目直属位置；任务会话仍回到原任务位置。
- 底层已归档但 Zeus 尚未归档的项目对话可以完成本地状态收敛。
- 运行中、排队中或等待交互的两类会话继续被拒绝归档。
- 不改变任务状态，不清理工作区，不执行 Git 写操作。
