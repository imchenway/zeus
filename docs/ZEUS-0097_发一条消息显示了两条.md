# ZEUS-0097 发一条消息显示了两条

## 任务结论

- 任务类型：缺陷。
- 现象：用户只发送一次“继续”，会话记录中出现两条相同用户消息，并形成两个独立处理轮次。
- 目标：一次已接受的用户提交最多启动一个 Provider 轮次；排队、重连和接口幂等能力保持不变。
- 当前阶段：已完成根因修复，静态检查、构建和真实运行结果见“验证记录”。
- Git 边界：本任务不执行 commit、push、merge 或 revert。

## 截图证据与根因

截图中两条“继续”分别拥有独立的“已处理”耗时。这说明问题不是一个气泡被重复绘制，而是同一用户动作进入了两个 Provider 轮次。

消息提交存在两个合法派发入口：

1. 消息接口把提交持久化后，在会话空闲时直接派发；
2. 后台队列排空在上一轮结束或并发名额释放时派发队首提交。

旧实现虽然有请求幂等、客户端消息身份和队列排空自身的互斥，但两个入口都会调用 `dispatchSubmission`。该函数先执行会话现场恢复和运行内核世代对账，经过异步等待后才把会话与提交标记为“正在派发”。如果接口直派与队列排空同时选中同一条刚持久化的提交，两边会在标记建立前一起通过空闲判断，并各自调用一次 `startTurn`。

因此，按消息正文去重、只隐藏第二个气泡或只禁用发送按钮都不能修复根因：这些方案会误伤用户有意连续发送相同内容，也无法阻止第二个 Provider 轮次真实执行。

## 实施规则

- 在 Codex 原生协调器内增加会话级派发租约，租约在第一次异步等待前建立。
- 同一会话、同一提交的并发派发请求共享同一个 Promise，只执行一次 Provider `startTurn`。
- 同一会话存在派发租约时，其他提交保持 `queued`，继续由现有队列顺序和并发规则处理。
- 接口派发与后台排空竞争时，接口的 Provider 写入生命周期会附加到已有租约；如果 Provider RPC 已开始，则立即补记 `rpc_started`。这样崩溃恢复仍能区分“尚未产生外部副作用”和“结果需要权威对账”。
- Provider 归档后的原提交重试继续沿用同一租约，不在恢复过程中再次取得第二份派发所有权。
- 不按正文、时间窗口或最新消息做模糊去重；两次明确用户动作仍会生成两个不同客户端消息身份和两个正常轮次。

## 方案取舍

优点：

- 从 Provider 写入入口阻止重复轮次，消息展示、耗时、Token 消耗和实际代码操作同时恢复为一次。
- 保留现有请求幂等、提交身份、队列顺序、并发限制和失败恢复语义。
- 不需要数据库迁移、接口变更或历史数据清理。

代价：

- 同一会话在任意时刻只能有一个派发所有者；其他提交即使同时到达，也要继续排队。这与现有单会话单活动轮次规则一致，但协调器多维护一份短生命周期内存状态。
- 进程已经产生的历史重复轮次不会被自动删除；删除历史消息会破坏审计事实，本任务只阻止后续新重复。
