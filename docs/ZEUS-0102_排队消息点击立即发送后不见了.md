# ZEUS-0102 排队消息点击立即发送后不见了

## 任务结论

本次按已确认计划同时修复后续消息列表的“引导”和 Composer 的立即引导。用户动作成功进入 Provider 后，消息从后续消息列表原子地转为当前轮次内的“引导中”用户消息；只有 Provider 回传精确匹配的 `userMessage.clientId` 后，才原位转为普通消息。

未采用历史提交 `834c848`。该提交混入大量无关改动，且其中本任务文档只记录诊断与候选方案；本次基于当前代码聚焦实现。

## 根因

原链路把 `turn/steer` RPC 返回成功等同于消息已经出现在 Provider 轮次中：

1. 队列项或 Composer 创建 `steer_now` submission。
2. 服务端调用 `turn/steer`。
3. RPC 一返回成功，服务端立即把 submission 写成 `resolved` 并广播队列变化。
4. Renderer 因权威队列已移除该项而停止显示后续消息。
5. 当 Codex 正等待用户问答时，对应 `userMessage` 可能要等回答完成后才出现，期间对话记录也没有可替代的用户消息。

因此正文没有被删除，但“队列投影已移除、Provider 投影尚未到达”形成了可见性空窗。

## Codex 对照

当前 Codex 在引导请求已发出、真实用户消息尚未确认时，保留一条带待处理引导状态的用户消息，而不是等待 Provider 事件后才显示。Zeus 本次采用同一产品语义，同时继续以本地持久 submission 作为刷新和重启恢复事实源。

## 状态流

### 正常路径

1. 后续消息是 `queue + queued`，显示在输入区旁的后续消息列表。
2. `turn/steer` 成功后保持 `steer_now + dispatching`。
3. 服务端广播 `conversation.submission.steering`，事件同时携带 submission 与最新队列快照。
4. Renderer 一次性从列表移除该项，并在目标 Provider 轮次创建“引导中”用户消息投影。
5. Provider `userMessage.clientId` 与 `clientUserMessageId` 精确匹配后，submission 变为 `resolved`，同一投影原位替换为普通消息。

### 恢复与异常路径

- 完整快照遇到 `steer_now + dispatching` 且没有持久的精确用户消息时，重建“引导中”投影。
- RPC 结果未知、终态轮次缺少精确用户消息或恢复快照无法确认时，submission 变为 `paused + recovery_required`，Renderer 显示“引导结果待确认”。正文、附件和客户端消息身份继续保留，不自动重发。
- Provider 明确报告目标轮已结束时，清除旧轮次绑定并按普通后续消息重新排入下一轮。
- 幂等恢复遇到已经进入 `dispatching`、已经 `resolved` 或处于引导恢复保护的 submission 时，只返回持久结果，不再次调用 `turn/steer`。

## 实现范围

### 服务端

- `NativeOperationStatus` 增加 `steering`。
- 两个 Codex 引导入口在 RPC 成功后保持 `dispatching`，并广播 `conversation.submission.steering`。
- 实时事件补齐 submission 与权威队列快照。
- Provider 用户消息持久化时只按精确 `clientId + providerTurnId` 完成对应引导 submission。
- 轮次终止和启动恢复不再把同轮引导 submission 当成主轮次 submission 自动完成；缺少精确消息时进入恢复保护。
- 队列引导的 API 幂等恢复接受已持久的待确认状态，避免重复副作用。

### Renderer

- 实时事件与队列引导 API 回执共用同一 submission 投影，按客户端消息 ID 去重。
- Composer 立即引导的乐观用户消息携带 `delivery=steer_now`，事件到达时迁移到真实目标轮次。
- 完整快照从 submission 重建未确认引导，刷新、切换会话和重启后仍可见。
- Provider 用户消息只通过精确客户端消息 ID 替换乐观投影；不按正文或当前轮次模糊匹配。
- `ThreadItemView` 显示“引导中”或“引导结果待确认”，状态使用可读文字和动态状态语义；乐观投影不开放编辑或重复引导。

## 优缺点

优点：

- 消息从点击开始持续可见，不再依赖 Provider 事件到达时机。
- UI 状态对应真实事实：RPC 接受、Provider 确认和异常待确认不再混为一体。
- 精确客户端消息身份关联避免相同正文、同轮多次引导造成重复或误确认。
- 持久 submission 可以覆盖刷新、切换会话、多窗口和应用重启。

代价：

- 服务端、实时事件和 Renderer 都要理解 `queued / dispatching / resolved` 三段状态。
- 写入结果未知时不能自动收敛为成功或失败，需要保留恢复保护并由后续权威事实或用户动作处理。
- “引导中”是本地持久投影，必须和 Provider 普通消息维持严格的身份替换规则。

## 兼容边界
