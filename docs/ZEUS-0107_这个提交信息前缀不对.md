# ZEUS-0107 这个提交信息前缀不对

## 当前阶段

已完成实现与静态、构建、隔离打包验证。

## 用户反馈

- 任务类型：优化。
- 现状：任务代码提交说明默认生成为 `任务编码: 任务标题`，没有根据任务类型使用 `feat`、`fix` 等前缀。
- 预期：用户未提供完整映射规则。
- 截图示例：`ZEUS-0035: 增加门店确认与货单查询交互`。

## 已确认事实

- 任务类型固定为 `requirement / defect / optimization`，界面分别显示“需求 / 缺陷 / 优化”。
- `TaskGitReviewModal` 和 `TaskGitMergeModal` 分别独立生成相同的默认提交说明：`任务编码: 任务标题`。
- 本机服务在请求没有提交说明时也使用 `任务编码: 任务标题` 作为兜底。
- 当前没有统一的“任务类型到 Conventional Commits 前缀”映射。

## 用户确认

- 需求、缺陷、优化分别固定映射为 `feat`、`fix`、`perf`。
- 最终格式采用 `前缀: 任务编码 任务标题`，例如 `perf: ZEUS-0107 这个提交信息前缀不对`。
- 任务类型前缀只作用于任务代码提交，不修改代码交付产生的合入提交说明。
- 提交输入框保留手工编辑能力，默认说明不是强制校验规则。

## 初步取舍

- 固定映射的优点：规则简单、所有入口一致、无需增加操作；缺点：任务“优化”同时可能表示性能优化和代码结构优化，单一前缀可能不准确。
- 提交时选择的优点：语义最准确；缺点：增加一步操作，也会让任务类型不再直接决定默认前缀。
- 统一生成函数的优点：两个弹窗与服务端兜底不会再次漂移；缺点：需要调整共享层或服务端边界，改动范围比只改一个输入框略大。
