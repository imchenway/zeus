# ZEUS-0110 引导消息自动引导后重复显示排队消息

## 任务信息

- 类型：缺陷
- 用户现象：用户选择“立即引导”发送补充内容，内容已经进入当前回复后，同一正文又在下方显示为“排队中”。
- 截图证据：同一正文先作为普通用户消息出现，并得到当前回复确认；约四分钟后，底部再次出现同文案的排队气泡。
- Git 边界：未经用户明确要求，不执行 commit、push、merge 或 revert。
- 验证边界：日常运行只允许使用独立身份 `Zeus Test.app` 和独立用户数据目录，不生成或启动任务目录中的生产身份 `Zeus.app`。

## 已核对的历史口径

- `ZEUS-000041`：队列消息只代表 Zeus 已保存、模型尚未接收；进入 Provider 后必须从队列事实中移除。
- `ZEUS-0078`：“引导”是把补充内容交给当前回复，不是再创建一条下一轮消息；只有明确未被当前回复接收时才能回到普通后续消息队列。
- `TASK_20260805_002`：Provider 明确返回当前轮已结束时，未发送的引导可以降级为普通下一轮队列；结果未知时必须保持恢复保护，不能猜测成功。

## 当前根因链

Codex 的 `steer_now` 目前不是一条原子领域路径：

1. 消息先通过普通 `submitMessage` 创建为 `message / queue / queued` submission。
2. `submitMessage` 会重新核对执行上下文、运行状态和并发，并可能把该 submission 当成普通下一轮直接派发。
3. 外层接口随后才把记录改写为 `steer_now / send_now`，再调用 `sendQueuedNow` 尝试引导当前轮。
4. 上述两个阶段之间，当前轮完成事件、队列排空或其他窗口快照都可能观察到临时的普通排队状态；Renderer 也可能先收到 `queued` 接受结果，再收到已经进入当前轮的 Provider 用户消息。

因此，同一用户动作存在“已经作为引导进入当前轮”和“仍作为下一轮排队”两个竞争身份。截图中的重复展示是这条服务端身份竞争在界面的投影，不应只用 CSS 或客户端去重掩盖。

## 修复方向与取舍

采用独立的 Codex 引导提交路径：从创建时就持久化为 `steer / send_now`，绑定用户选择的精确当前轮；在 Provider 明确接收前不参加普通队列排空。Provider 接收后收敛为 `resolved` 并广播权威空队列；只有 Provider 明确表示目标轮已经结束时，才把同一记录转换为普通 `message / queue` 并自动排到下一轮。

优点：一次用户动作只有一个可执行身份；既保留引导失败后的无损降级，也消除临时普通队列被其他流程接管或展示的竞态。

代价：Codex 协调器需要新增直接引导入口，并继续维护“明确未发送”和“结果未知”两类失败边界；不能简单复用普通消息派发函数。

## 阶段状态

- 已在 Codex Native 协调器新增独立 `steerMessage` 入口。引导记录从首次持久化开始就是 `steer / send_now / dispatching`，不会短暂进入普通排队列表，也不会被普通队列排空流程接管。
- 引导入口再次核对精确的当前轮编号。若发起 RPC 前发现轮次已经结束，或 Provider 明确返回目标轮已结束，同一记录会清除旧轮绑定并转为普通下一轮队列；其他无法确认副作用的错误仍暂停为 `recovery_required`。
- Provider 用户消息现在优先通过精确的 `clientUserMessageId` 关联提交记录，再回退到当前轮原始 submission，避免引导消息误拿首条消息的展示正文或附件。
- HTTP 接收路径不再执行“先普通排队、再改写并立即引导”的两段式流程，Codex 引导直接调用协调器的原子入口。
