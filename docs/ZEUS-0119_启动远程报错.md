# ZEUS-0119 启动远程报错

## 任务状态

- 阶段：实现与静态验证完成
- 类型：缺陷
- 已完成：真实错误保留、失败后状态回滚、设置页语义与恢复入口。
- 未执行：真实启用官方远程守护进程、手机配对与远端回答回流，避免改变当前机器的共享远程授权状态。

## 用户提供的现象

- 任务标题：启动远程报错。
- 当前错误：`Codex app-server generation exited (1).`
- 当前恢复提示：请运行官方安装命令 `curl -fsSL https://chatgpt.com/codex/install.sh | sh`，完成登录后在 Zeus 设置中重新检测。
- 产品边界：Zeus 不自动安装 Codex CLI，不使用内置回退。
- 预期结果与复现步骤尚未提供。

## 已确认的仓库事实

1. `CONTEXT.md` 已将“用户本机 Codex CLI”定义为用户自行安装、登录，再由 Zeus 检测或显式配置路径的外部依赖。
2. `packages/ai-runtime/src/codexAppServerManager.ts` 已在普通 app-server 初始化失败时抛出用户看到的完整安装引导；内层原因会被统一包装为 `ZEUS_CODEX_DEPENDENCY_UNAVAILABLE`。
3. 同一管理器的远程接管链路会执行 `codex remote-control start --json`，失败时使用 `ZEUS_CODEX_REMOTE_CONTROL_START_FAILED`。
4. 设置页的“Codex 远程接管”已有状态刷新、启用、关闭和配对入口；普通 Codex CLI 依赖检测另有“重新检测”语义。
5. 当前开发环境优先命中官方独立安装的 `/Users/david/.local/bin/codex`，版本为 `0.146.1`，同时支持 `app-server --listen stdio://` 与 `remote-control start`。这只能证明当前开发机环境可用，不能替代报错用户的实机证据。

## 当前核心歧义

“启动远程”存在两种不同语义，不能直接混合实现：

1. **启用远程接管**：用户在设置页点击“启用远程接管”后报错。
   - 优点：与任务标题及现有 Remote Control 功能最匹配，可将修复限定在远程守护进程的路径选择、诊断与恢复交互。
   - 缺点：不会改变普通会话首次创建时的 app-server 错误。
2. **启动任意 Codex 会话**：任务推送或新建会话时，普通 app-server 初始化就报错。
   - 优点：覆盖所有 Codex 会话的依赖不可用问题。
   - 缺点：范围更大，且与“远程接管”的官方独立版布局要求不完全相同。

## 初步建议

建议先按第一种语义处理：将本任务定义为“设置页启用 Codex 远程接管时，Zeus 选中了无法启动官方 Remote Control 守护进程的 Codex CLI”。后续应先保留真实失败原因，再给出安装、登录、选择路径和重新检测的恢复链；不自动执行安装命令。

优点：修复范围与用户操作路径一致，不改变已确立的外部依赖边界。

缺点：如果用户实际是在新建普通会话时报错，此定义会偏离真实入口，所以必须先确认。

## 已定位的错误丢失原因

`spawnRemoteControlCodexAppServer` 返回的是 WebSocket 输送适配器，而不是 Zeus 直接持有的 Codex 子进程。但当前适配器把 `process.pid`（Zeus 自身进程号）填入了子进程 `pid` 字段。

这会产生以下错误顺序：

1. `codex remote-control start --json` 返回了具体失败原因。
2. 适配器发出携带具体原因的 `error` 事件。
3. 管理器看到伪造的 `pid` 存在，不立即以该错误结束当前世代。
4. 后续 `exit(1)` 事件只生成泛化的 `Codex app-server generation exited (1).`，最终覆盖用户需要的真实诊断。

建议修复是让虚拟输送适配器明确表达“Zeus 没有可直接管理的子进程 PID”，使首个具体错误成为世代失败原因。

优点：修复与真实进程所有权一致，能保留官方 CLI 的具体诊断，不需要猜测错误。

缺点：用户仍需自行安装、登录或更正 CLI 路径；Zeus 不会自动修改外部环境。

## 重新检测的路径冲突

现有契约与代码都规定“用户显式配置的 Codex CLI 绝对路径优先”。因此，如果用户曾固定一个旧的 Homebrew CLI 路径，完成官方独立版安装后直接点“重新检测”，Zeus 仍会检查旧路径。当前提示语在这个场景下无法完成恢复闭环。

## 用户质疑后的架构分歧

用户明确质疑“为什么要检测 Codex 的远程能力，目标是让手机远程到 Zeus”。这与现有 `CONTEXT.md` 和 ZEUS-000063 对“远程接管”的定义存在潜在冲突，需先确认产品语义：

1. **Codex 官方远程链路承载 Zeus 会话**
   - 手机看到和操作的是 Zeus 当前执行现场，但设备登录、配对和网络连接由本机 Codex CLI 的官方 Remote Control 提供。
   - 优点：复用官方身份、配对、网络和原始交互协议，现有实现与实机主路径证据可继续使用。
   - 缺点：远程能力受 Codex CLI 安装、登录、版本与官方服务限制；产品文案容易让用户误以为是 Codex 会话而非 Zeus 会话。
2. **Zeus 自建手机远程链路**
   - 手机直接连接 Zeus 服务，不使用 Codex Remote Control。
   - 优点：产品概念与技术所有权一致，可自主支持未来非 Codex Agent。
   - 缺点：需新增手机端、用户身份、设备配对、端到端安全、网络穿透、请求同步与审计体系；不是当前缺陷的小范围修复。

当前任务描述中的官方 Codex 安装命令与“无内置回退”边界支持第一种解释；但用户的质疑可能表示真实需求是第二种，必须显式确认，不能由代码现状代替产品决策。

用户已确认继续采用第一种架构。产品文案必须以“手机远程操作 Zeus 当前会话”为主语；Codex Remote Control 只是底层依赖和失败恢复事实，不得把用户操作对象写成 Codex 会话。

优点：保留现有官方连接能力和实机证据，同时让用户正确理解自己在操作 Zeus。

缺点：底层仍受本机 Codex CLI 的安装、登录、版本和官方服务状态限制，错误恢复中仍需如实说明。

## 已确认的产品与验收边界

1. 已确认：报错发生在设置页“启用远程接管”，普通任务推送或新建会话不是本缺陷范围。
2. 已确认：手机操作对象是 Zeus 当前会话，底层继续复用 Codex 官方 Remote Control，不改建 Zeus 自己的手机远程服务。
3. 已确认：用户只操作“启用远程接管”。能连接时直接启用；不能连接时展示真实原因、官方安装与登录说明，并提供“重新检测并重试”。
4. 已确认：Zeus 不自动安装、替换或切换外部 Codex CLI，不使用内置回退。

## 实现记录

### 真实错误保留

- `packages/ai-runtime/src/codexAppServerManager.ts` 不再给 WebSocket 适配器填入 Zeus 自身 PID。官方守护进程启动失败时，首个携带具体原因的 `error` 事件会直接结束当前运行时世代，后续通用 `exit(1)` 不再覆盖诊断。
- 远程链路的顶层错误改为“Zeus 无法启动会话远程接管所需的 Codex Remote Control”，然后附上脱敏后的具体原因与官方安装恢复说明。
- 官方 CLI 标准错误使用已有 `summarizeStderr` 脱敏并限长，不向普通设置页暴露私钥、Bearer 值或无界终端输出。

优点：用户看到可执行的真实原因，排查时不再只有退出码。

缺点：错误信息仍然受官方 CLI 返回内容限制；没有标准错误时只能明确说明“没有返回诊断信息”。

### 失败状态回滚

- `packages/ai-runtime/src/codexRuntimeGenerationManager.ts` 只在新的 Remote Control 输送世代成功激活后才保留远程启用状态。
- 启用失败后，后续普通 Codex 操作不会被误导到已失败的远程链路；用户可以在完成外部恢复后显式重试。

优点：一次失败不会污染后续执行状态。

缺点：用户需在修复外部安装或登录后手动按一次重试，Zeus 不会在后台无限重连。

### 设置页恢复闭环

- `apps/desktop/src/renderer/settings/CodexRemoteControlSettings.tsx` 标题改为“Zeus 会话远程接管”，明确远端操作对象是 Zeus 当前会话。
- 错误在设置分组内以 `role="alert"` 展示，未启用时直接提供“重新检测并重试”，同时声明 Zeus 不自动安装或切换外部程序。
- React 改动沿用现有状态与请求函数，没有新增额外请求瀑布、全局订阅或重型依赖。

优点：失败原因、外部恢复和重试动作在同一设置区域内完成，用户不需要理解运行时世代。

缺点：安装与登录仍在终端和官方 Codex 流程中完成，Zeus 只能检测结果并重试。
