# ZEUS-0120 这个会话每次点击发送后都会闪一下然后又把消息回填到了输入框

## 任务信息

- 类型：缺陷
- 状态：已完成实现与独立测试包验证
- 用户现状：点击发送后，输入内容短暂消失，随后又回填到输入框。
- 用户预期：未直接提供；附件中的历史讨论倾向于发送后不回填，也不额外显示“发送中”。
- 复现步骤：未直接提供；附件显示问题发生在既有任务会话的底部输入区。

## 已核对事实

- `DESIGN.md` 已定义两条不同路径：空闲会话正常发送应进入新一轮；当前回复仍在执行时，后续消息应进入输入区附近的等待发送列表。
- `ZEUS-0078` 已明确：尚未交给模型的后续消息不属于对话记录，不得伪装成已发送气泡，也不得只用“排队中”解释状态。
- 当前 Renderer 的普通发送会先清空草稿并创建临时用户消息；服务端接受后再用权威快照对账。
- 当前不可续会话使用“新建承接会话”输入区；其本地内容只在新会话被接受并切换成功后清理。
- 仅凭截图还不能判断问题发生在空闲正常发送、当前回复期间的后续发送，还是不可续会话的自动承接路径；三者修复位置和验收标准不同。

## 待用户逐项确认

1. 已确认：问题发生在昨天已经结束回复的旧会话，不是当前回复仍在执行时发送后续消息。
2. 已确认：新用户消息会在对话记录中短暂出现，随后消失；同一正文回填到输入框。

## 当前排查方向

- 已排除“当前回复尚未结束，后续消息正常进入等待发送列表”作为本次现象的主路径。
- 优先检查旧会话是否被判定为不可续，以及自动承接新会话成功后旧输入区为何仍保留内容。
- 同时检查空闲可续会话的提交接受与权威快照对账，避免遗漏消息已持久化但界面错误恢复草稿的情况。
- “临时消息消失 + 草稿恢复”与当前 `send_failed` 收敛行为一致，不能通过无条件清空输入框掩盖；否则发送失败时会丢失用户正文。
- 用户截图中的 DeepSeek 会话及“已处理 20m 30s”与 `TASK_20260807_001` 记录的 Pi / DeepSeek 历史会话特征一致，需优先核对该旧会话的 Agent 身份和续接路径。

## 根因证据

- 只读核对正式数据库后，截图对应会话为 `conversation_6eca667db9a73f80c63ef9be`，标题为“排队消息点击立即发送后，不见了”。
- 该会话的原生会话 ID 与文件路径均指向 Pi 会话 `019fd7c2-8e8a-7fee-8860-6d5b9e67d6ba`，模型来源为 DeepSeek，历史消息来源也为 `pi_sdk`。
- 同一主记录却仍保存 `agent_kind=codex`、`provider_id=codex`，与 `CONTEXT.md` 中“Agent 身份”和“双层会话身份”的稳定绑定定义冲突。
- 消息提交接口以主记录的 `agent_kind` 选择运行内核，因此这条 Pi 会话的后续消息被误送到 Codex 协调器；失败后 Renderer 的 `send_failed` 安全收敛会删除临时用户消息并恢复草稿，完整解释了用户现象。
- 昨天的修复只纠正了 Pi 最终回答投影，没有修复历史会话主记录的 Agent 身份；因此回答能完整显示，但旧会话仍不能正确续接。

## 已确认修复边界

- 用户确认：对具备强 Pi 证据的历史会话统一修复 Agent 身份，再按 Pi 原生会话继续发送；不做单条会话 ID 特判。
- 证据至少包含 Pi 原生会话文件或 `pi_sdk` 消息来源，并要求原生会话身份一致；不得仅凭模型名猜测 Agent。
- 优点：修复领域事实源，不只照顾单条会话；会话列表、能力界面、发送路由和后续恢复保持一致。
- 代价：需要设计严格的证据门槛和幂等数据修复，不能仅凭模型名猜测 Agent，也不能改写真正的 Codex 会话。
- 不推荐仅在 Renderer 清空输入：它会隐藏真实发送失败并造成用户输入丢失。
- 不推荐仅在发送接口临时猜测 Pi：虽然改动较小，但会继续保留错误主记录，其他界面和恢复链路仍会错路由。

## 已确认的验收口径

1. 在这条昨天已结束的 Pi / DeepSeek 会话中发送后，新用户消息不再闪退或回填，继续留在同一会话并启动新的 Pi 执行轮次。
2. 正常发送不新增“发送中”文字；已有加载反馈可以保留，但不能让正文消失。
3. 只有真实发送失败时才恢复草稿，并同时展示可理解的失败原因。
4. 历史修复必须幂等且只命中强证据 Pi 会话；正常 Codex 会话及其原生身份保持不变。
5. 不新增单元测试；使用静态检查、构建和独立 `Zeus Test.app` 的真实旧 Pi 会话续接完成验证。

## 实现记录

- 存储层新增原生会话身份候选读取和 Pi 身份修复：只在原生 ID、原生路径、模型来源、`pi_sdk` 消息证据完全一致时，把错误的 Codex 主记录修正为 Pi；修复可重复执行，且不修改会话更新时间。
- Pi 协调器在启动时核对候选记录：原生文件必须真实位于当前用户数据目录的 Pi 会话目录内，并要求消息元数据明确声明 `agentKind=pi`；模型名不参与 Agent 身份猜测。
- Codex 协调器的恢复、排队、关闭快照和全局事件广播只处理 `agent_kind=codex` 的会话，避免共享 `codex_native` 传输标识的 Pi 会话再次被 Codex 恢复流程污染。
- 服务启动顺序调整为先修复会话 Agent 身份，再修复 Pi 消息投影；两类修复任一命中后统一持久化数据库。
- Renderer 的失败保护未被削弱：真实发送失败仍会恢复草稿，本次不通过无条件清空输入框掩盖服务端错误。

## 约束与取舍

- 优点：先区分发送路径，可以避免把真实发送失败误修成无条件清空输入，从而造成内容丢失。
- 代价：严格证据门槛会保留证据不足的异常记录，需要后续根据新增事实单独处理；这是为了避免误改真实 Codex 会话。
- 本任务未新增或恢复单元测试，按项目要求使用静态检查、构建和独立 `Zeus Test.app` 运行验证。
