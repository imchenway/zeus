## 根因

3 个配置了 `origin` 的仓库当前访问 GitLab 均返回 `Permission denied (publickey)`。

`GET /api/tasks/:taskId/git-workspaces` 使用外层 `Promise.all` 加载任务下全部仓库，并在每个仓库读取本地审查状态之前同步执行远端刷新。远端刷新异常没有在单个仓库内收敛，任意一个仓库失败都会让整个接口失败。桌面端因此拿不到任何工作区，显示“任务分支 0”，并把本地提交按钮一起禁用。

这说明“1 个纯本地仓库、3 个有远端仓库”的配置不是缺陷，但“远端读取失败阻断全部仓库的本地提交”是产品缺陷。

## 推荐处理规则

1. 工作区列表、本机未提交差异和本地提交只依赖本地 Git 状态，不等待远端刷新成功。
2. 每个仓库独立返回远端刷新状态；一个仓库失败不能清空其他仓库和其他开发线。
3. 有远端仓库刷新失败时，仍允许查看和创建本地提交，只阻止该仓库的推送与依赖最新远端的目标分支合入。
4. 纯本地仓库不显示远端刷新错误，继续允许查看、提交和本地目标分支合入。

## 已确认处理规则

用户确认纯本地仓库采用本地分支模式：

- 来源和目标都使用真实本地命名分支。
- 不执行远端拉取。
- 不执行远端推送。
- 缺少 remote 不阻止查看未提交变化、创建本地提交或本地目标分支合入。

用户进一步确认已经配置 remote、但当前远端认证或网络失败的仓库仍允许本地查看与提交；只阻止该仓库的远端拉取、远端推送和依赖最新远端的合入。

## 最终确认范围

本轮只修复远端状态把本地提交错误阻断的问题：

- 纯本地仓库使用本地分支，跳过远端拉取和推送。
- 已配置远端但刷新失败的仓库继续允许本地查看和本地提交，只禁用远端动作。
- 单个仓库远端失败时，其他仓库和其他开发线仍必须正常显示。

本轮不改变多条开发线的默认选中策略，不自动提交 CSS 业务代码，不修复用户 GitLab SSH 凭据。

优点：不再让网络或 SSH 凭据故障扩大成本地提交故障；多仓任务可以逐仓处理；未提交代码始终可见。

缺点：界面需要同时表达“本地操作可用、远端操作受阻”，状态比全局失败更复杂；远端失败仓库完成本地提交后仍需修复 SSH 凭据，才能推送或进行远端权威合入。

## 安全边界

- 全程没有对 CSS 业务仓库执行 `add`、`commit`、`push`、`merge`、`stash` 或 worktree 回收。
- 未提交代码必须原地保留；修复 Zeus 时不得借验收之名改写或提交用户业务代码。

## 实现结果

- 本地服务的任务工作区接口按真实仓库路径复用单次远端刷新，并把失败收敛为该仓库的 `remoteRefreshError`；一个仓库失败不再让整个接口失败。
- 纯本地仓库不执行远端刷新，目标分支继续来自本地命名分支。
- 远端刷新失败时不读取旧远端跟踪引用，目标分支列表保持为空，避免把缓存结果冒充最新状态。
- 本机审查、未提交差异和分支成果继续返回；本地提交按钮保持可用。
- 代码交付和独立提交弹窗明确显示“远端不可用，本地提交可用”，并禁用提交并推送、单独推送和远端合入。
