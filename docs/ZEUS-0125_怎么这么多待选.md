# ZEUS-0125 代码交付任务分支分组

## 任务信息

- 任务标题：怎么这么多待选？
- 任务类型：优化
- 现状：未提供
- 预期：代码交付中的待选项按当前分支分组。

## 现场结论

代码交付接口返回的是逐仓 `TaskWorkspace`。同一次任务推送在多仓项目中会为每个仓库保存一条工作区记录，因此一个任务分支可能对应多条记录。

当前界面把这些仓库工作区直接平铺在“任务分支”列表中，并用工作区条数作为任务分支数量。仓库名称、相对路径和任务分支又在每一项中重复展示，导致截图中的 11 条工作区记录看起来像 11 个独立任务分支。

## 实现规则

1. 第一层按工作区实时读取的当前分支分组；已回收、已交付等无法读取实时分支的记录回退到持久任务分支。
2. 分组标题展示分支名和组内仓库数量；“任务分支”标题旁只展示分支分组数量。
3. 组内继续逐仓展示仓库名称、必要的相对路径和真实状态，点击后仍只切换当前仓库工作区。
4. 代码交付和提交审查复用同一分支分组组件，避免两个入口再次出现不同结构。
5. 不修改接口、工作区记录、分支生命周期、提交、推送、合入或回收语义。

## 优缺点

优点：任务开发线一眼可见，分支数量不再被仓库数量夸大；多仓分支仍保留逐仓审查和交付所需的真实状态。

代价：多仓分支下仍需要选择具体仓库，因为不同仓库的差异、提交、远端和合入状态不能安全合并成一次操作。

## 验证范围

- 静态检查：`pnpm lint`、`pnpm typecheck`、`pnpm build`、`git diff --check`。
- 真实界面：代码交付弹窗中验证分支计数、分组、组内仓库切换、选中态、窄窗口滚动和控制台错误。
- 不新增或恢复单元测试、组件测试或 TDD 体系。
- 不执行 Git commit、push、merge、revert 或历史改写。

## 补充问题：CSS 项目被误报为没有 Git 仓库

### 现场证据与根因

- 正式数据中的 `css` 项目路径是 `/Users/david/cckg/tcapp/Back-End/css`，任务 `ZEUS-0043` 归属正确。
- 该目录当前实际包含 4 个 Git 根：`backend-java`、`dwt-miniapp`、`dwt-miniapp/miniprogram/packages/tc-design-weapp`、`frontend-miniapp-sdk`。
- 使用正式 Zeus 0.2.12 的任务推送能力接口复现后，接口返回的不是“没有仓库”，而是 `ZEUS_GIT_REMOTE_REFRESH_FAILED`：其中一个 GitLab `origin` 因 SSH 公钥认证失败而无法刷新。
- 服务端把逐仓远端刷新放在同一个 `Promise.all` 中，任一仓库失败就丢弃全部仓库能力；前端又把“能力为空”统一渲染为“没有 Git 仓库”，最终形成错误结论。

### 修复规则

1. Git 仓库发现与远端可用性分开表达；已经发现的仓库不能因远端失败而消失。
2. 远端刷新失败只记录在对应仓库，其他纯本地仓库和远端正常仓库继续返回。
3. 远端受阻仓库不展示本机缓存的旧远端分支，也不能创建 Worktree；修复网络或仓库凭据后重新读取能力。
4. 能力仍在加载或整体加载失败时，前端明确展示“正在扫描”或“检查未完成”，只有成功扫描且结果为空时才显示“没有 Git 仓库”。

### 优缺点

优点：界面如实展示已发现的 4 个仓库和具体受阻仓库，不再把认证问题误导成目录问题；同时保持远端最新基线门禁，不会使用旧缓存分支创建任务。

代价：多仓 Worktree 要求每个仓库都有明确来源，任一远端仓库受阻时创建按钮仍会禁用；用户需要先修复对应远端访问，不能靠切换文案绕过安全约束。
