# ZEUS-0128 这个后台创建太卡了，每次等半天

## 任务信息

- 任务类型：优化
- 现状：任务推送提交后，任务详情长时间显示“正在后台创建会话”，真实会话迟迟没有出现。
- 预期：不改变任务推送、工作区冻结、首轮执行和失败重试语义，减少创建链路中的重复等待。

## 诊断结论

截图对应的是任务推送后的后台创建状态。Renderer 已经在提交后立即关闭弹窗并保持当前页面可操作，等待发生在本机服务完成真实会话接收之前。

一次推送原先包含以下重复路径：

1. 打开推送弹窗时，完整读取模型、父任务上下文、仓库和远端分支快照。
2. 提交接口再次调用完整任务推送能力解析，其中包含仓库发现和远端刷新。
3. 提交接口随后调用任务环境解析，再次刷新远端并冻结所选来源提交，最后创建 app-server thread 和首轮 turn。

第二步只用于复验模型、账户、工作模式、附件和参数，并不参与最终工作区来源提交的冻结；它重复执行 Git 仓库扫描和远端刷新，是本次可安全移除的等待。

## 实现方案

提交接口改用轻量能力复验，只读取模型与运行能力；任务环境解析仍保留，并继续在创建 worktree 前刷新远端、校验用户选择的来源分支、冻结精确提交和处理失败回滚。

优点：

- 每次任务推送少做一次完整仓库发现和远端刷新，减少网络等待和本地 Git 扫描。
- 远端仍是创建 worktree 时的权威来源，没有使用弹窗阶段的旧分支快照冒充最新事实。
- 不改变幂等、附件受信根、工作区隔离、真实 thread/turn 创建和任务状态迁移边界。

代价：

- 如果用户只选择项目目录直接执行，本次优化主要减少能力复验开销；app-server 初始化和首轮启动仍需真实等待。
- 远端网络本身很慢时，创建仍可能等待一次必要的远端刷新；本任务不把网络失败降级成使用陈旧远端引用。

## 验收口径

- 提交接口不再调用包含 Git 仓库发现和远端刷新的完整任务推送能力解析。
- 任务工作区创建仍在提交阶段刷新远端并校验来源分支，失败时不创建半成品会话。
- Codex/Pi 模型能力校验、账户门禁、附件校验和父任务上下文校验保持有效。
- 执行 `pnpm lint`、`pnpm typecheck`、`pnpm build`；静态门禁不能替代真实 Provider 和 GUI 验收。
