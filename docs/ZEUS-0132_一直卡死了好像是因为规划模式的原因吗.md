## 结论

这不是计划工作模式本身卡死。

Codex 在 `2026-08-07 17:05:52` 已完成调研并发出三项 `request_user_input` 询问，正在等待用户选择。Zeus 没有及时消费并投影后续 Provider 事件，因此问题卡没有出现，界面继续沿用旧的“正在思考”状态。

直接根因是当前持久层使用 `sql.js`：每次 `db.save()` 都执行一次完整 `db.export()`，再用 `writeFile` 覆盖整个数据库文件。正式现场数据库的完整导出规模约为 `357 MiB`，而 Provider 的 reasoning、命令、工具结果和 Token 更新会产生高频事件；协调器又在几乎每个事件后等待一次完整保存，最终形成严重的写入放大和事件积压。

计划模式只影响本轮最终选择了“向用户提问”；即使换成普通模式，只要产生足够多的过程事件，同一持久化瓶颈仍会出现。

## 目标流程

`任务推送 -> 计划模式只读调研 -> 智能体发起 request_user_input -> Zeus 立即显示问题卡 -> 用户回答后同一轮继续`。

当前断点发生在“Provider 事件已产生”到“Zeus 持久化并广播问题卡”之间。

## 修复选项与取舍

### 方案一：先做持久化止血

对 `ZeusDatabase.save()` 增加单写者、脏标记合并、原子临时文件替换；普通流式事件按短时间窗口合并保存，询问、审批、轮次完成和错误等状态边界要求优先落盘并等待完成。

优点：改动范围较小，可以快速消除并发覆盖、半写文件和每事件完整导出的绝大部分重复开销；不需要立即迁移数据库驱动。

代价：`sql.js` 每次真正保存仍需导出完整数据库。数据库继续增长后，单次保存仍会越来越慢，只是频率降低；这不是长期根治。

### 方案二：迁移到原生 SQLite

改用支持 WAL、事务和增量页写入的原生 SQLite 驱动，让每次事件只写变化数据，不再导出整库。

优点：从根本上消除数据库规模与每次事件保存成本线性绑定的问题；读取快照、崩溃恢复和并发写入语义也更符合桌面执行宿主的长期需要。

代价：需要处理现有 sql.js 数据迁移、原生模块打包、macOS 架构与签名、升级兼容和回滚；实施与验证范围明显更大。

### 建议

建议分两步：先实施方案一恢复可用性，并加入保存耗时、积压事件数和最近成功持久化时间的诊断指标；随后单独推进方案二，避免把一次缺陷修复扩大成不可控的存储迁移。

短期方案的关键不是只加“问题卡兜底”或延长“正在思考”超时。那只能掩盖状态，无法解决后续 reasoning、命令结果、完成事件和其他会话同样被积压的问题。

## 紧急修复实现

### 数据库单写者与原子替换

- `ZeusDatabase.save()` 使用保存修订号和单一保存循环，同一时刻只允许一个 `db.export()` 和磁盘写入。
- 写入期间到达的并发保存请求不再各自重复导出，而是合并为当前写入后的至多一次补写。
- 完整数据库先写入同目录、权限为 `0600` 的唯一临时文件；写完后通过 `rename` 原子替换正式数据库。
- 写入失败时清理本次临时文件，并保留原正式数据库，不再把半写文件暴露给读取方。

优点：立即消除并发整库覆盖和半写数据库窗口，大幅压缩重复导出次数。

代价：一次真实保存仍然需要完整导出 sql.js 数据库；本次只解决紧急性能与完整性风险，不冒充原生 SQLite 迁移已经完成。

### Provider 过程事件合并保存

- reasoning、流式正文、命令活动和 Token 等普通过程事件先更新内存并广播界面，再等待两秒安静窗口合并保存。
- 连续输出没有安静窗口时，最长十秒强制形成一次持久检查点，避免长任务一直只存在于内存。
- 带 Provider request ID 的询问与审批、`turn/started`、`turn/completed`、请求解决和计划实施确认立即冲刷此前积压并等待落盘。
- 执行宿主交接或最终关闭前等待事件链、队列派发和待保存状态全部落盘。

优点：界面事件不再被数百兆整库写入逐条阻塞，问题卡和完成状态仍保持高优先级持久化。

代价：普通过程事件在极端崩溃时最多可能丢失最近十秒的投影；Provider 原生 thread 仍是恢复事实源，关键交互和轮次边界不使用该延迟。
