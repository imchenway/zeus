# ZEUS-0133 这个磁盘写入量，简直离谱

## 任务信息

- 类型：缺陷
- 当前阶段：磁盘写放大修复已实现并完成静态、隔离运行与测试包验证
- 用户截图：macOS 活动监视器中 Zeus 生命周期累计写入 `7.61 TB`、读取 `21.5 MB`
- 本阶段边界：已实现原生 SQLite 与 Provider 回执改造；未读取或修改正式数据库，目录治理继续排除在本任务之外

## 现状还原

用户没有提供文字版现状、预期和复现步骤。根据截图、当前正式应用和当前源码，现状可以稳定还原为：

1. Zeus 在持续会话期间频繁持久化 provider 流式事件。
2. 当前业务库使用 `sql.js` 常驻内存；`db.save()` 会执行 `db.export()`，生成整个数据库的新文件，再通过 `rename` 替换正式库。
3. 数据库越大，每次很小的会话变化造成的物理写入越大。
4. 活动监视器展示的是进程生命周期累计写入量，不等于磁盘当前被 7.61 TB 文件占满，但仍代表真实、不可接受的 SSD 写入放大。

## 建议预期

- 普通会话增量、状态变化和审计追加只写变化的数据页，不得重复写完整业务库。
- 长时间连续输出时，磁盘写入量与本次新增内容和必要索引更新近似相关，不再与数据库历史总大小相乘。
- 保留现有本机事实、崩溃恢复、单写入者和原子性边界，不以扩大数据丢失窗口换取表面写入下降。
- 历史 `zeus.db` 原地兼容，不删除任务、会话、图谱、日志或审计数据。

## 现场证据

2026-08-07 对当前正式数据目录执行只读统计：

| --- | ---: |
| `/Users/david/.zeus` 当前占用 | `2.7 GB` |
| `zeus.db` 当前大小 | 约 `380 MB` |
| `conversation_items` 表物理大小 | 约 `200.7 MB` |
| `project_nodes` 表物理大小 | 约 `54.7 MB` |
| `code_symbols` 表物理大小 | 约 `48.3 MB` |
| `project_edges` 表物理大小 | 约 `24.8 MB` |
| `graph_views` 表物理大小 | 约 `7.1 MB` |
| 会话条目数量 | 约 `2.65 万` |
| 图谱节点数量 | 约 `7.65 万` |
| 图谱边数量 | 约 `13.56 万` |

数据库不是异常膨胀到 7.61 TB；真正的问题是约 380 MB 的同一份数据库被反复完整改写。

### 代码链路

`packages/storage/src/index.ts` 中的 `ZeusDatabase.save()` 最终执行：

1. `this.db.export()` 导出完整内存数据库；
2. `writeFile(temporaryPath, 完整数据库)`；
3. `rename(temporaryPath, this.filePath)` 替换正式库。

本机服务中存在大量 `db.save()` 调用。仅 `packages/local-server/src` 中的直接调用约 `185` 处，Runtime 日志、会话事件、任务、设置和图谱都共用这条整库导出路径。

当前源码已经在 `ZEUS-0132` 中给 Codex provider 过程事件加入合并保存：安静 `2` 秒保存一次，持续输出最长 `10` 秒保存一次，轮次和询问边界立即保存。这个改动避免并发整库导出互相踩踏，但没有改变“每次保存重写整个数据库”的根本成本。

### 正式运行复验

对正在运行的正式 Zeus 只读观察三秒：

| 时刻 | inode | 文件大小 |
| --- | ---: | ---: |
| 开始 | `68917734` | `380334080` 字节 |
| 三秒后 | `68918727` | `380366848` 字节 |

inode 和文件出生时间都发生变化，证明期间不是增量修改原文件，而是重新生成并替换了约 380 MB 的完整数据库。业务内容只增长约 32 KB，却产生一次约 380 MB 的主库写入。

### 数量级对账

按当前约 `380366848` 字节的数据库计算：

- `7.61 TB ÷ 380366848 B ≈ 20007` 次完整数据库写入；
- 每 `2` 秒一次完整写入，理论约 `684.7 GB/小时`；
- 每 `10` 秒一次完整写入，理论约 `136.9 GB/小时`。

实际数据库会随使用逐渐增长，活动监视器还可能聚合 Electron 子进程写入，因此上述不是截图的精确历史反演；但数量级与截图完全一致，足以确认主因。

### 推荐方案隔离写入量实验

为了避免只做理论估算，使用当前正式应用自带的 `Electron 42.4.0 / Node 24.16.0` 在 `/tmp` 创建临时数据库，启用 `node:sqlite + WAL + synchronous=NORMAL`，完成实验后删除临时文件。实验没有读取或修改正式业务库。

估算物理写入量按“WAL 文件字节数 + checkpoint 回写页数 × 4096 字节”计算，不包含少量文件系统元数据和设备层写放大，因此用于比较方案数量级，不冒充硬件精确计量。

| 场景 | WAL | checkpoint 页 | 估算物理写入 |
| --- | ---: | ---: | ---: |
| 单次提交追加约 32 KB | `41,232 B` | `10` | `82,192 B` |
| 100 个流式片段合并为一次事务，总计约 32 KB | `70,072 B` | `17` | `139,704 B` |
| 100 个流式片段分别自动提交，总计约 32 KB | `2,603,872 B` | `632` | `5,192,544 B` |

与当前约 `380,366,848 B` 的一次整库替换相比：

- 推荐的“增量 SQLite + 流式事务合并”约下降 `2,700～4,600` 倍；
- 如果只切换 SQLite、却让每个流式片段单独提交，实验中只下降约 `73` 倍；
- 因此原生 SQLite、事件事务合并和去重大 JSON 收口必须作为同一个修复边界，不能只替换驱动。

按当前保存节奏换算，持续输出时 Zeus 业务库可从理论 `136.9～684.7 GB/小时` 降到大致几十至数百 MB/小时。真实总量还取决于命令输出、文件变化、浏览器缓存和 Codex 子进程写入；这些正常业务写入不会被承诺为零。

若把截图中的 `7.61 TB` 全部粗略按当前整库写入主因等比例换算，同等业务负载下主库部分预计降到约 `1.7～2.8 GB`。考虑真实表索引、事务边界和其他子进程写入，产品验收应采用“低个位数至十余 GB，而不是 TB”作为保守区间，并以隔离 `Zeus Test.app` 的真实长会话测量为最终结论。

## 根因

### 主因：`sql.js` 的整库快照持久化不适合持续事件流

`sql.js` 在当前架构中是内存数据库。任何一次 durable save 都必须导出整个数据库文件。该模型在小型配置库中可接受，但 Zeus 已同时保存长会话、Runtime、图谱和审计，主库达到数百 MB 后，写放大会随历史体积线性恶化。

这里的“整库保存”不是业务规则，而是当前存储实现的技术结果：

1. Repository 的写操作先修改 `sql.js` 内存数据库，不直接修改磁盘上的 `zeus.db`；
2. 为了让变化在应用重启后仍然存在，`save()` 调用 `db.export()` 得到一份完整 SQLite 镜像；
3. 为了避免写到一半崩溃破坏正式库，完整镜像先写临时文件，再通过同目录 `rename` 原子替换正式库。

早期选择纯 WASM `sql.js` 的优点是无需维护原生模块、打包简单、提供同步数据库接口；代价是文件持久化没有普通文件型 SQLite 的增量页写入和 WAL。随着 Zeus 历史事实增长到数百 MB，这个代价已经从实现细节升级为严重产品缺陷。

### 放大器：高频过程事件共享同一保存边界

会话文字增量、推理摘要、命令输出、工具进度、Token 用量等都会更新持久事实。即使已有 2 秒 / 10 秒合并，只要会话持续活跃，就会反复触发整库导出。

### 次级热点：去重状态使用单个大 JSON

`codex.native.processed_provider_events` 当前把最近一万条事件身份保存为一个设置 JSON，正式库中该值约 `1.88 MB`。协调器每处理一个 provider 事件都会重建并更新这个 JSON。迁移到增量 SQLite 后，如果不同时改造该结构，仍会造成明显写放大，只是量级低于当前整库重写。

### 非主因

- Electron Cache 当前约 `774 MB`，会占空间，但不能解释业务库 inode 在三秒内整体替换。
- Codex 自身 SQLite WAL、浏览器缓存和 Runtime 文本日志会产生正常增量写入，但都不是截图中 TB 级放大的主要来源。
- 单纯清理历史缓存能暂时减小每次整库导出的基数，不能阻止它再次随使用增长。

### 图谱在问题中的真实角色

本缺陷不是“全部由更新代码图谱导致”。图谱主表合计约 `136 MB`，确实显著放大每次整库导出的成本，但当前最大的单表是约 `201 MB` 的 `conversation_items`。正式运行复验期间没有执行图谱扫描，只进行普通会话和只读诊断，业务库仍在三秒内被完整替换。

因此需要区分两个因素：

- 写入触发器：会话流式事件、Runtime、任务、设置、图谱等任何共用 `db.save()` 的业务变化；
- 写入放大器：包含历史会话和图谱在内的整个 `zeus.db` 当前总大小。

即使清空全部可重建图谱缓存，剩余两百多 MB 业务库仍会被会话事件反复完整改写。只处理图谱无法根治 TB 级累计写入。

## 方案比较

### 方案一：改用 Electron 内置原生 SQLite 增量落盘（推荐）

使用 `node:sqlite` 打开现有 `zeus.db`，启用 WAL，保留当前同步 Repository 接口和单执行宿主写入者；`save()` 退化为兼容性持久屏障，不再导出完整文件。同时把 provider 事件去重从大 JSON 改为紧凑的持久事件账本或按 generation 保存高水位。

已验证当前正式运行环境 `Electron 42.4.0 / Node 24.16.0` 提供 `node:sqlite.DatabaseSync`，不需要增加第三方原生模块；现有 `zeus.db` 本身是标准 SQLite 文件格式。

优点：从机制上消除整库重写；历史库可以原地读取；无需维护第三方原生二进制；也能显著降低执行宿主内存中的数据库副本成本。

缺点：存储适配层改动面较大；需要处理 `sql.js` 与 `node:sqlite` statement 返回接口差异、关闭时 checkpoint、启动时完整性检查和异常回退；必须做真实历史库副本升级验证。

### 方案二：拆分大表并继续使用 `sql.js`

把图谱缓存、会话条目或 Runtime 日志拆成独立数据库，使高频库体积变小，再分别控制保存节奏。

优点：可保留大部分现有 `sql.js` 适配代码；可以分阶段迁移。

缺点：每个子库仍然整库重写；跨库一致性和备份恢复更复杂；会话库还会继续增长，问题只是延后；长期维护成本高于直接采用增量 SQLite。

### 方案三：只继续加大防抖或只在轮次结束保存

优点：代码改动最小，能快速降低写入次数。

缺点：仍然每次重写完整数据库；会扩大崩溃后的数据丢失窗口；询问、审批、长命令和持续会话仍需中途检查点；数据库继续增长后问题会再次出现。不建议作为正式修复。

## 推荐实施边界

如果选择方案一，建议一次完成以下边界，避免只把 TB 级问题降成 GB 级问题：

1. `@zeus/storage` 从 `sql.js` 切换到 `node:sqlite`，沿用现有标准 SQLite 文件。
2. 启用 WAL、外键、合理的 busy timeout 和桌面应用适用的同步级别；执行宿主继续保持唯一写入者。
3. 保留 `save(): Promise<void>` 作为调用兼容层，但禁止完整导出；增加显式 `close()` 和受控 checkpoint。
4. 把一万条 provider 事件身份的大 JSON 改成带精确唯一键的紧凑事件回执表，设置表不再每个事件重写 1.88 MB；不使用会丢失乱序证据的单值高水位。
5. 对高频流式条目使用事务合并，轮次、询问、审批等关键边界立即提交；不降低现有恢复语义。
6. 首次打开历史库前做只读完整性检查；失败时拒绝启动写入并保留可恢复原库，不静默新建空库覆盖历史事实。
7. 不在迁移时自动 `VACUUM` 正式库，避免为了“优化”再制造一次大写入；空间整理另设显式维护动作。
8. 验收记录主库、WAL 和进程累计写入增量，使用长回答、长命令输出、询问等待、重启恢复和历史大库副本覆盖真实场景。

## 推荐方案的风险与缺点

### 风险一：持久边界会从“内存快照”变成“磁盘事务”

当前 Repository 先修改内存数据库，只有 `save()` 完成后才形成磁盘事实。原生 SQLite 默认会让每条未包裹事务的语句自动提交。如果只是替换驱动并把 `save()` 改成空操作，多语句业务流程可能在进程崩溃时留下部分结果，高频流式事件也可能退化为逐条 WAL 写入。

控制方式：不能机械替换驱动；需要把任务、会话、询问、审批、幂等响应等业务操作明确放入短事务，把高频过程事件放入受控批次，关键边界立即提交。现有 `save()` 只作为兼容屏障，不能继续承担模糊事务语义。

### 风险二：WAL 增加了旁路文件和旧版本回退边界

WAL 模式运行时，最新数据可能位于 `zeus.db-wal`，不能再把单独复制 `zeus.db` 当作完整热备份。旧版 `sql.js` 只读取主文件，不理解当前运行中的 WAL 状态；若新执行宿主已经产生未 checkpoint 数据后再强行启动旧版，旧版可能看到陈旧快照。

控制方式：执行宿主交接和正常关闭必须显式 checkpoint 并关闭数据库；升级回退必须以执行宿主协议和数据库格式代际为门禁；热备份使用 SQLite 一致性备份能力或受控 checkpoint 后再复制，不能只复制一个正在使用的主文件。

### 风险三：两个驱动的参数和结果接口存在细节差异

`sql.js` 的 `run / prepare / step / getAsObject / free` 与 `node:sqlite` 的 statement API 不同；整数、BLOB、`undefined / null`、命名参数、返回列名和异常类型也需要统一。Zeus 的大量 Repository 共用一层 `ZeusDatabase`，适配错误可能表现为字段值变化，而不是立即报错。

控制方式：在 `ZeusDatabase` 内建立窄适配层，业务 Repository 不直接依赖 `node:sqlite`；使用正式历史库副本对迁移前后表名、记录数、关键状态投影和 `quick_check` 做对账。

### 风险四：事件去重账本迁移错误会造成重复或漏事件

当前一万条 provider 事件身份保存在一个约 `1.88 MB` 的 JSON 中。若为了省事只保存单一 sequence 高水位，跨 generation 或乱序事件可能被错误跳过；若迁移时直接丢弃旧集合，重连后可能重复处理历史事件。

控制方式：优先迁移为带唯一键的有界事件账本，保留 generation、sequence 和必要身份字段，并按确认安全的代际清理；不使用无法表达乱序事实的单值高水位替代完整去重语义。

### 风险五：同步文件型 SQLite 仍可能阻塞执行宿主

`DatabaseSync` 的磁盘事务、checkpoint 和大型迁移会同步占用执行宿主事件循环。虽然执行宿主已独立于界面，长事务仍可能延迟本机 API 和 provider 事件处理。

控制方式：事务保持短小；大型图谱写入分批；checkpoint 按 WAL 大小和空闲边界控制，不在每个 `save()` 调用后强制执行；用真实大库和长会话测量延迟。

### 缺点一：改动面大于继续防抖

存储适配、关闭生命周期、升级回退、备份语义、事件去重和高频事务边界都需要同步修改。短期开发与验收成本明显高于“把两秒改成十秒”。

### 缺点二：现有数据库占用不会自动缩小

切换增量写入会立即降低后续写入量，但当前约 `380 MB` 的主库仍会保留；WAL 运行时还会出现受控的临时旁路文件。本任务不应自动对正式库执行 `VACUUM`，以免迁移首日再次制造大写入和额外故障面。

### 缺点三：运行环境版本成为明确依赖

当前正式环境已验证 `Electron 42.4.0 / Node 24.16.0` 提供 `node:sqlite.DatabaseSync`，仓库也要求 Node 24 及以上。以后升级 Electron 或 Node 时，需要把内置 SQLite 可用性和行为纳入发布门禁；不能再把存储层当成完全独立的 WASM 包。

## 当初为什么选择当前方案

### 仓库可以确认的事实

1. `sql.js` 和整库 `db.export()` 保存方式在 2026-06-16 的首次开源提交 `f1e9ab2` 中已经存在。
2. 当时 `save()` 只有 `writeFile(filePath, Buffer.from(db.export()))`，没有当前的临时文件原子替换、并发保存串行化或过程事件合并。
3. 首次提交已经使用 Electron 42、Node 24，因此仓库证据不支持“当时运行环境没有原生 SQLite”这一说法。
4. Codex 原生连续会话、长任务执行宿主、流式 provider 事件和当前规模的历史数据库都是后续逐步加入的；初始方案没有面对今天的持续高频写入模型。
5. 仓库中没有发现解释“为什么选择 sql.js 而不是文件型 SQLite”的 ADR、设计记录或代码注释。

### 基于实现演进的合理推断

在没有原始决策记录的前提下，最合理的解释是初期优先选择了实现简单：

- 纯 JavaScript / WASM 依赖，避免额外的 SQLite 驱动适配和 Electron 打包处理；
- 同步内存接口容易接入大量 Repository，也方便用单个文件表达本地优先数据；
- 在数据库较小、写入以项目、任务和扫描边界为主时，整库导出的成本不明显；
- 先完成产品闭环，再处理持久化工程化问题。

这些优点在早期有现实价值，但它们不构成今天继续保留该方案的理由。随着会话流式事件和历史图谱、审计数据进入同一主库，工作负载已经从“小型本机快照”变成“持续增长的事件数据库”，原方案的适用前提已经失效。

## Codex 的持久化选型对照

### 官方公开边界

Codex App Server 官方文档明确说明：

1. 持久会话日志是落盘 JSONL；归档操作会把该 JSONL 移入归档目录。
2. `thread/list` 默认会结合状态数据库和 JSONL 会话日志工作；`useStateDbOnly` 才会禁止扫描 JSONL 修复元数据。
3. 回滚并不重写整个历史，而是在 rollout 日志中持久化回滚标记。
4. App Server 的流式协议把消息和事件作为独立增量传递，而不是反复传输整个会话快照。

参考：

- https://developers.openai.com/codex/app-server/

官方文档没有公开 Codex 桌面端或云端全部内部数据库实现，因此不能把本机观察外推为 OpenAI 服务端架构。以下结论只代表当前 Zeus 隔离运行目录中的 Codex 实例。

### 本机只读核对

当前 `/Users/david/.zeus/agent-runtimes/codex` 可确认：

- `sessions` 下有 30 个按日期和线程拆分的 JSONL 文件，总计约 `54 MB`；
- 查询型数据拆为 `state_5.sqlite`、`logs_2.sqlite`、`memories_1.sqlite`、`goals_1.sqlite`；
- 四个 SQLite 均为 WAL 模式，主库、`-wal` 和 `-shm` 按 SQLite 标准生命周期存在；
- 一次新事件使当前 rollout JSONL 在 inode 不变的情况下从 `7,751,891` 字节增长到 `7,755,878` 字节，增量约 `4 KB`，没有重写已有会话历史；
- SQLite 文件名带代际数字，且内部存在 `_sqlx_migrations`。这说明当前实例对不同用途、不同结构代际进行了显式隔离；但具体兼容和回退算法未由公开文档完整说明。

### 它如何降低本任务讨论的风险

| 风险 | Codex 当前做法 | 带来的效果 | 相应代价 |
| --- | --- | --- | --- |
| 高频事件导致整库重写 | 会话使用按线程拆分的 JSONL 增量日志 | 写入量主要随新增事件增长，不随全部历史增长 | JSONL 不适合复杂关联查询，需要索引或状态库辅助 |
| 一个大库同时承载事实、索引、日志和缓存 | 状态、日志、记忆、目标分库存储 | 单个热点写入不会牵连全部数据，故障和迁移边界更小 | 跨存储一致性、清理和备份流程更复杂 |
| 崩溃导致多步更新只有部分落盘 | 查询型数据使用 SQLite 事务和 WAL；历史使用顺序日志 | SQLite 负责原子提交，日志把影响范围收窄到尾部增量 | 必须正确管理 WAL、checkpoint、关闭和尾部异常 |
| 索引损坏拖累原始历史 | 状态库可由 JSONL 扫描并修复元数据 | 原始会话日志与可重建索引分层，索引不是唯一事实来源 | 启动或修复扫描会产生额外时间成本 |
| 结构升级和回退互相污染 | 本机按用途、代际使用不同数据库名并记录迁移 | 升级边界更显式，避免所有数据绑在一个结构上 | 会增加旧代际清理和磁盘占用治理成本 |

Codex 并没有消除所有风险。它仍会写 JSONL、WAL、运行日志和缓存；WAL 仍需 checkpoint，JSONL 仍需归档或压缩，分库也会带来一致性成本。关键差别是其写入单位通常是“新增的一条事件或少量数据库页”，而 Zeus 当前是“任何变化都重新输出整个约 `380 MB` 数据库”。

## 最佳方案审查结论

### 最终选择

本缺陷最合适的根治方案是：

> 主业务库原地切换为 Electron 内置 `node:sqlite`，启用 WAL；用“首次修改开启事务、`save()` 提交事务”的兼容层保留现有持久边界；把 Provider 去重集合改成结构化事件回执表。当前不新增 Zeus 会话 JSONL，也不在本次拆分图谱库或外置大字段。

这不是改动最少的方案，但它在写入量、数据一致性、历史兼容和实施风险之间最均衡。

### 为什么不直接照搬 Codex 的 JSONL

Codex 和 Pi 已经各自维护原生会话文件；Zeus 的 `conversation_items` 不是单纯的原始事件日志，而是与轮次、提交、询问、审批、资源授权、变更撤销和 UI 顺序关联的业务投影。再新增一套 Zeus 原始 JSONL 会造成：

- 同一会话同时存在 Provider 原始记录、Zeus JSONL 和 Zeus SQLite 投影三份事实；
- 数据库提交成功但 JSONL 失败，或反向失败时需要跨文件补偿；
- 归档、删除、敏感回答和附件授权要同时清理多处；
- Pi 与 Codex 的恢复能力不同，难以形成统一且可信的重放协议。

因此应学习 Codex 的“增量写入”原则，而不是复制其存储形态。

### 原生会话文件的归属决策

保留 Codex、Pi 各自的原生会话文件，Zeus 不创建自己的完整会话 JSONL 来替换它们，也不直接改写 Provider 文件。两层事实的职责必须明确：

- Provider 原生会话是模型上下文、原始工具事件和 Provider 恢复协议的事实源；格式、归档、续聊和兼容由对应 Runtime 适配器负责。
- Zeus SQLite 是项目、任务绑定、提交队列、询问、审批、附件授权、变更集、未读状态和统一 UI 投影的事实源。

Zeus 只保存受控定位信息，例如 `agent_kind`、`native_session_id`、`native_session_path` 和已确认的 Provider 版本；路径必须重新解析到受信任的 Agent Home，不能把历史绝对路径当成永久授权。

原生文件缺失、移动或格式变化时：

1. 优先通过 Provider 的 `thread/read`、`thread/resume`、归档或对应 Pi Runtime 接口按 session id 重新定位，不自行猜测路径。
2. 无法恢复时保留 Zeus 业务投影可读，并把会话标记为“Provider 历史不可用”；不得静默生成空会话覆盖原身份。
3. Zeus 的归档、恢复和删除应调用 Provider 正式接口，再更新本地投影；不得直接移动或删除 Provider JSONL。
4. 完整备份或迁移若需要带走 Provider 历史，应生成带清单和摘要的受控导出包，包含一致性数据库快照和经过授权的原生会话文件副本；运行中的散落文件复制不能冒充完整备份。
5. 原生日志可能包含命令输出、工具结果和本机路径，只允许最小权限落盘，不直接作为 Web 静态文件暴露；导出和诊断必须继续执行脱敏与路径授权检查。

保留原生文件的缺点是备份范围分散、依赖 Provider 格式和生命周期；上述定位接口、状态降级和受控导出用于收口这些风险。替换为 Zeus JSONL 虽能表面统一格式，却会丢失 Provider 专有语义，并把格式升级、续聊兼容、归档和删除责任全部转移给 Zeus，综合风险更高。

### 为什么本次不拆图谱库

当前图谱相关表约占 `136 MB`，确实很大；但它们不是持续会话写入的触发源。换成原生 SQLite 后，普通会话提交不会再重写这些页，图谱体积不再放大无关写入。

同时，当前任务完成会同步回写 `project_nodes.metadata_json` 并记录 `graph.node.writeback` 任务事件。如果现在拆库，会把一个现有原子流程改成跨库最终一致，新增“任务已完成但图谱未回写”的故障状态。这个代价对本缺陷没有必要。

图谱拆库可作为后续容量治理候选，但前提是先把任务回写改造成可重放投影，并用真实 WAL 指标证明图谱扫描仍影响业务库。不能为了减小文件表面体积，在根治写入放大的同时引入跨库一致性问题。

### 为什么不能只替换驱动

当前 Provider 流式事件会立即执行 SQL，只是 `save()` 在安静 `2` 秒或最长 `10` 秒时才导出。若替换为原生 SQLite 后让每条 SQL 自动提交，现有防抖将失效，尤其 `commandExecution.presentation.liveText` 会反复覆盖最多 `200 KB` 的 JSON 行。

使用正式 Electron 运行时、WAL、`synchronous=FULL` 做同一行增长到 `200 KB` 的隔离实验：

| 100 次更新方式 | WAL 与 checkpoint 估算写入 |
| --- | ---: |
| 同一事务批量提交 | `829,848 B` |
| 每次更新自动提交 | `22,980,184 B` |

自动提交仍会额外放大约 `27.7` 倍。因此“保留 `save()` 持久边界”是根治方案的组成部分，不是兼容性装饰。

### 存储契约

1. `ZeusDatabase` 直接打开现有标准 SQLite 文件，不再读入 WASM 内存，也不再 `export()`、写临时整库或 rename。
2. 首次发生修改时开启 `BEGIN IMMEDIATE`；同一连接的查询仍能看到未提交修改。
3. `save()` 提交当前事务并等待提交完成；并发 `save()` 继续按 revision 合并。
4. `transaction()` 在待提交事务内使用 SAVEPOINT，替换仓库中三处手写 `BEGIN / COMMIT / ROLLBACK`，保证嵌套边界明确。
5. 启动迁移使用独立事务，在本地服务开始监听前完成；迁移失败整体回滚并拒绝启动。
6. Provider 过程事件继续使用现有 `2` 秒安静窗口和 `10` 秒最长窗口；询问、审批、提交、轮次开始/结束等边界立即 `save()`。
7. Runtime 原始 chunk 文件继续即时追加；其 SQLite 日志投影改用同一受控批量提交，不再每个 chunk 强制提交。
8. 正常关闭顺序为：停止接收新写入、排空 Provider 链和 Runtime 写入、`save()`、受控 checkpoint、关闭数据库。

### SQLite 运行参数

- `journal_mode=WAL`：只追加变化页，允许读写并行。
- `synchronous=FULL`：优先保证断电后的已提交事实；高频过程写已被批量事务吸收，不依赖降低同步级别换性能。
- `foreign_keys=ON`：后续新增外键时默认生效。
- `busy_timeout=5000`：为 checkpoint、诊断读取和短暂文件占用留出可控等待。
- `wal_autocheckpoint=1000`：约每 `4 MB` WAL 尝试被动 checkpoint，不在每次 `save()` 后强制刷回主库。

运行中只做被动 checkpoint；正常关闭可做截断 checkpoint。checkpoint 失败不能删除 WAL，也不能把单独的 `zeus.db` 宣称为完整热备份。

### Provider 事件去重

新增结构化事件回执表，以 generation、sequence 和现有身份字段形成唯一约束；业务投影和回执必须在同一提交边界落盘。迁移时解析当前约 `1.89 MB` 的 `codex.native.processed_provider_events`，成功对账后才删除旧设置项。

内存只保留当前 generation 的有界热集合；当前代码只在写回设置时截取一万条，但运行中的 `Set` 本身持续增长，这一问题应同时修正。不能简化成单一 sequence 高水位，因为 generation 变化、乱序或身份冲突需要保留精确证据。

### 启动、失败和回退

1. 取得现有执行宿主单写锁后，先执行只读 `quick_check`；任何打开或读取异常都失败关闭，禁止当前 `catch` 后静默创建空库的行为。
2. 首次切换前检查可用空间，并在宿主静止时保留一次迁移前备份；这会产生约一个主库大小的一次性写入，但属于明确、可恢复的升级成本。
3. 提交因磁盘满或 I/O 失败时，存储进入只读故障态：拒绝新的状态变更，保留当前事务以便诊断或重试，不继续对 Provider 声称业务状态已经持久化。
4. 正常降级必须使用受控 checkpoint 后的数据库；异常崩溃后若需退回旧版，应恢复迁移前备份，不能让旧 `sql.js` 直接忽略遗留 WAL。
5. 不自动执行 `VACUUM`，现有约 `368 MB` 主库不会因为驱动切换立即缩小。

### 暂不做的优化

- 不新增 Zeus 会话 JSONL，避免三份会话事实和跨文件补偿。
- 不立即把大命令输出或 MCP 结果外置，避免数据库与文件的原子性、权限和清理问题。
- 不立即拆图谱库，先让增量 SQLite 消除无关页放大，再用指标决定。
- 不只增加防抖时间，因为这会扩大数据丢失窗口且无法消除整库导出。

当前 `conversation_items.payload_json` 约 `157 MB`，其中命令输出约 `104 MB`、MCP 结果约 `29 MB`。这些数据值得后续做投影精简，但它们在原生 SQLite 下不会再迫使每次业务保存重写全部历史；不应与本次存储引擎迁移绑成一次高风险数据搬家。

## 验收口径

- 使用隔离数据目录和正式历史库文件级副本启动 `Zeus Test.app`，不得写入当前正式 `/Users/david/.zeus/zeus.db`。
- 运行同等持续会话时，主库 inode 不再随每个持久检查点整体替换。
- 不再出现 `zeus.db.saving-*` 和整库 rename；业务仅增长少量文本时，磁盘写入不得再接近数据库总大小。
- 同一行累计增长到 `200 KB` 的 100 次流式更新必须在一个持久窗口内提交；主库与 WAL 估算写入控制在 `2 MB` 以内，禁止退化成逐事件自动提交。
- 强制退出后，已越过持久边界的轮次、询问、审批、队列和会话条目可以恢复。
- 覆盖长回答、长命令输出、MCP 大结果、询问等待、审批等待、轮次完成、执行宿主交接、强制退出和重启恢复。
- 迁移前后表数量、关键记录数量、Provider 去重回执数量和 `PRAGMA quick_check` 对账通过。
- 真实运行分别记录主库、WAL、checkpoint 和进程累计写入；静态构建结果不能替代磁盘写入验收。
- `pnpm lint`、`pnpm typecheck`、`pnpm build`、`pnpm package:mac` 通过；静态检查与构建成功不替代真实运行写入量验收。

## 当前结论

推荐按本节方案进入实现：原生 SQLite + WAL、保留 `save()` 提交语义、Provider 事件回执表、故障关闭和完整关闭生命周期。本任务不附带 JSONL、图谱拆库、大字段外置或自动空间整理。

### 核心问题一：一个根目录承载了五种完全不同的生命周期

当前代码把 `~/.zeus` 同时设置为 Electron 的 `userData`，又把业务数据库、附件、Agent Home、执行宿主、恢复快照和导入备份都从同一个 `userDataPath` 或 `dirname(dbPath)` 派生。结果是根层同时出现：

1. 必须永久保护的业务事实，例如 `zeus.db`；
2. 可重建缓存，例如 `Cache`、`GPUCache`；
3. Provider 自己管理的原生事实，例如 Codex JSONL 和状态库；
4. 有业务引用的恢复资产，例如 `turn-change-sets` 和附件；
5. 只应短期存在的锁、导入暂存、下载和迁移回退副本。

目录名没有声明“谁拥有、是否可重建、保留多久、如何验证引用、由谁清理”。因此用户看到的是一个杂乱目录，程序也无法提供可信的“一键清理”。

### 核心问题二：现有“清理缓存”名不副实

设置页数据分类中的“清理缓存”只把数据库内的 `code-index / graph-view / layout` 投影清空，然后调用 `db.save()`。它不会清理最大的 `Cache`，在当前 `sql.js` 架构下反而还会触发一次整库导出。

内置浏览器另有“清理浏览数据”，会同时清除网络缓存、Cookie、站点存储、认证缓存、站点授权、下载记录和浏览器评论。它不是单纯清缓存，可能让用户退出网站登录或失去站点授权。

优点是当前两个入口实现简单；缺点是产品名称与真实影响不一致，最大的默认会话缓存没有入口，用户也无法预估清理后会失去什么。

### 核心问题三：Codex 配置导入备份越过了配置边界

`codexConfigImportService` 把 `plugins` 当作一个整体配置项。导入时，只要目标 `plugins` 已存在，就把整个目录重命名到 `imports/codex/<事务>`，没有排除生成内容，也没有保留数量或到期策略。

当前一份约 `379 MiB` 的导入备份中：

- `plugins/.plugin-appserver` 约 `310 MiB`，主要是 Codex 和 code-mode-host 可执行文件；
- `plugins/cache` 约 `64.6 MiB`，主要是可重新安装的插件缓存；
- 真正的规则、提示词、技能和配置只占很小部分。

也就是说，“导入配置”实际备份了整套运行环境。优点是回滚时最保守；缺点是每次导入都可能复制数百 MiB，且把可重建二进制伪装成需要长期保存的用户配置。

最佳边界是：导入只处理 `config.toml`、`AGENTS.md`、规则、提示词、技能和可证明由用户维护的插件声明；`.plugin-appserver`、插件缓存、安装暂存和系统生成目录不进入配置导入与备份。没有正式声明文件时，宁可要求通过 Provider 插件管理能力重新安装，也不复制整棵运行目录。

### 核心问题四：附件先落盘，业务关联后建立，没有垃圾回收

任务选择、粘贴和物化附件时，Main 进程会立即把文件复制到 `task-attachments`，随后 Renderer 才创建或更新任务。用户取消创建、移除未保存附件、请求失败或窗口异常退出时，已经物化的文件没有对应回收动作。

当前 `task-attachments` 有 `137` 个顶层资源：

- `105` 个资源名能从任务 `source_context_json` 找到引用；
- `32` 个资源没有任何已持久任务引用；
- 这 `32` 个候选约占 `91.3 MiB`。

它们只能称为“无任务引用候选”，不能立即认定为垃圾：正式应用仍在运行，当前未保存草稿可能只在 Renderer 内存中持有路径。正确做法是为草稿附件建立租约和暂存区，而不是事后猜测。

会话附件目录当前只有约 `2.6 MiB`。其中 `14` 个文件名都能在会话历史中找到痕迹，但只有 `8` 个出现在当前结构化 submission/resource 字段，另外 `6` 个只存在于历史 payload 或正文。这个事实说明清理器必须兼容不同数据代际，不能只查最新资源表。

优点是当前“先复制”让预览和后续发送很直接；缺点是取消、失败和旧数据代际都会留下无法可靠判断的文件。

### 核心问题五：变更恢复资产没有统一迁移和保留规则

当前数据库有 `186` 个 `turn_change_sets`：

| 状态 | 数量 | 文件记录 |
| --- | ---: | ---: |
| `applied` | `47` | `159` |
| `capturing` | `102` | `0` |
| `conflicted` | `2` | `2` |
| `unavailable` | `34` | `535` |
| `undone` | `1` | `1` |

磁盘有 `84` 个变更集目录，全部能在数据库找到对应记录，没有无主目录。`102` 个 `capturing` 记录没有文件、也没有目录，只是未收敛的数据库状态；它们不占主要磁盘，但表明轮次结束或重启恢复时缺少终态收口。

不能按 `unavailable` 状态直接删除，因为这 `34` 个记录仍关联 `535` 个文件记录，可能保留部分可查看或可诊断数据。

更麻烦的是，`296` 个文件记录和 `2` 个 journal 记录仍保存旧数据根绝对路径。共 `565` 个不同旧引用在旧根和当前 `.zeus` 中都有对应文件，但当前 Undo/Reapply 实现直接读取数据库保存的绝对路径，不会自动重定向到新根。因此旧副本目前仍是活动依赖，当前副本又形成重复占用；在完成路径重绑定和摘要对账前，两边都不能整批删除。

### 核心问题六：Runtime 日志的“保留天数”目前只是设置值

当前 `sessions` 有 `43` 个 Runtime 会话目录和约 `4,613` 条日志。每条日志同时进入 `runtime_logs`、`terminal_events`，并写入单独 chunk、完整原始日志和标准化日志；绑定任务会话时还可能形成会话投影。

`logRetentionDays` 可以配置为 `1～365` 天，但代码中只发现校验、保存和展示，没有发现按该值删除到期日志。Runtime 会话“删除”只是给数据库记录写 `deleted_at`，不会同步删除日志行和磁盘目录。

优点是诊断材料充分，即使数据库异常也能人工读取文件；缺点是同一内容多份镜像、保留设置不生效，体积会随长期使用持续增长。

### 核心问题七：Provider Home 正在被多个进程共同使用

审查时，正式 Zeus 的 Codex app-server、当前 Codex/ChatGPT app-server，以及多个插件工作进程都打开了 `agent-runtimes/codex` 下的 SQLite、WAL、JSONL、锁文件或插件缓存。当前 `.tmp/plugins` 约 `40 MiB`，其中还有一个约 `11.4 MiB` 的 Git 临时 pack，但它属于 Codex 的安装现场，不应由 Zeus 在运行中自行删除。

这意味着即使退出 Zeus 界面，也不代表 Agent Home 已空闲。最佳规则是 Zeus 只展示 Provider 目录占用，并调用 Provider 提供的清理/重装能力；没有正式接口时只给诊断建议，不实现跨进程强删。

### 核心问题八：权限依赖根目录兜底，内部规则不一致

`~/.zeus` 根目录是 `0700`，当前机器上其他用户无法穿透，因此没有确认的直接越权暴露。但内部仍有明显不一致：

- 数据库和会话附件通常是 `0600`；
- 迁移前数据库备份和 `zeus.config.json` 是 `0644`；
- `task-attachments`、`sessions`、`command-scripts` 是 `0755`；
- 约 `95 MiB` 的任务附件文件保留了 group/world 可读位；
- 导入备份和 Runtime 会话中也有大量 `0644/0755` 文件。

在当前根目录保护下风险有限，但一旦用户复制单个备份、迁移子目录或打包导出，根目录的保护就不再存在。托管数据、备份和日志应统一使用文件 `0600`、目录 `0700`；可执行文件只增加必要的 owner execute 位，不继承来源文件的宽权限。

## 最佳目录与生命周期方案

### 设计原则

最好的方案不是先把现有目录“摆整齐”，而是先把路径所有权和清理规则变成代码契约，再迁移物理路径。否则只是换一套目录名，绝对路径、活动进程和无引用文件问题仍然存在。

建议把 Electron Profile 与 Zeus 数据根分离：

```text
~/.zeus/
  data/                 # zeus.db、业务配置、密钥
  artifacts/            # 任务/会话附件、变更恢复、Runtime 与命令产物
  agents/               # Codex、Pi 原生 Home；Provider 拥有
  backups/              # 数据库与配置导入备份，必须带清单和恢复说明
  cache/                 # 只放可重建内容，可按体积和时间回收
  runtime/               # 执行宿主、锁、更新事务和短期暂存
  profile/electron/      # Electron 默认 Profile、Cookie、Local Storage
  profile/browser/       # Zeus 内置浏览器 Profile
```

实现上增加唯一的 `ZeusDataLayout` 路径注册表。业务模块不能再自行调用 `join(userDataPath, ...)` 或 `join(dirname(dbPath), ...)`；每个路径必须声明：

- 所有者：Zeus、Electron、BrowserHost、Codex 或 Pi；
- 等级：核心事实、托管资产、备份、缓存、临时文件；
- 是否可重建；
- 引用来源和验证方法；
- 保留时间、体积上限和清理触发条件；
- 是否允许用户手动清理，以及清理的真实副作用。

Electron 的 `app.setPath('userData')` 指向 `profile/electron`，Zeus 业务数据改用独立 data root。这样 Chromium 自动生成的 `Cache`、Cookie、DIPS、Singleton 和 Storage 不再与 `zeus.db` 平铺在一起。

### 分类清理策略

1. 网络缓存：只清 HTTP cache，不碰 Cookie、站点存储和授权；退出对应会话或确认没有打开句柄后执行。设置体积上限和最近最少使用回收。
2. 浏览器站点数据：单独作为高影响操作，明确提示会退出登录、清除授权和本地站点数据。
3. 图谱投影：名称改为“重建代码图谱缓存”，说明它修改数据库事实投影，不与文件缓存混为一谈。
4. 配置导入备份：只备份用户控制的配置；每份备份写清单、摘要、来源版本和可恢复条目。默认保留最近一次成功导入前备份，旧备份需用户确认或在明确宽限期后回收。
5. 任务与会话附件：先写入 `runtime/staging/<draft-id>` 并建立草稿租约；任务或 submission 成功后再原子移动到托管目录并写业务引用。取消和失败只清理暂存区；过期租约至少保留 `24` 小时。
6. 托管附件垃圾回收：只处理“没有任务、submission、资源、历史兼容索引和活动租约引用”的文件；先生成预览清单并移动到隔离回收区，经过宽限期后再删除。
7. 变更恢复资产：保留到所属会话/任务按明确策略归档后；不能按 `unavailable` 等单一状态推断可删。空 `capturing` 记录在轮次结束或启动恢复时收敛为明确终态。
8. Runtime 日志：真正执行 `logRetentionDays`。收藏、活动、等待交互、与未完成任务关联的会话豁免；到期时同时处理数据库镜像和磁盘目录，并保留审计摘要。
9. Agent Home：Zeus 不删除 JSONL、Provider SQLite、插件运行包或临时安装现场；优先调用 Provider 清理接口。Provider 不支持时只展示占用和定位入口。
10. 数据库与迁移备份：始终有清单、创建原因、数据库摘要、完整性结果和恢复入口。自动清理不得删除唯一可用回滚点。

### 安全清理事务

任何正式清理必须采用“预览、隔离、复验、延迟删除”四步，而不是直接 `rm`：

1. 预览：计算候选大小、业务引用、活动租约、打开句柄和受影响能力；
2. 隔离：同一文件系统内原子移动到带事务 ID 的回收区，不立刻物理删除；
3. 复验：再次执行数据库引用对账、关键文件存在性和 `quick_check`，确认应用仍能恢复；
4. 延迟删除：宽限期结束后才清空回收区，操作写入本机审计日志。

优点是误判后可恢复，也能让用户看懂真正回收了什么；缺点是第一次清理不会立刻释放全部空间，并需要维护回收事务和恢复入口。

### 迁移顺序

建议把目录治理作为独立后续任务，不与本次 SQLite 引擎切换同时上线：

1. 先完成原生 SQLite + WAL，停止每次整理或清理都整库改写；
2. 引入 `ZeusDataLayout` 和生命周期清单，新产生的数据先写入新位置；
3. 应用、执行宿主和相关 Agent 全部退出后，对当前根与旧根做只读盘点、摘要和可用空间检查；
4. 先迁移并重绑定任务附件、会话附件和变更集引用，逐项校验大小、摘要、受信目录和数据库完整性；
5. 再迁移 Electron Profile、缓存、备份和短期运行文件；
6. 经过至少一个稳定使用窗口并确认旧根无数据库引用、无打开句柄、无唯一回滚资产后，才提供旧根回收预览。

不要先把当前 `2.71 GiB` 目录整体搬家：这会产生至少同量级的临时复制，并可能在磁盘空间紧张时失败。对同一文件系统优先使用原子移动，但任何数据库保存的绝对路径必须先通过受控迁移转换成稳定资源身份或新路径。

### 方案优缺点

优点：

- 用户能清楚区分业务数据、原生会话、恢复资产、备份和可重建缓存；
- 清理入口能准确说明可回收空间和副作用，不再把退出登录包装成“清缓存”；
- 附件、日志、导入备份和旧数据根都有可执行的生命周期，不会只增不减；
- Provider 原生 JSONL 与状态库继续由 Provider 管理，避免 Zeus 误删或复制出第三份事实；
- 目录迁移有摘要、引用和隔离回滚保护，不依赖肉眼判断文件名。

缺点：

- 路径注册、兼容读取、绝对路径重绑定和迁移恢复是一次较大的基础设施改造；
- 新旧目录并存和隔离宽限期会暂时增加占用，短期不会立即把磁盘降到最小；
- 缓存体积上限会带来重新下载，离线场景可能暂时无法使用未缓存插件或网页；
- Provider Home 没有正式清理接口时，Zeus 只能提示，不能承诺回收全部 Agent 空间；
- 清理器必须理解活动草稿、历史数据代际、Undo/Reapply 和旧根引用，开发与验收成本明显高于简单删除脚本。

### 审查结论

当前 `.zeus` 的确“乱且杂”，但主要问题不是目录名称不好看，而是职责、所有权和生命周期没有成为正式契约。当前约 `779 MiB` 默认网络缓存、`379 MiB` 过宽导入备份、`91.3 MiB` 无任务引用附件候选，以及旧根中的历史缓存和三代运行二进制，合计存在超过 `1 GiB` 的治理空间；但 `327 MiB` 变更集、Provider Home、迁移前数据库备份和仍被旧绝对路径引用的文件不能直接当垃圾。

本阶段最佳决策是：不在运行中的正式目录执行清理，不把目录大迁移并入 SQLite 修复；先完成存储引擎根治，再以独立任务实现路径注册、分层目录、暂存租约、引用感知回收、备份清单和旧根收口。

## 2026-08-08 实施记录

### 已落地内容

1. `@zeus/storage` 的业务数据库由 `sql.js` 内存库整库导出切换为 Node/Electron 自带的 `node:sqlite` 文件连接；schema 诊断功能仍保留独立的 `sql.js` 只读解析，不参与业务库持久化。
2. `ZeusDatabase.execute()` 在第一次写入时开启 `BEGIN IMMEDIATE`，现有 `save()` 成为提交当前批次的持久边界；高频 Provider 过程事件仍沿用两秒安静窗口与十秒最长窗口，不退化成每条事件自动提交。
3. `transaction()` 改为 SAVEPOINT，并替换提交队列重排、旧 Codex 线程导入中的手写事务控制，避免待提交批次内再次执行 `BEGIN`。
4. 启用 `journal_mode=WAL`、`synchronous=FULL`、`foreign_keys=ON`、`busy_timeout=5000`、`wal_autocheckpoint=1000` 和 SQLite 防御模式；正常关闭会排空写入、提交、执行截断 checkpoint 后关闭句柄。
5. 旧库首次切换前先只读执行 `quick_check` 和可用空间检查，再通过 SQLite 在线备份 API 写入临时备份、校验、原子改名为 `zeus.db.pre-native-sqlite.bak`；备份存在且有效时不会覆盖。任何打开、检查、备份或迁移失败都会拒绝启动，不再静默创建空库。
6. `codex.native.processed_provider_events` 已迁移为 `provider_event_receipts` 逐行回执；旧 JSON 成功解析、逐条写入并对账后才删除。业务投影与回执共享同一个待提交事务，当前 generation 只保留一万个内存热身份，已退出的 Provider generation 回执在新 generation 首次写入时收口。
7. Local Server 正常关闭和任意启动失败均会进入数据库关闭路径；正常关闭时 Provider 链、Runtime 持久任务和 Agent 管理器先排空，再关闭数据库，启动失败时回滚未提交变化。

### 当前方案的优缺点

优点：小变化只写变化页；保留现有 `save()` 原子边界和崩溃恢复口径；首次升级有稳定回滚点；去重回执不再反复重写约两兆字节 JSON；关闭和失败路径不会继续假装写入成功。

缺点：首次升级会额外写入约一个数据库大小的备份，并要求再保留 `64 MiB` 安全余量；WAL 运行时备份必须使用 SQLite 备份 API 或受控 checkpoint，不能只复制主文件；`synchronous=FULL` 比降低同步级别更重视持久性，单次提交延迟不会是最低；当前仍在使用中的 Provider generation 回执会随事件线性增长，只有 generation 退出后才清理；旧版本若要回退，必须恢复迁移前备份，不能直接忽略新 WAL 状态。
