# ZEUS-0136 Git 拉取和推送失败导致的问题

## 任务目标

把本地 Git 工作流与远端网络状态解耦。远端拉取或推送失败时，用户仍然可以选择本地来源分支、创建新会话、查看和提交代码、合入来源分支；失败只反馈在本次远端操作，不把任务工作区或代码交付流程改成失败状态。

## 现场根因

1. 打开“推送到新会话”时会逐仓自动执行 `git fetch`；真正创建会话时又执行一次。任一次远端失败都会让来源分支选择或会话创建受阻。
2. 任务 Git 工作区列表每次读取都会自动执行 `git fetch`，导致代码交付界面受网络和凭据影响，读取本地差异也被拖慢。
3. 代码交付把任务分支推送成功作为合入前置条件，最终动作又把本地合入和目标分支推送绑定在一次操作里。
4. 推送失败会把任务工作区持久状态改成 `failed`，扩大了单次远端错误的影响范围。

## 产品规则

### 任务推送与来源分支

- 打开任务推送弹窗和创建会话都不自动访问远端。
- 来源分支展示本机真实可用的本地分支和本机已经保存的远端跟踪分支，按“本地分支 / 远端名称”分组。
- 每个仓库提供明确的“刷新远端分支”按钮。只有用户点击后才执行 `git fetch`；失败时保留本地分支和已有选择，只显示本次错误。
- 来源分支可以选择任意展示出的分支。服务端提交时重新校验该引用仍然存在，不信任 Renderer 自报值。

优点：新建会话不再依赖网络；用户能明确决定何时承担远端等待和认证失败。

代价：用户没有手动刷新时，远端跟踪分支可能不是服务器最新状态；界面必须明确它是“本机已知”快照。

### 提交、合入与推送

- 提交代码只创建本地提交，不再接受“提交并推送”的组合动作。
- 代码交付只合入该任务开发线记录的来源分支，不再提供任意目标分支选择。
- 合入使用本地来源分支；来源最初来自远端且本地尚无同名分支时，使用任务创建时冻结的来源提交建立本地来源分支。
- 合入不要求任务分支已经推送，也不自动访问或写入远端。
- 合入完成后提供独立的“推送来源分支”按钮；这是可选操作，失败只在当前弹窗报错。
- 任务详情保留“推送代码”，其目标仍是任务分支。两个入口复用同一个非强制推送与远端 SHA 校验底层，但界面必须明确展示不同目标，不能让一个按钮静默换分支。

优点：本地提交、本地合入和远端同步职责清楚；网络故障不再卡住代码处置。

代价：本地已经合入不等于远端已经同步；用户需要主动完成可选推送，并留意按钮显示的目标分支。

## 安全边界

- 不使用 force push，不自动 rebase，不删除远端分支。
- 推送前刷新指定远端并检查非快进风险；推送后读取远端 SHA，必须与本次本地提交一致。
- 来源引用、远端名和分支名继续使用 Git 原生校验；远端选择和仓库归属由服务端复验。
- 远端刷新或推送失败不改写任务工作区生命周期状态，也不清空本地分支、差异或用户表单。
- 本任务不对用户真实项目执行提交、合入或推送。
