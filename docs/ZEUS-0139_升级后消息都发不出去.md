# ZEUS-0139 升级后未归档会话消息无法发送

## 问题结论

升级后的 `.zeus` 分层数据和 Codex Provider 会话文件仍然存在，问题不是消息丢失，也不是全局并发容量耗尽。

本次现场证据显示：

- 未归档任务会话仍绑定原 Provider thread；
- 原任务分支仍存在，但任务 workspace 已进入 `merged/reclaimed`，物理 worktree 已回收；
- 持久化 submission context 仍指向已经不存在的旧 `projectLocalPath`；
- 启动恢复使用旧路径失败后，会话进入 `paused`；
- 新消息写入 `queued`，但队列排空只向 `idle` 会话派发，因此消息一直不发送；
- 原队列状态投影没有把“Provider 已暂停但消息仍为 queued”识别为恢复失败，界面错误显示为等待容量。

## 行为约定

未归档任务会话可以继续使用原任务分支。原 worktree 被回收时，Zeus 必须重新创建同一分支的隔离 worktree，并同时恢复任务环境为 `ready`，允许继续修改、提交和推送。任何情况下都不能把项目根目录作为任务会话的写入目录。

归档会话不在启动时自动恢复；用户显式恢复时才尝试重新挂载对应分支。分支、远端和任务工作区身份都无法恢复时，保留消息并返回 `ZEUS_NATIVE_CONVERSATION_WORKTREE_UNAVAILABLE`。

已经带有 `providerTurnId` 的 submission 表示可能已经进入 Provider 轮次，不能自动重发。没有 `providerTurnId` 的 `recovery_required` submission 才能通过“恢复并发送”重新排队。

## 实施内容

- 本地服务端增加任务会话 worktree 恢复器：按任务环境恢复全部仓库和共享目录，使用同一分支，使用单航班锁避免重复 worktree。
- `CodexNativeConversationCoordinator` 在启动恢复、发送、队列排空和显式队列恢复前刷新执行上下文，并在 Provider 快照确认空闲后才派发。
- 增加 `/queue/recover` API 和桌面端“恢复并发送”操作。
- `providerState=paused` 且没有活动 Provider turn 时，队列状态统一投影为 `recovery_required`，不再显示为等待容量。
- 不修改 Provider JSONL、Provider SQLite 或会话路径事实；只通过 Provider API 使用新的 cwd，并更新本地 submission context。

## 取舍与边界

恢复为 `ready` 能让用户在原分支继续完成代码修改、提交和推送，但会重新开放已经合入任务的交付入口。恢复动作会记录任务事件，原分支历史不变，后续任务终态清理仍负责归档会话和回收 worktree。

## 验证记录

- 静态检查：`pnpm lint`、`pnpm typecheck`、`pnpm build`、`pnpm package:mac` 均通过；`git diff --check` 通过。
- 打包产物：生成 `dist/test/mac-arm64/Zeus Test.app` 和对应 arm64 DMG；`codesign --verify --deep --strict` 通过，Bundle Identifier 为 `dev.hypha.zeus.test`。
- 单仓恢复：隔离数据库和临时 Git 仓库中，原分支恢复到隔离 worktree；消息 `我已经升级完成` 返回 202，重复相同幂等键只调用一次 Provider `startTurn`，发送 cwd 始终是恢复后的 worktree。
- 多仓和共享目录：主仓库、嵌套仓库及共享目录均恢复到同一隔离环境；共享目录仍指向原持久目录；Provider cwd 不是项目根目录。
- 失败边界：分支和记录的远端均不存在时，submission 保持 `paused/recovery_required`，队列恢复 API 返回 `ZEUS_NATIVE_CONVERSATION_WORKTREE_UNAVAILABLE`，submission 同时保留真实失败原因。
- Provider 轮次保护：已有 `providerTurnId` 的活动 submission 在启动恢复中未再次调用 `startTurn`。
- 归档和并发：启动时未触碰归档 Provider 会话；两次并发显式恢复最终只留下一个同分支 worktree。
- 交付链路：恢复后的隔离 worktree 已完成一次本地提交和本地临时远端推送，远端 HEAD 与本地提交一致。
- 运行检查：最新 `Zeus Test.app` 在独立 `ZEUS_USER_DATA_DIR` 下成功启动并退出；既有其他 worktree 的 `Zeus Test.app` 和日常安装的 `Zeus.app` 均未触碰。
- 父会话现场复核：正在运行的正式 `Zeus.app 0.2.15` 仍报告 `providerState=paused`、workspace=`merged`、environment=`reclaimed`，目标 submission `我已经升级完成` 仍为 `queued` 且没有 `providerTurnId`；调用该已安装版本的 `/queue/recover` 返回 `404`，说明它尚未包含本次恢复 API。本轮未绕过正式包启动第二个服务，也未改变数据库或 Provider 数据，因此正式父会话消息仍保留在队列中，待安装包含本次代码的应用后再执行真实派发。

上述 Provider 探针使用隔离的假 Provider 管理器验证本地服务端状态机和幂等边界，不等同于真实 Codex 服务端或完整 GUI 验收。当前未执行截图级的完整桌面交互验收；已有 `Zeus Test.app` 单实例和日常安装应用均保持运行，未强行接管。
