# ZEUS-0144 怎么发出去的消息任务标题那些东西都不见了呢

## 任务目标

修复 Codex 原生会话中，首条用户消息已经发送后，任务标题、任务类型、现状和预期不可见的问题。任务提示词本身继续由现有任务正文构造器生成，不改变发送内容和结构化附件。

## 根因证据

- 任务推送提交记录中保存的是完整用户正文，包含任务标题、任务类型以及优化任务的“现状”和“预期”。
- `item/started` 与 `item/completed` 的 `userMessage` 事件可能只带消息元数据，文本字段为空或比本地提交正文短。
- 旧逻辑在完成事件中直接使用提供方事件文本生成项目正文，并用同一正文更新 `conversation_messages`；因此晚到的空文本覆盖了此前完整的乐观消息和本地记录。
- 会话快照又把 `conversation_messages` 作为历史用户消息来源，所以切换或重新打开会话后会继续显示被覆盖的正文。

## 返修根因

2026-08-09 对用户再次提供的截图和正式数据做只读核对后，确认首次修复只解决了持久化覆盖，没有覆盖最终渲染回归：

- 截图对应会话的 `conversation_submissions`、`conversation_messages` 和 `conversation_items` 均已保存完整的 60 字符任务正文，`clientMessageId`、`providerTurnId` 和 `providerItemId` 关联也正确。
- `sessionReducer` 从原生 item 和持久消息合并出的用户消息正文仍然完整，附件资源也正确关联到同一 Provider item。
- `ThreadItemView` 在流式渲染优化中把原来的通用正文分支收窄为仅渲染助手和思考正文，却没有保留静态用户正文分支。结果是用户气泡只渲染附件卡片、时间和操作区，任务文字完全不可见。
- 因此再次修改后端投影、附件协议或 CSS 都无法修复本次复现；必须恢复 Renderer 的用户正文渲染入口。

## 实现口径

在 `packages/local-server/src/codexNativeUserMessageProjection.ts` 集中处理 Codex 原生用户消息的关联和正文选择：

1. 明确的 `displayText` 优先，保留“是，实施此计划”等短展示文案。
2. 精确关联的提交正文其次，保留任务字段、换行和空字符串输入语义。
3. 没有关联提交时保留同一提供方消息已经保存的非空正文。
4. 只有没有本地正文可用时才使用提供方事件正文。

实时 `item/started`、`item/completed`、本地消息项目、持久化用户消息和广播事件使用同一结果。原生会话快照对已经存在的 Codex 用户消息按 `clientMessageId` 或唯一 `providerTurnId` 做读取兜底，不执行模糊全库迁移。

不修改任务提示词构造器、发送接口、事件字段、附件或客户端消息 ID 语义。Renderer 的乐观消息收敛逻辑保持不变。

返修只在 `ThreadItemView` 中为 `role === 'user'` 且正文非空的消息恢复静态 `SafeMarkdown` 渲染。助手和思考继续使用自适应流式渲染，纯附件消息继续只显示附件，长用户消息继续沿用既有折叠、展开、复制和编辑逻辑。

## 方案取舍

共享投影层能同时修复任务首条消息和普通 Codex 用户消息，避免只在一个页面上保留文本；代价是必须持续保留 `displayText` 的特殊展示语义。历史消息采用精确关联的读取兜底，可以立即恢复会话气泡，同时避免没有可靠关联时误改其他历史消息。

返修采用明确的用户角色分支，优点是恢复范围只覆盖静态用户正文，不把工具项、未知 Provider 项误当作自然语言正文，也不让用户消息进入流式缓冲；代价是 `ThreadItemView` 的角色渲染分支需要持续保持穷尽，后续优化助手流式渲染时必须单独核对用户正文入口。
