# ZEUS-0155 代码交付问题

## 任务目标

修复同一任务分支第一次合入来源分支后，继续产生新提交时仍被历史“已合入”状态阻断的问题。代码交付状态必须描述当前任务分支提交，而不是描述这个工作区是否曾经成功合入过。

## 现状与根因

服务端的每条合入记录都保存了该次交付使用的 `taskHeadSha`，后续本地提交也会把任务工作区重新标记为 `ready`。因此服务端具备区分“旧提交已交付”和“当前提交待交付”的事实。

桌面端此前只按工作区、来源分支和 `merged` 状态查找历史记录。只要同一工作区曾经成功合入过一次，任意后续提交都会继续命中旧记录，按钮永久显示“已合入来源分支”，请求甚至不会发送到服务端。

## 产品规则

- 同一任务分支可以多次提交，也可以在每次产生新提交后再次合入创建任务时锁定的来源分支。
- “已合入来源分支”只表示当前任务分支 HEAD 已存在对应的成功合入记录。
- 工作区只有未提交变化时，当前已提交 HEAD 仍可以显示为已合入；用户完成新提交后才重新开放合入。
- 冲突、未提交变化、来源分支变化、待同步和 Git 并发校验继续保留，不能为了允许重复合入而绕过。
- 历史数据缺少 `taskHeadSha` 时，仅在工作区仍明确处于 `merged`，且记录的工作区 HEAD 与当前可读取 HEAD 一致时兼容为已交付。

## 方案与取舍

桌面端用当前分支对比结果中的 `taskHeadSha` 匹配历史成功合入记录；读取不到分支对比时依次使用工作区审查 HEAD 和持久工作区 HEAD。只有提交号相同的记录才能驱动“已合入”、来源分支推送入口和步骤完成态。

优点：不修改 Git 历史和服务端安全门禁即可恢复多次交付；状态与真实提交一一对应，旧成功记录仍可审计。

代价：旧记录没有提交号时不能仅凭历史成功状态精确判断，只能使用工作区终态与 HEAD 一致性做保守兼容；若当前 Git 提交完全无法读取，则不会冒进开放重复写操作。
