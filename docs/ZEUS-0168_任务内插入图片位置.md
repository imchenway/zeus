# ZEUS-0168 任务内插入图片位置

## 任务目标

完成两条相互关联的任务首发优化：让任务字段中添加的图片、文件、文件夹和超长文本资源在查看、编辑和推送时保持字段归属；同时允许用户选择关联任务、关联任务会话和关联任务附件作为本次首发上下文。

## 当前阶段

开发、静态检查和测试身份打包已完成；GUI 与真实 Provider 验收因当前运行条件未完成。已完成证据与运行缺口分开记录。

## 已确认决策

### 所有附件具有字段归属

- 在支持附件输入的任务字段中添加的图片、普通文件、文件夹和超长文本资源必须持久归属到添加时所在的字段，例如“优化现状”或“缺陷预期”。
- 范围不是单一“现状”字段，而是需求描述、缺陷现状、缺陷预期、复现步骤、优化现状、优化预期和标签。
- 任务标题不允许插入附件；标题字段中的资源粘贴能力需要移除，普通文字粘贴保持不变。
- 这项归属不是当前界面的临时排序；重新打开任务、进入推送确认和创建新会话后都必须保留。
- 迁移完成后不再保留通用任务附件区；所有附件都进入字段归属模型。

优点：查看、编辑、推送预览和最终会话可以基于同一项真实归属展示图片。

代价：需要扩展任务附件元数据，处理历史无归属附件，并验证结构化图片输入能否稳定表达字段顺序。

### 字段附件固定显示在文字上方

- 查看状态在字段标题下先显示字段归属附件，再显示字段文字。
- 编辑状态在同一字段区域内先显示字段归属附件，再显示普通文本输入框。
- 不引入富文本编辑，不支持把附件插入文字中任意光标位置。

优点：当前普通文本编辑、输入法、选区和保存规则可以继续保持稳定，字段归属也清晰可见。

代价：一项字段存在多段文字时，不能表达某张图片位于其中两段文字之间。

### 历史无归属附件按任务类型自动归属

- 历史附件没有字段证据时，按迁移时任务类型确定性归属：需求归入需求描述，缺陷归入缺陷现状，优化归入优化现状。
- 自动归属结果必须持久保存；后续切换任务类型时不重新计算，沿用隐藏类型字段附件的保留规则。
- 迁移后不保留“未归类附件”兼容区，也不提供手动归类流程。

优点：所有历史与新附件都进入同一字段模型，任务详情和推送确认可以彻底取消底部通用附件区。

代价：历史附件可能实际属于预期、复现步骤或其他语义，但由于缺少证据，仍会按上述固定规则归类。

### 附件类型一视同仁

- 字段归属规则不只处理图片，也覆盖普通文件、文件夹和由超长文本物化的附件。
- 各类附件继续使用适合自身的预览或文件卡片表现，但字段归属、排列位置和推送关系使用同一规则。

优点：用户在同一字段添加的资源不会因文件类型不同而被拆到不同区域，行为更容易理解。

代价：实现不能只在图片预览层增加字段标记，需要统一扩展任务附件模型、保存接口和推送投影。

### 移除字段附件即解除任务关联

- 用户在字段区域点击附件的“移除”时，直接解除该附件与任务的关联，不把它降级或移动到其他附件区域。
- Zeus 托管资源文件仍沿用既有生命周期规则；解除任务关联不等于立即删除本机托管文件，也不破坏既有会话证据。

优点：“移除”的结果明确，字段区域与任务附件事实同步消失，不会在页面底部再次出现。

代价：附件放错字段时需要重新添加；若后续需要跨字段移动，应设计明确的移动操作，不能借“移除”隐式完成。

### 新任务取消通用附件区

- 所有新附件必须归属于具体任务字段，任务详情不再提供可新增内容的通用附件区。
- 历史无归属附件完成按类型自动迁移后，任务详情也不显示底部兼容区。
- 所有任务均只在具体字段内展示和操作附件。

优点：新任务的附件心智统一为“属于某个字段”，页面不再重复出现一个底部附件仓库。

代价：系统不再提供一个跨字段总览全部任务附件的区域。

### 字段附件只通过复制粘贴添加

- 不在每个字段旁新增“添加附件”按钮，也不保留底部通用附件选择按钮。
- 图片、普通文件、文件夹和超长文本资源都通过复制粘贴进入当前字段，并立即形成字段归属。
- 现有 Finder 与 Paste.app 原生剪贴板兜底继续保留，正常 DOM 粘贴和原生兜底必须避免重复添加。
- 创建任务弹窗与任务详情使用相同规则；不保留创建阶段的通用附件区或跨字段附件草稿。

优点：字段界面保持低噪音，不会因每个字段重复出现低频按钮而变得拥挤。

代价：用户不能通过 Finder 文件选择器添加附件；剪贴板读取失败时必须保留明确反馈和重试能力。

### 创建任务与任务详情使用同一字段附件模型

- 创建任务时粘贴的附件立即记录到当前草稿字段，创建成功后原样持久化为字段归属附件。
- 任务详情重新打开后不得丢失或重新推断创建阶段的字段归属。
- 标题在创建和详情两处都只接受普通文字；类型专属内容和标签在两处都支持附件粘贴。

优点：用户不需要理解“创建时通用、创建后归属”的两套规则，字段语义从草稿到首发保持一致。

代价：创建弹窗不再提供一个集中查看全部草稿附件的底部区域。

### 首发第一行直接显示任务标题

- 任务首发的第一行直接显示任务标题正文，不再添加“任务标题：”标签。
- 标题与后续任务类型、类型专属内容保持可读分隔，但标题自身不承载附件。

优点：首发内容开头更简洁，标题作为消息主标题更容易扫描。

代价：任务标题不再通过固定标签显式标识；消费提示词的逻辑不能继续依赖“任务标题：”前缀。

### 标签及其附件进入首发内容

- 标签作为支持附件输入的任务字段进入首发正文，并按“标签 → 标签附件 → 标签文字”组织。
- 当前任务、父任务和关联任务使用相同规则；未选择某个上下文任务的附件时，只发送其标签文字。

优点：标签字段附件拥有明确语义位置，推送预览与任务详情不会出现同一字段在发送阶段消失。

代价：这会改变现有首发正文契约；标签从仅用于任务管理变为模型可见上下文。

### 同时增加关联任务首发上下文

- 推送弹窗需要允许用户选择当前任务的关联任务，并在选中任务后逐项选择其会话和附件。
- 服务端必须重新校验关联关系、任务和资源归属、会话真实路径、附件授权、重复选择和选项快照；关联关系或资源变化后不得按旧选择创建会话。
- 关联任务内容进入首发正文；所选关联任务会话路径进入对应上下文；所选关联任务附件继续走结构化附件通道。
- 该能力只影响本次新会话的首条输入，不改变关联任务关系，也不追改既有会话。

优点：解决当前任务时可以一次携带真正相关的任务证据，不需要用户手工复制关联任务正文和会话路径。

代价：本任务从附件展示扩展到任务关系、会话选择和服务端安全复验，实施与真实验收范围明显增大。

### 关联任务上下文全部手动选择

- 关联任务默认不选，只有用户手动选择后才进入本次首发上下文。
- 关联任务会话和关联任务附件也必须逐项手动选择；选中关联任务不能联动全选其会话或附件。
- 每次打开推送弹窗重新选择，不自动记忆上次选择，也不根据关联关系、更新时间或附件类型推断选择。

优点：用户明确控制发送给模型的任务内容、本机会话路径和附件，避免上下文体积及本机信息意外扩张。

代价：关联内容较多时需要逐项操作，不能通过自动全选追求更少点击。

### 父任务与关联任务上下文使用稳定顺序并去重

- 首发上下文固定按“当前任务 → 父任务上下文 → 关联任务上下文”组织。
- 父任务按根任务到直接父任务排序；关联任务按推送弹窗中的稳定显示顺序排序。
- 同一任务如果同时处于父任务和关联任务选择中，只在父任务上下文发送一次。
- 同一真实附件被当前任务、父任务或关联任务重复选择时，只在首次出现的位置通过结构化附件通道发送一次。

优点：提示词顺序可预测，任务和大体积资源不会重复占用上下文。

代价：同一附件即使与多个上下文章节都有关，也只在第一次出现的位置展示和发送。

### 所选上下文会话只发送真实 JSONL 路径

- 父任务会话和关联任务会话使用相同规则：用户逐项手动选择后，只把服务端复验通过的真实 JSONL 文件路径写入对应任务上下文。
- 不把会话正文展开复制进提示词，不根据会话 ID、日期或用户目录猜测路径。
- 路径缺失、文件不存在、不是普通 JSONL 文件或归属变化时，该会话不可选择；提交阶段再次变化则阻止创建会话并要求刷新确认。

优点：长会话不会直接膨胀首发提示词，模型仍可按需读取完整原始记录。

代价：执行模型必须具备读取所选本机 JSONL 文件的权限；路径不可用时不能降级为猜测或部分会话摘要。

### 字段内部按名称、附件、文字发送

- 当前任务、父任务和关联任务的内容字段统一按“字段名称 → 字段归属附件 → 字段文字”组织。
- 推送确认预览、Provider 实际输入和发送后的用户消息使用相同顺序，不能只在某一个界面移动附件。
- 任务标题继续作为首行纯文字；标题不使用字段名称标签，也不承载附件。

优点：字段名称先建立语义，紧随其后的结构化附件和文字都能明确归属于该字段。

代价：附件固定出现在字段文字之前，不能表达文字段落之间的精细位置。

### 隐藏类型字段的附件保留但不发送

- 修改任务类型时，其他类型字段的文字和字段归属附件继续持久保存，不自动删除或改为未归类附件。
- 当前任务详情只展示当前类型字段及其附件；隐藏字段和附件不进入当前任务首发。
- 用户切回原任务类型后，对应字段文字和附件恢复显示，并重新具备随该类型发送的能力。

优点：附件生命周期与现有类型专属文字一致，切换类型不会造成不可逆数据丢失或错误发送。

代价：任务记录中可能长期保留当前界面不可见、当前首发也不使用的托管附件关联。

### 完整首发样例已确认

以下为已确认的结构示意；“结构化附件”代表真实图片或文件输入，不是把本机路径写成普通正文：

```text
任务内插入图片位置
任务类型：优化
现状：
[结构化附件：现状截图.png]
所有图片现在都统一显示在底部。
预期：
[结构化附件：期望效果.png]
图片应跟随字段展示和发送。
标签：
[结构化附件：标签说明.md]
任务，附件
补充信息：本次同时验证父任务和关联任务上下文。

父任务上下文：
父任务：ZEUS-0103 · 任务详情输入框粘贴附件
任务类型：需求
需求描述：
[结构化附件：父任务说明.pdf]
支持在任务内容字段粘贴资源。
标签：
任务详情
会话文件路径：
- /服务端复验后的/父任务会话.jsonl

关联任务上下文：
关联任务：ZEUS-0126 · 发出去的图片显示为图片
任务类型：缺陷
现状：
[结构化附件：关联任务现状.png]

- /服务端复验后的/关联任务会话.jsonl
```

优点：首发顺序、字段语义、上下文层次和会话路径边界都有可对照的目标样例。

代价：旧的“任务标题：”前缀和底部附件区属于明确的契约变更，不保留两套展示。

## 已核对现状

- 任务详情已支持在标题、需求描述、缺陷现状、缺陷预期、复现步骤、优化现状、优化预期和标签中粘贴图片或文件。
- 粘贴后的资源会立即成为任务附件，但持久数据只记录路径、名称、类型、大小等附件元数据，没有记录粘贴时所在的任务字段。
- 任务详情使用独立的“图片与附件”区域展示全部附件，因此所有图片都出现在任务内容后面。
- 任务推送正文只格式化标题、类型和类型专属文字；全部任务附件通过结构化附件通道发送，没有字段位置信息。
- 推送确认弹窗先展示“将发送的任务内容”，再在底部展示统一“附件”区域，与用户反馈一致。

## 实施规划

### 1. 统一字段归属附件数据契约

- 在共享层定义唯一的附件字段枚举：需求描述、缺陷现状、缺陷预期、复现步骤、优化现状、优化预期和标签；不包含标题。
- 任务附件引用增加必填字段归属，创建草稿、任务详情、API 校验、导入导出和推送都复用同一类型。
- 任务内同一真实资源路径继续只有一条附件关联；若用户把同一资源粘贴到另一字段，归属移到最后粘贴的字段，不制造两条重复关联。
- 附件上限继续按任务全部字段合计计算，不因字段拆分而成倍扩张。

优点：字段归属成为一个可持久、可校验的业务事实，所有界面和发送适配器共享一份真相。

代价：同一资源不能同时归属多个字段；这是对现有“路径唯一”附件身份的延续。

### 2. 一次性修复历史数据并守住所有写入入口

- 本地服务启动时扫描未删除任务，将缺少或非法字段归属的历史附件按当时任务类型修复。
- 修复只更新 `source_context_json`，不伪造任务内容更新时间或任务编辑事件；与现有托管附件路径恢复在同一次安全保存中完成。
- 历史备份或导入任务也走同样归属补全，避免启动后再导入的旧数据绕过修复。
- 新建和更新 API 拒绝缺少字段、标题字段或未知字段附件；任意 `sourceContext` 合并不得擦除已有归属。

优点：迁移后可完全取消“未归类”和通用附件兼容分支。

代价：历史语义误分类无法自动纠正；修复前后需对任务数量和附件数量做对账。

### 3. 改造创建弹窗和任务详情

- 把粘贴目标字段传入资源物化与保存链路，图片、文件、文件夹和超长文本使用同一归属。
- 标题不进入资源粘贴处理，仍保留普通文字粘贴。
- 每个支持字段按“标题文案 → 当前字段附件列表 → 文字输入/展示”渲染；字段附件列表使用附件集合派生，不再另存一份分组状态。
- 删除创建弹窗和任务详情底部通用附件区、文件选择按钮和资源拖放入口；字段内不新增按钮。
- 移除字段附件继续使用乐观并发版本校验，成功后解除任务关联；失败时恢复界面。
- 切换任务类型只改变可见字段，不迁移、不删除其他类型字段附件。

优点：创建、查看和编辑只有一套交互心智，界面噪音更低。

代价：取消了文件选择和拖放备用入口；系统剪贴板权限或原生读取失败时，用户只能修复剪贴板后重试。

### 4. 建立服务端权威的首发布局快照

- 共享层把首发从“一段字符串+一组底部附件”提升为有顺序的布局快照：当前任务、父任务和关联任务区块，区块内的字段文字、附件位置、标签和会话路径。
- 当前任务的当前类型字段和附件自动进入；父任务和关联任务只进入用户手选的任务、会话和附件。
- 关联任务选项与任务详情保持“最近更新优先、任务编码稳定破平”的展示顺序。同时是祖先的关联任务不在关联区重复出现，只从父任务区手选。
- 能力快照使用一个原子上下文修订值覆盖父任务、关联任务、会话路径和附件选项；提交时重建并对比快照，任一事实变化都阻止首发。
- 去重优先级固定为当前任务、根到直接父任务、关联任务；同一真实路径只保留第一个附件位置。
- 会话继续只写入复验通过的绝对 JSONL 路径；同时把该路径所在目录作为本轮只读资源根传给需要读取限制的运行适配器。

优点：弹窗预览、服务端接受、重试恢复和历史消息都可以复用同一份已验签布局。

代价：首发请求契约和本地持久提交记录都要增加结构化元数据，不能再靠解析一段普通文字恢复位置。

### 5. 扩展推送弹窗的父任务与关联任务手选

- 保留父任务现有手选逻辑，新增独立的关联任务区；两区都是任务默认不选，会话和附件逐项选择，不全选、不记忆、不联动勾选。
- 附件选项显示其字段归属，避免用户只看文件名无法判断会出现在哪个字段。
- “将发送的任务内容”改用结构化布局预览，直接在各字段文字上方展示当前会发送的附件，删除底部附件汇总。
- 预览数据由能力快照和当前表单选择派生；独立资源读取并行执行，不逐任务串行形成等待链。

优点：用户在提交前能按真实字段位置审查本次会发出什么。

代价：上下文较多时弹窗会变长；必须依靠清晰分组和稳定滚动区保持可扫描性，不增加全选捷径。

### 6. 让 Provider 输入和已发消息保留同一布局

- Codex 原生提交记录持久化服务端布局快照；派发、排队、接管和重试均从这份快照生成交错的文字、本地图片和文件提及输入，不回读可能已变化的任务。
- 附件形成会话资源时保存安全的布局位置标识，不把真实路径暴露给渲染层。
- 已发用户消息读取布局快照，在对应字段渲染资源，并抑制这些资源的底部重复卡片；普通会话附件和其他资源的现有展示不受影响。
- Pi SDK 适配器使用同一布局快照，把普通文件/文件夹路径写在对应字段标记处，图片数组按布局出现顺序传入。Pi SDK 底层协议仍是“一段文字+独立图片数组”，无法像 Codex 原生协议一样在字节级真正交错；界面和消息展示仍保持字段位置。

优点：会话首次展示、重开、Provider 重放和失败重试不会把附件重新堆到底部。

代价：会话资源投影和用户消息渲染契约需要扩展；Pi SDK 的原始协议表示存在上述已明示的能力差异。

### 7. 同步长期设计与任务文档

- 实施时在 `DESIGN.md` 追加 ZEUS-0168 契约，记录字段归属、历史修复、上下文手选、快照持久化、去重优先级和适配器差异。
- 本文按开发、静态验证、打包和真实运行阶段持续追记，不把未执行项写成已完成。

优点：后续修复推送或资源投影问题时有稳定契约可查。

代价：需要同步维护任务记录、设计契约和领域语言，不能只修改组件代码。

## 主要风险与控制

1. **历史附件误归类**：缺少原始字段证据，只能执行用户已确认的固定规则；修复前后对账任务和附件数，不删除托管文件。
2. **界面顺序正确但 Provider 顺序错误**：禁止从底部附件数组二次拼接，必须从持久布局生成实际输入并检查 app-server 发送记录。
3. **乐观消息与重开消息不一致**：客户端预览用同一共享布局生成器，服务端接受后以持久快照为权威，重开会话复验。
4. **上下文在弹窗打开后变化**：用一个修订值覆盖父任务、关联任务、会话和附件，差异时整体刷新、重新手选，不静默丢弃失效项。
5. **会话路径可见但模型不可读**：服务端复验普通 JSONL 文件，并向有额外读取根限制的适配器传递只读目录；不把会话正文复制进提示词降级。
6. **Pi SDK 无法原生交错图片**：字段标记和图片数组使用同一顺序，但不声称底层协议已实现 Codex 式交错；真实验收单独报告。
