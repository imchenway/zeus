# ZEUS-0174 发出去的图片经常延迟显示

## 任务信息

- 任务类型：缺陷
- 现状：图片消息刚发出时长时间显示文件名和 MIME 类型，之后才替换为图片缩略图。
- 预期：发送操作后立即显示图片，不等待 Provider 后续回放。
- 截图状态：用户消息处于“引导中”，图片区只显示文件名 `Zeus 2026-08-11 11.43.10.png` 和 `image/png`。

## 当前阶段

- 阶段：开发与可执行验证完成。
- 已按项目约束完成 `grilling` 与 `domain-modeling` 的逐项确认，再进入设计和实现。
- 已完成代码、领域词汇、静态检查、构建、测试身份打包和隔离桌面运行检查；真实 Provider 发送受独立测试数据中的 Codex 登录门禁阻断。

## 已确认事实

1. ZEUS-0126 已实现“持久会话资源中的图片附件显示缩略图”，但当时明确保留了首次异步读取预览的过程。
2. 当前发送链路会在 Renderer 中立即建立一条“乐观用户消息”，以便不等待本机服务和 Provider 回执就显示已发内容。
3. `addOptimisticUserItem` 把附件原始元数据写入 `payload.attachments`，却把可用于图片展示的 `resources` 固定为空数组。
4. `ThreadItemView` 检测不到持久附件资源时，会用 `ItemAttachments` 把原始附件显示为“文件名 + MIME 类型”，与截图完全一致。
5. 只有当 Provider 用户消息事件或完整会话快照返回后，乐观消息才会被带 `ConversationResource` 的权威消息替换，随后进入 ZEUS-0126 的图片缩略图分支。
6. “引导中”表示当前轮次仍在执行，新消息通过 `steer_now` 进入当前轮次。Provider 精确回放用户项的时间可能远晚于本地发送操作，因此当前实现会把图片卡片延迟放大到整个 Provider 等待窗口。
7. 会话输入区在发送前已能通过受信 Main 预览接口立即显示同一张图，所以修复不需要放宽 `file://` 或任意本地路径权限。

## 根因判定

这是“临时消息投影缺少图片展示资源”导致的可见延迟，不是图片文件解码慢、样式渲染慢或 Provider 上传失败。

## 已确认产品边界

用户已确认把“刚发送、尚未获得 Provider 持久回放的本地投影”定义为“发送中消息”：

- 用户点击发送后立即显示本地受信图片缩略图；
- 保留“发送中 / 引导中 / 排队中”状态，不把本地可见误表达为 Provider 已接收；
- Provider 持久消息到达后，按稳定消息身份无感替换为权威会话资源；
- 本地预览失败时才降级为文件卡，发送失败则保留原草稿与附件的既有安全语义。
- 普通发送、当前轮次“引导中”和“排队中”三种消息状态统一适用这一口径，不只修复截图分支。

优点：

- 交互结果与用户的发送操作同步，不再受 Provider 回放时机影响。
- 复用已有受信预览能力，不放宽本地文件访问边界。
- 通过状态文案继续区分“本地已显示”和“Provider 已确认”。

代价：

- Renderer 需要在同一条消息的临时附件与持久会话资源之间稳定交接，否则会出现重复图片或闪烁。
- 需要同时验证普通发送、活动轮次引导、排队、失败回滚、重开会话和多图消息。

## 实施设计

1. 不为发送中消息伪造 `ConversationResource`；它仍是只属于 Renderer 的临时投影，不获得持久资源的打开权限。
2. 临时投影从已提交附件中识别图片，使用现有 Electron Main 会话输入资源预览接口读取；该接口只接受有效签名 `uploadRef` 或 Zeus 自管附件根中的真实路径。
3. 临时图片成功后使用持久会话图片的同级容器尺寸；预览不可用或加载失败时，在原位降级为文件名与类型卡片。
4. 用户消息只要还没有权威附件资源，就继续使用临时图片；这覆盖从 Renderer 乐观消息到 Provider 项已回放、但资源尚未进入快照的短暂交接窗口。
5. 权威附件资源到达后，既有 `clientUserMessageId` 匹配逻辑原位替换临时消息，临时图片不再渲染，避免重复。
6. 已持久队列消息使用同一临时图片组件；普通文件和文件夹保持既有文件名表达。
7. 发送中图片只表达本地已可见，继续依赖消息上的“发送中 / 引导中 / 排队中”状态表达 Provider 交付事实。

优点：

- 不改 Provider 协议、数据库和会话资源归属。
- 不放宽 Renderer 本地文件权限，也不引入任意 `file://` 读取。
- 普通发送、引导和排队共用一套即时预览行为。

代价：

- 临时图片在 Provider 确认前只负责展示，点击打开继续以持久会话资源到达为准。
- 临时预览和持久资源预览是两个受信读取阶段，需要在真实界面核对交接时是否有短暂占位闪烁。

## 实施结果

1. `ConversationPendingAttachmentImages` 已承担未持久图片的统一展示，直接使用附件已持有的 `uploadRef / localPath` 请求 Electron Main 预览。
2. 临时图片展示完整内容且不提供未授权的点击打开；加载失败则在原位显示图片文件卡。
3. `ThreadItemView` 在权威附件资源到达前持续使用临时图片，不只依赖 `optimistic` 标志，因此覆盖 Provider 项已回放但资源尚未进入快照的交接窗口。
4. 权威附件资源存在时，临时图片不再渲染，既有会话资源图片接管，不生成重复图片。
5. 任务首发图片使用 `taskPushAttachmentKey` 定位到原字段；普通发送和引导消息显示在对应用户消息内。
6. `QueuedConversationMessages` 已使用同一临时图片组件，纯图片队列不再产生空附件列表；非图片仍显示文件名。
7. 临时图片使用不可交互容器，已取消与持久图片打开按钮相同的悬停和键盘焦点反馈。
