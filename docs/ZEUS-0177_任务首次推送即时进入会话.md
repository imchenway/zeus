# ZEUS-0177 任务首次推送即时进入会话

## 任务信息

- 任务类型：优化。
- 现状：用户点击任务首发提交后，界面停留在任务页并持续显示后台创建状态；只有真实会话和首轮执行建立后才进入会话页。
- 预期：点击提交后立即进入会话工作区，并立即看到本次首发内容；工作区、运行内核原生会话和真实执行轮次可以继续在后台创建。

## 当前阶段

- 阶段：回归修复实现完成，静态、构建与打包验证已完成；最新包的桌面界面复验受本机控制服务不可用阻断。
- 已按项目流程完成 `grilling` 与 `domain-modeling` 的逐项确认，并将“任务首发工作面”写入项目领域语言。
- 隔离应用可以正常启动并创建验收项目、优化任务、打开任务首发配置；由于 Zeus 独立 Codex 账号未登录，本轮没有越权进入官方登录流程，因此真实 Provider 首发点击和后台接管的端到端验收仍待已登录环境补充。

## 已确认事实

1. 当前 Renderer 在提交时已经冻结任务首发布局、附件、请求幂等身份和用户消息身份，并保存按任务隔离的后台创建操作。
2. 当前提交后立即关闭弹窗，但仍停留在原页面；真实会话和 Provider thread 建立后，只有用户没有切换页面时才自动进入真实会话。
3. 当前会话输入体系已经支持以稳定 `clientUserMessageId` 立即投影“发送中消息”，再由 Provider 持久消息原位接管。
4. 既有领域规则明确区分“会话创建操作”和“真实会话”：原生会话或真实执行轮次尚未建立时，创建操作不能进入真实会话列表。
5. 既有 ZEUS-000065 曾明确取消临时会话页，原因是临时身份与真实身份切换会导致重复会话、闪动和异步抢页；本任务的预期重新打开了即时会话工作区这一产品决策，需要先确认失败语义和真实性文案。

## 已确认决策

### 即时首发内容的真实性表达

1. 点击提交后立即进入任务首发工作面，并立即显示完整首发内容。
2. 消息气泡不额外显示“发送中”或“已发送”。
3. 工作面底部使用“正在创建会话”的 loading 作为唯一创建状态。
4. 真实会话建立后由同一工作面原位接管，不闪动、不重复生成消息，也不在建立前进入真实会话列表。

优点：页面瞬间响应，状态表达集中，不在同一屏重复展示多个近义进度。

代价：用户需要通过底部 loading 理解当前仍在创建；因此失败时必须在原位置给出清楚且可恢复的结果，不能静默返回任务页。

### 创建失败收口

1. 创建失败后保留任务首发工作面和完整首发内容。
2. 底部 loading 原位转为失败原因与重试操作。
3. 重试沿用同一请求身份和工作面，不返回任务页，也不创建第二份首发内容。

优点：失败不会打断用户的阅读现场，重试路径短，并保留幂等身份。

代价：创建失败的工作面仍然不是真实会话；用户可以继续编辑草稿和后续队列，但这些内容要等重试成功后才能真正交给 Provider。

### 真实会话原位接管

1. 用户停留在任务首发工作面时，真实会话建立只更新当前工作面内部状态，不触发页面重选、重新挂载、滚动动画或可见闪烁。
2. 用户在创建期间主动离开后，成功回调只更新真实会话列表和后台状态，不允许抢回页面。
3. 当前工作面接管前后保持同一份首发内容和稳定消息身份，禁止出现重复消息或先消失再出现。

优点：后台时序不会打断用户，创建完成在视觉上只是当前页面自然进入可用状态。

代价：成功完成不再通过强制导航提醒用户；用户离开后只能从列表或任务状态发现新会话。

### 创建期间的会话列表

1. 点击提交后，左侧会话列表立即按正常任务会话样式显示任务标题。
2. 列表行、任务首发工作面和首发内容使用同一稳定首发操作身份；真实会话建立后只绑定真实身份，不删除旧行、不插入新行、不重新挂载页面。
3. 列表行本身不增加“临时”“发送中”等技术文案；创建状态只在工作面底部表达。
4. 创建失败后同一列表行继续返回原任务首发工作面，并在底部提供失败原因和重试。

优点：用户从点击开始就获得完整会话导航体验，真实身份接管不会造成视觉变化。

代价：Renderer 必须维护首发操作身份到真实会话身份的稳定映射，并处理刷新、失败重试和并发创建，不能再按会话 ID 直接决定列表行生命周期。

### 创建期间保持完整输入能力

1. 用户进入任务首发工作面后，普通输入、后续消息排队和引导能力始终可用，不因真实会话、工作区或首轮执行仍在创建而禁用。
2. 用户操作立即形成稳定、可见、可编辑的消息事实；Zeus 根据后台真实阶段决定消息等待、首轮接管后顺序派发，或在当前执行可接收时引导。
3. 真实会话建立只绑定后台身份并启动适合当前状态的调度，不改变用户已经看到的消息顺序，不重复派发，也不要求用户再次点击。
4. 页面不得把底层创建、排队或引导时序转化为用户限制；失败只在当前工作面局部说明并提供恢复。

优点：用户始终可以继续表达意图，创建耗时与 Provider 时序不再阻塞交互。

代价：首发操作必须在真实会话建立前持久承载后续消息，并在接管时保证顺序、精确身份、单次派发和失败恢复；实现复杂度由 Zeus 承担。

## 共同理解

- 点击推送后，弹窗立即关闭并进入任务首发工作面。
- 首发内容、正常会话列表行和 composer 立即出现。
- 工作面底部只显示真实的创建 loading；消息不显示“发送中/已发送”附加状态。
- 用户可继续输入、排队、编辑、调整顺序和引导，Zeus 自行处理后台时机。
- 真实会话建立后在原列表行、原工作面、原消息上无感接管，不跳页、不闪烁、不抢回、不重复。
- 创建失败留在原地，保留全部内容和操作现场，并提供失败原因与重试。

## 实现记录

1. `TaskModelPushPendingState` 现在在请求发出前创建稳定 `navigationId`、普通会话行、首发 transcript、完整 composer 状态和本地后续消息队列。
2. `ProjectConversationTree` 的选中态和 React key 使用稳定导航身份；真实 conversation ID 只用于服务端读写，后台成功回调已经移除选会话、改 URL 和滚动操作。
3. 首发任务布局消息不再展示乐观“发送中/排队中”元信息；工作面底部统一展示创建、失败原因和重试。
4. 创建期间的草稿、附件、排队、编辑、删除、调整顺序和立即引导复用正常会话组件。后续消息分别持有幂等身份，真实会话接受后按顺序提交；失败消息原地保留并可重试。
5. 真实身份接管保留同一导航身份和首发乐观状态，列表刷新会把真实选择重新投影到原列表行，不插入第二行。

## 首次实现回归与修复

用户在真实环境发现：同一任务先出现一个 `Conversation not found` 的失败行，随后又出现一条能正常运行的真实会话行。根因不是服务端主动创建了两个会话，而是 Renderer 在一次异步回调中先排队更新真实会话身份，随后立即从旧 React 状态读取临时导航身份；旧状态被误判为已接受，连接控制器便使用 `task-push:*` 临时身份请求服务端，形成 404 工作面。与此同时，服务端已经创建的真实会话被历史刷新加入列表，于是视觉上出现两行。

本次修复收口如下：

1. 首发操作的同步引用改为唯一时序事实源，更新引用后再投影 React 状态，旧提交不能反写覆盖新身份。
2. “已接受”和后续消息派发都增加真实会话与 Provider thread 双重门禁；临时导航身份在任何路径下都不能连接、派发或转成成功态。
3. 待创建和真实会话统一使用同一个 `ConnectedSessionWorkspace`、同一个 React key 与稳定导航身份。真实 ID 只重建内部控制器，外层列表行、消息、输入框、滚动和焦点不重挂。
4. 真实控制器完成权威快照加载前，页面继续展示原本的本地工作面和“正在创建会话”；加载完成后原位切换到运行态。正常链路没有失败提示或中间页。
5. 创建阶段只开放本地输入、附件和消息队列动作；资源预览、变更操作等依赖真实会话 ID 的能力，要等真实控制器可用后才启用。
6. 用户在后台创建期间离开页面时，完成回调只绑定身份并刷新列表，不执行选中、跳转、滚动或聚焦。
7. 真实控制器加载权威快照期间，本地草稿和附件继续同步进真实控制器，接管完成不会清空用户刚输入但尚未提交的内容。

修复后的正常可见链路只有：`正在创建会话 → 原工作面开始运行`。失败原因和重试只属于服务端真实拒绝、创建异常或真实连接失败，不是正常创建过程的一部分。
