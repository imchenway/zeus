# ZEUS-0180 已回答询问记录时间线错位

## 任务类型

缺陷。

## 当前阶段

已完成截图、既有任务文档、领域词汇、会话快照与 Renderer 时间线投影代码的现状核对；用户补充了“最终回答前后”两张标准图，已按该标准完成实现与静态、构建、测试包验证。受“不抢占用户当前窗口”的边界约束，本轮未启动 GUI。

## 用户现场

- 截图中，多个“已回答”询问记录与普通用户消息交错展示；“我警告你们一次……”出现在第 4、5 条已回答记录之间，“写入全局的项目记忆”出现在第 5、6 条已回答记录之间。
- 用户质疑：按时间戳核对时，已回答内容在会话中的位置同样错位。

## 现场时间复核

- 前 4 条询问分别完成于 `05:47:21.646Z`、`05:55:14.887Z`、`05:57:55.980Z`、`05:58:55.946Z`。
- “我警告你们一次……”创建于 `05:59:32.172Z`，因此它位于前 4 条与第 5 条询问之间是正确的。
- 第 5 条“审查权限”完成于 `06:01:37.532Z`，“写入全局的项目记忆”创建于 `06:01:37.540Z`，后者晚 `8ms`，因此这两项在截图中的相邻顺序也是正确的。
- 真正被搬离原时间位置的是同一 Provider 轮次中的过程内容：`projectTranscriptTurnRows` 把十次问答前后的命令、思考和过程说明全部跨越问答合并到最上方一个过程组。

## 用户补充的标准展示

### 尚无最终回答

- 发起本轮的第一条用户消息位于耗时区域上方，不属于模型处理过程。
- 保持完整现场展开。
- 模型过程、工具活动、已回答询问和用户中途引导按真实时间穿插。
- 用户需要看清每次引导前后模型做了什么，不能提前应用最终整理规则。

优点：进行中的执行现场可追溯，用户能确认引导是否被模型接收并影响后续过程。

缺点：长轮次在最终回答前会占用较多纵向空间，这是尚未收口现场的必要成本。

### 最终回答到达后

- 发起本轮的第一条用户消息继续位于处理耗时摘要上方。
- 自动把模型过程与工具活动收纳为一个处理耗时摘要。
- 用户中途引导继续逐条完整显示，不合并、不隐藏。
- 最终回答位于全部中途引导之后，作为该轮次的收口内容。

优点：完成后的历史紧凑，用户输入和最终结果仍清晰可见。

缺点：过程详情默认被收纳，需要展开耗时摘要才能回看。

## 已核对事实

1. 既有领域词汇把“已回答询问记录”定义为普通用户询问提交后的持久对话记录；它不是普通用户消息，也不能再次提交。
2. `ZEUS-0073` 已确认 Renderer 应把已解决的 `request_user_input` 与普通消息按时间合并，但没有进一步明确比较哪一种时间。
3. 当前 `projectTranscriptRows` 使用询问的 `resolvedAt` 作为已回答记录时间，这是回答实际完成的时间。
4. 当前插入位置却与普通会话条目的 `updatedAt` 比较。`updatedAt` 是条目最后一次增量或完成事件的时间，不等于条目进入会话时间线的时间。
5. 会话快照恢复时，普通条目自身按 `startedAt ?? updatedAt` 排序；普通用户消息按消息 `createdAt` 排序。已回答询问插入阶段再次改用 `updatedAt`，与既有时间线口径不一致。
6. 因此，一个较早开始、较晚完成的流式条目可能被当成较晚条目，已回答询问记录会被插到错误位置。该缺陷属于时间线投影规则错误，不是 CSS 布局错位。

## 根因

时间线投影混用了两种业务含义不同的时间：

- 已回答询问记录：回答完成时间 `resolvedAt`；
- 普通会话条目：最后更新时间 `updatedAt`；
- 普通会话条目的既有顺序：开始时间 `startedAt`，缺失时才回退最后更新时间。

这会使已回答询问与普通消息、过程条目无法落在同一条稳定时间轴上。除此之外，后续的轮次过程聚合缺少“最终回答是否已经到达”的状态边界：

- `projectTranscriptRows` 完成初步时间合并；
- `projectTranscriptTurnRows` 不论轮次是否已有最终回答，都按 `turnId` 收集同一轮次的全部过程行；
- 对仍在进行、尚无最终回答的轮次，它也提前套用了完成后的整理规则；
- 收集逻辑忽略中间的已回答询问和普通用户消息，把所有过程行一次性投影到该轮次第一个过程行的位置；
- 结果是进行中的多次问答与引导失去前后过程上下文。

## 实现记录

- Renderer 会话条目新增只用于排序的稳定时间 `timelineAt`。
- 快照中的 Provider 条目使用 `startedAt ?? updatedAt`，普通用户消息使用 `createdAt`。
- 实时条目在首次事件到达时确定 `timelineAt`，后续增量和完成事件只更新 `updatedAt`，不再改变时间线位置。
- 已回答询问继续使用 `resolvedAt ?? createdAt`，插入时改为与普通条目的 `timelineAt` 比较。
- 活动轮次尚无最终回答时，把该轮的过程、已回答询问和用户中途引导按原顺序放在一个默认展开的耗时区域中，不搬动相对位置。
- 最终回答出现后，才把同一轮次的过程行聚合成一个默认收纳的耗时摘要；已回答询问、普通用户消息和最终回答保持在摘要外并继续可见。
- 计划产物继续独立展示，不被当作普通过程正文收纳。
- 没有修改服务端数据库结构、询问回答协议、敏感回答脱敏规则或普通消息投影。

## 已确认的产品口径

用户确认：把已回答询问记录定位在“用户实际提交该询问答案”的时刻，即继续使用 `resolvedAt`；普通会话条目则使用其进入时间线的时间，即 `startedAt`，普通用户消息使用 `createdAt`，仅在缺失时才回退 `updatedAt`。同一时间戳需要稳定次序，避免刷新后跳位。

### 推荐口径的优点

- 已回答记录紧邻用户真正完成回答的时点，符合“这次交互何时发生”的认知。
- 与会话快照已有的条目排序规则一致，刷新前后不容易跳位。
- 不需要修改持久化事实，只修正 Renderer 投影使用的时间字段。

### 推荐口径的缺点

- 一个从回答前开始、到回答后才结束的长过程条目，仍按开始时间位于已回答记录之前；这是按事件开始时间排序的自然结果。
- 需要为 Renderer 条目明确保留时间线时间，不能继续只暴露含义模糊的 `updatedAt`。

## 明确边界

- 不把已回答询问伪装成普通用户消息。
- 不修改敏感回答的脱敏与持久化规则。
- 不新增或恢复单元测试体系；后续验证遵循项目现行静态门禁和必要的真实 `Zeus Test.app` 检查。
- 未经用户明确要求，不执行 Git 提交、推送、合并或回退。
