# ZEUS-0184 处理冲突的流程优化

## 任务目标

优化代码交付中的 AI 冲突处理会话：

1. 会话打开后立即看到本次冲突处理提示词，不再等待 Provider 回放后才出现。
2. 创建冲突处理会话前，由用户明确选择一次自动或完全访问权限。
3. 会话标题和任务事件统一使用“冲突处理：”前缀。
4. 提示词不再重复列出“当前界面文件”和“待处理冲突文件”。

## 现场与根因

- 冲突接口在服务端直接写死 `permissionMode: 'auto'`，Renderer 没有确认机会。
- 会话标题使用“本地合入：”，而项目会话树和会话页标题还会把任务会话强制替换为任务标题；任务事件同时使用多种 AI 文案，从列表和时间线不能快速识别这是专用冲突会话。
- Codex 在启动轮次前已持久化 submission，但会话时间线只在 Provider 回放 userMessage 后才投影普通首发消息；因此新会话可以先显示为空白。
- 提示词已经要求处理全部 Git 冲突，底部两份文件清单属于重复上下文。

## 已确认口径

- “冲突处理会话”是专用会话，不是普通任务开发会话。
- 冲突处理必须写入隔离合并工作区，所以不提供无法完成任务的只读选项；用户在“自动”和“完全访问”之间确认。
- 默认高亮“自动”，但必须由用户点击开始，不再由服务端静默决定。
- 即时提示词使用已持久的 submission 投影，Provider 真实消息到达后依身份原位接管，不生成第二条假消息。
- 保留原安全边界：AI 不 commit、不更新目标分支、不 push；Zeus 在轮次结束后复验并收尾。

## 实现方案

### 权限确认

“AI 处理”先打开本次会话的权限确认层，展示自动和完全访问的影响；确认后才向服务端发起会话。服务端对缺失、非法或只读权限继续拒绝，防止旧客户端绕过界面门禁。

优点：权限责任可见，完全访问不会被默认开启。

代价：启动 AI 处理多一次确认；这是对本机 Git 写入的必要门禁。

### 首发消息即时投影

会话快照在 Provider userMessage 尚未回放时，把已进入轮次且具有精确客户端消息身份的持久 submission 投影为用户消息。Provider 项到达后使用同一身份替换，避免重复。

优点：立即显示真实已提交内容，且对新建会话和重新打开会话都有效。

代价：Renderer 需要同时调和持久 submission 与 Provider 消息两个时序来源。

### 身份文案与提示词

- 新会话标题使用 `冲突处理：本地合入 <任务分支> → <目标分支>`。
- 普通任务会话继续在项目会话树和会话页使用任务标题；只有“冲突处理：”会话保留自身标题。
- 启动、完成、本地待同步和失败任务事件统一使用“冲突处理：”前缀。
- 历史“本地合入：”会话仍可恢复，不通过改名迁移旧记录。
- 提示词保留全部 Git 冲突、`git add`、禁止 commit/push 和未解决现场等必要边界，删除底部两份重复文件清单。
