# ZEUS-0186 退出时无法终结所有活动工作

## 当前阶段

已完成产品口径确认、实现、静态门禁、测试包和隔离执行宿主主链路验收；原生退出弹窗的自动点击因本机 `computer-use` 服务不可用而未完成，未把接口证据冒充为 GUI 点击证据。

## 用户现场

- 普通退出时，Zeus 显示 5 个正在执行的轮次、1 个等待交互、0 个其他 Runtime。
- 用户选择“停止任务并退出”后，应用提示无法安全停止全部任务，并明确报告无法停止 5 个执行轮次。
- 应用保持打开，没有把停止失败伪装成退出成功。

## 源码事实

1. `apps/desktop/src/main/main.ts` 在用户选择“停止任务并退出”后调用执行宿主的 `stopActiveWork()`；任一轮次停止失败时取消退出并保持应用打开。
2. `packages/local-server/src/index.ts` 的全局 `/api/execution-host/stop-active` 会枚举活动 submission，但当前无论会话属于哪个 Agent，都固定调用 `codexNativeCoordinator.interruptTurn()`。
3. 同文件的单会话停止入口已经按 `conversation.agentKind` 正确区分：Pi 轮次调用 `piNativeCoordinator.interruptTurn()`，其余当前已开放的原生会话调用 Codex 协调器。
4. Git 历史显示全局停止入口创建于 2026-07-31；Pi 会话级中断路由于 2026-08-05 加入，但全局停止入口没有同步扩展。
5. 因此，现场 5 个 Pi 活动轮次被错误发送给 Codex 协调器，均会以“不是当前 Codex 活动轮次”一类错误失败；退出协调层汇总为“无法停止 5 个执行轮次”。

## 初步缺陷定义

“停止任务并退出”应解释为停止执行宿主当前持有的全部活动工作，并在确认它们进入真实终态后关闭宿主与界面；它不应删除、归档或终结已经完成的历史会话。

活动工作至少包括：

- Codex 活动执行轮次；
- Pi 活动执行轮次；
- 与活动轮次绑定的等待交互；
- 其他运行中的 Runtime 会话和命令执行；
- 尚未开始的队列消息如何处置，等待用户确认。

## 推荐口径

推荐选择“停止全部活动工作并取消尚未开始的队列消息，然后退出”：

- 优点：符合用户点击危险操作后的直觉，不会在下次启动时自动继续本次明确放弃的后续输入；Codex、Pi 和未来 Agent 统一按各自适配器停止。
- 缺点：队列中尚未开始的输入也会被取消，需要在会话历史中保留清晰的“已取消”事实，避免用户误以为已经发送或执行。

不推荐只修 Pi 路由而保留队列：

- 优点：改动最小，当前 5 个停止失败可直接消失。
- 缺点：用户已经选择“停止任务并退出”，下次打开后队列仍可能继续派发，产品语义容易形成新的隐蔽缺陷。

## 已确认口径

1. 用户选择“停止任务并退出”时，同时停止 Codex、Pi 等全部活动工作并取消所有尚未开始的队列消息。
2. 历史会话、已完成消息和既有文件变更始终保留，不删除、不归档。
3. 停止方式为：先并行向各 Agent 发出一次中断请求，但不等待 Provider 返回终态，随后立即强制结束本机执行宿主并退出 Zeus。
4. 其他 Runtime 会话和命令执行一并强制结束；等待交互一并取消。
5. 强制退出前必须先持久化队列取消与活动轮次中断事实，避免下次启动自动重放。
6. 活动轮次在会话时间线中显示“已中断”；审计和技术详情保留“本机强制终止、Provider 终态未确认”的事实。
7. “已中断”不代表已经撤销或确认停止远端 API、Git 服务或其他外部系统已经接收的副作用。

## 方案取舍

### 已选：中断请求后立即强制终止

- 优点：用户选择退出后不再被失效或不响应的适配器阻塞；Codex、Pi、其他 Runtime 和命令执行使用同一个退出结果。
- 缺点：无法等待 Provider 确认真实终态，最后一批流式事件可能来不及到达；已经发往外部系统的动作不能由杀死本机进程撤销。

### 未选：等待 5 秒后再强制终止

- 优点：给 Provider 终态、数据库落库和日志排空留出时间，历史结果更完整。
- 缺点：退出存在肉眼可感知的等待，并可能再次被理解为卡住。

### 未选：停止失败时保持应用打开

- 优点：没有确认终态时继续保护执行现场，安全性最高。
- 缺点：正是当前用户无法退出的直接体验，不符合本任务确认的产品口径。

## 最终确认后进入的阶段

1. 设计统一的 Agent 停止路由，复用会话级 Codex/Pi 中断能力，避免全局入口再次写死单一内核。
2. 设计一次持久化的强制退出收口：取消队列和待交互，把活动轮次记录为已中断，并写入终态未确认的技术原因。
3. 收口命令执行与其他 Runtime 的进程树，随后由 Main 复验目标执行宿主身份并强制结束宿主。
4. 保留无法验证宿主身份或无法结束目标进程时的显式错误，避免误杀无关进程或假报退出成功。
5. 按项目门禁执行 `pnpm lint`、`pnpm typecheck`、`pnpm build`、`pnpm package:mac`，并仅使用隔离身份 `Zeus Test.app` 做真实运行检查；不新增单元测试，不操作正式 Zeus。

## 实现结果

### 多 Agent 与持久化收口

- 全局停止入口按会话 `agentKind` 路由：Pi 发送给 Pi 协调器，Codex 发送给当前 Codex 运行时世代；不再把所有轮次写死到 Codex 协调器。
- 停止入口不等待 Provider 返回终态；发出一次中断请求后，把活动轮次持久化为 `interrupted`，技术详情记录 `providerOutcomeUnconfirmed: true`。
- 已绑定执行轮次的 submission 收口为已完成，尚未绑定轮次的排队或暂停 submission 收口为已取消；下次启动不会自动重放。
- 全部待交互请求写入失败终态，原因与强制退出一致。
- 受影响会话保留为可见历史，会话、已完成消息、附件和文件变更均不删除、不归档。

### Runtime、命令与宿主收口

- 命令中心新增批量停止能力：活动命令记录为已取消，并立即向关联 Runtime 进程组发送停止与强制终止。
- 其他运行中 Runtime 同样立即强制终止，不再只发 `SIGTERM` 后直接报告停止成功。
- Main 在停止事实成功落库后进入 `force_quit`；强杀前重新读取控制面，逐项复验执行宿主实例 ID、PID 和危险 PID 边界。
- 执行宿主由独立进程组启动，Main 使用该已复验进程组身份一次结束宿主及其 Codex、Pi、Runtime 子进程；控制面不可达时不按陈旧 PID 强杀，身份不一致时保持应用打开并明确报错。
- 退出弹窗同步展示命令执行数量，危险操作文案收紧为“停止活动工作并退出”。
