# ZEUS-0187 新任务补充信息支持粘贴附件

## 任务信息

- 任务类型：优化
- 用户诉求：推送任务到新会话时，补充信息输入区域也需要支持粘贴附件。
- 现状：未提供。
- 预期：未提供。

## 当前阶段

- 阶段：实现完成，静态、构建、测试身份打包与隔离启动健康检查通过。
- 流程：已完成 `grilling` 与 `domain-modeling` 的逐项澄清和用户总确认。
- React 状态更新遵守函数式更新与稳定组件边界；附件卡、错误和预览按 WCAG 2.2 AA 的键盘、焦点、名称和动态反馈要求实现。

## 已查明事实

1. 任务详情的任务内容输入已经支持粘贴图片、文件、文件夹和超长文本物化资源；资源通过 Main 进程授权与物化，不直接信任 Renderer 给出的任意路径。
2. `TaskModelPushModal` 当前的“补充信息”只是普通 `textarea`，表单仅保存 `supplementalInfo: string`，没有本次推送附件草稿。
3. 任务本身已有字段归属附件；父任务和关联任务附件也可以在首发弹窗中逐项选择，并通过结构化附件通道发送，不写进正文。
4. 服务端会复验附件真实路径、文件类型、可信根和图片内容；任一不可用附件会阻止创建会话，不能静默丢弃。
5. 现有领域定义把“补充信息”限定为只补充本次新会话的首条输入，不改变任务内容，也不追改既有会话；“任务附件”则持续归属于任务字段。用户本次表述跨越了这两个不同生命周期。
6. 任务首发提交后会立即进入任务首发工作面；该工作面的普通 composer 已支持后续消息附件，但这不等于首条任务输入已经携带补充附件。

## 第一项已确认决策：附件生命周期

### 已选择：方案 A，本次推送附件

粘贴到“补充信息”的附件只进入本次新会话的首条输入，不写回任务附件。

优点：

- 与“补充信息只影响本次推送”的既有语义一致。
- 不会因为一次临时日志或截图，悄悄改变任务详情和后续其他会话的输入。
- 用户取消弹窗时可以连同补充文字一起放弃，行为容易理解。

缺点：

- 同一附件下次再次推送时需要重新粘贴。
- 需要定义独立的“本次推送附件”草稿和服务端复验契约，不能冒充已有任务附件。

确认结果：用户选择“仅本次推送”。领域统一使用“本次推送附件”，明确它不写回任务，也不影响后续其他推送。

### 方案 B：同时写入任务附件

粘贴后立即或提交时把附件关联到当前任务，后续推送也默认携带。

优点：

- 附件长期保留，下次推送不必重复添加。
- 可以复用任务附件持久化和字段归属能力。

缺点：

- “补充信息”会产生任务内容写入副作用，取消推送时的回滚语义复杂。
- 需要决定附件归属于优化现状、优化预期还是新增位置；自动选择容易违背用户意图。
- 一次性调试材料可能污染任务详情和后续会话。

## 第二项已确认决策：粘贴资源范围

已选择复用任务输入的现有粘贴语义：

- 截图、复制的图片、文件和文件夹都可成为本次推送附件。
- 普通文字仍进入补充信息正文，不因增加附件能力而改变正常粘贴。
- 超长文字沿用现有物化规则成为可恢复文本附件，不另设阈值或第二套处理逻辑。

优点：

- 用户在任务内容和推送补充信息中得到一致行为。
- 可以复用现有剪贴板解析、Main 进程授权、物化、去重和失败反馈边界。
- 不会出现同一份 Finder 文件在一个输入框能粘贴、另一个输入框却失败的割裂体验。

缺点：

- 范围不只包含图片，需要同时验证文件、文件夹、超长文本和普通文字回退。
- 文件夹与超长文本比仅截图方案占用更多验收场景。

## 第三项已确认决策：附件添加入口

已选择只支持在补充信息输入区域粘贴附件；本任务不增加“添加附件”按钮，也不增加拖放入口。

优点：

- 严格修复用户指出的粘贴缺口，不扩大弹窗操作密度。
- 不需要为新增按钮和拖放命中区增加额外交互状态。

缺点：

- 附件能力不如显式按钮容易发现。
- 只使用鼠标的用户没有等价的附件添加入口，需要先通过系统剪贴板复制资源。

## 第四项已确认决策：附件呈现

已选择在补充信息区域、文字框上方复用完整资源卡：图片可放大预览，普通文件可打开，所有附件都可单独移除。

优点：

- 粘贴是否成功、即将发送什么可以直接核对，不依赖短暂提示。
- 复用任务附件已有的预览、打开、移除和键盘语义，减少新的交互语言。
- 用户在提交前可以发现误粘贴并移除。

缺点：

- 多附件会增加弹窗内容高度，需要限制资源区域并验证窄窗口滚动。
- 相比紧凑附件条，需要加载图片预览并处理预览失败状态。

## 第五项已确认决策：允许仅附件推送

补充文字可以为空；只要存在本次推送附件，用户仍可正常确认推送。附件继续走结构化通道，正文不添加伪造的占位说明。

优点：

- 截图、日志或文件本身已经足够表达补充内容时，不强迫用户重复写说明。
- 与会话 composer 支持仅附件消息的行为一致。

缺点：

- 没有文字说明的附件可能降低模型理解度，但这是用户明确提交的真实内容，产品不应代写正文。

## 第六项已确认决策：附件草稿生命周期

本次推送附件在当前弹窗过程内保留：登录、能力刷新、上下文刷新和提交失败时继续存在；用户明确关闭弹窗后放弃，重新打开同一任务时不恢复。

优点：

- 外部登录或失败重试不会迫使用户重新粘贴。
- 明确关闭仍能彻底放弃临时材料，不形成难以发现的长期草稿。
- 生命周期与补充文字保持一致。

缺点：

- 用户误关弹窗后不能恢复附件。
- 实现必须覆盖异步登录、上下文过期重确认和失败重试，不能只保存在临时 DOM 中。

## 已确认的共同理解

1. “补充信息”中的附件统一称为“本次推送附件”，只进入这次新会话首条输入，不写回任务详情，也不影响后续推送。
2. 只增加粘贴入口，不增加附件选择按钮和拖放。
3. 粘贴行为完整复用任务输入：支持截图、图片、文件、文件夹；普通文字保持文本粘贴，超长文字沿用现有物化规则。
4. 附件显示在补充信息文字框上方，使用完整资源卡；图片可放大、文件可打开、附件可移除。
5. 允许补充文字为空、仅携带附件推送。
6. 登录、上下文刷新和提交失败时保留附件；明确关闭弹窗后放弃。
7. 同一资源重复粘贴沿用现有去重语义；失败时保留已有文字和已成功附件，并显示可恢复错误，不把失败资源伪装成已添加。
8. 附件通过结构化通道发送，不把路径、MIME、大小或 JSON 拼进补充文字；提交时冻结进本次首发布局快照，后续任务变更不追改它。
9. 服务端继续复验真实文件、可信目录、文件类型和图片内容；任一待发送附件不可用时阻止创建会话，不静默跳过。
10. 非 Codex Adapter 没有真实附件协议时继续明确拒绝，不伪装成已发送。

整体优点：补充材料可以在首条任务输入中真实送达，且不污染任务长期内容；交互、安全和失败语义与现有任务附件保持一致。

整体代价：需要贯通 Renderer 草稿、Main 进程物化、任务首发请求、服务端冻结和 Provider 结构化附件链路；验证范围必须覆盖多种剪贴板资源、失败重试与真实首轮接收，不能只看资源卡出现。

## 实施设计

### 领域与数据归属

- `任务附件` 继续归属于任务字段并持久保存。
- `本次推送附件` 归属于一次任务首发请求，使用会话输入资源根与精确路径授权，不写入任务记录。
- `任务首发布局快照` 新增本次推送附件的有序元数据，只保存展示和位置需要的键、名称、类型、MIME 与大小，不保存授权令牌或原始路径。

### Renderer

1. `TaskModelPushForm` 增加带唯一位置键的本次推送附件草稿。
2. `TaskModelPushModal` 的补充信息文本域复用会话输入资源粘贴处理；不挂载选择按钮和拖放事件。
3. 资源按真实身份去重；新资源分配本次推送位置键，移除与超长文本恢复使用函数式状态更新，避免异步粘贴覆盖最新表单。
4. 补充信息区域在文本框上方显示完整资源卡；图片可打开模态预览，文件和文件夹通过 Main 的受控资源打开接口处理。
5. 本地粘贴错误使用 `role="alert"`，保留文字和已成功资源；处理中使用 `aria-busy` 并阻止重复提交。
6. 登录、仓库刷新和任务上下文重确认继续携带完整表单；明确关闭时由既有弹窗重置逻辑放弃草稿。

### Main 与本机资源授权

1. 继续复用 `conversationInputResources` 读取原生剪贴板、物化截图与超长文本、生成外部文件精确授权。
2. 增加只读打开待提交会话资源的 IPC；Main 先解析授权或托管根内真实路径，再调用系统打开，不接受 Renderer 自报任意路径。
3. 不把本次推送附件复制到任务附件根，不新增任务附件关联，也不删除用户原文件。

### 请求与服务端冻结

1. `StartTaskModelPushRequest` 增加 `supplementalAttachments`，只包含位置键、名称、类型、MIME、大小和 `localPath/uploadRef` 二选一；可恢复长文本正文不进入请求元数据。
2. Local Server 对每项附件执行数量、字段、位置键唯一性、授权令牌、真实路径、普通文件/目录、真实大小和图片签名复验。
3. 服务端把复验后的资源并入任务附件输入，但按位置键而非物理路径合并，避免同一资源在不同语义位置互相吞掉。
4. 本次推送附件放在布局快照的“补充信息”区域，Provider 输入顺序为区域标题、结构化附件、补充文字；仅附件时仍形成合法输入。
5. Codex 与 Pi 继续消费同一布局快照；Provider 不支持的资源保持现有明确失败，不把路径或 JSON 拼入用户正文冒充附件。

### 历史与即时投影

1. 弹窗“将发送的任务内容”预览显示本次推送附件占位与补充文字。
2. 后台创建工作面使用同一位置键投影本次推送附件，不等待服务端回包后才出现。
3. 已发送用户消息按布局快照把真实会话资源放回补充信息区域；旧快照没有新字段时按空数组兼容。

### 方案优缺点

优点：

- 一次性附件不会污染任务长期内容，首发前后展示与 Provider 输入可以按位置键对账。
- 复用会话资源授权和剪贴板能力，不新增不受控本机路径通道。
- 同一布局同时服务乐观工作面、持久消息、Codex 和 Pi，避免各自猜测附件位置。

缺点：

- 需要同步修改共享类型、Renderer、Main、Local Server 和两种消息投影，交付面较宽。
- 为满足完整资源卡，需要补充待提交会话资源的安全打开能力和图片大图焦点管理。
- 同一真实文件如果既属于任务字段又被用户再次粘贴到补充信息，会按两个明确位置发送两次；这是保留用户语义位置的代价。
