# ZEUS-0189 答案选项自由输入粘贴附件

## 任务目标

让普通用户询问中的自定义回答与纯自由输入支持粘贴附件，并确保附件真正进入当次 Agent 上下文，不只停留在界面预览。

## 已核对事实

- 询问界面由 `PendingRequestSurface.tsx` 中的 `RequestUserInputPanel` 承载，自定义回答和纯自由输入当前只保存字符串。
- 这些输入控件没有接入会话已有的 `useConversationInputResources` 资源收集管线，因此粘贴图片、文件或文件夹时不会生成附件。
- 普通会话输入已支持图片、文件、文件夹和超长粘贴文本，包含本机路径授权、物化、去重、预览、移除和失败保留能力。
- `request_user_input` 的当前 Renderer、Local Server 与 Coordinator 回答契约均是按问题 ID 提交字符串数组，没有原生附件字段。
- 因此本任务需要同时明确资源范围、回答与附件的交付时序、敏感问题边界、草稿恢复与失败语义。

## 初步方案取舍

### 方案 A：只处理图片粘贴

优点：界面改动较小。

缺点：与会话输入的“附件”心智不一致；文件、文件夹和超长文本仍然无法使用。

### 方案 B：复用完整会话附件能力（推荐）

优点：用户在会话输入和询问回答中使用同一套附件类型、资源卡和失败恢复规则，也能复用已验证的本机安全边界。

缺点：需要处理多个问题切换时的附件归属，并增加底层回答交付编排，不是单一前端事件补丁。

## 待用户逐项确认

1. 资源类型：已确认与会话输入一致地支持图片、文件、文件夹和超长文本。
2. 回答交付：已确认附件必须随当前回答交付；Zeus 先把结构化附件注入当前轮次，确认 Provider 接收后再提交询问文字答案。不允许把附件默认排到下一轮。
3. 敏感回答：已确认普通自由回答支持附件；Agent 通过 `isSecret` 标记的敏感问题继续只允许文字，不显示附件能力，保持不写入草稿和会话记录的现有承诺。
4. 多问题归属：已确认附件归属于当前具体问题；切换上一个或下一个问题时分别恢复各自的文字和附件。
5. 纯附件回答：已确认允许不输入文字直接提交附件；Zeus 在底层字符串协议中使用明确的附件占位文案，已回答记录需展示真实资源。
6. 跳过与关闭：已确认为明确放弃回答，清除文字和附件草稿；不删除用户原文件，只清理 Zeus 为剪贴板生成的未提交托管副本。
7. 重启恢复：已确认非敏感问题的文字和附件按请求 ID 与问题 ID 持久化；Zeus 界面重启后，只要请求仍待回答就恢复。
8. 添加入口：已确认同时支持粘贴、附件选择器和拖放。

## 实施设计

### 界面与草稿

- `RequestUserInputPanel` 按问题 ID 管理文字、选项和附件草稿，非敏感自由输入复用会话资源收集器。
- 自定义回答和纯自由输入共用资源卡；列表支持预览、移除和可恢复长文本。
- 有附件时允许空文字提交，底层答案使用明确的“见附件”占位；界面历史优先显示真实资源。
- 草稿只保留 Renderer 已获得的精确资源身份，恢复时仍由 Main 与 Local Server 重新验证路径和授权。

### 两阶段交付

1. Local Server 先验证请求仍待回答、问题 ID 完全匹配、问题不敏感，并对附件逐项验签、`realpath` 和文件类型复验。
2. 按请求 ID 创建稳定的内部 `steer_now` 提交，把问题与附件映射文字、结构化附件一并注入当前等待轮次。
3. Provider 确认接收后，再调用原生 `request_user_input` 响应协议提交字符串答案。
4. 附件注入失败时不回复问题；附件已接收、文字回复失败时，重试复用稳定幂等身份，禁止重复注入。
5. 原轮次已因执行宿主交接失效时，附件与恢复回答共用新的安全续接提交，不将附件排成无关的下一条消息。

### 历史展示

- 请求解决记录持久化每道问题的已验证附件展示身份，`AnsweredRequestHistory` 在对应问题下展示资源卡。
- 为底层协议注入的内部附件补充消息不单独显示为普通用户气泡，避免同一用户意图重复。

## 实现结果与取舍

### 已落地

- Renderer 复用现有会话附件收集器和资源卡，没有建立第二套文件读取逻辑。
- Local Server 仅接受规范问题 ID，禁止敏感问题附件，并复用会话附件的授权路径复验。
- Coordinator 用稳定幂等键先将附件 `steer_now` 到当前等待轮次，再回复 `request_user_input`；内部附件消息不重复投影成普通用户气泡。
- 回答失败不清空草稿；成功解决后将附件展示元数据持久化到对应问题。

### 优点

- 附件属于当次询问回答，Agent 不会在下一条无关消息才看到。
- 原有路径 capability、托管目录、预览和资源大小边界继续有效。
- 多问题、纯附件、重启恢复和已回答历史的用户心智一致。

### 缺点与限制

- Provider 原生回答协议只接受字符串，因此仍需要“附件注入 + 字符串回答”两步编排，代码和失败状态都比纯文字回答复杂。
- Pi 目前没有等价的结构化附件交付通道，本次保持不显示入口，而不做只展示不交付的假能力。
- 实机验收依赖一个不与其他任务共用数据目录的 `Zeus Test.app` 运行环境。
