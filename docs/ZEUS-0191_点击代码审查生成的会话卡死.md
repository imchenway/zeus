# ZEUS-0191 点击代码审查生成的会话卡死

## 任务信息

- 类型：缺陷
- 用户现象：从环境信息卡片启动代码审查后，新会话长时间留在空白页，首条“请审查当前工作区的完整代码变化”显示为“等待其他会话完成后按顺序自动发送”。
- 截图时间：`2026-08-11 18:28:29 +0800`。
- Git 边界：未经用户明确要求，不执行 commit、push、merge 或 revert。
- 验证边界：不操作生产身份 `Zeus.app`；开发验收只能使用独立身份和独立数据目录的 `Zeus Test.app`。

## 当前阶段

- 已完成现场只读对账、方案确认、代码实现、静态检查、完整构建和独立测试身份打包。
- 未修改正式数据，未停止或重启正式 Zeus 与执行宿主，也未执行 Git 提交或远端操作。
- 真实 Electron 界面验收仍受当前机器上另一条任务的同 Bundle ID 测试实例和 Computer Use 服务不可用影响，未把构建或普通浏览器页面冒充为真实运行验收。

## 已确认领域口径

- `CONTEXT.md` 已把“AI 代码审查会话”定义为基于当前开发现场的独立复核会话，不是开发会话续聊或普通 Git 变更查看。
- `CONTEXT.md` 已把“宿主安全交接”定义为新版界面暂时连接旧宿主、只限制旧宿主不支持的新能力，并在可恢复边界切换到唯一新宿主。
- 因此本缺陷不应定义为普通“会话排队”，而是“旧执行宿主接收了自身不理解的新版代码审查命令”。

## 正式现场证据

### 界面与执行宿主版本错配

- 正式 `/Applications/Zeus.app` 版本为 `0.2.36`。
- 当前唯一执行宿主 PID 为 `64378`，启动于 `2026-08-11 11:39:21 +0800`。
- `/Users/david/.zeus/runtime/execution-host/rendezvous.json` 声明宿主 `appVersion=0.2.31`、`protocolVersion=1`。
- 新界面与旧宿主使用相同的粗粒度协议版本 `1`，但协议内已新增 `code_review` 请求语义；当前握手没有声明该能力。

### 截图会话的持久事实

- 截图对应任务为 `ZEUS-0176 环境信息卡片优化`。
- 新会话 ID 为 `conversation_14472e641fd2b7508ec519c5`，创建于 `2026-08-11T09:54:33.098Z`。
- 会话被旧宿主持久化为普通标题 `任务会话：环境信息卡片优化`，而不是新版语义要求的 `代码审查：环境信息卡片优化`。
- 会话状态为 `status=starting`、`providerState=unbound`，`providerThreadId` 为空，没有任何 `conversation_turns` 记录。
- 首条 submission 为 `conversation_submission_b9834f91ad5e3d2502c66e14`，从创建起始终是 `queued`，没有 `providerTurnId`、`dispatchedAt` 和 `resolvedAt`。
- submission 中只有界面短文“请审查当前工作区的完整代码变化。”，缺失新版服务端才会生成的冻结基线、单仓边界、只分析不修改等完整审查提示。
- submission 的调度上下文没有新版代码审查路径的 `bypassConcurrency=true`，因此旧宿主把它留在普通项目队列。

## 根因链

1. ZEUS-0176 新界面增加了 `source=code_review` 的专用创建语义。
2. 升级后的 `0.2.36` 界面仍附着在 `0.2.31` 执行宿主上；宿主交接尚未完成。
3. Renderer 已收到 `executionHostTransition=draining_previous` 所需的版本事实，但业务页没有消费该事实，也没有按能力限制新版专属写操作。
4. 旧宿主不理解代码审查的完整服务端语义，却没有拒绝未支持命令，而是退化成普通会话。
5. 普通会话又被项目并发门禁排队，导致没有 Provider thread 和 turn 的空会话长期显示为“等待其他会话完成”。

## 修复选项与取舍

### 选项一：只修代码审查创建路径

在当前服务端保留审查会话的专用标题、完整提示和并发绕过语义。

优点：改动小，当界面与宿主已经同版时可以正常启动审查。

缺点：截图现场中这些代码已经存在于新版源码，无法阻止新界面继续向旧宿主发送其他新命令，不是真实根因修复。

### 选项二：修复宿主跨版本能力门禁与交接收敛（建议）

- 执行宿主握手显式广播可用业务能力，或者在新增命令语义时提升协议版本；不再只用数字 `1` 覆盖所有业务变更。
- 新界面连接旧宿主时，上一版已支持的读取、新建会话和任务推送继续可用；代码审查等旧宿主不支持的新能力局部阻断并说明正在交接。
- 专用请求继续由服务端 fail-closed（安全失败）：无法识别的 `source` 必须拒绝，不得降级成普通会话。
- 宿主安全交接在没有真正仍在产生副作用的轮次时必须自动收敛；已经卡住的未绑定队列不能无期阻断宿主切换。
- 对已产生的错误会话，不自动重发可能有副作用的首条消息；将其标记为可理解的失败或提供用户明确重试。

优点：修复真实失败链，保留无损升级对存量轮次的保护，同时防止未来其他新界面能力被旧宿主错误执行。

缺点：需要同时改执行宿主协议、Main 交接、Renderer 局部能力门禁、Local Server 请求验证和历史错误状态收敛，验证面明显大于单点修复。

## 用户质疑与规划修订

用户指出：代码审查本质上只是向一条新会话发送审查提示，应该复用现有会话链路，不应如此容易产生第二套错误。

经对照源码，该质疑成立：

- Renderer 已复用通用 `onStartConversation` 和持久接受信封，这一层不应另起流程。
- Local Server 的 `body.source === 'code_review'` 分支却自行复制了模型解析、权限继承、环境恢复、Pi/Codex 分流和启动参数组装。
- 代码审查真正特有的只有：从来源会话复验精确工作区、生成服务端权威审查提示、使用专用标题和短展示文案；后续的会话创建、Provider 启动、持久化与实时投影都应进入唯一主链。
- 跨版本宿主错配之所以能产生空会话，是因为旧宿主对未识别的 `source` 没有 fail-closed，通用分支又允许它降级进入普通队列。

### 修订后的建议方案

1. 提取唯一的“会话启动计划”：统一承载标题、Provider 提示、界面展示文案、模型、权限、环境和调度语义。
2. 普通新会话、任务首发和代码审查只负责生成该计划；实际的 Codex/Pi 启动、持久接受、导航和失败收敛共用同一执行器。
3. `code_review` 保留为受控的提示生成类型，不保留第二套会话生命周期。
4. 新界面正在连接旧宿主时，仅对旧宿主不支持的代码审查入口显示“正在安全交接”；上一版已有的通用会话能力不受影响。
5. Local Server 对未支持的专用 `source` 必须明确拒绝，禁止默默转成普通会话。
6. 已有错误会话没有 Provider thread，但由于旧数据未持久化 `source=code_review`，不使用短文相等的启发式逻辑自动重发或改写，避免误处理用户手工发送的同文消息。

该方案的优点是代码审查只保留必要的领域差异，会话生命周期只有一条主链；缺点是需要重构 Local Server 已有分支，并补齐交接期局部门禁，不是改一个提示字符串即可完成。

## 冲突处理会话的同类问题

用户进一步指出：代码交付中的“AI 处理”也是向专用会话发送提示，会话创建与消息派发同样应该复用主链。

源码对账结果支持该判断：

- `/api/tasks/:taskId/integrations/:integrationId/conflict/ai-session` 当前直接生成 `conversationId`、`submissionId`、`idempotencyKey` 和 `clientUserMessageId`。
- 该端点自行复制 Pi/Codex 分流，并分别直接调用 `piNativeCoordinator.startConversation` 与 `codexNativeCoordinator.startTaskConversation`。
- 重复点击主要依赖进程内 `taskConflictAiOperations` Map 避免并行创建，而不是通用新会话链的持久幂等接受信封；宿主切换或结果未知时更容易漂移。
- ZEUS-0152 的历史根因已经是“会话已创建、模型未收到、界面提示重试”，与本次代码审查空会话属于同类生命周期分叉问题。

### 复用边界

冲突处理不只是一段不同提示，仍然需要保留以下专属规则：

- 创建前复验精确任务、工作区、合入记录、目标 HEAD 和任务 HEAD。
- 把用户当前草稿写入隔离 integration worktree，不直接改用户主工作区。
- 使用可写权限且只允许 integration worktree 作为写入根。
- 轮次结束后再由 Zeus 完成冲突、目标 HEAD 复验和本地合入收尾，不把 commit、目标分支更新或 push 交给通用会话启动器。

通用主链应负责的部分是：持久操作身份、会话与 submission 创建、Agent 和模型分流、Provider thread/turn 启动、实时投影、持久接受、错误与未知结果收敛。

优点：代码审查与冲突处理共享唯一会话生命周期，各自只保留领域前置和后置规则；不再反复修复“空会话”、“假排队”和“重复点击”。

缺点：任务范围从代码审查单点缺陷扩展为两条专用会话入口的主链收敛，需要同时验证只读审查与可写隔离合入两类安全边界。

## 产品表达修订

用户指出“新版宿主、旧版宿主”等内部概念过多且混乱。该质疑成立：

- 执行宿主、协议版本和安全交接是 Zeus 内部责任，不属于用户必须理解的产品概念。

## 会话身份口径

用户确认：

- 每次用户点击并确认“代码审查”或“AI 处理”，都是一次新的业务会话创建动作。
- 内部执行能力切换只能接管并继续这次点击已经建立的同一条会话，不得再新开一个会话框或追加第二条会话记录。
- 因此需要区分“用户新的显式点击”与“同一点击中的内部执行切换”：前者创建新会话，后者必须保持原会话身份。

优点：每次审查或冲突处理都可独立回看，同时内部切换不会制造重复会话。

缺点：前端与服务端必须用稳定操作身份精确区分用户的两次显式点击和同一点击的结果未知重试，不能只依赖内存中的忙碌标记。

## 冲突处理隔离方式澄清

用户追问隔离是否同时新建分支，以及是否通过 worktree 实现。源码事实如下：

- 现有 `startTaskBranchIntegration` 已使用 `git worktree add --detach <integrationPath> <targetHeadSha>` 创建隔离合入目录。
- 该目录处于 detached HEAD，不创建新的业务分支；随后只在这个目录执行 merge 或 squash。
- 候选结果完成后，Zeus 重新比较目标分支 HEAD；只有仍等于创建候选时冻结的 `targetHeadSha`，才允许安全更新本地目标分支。
- 目标工作区不干净或目标 HEAD 已变化时，候选结果保留在隔离目录，不覆盖用户当前现场。

若坚持“每次显式点击都创建新冲突处理会话”，建议每次点击同时创建独立的冲突处理尝试目录：

1. 从同一条合入记录冻结的目标 HEAD 与任务 HEAD 创建新的 detached worktree，不新建分支。
2. 在该 worktree 内重新形成同一组 Git 冲突，再写入本次界面草稿并交给该会话处理。
3. 每条会话只能写自己的 worktree；不能让两条会话同时写现有 `integrationPath`。
4. 第一条完成的安全候选仍需通过目标 HEAD 比较后才能落到目标分支；目标分支一旦变化，其余尝试标记为已过期，不自动覆盖。

优点：不会污染分支列表，也不会让并行会话互相覆盖文件；每次点击和每条会话的现场一一对应。

缺点：每次点击都需要重新创建 worktree 和重放合入，增加磁盘占用；失败或过期尝试还需要明确的保留、查看与清理策略。

## 实现结果

### 唯一会话启动主链

- `packages/local-server/src/index.ts` 新增统一的任务会话启动计划执行器。
- 普通任务会话、任务推送、代码审查和冲突处理都先组装计划，再由同一个执行器完成 Pi/Codex 分流、固定 conversation/submission 身份、Provider 派发和持久接受生命周期。
- Pi 启动也会在打开 SDK 会话前写入同一套“已准备、Provider 调用已开始”幂等阶段，结果未知时禁止静默重复启动。
- 冲突处理包装端点不再直接生成随机会话并调用 Coordinator，而是携带客户端幂等键进入 `/api/tasks/:taskId/conversations` 使用的同一持久主链。
- 服务端对未知 `source` 明确拒绝，不再把新语义降级成普通会话。

### 代码审查边界

- 代码审查工作目录固定为来源会话对应的单仓任务 worktree，不使用整个环境根目录，也不复制额外 worktree。
- 权限固定为只读，写入根为空；前端不能请求扩大权限。
- 仍由服务端生成审查提示、来源基线和唯一仓库范围；前端短文只用于展示。

### 冲突处理尝试

- `packages/storage` 增加 `task_integration_attempts` 持久表，记录尝试、会话、submission、独立 worktree、冻结 HEAD 和状态。
- `packages/git-core` 每次从合入记录冻结的目标与任务提交创建新的 detached worktree，不创建临时业务分支。
- 每条冲突会话只能写自己的尝试 worktree；多条尝试可并行，不再阻断原三栏手工处理。
- 独立现场实际已无冲突或合入命令异常失败时，新创建的 worktree 会立即安全回收；草稿写入前先持久化尝试身份，失败后可按同一幂等身份恢复。
- 第一条候选仍通过目标 HEAD 比较后安全落地；其他尝试标记过期，运行结束后回收 worktree。
- 过期尝试的后续消息明确拒绝，不能回退到任务 worktree 或项目目录继续写入。
- 成功尝试会回收原始冲突 worktree；本地目标工作区不安全时仍保留成功候选用于后续同步。

### 准备态与同一身份续接

- 当界面仍在等待内部执行能力切换时，代码审查与冲突处理只先写入本机待启动信封，不创建会话、submission 或排队消息。
- 用户可见文案为“正在准备，完成后自动开始”，并提供取消；不暴露宿主、协议或版本术语。
- 内部切换完成并刷新后，Renderer 使用原幂等键自动派发，因此仍是本次点击对应的同一条会话，不生成第二条会话。
