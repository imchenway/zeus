# ZEUS-0193 ChatGPT iOS 远程回复消息在 Zeus 不可见

## 任务状态

- 阶段：已按用户确认方案完成开发、静态检查、迁移探针、打包和隔离宿主启动验证；真实 iOS 双端闭环待设备验收。
- 类型：缺陷。
- 用户现象：在 ChatGPT iOS 中通过远程能力回复后，消息在 Zeus 会话中不可见。
- 现状、预期、复现步骤和标签：用户未提供。

## 已确认历史边界

历史任务 `ZEUS-000063` 验证的是 iOS 处理同一个阻塞交互请求后，Zeus 根据 `serverRequest/resolved` 收口桌面的待回答状态。该回执只说明原请求已解决，不携带远端答案正文，也不等于远程新发的普通会话消息已经同步到 Zeus。

当前领域模型中的“远程接管”也明确区分两类行为：

1. 回答当前阻塞交互请求，按原请求身份继续同一执行轮次；
2. 从远程端新增普通会话消息，形成新的执行轮次。

“远程回复”可能同时指向这两类行为，修复链路不同，不能在用户确认前混为一类。

## 当前代码事实

当前协调器可以按已知 `providerThreadId` 找到 Zeus 会话，但 `item/started`、`item/completed` 和 `turn/completed` 都要求本地已经存在同一 `providerTurnId` 的执行轮次记录。Zeus 自己发起轮次时会先建立该记录；若 ChatGPT iOS 从远程端新建轮次，当前代码没有在 `turn/started` 时接纳并建立对应本地轮次，因此其后普通用户消息与智能体回复会被忽略。

这只是静态代码证据，尚未用本任务的真实 iOS 操作、Provider 事件流和 Zeus 数据库记录完成闭环验证。

### 问题 1：缺陷对象

建议把本任务中的“远程回复”精确定义为“远程普通消息”：用户在 ChatGPT iOS 的普通输入框输入一段新文字并发送，而不是点击 Zeus 当前 `request_user_input` 的选项、自定义答案或跳过。

建议预期：该远程普通消息、它启动的同一执行轮次以及后续智能体输出，都应自动进入原 Zeus 会话并实时可见，不依赖切换会话或手动刷新。

状态：用户已确认，缺陷对象是 ChatGPT iOS 普通输入框发送的新消息。

## 根因说明

当前实现只完整接纳“由 Zeus 本机提交启动的执行轮次”，没有接纳“由 ChatGPT iOS 远程启动的执行轮次”。

### Zeus 本机发送路径

1. Zeus 先持久化本机提交；
2. Zeus 调用 Codex 启动执行轮次；
3. Codex 返回轮次 ID 后，Zeus 创建本地轮次记录，并把它绑定到本机提交；
4. 后续 `item/started`、`item/completed` 和 `turn/completed` 事件可以通过该轮次 ID 找到本地轮次，进而保存用户消息、智能体消息并广播给界面。

### iOS 远程发送路径

1. ChatGPT iOS 直接通过官方远程宿主向同一个 Codex thread 发送普通消息；
2. 该动作不经过 Zeus 的本机提交接口，因此 Zeus 没有本机提交记录；
3. Codex 会向 Zeus 已连接的宿主发送新轮次和消息事件，但当前协调器没有在 `turn/started` 时接纳并创建远程轮次；
4. `item/started`、`item/completed` 和 `turn/completed` 处理都先查找已存在的本地轮次，找不到就直接返回；
5. 因此消息没有进入 Zeus 的 `conversation_turns`、`conversation_items` 和 `conversation_messages`，Renderer 也收不到对应会话广播。

数据库模型进一步暴露了同一假设：`conversation_turns.client_submission_id` 当前是必填字段，意味着每个轮次都被假设为必须由一条 Zeus 本机提交产生。远程普通消息没有这项身份，现有模型无法原样表达它。

会话重新打开时，完整快照仍从 Zeus 本地持久记录构造，没有把 Codex thread 中缺失的远程轮次自动补入。因此刷新或切换会话通常也不会恢复该消息。

## 为什么阻塞请求远程回答可以工作

历史远程接管只为 `serverRequest/resolved` 建立了专门回流：Zeus 可以使用运行时世代和原请求 ID 找到本地待回答请求，并把它标记为由远端解决。这个过程不要求创建一条新的用户消息或新的本地轮次，所以能够生效。

普通消息会创建或引导真实执行轮次，需要补齐远程轮次、用户消息、智能体输出和生命周期的整条投影链。旧实现没有覆盖这条链路，因此出现“手机端已经发送并继续，Zeus 中却看不见”的不一致。

## 证据边界

以上根因由当前协调器事件门禁、轮次持久化结构和完整快照来源共同确认。尚未读取用户本次复现对应的真实 Provider 事件日志与本机数据库记录，因此当前结论是代码级根因，不冒充本次设备现场已经完成动态闭环取证。

## 官方协议能力

OpenAI 官方 Remote 文档明确把“在已有任务中发送新指令”作为手机远程能力；App Server 文档明确区分：

- `turn/start` 为 thread 创建新轮次；
- `turn/steer` 向当前活动轮次追加用户输入，不创建新轮次；
- 新轮次与其内容通过 `turn/started`、`item/started`、`item/completed`、`turn/completed` 等标准事件表达；
- `item/completed` 是条目的权威最终状态；
- `thread/read` 携带 `includeTurns: true` 可以读取已保存 thread 的完整轮次历史，而不恢复或订阅该 thread。

官方依据：

- <https://learn.chatgpt.com/docs/remote>
- <https://learn.chatgpt.com/docs/app-server>

这说明 Zeus 不需要建立第二套远程消息协议，但必须同时消费实时事件和权威历史快照。

### 问题 3：多端无感续接的精确定义

用户提出 Zeus 与 ChatGPT iOS 两边应当可以随意切换发送且操作无感。建议把该目标精确定义为“多端无感续接”：

1. 两端始终操作同一个 Zeus 产品会话和同一个 Provider thread，不因发送来源改变会话身份；
2. 任一端发送的普通消息、模型过程和最终回复都自动投影到另一端，不要求刷新、重新配对或重新打开会话；
3. 模型空闲时，先被权威宿主接受的消息创建下一轮；
4. 模型正在回复时，明确作为当前轮引导的消息进入当前轮，普通后续消息进入下一轮等待，不能凭客户端来源改变语义；
5. 两端近乎同时发送时，以权威宿主实际接受顺序串行收敛；任一消息都不得被覆盖、模糊去重或自动重复发送；
6. 一端暂时离线后重新连接，只补齐修复生效后同步检查点之后的缺口，再继续实时事件；不追溯修复前历史。

优点：用户可以自然地在 Mac 与手机之间切换，同一工作现场不会分叉；消息顺序、执行状态和权限请求都可对账。

代价：严格意义上的“同时发送”仍需要权威顺序，不能承诺两条普通消息同时各自成为活动轮次；界面需要如实显示引导中、等待下一轮或已进入轮次，而不是把内部竞争伪装成两个都已立即执行。

状态：用户回复“继续”，确认采用上述“多端无感续接”定义。

### 问题 4：修复生效后的断线缺口

“不恢复修复前历史”与“修复后断线重连”是两个边界。建议修复生效后保存最后一个已接纳的 Provider 事件身份；若 Zeus 短暂断线或执行宿主重连，只校准该检查点之后的新 turn 和 item，不扫描或补写修复前的旧缺口。

优点：满足多端无感续接，修复后不会因为一次网络抖动或界面重启再次漏掉新消息，同时严格遵守“不恢复当前历史”的范围。

代价：仍需保留增量检查点和重连校准；如果完全取消校准，实时连接窗口内的任何短暂丢包都会重新制造相同现象。

状态：用户已确认需要。修复后以同步检查点为边界，Zeus 短暂断线、重启或执行宿主重连时自动补齐此后的新消息；不追溯修复前历史。

### 问题 5：是否在会话正文突出消息来源

建议主会话正文不为 iOS 普通消息增加单独气泡样式或醒目的“来自手机”标记，让它和 Zeus 本机发送的普通消息保持同一阅读语义；但在持久化记录中保留发送来源，供问题诊断和对账使用。

优点：符合“随意切换、操作无感”的目标，会话不会因设备来源被视觉切碎；后台仍能定位跨端同步问题。

代价：用户仅看正文时不能立刻判断某条消息从哪台设备发出。如果需要明显来源标识，就会增加界面信息和跨端差异感。

状态：用户补充确认可以在远端消息底部展示一个低干扰的小手机图标，但不增加“来自手机”等正文文字。该图标只能由 Zeus 本地结构化元数据驱动，不得拼入消息正文、发送给 Provider 或进入模型上下文。若实现同步身份、幂等去重或诊断需要来源字段，可以复用同一字段；不能仅靠正文或图标猜测来源。

优点：跨端切换不会造成草稿丢失或误发，消息同步只改变会话记录，不擅自改变用户意图。

代价：新消息出现后，本机草稿的上下文可能已经过时，需要用户自行检查后再发送。

状态：用户已确认原样保留。远端消息到达只更新会话记录，不清空、不自动发送，也不合并 Zeus 本机尚未发送的文字或附件。

## 方案调研新增事实

本机 `codex-cli 0.147.0` 生成的 App Server TypeScript schema 表明：

- `turn/started` 携带完整 `Turn`，其中包含稳定 turn ID、状态、时间和当前 items；
- `item/started`、`item/completed` 携带稳定 thread、turn、item 身份；
- `thread/read(includeTurns: true)` 可以返回 turn 历史；当前协议还提供 `thread/turns/list` 的分页读取和 `itemsView: full`；
- `userMessage` 只有消息 ID、可选 `clientId` 和内容，没有逐条消息的设备类型、平台或远程客户端 ID；
- Remote Control 虽能单独列出已配对客户端及其 `deviceType`、`platform`，但 turn/item 事件没有字段把一条用户消息关联到其中某台设备。

因此 Zeus 可以使用“是否精确匹配本机 submission/client message 身份”可靠区分本机输入与非本机输入，但不能把某一条非本机输入严格证明为来自 iOS。

### 问题 8：手机图标的真实语义

建议把小手机图标定义为“远程设备输入”：凡是 Provider 用户消息无法精确匹配 Zeus 本机 submission，就显示小手机图标。当前用户只通过 ChatGPT iOS 远程发送时，视觉结果与预期一致；未来如果网页或其他远程客户端向同一 thread 发消息，也会显示同一图标。

优点：只依赖 Provider 稳定身份，不猜测设备，不会把来源文字送入模型；当前 iOS 场景可以实现。

代价：图标不能证明具体是 iPhone，也不能区分不同远程设备。备选是暂不显示图标，等协议提供逐消息设备身份后再做精确标记。

状态：用户已确认接受。小手机图标的真实语义是“非 Zeus 本机的远程输入”，不承诺具体设备型号或平台。

## 推荐修复方案

### 一、让执行轮次表达真实来源

把 `conversation_turns.client_submission_id` 从必填调整为可空：

- Zeus 本机发起的 turn 继续绑定真实 submission；
- 远程发起的 turn 保持 `client_submission_id = NULL`；
- 后续若 Provider 用户消息的 `clientId` 精确匹配到本机 submission，再把同一 turn 绑定回真实 submission，处理 RPC 返回与 `turn/started` 事件先后不确定的竞态；
- 不为远程 turn 伪造 submission，不让它进入本机队列、重发、草稿恢复或本机发送统计。

优点：领域事实真实，现有 submission 的发送、恢复和幂等语义不被污染；本机与远程竞态可以通过稳定身份最终收敛。

代价：需要安全迁移 `conversation_turns`，并逐一补齐原来默认 submission 必然存在的空值分支。

### 二、实时接纳远程 turn 和 item

在 Codex 协调器中正式处理 `turn/started`：

1. 先按 `providerThreadId` 找到原 Zeus 会话；
2. 按稳定 provider turn ID 幂等创建或更新本地 turn；
3. 从 turn 当前 items 或后续 `userMessage.clientId` 精确匹配本机 submission，匹配不到则标记为远程输入；
4. 更新会话 Provider 状态和运行状态，并广播既有 `conversation.turn.started`；
5. 让该 turn 后续 `item/started`、文本增量、`item/completed`、交互请求和 `turn/completed` 沿用现有持久化与广播链；
6. 远程 turn 正常完成后，本机已经排队的消息再按原队列顺序继续，不能覆盖或抢占 Provider 权威顺序。

现有 `provider_event_receipts` 继续负责同一 App Server 世代内的事件幂等；`conversation_turns` 和 `conversation_items` 的 Provider 唯一索引负责业务投影幂等。正文不参与去重。

优点：实时延迟低，复用当前成熟的 item、交互请求、变更集和 Renderer 广播链路。

代价：必须处理“本机 RPC 仍在等待、Provider 事件先到”的竞态，不能简单把所有无 turn 记录的事件都判为远程。

### 三、建立修复后的增量同步检查点

新增按会话保存的 Provider 同步检查点，至少记录：

- Zeus 会话与 Provider thread 身份；
- 功能首次启用时的基线 turn ID；
- 最近一次已完整接纳的 turn ID；
- 初始化时间与更新时间。

首次启用时，只用 `thread/turns/list` 倒序读取最新一条 turn 作为基线，不导入它及更早内容。此后重连时，以 `itemsView: full` 从最新 turn 向前分页，最多回溯到最近检查点：

1. 检查点 turn 本地已存在时，允许重新投影它，用于补齐该 turn 在断线期间新增或完成的 items；
2. 只创建检查点之后的新 turns；
3. 每个 turn 和 item 按 Provider ID 幂等 upsert；
4. 全部成功持久化后才前移检查点；
5. 若 Provider 历史中找不到检查点，停止增量校准并报告真实同步错误，不退化为全量导入旧历史。

空 thread 建立检查点后，其后出现的第一条 turn 自然属于修复后内容，可以接纳。

优点：满足“修复后断线自动补齐”和“修复前历史不补录”两个边界；分页只读取检查点附近的缺口，不随完整会话长度线性放大。

代价：需要增加 App Server turn 分页读取能力和一张轻量检查点表；检查点因 Provider 历史压缩而失效时会显式报错，不能静默猜测边界。

### 四、投影远程来源图标

远程用户消息持久化时，在 Zeus 本地 message metadata 和 item payload 中写入结构化 `inputOrigin: remote_device`：

- 只在 `ThreadItemView` 的用户消息底部显示低对比度小手机图标；
- 模型回复不显示；
- 图标提供无障碍名称和悬停说明，但不增加正文文字；
- 该字段不进入 Provider 输入、模型上下文、复制正文或按正文生成的去重指纹；
- 若后续精确匹配到本机 submission，则同一 Provider 消息改回本机来源，不显示远程图标。

优点：满足用户确认的轻量来源提示，同时不干扰模型和正文阅读。

代价：受协议限制，只能表达“远程设备”，不能证明具体是 iPhone。

### 五、保持本机草稿独立

远程 turn/item 事件只进入会话转录和运行状态，不触发 `draft_changed`、附件清空或本机 pending send 恢复逻辑。现有草稿以会话维度持久化，方案只增加回归验证，不主动改写草稿链路。

## 不采用的方案

### 为远程 turn 伪造 submission

优点：表结构改动较少。

缺点：把未经过 Zeus 发送的消息伪装成本机提交，会污染队列、重发、恢复和失败语义；后续很难判断消息是否可以自动操作，因此不采用。

### 每次重连全量导入 `thread/read`

优点：实现直观，容易把旧缺口一次补齐。

缺点：直接违背用户“不恢复修复前历史”的确认；长会话读取和重复投影成本持续增长，因此不采用。

### 只增加 `turn/started` 实时分支

优点：代码改动最小。

缺点：任何网络抖动、Zeus 重启或 App Server 世代切换都会再次漏消息，无法满足已确认的断线补齐，因此不采用。
