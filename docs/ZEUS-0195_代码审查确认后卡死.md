# ZEUS-0195 代码审查确认后卡死

## 任务信息

- 类型：缺陷。
- 现象：用户在“开始代码审查”中确认后，界面长期停在“正在准备，完成后自动开始”，不创建审查会话。
- Git 边界：未经用户明确要求，不执行 commit、push、merge 或 revert。
- 验证边界：不操作生产身份 `Zeus.app` 和正式用户数据；真实运行验收只能使用独立身份 `Zeus Test.app` 与独立数据目录。

## 用户已确认的产品口径

- 已经开始的执行轮次继续绑定原运行时世代，升级不得中断、迁移或重跑。
- 用户升级后确认的新任务推送、新建会话、代码审查和冲突处理都属于新执行轮次，必须立即由当前运行时世代承接，不等待旧轮次全部结束。
- 旧运行时世代进入排空后不再接新轮次；它只完成已有轮次和精确归属其中的待回复交互。
- 继续保留单一业务持久化权威；不允许新旧 Local Server 同时直接写入同一份 `zeus.db`。

## 现场事实

- 正式 `/Applications/Zeus.app` 的当前界面版本为 `0.3.1`。
- 界面仍连接 PID `25120` 的脱离执行进程；该进程于 `2026-08-12 09:40:12 +0800` 启动，握手声明 `appVersion=0.2.38`。
- 新界面和旧执行进程都声明粗粒度 `protocolVersion=1`；`connectOrLaunchExecutionHost` 只校验该数字与进程健康，因此主动复用了 `0.2.38` 的 Local Server 端点。
- 本任务新推送的普通会话也已由 `0.2.38` 进程创建和派发；这证明旧进程并非只排空存量轮次，而是仍在承接新工作。
- Renderer 对 `code_review` 特殊处理：只要 `executionHostTransition.state=draining_previous`，就把本次点击保存为待启动信封，直到整个旧宿主被关闭才自动派发。
- 交接又依赖数据库中 `running/dispatching` 轮次记录归零。现场至少有 4 条记录从前一天起未再更新仍被当成真实执行，同时新会话还在继续增加旧宿主的工作。

## 根因

`docs/adr/0003-升级期间执行宿主独立于界面生命周期.md` 和长任务无损升级设计已经明确“旧轮次留在原世代，新轮次进入当前世代”。当前实现把“运行时世代排空”错收缩成了“整个旧版本执行宿主继续当唯一 Local Server”：

1. 运行时世代与 Local Server 版本的所有权边界被混在一起。
2. 新轮次没有独立的“必须路由当前世代”门禁，普通会话会继续进入旧宿主。
3. 代码审查则被反向特判为等待整个宿主交接，于是出现永久“准备中”。
4. 宿主活动性又直接信任持久化运行标记，残留记录可以让全局交接无限期等待。

## 方案及取舍

### 只修代码审查准备态

优点：改动小，可以很快让弹窗离开“准备中”。

缺点：新任务推送和普通新会话仍由旧版本执行，旧宿主仍无法真正排空；不采用。

### 等待旧宿主整体排空再启动所有新工作

优点：保留单一 Local Server，实现容易。

缺点：长轮次会让用户在升级后长期无法开始任何新工作，与已接受的无损升级决策相反；不采用。

### 恢复运行时多世代路由（已确认）

- 单一持久化权威继续管理 conversation、submission、turn、request 与全局并发。
- 当前运行时世代唯一接收新轮次；旧世代只处理已绑定轮次和待处理交互。
- 运行时激活、能力握手和轮次归属使用显式事实，不用 App 版本字符串代替能力表。
- 代码审查不再独自等待整个宿主关闭，它与其他新轮次使用相同的当前世代路由。

优点：新功能立即生效，长任务不中断，旧世代能够真正排空。

缺点：必须重新校正被“整宿主交接”替代的世代激活与归属链；对无法理解新握手的存量旧宿主，仍需安全、可解释的兼容收敛路径。

## 实现结果

### 执行宿主能力握手

- `executionHostProtocol.ts` 定义 `nativeConversationSources`，当前宿主显式声明 `task_push`、`code_review` 和 `conflict_resolution`。
- 执行宿主在健康状态和界面租约回执中返回同一份能力事实。
- Electron Main 把能力投影到 Renderer 配置；不再让 Renderer 用 `currentAppVersion === hostAppVersion` 猜测业务能力。

### 存量宿主兼容

- 新宿主必须优先使用自己声明的能力表，且 Main 只保留当前界面认识的值。
- 已经运行的旧宿主不会因为升级而自动获得新字段；因此 Main 只对已验证发布边界做兼容收敛。
- Git 历史证明 ZEUS-0191 专用会话主链在 `0.2.37` 起已进入发布标签；因此 `0.2.37+` 的无能力字段宿主可安全识别 `code_review/conflict_resolution`，更旧或版本无法解析的宿主继续 fail-closed。

### 专用会话路由

- 代码审查确认后，只有宿主未声明 `code_review` 时才进入可取消准备态；已支持时立即进入通用会话启动主链。
- 已存在的待启动代码审查信封，在刷新后发现宿主具备能力时使用原幂等键自动派发，不新建第二条会话。
- 冲突处理的即时启动和待启动恢复使用同一能力口径，不再与代码审查分叉。
