# ZEUS-0196 冲突处理页面

## 任务类型

缺陷。

## 用户反馈

1. 冲突处理页面信息层级混乱、视觉体验差。
2. 任务分支落后 `main` 时，页面表现为不允许继续处理冲突。

## 已确认实施范围

用户在 2026-08-12 补充说明：IDEA 截图不是任务级代码交付窗口的视觉参考，而是项目侧边栏“代码”入口的目标能力范围。点进“代码”后需要具备完整 Git 工作区，包括动作入口、分支操作、Repository Diff、Git Log，以及合入触发的冲突处理。

这项口径覆盖此前只重构任务级代码交付窗口的范围判断。任务代码交付仍是任务开发线的受控流程；项目代码页则提供独立的仓库级 Git 工作能力，动作直接作用于用户选中的项目仓库，而不是把任务弹窗放大后冒充完整 Git 页面。

优点：Git 查看、比较、分支操作、提交、合入和冲突处理拥有统一入口，用户不需要从任务详情或会话快捷键才能进入。

代价：范围从单个缺陷扩大为仓库级 Git 客户端能力；它会与现有“代码＝源码 / 图谱 / 命令”的信息架构冲突，并引入 checkout、pull、merge、rebase、reset、delete 等高风险写操作，必须重新确认模式归属和授权边界。

## 两个 Git 入口必须分开

用户进一步明确：项目侧边栏“代码 → Git”和从会话环境信息打开的“代码交付”是两个不同工作面，不能把能力混在一起。

### 项目侧边栏“代码 → Git”

这是当前项目全部仓库的通用 Git 工作台，范围以本任务确认的 IDEA 截图工作面为准。

### 会话环境信息“代码交付”

这是当前会话所在任务 worktree 和当前任务分支的交付页。它不再要求用户选择开发分支，也不展示通用 Git 菜单，改造后只保留三个业务动作：

1. 提交当前任务分支的代码。
2. 推送当前任务分支到远端。
3. 将当前任务分支合入其来源分支。

页面布局参考 IDEA Repository Diff：顶部左侧是全部变更文件，顶部右侧放紧凑的当前分支事实与三个动作；现有提交、推送、合入大卡片压缩为上下文工具栏。下半区用于当前文件的便捷双栏对比。文件可双击打开独立 Diff 窗口，支持最大化或全屏审查，主交付页保留原文件选择和滚动位置。

优点：环境入口天然知道当前 worktree 与当前分支，用户不再重复选择对象；代码内容成为视觉主角，主窗口和独立窗口可以分别承担概览与深度审查。

代价：交付页不再承载 checkout、rebase、reset、远端管理等通用动作；这些动作只能去项目“代码 → Git”执行。主窗口和独立 Diff 窗口还需要同步文件状态、选中项和刷新结果。

### 交付冲突的两种处理方式

- “魔法棒”只处理可由确定性规则安全解决的简单冲突，行为参考 IDEA 的 Accept Left、Accept Right 和自动合并；无法唯一判断时必须保留为待人工处理，不能猜测业务语义。
- “交给 AI”继续使用隔离区解决复杂冲突，但处理结果需要形成真实提交，并让 AI 会话后续进入当前任务 worktree 的当前分支，使用户从该会话再次打开代码交付时能看到冲突处理后的真实已提交代码，再自行选择推送或合入等后续动作。

AI 冲突处理延续用户已经发起的“当前任务分支 → 来源分支”动作：隔离候选解决全部冲突后由 Zeus 生成合并提交，并安全更新该任务 worktree 记录的真实来源分支。来源分支来自 `workspace.sourceBranch`，不假定也不写死为 `main`。成功后，AI 会话的执行现场迁移到实际承载该来源分支的本机 worktree；用户从该会话再次打开代码交付时，可以看到冲突处理后的真实已提交结果，再决定是否推送等后续 Git 操作。

优点：简单冲突无需启动 AI，复杂冲突又保留可追问、可审查的真实会话。

代价：隔离区结果写回真实分支属于修改 Git 历史的动作；必须把分支方向、提交 SHA 和当前工作目录显示清楚，不能继续使用模糊的“来源/目标”提示。

## 与现有代码页的冲突

- 当前最新实现由 `ZEUS-0163` 定义：点击“代码”默认进入源码编辑器，右上角切换“源码 / 图谱 / 命令”。
- 更早的代码图谱文档曾把代码页定义为图谱首屏，后来已经被 `ZEUS-0163` 的源码默认模式覆盖；不能只依据旧稿恢复图谱或 Git 页面。
- 当前源码工作台已经提供真实目录树、CodeMirror 编辑、保存冲突保护和未保存门禁；图谱和命令也有独立真实能力。直接替换“代码”会造成这些能力不可达。
- 当前任务级代码交付只针对任务开发线，并继续保留自己的工作区、目标分支和合入记录归属校验；项目 Git 工作台不复用这套任务门禁，两种入口必须在接口和界面上明确分开。

已确认入口结构：项目“代码”默认进入 Git 工作台，同时保留“源码 / 图谱 / 命令”为同级模式。

优点：用户进入代码页即可获得仓库级 Git 能力，既有源码编辑、图谱和命令中心仍保持可达。

代价：代码页从三种模式扩展为四种模式，需要迁移每项目模式偏好并处理旧地址；Git 模式不能把仓库级写操作伪装成任务代码交付完成。

## 已确认 Git 操作边界

### 当前项目全部仓库

Git 工作台覆盖当前项目容器内 Zeus 已发现的全部项目仓库，包括根仓库、并列仓库和嵌套仓库；用户先选择仓库，再查看和执行对应 Git 动作。内部派生仓库与当前项目外的任意路径不进入候选。

优点：覆盖 Zeus 的真实多仓项目场景，同时保持项目侧边栏的对象语义。

代价：仓库发现、排序和切换必须稳定；父仓与嵌套仓库不能自动级联提交、拉取、合入或推送。

### 直接 Git 语义

用户明确选择取消任务、开发线、代码交付状态、HEAD 并发、脏状态保护和审计门禁。项目 Git 工作台中的动作直接交给底层 Git，以 Git 自身成功、冲突或失败结果为准；不增加 Zeus 自创的权限或确认层。

唯一保留的入口边界是操作对象必须属于当前项目已发现的项目仓库，不能提交任意本机路径。该边界用于维持项目 Git 工作台的对象身份，不承担任务工作流保护。参数格式和 Git 引用合法性校验仍是执行命令所需的输入边界，不属于产品操作门禁。

优点：行为接近 IDEA 和终端，用户不会被任务状态或 Zeus 候选过期逻辑阻断。

代价：多个窗口同时操作、目标分支前进、脏工作区、历史改写、分支删除和远端写入可能造成现场丢失；Zeus 不再保留可审计的保护证据或产品级恢复承诺，风险由执行动作的用户承担。

## 已核实现场

- 截图中的红色提示来自 `ZEUS_TARGET_HEAD_CHANGED`，实际含义是隔离合入候选创建后，本机来源分支又前进了，不是任务分支落后某个固定 `main` 被禁止。
- 代码内部把合入落点记为 `targetBranch`，但在环境代码交付的产品语义中它就是该任务开发线的来源分支。界面必须展示真实来源分支名称和新旧提交，不能只显示抽象错误码。
- 当前实现会在保存冲突或收尾时发现候选过期，再占用整页忙碌状态重建；安全校验成立，但反馈时机和交互方式会让用户感觉处理权被收走。
- 权限确认层叠在冲突编辑器之上，背景再叠加整页交付层；文件、冲突块、三栏编辑、权限与底部错误分散在多个区域，当前对象、真实状态和下一步操作不够集中。

## 已确认领域口径

### 最新本地来源基线

冲突候选以该任务开发线真实来源分支的最新本机提交为准。冲突处理不自动访问远端；远端刷新和推送继续由用户单独触发。

优点：本地冲突处理不受网络和凭据故障阻断，符合本地优先的代码交付边界。

代价：用户未主动刷新远端时，本机来源分支可能不是服务器上的最新提交，界面必须如实表达这是本地基线。

### 过期合入候选

本机来源分支在冲突处理期间前进后，Zeus 自动基于最新本地来源基线重建候选；冲突指纹一致的草稿继续保留，只让真正变化的冲突重新确认。

优点：保留来源分支并发安全，同时不中断用户的冲突处理主路径。

代价：重建期间需要明确表示正在校准；冲突结构变化时，无法安全复用的草稿必须失效。

### 页面核心目标

冲突页默认采用“人工审查优先”：首屏围绕当前冲突和可编辑合并结果，确定性自动合并与 AI 处理作为辅助动作，不代替用户确认最终结果。

优点：当前对象、真实差异和保存边界保持可见；AI 等待、权限或失败不会遮断人工处理能力。

代价：复杂冲突仍要求用户理解三方差异；页面需要把辅助动作做得容易发现，但不能再次形成多个主操作。

### AI 权限确认

点击“AI 处理”后，在触发入口附近展开就地轻量确认。每次默认自动权限，用户需要显式改选完全访问；权限不跨会话记忆，也不使用覆盖冲突工作台的居中遮罩。

优点：安全确认仍然明确，当前冲突和人工处理能力保持可见。

代价：轻量确认的空间较小，权限说明必须精简，并保证键盘焦点、Escape 关闭和窄窗口定位可靠。

### 页面结构

页面采用“文件列表＋单块审查”。左侧只展示冲突文件、每个文件的已处理数量和完成状态；右侧一次聚焦当前文件的一个冲突块，通过上一处、下一处切换。完整文件三栏按需打开，不与默认冲突块视图同时常驻。

优点：文件层与冲突层职责分开，首屏能直接看懂当前处理对象；大文件默认只渲染必要上下文。

代价：跨冲突对照需要切换；完整文件中的远距离上下文需要额外打开完整视图。

### AI 会话窗口协同

AI 冲突会话创建成功后，主窗口立即进入该真实会话；代码交付窗口继续保留当前冲突位置、人工草稿和处理状态，并显示会话正在处理或已经结束。用户可以并排查看两个窗口。

优点：审批、追问和过程信息留在会话中，冲突审查现场不被跳转替换。

代价：需要可靠同步两个窗口的会话身份和处理状态；窗口重开后仍要从服务端真实记录恢复，不能依赖临时前端状态。

### 整窗信息架构

代码交付采用阶段式单工作台，按真实 Git 事实呈现“审查本机变化、准备提交、合入、处理冲突、推送”。同一时刻只有一个主工作区和一个主操作，已完成阶段可以回看，但不会用总览卡片或不可逆向导把用户困住。

优点：页面始终能回答“现在处理什么、为什么、下一步是什么”，状态与操作不会分散在多个面板。

代价：需要把当前组件中并列的文件树、差异范围、提交、合入和推送状态重新划分所有权；跨阶段切换必须保留真实选择和未保存草稿。

## IDEA Git 界面学习记录（2026-08-12）

用户补充了 IDEA 的 Git 主菜单、Repository Diff、分支上下文菜单和 Git Log 工作面截图。本轮同时对照 JetBrains 官方的 Diff Viewer、Manage Git branches 与 Log tab 文档核实可见行为。

### 动作菜单

- Git 主菜单按普通本地动作、远端同步、合入与变基、分支管理、历史或差异查看、远端管理分组，不把全部动作做成一个同权重按钮区。
- 分支上下文菜单始终围绕“选中分支”和“当前分支”组织，比较、显示工作区差异、合入和变基的方向直接写进文案；危险删除独立放在末尾。
- Zeus 采用对象和方向明确、动作分组的方式；Checkout、Rebase、Reset、Pull、Delete 等通用 Git 能力属于新项目 Git 工作台，但不能反向混入任务代码交付流程。

优点：用户不需要先理解内部 `source`、`target` 或 integration 术语，就能知道谁与谁比较、谁合入谁。

代价：完整分支名会增加文案长度，需要软换行、复制和窄窗口布局，不能用省略号隐藏关键身份。

### Repository Diff

- 差异内容占据绝大多数窗口；标题、文件序号、两侧提交身份和差异总数靠近窗口边缘，避免重复卡片。
- 顶部紧凑工具栏只承载前后文件、前后差异、双栏或统一视图、空白忽略策略、差异粒度、设置和帮助。
- 双栏各自展示真实内容，使用共同滚动、对齐行号、行级和词级高亮以及滚动条差异标记；只读一侧明确显示提交身份。
- 普通代码审查适合双栏；只有真正的冲突合并才需要目标、结果、任务三方语义，不能把三栏扩散到所有差异场景。

优点：视觉主角始终是代码，审查路径短，页面不会退化为状态卡片集合。

代价：工具栏图标依赖可靠提示、键盘名称和命中区；长文件仍需要可见区域渲染和位置同步。

### Git Log

- 左侧分支树、中间提交图、右侧变更文件与提交详情各自拥有稳定职责；选择提交后才改变右侧上下文。
- 本地分支、远端分支、提交标签、作者、时间和 SHA 均使用真实事实，颜色只辅助识别，不替代文字身份。
- Log 是独立历史调查工作面，不与提交表单、冲突编辑或推送确认同时成为主操作。

优点：分支拓扑、提交顺序和文件结果可以直接对账。

代价：完整 Log 属于独立大型能力；本次如果直接复制到代码交付，会扩大为仓库级 Git 客户端并偏离任务交付目标。

### 对 ZEUS-0196 的修正启示

- 保留单一主工作区，但把“阶段式单工作台”进一步修正为“对象驱动的上下文工作台”：用户可以围绕工作区差异、提交、分支、标签、远端或冲突自由切换，不被不可逆步骤条限制。
- Git 模式默认子页仍待确认；上下文工具栏根据当前对象展示相关动作，不能把全部动作铺成同权重按钮墙。
- 所有合入、比较和过期提示必须显示真实来源分支名称、任务分支名称、方向和新旧提交；不能把来源分支假定成 `main`，也不能只写“分支变化”。
- Git Log 是本任务的正式能力，不再作为任务代码交付中的按需附属面板。

优点：兼顾 IDEA 的高效上下文切换与 Zeus 的项目多仓语义，也能避免线性向导在分支变化或冲突重建时把用户卡住。

代价：需要撤回先前过强的线性阶段表达，改为由真实对象和能力状态驱动工具栏、主区和底部动作。

## 现有能力差距核查（2026-08-12）

### 已有可复用基础

- `git-core` 已能发现项目容器内的根仓库、并列仓库和嵌套仓库，并读取当前分支、工作区状态、远端分支、最近 5 条提交、未暂存与已暂存差异。
- 已有统一差异解析、补丁导出、任务级分支比较、任务级合入冲突读取与保存能力。
- 项目代码页已有“源码 / 图谱 / 命令”三种保活模式和每项目偏好，可扩展为“Git / 源码 / 图谱 / 命令”。

优点：仓库发现、基础状态解析和代码编辑器不用从零重写。

代价：这些能力分散在项目根仓入口、任务代码交付和通用确认流程中，不能直接拼接成完整 Git 客户端。

### 当前阻断与缺口

- 项目 Git 状态、差异和写操作当前只接受项目 ID，并通过 `resolveProjectGitScope` 绑定单一项目根仓；只要登记了多仓或嵌套仓库就直接返回“不支持”。
- 项目写操作必须先创建、确认并消费高风险确认单，执行目录固定为服务启动时的 `projectRoot`，并不是当前项目中用户选中的仓库。
- 通用写操作目前只有提交、stash、应用 stash、恢复文件、新建或切换分支、`pull --ff-only` 和 push；不具备 fetch、任意 merge、rebase、reset、标签、远端管理、分支删除或重命名等 IDEA 动作。
- 状态页只有扁平文件状态和合并后的 unified diff；没有逐文件暂存或取消暂存、任意引用比较、双栏/统一视图切换、空白策略、差异粒度和差异导航。
- Log 只返回最近 5 条提交；没有分页提交图、父提交、引用、路径/作者/日期过滤、选中提交文件和详情。
- Stash 只能创建和按手填引用应用；没有列表、内容比较、pop、drop 或 clear。
- 尚无项目级通用冲突会话。现有冲突编辑器绑定任务 integration worktree，不能处理项目 Git 工作台发起的 merge、rebase、pull 或 checkout 冲突。
- 尚无 Git Console；IDEA 的 Shelf 也不是 Git 原生命令，需要 Zeus 自己定义补丁存储、恢复和生命周期。

优点：缺口已经能按仓库模型、读取模型、操作模型和冲突模型拆开实施，不会只完成一张外观相似的空页面。

代价：这不是一次局部视觉修补；完整能力会跨 `git-core`、本地服务、Renderer API、项目代码页状态管理、差异编辑器和冲突恢复。

### Shelf 与 Git Console

用户确认两者都纳入正式范围。

- `Shelf` 作为 Zeus 管理的项目仓库补丁搁置区，至少记录来源仓库、补丁内容、标题或备注、创建时间、应用状态，并支持查看差异、应用、重命名和删除。
- `Git Console` 记录从项目 Git 工作台发起的每次 Git 调用，包括仓库、参数、开始与结束时间、退出码、标准输出和标准错误；它用于还原真实执行结果，不重新引入操作审批或审计门禁。

优点：IDEA 截图中的 Git、Local Changes、Shelf、Stash、Log、Console 不会出现只有外壳没有能力的占位页。

代价：Shelf 需要新的持久化实体和补丁应用冲突处理；Console 会产生持续增长的本机数据，需要分页、大小上限和清理策略。

### Clone 归属

用户确认 Clone 同时支持两种落点：

1. 克隆到当前项目容器内，成功后重新发现仓库并纳入当前项目 Git 工作台。
2. 克隆到用户选择的新目录，并用该仓库创建新的 Zeus 项目。

优点：既能补充多仓项目，也能从 Git 工作台直接开始一个新项目。

代价：Clone 入口必须先明确“加入当前项目”或“创建新项目”；前者要限制在当前项目容器内，后者要复用项目创建与重名处理，任何一步失败都不能留下已登记但不可用的项目记录。

### IDEA 式多仓操作

用户明确要求按 IDEA 的多仓交互实现，而不是提供一个抽象的“批量同步”按钮。

- Push 打开独立弹窗，列出当前项目所有仓库及各仓库当前分支尚未推送的提交；未启用同步分支控制时只默认勾选当前仓库，用户可以改选仓库、检查提交和文件差异、修改目标远端分支，并选择是否推送标签。
- Force Push 使用 `--force-with-lease`；Push 被拒绝后展示受影响仓库，并允许用户选择 merge 或 rebase 更新，不静默伪装为成功。
- 分支动作提供 IDEA 式“对所有仓库同步执行”项目设置；关闭时先选仓库再执行，开启时 checkout、merge、delete 等同名分支动作作用于全部项目仓库。
- 多仓同步动作必须逐仓返回成功、冲突或失败。只要出现部分成功，就如实列出已执行仓库，并提供对已成功仓库的反向操作建议；不能把它压成一个整体成功状态。

优点：与 IDEA 的 Push Commits 和同步分支控制心智一致，既支持当前仓精确操作，也支持真实多仓项目协同。

代价：跨仓操作不具备数据库事务式原子性；反向操作本身也可能失败，因此页面必须保留每个仓库的命令与结果，不能承诺一键绝对恢复。

### Git 默认子页

项目按项目记住上次打开的 Git 子页；首次进入项目 Git 工作台时默认打开 `Log`。

优点：首次呈现用户截图中的分支树、提交图、变更文件和提交详情，后续又能恢复真实工作位置。

代价：存在未提交改动时不会自动跳去 `Local Changes`，因此工具栏必须常驻显示当前分支、改动数量和冲突数量，并允许一键进入本地变更。

代价：远端代码审查与平台协作仍需使用浏览器或后续独立能力，不能在本任务中当作已经交付。

## 已实施：AI 冲突会话的来源分支语义（2026-08-12）

- 冲突会话标题由内部“目标分支”表达改为“当前任务分支合入来源分支”，同时兼容识别已经持久化的旧标题。
- 提示词明确本次任务是完成“当前任务分支 → `workspace.sourceBranch`”的代码交付，不允许只处理入口文件或只留下工作区、暂存区修改。
- AI 必须处理仓库内全部冲突、逐项 `git add`，并在 detached 隔离候选中生成 merge 或 squash 提交；结束前复验未解决冲突为空并报告候选提交 SHA。
- AI 不 checkout、reset、rebase、不直接移动真实来源分支，也不 push。Zeus 在 AI 提交后继续复验任务分支和来源分支 HEAD，再把候选提交安全同步到动态来源分支。
- 专用冲突会话开启提交能力；界面权限说明同步表达“修改、暂存并生成合入提交”，不再把暂存描述成终点。

优点：AI 与用户看到的是同一个“合入来源分支”任务，候选提交成为明确交接物，后端现有安全落地流程仍保留。

代价：来源分支最终更新仍依赖 AI 会话完成后的 Zeus 收尾；若来源分支已经前进或实际 worktree 无法安全更新，必须保留候选并如实显示失败或待同步，不能把候选提交冒充已合入。

静态验证已通过：`pnpm lint`、`pnpm typecheck`、`pnpm build`、`git diff --check`。构建成功不代表 Electron GUI 和真实冲突仓库流程已经验收。
