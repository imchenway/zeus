# ZEUS-0203 任务首发完全访问显示为只读诊断

## 任务类型

缺陷诊断。

## 用户反馈

任务推送时已经选择“完全访问”，进入会话后权限控件却显示“只读”。

## 当前结论

当前问题是任务首发创建期工作面的权限投影错误，不是这条会话的实际执行权限降级。

本次只读核对的 ZEUS-0203 真实会话中：

- `conversations.permission_mode` 为 `full-access`；
- `next_turn_settings_json.permissionMode` 为 `full-access`；
- 首轮 `conversation_submissions.input_json.context.permissionMode` 为 `full-access`；
- 当前 Provider 线程实际运行权限为完全访问。

因此，“只读”只来自 Renderer 创建期界面的默认回退，不能作为 Provider 实际权限事实。

## 根因链路

1. 推送弹窗把用户选择的 `full-access` 正确写入 `StartTaskModelPushRequest.permissionMode`。
2. Local Server 正确解析该值，并把它写入会话、下一轮配置和首轮提交上下文。
3. Codex Coordinator 根据 `permissionMode` 把完全访问映射为 `dangerFullAccess` 与 `never` 审批策略。
4. 用户确认推送后，Renderer 会先创建一个即时可见的任务首发工作面。该工作面的 `NativeConversationChoice.permissionMode` 已经是 `full-access`。
5. 但同一工作面的本地 `NativeSessionState` 没有写入 `snapshot.permissionMode` 或 `snapshot.nextTurnSettings.permissionMode`。
6. `SessionWorkspace` 的输入区权限控件只从 `NativeSessionState.snapshot` 派生权限；快照缺值时固定回退为 `read-only`，没有使用已经正确存在于 `NativeConversationChoice.permissionMode` 中的值。
7. 在真实会话快照完成接管前，界面因而错误显示“只读”。

## 产品风险

- 用户无法相信推送弹窗中的授权是否真正生效。
- 如果用户在创建期继续发送后续消息，输入区可能把错误的只读值作为本轮设置提交，形成从“显示错误”扩大为“后续轮次配置错误”的风险。
- 仅检查 SQLite 或仅修正文案都不够；创建期工作面、真实快照、持久配置和 Provider 首轮必须显示并采用同一权限事实。

## 修复方向

推荐让任务首发创建期状态在建立时就携带本次冻结的权限和计划模式，并让输入区统一读取该状态；真实会话接管后再由服务端快照覆盖。

优点：创建前后只有一个权限事实，界面立即正确，创建期后续消息也不会带错权限。

代价：需要同时核对创建期状态构造、真实身份接管和输入区配置初始化，避免只改一个显示入口后仍留下发送配置不一致。

不推荐只把权限控件的默认值从“只读”改成“完全访问”。

优点：改动表面较小。

缺点：会把所有缺失权限事实的场景误报为完全访问，扩大安全风险，也没有修复创建期后续消息的真实配置来源。

## 实现

- `SessionWorkspace` 初始化输入区运行配置时，服务端快照仍是第一事实源；创建期快照尚未到达时，改为读取本次任务首发已经冻结在 `NativeConversationChoice` 中的权限与计划模式。
- 权限控件使用相同优先级：输入区本地选择、服务端下一轮配置、服务端会话权限、本次会话选择、安全只读默认值。
- 未把全局默认值改为完全访问；没有任何可信权限事实时仍回退为只读。

这样既修复创建期显示，也保证创建期间追加的后续消息使用本次确认的 `full-access`，真实会话接管后继续由服务端快照覆盖。
