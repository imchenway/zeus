# ZEUS-0204 会话工作态与授权真实生效修复

## 任务类型

严重缺陷。

## 用户反馈

- 只读会话出现“允许一次”和“允许所有编辑”时，点击并未真实放行请求，审批弹窗也无法可靠结束。
- 会话里尚未发送的内容，以及模型、推理等级、速率、会话权限和计划模式，修改后切换会话会全部回退。
- 修改权限后即使发送消息，Provider 仍可能使用旧权限，界面随后也回退到之前的权限。
- 同一项目需要记住用户最近选择，但任务开发、冲突处理、代码审查和项目普通会话必须分别记忆。

## 已确认产品规则

### 会话工作态

- 未发送文字、附件、模型、推理等级、速率、权限和计划模式按具体会话独立保存。
- 用户修改后立即保存；切换会话或重启 Zeus 后原样恢复。
- 当前轮执行期间修改配置只影响尚未开始的后续轮次，不追改正在运行的轮次。
- 发送成功只清空本次文字和附件，五项配置继续作为该会话的下一轮配置。
- 旧快照、其他会话和项目默认值都不得覆盖用户在当前会话刚确认的选择。

优点：会话切换和重启不会丢失工作现场，用户看到的配置与下一轮真实配置一致。

代价：Renderer 本地状态、服务端下一轮配置和 Provider 派发必须使用带会话身份的单一优先级，不能继续各自回退。

### 只读会话的显式授权

- “允许一次”只放行当前命令或当前文件修改请求，会话仍保持只读，后续请求继续询问。
- “允许所有编辑”放行当前会话后续的项目工作区文件编辑，并跨会话切换和 Zeus 重启保留。
- 会话文件允许不放行命令、项目外路径、Git 提交、推送或其他高风险动作，也不改变其他会话。
- 用户切换会话权限模式时撤销旧的会话文件允许，后续按新模式重新判断。

优点：审批按钮具有真实运行含义，同时保持最小授权范围。

代价：Zeus 需要持久记录会话级编辑例外，并在 Provider 再次申请文件审批时自动按同一安全范围回复。

### 项目分类型默认配置

- 每个项目分别记忆任务开发、冲突处理、代码审查和项目普通会话四类默认配置。
- 记忆字段为模型、推理等级、速率、权限和计划模式；用户一修改就立即更新，不等待发送或创建成功。
- 项目类型默认值只初始化当前正在编辑的新会话入口和以后新建的同类会话，不追改其他已有会话。
- 记忆值与当前入口或模型能力不兼容时，只降级不兼容字段，其他字段继续保留，并展示实际降级结果和原因。

优点：高频配置不必重复选择，不同用途的安全边界不会互相污染。

代价：四类入口需要统一使用同一偏好结构，同时保留代码审查固定只读、冲突处理必须可写等入口门禁。

## 已核实现状

- 草稿已经按项目和会话 ID 写入本地存储，但创建期 `localState` 在真实控制器接管后仍可能把旧草稿再次写回。
- 下一轮配置同时存在 Renderer 本地缓存、SQLite `next_turn_settings_json` 和会话快照；切换身份时缺少阻止旧异步响应回写新工作面的门禁。
- 下一轮配置接口只更新 `next_turn_settings_json`，会话主权限在实际派发时才同步；旧响应和旧快照仍可能造成界面回退。
- 任务推送偏好与项目服务档位偏好目前分开保存，而且只在成功接受后记忆，不符合“修改即记忆”和分会话类型要求。
- 文件审批的允许选项直接使用 Provider 决策，但 Zeus 没有持久的“会话文件允许”，无法确保“允许所有编辑”覆盖后续新文件。

## 已完成实现

- 同一会话的下一轮配置请求改为按用户操作顺序提交，只采用最后一次选择的返回值，避免旧请求晚到后覆盖新权限。
- 创建期临时工作面在权威会话快照接管后停止回写，避免切换会话时用旧草稿覆盖真实草稿和附件。
- 新增按“项目 + 会话类型”隔离的运行配置偏好；任务开发、冲突处理、代码审查、项目普通会话互不串值。
- 任务推送和各入口改为用户选择后立即记忆；项目普通会话补齐模型与推理等级选择，并把五项配置真实传给首轮。
- 新增持久的会话文件编辑授权。Provider 确认“允许所有编辑”成功后才记录；后续仅对同一会话、项目内、目标可审计的文件请求自动真实允许。
- 切换会话权限模式会撤销旧的会话文件编辑授权；命令、项目外路径、Git 提交/推送和其他会话不继承。
- Provider 自动答复失败时继续展示待授权请求，不伪造成功状态。

## 实现取舍

- 会话类型按既有所有者和标准标题识别，优点是不扩大会话主表改造范围，能兼容现有代码审查与冲突会话；缺点是新增特殊会话类型时必须同步登记标准标题。
- 项目分类型偏好保存在 Desktop 本机持久存储，优点是用户修改后即时生效且不会反写历史会话；缺点是它不跨设备同步。
- 会话文件编辑授权保存在 SQLite，优点是重启后仍能由服务端作为唯一授权事实；缺点是比单纯复用 Provider 的 `acceptForSession` 多一层范围校验与状态维护。
