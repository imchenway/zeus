# ZEUS-0206 会话未读与专属关注状态

## 问题

模特在其他会话产生普通回复后，Zeus 没有可靠的未读提示。现有“完成未读”只覆盖部分 Codex 成功完成链路，Pi 普通回复不会写入同类事实；会话行又只在 `ready` 且非当前选中时显示蓝点，因此执行状态未及时收敛、会话仍保留选中 ID、用户停留在其他页面或窗口不在前台时都会漏掉提示。

系统通知也没有覆盖原生会话回复，且当前通知桥不判断 Zeus 是否处于前台，无法满足“Zeus 活跃时不打扰，后台或关闭窗口时通知”的产品要求。

## 已确认范围

1. 未读是所有原生模型的会话级基础能力，不绑定 Codex 或成功完成事件。
2. 能识别具体含义时显示专属关注状态；只有无法细分时才回退为蓝色普通未读圆点。
3. 初始专属状态包括待批准、需要回复、正在响应、已完成、失败和已中断。
4. 单条会话只显示最高优先级状态：待批准或需要回复，高于失败或已中断，高于已完成，高于普通未读。
5. 用户可见的新模型回复、最终回复、失败或中断结果、批准请求和用户询问触发关注；思考摘要、工具日志、流式增量、用量与内部同步不单独触发普通未读。
6. 待批准和需要回复必须在事项真正解决后才结束，不能以“用户看过”代替“已经处理”。
7. 只有 Zeus 前台、目标会话正文真实显示且最新关注内容进入可见区域后才确认已读。仅选中、其他页面、后台、遮挡、关闭窗口或向上阅读历史都不算已读。
8. 项目“会话”入口按未读会话数聚合；存在专属待处理状态时优先表达专属状态，数量按会话而非消息计。
9. 状态跨重启、断线和项目切换持久保留；断线校准不得重复发送系统通知。
10. 桌面通知开启时，没有任何 Zeus 窗口处于前台焦点才发送通知；关闭窗口但后台驻留需要通知，任一 Zeus 窗口活跃时不通知，明确退出后不承诺实时通知。
11. 通知按同一轮有意义状态变化去重；点击后精确打开对应项目和会话，通知点击本身不算已读，也不执行批准、回答或重试。

## 方案取舍

采用持久化会话阅读事实与可识别专属状态的统一模型，由 Provider 协调器在用户可见内容或终态形成时写入，列表与项目入口读取同一份服务端投影；Renderer 只在满足前台、正文和最新内容可见条件后带版本确认已读。

优点：跨模型语义一致；断线和重启后不丢；已读确认不会与新回复竞态；项目入口和系统通知都能复用同一关注事实。

代价：需要数据库迁移、Codex 与 Pi 事件归一、Renderer 可见性检测、项目聚合和 Main 通知导航同步改造。

不采用以下方案：

- 只放宽现有 `completion_unread` 红点条件：改动小，但仍漏掉 Pi、普通消息、失败、中断和后台选中会话。
- 只在 Renderer 收到事件时维护未读：无法跨重启，断线会漏，多个窗口之间也无法对账。
- 每条流式增量都通知：反馈快，但会造成重复横幅和未读数量膨胀。

## 实施记录

1. 存储层保留历史 `completion_unread` 数据列作为兼容载体，新增关注类型、修订号、轮次和发生时间；旧完成未读自动迁移为“已完成”关注状态。
2. Codex 在首个有意义的模型回复内容形成时写入普通未读，轮次终止时升级为已完成、失败或已中断；Pi 的模型消息、审批请求和终态使用同一套写入规则。
3. 同一轮同一类型的重复事件保持幂等，流式增量不会增加未读数量或重复通知；思考、计划、工具日志、用量和同步事件不创建普通未读。
4. 服务端会话轻量投影统一返回未读、关注类型和修订号；项目侧栏同时返回最高优先级状态和未读会话数。
5. 会话行优先显示待批准或需要回复，其次显示执行中、失败、已中断、已完成，无法细分时显示蓝色未读圆点；不再以 `ready`、非当前选中作为显示前提。
6. Renderer 只有在窗口前台、会话正文已挂载、最新内容位于滚动区域底部且未被其他界面遮挡时，才携带当前修订号确认已读。确认期间到达的新修订不会被旧请求误清。
7. 系统通知桥只在没有任何 Zeus 窗口获得焦点时显示会话通知；普通回复、待审批或回答、完成、失败和中断按轮次去重，断线快照产生的终态事件不具备通知资格。
8. 通知携带项目与会话身份。点击后由 Main 恢复主窗口并通知 Renderer 重新读取权威会话投影，再进入对应项目和会话；只有最新内容真正可见后才确认已读。

主要优点：跨模型一致、重启不丢、不会因“选中”误判已读、后台通知不打扰前台操作，并且专属状态与普通未读共用一个事实源。

已知代价：项目入口需要同时维护最高优先级状态与未读会话计数；真实可见性判断依赖滚动位置和页面命中检测，比“选中即已读”多一层界面状态同步。

代价：请求关注投影必须依赖自动批准的真实结果，不能在请求到达时无条件写入。
