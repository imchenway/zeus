# ZEUS-0219 引导消息删除后残留排队气泡

## 任务信息

- 类型：缺陷
- 用户现象：删除等待发送的消息后，消息仍以“排队中”气泡残留在会话记录底部。
- 截图事实：残留项显示“排队中”，没有显示“引导中”或“引导结果待确认”。
- Git 边界：未经用户明确要求，不执行 commit、push、merge 或 revert。
- 验证边界：真实运行只允许使用当前任务生成的独立身份 `Zeus Test.app`、`dev.hypha.zeus.test` 和独立用户数据目录。

## 术语澄清

- **待发送的后续消息**：仍在 Zeus 队列中、尚未交给 Provider 的用户输入；可以编辑、删除、排序或选择“引导”。
- **引导消息**：用户已经选择“引导”，Zeus 正在把该输入补充给当前执行轮次的消息；它使用“引导中”或“引导结果待确认”表达真实状态。
- 当前截图属于前者。为避免把删除问题和 Provider 引导确认问题混为一谈，本文后续使用“待发送的后续消息”。

## 已核对的根因

服务端删除路径会把 submission 标记为 `deleted`，并返回已经移除该项的权威队列快照，持久队列事实没有继续排队。

Renderer 的删除回执只派发通用 `queue_hydrated`：

1. 队列快照移除了被删除的 submission。
2. 发送时创建的乐观用户消息投影仍留在 `state.items`，状态仍是 `queued`。
3. `ConversationTranscript` 会把“不再存在于权威队列、但仍是 queued 的乐观项”作为兜底气泡绘制到会话记录底部。
4. 因为后续不会再有 Provider 消息来替换这条已删除输入，残留气泡会永久显示“排队中”。

因此，截图不是 Provider 仍在排队，而是删除动作没有同步收敛同一客户端消息身份的 Renderer 乐观投影。只隐藏气泡会掩盖状态泄漏，不能作为修复。

## 已确认的产品语义

用户已确认把“删除待发送的后续消息”定义为取消这条尚未交给 Provider 的输入：删除成功后，同一消息身份必须同时从后续消息列表和会话乐观投影中消失，刷新、切换会话和重启后都不得恢复。

优点：删除结果和服务端 `deleted` 事实一致，不再留下虚假的“排队中”；同一消息身份只有一个可见生命周期。

代价：删除成功后不自动回填输入框；如果用户想保留正文，应先使用编辑或复制。删除与自动派发发生竞态、服务端拒绝删除时，界面必须保留消息并展示真实状态，不能假装删除成功。

## 实施决策

- 已完成仓库约束、既有队列与引导契约、服务端删除路径和 Renderer 投影路径核对。
- 用户已确认删除语义，按最小范围实现。
- 实现必须使用删除动作携带的精确 submission 和客户端消息身份收敛乐观投影；不能把所有“不在当前队列中的 queued 乐观项”一并删除，因为正常派发到 Provider 时仍需要这些投影覆盖消息确认到达前的可见窗口。
- 本项是容易回退的局部状态收敛，不新增 ADR。

## 实现记录

- Renderer 增加显式 `queued_submission_deleted` 动作；删除请求成功后同时携带 submission ID、已有客户端消息 ID 和最新权威队列快照。
- Reducer 只移除与本次删除身份精确匹配的乐观用户消息投影，并同步更新队列、会话状态、消息顺序和 transcript revision。
- 通用 `queue_hydrated` 保持原语义，不清理普通的队列外乐观项，避免误删已经开始派发但尚未获得 Provider 持久回放的消息。
- 删除请求失败时仍由现有 operation 错误路径保留原队列和乐观投影，不伪造删除成功。
