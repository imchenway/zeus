# ZEUS-0220 会话消息发送状态可见性

## 当前状态

- 阶段：第一层方案已实施并通过静态门禁与测试包校验。
- 已确认范围：修复全部原生会话的发送中、Provider 启动等待、结果待确认和明确失败反馈。
- 待讨论范围：AI 冲突处理会话完成隔离合入后的执行现场与持续对话方案，本阶段不修改。
- Git 边界：不执行 commit、push、merge 或 revert。

## 用户现象

用户消息气泡已经出现在会话底部，但下方没有 loading、思考状态或失败信息。普通会话和冲突处理会话都可能因此看起来像卡死，用户无法判断消息是尚未提交、已经排队、Provider 正在启动、结果未知还是明确失败。

截图中的冲突处理会话还有一项独立事实：首轮在独占的隔离合入目录中执行；冲突结果落地并回收该目录后，后续消息可能因执行目录不可用而被服务端拒绝。该拒绝此前又被通用发送错误展示缺口吞掉，因此表面上像冲突会话天生不能继续。

## 根因

### 发送反馈只覆盖了部分时窗

Renderer 在点击发送时会创建带 `clientUserMessageId` 的乐观用户消息，并将会话设为 `starting_turn`。正常情况下会显示“发送中”和“正在思考”。但后续队列快照或完整会话快照可以在 Provider 轮次建立前把会话阶段重新投影为空闲；乐观消息虽然仍存在，过程占位却因此消失。

### 明确失败删除了消息

发送接口异常后，控制器会用同一客户端消息身份读取权威快照。快照明确证明不存在 submission、Provider 用户项和持久用户消息时，Reducer 原逻辑删除乐观气泡、把文字和附件恢复到输入区，并只把错误保存到 `state.error`。

会话传输仍正常且阶段回到空闲时，现有工作面不会渲染这项操作错误，于是用户只看到内容返回输入框，时间线没有失败记录，也没有原因。

### 冲突隔离现场是另一层问题

冲突处理会话通过 `taskIntegrationAttempts` 绑定独立 integration worktree。该设计保证并行尝试不共享目录或 Git 索引。结果安全落地后，隔离目录可能被回收；当前会话执行目录解析仍优先读取该尝试，目录不存在就返回 `ZEUS_NATIVE_CONVERSATION_WORKTREE_UNAVAILABLE`，不会回退到项目根目录。

隔离约束本身是正确的安全保护；本阶段只保证这个真实拒绝能够贴近消息显示，不把执行现场交接方案混入已确认范围。

## 已确认的消息状态口径

1. 点击发送：原消息立即出现并显示“发送中”“引导中”或“排队中”。
2. 服务端接受但轮次尚未回放：显示“消息已接收，正在启动处理”。
3. Provider 轮次开始：既有“正在思考”和真实过程内容接管反馈。
4. 接受结果已返回但持久记录暂不可读：显示“消息已接收，正在确认记录”。
5. 权威结果不确定：显示“发送结果待确认”，不得自动重发。
6. 权威快照证明没有发送：原消息显示“消息发送失败”和可读原因；原输入同时回到输入区，允许用户修改或安全重试。

## 实施方案

- `send_started` 为乐观消息记录稳定的本机时间，避免完整快照校准时使用不断变化的会话更新时间重排消息。
- `send_failed` 不再删除乐观消息，而是把它标记为 `failed` 并附带脱敏后的消息级错误；文字、附件和浏览器批注仍按既有规则恢复到输入区。
- `send_uncertain` 在保留消息的同时附带消息级错误，继续禁止自动重发。
- 时间线在会话过程占位缺失时，为尚未完成 Provider 交接的用户消息补充局部状态；失败和结果待确认始终显示局部说明。
- 明确失败的反馈提供“回到输入框”入口；输入内容已经按既有恢复规则回填，用户可先修改再发送，按钮本身不自动重发。
- 常见失败使用产品文案解释执行目录、任务终态、登录、持久记录确认、冲突收尾和限流原因；原始代码与信息只放进可展开技术详情。
- 不新增数据库表或发送协议，不修改 submission 调度、Provider 幂等和冲突处理 Git 行为。

## 方案优缺点

优点：

- 普通会话和特殊用途会话使用同一反馈规则，用户不会再从空白界面猜测后台状态。
- 明确失败保留消息审计，同时保留可编辑恢复内容。
- 结果不确定继续遵守不自动重发的安全边界，不会为了视觉收敛制造重复 Provider 输入。

代价：

- 明确失败后，时间线保留失败消息，输入区也恢复同一内容；两处分别表达历史失败事实和下一次可编辑输入，不能按正文去重。
- Renderer 需要同时协调乐观消息、submission、Provider 用户消息、持久消息和会话阶段，状态判断仍必须以稳定身份为准。

## 冲突会话后续讨论

用户提出把冲突处理现场改为“任务分支名加 merge 后缀”的命名分支和 worktree。该方案能够让物理执行目录在合入后继续存在，从而避免因 detached integration worktree 被回收而直接失去 cwd；但它同时改变现有“冲突处理尝试不创建临时业务分支”的领域规则，并需要重新定义：

- merge 分支从任务分支还是来源分支创建；
- 冲突解决提交落在哪条分支，如何同步到真实来源分支；
- 合入完成后继续写 merge 分支时，后续提交如何再次交付；
- 多次并行 AI 处理时分支命名、赢家落地和失败分支回收；
- 任务完成、会话归档与 merge 分支清理之间的关系。

当前判断：只要该命名分支及其 worktree 在任务完成前持续存在，它确实能消除“冲突尝试收尾后目录被回收，原会话失去 cwd”这一类问题。但分支名可以沿用任务分支加 merge 后缀，分支基点不能直接照名字推断；建议从真实来源分支当前 HEAD 创建，再把任务分支合入，这样来源分支保持第一父提交，后续同步更直观。并行尝试还需要附加尝试身份，不能只有一个固定 merge 后缀。

该方案仍不会自动解决两个问题：一是本任务已修复的消息状态可见性；二是冲突结果首次同步来源分支后，会话继续产生的新改动如何再次交付。若采用该方案，建议把命名 integration 分支视为任务完成前的持续开发线：首次冲突解决可以同步来源分支，但分支与 worktree 继续保留；后续修改仍落在此开发线，通过现有代码交付入口再次同步；只有任务完成或明确取消后才归档会话并清理现场。

优点是会话、分支和可写目录的生命周期一致，用户可以继续追问和修改；代价是会增加可见分支、并行尝试命名与重复交付管理，且必须防止已经落后于来源分支的长期现场被误当作最新结果。本阶段只给出结论，不修改冲突分支和收尾逻辑。
