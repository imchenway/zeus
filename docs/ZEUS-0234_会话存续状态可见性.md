# ZEUS-0234 会话存续状态可见性

## 当前阶段

- 用户已确认产品边界，实现、静态门禁、构建与独立测试包校验已经完成。
- 真实 GUI 与 Provider 验收受窗口首次落点护栏阻断，未冒充完成。
- 本任务不新增或恢复单元测试，不执行 Git commit、push、merge 或 revert。
- 真实运行验收只允许使用本任务生成的 `Zeus Test.app`、`dev.hypha.zeus.test` 和独立用户数据目录。

## 用户现场

用户消息已经出现在会话底部，停止按钮也表明会话可能仍在运行，但消息下方长时间没有连接、思考、活动、等待或失败反馈，看起来像消息发出后没有任何响应。

## 根因判断

1. 乐观用户消息从本机状态切换为服务端持久消息后，Provider 轮次可能尚未建立；如果此时权威快照仍投影为空闲，原有“发送中”和“正在思考”会同时消失。
2. 当前轮次只要曾经出现过一次可见反馈，`visibleFeedbackEpoch` 就会持续压住通用思考占位；活动完成后的下一段安静期因此再次变成空白。
3. “正在连接”同时被拿来表达会话创建、网络恢复和普通消息调度，无法说明用户究竟在等待哪一层。

## 已确认产品边界

- 会话创建或首次接管显示“正在连接”。
- 网络中断恢复显示“正在重新连接”。
- 普通消息开始提交、Provider 尚未建立轮次时显示“正在启动处理”。
- Provider 轮次存续且没有更具体的实时活动时显示“正在思考”。
- 命令、读取、写入等真实活动存在时，轮次最后一行显示最新活动；活动结束但轮次未结束时恢复“正在思考”。
- 尚未轮到处理的后续消息保留“排队中”。
- 等待审批、等待回答、明确失败、中断和完成由各自真实状态接管。
- 全局移除面向用户的“发送中 / Sending”进行态文案。
- 存续状态固定为当前轮次最后一行，正常参与最新内容跟随；用户主动上翻历史时不强制抢回底部。

## 方案取舍

优点：

- 用户无需借助停止按钮猜测会话是否仍在工作。
- 连接、消息调度和智能体运行使用不同术语，问题停在哪一层更清楚。
- 长任务在两个活动之间不再出现无反馈空窗。

代价：

- 长轮次会持续保留一行低噪音动态状态，界面不会再以完全空白表达后台工作。
- Renderer 必须判断“当前仍在发生的反馈”，不能继续使用“本轮曾经出现过反馈”的一次性标记。

## 实施设计

1. 会话记录根据 `starting_turn` 与活动轮次分别展示“正在启动处理”和“正在思考”。
2. 通用状态只被当前仍在进行中的 reasoning、assistant、commentary 或工作活动替代；这些内容完成后，如果轮次仍存续，通用思考状态重新出现。
3. 快照校准保留仍处于 `dispatching` 的当前提交，避免持久用户消息先到、Provider 轮次后到时错误回落为空闲。
4. 消息气泡、附件预览和后续消息队列移除“发送中 / Sending”进行态，保留“排队中”和明确失败语义。

## 验证计划

- 执行改动文件格式检查、`git diff --check`、`pnpm lint`、`pnpm typecheck`、`pnpm build` 和 `pnpm package:mac`。
- 核对测试包名称与 bundle ID，只允许生成 `Zeus Test.app` 和 `dev.hypha.zeus.test`。
- 真实 GUI 和 Provider 验收需要满足独立用户数据目录、同身份实例隔离和窗口首次出现在非主外接屏的护栏；条件不足时记录缺口，不用静态页面或构建结果冒充。

## 实施结果

1. `dispatching` 提交即使处在 Provider 轮次建立前的快照空窗，也继续投影为“正在启动处理”，不再回落为空闲。
2. 活动轮次只在当前确有进行中的 reasoning、assistant、commentary 或工作活动时隐藏通用状态；具体活动结束而轮次仍存续时，轮次最后一行恢复“正在思考”。
3. 通用存续状态统一放在当前消息流末尾，不再嵌入较早的活动组或最终正文上方。
4. 用户消息气泡、待处理图片和后续消息调度已移除“发送中 / Sending”进行态；后续消息仍保留“排队中”，引导当前回复时显示“正在接续当前回复”。
5. 会话创建和网络恢复继续分别使用“正在连接”和“正在重新连接”，不与普通消息调度混用。
