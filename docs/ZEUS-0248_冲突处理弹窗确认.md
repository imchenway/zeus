# ZEUS-0248 冲突处理弹窗确认

## 任务类型

缺陷与跨流程一致性修复。

## 用户反馈

点击冲突处理权限弹窗的确认按钮后，界面仍停留在弹窗数秒，表现为卡死。并行任务持续向来源分支和任务分支提交是正常场景，冲突处理不能因为分支继续变化而拒绝工作。任何名为“重试”的动作都不能通过新建会话、任务、消息或其他业务身份伪装成恢复。

## 根因

- Renderer 只有等 `/conflict/ai-session` 完整返回后才关闭权限弹窗并进入会话。
- 服务端在返回前同步创建独立 Git 合入现场、写入冲突草稿、持久会话并准备首轮；真实准备耗时被错误留在权限确认层。
- 现有冲突尝试冻结首次来源提交和任务提交，把后续提交变化视为过期或失败，不适合多个任务与会话并行写入的真实交付场景。
- 全应用部分创建入口没有第一次点击即生成的稳定创建意图；如果服务端已成功但客户端响应丢失，用户重试可能重复创建对象。
- “重试”“再次执行”“重新读取”混用，界面无法准确表达是否沿用原业务身份。

## 已确认领域口径

### 冲突会话即时建立

权限确认后先持久创建唯一冲突处理业务操作、Zeus 会话和首发消息并立即导航；Git 现场和 Provider 在后台准备。Codex 与 Pi 行为一致。

优点：用户立即进入真实会话，首发要求、准备状态和后续失败都有稳定落点。

代价：产品会话需要支持 Provider 和执行目录尚未绑定的持久准备态。

### 准备期间继续交互

准备期间允许发送消息，消息以稳定身份进入同一会话队列，现场就绪前不派发。模型、权限和执行模式可以修改，并同步到全部尚未派发提交；已经开始派发的提交不追改。

优点：用户不必等待 Git 准备完成才补充上下文，界面配置与实际首轮一致。

代价：队列需要区分“已持久但因现场准备冻结”和普通并发排队，并支持批量更新未派发配置。

### 两端分支持续追最新

来源分支和任务分支持续变化属于正常并行交付。当前业务操作在同一会话内自动读取最新两端提交、创建内部执行代次并重建隔离现场。冲突指纹一致的有效草稿继续保留，真实变化的内容重新处理。

优点：不会在最需要冲突处理时因来源分支前进而卡死，也不会遗漏任务分支的新提交。

代价：高频提交可能产生多次内部准备和 Provider turn；必须在落地前再次校验最新提交，避免过期结果生效。

### 重试身份

重试沿用第一次提交前已经持久生成的业务身份。冲突准备失败时留在当前会话重试，不新建会话、首发消息或冲突处理操作。内部执行代次可以新增，以真实记录追赶和 Provider 执行历史。

全应用词汇统一为：

- 重试：原业务意图未完成，复用原身份。
- 再次执行：上一轮已经终结，用户开始新运行，允许新运行身份。
- 重新读取：只刷新权威事实，不创建业务操作。

优点：恢复和重新开始不再混淆，服务端成功但响应丢失时不会重复创建。

代价：创建类入口需要稳定创建意图和服务端幂等恢复；旧按钮和错误文案需要按真实动作校正。

## 实施计划

1. 扩展冲突尝试持久记录，保存业务操作、准备态、最新两端提交、内部执行代次和可恢复错误。
2. 权限确认接口先落产品会话、首发提交与冲突创建信封，立即返回会话身份；后台准备独立现场并绑定 Codex 或 Pi。
3. 准备态冻结 Provider 派发但允许当前会话继续排队；配置修改同步全部未派发提交。
4. 来源分支或任务分支变化时在同一业务操作内重建最新现场；最终落地前再校验，变化则继续追赶。
5. 当前会话提供“重试准备”，复用原业务身份并恢复全部队列。
6. 为任务创建类入口补稳定创建意图；审计全应用可见重试入口并按三分法校正文案和行为。
7. 不新增单元测试；执行格式检查、`git diff --check`、`pnpm lint`、`pnpm typecheck`、`pnpm build`、`pnpm package:mac` 和可行的独立 `Zeus Test.app` 真实检查。

## 不变边界

- AI 不直接更新来源分支，不推送远端；Zeus 复验后才完成本地合入。
- 不执行本任务仓库的 `git commit`、`push`、`merge` 或 `revert`。
- 不生成或启动生产身份 `Zeus.app`。
- 静态检查、构建、打包与真实 GUI/Provider 验收分别陈述，不能互相替代。

## 当前阶段

代码、文档、静态门禁、构建和测试身份打包已完成；真实 GUI 与 Provider 动态链路因其他 worktree 的同 Bundle ID 测试实例正在运行而未执行。

## 实施结果

- 冲突确认接口不再同步等待 worktree、merge 和 Provider。它先持久创建唯一会话、首条提交、冲突业务操作和可恢复准备信封并返回；Renderer 随即打开真实会话并关闭交付窗口。
- Codex 与 Pi 都支持“只持久、不派发”的准备态。准备期间发送的消息进入同一会话队列；模型、权限和执行模式读取会话最新下一轮配置，现场就绪后才释放。
- 会话队列明确显示“正在准备最新冲突现场”；准备失败保留当前会话、首发消息、草稿和队列，并提供“重试准备”。应用重启会恢复仍处于准备中的操作。
- 后台每次创建现场前读取来源分支和任务分支最新提交，创建后再次比对；变化时清理旧现场并在同一业务操作内继续下一执行代次。落地前再次校验，变化时继续当前会话而不是把合入标记失败。
- 冲突草稿携带三方指纹；只有最新现场指纹一致时才复用草稿。内部追赶代次可以产生新的 Provider turn，但不会投影成新的用户消息。
- 常规创建任务、图谱节点转任务、模板转任务、图谱问答转任务和 Runtime 会话转任务均在首次提交前保存稳定幂等身份；原请求失败后的同输入重试返回原任务。
- 更新检查、用量读取、任务列表、Git 工作台和代码扫描等纯刷新入口分别改为“重新检查”“重新读取”或“重新扫描”，避免把刷新误称为重试。

- `pnpm package:mac`：通过，只生成当前任务的 `Zeus Test.app`、测试 DMG 和 blockmap。
- 测试包身份：`CFBundleDisplayName=Zeus Test`、`CFBundleIdentifier=dev.hypha.zeus.test`、版本 `0.3.2`；`codesign --verify --deep --strict` 和 Designated Requirement 校验通过。

### 未冒充通过的边界

- 当前显示器为主外接屏 ID 3、内建屏 ID 1、非主外接竖屏 ID 5；真实 GUI 启动必须首次落在 ID 5。
- 只读进程检查发现另一个 worktree 的 `Zeus Test.app` 正以相同 Bundle ID 运行。启动本任务包会被单实例机制接管，无法证明窗口来自本任务包，也不能保证首次落在非主外接屏。
- 本轮没有终止、复用或修改该实例，没有启动生产 `Zeus.app`。因此权限弹窗关闭时机、真实会话准备状态、Codex/Pi Provider 启动和分支持续推进的端到端 GUI 行为仍需在同 Bundle ID 实例空闲后，用本任务独立数据目录补验；静态检查、构建和打包不代表这些动态链路已通过。

## 方案得失

优点：用户确认后立即进入同一真实会话；分支继续提交成为后台自动追赶的输入；准备失败和未知响应重试不会重复创建会话、任务或用户消息。

代价：高频并行提交可能触发多次隔离现场重建和内部 Provider turn；最终完成时间取决于能否取得一次可安全落地的最新两端提交快照。持久队列和准备信封也增加了恢复链路的状态复杂度。
