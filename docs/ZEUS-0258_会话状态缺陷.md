# ZEUS-0258 会话状态缺陷

## 当前阶段

已完成领域口径确认、统一终态收口实现、历史数据副本校准和静态/打包门禁。因当前无法在启动前保证隔离应用首窗落在非主外接屏，本任务未启动 GUI 验收包。

## 用户现场

- 会话列表中多条会话长期显示“运行中”。
- 点进会话后运行态短暂消失，继续其他操作后又回到“运行中”。
- 会话内部已经存在模型最终回复，不应继续表达为当前正在处理。

## 已核对事实

### 代码链路

1. 会话行的“运行中”来自 Local Server 投影的 `listRuntimeState=streaming` / `taskRunStatus=running`。
2. 列表投影只要看到 `conversation_submissions.status` 为 `dispatching` 或 `active`，就会判定为运行中。
3. 打开会话后，已连接 controller 依据“没有活动轮次”暂时投影为就绪。
4. 当前 Renderer 每 10 秒读取一次项目权威会话快照；快照再次读到残留的 `dispatching` 提交后，又把会话改回运行中。

### 正式数据只读证据

本轮只读查询 `/Users/david/.zeus/data/zeus.db`，没有启停正式 Zeus，也没有修改数据。

- “品牌使用费抵减情况”：0 条未结束轮次，0 条待处理请求，残留 3 条 `dispatching` 提交。
- “查询在库商品批次”：0 条未结束轮次，0 条待处理请求，残留 1 条 `dispatching` 提交。
- “查询已到货商品批次”：0 条未结束轮次，0 条待处理请求，残留 2 条 `dispatching` 提交。
- 上述每条残留提交都已绑定到一个 `completed` 或 `interrupted` 轮次，并且都能找到客户端消息身份一致的真实用户消息。

## 根因结论

这不是刷新不及时，而是“多条排队消息被立即发送到同一 Provider 轮次”时的提交终态收口缺陷。

- `sendQueuedNow` 会把普通排队提交改为 `dispatching`，并绑定当前 Provider 轮次。
- Provider 轮次结束时，收口代码只用 `find` 取第一条普通活动提交并结束它。
- 同一轮次中其余已成功送达的普通提交没有被收口，长期留在 `dispatching`。
- 完整会话 controller 看到的轮次已终止，而列表轻量投影看到的提交仍在活动，于是产生“点进去消失，自动校准后又回来”的摇摆。

## 已确认的领域口径

1. 已确认：已绑定终态 Provider 轮次、且能证明用户消息已被 Provider 接收的提交，视为“已送达提交”，不得再参与“会话正在运行”判定。
2. 已确认：修正新提交终态链路的同时，自动收口能够精确证明已送达的历史残留，不要求用户逐条打开会话。
3. 已确认：已无活动轮次但无法证明已送达的提交，保留为“需要恢复提交”，会话显示运行失败或需要恢复；不得猜测为成功，也不得继续显示普通“运行中”。
4. 已确认：修复覆盖会话侧边栏、任务表运行状态、会话归档门禁、队列恢复和当前会话标题等同源投影，不做只隐藏侧边栏胶囊的表层修复。

## 历史数据影响面

正式数据首次只读统计共发现 29 条 `active / dispatching` 提交。诊断期间正式 Zeus 继续运行，最终制作校准副本时数据自然推进为：

- 24 条已绑定终态轮次，且具有精确用户消息身份，可以安全自动收口为已送达。
- 5 条没有终态轮次，仍可能属于真实活动工作，不得被历史修复改写。
- 当前没有“轮次已终止但无法证明送达”的正式记录；代码仍必须覆盖该失败分支。

## 完成口径

- 同一 Provider 轮次承载多条已送达用户消息时，轮次终止必须收口所有有精确证据的提交，不只收口第一条。
- 启动或权威快照校准能自动收口精确可证的历史残留，用户无需打开每条会话。
- 不能证明送达的终态绑定提交保留内容并进入需要恢复，不被静默删除或伪造成功。
- 活动轮次和尚未绑定轮次的排队消息继续正确显示运行或排队状态。
- 侧边栏、任务表、归档、队列、标题区在同一次状态校准后收敛为一致结果，不再因点击或 10 秒快照校准反复摇摆。

## 初步修复方向与取舍

### 仅在列表中忽略残留提交

- 优点：改动小，能立即停止假“运行中”。
- 缺点：错误提交仍留在数据层，归档门禁、恢复、队列和其他投影仍可能受影响；只是遮住现象。

### 统一修正提交终态，并自动收口历史残留

- 优点：新消息和历史数据回到同一事实，列表、归档、队列、恢复和任务运行状态都可以共用。
- 缺点：必须严格要求“轮次已终止 + 消息身份精确匹配”，无法证明送达的提交仍要保持待恢复，不能猜测为成功。

本任务采用第二种方向。

## 实施结果

### 统一提交终态

- Provider 轮次完成、中断或失败时，按同一 `providerTurnId` 枚举全部 `dispatching / active` 提交。
- 轮次首提交身份或已持久用户消息的客户端身份精确匹配时，普通提交随轮次收口为完成或失败，引导提交收口为已解决。
- 缺少精确送达证据时，提交保留原文并进入 `paused / recovery_required`，错误码为 `ZEUS_NATIVE_SUBMISSION_DELIVERY_UNCONFIRMED`。
- 普通队列恢复拒绝自动重发这种“可能已经送达”的提交，避免产生重复用户消息。

### 历史残留与实时链路

- 执行宿主恢复时先用本地终态轮次收口历史残留，再连接 Provider；外部恢复失败不会把已证明送达的提交重新降级。
- Provider 实时终态事件与权威线程快照共用同一收口函数，修复同一轮次只结束第一条普通提交的问题。
- 历史校准只改写已绑定本地终态轮次的提交；没有终态轮次的真实活动记录保持不变。

### 同源状态投影

- 精确可证的残留提交收口后，不再影响会话侧边栏、任务运行状态、归档门禁和队列恢复。
- 需要恢复的提交统一投影为失败/需要恢复：后台列表、已连接会话、任务运行状态和当前会话标题不再各自猜测。
