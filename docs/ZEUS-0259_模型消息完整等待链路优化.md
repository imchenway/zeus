## 已确认领域口径

### 模型消息等待链路

用户从进入会话、读取真实历史、建立运行内核连接，到模型产生首段回复、持续补齐正文并完成结构化内容呈现的连续可见过程。各阶段必须表达真实等待对象，不能用同一个通用加载状态混淆。

优点：优化目标从一张骨架图扩展到用户真实感知的完整过程，能系统处理空白、跳变和状态误解。

代价：需要同时核对会话切换、首发创建、历史水合、模型首段等待和结构化流式呈现，改动与真实验收范围大于单纯调整 CSS。

### 真实内容优先

只要界面已经拥有可读的真实正文，就继续保留正文；后台刷新、连接或目标会话首次读取用紧邻当前工作位置的轻量状态反馈。只有应用首次进入或目标区域确实没有任何真实内容时，才展示消息骨架。

优点：用户阅读现场、滚动位置和已加载资源保持稳定，后台校准不会被误解为正文丢失。

代价：会话切换过渡期可能短暂同时出现上一会话正文和目标会话加载状态，必须明确标出内容与输入分别归属哪个会话。

### 首屏历史骨架行数

骨架根据消息正文区域的可用高度动态显示 2–4 行，默认 3 行；行宽使用稳定模式，不按未知的真实消息数量随机变化，也不铺满全部剩余空间。

优点：紧凑窗口不会挤压计划条和输入区，高窗口又不会只留下过量空白。

代价：实现需要感知正文容器尺寸；动态范围必须受控，否则会制造“存在很多历史消息”的错误暗示并增加动画噪音。

### 分阶段等待反馈

等待反馈至少区分“载入历史”“建立连接”“模型处理中”和“正在整理结构化内容”，同一时间只呈现当前阶段，不把多种状态同时堆在界面上。

优点：用户能判断等待发生在哪一段，失败时也能获得与真实原因匹配的恢复动作。

代价：状态投影必须有明确优先级与切换规则，不能让短暂内部事件造成文案频繁跳变。

### 骨架位置与稳定区

首屏历史骨架贴近消息正文底部，也就是未来最新消息进入的位置；计划条、待处理交互和输入框保持既有信息架构与位置，不随骨架出现或消失上下漂移。

优点：真实内容接管时视线移动和布局位移最小，用户仍能判断下一步操作位置。

代价：高窗口上方会保留自然留白，骨架不会占满整个正文画布。

### 骨架出现节奏

首屏读取在 120ms 内完成时直接显示真实正文；超过 120ms 才显示骨架。真实内容一旦到达立即接管，不为了播完动画或满足最短展示时长而延迟正文。

优点：高速路径不会闪一下骨架，慢路径仍有明确反馈，同时不牺牲真实内容的到达速度。

代价：刚超过阈值完成时，骨架可能只短暂可见；视觉收口需要依靠低对比淡出，而不是强制停留。

## 体验评估

### 当前做得正确的部分

1. 已查看会话优先使用真实热缓存，后台校准不会重新遮住正文。
2. 目标会话首次读取时可以保留上一会话正文，目标输入与旧正文动作的归属已经隔离。
3. 任务首发先展示真实用户消息，再在原位置显示连接状态和失败重试，不需要等待 Provider 完成后才出现现场。
4. 模型已经产生可见内容后，通用“正在思考”会收起，避免与真实回复长期并存。
5. 未闭合表格和代码围栏已有结构骨架，并提供“正在整理表格 / 代码块”的读屏标签。
6. 系统开启“减少动态效果”时，会话区域现有循环动画会被统一取消。

### 结构性缺口

#### 高优先级：首次历史读取仍是居中通用加载态

当前 `SessionLoading` 立即出现、固定两行、位于正文区域中央，并显示“正在加载会话”。它与真实消息最终出现的位置不同，也没有 120ms 抑制，因此高速读取可能闪一下，慢读取又会产生从中央跳到底部的视觉位移。

建议：只在没有任何真实正文时进入“载入历史”骨架；延迟 120ms 出现，贴近正文底部，按正文可用高度显示 2–4 行，正文到达后立即接管。

优点：消除大面积无反馈和高速闪烁，同时不改变热缓存与旧正文保留规则。

代价：需要观察正文容器高度并维护受控行数，不能只改几条静态 CSS。

#### 高优先级：等待语义分散，没有统一投影优先级

当前顶部状态、首屏骨架、切换底部、首发连接、模型思考和结构骨架分别自行表达状态，存在“正在加载会话”“正在加载”“正在连接”“正在思考”等多套口径。它们单独看大多合理，组合时可能重复或短时间跳文案。

建议：建立单一等待状态投影，优先级为失败与待用户操作 > 真实内容更新 > 结构整理 > 模型处理中 > 建立连接 > 载入历史；同一位置一次只表达一个真实等待对象。

优点：用户知道自己在等什么，失败后的重试也能对应真实阶段。

代价：需要梳理现有状态机，不应靠文案替换或 CSS 互斥猜测业务状态。

#### 中优先级：模型首段等待文案“正在思考”过度假设 Provider 行为

`starting_turn`、前置处理和最终回答阶段目前主要统一显示“正在思考”。对不暴露推理过程或只是排队、调度、调用工具的模型，这个词并不精确。

建议：首段可见内容前使用中性的“模型处理中”；只有 Provider 明确提供推理活动时才使用“正在思考”。已有工具活动或过程说明出现后，不再叠加通用等待提示。

优点：跨 Codex、Pi 和后续运行内核都更真实。

代价：文案更准确但情绪感更弱，需要依靠位置和轻量节奏维持反馈感。

#### 中优先级：读屏可能收到重复状态播报

会话顶部状态、加载骨架、连接状态、正文思考提示和失败卡分别使用多个 `status`、`alert` 与 `aria-live` 区域。截图无法证明真实读屏结果，但从 DOM 结构看存在同一状态变化被多处播报的风险。

建议：视觉上可以在不同区域保留必要状态，读屏播报应由一个稳定 live region 汇总；骨架线条保持 `aria-hidden`，只播报阶段文案。失败使用 `alert`，普通阶段变化使用 `polite`。

优点：减少重复打断，状态顺序更可理解。

代价：需要真实 VoiceOver 验证，静态代码审查不能替代。

### 视觉细节建议

- 载入历史骨架使用稳定宽度序列，建议按行循环 `78% / 96% / 62% / 84%`；行数由容器高度截取，不随机生成。
- 骨架高度保持接近一行正文的视觉重量，但颜色只需比背景高一层，不模拟真实文字颜色。
- 普通动效只做低对比呼吸或轻微明度移动，不横向扫出高亮带；减少动态效果时显示静态占位。
- 骨架淡出只服务于视觉收口，不得延迟真实正文挂载，也不得重置滚动位置。
- 表格和代码块继续使用现有带外框的结构骨架，不与首屏历史骨架共用外观，避免用户误判正在读取历史还是整理当前回答。

## 推荐实施顺序

1. 先建立统一等待状态投影与播报出口，避免在旧分支上继续增加第五套加载状态。
2. 再把首次历史读取骨架改为 120ms 延迟、正文底部、2–4 行动态布局。
3. 将“正在思考”收紧为“模型处理中 / 明确推理活动”两类真实语义。
4. 最后统一骨架颜色、动效、深浅主题、窄窗口与减少动态效果细节。

这个顺序的优点是先修真实语义再调视觉，后续样式不会建立在错误状态上；代价是首轮改动不止一个组件，但可以避免重复返工。
