# ZEUS-0260 会话 Markdown 列表换行诊断

## 用户现场

会话回复中的有序列表被拆成“编号一行、标题一行、正文再空一行”，列表项之间也有过大留白。用户需要确认这是模型原文问题，还是 Zeus 渲染问题。

## 本轮领域口径

- **原始换行**：模型或用户在消息源文本中真实写入的换行与连续空行，属于已有“保真正文”。
- **Markdown 结构换行**：Markdown 解析后为组织列表、段落和显式换行节点而产生的结构空白；它不等于用户或模型原文。
- **视觉软换行**：文字超出可用宽度后由界面自然折行，不改变消息原文。

## 已核对事实

### 模型原文

原生 Codex JSONL 中的对应回复为：

```text
1. SDK 快速通道  
   “转人工、人工客服、投诉”等确定性短语仍在客户端直接转七鱼。

2. 后端可信受理  
   未命中固定关键词的自由文本照常发给后端。
```

因此模型确实主动写入了两种排版：

1. 列表标题末尾的两个空格加换行，表示 Markdown 显式换行。
2. 相邻编号项之间的一个空行，使该列表成为松散列表。

这会产生一定纵向间距，但不应把 `1.` 与 `SDK 快速通道`拆成两行，也不应在标题和正文之间再额外增加一整行空白。

### Zeus 渲染链

- `SafeMarkdown` 把原文交给 `react-markdown` 与 GFM 插件，没有在传入前删除上述换行。
- 全局“保真正文”样式同时对 Markdown 的 `p` 和 `li` 设置 `white-space: break-spaces`。
- 松散列表会把每个项目组织成 `li > p`；显式换行还会生成 `br`。渲染器在这些结构节点之间产生的排版空白，又被 `li` 和 `p` 上的 `break-spaces` 当成正文显示。
- 会话样式另外给段落和列表块设置 `12px` 底部间距，并给相邻列表项设置 `4px` 顶部间距，进一步放大结果。

## 诊断结论

这是“模型排版偏松 + Zeus 渲染缺陷放大”的组合问题，但截图中最丑的部分主要由 Zeus 渲染导致。

- 模型责任：使用了松散有序列表，并在短标题后增加显式换行，原始排版本身不够紧凑。
- Zeus 责任：把 Markdown 结构换行误当作原始换行保留，导致编号、标题、正文之间出现模型原文中没有的额外空行。

即使以后约束模型少用空行，同样的 Markdown 仍可能来自用户、历史消息或其他模型，因此不能只靠提示词规避。

## 补充现场：紧凑嵌套列表

第二张用户截图中，外层开关名与内层 `false / true` 被拆成多段大留白。对应 Provider JSONL 原文为：

```text
- `text_moderation_enabled`
  - `false`：完全跳过 `chat_detection`，没有调用费用和额外延迟。
  - `true`：每条符合条件的用户自由文本调用审核服务。

- `text_moderation_auto_handoff_enabled`
  - `false`：只记录风险结果，不改变用户流程，便于先观察误报。
  - `true`：中、高风险辱骂或网络暴力自动转人工。
```

内层列表项之间没有原始空行，外层开关名与所属内层列表之间也没有原始空行。这是标准的紧凑嵌套列表，正常显示应为连续的外层项和紧随其后的内层项。

因此第二个现场比第一个现场更能排除模型原始空行的责任：

- `react-markdown` 为外层 `li`、内层 `ul` 和内层 `li` 组织结构节点。
- `white-space: break-spaces` 作用在每层 `li` 后，各层结构空白被叠加成可见空行。
- 列表块和相邻列表项的额外 margin 继续放大纵向间距。

第二个现场的过大留白可以直接定性为 Zeus 渲染缺陷，不是模型输出了这些空行。

## 修复方案对比

### 方向一：只约束模型输出更紧凑

优点：改动小，新回复出现松散列表的概率会降低。

缺点：无法修复历史消息、用户输入和其他运行内核的同类内容，也不能消除结构空白被误渲染的根因。

### 方向二：只收紧所有列表间距

优点：可以快速缓解截图中的大面积留白。

缺点：会吞掉用户真实输入的空行，与“保真正文”契约冲突；编号被拆行的问题也不一定消失。

### 方向三：区分原始空白与 Markdown 结构空白

优点：保留真实原文，同时不显示渲染器自己产生的换行；历史消息重新渲染即可生效。

缺点：需要按 Markdown 节点类型收窄空白保留边界，并真实核对普通段落、显式换行、紧凑与松散列表、嵌套列表、代码块和引用。

用户确认选择方向三，并统一覆盖智能体回复、用户消息、排队消息和计划等共用 `SafeMarkdown` 的入口。

## 实施记录

- 保留 `SafeMarkdown` 的 GFM 解析、受信资源和复杂度边界，不改写或清洗消息原文。
- 保真空白只作用于标题、段落和表格单元格等文字叶子。
- 列表项与引用属于可容纳子块的 Markdown 结构容器，不再使用 `break-spaces`；渲染器组织 `li > p`、`li > ul` 和 `blockquote > p` 时产生的空白回归普通折叠。
- 显式 Markdown 换行继续由 `br` 表达，段落与列表项间距继续由会话排版样式表达。
