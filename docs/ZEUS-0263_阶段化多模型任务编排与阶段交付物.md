# ZEUS-0263：阶段化多模型任务编排与阶段交付物

- 调研日期：2026-08-25
- 当前阶段：实现与分层验收已完成；真实 Provider 多模型发送待具备隔离凭据后补验
- 用户目标：同一任务在不同阶段使用不同模型，例如 GPT 制定计划、DeepSeek 执行、GPT 代码审查；任务详情可按阶段查看完整、可追溯的交付物

## 结论

Zeus 不应只增加一个“按顺序换模型”的下拉框。要让这个能力在失败恢复、返工、代码审查和长期追溯中成立，最小完整模型应包含四层：

1. **任务工作流**：任务采用的阶段路线及配置快照；
2. **任务阶段**：计划、实施、代码审查等具有输入输出契约的工作单元；
3. **阶段尝试**：某阶段一次冻结配置后的真实执行，重试和返工必须创建新尝试；
4. **阶段交付物**：由某次尝试生成、按版本保留并可被验收或驳回的任务资产。

推荐默认路线为“计划 → 实施 → 代码审查”：

- 计划阶段默认使用 GPT，工作态为只读规划；
- 实施阶段默认使用 DeepSeek，在任务获准工作区内执行；
- 代码审查阶段默认使用 GPT，只读审查已冻结的代码来源；
- 下游阶段只接收上游已验收的交付物引用，不从聊天末尾猜测输入；
- 审查要求修改时，创建新的实施尝试和新的审查尝试，不覆盖旧证据。

优点：模型、权限、代码来源、阶段结果和返工链都可审计，进程中断后也能从明确边界恢复。

缺点：比单会话连续聊天多出阶段状态、交接和验收操作；如果一开始支持任意图编排，会显著扩大状态机和界面复杂度。

因此首版应先支持有序阶段和返工回路，不应直接建设通用 DAG 编排器。

## “调研市面所有 harness”的范围说明

无法对持续变化、没有公开实现或没有稳定文档的全球所有项目做可证实穷举。本次采用“设计家族全覆盖、代表项目取官方资料”的口径，覆盖以下能力类型：

- 模型智能体运行 harness；
- 多智能体交接与主管模式；
- 确定性或图式工作流；
- 长任务持久化、暂停、恢复与重放；
- 版本化交付物和面向人的运行产物；
- 编码智能体轨迹与代码审查隔离。

纯模型网关、只做路由的 SDK、没有可核实官方语义的闭源宣传，以及与阶段交付无关的聊天机器人框架，不作为主要设计证据。后续新增框架若仍落入上述家族，只需验证它是否带来新的领域语义，不按品牌数量反复扩张模型。

## 市面 harness 对照

### 1. OpenAI Codex 与 Agents SDK

官方资料：

- [Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform)
- [Agents SDK orchestration](https://developers.openai.com/api/docs/guides/agents/orchestration)

Codex 把 harness 定义为模型周围的执行系统：理解任务、维护上下文、调用工具、报告进度、处理失败、承接批准并产生可用结果。宿主应用仍需拥有业务上下文、权限规则、用户同意和结果呈现。Agents SDK 区分两种编排：主管持续拥有对话的 agents-as-tools，以及由专家接管后续响应的 handoff。

可借鉴点：Zeus 必须拥有任务阶段、权限、交付物和验收语义，不能把 Provider thread 当作任务工作流；阶段间由谁继续面向用户必须是显式契约。

优点：宿主与运行 harness 的责任边界清楚，适合 Zeus 已有 App Server 与多 Provider 架构。

缺点：通用 agent orchestration 不会自动提供 Zeus 所需的任务级交付物、代码来源冻结和本地工作区交付关系。

### 2. LangGraph

官方资料：

- [Persistence](https://docs.langchain.com/oss/javascript/langgraph/persistence)
- [Interrupts](https://docs.langchain.com/oss/javascript/langgraph/interrupts)

LangGraph 在每个 super-step 保存 checkpoint，以 thread 标识持久状态，支持暂停、人机协作、重放、分叉和故障恢复。恢复 interrupt 时，所在节点可能从头执行，因此节点中的副作用必须幂等。

可借鉴点：阶段配置和接受结果应形成不可变快照；重试不能原地覆盖；暂停点必须是持久事实。

优点：恢复与 time travel 语义成熟，能解释为什么“阶段尝试”必须独立建模。

缺点：graph checkpoint 是运行状态，不等于面向任务使用者的正式交付物；直接引入图模型会让首版过度通用化。

### 3. Microsoft Agent Framework、AutoGen 与 Semantic Kernel

官方资料：

- [Agent Framework overview](https://learn.microsoft.com/en-us/agent-framework/overview/)
- [Workflow checkpoints](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints)

Microsoft Agent Framework 是 AutoGen 与 Semantic Kernel 的后继方向，明确区分开放式 agent 与步骤清楚、可重复的 workflow，并为类型化图工作流、长任务、人机协作和 checkpoint 提供统一模型。

可借鉴点：Zeus 的模型自由执行应留在阶段内部；阶段顺序、验收和返工则应由确定性工作流控制。

优点：把 agent 和 workflow 分层，适合“阶段固定、阶段内部智能”的任务形态。

缺点：完整工作流基础设施较重，且不会替 Zeus 解决桌面端任务详情与本地代码资产归档。

### 4. Google Agent Development Kit

官方资料：

- [Workflow agents](https://adk.dev/agents/workflow-agents/)
- [Artifacts](https://adk.dev/artifacts/)

ADK 提供顺序、循环、并行等确定性 workflow agent，并把 artifact 定义为带名称、版本和作用域的二进制数据；同名写入产生新版本。

可借鉴点：阶段路线与模型执行应分离；交付物必须有稳定身份和版本，而不是只保存最后一条回复。

优点：workflow 与 artifact 两条概念线清楚，直接支持版本化思路。

缺点：ADK artifact 主要以会话或用户为作用域；Zeus 需要任务作用域、阶段归属、验收状态和下游交接引用。

### 5. CrewAI Flows

官方资料：[Flows](https://docs.crewai.com/en/concepts/flows)

CrewAI Flow 以结构化或非结构化状态连接 agent，支持持久化、恢复、分叉和人工反馈。默认可用 SQLite 保存流程状态。

可借鉴点：模型 agent 应作为阶段执行者嵌入受控 Flow，人工反馈是流程状态而非普通聊天消息。

优点：上手轻，agent 与持久流程结合直接。

缺点：部分恢复路径以便利性为先，Zeus 不能在状态缺失时静默创建新流程；本地代码任务需要更严格的来源和权限证据。

### 6. Mastra Workflows

官方资料：[Workflow snapshots](https://mastra.ai/en/reference/workflows/snapshots)

Mastra snapshot 保存步骤输出、已走路径、暂停元数据与重试信息，流程暂停时持久化，恢复时从快照继续；大内容推荐保存稳定引用而非塞入状态。

可借鉴点：阶段状态只保存索引、摘要和引用，大正文交给资产仓储；不同步骤可绑定各自的执行配置。

优点：快照与大对象外置的边界贴近 Zeus 当前架构。

缺点：workflow snapshot 仍偏运行时内部事实，必须另建面向人的交付物投影和验收状态。

### 7. Prefect

官方资料：

- [Artifacts](https://docs.prefect.io/v3/concepts/artifacts)
- [Results](https://docs.prefect.io/v3/advanced/results)

Prefect 明确区分面向人的 artifact 与任务/流程 return result。artifact 可在界面展示 Markdown、表格、链接等内容并保留更新历史；result 则服务恢复、缓存和下游计算，两者的持久化策略不同。

可借鉴点：运行结果、checkpoint、日志和任务交付物不能合成一张表或一个 JSON 字段。

优点：对“机器继续执行的数据”和“人要验收的产物”区分最清晰。

缺点：它是通用数据工作流平台，不处理模型会话、代码工作区和 Provider 审批语义。

### 8. Temporal

官方资料：[Temporal documentation](https://docs.temporal.io/)

Temporal 以事件历史重放实现长时间、可恢复的 durable execution，进程或基础设施失败后继续既有工作流。

可借鉴点：阶段转换应由持久事件驱动，任何外部副作用都需要稳定幂等身份。

优点：故障恢复和长期工作流语义非常强。

缺点：基础设施和确定性约束重；它不提供模型特定配置或任务交付物界面，当前 Zeus 本地桌面架构没有必要为首版引入其运行时。

### 9. Claude Agent SDK 与 Managed Agents

官方资料：

- [Multi-agent systems](https://platform.claude.com/docs/en/managed-agents/multi-agent)
- [Events and streaming](https://platform.claude.com/docs/en/managed-agents/events-and-streaming)

Managed Agents 可共享 sandbox、文件和凭据，但每个 agent 拥有隔离且可持久的 thread，并可分别配置模型、工具、MCP 和 skills。事件流区分 session 与 thread；临时 sandbox 有保留期限，重要结果需要及时导出。

可借鉴点：共享任务工作区不等于共享会话；每个阶段尝试应能有独立运行身份，正式交付物必须由 Zeus 资产仓储持有，不能只留在 Provider sandbox。

优点：独立 thread 与共享资源的组合适合阶段隔离。

缺点：Provider 托管生命周期和 Zeus 本地任务生命周期不同，不能把托管 thread 当作永久档案。

### 10. GitHub Copilot SDK 与 custom agents

官方资料：[Custom agents](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/custom-agents)

Custom agent 可分别指定提示词、工具、MCP、模型和推理配置，并通过父会话观察子 agent 生命周期；系统也可自动推断何时委派给某个 agent。

可借鉴点：不同阶段配置不同模型和工具是可行机制，但 Zeus 的正式阶段不能依赖不确定的自动推断，必须把选择和交付边界写成任务事实。

优点：角色级模型与工具配置直观，适合预设“规划者、实施者、审查者”。

缺点：自动委派对灵活聊天友好，对审计型任务阶段不够确定；custom agent 输出本身也不等于已验收交付物。

### 11. OpenHands

官方资料：[Agent API](https://docs.openhands.dev/sdk/api-reference/openhands.sdk.agent)

OpenHands 以事件驱动的 agent、工具和轨迹组织编码执行，持久化配置与运行时 agent 有明确区别，并可导出 trajectory。

可借鉴点：完整轨迹适合作为执行证据，但任务详情应展示低噪音交付物摘要并按需链接原始证据。

优点：编码任务事件与工具证据丰富。

缺点：轨迹体积大、噪音高，不能直接充当计划、实施结果或审查报告。

### 12. SWE-agent

官方资料：[Agent reference](https://swe-agent.com/latest/reference/agent/)

SWE-agent 的主循环保存 history、环境信息、模型统计和 trajectory，便于复盘软件工程任务。

可借鉴点：阶段尝试应记录模型、工作现场和执行统计，但这些属于来源证据，不是交付物正文。

优点：编码任务复现实证较完整。

缺点：主要围绕一次 agent run，缺少任务级多阶段验收、返工和交付物聚合。

## 跨框架共同规律

| 设计问题 | 市面共同做法 | Zeus 采用方式 |
| --- | --- | --- |
| 模型与流程 | 模型负责开放式工作，workflow 负责确定性顺序 | 阶段内部由模型执行，阶段推进由 Zeus 控制 |
| 持久化 | checkpoint/snapshot 保存可恢复运行状态 | 阶段尝试冻结配置和状态，但不冒充交付物 |
| 重试 | 新运行、重放或分叉保留原历史 | 重试创建新阶段尝试，不覆盖旧尝试 |
| 交付内容 | 大正文或文件以 artifact/reference 外置 | 复用 Execution Assets，只在阶段表保存稳定引用 |
| 人工介入 | interrupt/human feedback 是显式状态 | 阶段验收、驳回、要求修改是持久操作 |
| 多智能体 | 独立 thread 或 handoff，边界可观测 | 每次阶段尝试拥有明确会话/运行来源 |
| 可读性 | 面向人的 artifact 与机器 result 分离 | 任务详情展示交付物；运行过程留在会话详情 |

## Zeus 当前现场

### 已有可复用能力

- `tasks`、`task_workspaces`、`task_events` 已提供任务、真实工作区和通用事件归属；
- 产品会话可关联任务，并已拥有 submission、turn、运行分段、执行快照、模型请求和模型历史；
- 会话运行时已经能选择 Provider、模型、推理强度、工作态和权限；
- 代码审查入口已经采用独立只读会话，并可绑定真实工作区；
- Execution Assets 已适合保存完整正文或文件，其他上下文只持有稳定引用；
- 任务详情已有相关会话、代码交付工作区和事件区域，可扩展阶段视图。

优点：无需新造模型调用内核、资产存储或任务基础实体。

缺点：现有能力分散在任务、会话和运行时上下文中，还没有统一的阶段归属与验收契约。

### 当前缺口

- 没有“任务工作流”或“任务阶段”实体；
- 任务事件只表达发生过什么，不能承担当前阶段、重试分支或验收指针；
- 会话模型历史说明模型何时切换，不说明哪次切换属于哪个任务阶段；
- assistant 消息和完整运行轨迹没有交付物类型、版本、验收状态或下游引用；
- 代码审查会话虽只读，但没有一等的审查阶段和返工闭环；
- 任务详情无法按阶段聚合配置、执行尝试、正式产物与来源证据。

## 领域模型

### 任务工作流

任务采用的有序阶段路线及其配置快照。首版只支持线性主路线和“审查要求修改 → 新实施尝试”的受控返工，不开放任意 DAG。

### 任务阶段

任务中具有明确目的、输入契约、输出契约和执行策略的工作单元，例如计划、实施、代码审查。它不是任务状态、会话、模型或一次运行。

建议状态：`pending`、`ready`、`running`、`awaiting_acceptance`、`accepted`、`changes_requested`、`failed`、`cancelled`、`skipped`。

### 阶段尝试

任务阶段在一组冻结配置下的一次真实执行。记录会话、submission/segment、Provider、模型、推理强度、工作态、权限、工作区、开始结束时间和结果。重试、换模型、改权限或返工都创建新尝试。

### 阶段交付物

由某次阶段尝试产生、任务使用者可查看和验收的版本化结果。保存标题、类型、摘要、资产引用、内容指纹、版本、来源尝试和验收状态，不把大正文复制进阶段表。

### 阶段交接

上游阶段被验收的交付物引用以及必要的结构化摘要。下游阶段从交接清单构造输入，不扫描整段聊天寻找“最终答案”。

## 默认三阶段契约

### 计划阶段

- 默认角色：规划者；
- 默认模型：GPT；
- 默认工作态：计划/只读；
- 输入：任务描述、主任务文档、领域上下文、允许读取的工作区事实；
- 必须交付：Markdown 计划、验收标准、风险、假设、明确未决项；
- 验收后交接：已接受计划版本及结构化验收标准。

优点：实施模型拿到的是已确认计划，不需从长会话中猜测用户决定。

缺点：计划验收增加一次人工动作；对极小任务显得偏重，应允许跳过阶段。

### 实施阶段

- 默认角色：实施者；
- 默认模型：DeepSeek；
- 默认工作态：开发；
- 输入：已验收计划、任务主文档、授权工作区；
- 必须交付：变更摘要、文件清单、运行/构建验证证据、未验证项、工作区与来源快照；
- 可选交付：界面截图、构建包、日志、数据迁移说明等资产引用。

优点：适合把成本、速度或编码能力不同的模型放到执行阶段。

缺点：模型或 Provider 切换会带来上下文重新编译；实施结果必须结构化导出，不能只依赖原生 thread。

### 代码审查阶段

- 默认角色：审查者；
- 默认模型：GPT；
- 默认工作态：代码审查/只读；
- 输入：已验收计划、实施交付物、精确工作区、来源 HEAD 或工作区指纹；
- 必须交付：按严重程度排序的发现、审查覆盖范围、证据、结论；
- 结论：通过、带已知限制通过、要求修改；
- 要求修改：回到同一实施阶段创建新尝试，随后再创建新审查尝试。

优点：审查者与实施上下文隔离，权限和来源清楚，旧审查不会被返工覆盖。

缺点：未提交工作区需要额外冻结文件状态或指纹，单靠 Git SHA 不足以表达全部被审内容。

## 持久化建议

### `task_workflows`

保存任务采用的工作流模板、修订号、总体状态、当前阶段和创建时间。任务初始化后保存模板快照，后续模板变化不回写既有任务。

### `task_stages`

保存阶段 key、顺序、类型、标题、状态、输入输出契约和执行策略。阶段第一次启动后冻结该修订；改变已启动阶段配置只能创建新尝试或新工作流修订。

### `task_stage_attempts`

保存尝试序号、关联会话和运行证据、冻结的模型与权限配置、工作区/来源快照、状态、时间、错误和结果摘要。每个尝试只允许一次终态收敛。

### `task_stage_deliverables`

保存任务、阶段、尝试、交付物类型、标题、摘要、版本、资产引用、SHA-256、验收状态和时间。正文、文件、截图或大型 JSON 由 Execution Assets 持有。

### `task_events`

继续记录阶段创建、启动、提交验收、接受、驳回、返工等时间线事件，但不作为阶段当前状态或交付物权威来源。

优点：领域事实可查询、约束和恢复，任务详情不必反解事件 JSON。

缺点：新增实体和事务边界较多，必须确保“运行完成、交付物落盘、阶段进入待验收”不会出现半成功。

## 一致性与失败边界

- 阶段开始前冻结模型、推理强度、权限、工作态、工作区和输入交付物版本；
- Provider 接受运行前失败可安全重试为新尝试；结果未知时保持阻塞，不自动重发；
- 运行完成不等于阶段完成，只有正式交付物成功落盘后才进入 `awaiting_acceptance`；
- 接受操作以交付物版本为目标，旧版本永不被新版本隐式替换；
- 下游已开始后，上游接受指针不能静默改变；修改上游需要显式返工并让下游旧尝试失效或保留为历史；
- 删除或过期 Provider thread 不影响已导出的任务交付物；
- 资产写入和数据库引用必须采用可恢复的暂存/提交协议，并维持资产引用持有关系。

## “沉淀任务相关所有内容”的安全口径

任务详情应聚合用户完成工作所需的全部可交付事实，而不是复制所有内部数据：

应沉淀：

- 每阶段的目标、配置快照、状态和尝试历史；
- 正式计划、实施摘要、审查报告及其历史版本；
- 相关文件、截图、构建包、验证日志等资产；
- 会话、模型请求、工作区、Git 来源与验证证据的可追溯链接；
- 验收、驳回、返工和跳过理由。

不应作为任务交付物沉淀：

- 模型隐藏思维链；
- 密钥、令牌、环境敏感值；
- 未裁剪的 Provider 私有载荷；
- 重复复制的原生 JSONL 或完整工具轨迹；
- 尚未被用户或阶段契约认定为结果的中间闲聊。

优点：任务长期可读且满足安全边界。

缺点：完整运行诊断仍需跳转会话或原始资产，任务详情不是所有底层日志的单页镜像。

## 任务详情建议

任务详情新增“阶段与交付物”主区域：

1. 顶部显示阶段轨道、当前阶段和总体进度；
2. 每个阶段显示角色、模型、工作态、权限、状态和最近尝试；
3. 展开后按版本列出交付物，支持预览原文、查看来源会话和验收/要求修改；
4. 尝试历史折叠展示模型配置、开始结束时间、失败或中断原因；
5. 代码审查显示被审工作区、HEAD/工作区指纹和结论；
6. 通用任务事件保留为低优先级时间线，不与正式交付物混排。

优点：用户先看到“阶段产出了什么”，再按需下钻运行过程。

缺点：窄屏下信息密度高，需要阶段摘要、折叠和长路径换行，不能把所有字段默认平铺。

## 首版建议范围

纳入：

- 任务级有序阶段；
- 默认计划、实施、代码审查三阶段；
- 每阶段独立模型、推理强度、工作态和权限快照；
- 阶段尝试与版本化交付物；
- 人工验收、要求修改、重试、跳过；
- 任务详情阶段轨道、交付物预览和来源链接；
- 已有会话、代码审查、Execution Assets 与任务事件的关联。

暂不纳入：

- 任意 DAG、并行 join 或条件表达式编辑器；
- 自动让模型创建无限子阶段；
- 跨任务全局 artifact 市场；
- 根据基准分数自动替换用户选定模型；
- 把阶段推进授权给不可解释的模型路由器；
- 以提交、推送或发布作为所有任务的强制终点。

## 已确认产品决策

2026-08-25，用户确认以下边界。实现与验收均以这些选择为准。

### 1. 阶段与会话的关系

确认：每次阶段尝试使用独立产品会话，任务详情负责聚合，上游通过已验收交付物交接。

- 优点：模型、权限、工作态、代码审查来源和失败边界最清楚；
- 缺点：会话数量增加，需要把交接摘要显式编译给下游。

备选：全阶段复用一个产品会话。

- 优点：聊天连续、用户切换少；
- 缺点：阶段与模型历史边界模糊，只读审查容易被实施上下文污染，权限切换更难审计。

折中：计划与实施共用，代码审查独立。

- 优点：保留主要连续性并隔离审查；
- 缺点：规则不一致，后续扩展阶段时更难预测。

### 2. 阶段配置范围

确认：从模板初始化到任务，尚未开始的阶段可在任务内编辑，开始后冻结。

- 优点：兼顾团队默认值与单任务模型选择；
- 缺点：需要保存模板版本和任务快照，并解释何时不可编辑。

备选：固定三阶段；或只能修改项目模板、任务内不可改。

- 固定三阶段优点是首版简单，缺点是无法覆盖设计、测试、发布等任务；
- 仅模板可配优点是团队一致，缺点是临时任务适应性弱。

### 3. 阶段推进方式

确认：按阶段分别配置人工或自动推进。默认计划和代码审查采用人工验收；实施阶段首版也默认人工验收，用户可在阶段开始前改为自动推进。

- 优点：不会把错误计划或实施结果自动扩散到后续模型；
- 缺点：长任务需要用户多次确认。

未选择的备选：全程统一人工推进或全程自动推进。

- 全自动优点是吞吐高，缺点是错误扩散和外部副作用风险高；
- 分阶段配置最灵活，缺点是首版状态与授权说明更复杂。

## 实现结果

### Work Management 与 Execution Assets

- 新增 `task_workflows`、`task_stages`、`task_stage_attempts`、`task_stage_deliverables` 四张 Core 表，并纳入表权威与生命周期矩阵；

- 阶段启动只接受独立新会话；请求中的模型、推理强度、服务等级、工作态和权限必须与冻结阶段配置完全一致；

- Provider 调用前失败记录为 `failed`，已开始 RPC 而结果未知时记录为 `outcome_unknown`，不会自动重发；
- 下游提示词只编译已验收交付物；正文读取失败时停止启动，不以摘要或空内容继续；
- 代码审查必须继承产生当前已验收实施交付物的精确会话现场，并继续保持只读权限。

### 任务详情

- 新增“阶段交付”区域，展示总体进度、阶段状态、模型、推理强度、推进方式和独立阶段会话入口；
