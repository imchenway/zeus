# ZEUS-0267 任务推送即时进入开发中

## 任务目标

用户确认推送任务后，任务与新会话从第一帧起直接位于项目配置的“推送后状态”（默认显示“开发中”），不再先创建“待开始”分组、随后跨组跳动。

## 现状与根因

- Renderer 在用户确认后立即投影任务首发工作面和侧边栏会话行。
- 这条会话行按任务当前管理状态分组，因此首次出现时仍位于“待开始”。
- Local Server 只有在真实会话持久化且首轮执行进入 `active` 后，才把项目默认状态改为推送后状态。
- 实时任务更新到达后，会话行再次移动到“开发中”，形成用户看到的分组闪现与跳动。

## 已确认规则

1. 任务处于项目默认状态时，确认推送即进入项目推送后状态，不等待会话或首轮结果。
2. 任务已经处于推送后状态时直接推送，不重复询问。
3. 测试中、待验收、阻塞、已完成、已取消及项目自定义的其他状态，在原推送弹窗内询问一次。
4. 询问提供“改为推送后状态并推送”和“保留当前状态并推送”；用户可以返回继续编辑推送配置。
5. 终态任务只有选择“改为推送后状态并推送”时才重开，不允许静默重开。
6. 选择改状态后，会话创建失败、首轮失败或重试都不回退任务状态。
7. 状态同步失败仍继续创建会话；当前界面保持推送后状态，在会话工作面原位提示未同步并允许重试。
8. 推送后用户手动修改状态时，人工选择优先，停止本次推送的后台状态重试。
9. 状态变化是任务全局事实，任务列表、任务详情、会话标题和侧边栏分组必须一致，不做仅侧边栏生效的视觉特例。

## 方案取舍

### 状态确认时点

采用“用户确认推送即形成状态意图”。

- 优点：界面即时稳定，任务状态表达用户已经开始本次工作。
- 缺点：推送后状态不再保证真实会话或首轮已经成功建立，运行结果需要由会话状态独立表达。

不再采用“首轮进入 active 后才改状态”。

- 优点：状态能证明 Provider 已经开始执行。
- 缺点：即时会话行会先落入旧分组，异步成功后再跨组移动；失败还会让用户已经确认的开工意图不可见。

### 状态同步与会话创建

采用两个并行结果：界面先统一投影，状态持久化独立重试，会话创建不等待状态保存。

- 优点：状态服务短暂失败不会阻断任务执行，也不会让会话跳回旧分组。
- 缺点：需要显式展示“任务状态未同步”，并用原状态保护重试，避免覆盖后续人工修改。

### 非默认状态

采用原推送弹窗内的显式选择，不叠加第二层弹窗。

- 优点：模型、权限、工作区和补充信息现场完整保留；终态重开和阶段回退都有明确授权。
- 缺点：提交动作多一个确认阶段，弹窗需要同时承载配置与状态决策。

## 实现范围

1. 在推送弹窗中增加非默认、非推送后状态的原位确认。
2. 建立任务推送状态意图，并在首发工作面与会话行出现前投影到所有状态入口。
3. 增加受原状态保护的推送状态同步接口，记录任务事件、审计与实时更新。
4. 移除首轮 `active` 后才自动迁移默认状态的旧逻辑。
5. 状态同步失败时保留当前投影、原位提示并支持自动或手动重试。
6. 人工状态修改使本次推送状态同步失效，迟到结果不得覆盖人工选择。
7. 不新增或恢复单元测试、组件测试或 DOM/CSS 契约测试。

## 实施结果

1. 待开始任务确认推送时，Renderer 在同一批界面更新中先投影项目推送后状态，再插入任务首发工作面与侧边栏会话行；任务列表、详情、会话标题和分组读取同一任务投影。
2. 已处于推送后状态的任务直接推送；其他状态在原推送弹窗底部显示当前状态，并提供“改为推送后状态并推送”“保留当前状态并推送”“返回”三个动作。
3. 状态持久化使用独立接口，与会话创建并行开始；接口只在服务端当前状态仍等于推送确认时的原状态时迁移，状态已经被人工改动则返回已被替代，不覆盖新事实。
4. 状态同步记录 `task.management_status.changed` 任务事件、系统审计和 `task.updated` 实时事件；旧的首轮 `active` 成功回调不再修改任务管理状态。
5. 状态同步失败时保留推送后状态投影，使用退避策略自动重试；真实会话接管后在首发消息下方显示“任务状态未同步”和手动重试入口。
6. 会话创建与状态同步同时失败时合并表达两项失败；重试会先收口状态同步，再继续原会话创建或上下文重新确认，避免丢失状态意图。
7. 用户从任务列表、任务详情或会话标题手动选择其他状态时，本次推送状态同步立即失效，清除乐观投影和后台重试；已经在途的同步与人工修改复用任务串行队列，人工结果最终生效。
8. 任务首发上下文修订只绑定真实首发正文、附件和关联上下文，不再把与首发正文无关的管理状态更新时间计入修订，避免并行状态同步误报上下文变化。
