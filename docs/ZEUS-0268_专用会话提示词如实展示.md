# ZEUS-0268 专用会话提示词如实展示

## 当前阶段

用户已确认产品边界，领域词汇、设计契约、实现、静态检查、构建和独立测试包均已完成。真实 Provider 与 Electron 会话链路尚未动态验收，不以构建结果替代。

## 用户反馈

冲突处理会话中展示的首条用户消息是“请处理当前本地合入中的全部冲突。”，但 Zeus 实际提交给模型的是包含分支方向、合入方式、隔离现场、提交要求和禁止推送边界的完整提示词。用户要求“发给模型是什么，就展示什么”。

## 已核对事实

1. 冲突处理链路为同一次会话首发同时传入 `prompt` 和 `displayText`：前者持久化并提交给模型，后者优先覆盖会话中的可见正文。
2. 代码审查链路也使用相同的摘要覆盖：模型收到完整审查范围和硬性边界，会话只显示一句简短请求。
3. 任务推送没有使用摘要覆盖；它以同一份布局数据生成模型输入，并在会话中按字段和附件结构化展示。
4. 询问回答、权限批准和实施计划等交互使用可读展示文本表达内部协议动作，它们不是专用会话首发提示词。
5. Codex 的排队快照、Provider 用户消息回放和持久历史都会优先读取 `displayText`；Pi 在不同阶段读取字段的方式不同，因此双文本还可能造成同一消息前后变化。

## 已确认决策

### 所有专用会话首发内容完整等价

- 冲突处理、代码审查、任务推送及后续专用会话统一遵守同一规则。
- 会话展示可以改变排版，但实际发给模型的全部文字和附件信息必须完整可见，不能隐藏、增写或用摘要替换。
- 任务推送保留现有字段和附件布局，因为它展示的是同一份内容，不是另一套摘要。

优点：用户能直接审计模型收到的任务边界，专用会话之间的透明度一致。

代价：完整提示词会增加首条消息长度，代码审查和冲突会话的首屏信息密度上升。

### 保留协议回执投影

- 询问回答、权限批准、实施计划等内部控制动作继续显示可读的人类动作文字。
- 协议回执投影只能用于控制载荷，不能用于专用会话首发或普通用户输入。

优点：不向用户暴露内部控制结构，会话仍保持自然可读。

代价：系统必须明确区分用户输入与协议回执，不能仅凭两者都来自用户操作就共用展示规则。

### 在专用会话启动边界禁止摘要覆盖

- 从专用会话启动计划中移除独立的展示正文能力，首发消息只保留真实提示词这一份事实源。
- 冲突处理和代码审查不再传入摘要；任务推送现有结构化布局继续作为同一输入的等价渲染。
- 通用会话内的协议回执机制保持不变。

优点：约束落在公共入口，后续新增专用会话无法再次无意引入两套首发正文。

代价：如果未来确实需要专用展示，只能设计为对同一输入的结构化渲染，不能直接复用一个任意字符串覆盖字段。

## 实施范围

1. 更新领域词汇，区分实际用户输入、可见用户消息和协议回执投影。
2. 更新设计契约，要求所有专用会话首发内容完整等价。
3. 移除专用会话启动计划及 Codex、Pi 分流中的 `displayText` 字段。
4. 删除代码审查和冲突处理入口的摘要覆盖。
5. 核对任务推送结构化展示仍与实际输入同源，协议回执投影不受影响。

## 验证边界

- 执行格式、差异、类型、静态检查和构建验证。
- 使用只读运行探针核对冲突处理与代码审查提示词内容，并核对专用启动链路不再接受独立展示正文。
- 静态检查和构建不等同于真实 Provider 或 Electron 界面验收；没有真实链路证据时单独记录缺口。
- 不执行 Git commit、push、merge 或 revert。

## 实施结果

1. `NativeTaskConversationStartPlan` 不再声明或向 Codex、Pi 转发独立展示正文；专用入口的首发可见正文只能来自实际提示词。
2. Codex 的任务会话首发契约与 Pi 的会话首发契约也删除了独立展示正文字段，直接调用底层协调器同样不能绕过公共入口。
3. 代码审查删除“请审查当前工作区的完整代码变化。”摘要，首条消息改为展示包含任务、唯一仓库、冻结基线、硬性边界、审查范围、审查标准和输出要求的完整提示词。
4. 冲突处理删除“请处理全部冲突并完成……合入来源分支……”摘要，首条消息改为展示实际提交的完整代码交付提示词。
5. 任务推送继续以 `taskPushLayout` 同时生成 Provider 输入和结构化会话内容，没有退回重复纯文本。
6. 普通消息提交、引导消息及询问回答、权限批准、实施计划等协议回执继续保留可读投影能力。
