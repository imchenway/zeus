# ZEUS-0278 补充附件失败与历史会话续接修复

## 任务结论

用户看到的是两个连续故障，不是同一个附件错误反复发生：

1. 0.3.10 界面仍连接 0.2.38 独立执行宿主时，任务首发补充附件的位置键已经写入布局，但对应附件没有进入同一提交的真实附件数组，Provider 组装因此报 `Task push attachment placement is missing`。
2. 0.3.11 已移除独立执行宿主，但内嵌 Local Server 创建 Codex app-server 时漏传 Zeus 专属 `CODEX_HOME`。历史线程实际保存在 `~/.zeus/providers/codex`，Codex 子进程却到默认 `~/.codex` 查找，因此后续纯文字“现在呢？”报 `no rollout found for thread id ...`。

当前修复范围是第二个回归，并保留第一个故障的历史事实。0.3.11 已经让新任务不再进入旧版独立宿主；本次继续恢复既有 Zeus 专属 Codex 线程的续接能力。

## 现场证据

- 正式 `/Applications/Zeus.app` 当前版本为 0.3.11，主进程 PID `40391` 于 2026-08-15 09:18 启动；现场没有 `executionHost.js` 进程。
- 目标会话 `conversation_8bc60f9c395f73cde3782f9b` 绑定线程 `01a000fc-b592-7d52-ae0a-669d51155e2e`。
- 线程文件真实存在于 `~/.zeus/providers/codex/sessions/2026/08/14/...jsonl`，并且 Zeus 专属 `state_5.sqlite` 的 `threads` 表包含相同线程 ID 和相同路径。
- 0.3.11 对“现在呢？”的提交已失败，错误为 `no rollout found for thread id 01a000fc-b592-7d52-ae0a-669d51155e2e`。
- 当前 Codex stdio app-server 使用 Zeus 专属二进制启动，但进程环境没有 `CODEX_HOME`；其拉起的 Remote Control 守护进程来自默认 `~/.codex`，与历史线程实际目录不一致。

## 根因

旧的独立执行宿主由 `connectOrLaunchExecutionHost()` 启动时，会显式注入 `CODEX_HOME=~/.zeus/providers/codex`。0.3.11 把 Local Server 和 Agent 调度移入 Electron 主进程后，启动链只把 `codexHome` 用于选择 Codex 可执行文件，没有继续把它传给 Codex app-server 的进程环境。

“二进制来自哪里”和“运行数据存在哪里”是两个独立条件。只选中 Zeus 专属二进制并不能让 Codex 自动使用 Zeus 专属数据目录。

## 修复设计

- Codex app-server manager 增加由宿主传入的固定运行环境；创建每个 app-server 世代时统一注入。
- 多世代 manager 将同一固定运行环境传给所有新世代，避免配置热启用后再次掉回默认目录。
- 桌面内嵌启动链把 `options.codexHome` 显式映射为 `CODEX_HOME`。
- Local Server 自行创建 manager 的非桌面入口也使用解析后的 `codexHome` 注入，避免同类缺口只在正式桌面入口修复。
- 自定义 Responses Provider 的临时凭据环境仍按原链路叠加；固定 `CODEX_HOME` 不进入数据库、Renderer 或日志。

优点：恢复全部 Zeus 专属历史线程，普通发送、配置热启用和后续 app-server 世代使用一致的数据目录；修复不是针对单个线程改数据库。

缺点：已经启动在错误目录的 Codex 子进程不能原地改变 `CODEX_HOME`，需要随新构建重启；错误提交仍保持失败记录，不自动重发，避免重复发送用户消息。

- `createCodexAppServerManager()` 在每次启动 stdio 或 Remote Control app-server 时注入固定运行环境，并让 Zeus 固定运行身份覆盖自定义 Provider 临时环境中的同名键。
- `createCodexRuntimeGenerationManager()` 把固定运行环境传给每个新世代，配置热启用和多世代排空不会丢失 `CODEX_HOME`。

- `DESIGN.md` 已补充“专属二进制与 `CODEX_HOME` 必须作为同一运行身份”的安全契约。

## 2026-08-15 发送失败提示视觉收口

用户进一步指出“消息发送失败”提示过于厚重。原实现把失败标题、说明、恢复文案和下划线动作纵向堆在一张横跨完整会话列的红色卡片中；在宽窗口下红色面积过大，恢复动作也不够像可操作控件。

本次改为紧凑的会话内错误条：

- 最大宽度收敛到 680px，使用中性表面、细边框和左侧语义色标记，不再整块铺红。
- 标题与具体原因优先同行，恢复说明使用次级文字，减少纵向高度。
- “回到输入框”改为“修改后重发”，并使用 28px 高的紧凑按钮；动作只恢复草稿和焦点，不自动发送。
- 窄窗口下按钮换到正文下方，避免挤压失败原因；键盘焦点继续使用清晰的语义色焦点环。
- 待确认状态沿用相同结构但使用警告色，发送中状态不增加卡片背景。

优点：错误仍清晰可见，但不会盖过用户消息与会话正文；恢复路径更像明确动作。缺点：技术详情继续折叠，用户需要主动展开才能看到底层错误码；紧凑宽度会让极长错误在窄窗口中增加一至两行。
