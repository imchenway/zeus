# ZEUS-0284 菜单栏今日 Token 与近 7 日用量数值差异诊断

## 结论

截图中的两个数字不是同一个统计周期：

- `1636.3 万` 是当天本地时间 `00:00` 到浮窗刷新时的 Zeus 本地 Token；
- `8901.2 万` 是最近 7 个自然日（含当天）的 Zeus 本地 Token 合计，不是最右侧“六”这根柱子的单日值。

两个数字都来自同一份 `codex_usage_ledger` 本地账本，没有混用官方账户日桶。当前问题是图表标题的 7 日合计靠右放置后，视觉位置正好落在最右侧柱子上方，容易被误读为周六单日值。

这组 Zeus 本地数字不能与 Codex 自带的账户用量图直接对账。Codex 自带图读取账户级日桶，Zeus 当前浮窗读取本地账本；进一步排查确认，本地账本不仅范围较窄，还错误地把 Codex 的“最后一次模型调用用量”当成了“整轮累计用量”，因此存在严重少记。

## 代码证据

### 今日 Token

`packages/local-server/src/usageOverviewService.ts` 先按本地当天零点筛出 `todayRows`，再聚合为 `todayLocal`。

菜单栏 `apps/desktop/src/renderer/settings/MenuBarUsageWindow.tsx` 的“今日 Token”直接展示 `provider.todayLocal.totalTokens`。

### 近 7 日合计与柱状图

服务端从本地当天零点向前取 6 天，聚合为 `sevenDayLocal`，并按自然日形成 `dailyLocal`。

菜单栏图表标题右侧展示的是 `provider.sevenDayLocal.totalTokens`；每根柱子只使用对应 `dailyLocal` 日桶控制高度，普通界面没有在柱子上方展示单日数值。

## 与 Codex 官方 8 月 14 日数据的对照

正式数据库同时缓存了 Codex `account/usage/read` 返回的官方账户日桶。8 月 14 日两份原始事实是：

| 数据源 | 8 月 14 日 Token | 覆盖范围 |
| --- | ---: | --- |
| Codex 官方账户日桶 | 207,817,634 | 当前 Codex 账户的官方日用量，界面紧凑显示为 `2.1 亿` |
| Zeus 本地账本 | 4,279,599 | 当天经 Zeus 记录成功的 39 个 Codex 轮次，界面紧凑显示约 `428 万` |

两者相差 `203,538,035` Token，官方值约为 Zeus 界面日桶值的 `48.6` 倍。如此大的差异不能由一位小数的紧凑显示或普通日界线误差解释。用户补充约 90% 的任务都在 Zeus 执行后，继续排查确认覆盖范围不是主要解释，Zeus 本地记账逻辑本身存在少记与日期漂移。

### 根因一：把最后一次模型调用当成整轮用量

Codex 官方源码明确说明：`total_token_usage` 是会话累计总量，`last_token_usage` 是最新活动上下文大小。Zeus 虽然同时解析了 `total` 与 `last`，但 `codexUsageService.recordTurn` 写账本和估价时只使用 `input.last`；同一 Provider 轮次反复收到更新时，存储层又用最终值覆盖原行。

8 月 14 日一个只有一轮的真实 Zeus 会话提供了直接证据：

| 同一轮 Token 事实 | Token |
| --- | ---: |
| Codex JSONL 最终 `total_token_usage` | 1,219,373 |
| Codex JSONL 最终 `last_token_usage` | 111,216 |
| Zeus 账本实际写入 | 111,216 |

这一轮被少记 `1,108,157` Token，约只记入真实累计量的 `9.1%`。长任务内部经历的模型调用越多，偏差越大。

按 Asia/Shanghai 的 8 月 14 日窗口扫描 Zeus 专属 Codex 目录全部 24 个相关 JSONL，对 1,221 个 `token_count` 事件按会话累计量做增量复算，得到 `142,559,384` Token。它约占 Codex 官方 `207,817,634` 的 `68.6%`，也证明“Zeus 当天只有约 428 万 Token”不成立。

### 根因二：恢复回填使用接收时间，导致跨日漂移

8 月 14 日完成的 52 个 Codex 轮次都能在账本找到，但其中 13 个直到 8 月 15 日执行宿主恢复时才重新接收 Token 事件。Zeus 把 `event.receivedAt` 直接写为 `occurred_at`，使这 13 个轮次的 `1,671,566` Token 被错误归入 8 月 15 日。

即使只把这 13 个最终调用值放回 8 月 14 日，旧算法也仅得到约 `595 万`，说明日期漂移是次要误差，主要误差仍是只保存 `last_token_usage`。

### 尚不能逐项归因的剩余差额

Zeus JSONL 增量复算值与官方账户日桶仍相差 `65,258,250` Token。任务数量占比不等于 Token 占比，少量非 Zeus 长任务也可能占较多 Token；此外官方账户日桶和本地时间窗口可能存在边界差异。当前没有账户侧逐线程明细，不能把这部分差额强行分摊到具体客户端。

## 产品判断

现有设计的优点是能在一个区域同时看到 Zeus 当天值、7 日合计和每日趋势；缺点有三层：一是 7 日合计没有紧邻“近 7 日用量”标题，反而靠近最右侧柱子；二是浮窗页签写着 `Codex`、紧凑字段只写“今日 Token”，用户自然会把它当成 Codex 官方账户统计；三是当前本地数值本身严重少记，不能通过补充“Zeus 本地”文案把它包装成可信统计。

如果后续只修文案和布局，无法解决本次问题。优点只是改动小；缺点是会继续展示一个口径写清楚但数值仍错误的本地统计。

如果产品目标是让 `Codex` 页签与 Codex 自带统计一致，应把官方账户日桶作为 Codex 订阅账户的主用量；同时修复本地账本为基于会话累计量差值的增量记账，并使用真实轮次发生时间处理恢复回填。优点是官方账户值可以直接对账、本地值仍能按项目和会话拆分；缺点是需要为累计量基线、重复事件、会话恢复、压缩或计数重置建立明确状态，不能简单把 `total` 字段直接逐轮相加。

## 2026-08-15 修复实施

### 本地逐轮记账

`codex_usage_ledger` 新增 `provider_baseline_json`、`provider_total_json` 和 `usage_complete`：

- 每轮保存 Codex 会话累计量在轮次开始前的基线与当前累计终值；
- 本轮真实用量使用“累计终值减累计基线”，不再保存 `last_token_usage`；
- 同一轮多次 Token 更新复用同一基线，最终覆盖为当前完整轮次用量；
- 下一轮以最近一个不大于当前累计量的线程终值作为基线，避免把历史会话累计量重复相加；
- Provider 只重发相同累计量时差值保持不变，不因限额更新重复计数。

优点：与 Codex 累计语义一致，长任务内每次模型调用都会进入当前轮次用量；按项目、会话、模型、缓存和费用的本地拆分继续可用。

代价：旧账本缺少历史累计终值，无法只靠数据库无损还原。迁移只使用会话最后成功快照为每个线程最新旧记录建立兼容基线，并将旧记录保持为 `usage_complete = 0`，防止升级后把历史欠账一次性冲入当天。

### 恢复跨日

Token 事件写账时优先使用已持久轮次的 `completedAt`，轮次仍在运行时才使用事件接收时间。恢复宿主重放旧 Token 事件时不再把旧轮次改记到恢复当天。

优点：历史重放保持原自然日；代价：极少数跨午夜且 Token 事件先于完成事件到达的活动轮次，会先使用接近完成时刻的接收时间，后续同轮更新再校准。

### 菜单栏数据口径

- 顶部明确显示“今日 Zeus Token”，保留本地实时统计；包含修复前旧记录时显示 `≥` 和“Zeus 本地记录不完整”，不再冒充精确值；
- 本地历史不完整时，缓存命中率和费用显示不可用，不根据残缺数据给出伪精确比例或金额；
- Codex 订阅页的“账户近 7 日用量”改用官方 `dailyUsageBuckets`，8 月 14 日柱子读取 `207,817,634`；
- 每根日柱增加完整日期和紧凑 Token 悬停说明；
- 官方当日日桶尚未生成时保持缺失，不拿 Zeus 本地值回填官方账户值；
- 旧执行宿主兼容分支同步归一化新增字段，缺少完整性证据时按不完整处理。

优点：今天仍能看到 Zeus 实时最低值，历史账户趋势可以直接与 Codex 对账。代价：升级当天的本地值只能表达下限；从修复后的完整自然日开始才恢复精确本地统计。

## 实施验证

- 正式数据库只读副本迁移：657 条旧账本记录完成迁移，为 236 个线程的最新记录建立累计兼容基线，旧记录完整性保持为假；正式数据库未写入。
- 真实单轮累计探针：连续累计 `24,846 → 54,497 → 1,219,373` 后账本保存 `1,219,373`，不再保存最终调用 `111,216`。
- 真实两轮差值探针：下一轮累计终值 `1,500,000` 时只入账 `280,627`，没有重复累计前一轮。
- 官方日桶投影探针：8 月 14 日返回 `207,817,634`；当前日官方桶缺失时返回不可用，本地值不回填。
- `pnpm lint`：通过。
- `pnpm typecheck`：通过。
- `pnpm build`：通过；仅保留既有大 chunk 警告。
- `pnpm package:mac`：生成独立身份 `Zeus Test.app`，Bundle ID 为 `dev.hypha.zeus.test`，`codesign --verify --deep --strict` 通过；测试包为 ad-hoc 签名且未公证，未启动 GUI，未触碰正式 `Zeus.app`。
