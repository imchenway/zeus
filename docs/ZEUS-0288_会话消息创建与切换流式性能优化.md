# ZEUS-0288 会话消息创建与切换流式性能优化

## 用户现场

- 用户消息提交后先出现在底部，Provider 开轮后才跳到新轮次顶部。
- 冲突处理等排队消息会从时间线消失，改在输入区上方的队列中显示，派发后再跳回时间线。
- 思考摘要和回复正文按大块更新，增量到达时反复播放淡入位移，视觉上持续卡顿。
- 冷切换会话时，左侧已经选中目标会话，主区仍保留旧会话正文，直到目标快照就绪才整体替换。

## 根因证据

### 消息位置

- `send_started` 已经用稳定的 `clientUserMessageId` 创建乐观用户消息，但 `ConversationTranscript` 把乐观消息放在所有历史行之后，再主动滚到底部。
- 目标 submission 出现在权威队列后，同一客户端消息会被时间线过滤，正文所有权转给输入区附近的 `QueuedConversationMessages`。
- Provider 开轮后才设置大块 spacer 并再次定位，所以页面必然经历“底部消息、队列消息、新轮次顶部消息”三段位置。

### 流式输出

- Local Server、Renderer 和可见 Markdown 各自存在增量合并窗口；Renderer 原窗口为 `40ms`，可见文本还会等待 `120ms / 180ms`，未闭合结构最长等待 `1200ms`。
- 每次可见文本修订都会取消并重启一次 `140ms` 的透明度和位移动画；增量频率接近动画时长时，动画长期无法自然结束。
- 思考摘要直接替换整段文字，并把活动摘要设为整段实时播报，增量既不平滑，也会制造过多读屏更新。

### 会话切换

- `ZEUS-0224` 的旧实现会在目标无热缓存时同时挂载两个 `ConnectedSessionWorkspace`：旧会话保留完整正文，目标会话只显示输入坞和加载状态。
- 目标快照就绪后才卸载旧工作面，因此用户看到的不是缓存串线，而是与当前预期冲突的既定过渡行为。
- 热缓存本身按项目和会话身份校验，命中时仍可安全直接显示目标正文。

## 本次设计决策

### 用户消息只有一个可见正文身份

- 用户提交后，消息立即进入时间线，并从首帧开始使用稳定 `clientUserMessageId`。
- `queued`、`dispatching`、`active` 和需要保留的暂停状态只更新同一条消息的状态、内容与 Provider 身份，不再卸载并迁移正文节点。
- 队列区保留编辑、删除、排序、引导和恢复能力，但默认折叠为轻量摘要，不再隐藏或替代时间线正文；展开后只显示单行管理摘要与附件数量，不重复渲染完整 Markdown、图片和附件正文，需要用户处理的暂停态自动展开。
- `user_confirmation` 仍属于尚未确认进入会话记录的恢复输入。Controller 必须先把正文和附件合并、持久化到输入框，再撤下时间线投影并删除服务端确认记录；任意实时队列、恢复结果和完整快照都走同一恢复流程。
- 冷加载时缺少 Provider user item 的 `failed`、`completed` 和 `resolved` submission 仍按同一客户端身份收敛；失败保留可见原因，完成或已引导消息不再作为待回复乐观消息。

这项决策以用户当前要求和较新的 `ZEUS-0220`“原消息立即稳定留在时间线”口径为准，覆盖 `ZEUS-0078` 中“排队消息正文只在输入区附近显示”的旧视觉口径；队列操作能力不变。

优点：消息从点击发送到 Provider 接管保持同一视觉身份，排队和冲突准备不会再产生正文跳位；发送状态仍然可见。

代价：时间线会展示模型尚未接收的排队消息，必须持续显示“排队中”等真实状态，不能让用户误解为 Provider 已开始处理。

### 提交首帧完成新轮次定位

- 明确发送时，在绘制前同时生成用户消息和回复空间，不再先滚到底部、再等待 `turn.started` 二次定位。
- 同一消息已经预定位后，Provider 开轮只接管身份和状态，不再次滚动。
- 排队消息在旧轮结束与新轮开始的间隙继续保留回复空间；失败或结果待确认时撤销空白回复空间。

优点：新消息第一帧就落在稳定位置，消除“先底部排队再跳到顶部”。

代价：刚发送后会立即为回复留出可视空间；这是新轮次阅读锚点的一部分，不是历史列表空白。

### 流式内容使用连续节奏

- Renderer 增量合并窗口从 `40ms` 收紧到 `16ms`，使同一帧内的事件仍合并，但不额外积压两帧以上。
- 可见文本空闲刷新、最长等待和批次阈值分别收紧到 `48ms`、`80ms` 和更小字符批次；最长等待会完整刷出安全尾字，不再把最后一个词留到下一次增量；未闭合结构的保护等待收紧到 `700ms`。
- 删除每次文本修订都会重启的 Web Animation，只保留新消息一次性 `160ms` 入场，并使用独立的连续流式进度线表达仍在输出。
- 思考摘要复用同一自适应文本投影并使用 `memo`；读屏只播报状态变化，不逐增量重复整段摘要。

优点：首字更快出现，正文和思考摘要连续增长，动画不再互相取消；同帧合并仍限制 Markdown 重算频率。

代价：Markdown 仍按安全块重新投影，超长历史和超大活动尾部的极端场景后续仍可能需要可见区渲染；本次不引入高风险的动态高度窗口化。

### 会话切换立即切到目标身份

- 删除旧正文保留和目标 `transitionDock` 双工作面。
- 热缓存命中时立即展示目标真实正文并后台校准；未命中时立即展示目标标题、目标输入区和目标专属骨架。
- 冷加载时目标 controller 可以安全接收输入，消息在快照就绪前按目标会话身份排队。
- 不使用 React 延迟身份切换，因为延迟提交会重新保留旧会话画面。

这项决策覆盖 `ZEUS-0224` 中“目标首次读取时保留旧正文”的旧口径；跨项目原子导航、热缓存校验和失败恢复规则继续保留。

优点：选中身份与主区内容从第一帧一致，旧长正文、旧控制器和目标控制器不再同时挂载，降低内存、订阅和绘制开销。

代价：首次打开或缓存淘汰时会短暂看到目标骨架；这是比继续展示旧消息更真实的加载反馈。

## 实施结果

1. `App.tsx` 删除 `conversationSwitchTransition`、旧工作面上下文和双工作面渲染，只返回目标工作面。
2. `SessionWorkspace.tsx` 删除 `transitionDock` 与旧正文专用输入抑制；普通冷会话直接启用目标 controller 的安全延迟发送。
3. `sessionReducer.ts` 从权威 submission 恢复排队、失败和缺失 Provider item 的终态消息；发送接收结果立即绑定 submission 与 Provider turn，queue、steer、`turn.started` 和 `turn.completed` 都按 `clientUserMessageId` 原地同步并收口同一消息。
4. `ConversationTranscript.tsx` 让乐观消息和正式消息共用同一 `turnRows` 管线与 `user-message:<client id>` React 身份；提交首帧建立 spacer，Provider 开轮不重复定位，多条队列回退不会把旧消息误判为新提交。
5. `QueuedConversationMessages.tsx` 改为可访问的折叠管理区，默认只展示数量与真实队列说明，展开也只显示单行管理摘要；队列清空后重置下一周期的默认折叠状态。
6. `ThreadItemView.tsx`、`SessionReasoningSummary.tsx` 和 `session.css` 收紧流式节奏，删除逐增量重启动画，以轮次级稳定 reasoning key 保留摘要节点，继续支持减少动态效果。
7. `useSessionController.ts` 将 Renderer 增量合并窗口收紧到一帧，把发送接收身份立即交给时间线，并把人工确认恢复统一接到实时队列和所有权威快照；`useThreadScrollController.ts` 新增明确提交的首帧定位语义。
