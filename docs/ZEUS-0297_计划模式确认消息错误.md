# ZEUS-0297 计划模式确认消息错误

## 任务目标

修复计划完成后的“实施此计划”确认被当成普通后续消息排队、可被误操作为“引导”，以及同一工作连续要求用户确认三四次的问题。

## 真实现场证据

本次只读检查了 Zeus 当前业务数据库，没有修改、恢复或删除任何生产数据。用户截图对应会话 `任务会话：任务页的看板模式`，现场时间线如下：

1. 05:38:17Z，一条 Plan 轮次完成并生成计划实施请求；此时同一会话已有另一条 Plan 后续消息。
2. 协调器没有等待计划实施请求处理，05:38:18Z 自动启动了下一条 Plan 后续消息。
3. 05:42:40Z，用户点击“是，实施此计划”；因为第二条 Plan 轮次仍在运行，控制动作被创建成普通 queued submission。
4. 05:43:53Z，第二条 Plan 轮次完成并再次生成计划实施请求；此前排队的“实施”提交开始派发。
5. 该“实施”提交创建时是 Default，但派发前读取“下一轮最新设置”后被改写为 Plan，最终又产出计划并在 05:45:20Z 第三次生成实施请求。
6. 05:45:30Z 用户再次确认时，上一条实施轮次仍在运行，确认文案再次进入后续消息列表；这与截图中的“后续消息（1）/ 是，实施此计划 / 引导”完全一致。

现场不是一次请求被前端简单重复点击。数据库中存在多个不同的 `conversation_plan_actions`、对应 submission 和 Provider turn；重复确认由队列放行顺序与控制动作模式被覆盖共同造成。

## 根因

### 计划确认没有成为队列门禁

Plan 轮次完成后，协调器一边创建持久计划实施请求，一边继续执行普通队列排空。只要会话中已经存在后续消息，下一轮就会在用户处理计划确认前启动。用户随后点击确认时，会话已是 active，确认动作只能落入普通后续队列。

### 控制动作错误继承下一轮协作模式

普通排队消息遵循既有产品选择：真正派发前读取会话最新模型、推理强度、服务档位、权限和协作模式。计划实施也是 submission，却没有标记“协作模式由控制动作固定”。因此它在等待期间可能从 Default 被最新 Plan 设置覆盖，再次执行规划而不是实施。

### 界面忙碌态与事件状态缺少保护

计划确认操作的 busy key 使用 `plan-request:`，界面只识别普通请求的 `request:respond:`，按钮在等待本机回执时没有进入禁用状态。计划请求实时事件也允许已解决状态被迟到的 pending 事件回退，增加重复操作窗口。

## 产品规则与取舍

- 待处理计划实施请求是当前会话下一步的决策门禁；在实施、修订或关闭前，普通后续消息不得自动启动。
- “实施”固定使用 Default，“修订”固定使用 Plan；只固定这一个控制动作的协作模式，模型、推理强度、服务档位和权限仍在实际派发前读取会话最新值。
- 用户确认的计划动作排在既有普通后续消息之前。确认后优先完成计划动作，再继续原队列；既有后续消息不删除、不改正文。
- 计划动作因全局并发容量暂时等待时显示为“计划操作”，不再显示普通消息的引导、编辑、删除和重排能力；普通消息不能越过它，服务端也拒绝绕过界面改写或重排控制动作。
- 关闭计划确认后立即恢复普通队列排空。
- 已解决的计划请求状态不可被迟到的 pending 事件回退；提交期间按钮立即禁用。

优点：一次确认只对应一次明确动作；计划结果不会被下一条普通消息抢跑；普通后续消息的最新配置规则保持不变。

代价：计划确认未处理期间，已经排队的普通后续消息会等待用户决策；并发名额确实不可用时，已确认的计划动作仍需要等待容量，但它保持正确的动作顺序和协作模式。

## 实施范围

- Local Server：计划请求成为普通消息提交与队列排空门禁；计划动作提交置于队首且不可作为普通消息操作；实施和修订分别固定协作模式；关闭后恢复排空。
- Renderer：计划请求操作识别正确 busy key；计划请求状态只允许从 pending 前进到终态，不允许终态回退；容量等待中的控制动作显示独立标识并隐藏普通消息操作。
- 设计契约：记录计划控制动作与普通下一轮配置的边界。
- 不新增或恢复单元测试、组件测试、DOM/CSS 契约测试。
- 未经用户明确要求，不执行 Git commit、push、merge 或 revert。
