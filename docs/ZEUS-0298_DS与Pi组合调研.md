# ZEUS-0298：DeepSeek 与 Pi 组合调研

- 调研日期：2026-08-15
- 输入文章：[DeepSeek + Pi 王炸组合跑赢 Claude Code？](https://mp.weixin.qq.com/s/xjjBsGijp7DdrnU_6hp-_w)
- 调研范围：文章论据、DeepSeek 官方缓存机制、Pi 官方能力、第三方缓存扩展，以及 Zeus 当前 DeepSeek/Pi 路由

## 结论

我认同文章指出的方向，不认同标题式结论。

“模型能力”不是最终效果的全部，运行模型的智能体框架会通过系统提示词、工具定义、上下文裁剪、压缩策略和重试逻辑，显著影响成功率、速度和费用。Pi 的轻量上下文确实适合发挥 DeepSeek 的前缀缓存价值，值得 Zeus 继续投入。

但现有材料不足以证明“Pi 普遍跑赢 Claude Code”，也不能证明 Pi 默认安装就能稳定得到 99.9% 以上缓存命中。对 Zeus 来说，正确动作不是把 DeepSeek 官方链路立即切回 Pi，而是保留已经验证的官方 DeepSeek App Server 路线，同时补齐缓存观测，做同模型、同工具、同任务的 App Server/Pi 对照实验，再根据结果决定路由。

## 文章讲对了什么

### 1. 智能体框架会影响模型上限

文章引用的对比说明，同一个 DeepSeek 模型放进不同框架后，任务结果可能明显不同。这个判断在机制上成立：框架发给模型的系统提示词、工具数量和描述、历史消息、压缩摘要、错误反馈都属于模型输入，而不是无关的外壳。

优点：这提醒 Zeus 不能只做“模型接口接通”，还要持续优化模型看到的上下文和工具闭环。

缺点：框架差异、工具差异和提示词差异同时存在时，测试结果不能只归因于 Pi 本身。

### 2. 稳定的长前缀可以显著降低 DeepSeek 输入费用

[DeepSeek 官方文档](https://api-docs.deepseek.com/guides/kv_cache/)确认：上下文缓存默认开启，后续请求如果复用了持久化的输入前缀单元，会在返回用量中得到 `prompt_cache_hit_tokens` 和 `prompt_cache_miss_tokens`。所以系统提示词、工具定义和较早历史越稳定，越容易复用已有缓存。

优点：长会话中反复出现的固定上下文可以少付输入费用，也可能减少首字等待时间。

缺点：官方明确说明缓存是尽力命中，不保证 100%；缓存构建需要时间，也会在数小时到数天后清理。命中率不是永久承诺。

### 3. Pi 的克制设计对缓存友好

[Pi 官方仓库](https://github.com/earendil-works/pi/tree/main/packages/coding-agent)把自身定位为轻量终端编码框架，默认工具较少，扩展能力由使用方选择。较短、较稳定的系统提示词和工具定义，理论上比频繁变化的大型运行时更容易维持缓存前缀。

优点：上下文负担小、供应商接入灵活、容易针对特定模型调整。

缺点：轻量不等于产品能力自动完整。权限审批、审计、宿主恢复、会话一致性和桌面体验仍要由 Zeus 承担。

## 文章还不能证明什么

### 1. 30 道题不能推出“Pi 全面胜过 Claude Code”

文章报告 Pi 完成 20/30、Claude Code 和 Codex 各完成 16/30，但本次调研没有找到 Composio 对应的原始结果页、任务数据和完整复现实验。文章也没有给出多次重复、置信区间、精确版本、统一工具定义、超时策略和失败判定细节。

另外，“Claude Code 使用 DeepSeek”并不是 Claude Code 使用原生 Claude 模型的完整产品体验。模型适配层、工具协议和提示词兼容性都可能改变结果。Prime 还有 6 项未评分，也会影响横向排名。

因此，这组数据可以作为“值得复测”的线索，不能作为 Zeus 改默认路由的决策依据。

### 2. 99.93% 是特定长会话样本，不是 Pi 默认承诺

[相关 X 讨论](https://x.com/badlogicgames/status/2086877202239353285)属于使用者和 Pi 作者的经验陈述，没有公开原始请求序列。接近 10 亿输入 token 的长会话，本身就可能由大量重复前缀构成，因此极高命中率并不意外。

缓存命中率还不等于任务成功率。一个系统可以非常稳定地复用错误或陈旧上下文，同时保持很高的缓存命中。

### 3. 文章混合了 Pi 默认能力和第三方优化

文章同时讨论 Pi、DeepPi、Reasonix 和 `pi-deepseek-cache`，容易让读者误以为所有优化都来自 Pi 默认实现。实际上，[`pi-deepseek-cache` 包页面](https://pi.dev/packages/@rohaquinlop/pi-deepseek-cache)和[源码仓库](https://github.com/rohaquinlop/pi-deepseek-cache)显示，它是第三方扩展，会监听 Pi 事件、改写提示词、接管压缩，并在用户目录写入缓存和统计文件。

源码还显示，它尝试冻结 Pi 系统提示词中的当前日期和工作目录；但当前 Pi 默认系统提示词包含工作目录，没有文章所描述的当前日期字段。至少“冻结日期带来主要提升”这一条，不能直接套用到 Zeus 当前使用的 Pi 版本。

优点：扩展里的前缀诊断、压缩结果复用和命中统计值得借鉴。

缺点：宣传数字主要来自项目自身，缺少独立复现；扩展可执行任意代码并读写用户目录，不适合不经审计直接进入 Zeus。

## Zeus 当前现场

### 路由并不是所有 DeepSeek 都走 Pi

当前代码和 `docs/ZEUS-0256_DeepSeek官方V4模型接入AppServer.md` 已明确：

- DeepSeek 官方 `api.deepseek.com` 的 Flash/Pro 模型走 App Server；
- 其他 OpenAI-compatible 模型连接走 Pi；
- 已建立的 Pi 会话继续走 Pi，不静默迁移运行内核。

官方 DeepSeek 路线已经验证了真实文本、工具和基础重启链路。直接切回 Pi，会丢掉既有验证成果，并重新引入 thread、turn、审批、恢复等产品语义的验证成本。

### Pi 扩展在 Zeus 中默认关闭

`packages/ai-runtime/src/piSdkRuntimeDriver.ts` 当前通过 `DefaultResourceLoader` 关闭 extensions、skills、prompt templates 和 themes，也关闭 Pi 内置工具，只装载经过 Zeus 权限代理的工具。

这是刻意的安全边界。因此，第三方 `pi-deepseek-cache` 不是“安装后即可使用”，强行打开扩展还可能绕过 Zeus 的隔离目录、审批和审计设计。

### 已有缓存字段，但费用和诊断还不完整

`packages/local-server/src/piNativeConversationCoordinator.ts` 已经汇总 `cacheRead`、`cacheWrite` 等用量，界面也有通用缓存命中率能力；但 Pi 动态模型当前把输入、输出、缓存读写单价都设为 0，不能据此准确计算 DeepSeek 实际费用。

这意味着 Zeus 具备缓存观测的基础结构，但还没有形成“供应商原始用量 → 统一账本 → 单轮/会话命中率 → 实际费用”的完整证据链。

## 建议方案

### 建议一：先补齐 DeepSeek 缓存观测，不改默认路由

应统一接收和记录 DeepSeek 返回的命中、未命中 token，按轮次和会话展示：

- 缓存命中率；
- 命中/未命中输入 token；
- 实际输入、输出和缓存费用；
- 压缩前后第一次请求的未命中增量；
- 工具定义或系统提示词变化造成的前缀指纹变化。

优点：先把文章中的宣传数字变成 Zeus 自己可验证的数据，风险小，也能服务 App Server 和 Pi 两条路线。

缺点：需要逐供应商核对用量字段和价格，不能只做一个通用百分比。

### 建议二：吸收思路，做 Zeus 原生缓存稳定层

不加载任意第三方 Pi 扩展，而是在 Zeus 控制的运行时中逐项实现并审计：

- 同一产品版本内保持系统提示词稳定；
- 固定工具定义的排序和序列化；
- 历史消息尽量追加，不在中间改写；
- 对超大工具结果先做有界裁剪，再决定是否压缩；
- 给系统提示词、工具定义和压缩摘要生成前缀指纹，定位缓存失效点；
- 只有在实测证明语义质量不下降后，才启用确定性压缩结果复用。

优点：保留 Zeus 的权限、隔离和审计边界，优化可以按供应商开关和回滚。

缺点：会增加 App Server/Pi 双运行时维护成本；过度追求前缀稳定，可能让旧上下文或错误摘要停留太久。

### 建议三：做同条件 App Server/Pi 对照实验

对同一个 DeepSeek 模型、同一个 endpoint、同一组任务，至少每题重复 3 次。固定版本、权限、工具集合、思考强度、超时和判分规则，分别记录：

- 任务成功率和人工纠正次数；
- 总耗时、首字时间和工具重试次数；
- 输入、输出、缓存命中、缓存未命中 token；
- 实际费用；
- 中断、恢复、长历史和压缩后的正确性。

优点：可以回答“在 Zeus 产品约束下哪条路线更好”，而不是复述别人的框架排名。

缺点：成本和执行时间高；任务集偏向某类代码时，结果仍可能过拟合，必须保留原始运行记录。

## 不建议做的事

- 不因一篇文章把 DeepSeek 官方默认路由从 App Server 全量切到 Pi；
- 不把 99.9% 缓存命中率设为产品目标，产品目标应优先是成功率、费用和可恢复性；
- 不直接开启 Pi 任意第三方扩展加载；
- 不把“成功任务平均费用”当成整体平均费用，失败任务同样会消耗 token；
- 不把本地模型缓存经验直接等同于 DeepSeek 云端缓存行为。

## 推荐的阶段顺序

1. 缓存字段和真实费用归一化；
2. 前缀指纹与失效诊断；
3. App Server/Pi 同条件基线测试；
4. 只落地测试中能同时提升成功率或费用、且不破坏恢复语义的优化；
5. 数据足够后再评估是否按模型能力自动选择运行内核。

## 当前交付边界

调研阶段已完成文章、官方资料、第三方扩展源码和 Zeus 当前实现的判断。随后根据用户确认，进入缓存用量和费用统计补齐阶段。

## 缓存用量与费用统计实现

### 统一统计口径

- 缓存命中 token：供应商或运行内核报告的缓存读取 token；
- 缓存未命中 token：总输入减去缓存命中和单列缓存写入，结果不小于 0；
- 缓存命中率：缓存命中 token 除以总输入 token；
- 费用：按请求发生时的官方公开单价计算，是 Zeus 本地估算，不冒充供应商最终账单；
- 费用覆盖率：有官方费率的 token 占全部可计费 token 的比例，历史未知价格不会被猜测补齐。

优点：Pi 和 App Server 使用同一统计含义，用户可以直接比较命中、未命中和费用。

缺点：供应商账单还可能受赠金、折扣或后续结算规则影响，所以 Zeus 只能给出可追溯估算，不能称为已扣款金额。

### DeepSeek 官方价格快照

价格来源为 [DeepSeek 官方 Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing/)，采集日期为 2026-08-15。实现同时固化了：

- 2026-08-16 16:00 UTC 之前的当前价格；
- 此后 01:00—04:00、06:00—10:00 UTC 的峰时价格；
- 其他时段的谷时价格。

每一轮会把实际采用的费率快照写入账本。后续官方调价只影响新轮次，不回写历史费用。

优点：既不会在峰谷切换后继续使用旧价格，也不会因未来升级改写旧账。

缺点：价格目录仍需随官方调整维护；未列入目录的新模型只记录 token，费用覆盖率为 0。

### App Server 与 Pi 的供应源归并

- App Server 承载的 DeepSeek 外部模型改按 `api:{sourceId}` 入账，不再混入 Codex 订阅账户；
- Pi 保留运行时原始账本身份，但汇总时与同一 `sourceId` 的 App Server 用量归并为一个 API 供应源；
- 数据迁移会把已有外部 App Server 记录从 Codex 统计中拆出，并把历史 Pi 逐轮记录标记为完整；
- 历史费用没有可靠官方连接证据时不倒推，继续由费用覆盖率如实反映缺口。

优点：用户看到的是“DeepSeek 连接花了多少”，不会被内部运行内核拆成两张互相矛盾的账。

缺点：历史没有费率快照的数据无法自动得到费用，只能从新版本开始形成完整价格证据。

### 会话与界面

- Pi 每轮结束后写入统一用量账本和会话累计快照；
- 会话运行详情展示累计缓存命中、缓存未命中、命中率、累计费用和本轮费用；
- 本轮摘要同时展示命中、未命中和输出 token；
- 菜单栏供应源详情展示近 7 日命中 token、未命中 token、命中率和费用；
- Codex 用量详情也补充缓存未命中，避免只显示命中而无法判断分母。

### 未扩大范围

- 没有改变 DeepSeek 官方模型的 App Server 默认路由；
- 没有启用或安装任意 Pi 第三方扩展；
- 没有伪造历史费用；
- 没有执行真实供应商付费调用；
- 没有把静态检查或构建结果写成桌面界面验收。
