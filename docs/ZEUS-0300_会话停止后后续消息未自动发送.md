# ZEUS-0300 会话停止后后续消息未自动发送

## 任务目标

修复会话本轮已经结束后，队首后续消息没有及时自动派发，并且界面展示了不真实等待原因的问题。

## 现状证据

- 目标会话上一轮在 2026-08-15 14:14:35 正常完成；截图中的英文错误来自文件变更恢复快照校验，不代表模型轮次失败。
- 截图对应的后续消息在 14:18:16 进入队列，14:31:29 才被派发，14:31:31 才由模型接收，实际等待约 13 分钟。
- 等待期间后台多次尝试恢复任务工作区，但只有最后一次成功启动下一轮；此前失败原因没有被持久化，事后无法精确审计。
- 当前界面在无法识别具体阻塞原因时统一显示“等待其他会话完成后按顺序自动发送”，该文案不是实际调度证据。
- 目标提交带有 `bypassConcurrency=true`，因此不能把此次等待归因于项目或全局并发名额不足。

## 已确认产品规则

用户已于 2026-08-15 确认以下规则：

1. 本轮结束后，调度器必须立即重新评估并尝试派发队首消息。
2. 如果仍不能派发，系统必须持久化真实阻塞原因，界面展示同一真实原因，不能继续使用无依据的兜底文案。
3. Zeus 不再自行设置项目级和全局会话并发上限；供应商的并发、排队和限流能力由供应商自行处理。

## 方案利弊

- 优点：消除 Zeus 与供应商两套并发规则的冲突，避免本地上限误阻塞供应商本可接收的消息，也让等待原因回到真正执行排队的一侧。
- 缺点：多个会话同时提交时，Zeus 不再主动削峰；供应商可能返回限流、排队或暂时不可用，相关状态必须被准确记录和展示。

## 已确认实施边界

用户已确认只删除跨会话的项目级和全局并发门禁，继续保留单个会话内部“一次只有一个执行轮次”和后续消息先进先出的顺序。供应商拒绝或限流时，Zeus 记录并展示真实原因，不把同一会话的多条普通消息并行提交。

## 实施记录

- 删除 Runtime 设置快照、设置保存接口和设置页中的项目级、全局并发上限。
- 删除 Codex 原生协调器及旧 Runtime 启动、续接链路中的跨会话并发判断；历史 submission 中的 `bypassConcurrency` 只作为旧数据存在，新实现不再读取或写入。
- 保留单会话活动轮次判断、计划确认门禁、执行现场准备、审批与用户选择等真实发送条件。
- 队列快照新增 `waitReason`，由持久执行轮次、submission、计划请求和执行现场状态生成；界面不再使用“等待其他会话完成”的兜底文案。
- 代际协调或队列派发出现异常时，把 submission 改为需要恢复并保存原始错误，同时发布队列变化；不再静默返回无法解释的 `queued`。
- 正常轮次结束后立即排空本会话队首；计划轮次生成确认请求时同步刷新队列等待原因。
