# ZEUS-0309 上下文用量显示错误

## 一、缺陷现象

用户使用 Claude 模型（apikey 供应源，`claude-fable-5` / `claude-opus-5`）时，输入框旁的上下文占用圆环提示：

- 占用：**189.2%**
- 已用 / 容量：**1,892,160 / 1,000,000 Token**
- 剩余：0 Token
- 风险提示：上下文接近上限

用户同时指出：上下文大小按惯例应以 K / M 为单位展示，而不是逐位显示的完整数字。

## 二、根因定位（有真实数据佐证）

### 2.1 分子口径错误：把"整轮累计消耗"当成了"当前上下文规模"

`apps/desktop/src/renderer/session/ContextUsageIndicator.tsx:15-16` 的取数逻辑：

```ts
const used = props.unifiedUsage ? (props.unifiedUsage.latestModelRequest?.inputTokens ?? null) : (props.usage?.last.inputTokens ?? null);
const capacity = props.unifiedUsage ? (props.unifiedUsage.latestModelRequest?.contextWindow ?? null) : (props.usage?.modelContextWindow ?? null);
```

后半段的回退分支使用 `usage.last.inputTokens`。而 `usage.last` 在 Pi 运行路径上的真实语义是
**"一个产品轮次内所有模型请求用量的累加值"**，不是"最后一次请求的上下文大小"：

`packages/local-server/src/piNativeConversationCoordinator.ts` 中，每次 `message_end` 都执行
`addUsage(run.usage, requestUsage)`，轮次结束时把累加结果作为 `last` 写入快照
（`buildPiUsageSnapshot` 的 `last: input.last`）。

因此一轮里工具循环次数越多，这个"已用"数字越大，可以无上限地超过上下文窗口。这解释了 189.2% 与"剩余 0 Token"。

### 2.2 本机数据库实测比对

对本机 `~/.zeus/data/zeus.db` 的实际读取（只读）结果：

`conversations.provider_token_usage_json`（错误口径的来源）：

| 会话 | 模型 | last.inputTokens | modelContextWindow | 按错误口径算出的占用 |
| --- | --- | --- | --- | --- |
| conversation_a09eed85… | claude-opus-5 | 1,849,987 | 1,000,000 | 185.0% |
| conversation_3d6d6e62… | claude-fable-5 | 286,870 | 1,000,000 | 28.7% |

同一会话 `conversation_model_requests`（真实的逐次请求记录，共 68 条）最后一条：

| 模型 | context_window | input_tokens | total_tokens |
| --- | --- | --- | --- |
| claude-opus-5 | 1,000,000 | 104,654 | 105,262 |

**正确占用应为约 10.5%，UI 却显示 185%～189%，偏差约 18 倍。**

另外，全库 `conversation_model_requests` 中最大的单次 `input_tokens` 只有 244,412，
不存在任何一次真实请求达到 1,892,160。这从数据上排除了"供应商上报异常"或"上下文窗口配错"的可能，
坐实问题出在渲染端的取数口径。

### 2.3 上下文窗口值本身不是这次的根因

`claude-fable-5`、`claude-opus-5` 等模型在模型连接配置里的 `contextWindow` 均为 1,000,000
（来源是模型连接配置，不是运行时推断）。这个值是否符合供应商真实能力是另一个独立问题，
但即使它完全正确，2.1 的分子错误依然会让占用显示失真。

### 2.4 同一错误口径在运行详情面板里也存在

`apps/desktop/src/renderer/session/SessionWorkspace.tsx:3128` 附近的旧分支同样用
`usage.last.inputTokens / usage.modelContextWindow` 计算"上下文占用"这一行，问题一致。

### 2.5 单位展示问题

`ContextUsageIndicator.tsx` 的 `formatExactTokens` 只做千分位分组，输出
`1,892,160 / 1,000,000 Token`。项目里 `SessionWorkspace.tsx:1242` 已有现成的
`formatTokenCount()`，可同时给出 `compact`（1.89M / 1M）与 `exact`（精确值）两种形态，
但上下文圆环的提示气泡没有复用它。

## 三、正确口径参考（Pi 官方实现）

Pi 运行内核自身的上下文占用算法（`@earendil-works/pi-coding-agent`）：

- `calculateContextTokens(usage)` = `usage.totalTokens || input + output + cacheRead + cacheWrite`
- `getContextUsage()` 用**最后一条有效 assistant 消息**的用量，而不是整轮累加
- 压缩阈值判断也基于同一口径

即：上下文规模 = 最后一次真实请求的 prompt 部分（input + 缓存读 + 缓存写），
若要贴近 Pi 口径还需加上该次的 output（因为它会成为下一次请求的输入）。
Zeus 现有的 `latestModelRequest.inputTokens` 与 `latestModelRequest.totalTokens`
正好对应这两种口径，数据已经完整落库，无需新增采集。

## 四、已实施的修复

用户已确认采用**口径 B**（`latestModelRequest.totalTokens`，即提示词 + 本次输出），
理由是它与 Pi 运行内核的自动压缩阈值判断完全一致，能更早预警压缩时机。

### 4.1 服务端：修正 `last` 字段被污染的语义

`packages/local-server/src/piNativeConversationCoordinator.ts`

- `PiRunContext` 新增 `lastRequestUsage` 字段，在每次 `message_end` 记录该次请求的用量；
- 轮次结束时 `buildPiUsageSnapshot` 的 `last` 改用 `run.lastRequestUsage ?? run.usage`，
  与 Codex 路径下"`last` = 最后一次请求"的既定语义对齐；
- 用量账本（`usageLedger.upsert`）继续使用 `run.usage` 整轮累加值，计费口径不受影响。

这一步是根本修复：只要 `last` 还携带整轮累加值，任何消费该字段的界面都会重现失真。

### 4.2 渲染端：上下文占用只认真实请求

`apps/desktop/src/renderer/session/ContextUsageIndicator.tsx`

- 移除 `usage` 属性与 `usage.last` 回退分支，分子只来自 `latestModelRequest.totalTokens`，
  分母只来自 `latestModelRequest.contextWindow`；
- 拿不到真实请求记录时显示"完成首轮后显示上下文占用"，不再用轮次累计值冒充。

### 4.3 渲染端：单位改为 K / M

- 新增 `apps/desktop/src/renderer/session/tokenUsageFormat.ts`，
  从 `SessionWorkspace.tsx` 抽出 `formatTokenCount()` 供两处共用；
- 气泡里"已用 / 容量 / 剩余"改用 `compact` 形态（如 `105K / 1M Token`），
  精确值保留在无障碍标签与 `title` 悬停提示中。

### 4.4 渲染端：统一运行详情面板

`apps/desktop/src/renderer/session/SessionWorkspace.tsx`

- 统一使用与圆环相同的 `totalTokens` 口径与 K/M 单位，消除同一概念两套算法。

### 4.5 修复效果推演（基于本机真实数据）

以 `conversation_a09eed85…`（claude-opus-5）为例：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 分子 | 1,849,987（整轮累加） | 105,262（最后一次请求 totalTokens） |
| 显示 | 185.0% · 1,849,987 / 1,000,000 | **10.5% · 105K / 1M Token** |
