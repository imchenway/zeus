# ZEUS-0319 会话切换模型后回退与续发失败

## 结论

本次现场不是一个故障，而是三条链路连续失效：

1. DeepSeek 官方 Responses 模型被送入已启用的 Codex Remote Control 宿主。Zeus 在本地能够读到连接密钥并完成路由，但长期运行的 Remote Control 守护进程没有获得连接专属环境变量，最终三轮都由模型运行时以 `Missing environment variable` 拒绝。
2. 用户随后明确选择的 `apikey / Claude Sonnet 5` 已通过 Pi SDK 成功执行并回复；这不是用户记忆偏差，也不是另一个同名的 `1xm / Claude Sonnet 5`。回复结束后，输入框没有忠实保留该复合模型身份，而是在模型目录对该身份解析失败时静默回退到首选或首个可用模型，现场回退成了 `DeepSeek V4 Pro`。
3. 下一条消息因此尝试从当前 Pi 分段切到 Codex 分段。Codex 协调器虽然允许“需要新分段”的产品会话进入提交准备，却在后续再次强制要求产品会话当前已经是 Codex，导致新分段尚未接受就报 `Codex native conversation was not found.`。

因此，用户看到的现象是确定存在的产品缺陷：成功使用 Claude 后，下一轮被界面改回 DeepSeek；该轮随后又在 Pi 到 Codex 的跨运行分段切换阶段失败。

### DeepSeek 为什么明明配置了连接仍报缺少 Key

- `resolveResponsesRuntime` 会从 Keychain 读取连接密钥；如果没有密钥，会在进入 Codex 前直接抛出 `ZEUS_CODEX_PROVIDER_CREDENTIAL_UNAVAILABLE`。现场没有出现该错误，且冻结配置和运行时确认都已经完成。
- 实际错误中的环境变量哈希与所选 DeepSeek 连接完全对应，说明模型供应源身份没有串错。
- 正式设置中 `codex.remote_control.enabled = true`。Remote Control 适配层只把环境变量传给 `codex remote-control start`，再连接已存在的守护进程；如果守护进程早已运行，新的启动命令不能更新其进程环境。
- App Server 管理器只校验 Zeus 自己内存里的环境映射，所以本地预检通过；真正执行请求的旧 Remote Control 宿主仍然缺少变量，直到模型调用时才失败。

这也是为什么“重新发送”以及从 Pro 换到 Flash 都无效：两个模型复用同一个连接和同一个旧宿主。

### 为什么输入框会自动回退到 DeepSeek

输入框同时维护三份相近但不同的事实：本地 `localStorage` 的逐会话设置、服务端 `nextTurnSettings`、当前运行分段的模型。Pi 成功接纳路径已经把连接与模型的完整复合身份写回下一轮设置，因此不能把本次问题归因成 Pi 固定写入裸模型名。当前实现中真正确定存在的问题是：

- `resolveComposerModel` 找不到已选模型时，会静默选择 `preferredModel` 或第一个可用模型；
- `presentModelOptions` 再次找不到选择时，也会静默选择第一个可用模型；
- 发送时使用的是这个“展示层有效模型”，并会把它冻结为真实提交路由。

本机 LevelDB 能确认该会话曾写入完整的 Claude 连接与模型复合身份；09:43 的正式提交却被写成 DeepSeek。现有记录没有保留当时那一帧模型能力目录，无法继续断言 Claude 条目为何在刷新时没有被解析；但“解析失败后静默换模型，并把换后的展示值用于真实发送”是源码确定存在的错误行为。也就是说，会话绑定的选择未必先被持久化覆盖，展示层已经可以绕过它，并在用户下一次发送时把回退结果变成真实路由。

### 为什么出现 `Codex native conversation was not found.`

产品会话在新运行分段首轮被 Provider 接受前，应继续保留旧的 Pi / Claude 当前分段，这是既有架构约束。Codex 协调器的 `submitMessage` 起点已经为 `requiresNewSegment` 放宽了检查，但随后又执行：

- `requireConversation(conversation.id)`；
- `ensureConversationExecutionContext` 内再次执行 `requireConversation(conversationId)`。

而 `requireConversation` 强制要求顶层产品会话的 `agentKind === 'codex'`。此时新 Codex 分段尚未被接受，顶层身份理应仍是 `pi`，于是形成循环依赖：只有接受后才能升格为 Codex，但协调器要求先升格才能发出首轮。

这直接违背 ZEUS-0311 已确认的“同一产品会话可在 Codex 与 Pi 之间继续，不再以 `agentKind` 拒绝发送”，也违背 ADR 0014 的候选分段接纳边界。空闲时应立即按下一条 submission 的模型切换；活动轮次期间的新消息应依序排队并冻结各自路由，但不能因为运行内核不同而要求创建新产品会话。

## 实施方案与取舍

### 已实施方案

1. 保留 Remote Control 总开关。外部 Responses 供应源会强制进入本地隔离的 App Server 世代，并按线程保存的供应源与环境恢复；回到官方 Codex 时再恢复用户选择的 Remote Control 宿主。既有正在执行的轮次仍固定在原宿主，不被中途迁移。
2. 会话下一轮设置保存连接与模型的复合身份。服务端快照是权威值；浏览器本地设置只在用户修改尚未确认时作乐观显示，不再于页面重挂载时反向覆盖服务端。
3. 当权威模型暂时不在能力目录中时，选择器显示“当前选择不可用”并禁止发送，但仍允许用户打开下拉框主动选择其他模型。展示层不再用首选模型或第一个可用模型代替真实选择。
4. Codex 协调器拆分了“产品会话存在”与“当前已是 Codex 分段”两类校验。Pi 到 Codex 的新分段可以先完成上下文准备和 Provider 接受，接受后再提升当前分段；同运行时续发、恢复和归档路径仍保持严格的 Codex 身份校验。
5. 携带执行快照的忙碌期跨模型消息仍由统一队列派发，Codex 内部旧队列会跳过这类提交，避免漏发或重复派发。

### 优缺点

- 优点：不会再悄悄替用户换模型；无需关闭全局 Remote Control；Remote Control 与自定义供应源的凭据边界明确；Pi 和 Codex 能按既有产品会话语义正常续接；错误可直接指导恢复。
- 缺点：自定义 Responses 模型暂时不能获得 Remote Control 的远程宿主收益；同一进程需要持有远程与本地两类 App Server 世代；模型被删除或禁用后必须由用户重新选择；协调器需要梳理所有默认假设“当前会话就是 Codex”的帮助函数，修改面比单点绕过稍大。

不采用“在报错处补环境变量”或“全面删除 `agentKind` 检查”。前者无法修改已经运行的守护进程环境，后者会让归档、恢复和普通 Codex 续接失去运行宿主边界。

## 当前恢复方式

- 当前成功运行分段和历史仍是 `apikey / Claude Sonnet 5`，无需修复 Provider 会话或重建历史。
- 本次没有修改正式会话数据，因此现场会话的服务端“下一轮设置”仍可能保留 DeepSeek V4 Pro。使用修复后的应用时，用户可以在该会话中主动选回 `apikey / Claude Sonnet 5`，该复合身份会作为会话下一轮权威设置保存。
- 不应把关闭 Codex Remote Control 作为正常使用 DeepSeek 的前提。关闭只是一种会牺牲其他 Codex 会话远程接管能力的应急绕行，本次没有替用户执行，也不把它列为推荐产品方案。
