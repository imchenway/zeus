# ZEUS-0321 会话工具活动分组与进行中思考摘要收敛

## 任务目标

收敛长轮次会话中的过程噪音：工具活动按 Codex 客户端语义分组，类似 `Planning protocolFamily integration` 的思考摘要只表达当前状态，不作为历史正文逐条留在会话记录中。

## 现状与根因

- Zeus 只按“是否连续、是否同一轮”归并活动，把命令、MCP、网页、图片和文件变更全部混入同一数量摘要，容易出现“运行命令并使用工具”但无法判断边界的混合组。
- 每条 reasoning item 都生成一行思考摘要。长任务在“摘要—命令—摘要—工具”之间多次切换后，活动轮次会形成很长的状态瀑布。
- 完成轮次虽然默认收进“查看处理过程”，展开后仍会看到全部阶段性思考摘要；这把短暂状态误当成了会话历史正文。

## 调研结论

- OpenAI App Server 协议把 reasoning、command execution、MCP、网页搜索、图片和文件变更作为独立事件提供，不规定界面必须把它们画成同一组。
- OpenAI 当前公开 Codex 客户端使用可变活动单元归并命令：连续成功的智能体命令可以合并；读取、列目录和搜索形成探索组；失败、用户命令、统一执行交互、其他可见活动或达到 32 条时截断命令组。核对源码为 `openai/codex` 的 `codex-rs/tui/src/exec_cell/model.rs`、`chatwidget/command_lifecycle.rs` 与 `chatwidget/streaming.rs`，调研快照提交为 `1f41cc5d92722748e45cae9cecc6d883a4e7cbb1`。
- MCP、网页搜索、图片等非命令活动有各自的开始和完成生命周期，不进入命令活动单元。
- reasoning 摘要是独立可见内容时会截断命令组，但“一个思考摘要固定对应一个工具组”不是协议契约。
- Zeus 产品侧采用更克制的摘要口径：活动轮次只显示最新思考摘要；最终回答开始或轮次成为历史后不再显示阶段性摘要。原始 reasoning item 继续持久化，用于审计、跨运行内核上下文和故障恢复。

## 实现口径

1. 命令活动只和命令活动分组，同一组最多 32 条。
2. 连续完成的智能体命令可以合并；仍有命令运行时，只有读取、列目录和搜索类探索命令可以继续加入同组。
3. 失败命令在当前组中收口并立即截断；用户 Shell 和统一执行交互不参加后续合并。
4. MCP、网页、图片、文件变更和其他工具活动各自形成独立组，不再和命令混合计数。
5. reasoning 事件继续作为活动分组边界，但只投影活动轮次最新一条；最终回答开始、轮次完成或切换到历史后均不显示旧摘要。
6. 进行中与展开后的历史过程共用紧凑行距：容器行间距从 `14px` 收至 `6px`，保留原有字号、行高和最小点击高度。

## 方案取舍

采用方案的优点：命令计数与工具生命周期不再混淆；长任务只保留当前思考状态，纵向噪音显著降低；底层事件没有丢失，后续上下文和审计语义保持不变。

行距收紧的优点：活动标题与摘要更像同一组连续记录，同一视口能看到更多有效信息；同时不牺牲可点击面积。代价是过程行之间的分隔感略弱，因此保留 `6px` 而没有压到零间距。

采用方案的代价：用户不能再从主会话逐条回看模型每个阶段的可读思考摘要；非命令工具不会为了减少行数被强行合并，工具非常密集的任务仍可能有多条活动记录。

未采用“整轮所有工具合成一个组”：行数最少，但会跨 reasoning 阶段、失败边界和不同工具生命周期合并，摘要看似简洁却失去真实执行顺序。

未采用“每条 reasoning 固定拥有一个工具组”：结构直观，但协议没有这种父子关系，并行命令和跨事件完成时序会让归属不可靠。

## 实施与验证结果

- `ConversationTranscript` 在一次记忆化投影中同时处理命令分组、非命令工具分组和当前 reasoning 选择，没有新增同步状态、效果订阅或持久化字段。
- 一次性投影探针构造“旧摘要、两条成功搜索命令、当前摘要、一个 MCP 工具”的有序现场。活动态输出为 `command-1,command-2` 同组、`current-reasoning` 单条、`mcp-1` 独立组；历史态只保留命令组与 MCP，reasoning 数量为 0。
- 过程行距收紧后，`pnpm exec prettier --check`、`git diff --check`、`pnpm lint`、`pnpm typecheck`、`pnpm build` 均通过；构建只保留既有大分块体积提示。
