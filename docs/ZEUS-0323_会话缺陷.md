# ZEUS-0323 会话缺陷

## 任务目标

- 会话中的资源按真实类型展示：图片显示缩略图，非图片文件显示可读的文件卡。
- 同一轮次的处理过程固定位于开场用户消息之后、最终回答之前。

## 正式现场只读证据

本轮只读检查正式 `/Users/david/.zeus/data/zeus.db`，没有回答会话、停止任务、修改数据库或重启正式应用。

- 截图对应 ZEUS-0320 的首轮会话。
- 卡片资源的真实文件名后缀为 `.jsonl`，MIME 为 `application/octet-stream`，资源投影为 `previewKind=none` 与 `iconKind=json`。它不是图片，不应进入图片预览。
- 用户消息内的文件卡受图片缩略图紧凑列宽影响，文件名和类型被挤到几个字符，造成“像图片但无法预览”的误解。
- 该轮部分 reasoning 条目的起始时间早于 `userMessage` 落库时间。`projectTranscriptTurnRows` 当前把处理过程放在第一条过程记录的位置，因此“查看处理过程”出现在开场用户消息之前。

## 实施口径

1. 完成轮次和活动轮次共用同一条时间线规则：存在开场用户消息时，处理过程紧跟其后；缺少用户消息的恢复或异常轮次才回退到第一条过程记录的位置。
2. 中途用户引导继续属于处理过程，不冒充新轮次的开场用户消息。
3. 资源卡根据当前资源集合标注图片或文件布局；图片继续使用紧凑缩略图，包含非图片卡时保留足够的文件名和“打开方式”空间。
4. 不改动 Provider、资源授权、预览接口、持久化顺序或原始过程数据。

## 方案取舍

优点：资源类型与真实文件一致，不会把 JSONL 伪装成图片；处理过程不再受 Provider 事件落库先后影响，阅读顺序稳定。

代价：非图片文件卡会比图片缩略图占用更多水平空间；恢复出的异常轮次若确实没有用户消息，处理过程仍只能按自身第一条可见记录定位。

## 验证结果

- 会话 QA 页构造了原始条目顺序为“过程 → 用户消息 → 最终回答”的完成轮次；干净启动页面后的实际 DOM 顺序为“用户消息 → 查看处理过程 → 最终回答”。展开入口后，过程摘要仍位于用户消息和最终回答之间。
- 同页使用 JSONL 与图片混合资源验证真实类型分支：JSONL 保持文件卡、完整文件名及“打开方式”无障碍名称，图片保持“在 Zeus 中预览”入口。内置浏览器本轮返回了异常视口尺寸，懒加载图片停留在“正在加载图片”，因此不把该页面验证夸大为图片像素或桌面 GUI 验收。
- 目标文件 Prettier、`git diff --check`、`pnpm lint`、`pnpm typecheck`、`pnpm build` 均通过；构建仅保留既有的大分块提示。
