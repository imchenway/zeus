# ZEUS-0331 上下文参数缺陷

## 一、任务对象与结论先行

本任务分析“上下文用量显示错误”这则对话的 **1M 上下文参数**：

- 对话 ID：`conversation_a09eed85754bee46f4d0c78e`
- 标题：`上下文用量显示错误`
- 运行内核：`pi`
- 模型来源：`model_connection_c8d74855a9094a2c85ac17a79672e327`（连接名 `apikey`）
- 模型：`claude-opus-5`
- 模型连接配置里的 `contextWindow`：`1,000,000`

结论：这则对话里反复出现的 `contextWindow = 1,000,000` 不是运行内核测出来的事实，而是
**模型连接配置里一个既不可见、也不可编辑、且未被供应商能力证据核验的遗留参数**。它被下游
当作权威值直接参与上下文占用显示、Pi 压缩阈值和便携上下文预算，形成“上下文参数缺陷”。

本机数据库只读核对 `conversation_model_requests`：

| 模型 | 请求数 | context_window | 最大 input_tokens | 最大 total_tokens |
| --- | --- | --- | --- | --- |
| claude-opus-5 | 132 | 1,000,000 | 177,568 | 178,537 |
| claude-fable-5 | 65 | 1,000,000 | 83,225 | 83,668 |
| claude-sonnet-5 | 50 | 1,000,000 | 31,467 | - |

`conversation_a09eed85754bee46f4d0c78e` 最新一次请求为 seq 140：

- `input_tokens = 177,568`
- `output_tokens = 969`
- `total_tokens = 178,537`

该会话的 `provider_token_usage_json` 也记录 `modelContextWindow = 1,000,000`。

要点：历史观测到的最大输入只有约 17.8 万 Token，**远低于 1M**，因此单靠历史用量无法反证
`1,000,000` 正确；这个值只能是配置输入，不是供应商真实能力验证结果。

## 三、1M 参数的来源与流向

### 3.1 存储位置

模型连接配置存在 SQLite `settings` 表，键为 `models.connections`：

- `packages/local-server/src/modelConnectionService.ts:60` 定义键
- `packages/local-server/src/modelConnectionService.ts:68` 读取并规范化
- `packages/local-server/src/modelConnectionService.ts:96` 保存时调用 `normalizeModelConnection`

本机 `models.connections` 中，`claude-opus-5` / `claude-fable-5` / `claude-sonnet-5` 均为
`contextWindow: 1,000,000`、`maxTokens: 128,000`。

其它模型也存在“1M 附近”但互不相同的值：

| 模型 | contextWindow |
| --- | --- |
| deepseek-v4-flash / pro | 1,000,000 |
| gpt-5.6-sol / terra / luna | 1,050,000 |
| gpt-5.5 | 1,050,000 |
| glm-5.2 | 1,000,000 |
| kimi-k3 | 1,048,576 |
| claude-haiku-4-5 | 200,000 |

同一种“1M 上下文”出现 `1,000,000`、`1,048,576`、`1,050,000` 三种写法，说明不是单一权威目录
产出的规范值。

### 3.2 参数如何进入请求记录

Pi 运行内核每个 `message_end` 都从连接配置现读该模型的 `contextWindow`：

- `packages/local-server/src/piNativeConversationCoordinator.ts:731` 取
  `connection.models.find(...).contextWindow` 写入 `observeModelRequest` 的 `contextWindow`
- `packages/local-server/src/piNativeConversationCoordinator.ts:873` 写入
  `buildPiUsageSnapshot` 的 `modelContextWindow`

因此本对话 132 条记录的 `context_window = 1,000,000` 全部来自 `models.connections` 里的该参数。

### 3.3 参数被哪些下游消费

- 圆环容量分母：`apps/desktop/src/renderer/session/ContextUsageIndicator.tsx:19`
  `latestRequest.contextWindow`
- 会话详情同口径：`apps/desktop/src/renderer/session/SessionWorkspace.tsx:3104`
- Pi 压缩阈值：`packages/ai-runtime/src/piSdkRuntimeDriver.ts:145` 起，用
  `contextWindow` 计算 `reserveTokens` / `keepRecentTokens`
- 便携上下文预算：`packages/local-server/src/conversationPortableContext.ts:135` 起，用
  `target.contextWindow` 计算预算

## 四、缺陷定位

### 4.1 当前界面不再暴露“上下文窗口 / 最大输出”

模型编辑组件只允许改启用状态、请求协议、认证方式，不能看也不能改 `contextWindow`、`maxTokens`：

- `apps/desktop/src/renderer/settings/ModelConnectionsSettingsPane.tsx:440` 起的
  `ModelDefinitionEditor` 只有 `enabled`、`protocolFamily`、`authenticationScheme`
- 手动新增模型时固定写死默认值：`apps/desktop/src/renderer/settings/ModelConnectionsSettingsPane.tsx:563`
  `contextWindow: 128_000`、`:564` `maxTokens: 8_192`

结果：`1,000,000` 是旧版或手工遗留值，当前界面既看不到，也无从修正。

### 4.2 “不允许目录覆盖”与“用户无法确认”形成闭环

能力档案应用逻辑明确不覆盖 `contextWindow`：

- `packages/ai-runtime/src/modelConnectionCatalog.ts:431` 注释
  “连接中持久化的窗口与输出限制属于该路由的执行配置；内置目录只补全能力证据，不能静默覆盖用户已经确认的限制”

但界面并没有让用户“确认”这个限制。于是参数处于“系统不覆盖、用户不确认、运行照常相信”的空档。

### 4.3 1M 不是唯一口径

本机请求记录里，同样配置成 1M 的 DeepSeek / GPT 模型实际落库不是 1M：

| model_id | 请求记录 context_window | 连接配置 contextWindow |
| --- | --- | --- |
| gpt-5.6-sol | 258,400 | 1,050,000 |
| deepseek-v4-pro | 258,400 | 1,000,000 |
| claude-opus-5 | 1,000,000 | 1,000,000 |

说明“上下文窗口”目前存在至少两套来源，Claude 路径直接相信连接配置，其它路径落库值又不一致。

### 4.4 错误参数会真实影响行为

- `contextWindow` 被 `piSdkRuntimeDriver.ts:145-147` 用来推压缩阈值：以 1M 计算时
  `reserveTokens = 16,384`、`keepRecentTokens = 20,000`，触发阈值约 98.4 万。
- 若该模型真实窗口远小于 1M，系统会到很晚才压缩，可能出现供应商超限、截断或拒收。
- 圆环分母同样用 1M，百分比读数会整体偏小。

## 五、本对话的具体风险（需供应商事实核验）

同连接的 `claude-haiku-4-5 = 200,000`、另一连接的 `claude-sonnet-4-5 = 200,000`，而
`claude-opus-5` 被配成 `1,000,000`，两者口径相差明显。

如果 `claude-opus-5` 真实窗口不是 1M 而是更小（例如 200K）：

- 最新 `total_tokens = 178,537` 约占 200K 的 89%，本应接近压缩/预警；
- 按 1M 口径只显示约 17.9%，会延误压缩。

这只是基于配置不一致提出的假设，**不能凭代码推断出正确值**；正确值需要供应商文档或真实
能力探针确认。

## 六、建议方向（各有利弊）

- **方案 A：恢复参数可编辑并展示建议值。** 在模型编辑页恢复“上下文窗口 / 最大输出”输入，
  内置目录只提供建议值、不覆盖已保存值。优点：用户能核对修正；缺点：依赖用户知道真实值。
- **方案 B：给 contextWindow 增加证据状态。** 区分 `catalog / probe / manual / unverified`，
  未验证时用保守回退窗口做压缩阈值，并把“展示容量”与“压缩阈值”分开。优点：不再盲信 1M；
  缺点：改动面较大。
- **方案 C：先做供应商只读核验，再最小修正持久化数据。** 确认 Claude 三模型真实上下文窗口后
  一次性更新 `models.connections`。优点：改动最小；缺点：需要外部事实源，且要避免误改其它
  正确的 1M 配置。

## 八、多模型参数管理方案（设计讨论）

### 8.1 核心原则：参数必须带“来源 + 可信状态”

当前 `capability` 已经有 `{ source, state, checkedAt, reason }` 的证据模型，只覆盖推理、工具、
图片、流式、用量；`contextWindow` / `maxTokens` 却是裸数字，所以才会出现无人可核对的 1M。

应把 `contextWindow` / `maxTokens` 也纳入同一套证据模型，任何展示给运行内核的数字都有三态：

- `catalog`：内置目录给出的建议值；
- `probe`：真实运行/供应商上报校准后的值；
- `manual`：用户手动覆盖的值（必须显示“手动覆盖”，优先级最高但要有据可查）。

### 8.2 四层模型

- **身份层**：规范化模型 ID → 显示名、协议族、推理档位、输入模态等稳定属性。
- **路由层**：连接 = baseUrl + 协议 + 认证 + 密钥槽；模型只绑定到连接，不改全局身份。
- **执行参数层**：`contextWindow` / `maxTokens` 的“有效值”，由目录建议 + 连接级覆盖 + 探测修正合成。
- **观测事实层**：`conversation_model_requests` 中供应商实际回传的 `context_window`、Token、缓存命中，
  用于把参数状态推进到“已验证”或标记“过期”。

### 8.3 关键边界：同名模型不等于同能力

`claude-opus-5` 同时出现在 `apikey.fun` 和 `1xm.ai` 两个连接，当前配置一个是 1M，另一个也写 1M，
但两个供应商的真实窗口可能不同。因此不能只按模型 ID 做全局注册表，必须允许“连接级覆盖”，
共享目录只给基准值，连接内的差异显式记录，避免同名模型被错误统一。

### 8.4 多模型管理能力建议

- 统一模型目录/注册表，连接只存“路由 + 覆盖”，减少同一模型多份发散配置。
- 模型编辑页恢复“上下文窗口/最大输出”可编辑，并展示来源徽标（目录/探测/手动/未验证）。
- 供应商上报的 `context_window` 回流校准，连续真实请求超过配置窗口时自动标记为“参数可疑”。
- 批量管理：按供应商分组、批量启用/停用、一键刷新能力与健康状态。
- 未验证模型在压缩阈值上使用保守回退窗口，不在 UI 上假装 1M。

### 8.5 落地顺序与取舍

- 阶段一（治标）：补回参数编辑，把现有 1M 标为“手动/未验证”。改动小，能立即止血；仍依赖用户知道正确值。
- 阶段二（治本）：给 `contextWindow` / `maxTokens` 增加证据与探测回流。不再盲信配置；改动面较大。
- 阶段三（结构化）：引入共享模型目录和批量管理。长期最清晰；需要先明确跨供应商同名模型的能力边界。

### 8.6 建议

优先做阶段一 + 阶段二的最小闭环：把参数改为“带证据的有效值”，并让供应商上报值回流校准；
共享目录和批量管理放到后续任务，避免一次改动过大。

### 8.7 CC Switch 对照（只读源码核对）

- CC Switch 的 `piModelCatalog.ts` 把 `claude-opus-5` / `claude-fable-5` / `claude-sonnet-5` 直接写死
  `contextWindow: 1_000_000`，所以这些内置模型不需要用户手工声明 1M。
- 手工新增 Pi 模型时，`PiProviderForm.tsx` 的 `contextWindow` 是必填项，占位提示是 `128000`；
  不填写会校验失败，不会静默给默认。
- 如果模型 JSON 原本没有 `contextWindow` 字段，CC Switch 会原样省略，最终交给 Pi 运行内核回退；
  Zeus 侧对应回退是 `128_000`（`piSdkRuntimeDriver.ts:145` 的 `model?.contextWindow ?? 128_000`）。
- 结论：CC Switch 与 Zeus 的手工模型默认/提示都是 128K，1M 只出现在“内置目录明确声明”或“用户手动写入”。

## 九、默认值与每会话上下文预算（设计决策）

### 9.1 默认值是否统一为 256K

不建议把 256K 当作所有模型的“真实能力”默认值，但可以作为“未验证占位值”：

- 已知目录模型：直接使用目录声明（如 DeepSeek V4 声明 1M、GPT-5.6 声明 272K、Claude 5 声明 1M）。
- 未知/未验证模型：可统一回退到 256K，但必须显示“未验证”，不能冒充已核实能力。
- 继续保留 128K 的好处是保守；统一 256K 的好处是更贴近现代模型、减少过早压缩，但会把真正只有
  128K 的小模型高估，导致压缩过晚。

建议：目录值 > 真实探测 > 未验证回退 256K > 手动覆盖；供应商配置处必须显示当前值及其来源。

### 9.2 供应商配置处展示 1M

模型编辑页需要恢复并展示 `contextWindow` / `maxTokens`，同时显示来源徽标：

- `catalog`：内置目录声明，例如 Claude 5 系列与 DeepSeek V4 的 1M。
- `probe`：真实运行校准。
- `manual`：用户手动覆盖。
- `unverified`：只回退占位，尚未核实。

### 9.3 每会话是否可以切换上下文窗口

产品边界：模型真实上下文窗口由供应商决定，Zeus 配置得再大也不会让模型真的变大；配置得小只会让
Zeus 更早压缩、显示更小的容量。因此“A 会话 1M、B 会话 256K”应建模为**会话级上下文预算/整理阈值**，
而不是修改模型能力，并且只能小于等于模型声明窗口。

现状：同一模型的 `contextWindow` 是连接级共享的，A/B 两个会话不能各自覆盖，当前代码无法直接满足。

建议实现：

- 复用 `conversations.next_turn_settings_json` 增加 `contextWindowBudget`，解析链为
  `会话预算 ?? 模型配置 contextWindow`，并 clamp 到 `[1_000, 模型 contextWindow]`。
- 让该有效值同时流入 Pi 压缩阈值、Codex Responses 的 `model_context_window`、便携上下文预算和
  圆环容量显示，并记录来源（模型默认 / 会话预算）。
- UI 在会话设置里显示“当前有效窗口”，允许下调，不允许超过模型声明窗口。
- 排队提交继续冻结旧执行快照；新预算只影响之后的新提交。

### 9.4 DeepSeek 1M 需要先核实

本机 DB 中 `deepseek-v4-pro` 的真实请求记录 `context_window = 258,400`，而连接配置写的是
`1,000,000`。两者不一致，说明“DeepSeek 支持 1M”目前还只是配置/目录声明，不是运行时已确认事实；
实施每会话 1M 预算前需要先确认 258,400 与 1,000,000 哪个是权威。

## 十三、模板连接补 1M 勾选并收敛 maxTokens（2026-08-18 第四轮）

用户反馈两个问题：截图报错“最大输出 Token 必须是 1 到 256000 之间的整数”，且 DeepSeek 等模板连接的模型卡片没有“支持 1M 上下文”勾选。

### 根因

- `ModelConnectionsSettingsPane.tsx` 的 `ModelDefinitionEditor` 按 `readOnly = templateId !== 'custom'` 整卡走只读分支，模板连接（deepseek / bailian / kimi / zai）的模型只显示请求协议与认证方式，1M 勾选被一起隐藏。
- 勾选取消时渲染层只把 `contextWindow` 改为 `256_000`，`maxTokens` 保留旧值（如 DeepSeek 的 `384_000`）；服务端 `normalizePositiveInteger(…, 1, contextWindow)` 随即抛错，配置不可保存。
- 同样的校验错误还会让 `normalizeStoredModelConnections` 把整条连接按坏记录丢弃：遗留数据中“无 `supports1MContext` 字段且 `maxTokens > 256K`”的模型会连累整个供应商从列表和运行目录消失。
