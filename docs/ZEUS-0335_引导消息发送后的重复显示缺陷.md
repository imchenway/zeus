# ZEUS-0335 引导消息发送后的重复显示缺陷

## 任务信息

- 类型：缺陷。
- 用户现场：任务首发消息已经按结构化任务布局显示，执行期间发送引导后，同一段任务正文又以普通纯文本用户气泡出现一次。
- 预期：一次用户输入在会话时间线中只有一个可见消息身份；引导只补充当前轮次，不得复制首发任务消息。
- Git 边界：未经用户明确要求，不执行 commit、push、merge 或 revert。
- 验证边界：真实运行只允许使用独立身份 `Zeus Test.app`、`dev.hypha.zeus.test` 和独立用户数据目录。

## 已核对的历史口径

- `ZEUS-0102`：引导在 Provider 精确返回 `userMessage.clientId` 前保留本地“引导中”投影；确认后必须原位接管，不能创建第二条消息。
- `ZEUS-0110`：引导从创建开始使用独立 `steer_now` 提交身份，不能与普通下一轮队列竞争。
- `ZEUS-0238` 与 `ZEUS-0288`：乐观消息、Provider item 和持久消息必须按稳定客户端消息编号原地交接，不能按正文或位置模糊匹配。

## 根因

Codex 协议中的 `userMessage.clientId` 是用户消息跨实时事件和历史回放的稳定身份。当前服务端解析存在两处不一致：

1. 同一客户端消息编号已被一个 Provider item 使用后，后续携带相同编号的 Provider 回放会被判为“编号已占用”，继而丢失本地提交关联并降级成远端消息。
2. 服务端为 Provider 用户项补展示信息时使用了另一套较宽松的当前轮次回退。缺少精确编号时，后续用户项可能借用首发 submission 的 `displayText`、附件和 `taskPushLayout`。

Renderer 完整快照虽然会跳过第二个同编号 Provider item，却没有把第二个 `providerItemId` 登记为首个可见项的别名。随后对应持久消息无法按 Provider item 合并，便以原始纯文本再次进入时间线。

这解释了截图中的两种外观：第一条是正确的结构化任务首发消息，第二条是失去稳定身份后的原始纯文本回放；第二条右下角又出现“远程输入”小手机图标，进一步证明它被错误降级成了远端新消息。它不是单纯的 CSS 样式问题。

## 修复方案

1. Provider 返回非空 `clientId` 时始终把它视为稳定用户消息身份；即使另一个 Provider item 已使用该编号，也沿用同一消息，而不是降级成第二条远端消息。
2. Provider 用户项展示信息统一复用同一个身份解析器，并纳入已有持久消息身份；缺少精确编号时，只允许尚未被其他用户项占用的首发提交回退关联。
3. Renderer 水合遇到同客户端编号的 Provider item 别名时，把别名 `providerItemId` 映射到既有可见消息，使随后持久消息继续合并到同一气泡。
4. 不按正文去重，不用 CSS 隐藏重复项，也不把结果未知的引导猜成已经成功。

## 优缺点

### 优点

- 同一引导在乐观态、Provider 实时事件、历史回放和完整快照中保持一个可见身份。
- 任务首发布局、附件和正文不会被后续无身份用户项错误借用。
- 远端真实新消息仍以自己的 Provider 身份进入时间线，不按相同正文误删。

### 代价

- 如果 Provider 返回了重复客户端编号但正文实际不同，Zeus 会优先相信协议身份并视为同一消息，不展示两条；这比把一次引导重复执行或重复展示更安全。
- Provider 完全不返回引导编号时，Zeus 继续保留“引导结果待确认”，不会根据当前轮次或正文猜测成功。
