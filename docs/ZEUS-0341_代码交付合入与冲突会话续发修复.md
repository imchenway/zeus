# ZEUS-0341 代码交付合入与冲突会话续发修复

## 任务目标

修复代码交付中同一次冲突处理的两个连续故障：

1. 任务分支尚未真正合入来源分支时，右侧“合入所选仓库”错误显示为 0 并禁用，用户必须在页面右下角另找“重新同步本地来源分支”才能继续。
2. 冲突处理会话的首条处理消息长时间停留在“正在准备最新冲突现场”，没有进入模型处理；后续消息也会被同一准备态卡住。

## 已核对的现状

- 代码交付的合入计数只统计“可创建新合入记录”的仓库，却把 `pending_local_sync` 这类“合入候选已生成、来源分支尚未落地”的可继续现场排除在外。
- 批量合入函数遇到可恢复记录时只返回“需继续处理”，真正的继续动作只绑在弹窗底部按钮上。
- 冲突会话创建时先持久化带 `holdDispatch` 的首条消息，后台准备命名冲突 Worktree 后再用替换 submission 解除等待。替换会生成新消息编号，但后续派发仍拿旧编号按“不可变请求”校验，触发资源冲突并中止，因此界面一直显示准备中。

## 修复原则

- “合入所选仓库”必须覆盖新建合入、继续本地同步、进入未解决冲突和确认已解决冲突，不再把真正主操作藏在弹窗底部。
- 已合入当前任务提交的仓库仍不重复合入；有未提交文件的仓库仍不能绕过提交边界。
- 冲突现场准备成功后，解除首条和后续消息的 `holdDispatch`，随即请求同一会话队列派发；失败则保留消息并显示真实错误，不伪装为仍在准备。

## 方案取舍

优点：右侧的主按钮始终完成用户当前真正的合入动作；冲突消息从“已持久化”到“已进入 Provider”的边界可追踪，不会再靠隐藏按钮或重开页面推进。

代价：“可合入”不再是单一布尔值，需要依据每个仓库的实时记录选择新建、续接、进入冲突或跳过；队列收口也必须同时维护原消息身份和替换记录。
