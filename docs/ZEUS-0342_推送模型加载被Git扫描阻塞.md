# ZEUS-0342 推送模型加载被 Git 扫描阻塞

## 用户现场

打开“推送到新会话”后，Worktree 区域长时间显示“正在扫描项目目录下的 Git 仓库”，模型下拉框同时显示“没有可运行模型”。模型实际存在，只是要等完整仓库扫描结束后才出现。

## 根因

弹窗只调用完整的任务推送能力接口。服务端会并行读取模型运行能力和递归发现 Git 仓库，但 HTTP 响应必须等两项都结束；Renderer 又只从这份完整响应读取模型，因此较慢的 Git 扫描把已经可用的模型一起挡住了。

此外，完整能力返回后会用打开弹窗时的旧偏好重建整张表单。用户若在加载期间修改模型、权限或补充信息，晚到的响应存在覆盖当前输入的风险。

## 修复决策

1. 打开弹窗时同步读取项目级模型能力缓存；命中时第一帧直接展示真实模型。
2. 缓存未命中时，单独启动现有项目模型能力请求；它不等待 Git 仓库扫描。
3. 完整任务推送能力继续并行加载，并且仍是创建会话、仓库选择和服务端复验的唯一权威依据。
4. 完整能力返回时，以用户当前表单选择做合法化，不再回退到打开弹窗时的旧偏好；加载期间填写的补充文字和本次附件原样保留。
5. 模型已返回但完整能力未完成时，界面明确显示“模型已就绪”，创建按钮继续禁用，避免用缓存绕过任务上下文和工作区校验。

## 方案取舍

优点：

- 模型展示不再受递归 Git 扫描时长影响；已有缓存时可首帧出现。
- 不引入假模型或弱化提交校验，完整能力与服务端复验仍决定能否创建会话。
- 加载期间的用户输入不会被晚到响应覆盖。

代价：

- 弹窗内部从单一加载事实拆成“模型运行能力”和“完整任务推送能力”两段状态。
- 冷启动时会同时发出轻量模型能力请求和完整任务能力请求；执行内核会复用既有就绪状态，完整请求仍会读取一次最终权威能力。

## 实施范围

- `apps/desktop/src/renderer/session/SessionWorkspace.tsx`：开放项目模型能力缓存的只读首帧入口。
- `apps/desktop/src/renderer/App.tsx`：模型快通道与完整任务能力并行加载，并保留加载期间表单草稿。
- `apps/desktop/src/renderer/task/TaskModelPushModal.tsx`：模型选择器消费快通道，工作区和提交继续依赖完整能力。
