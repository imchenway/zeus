# ZEUS-0346 切换模型后报错

## 任务目标

修复同一产品会话从 DeepSeek 切换到 Codex 后，发送消息报
`UNIQUE constraint failed: conversation_runtime_segments.conversation_id`，并暂停后续自动发送的问题。

## 只读现场结论

- 正式应用版本为 `0.3.26`；核验期间没有退出、重启或修改正式应用。
- 发生错误的产品会话当前同时存在一个 Pi `current` 分段和一个 Codex `provisional` 分段。数据库仍满足“一个 current”的约束，但旧的
  provisional 已从 2026-08-17 残留至今。
- 旧 provisional 对应的 submission 已于 2026-08-17 被用户删除，switch operation 却仍是 `provisional`，目标分段也没有转为
  `abandoned`。该目标没有原生会话身份，不能代表 Provider 已接纳。
- 2026-08-20 的新提交在 Provider 写入前创建候选分段时，撞上“每个产品会话只能有一个 provisional 分段”的部分唯一索引；新
  submission 因而以 `preflight_failed` 暂停，`segment_id` 为空，消息没有发送给 Codex。
- SQLite 对 current 和 provisional 两个部分唯一索引都只报告
  `conversation_runtime_segments.conversation_id`，所以错误文本本身无法指出实际冲突的是 provisional。

## 根因

队列删除路径只把 `conversation_submissions.status` 改为 `deleted`，没有同步结束该 submission 所属的开放切换操作，也没有废弃其尚未接纳的
provisional 分段。之后 `beginSwitch` 直接插入新 provisional，既不识别终态 submission 遗留的开放操作，也不把底层唯一约束转换为领域错误。

这破坏了 ZEUS-0311 的既有契约：候选分段只在运行时接纳后提升；未接纳且已取消的候选必须结束，不能永久占用会话切换槽位。

## 修复设计与取舍

1. 在统一执行仓储增加“按 submission 取消开放切换”事务：仅处理 `preflight`、`provisional`、`outcome_unknown`，把仍为 provisional 的目标改为
   `abandoned`，把 switch operation 改为 `cancelled` 并保留原因和结束时间。current 来源分段不变。
2. 队列删除在同一数据库事务中先收口开放切换，再把 submission 改为 `deleted`、恢复被队首阻塞的队列并重排。
3. `beginSwitch` 在建立新候选前检查当前开放切换。若其 submission 已是 `cancelled` 或 `deleted`，按历史残留安全收口后继续；若仍是非终态，返回明确的
   “切换仍在进行”领域错误，不依赖 SQLite 唯一约束兜底。

优点：新删除路径立即恢复不变量；已有正式数据无需离线改库，下一次合法切换即可安全自愈；不会封存 current，也不会重发已删除消息。

缺点：历史残留会一直保留到相关会话再次派发消息；`outcome_unknown` 被用户明确删除时，目标原生会话即使事后证明已接纳，也不会再自动并入产品历史。这与现有
“结果未知必须恢复核对或取消”的产品边界一致。

不采用删除唯一索引或 `INSERT OR REPLACE`。前者会允许多个候选并存，后者可能静默删除审计记录，两者都会把状态错误扩大为会话历史错乱。
