当前三处真实断点

  1. digitalEmployeeOrchestrator.dispatchExecution() 仍构造普通 source: "task_push"，只传员工默认 skillId，没有读取工作流或传入 stageId。
  2. monitorConversation() 在产品会话进入 completed 后直接切到 delivery_pending，尚未等待阶段交付物提交和验收。
  3. taskStageRoutes.ts 的初始化、配置、捕获、手工交付物、跳过、接受和请求修改 7 个写入口直接调用应用服务，尚无统一 Work Management Command Envelope。

阶段启动解析规则

  • 员工：阶段显式员工优先，未配置时继承任务默认员工；模型不能自行选择员工。
  • Skill：阶段 explicit ＞ 员工默认；none 表示明确禁用，不能与“未配置”混淆。
  • 模型：阶段冻结配置权威；员工偏好只用于初始化，能力不兼容时阻塞而不是静默换模型。
  • 能力：任务权限 ∩ 员工快照 ∩ 阶段策略 ∩ Runtime 能力；Skill 不参与权限计算。

方案依据：docs/ZEUS-0352_引入数字员工.md#Harness-Engineering-完整方案

自动交付的放行条件

  • 整个工作流已经完成，最终质量阶段已验收，没有未解决阻断项。
  • 目标仓库、分支、环境、工作区水位和验证/审查证据被最终检查点冻结。
  • 任务权限、员工授权和动作自身策略都允许本次具体动作。
  • 每个动作拥有稳定命令身份和回执；前一动作未知时后续动作全部停止。

现有基础：Command ledger、Git/部署耐久回执、数字员工逐动作授权；新增边界：final delivery checkpoint

代码审查：已存在与待补齐

当前已存在：代码审查要求继承产生已验收实施交付物的精确会话，固定只读权限与 writableRoots=[]，并覆盖冻结基线之后的已提交、暂存、未暂存和未跟踪变更。

目标待补齐：把主任务文档、确认会话决策、已验收计划、完整变更和真实验证结果编译成 Requirements / Change / Verification 三份可追溯清单，并把审查结论固化为 CodeReviewReportV1。
