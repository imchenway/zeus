# ZEUS-0352 引入数字员工

## 当前阶段

首版纵切实现已完成，并已依次 cherry-pick ZEUS-0351 的 Zeus Skill 管理与 ZEUS-0263 的阶段交付能力。Skill 与人工阶段启动已经在同一原生会话提交中共存，数字员工默认 Skill 也已进入真实 Catalog 和 Runtime 投影。用户已确认采用“每阶段员工 + 任务默认员工”的组合语义；当前已完成数字员工、Skill、阶段交付物、代码审查与自动交付的一版 Harness Engineering 总体方案，尚未按该目标架构继续改造业务代码。受当前 Computer Use 运行环境缺少原生交互能力影响，真实桌面页面的点击、视觉和交互仍保留为待复验项。

## 原始需求

1. 内置产品、前端、开发、测试、部署等角色，并允许用户自定义数字员工。
2. 支持按业务领域组合岗位，例如“CSS 测试”“PIM 产品”。
3. 数字员工可配置 Skill、提示词等能力和行为内容。
4. 任务指派给数字员工后，由员工自动处理。
5. 可配置员工自动探索、捞取、执行与交付任务。
6. 可为员工配置自动化任务。

## 已核实的现状

- Zeus 的“任务”已经拥有项目、类型、父子/关联关系、管理状态、Agent 运行状态，以及 `allowCodeChanges`、`allowTests`、`allowGitCommit` 等任务级权限。
- Zeus 的“产品会话”及其“目标”可以承载一次工作执行；目标绑定单条 Provider 原生会话，允许跨轮自动续跑，但不负责跨任务找活、认领和排班。
- Zeus 当前界面里的“智能体”表示一条会话派生的运行线程，不是跨任务存在的员工身份。
- 命令中心已具备全局/项目命令、参数、风险标记、逐次确认、执行记录、日志与产物，但它不是任务池或员工调度器。
- 当前任务启动主要来自用户显式操作或 API 调用；尚未发现数字员工身份、能力组合、任务认领策略、定时自动化或跨任务后台调度事实。

因此，不能把现有“智能体”“目标”“任务模板”中的任意一个直接改名为“数字员工”。这样会混淆工作主体、执行载体和工作定义，也无法表达长期配置、授权与审计。

## 候选领域模型

以下术语已经确认，并已同步写入工作管理领域词汇表：

### 数字员工

长期存在、可配置、可授权、可分派且可审计的工作主体。它描述“谁以什么规则工作”，不拥有 Provider 原生线程，也不等于某次会话。

建议由以下配置组合产生，而不是新增固定的 `product/frontend/developer/test/deploy` Agent 枚举：

- 岗位：产品、前端、开发、测试、部署等职责基线。
- 领域：CSS、PIM 等业务知识与项目范围。
- 能力配置：默认 Skill、Provider/模型、提示词、命令和工具。
- 工作策略：可接受的工作来源、筛选条件、并发上限、优先级与静默时段。
- 权限策略：只读探索、修改代码、执行检查、提交、推送、合入、部署及任务状态变更的独立授权。

优点：岗位与领域可以自由组合，新增业务员工不需要改枚举或数据库结构；运行时可以替换而员工身份保持稳定。

缺点：必须处理配置版本、能力兼容、权限冲突和历史执行可追溯性，首版实现面明显大于新增一个 Agent 下拉项。

### 工作指派

把一个明确任务交给某个数字员工的业务事实。指派只决定责任主体和采用哪一版配置，不表示已经建立会话、已经开始执行或已经交付。

优点：可以把任务管理状态、排队状态和真实运行状态分开，失败重试或换 Provider 时不会丢失责任关系。

缺点：需要单独定义接受、拒绝、撤回、转派、并发冲突和重复指派规则。

### 工作来源

向数字员工提供“可评估工作项”的受控来源，例如 Zeus 任务池、用户配置的定时任务、代码仓库扫描结果或外部系统。来源只发布候选，不直接绕过策略启动副作用。

优点：可扩展新的项目与外部系统，同时保留来源、筛选和幂等证据。

缺点：来源越开放，误认领、重复执行、凭据暴露和不可控成本越高。

### 自动化规则

由触发器、筛选条件、目标数字员工、执行预算、权限策略和人工闸门组成的版本化规则。定时只是触发器之一，不应与“数字员工”本身绑定成一个 Cron 字符串。

优点：同一员工可以同时接受人工指派、任务池认领和定时巡检；规则可暂停、审计和独立修改。

缺点：需要可靠调度、幂等、漏跑/补跑、时区、并发和故障恢复语义。

### 工作执行

一次指派或自动化触发产生的可审计执行实例。它引用任务、数字员工配置版本、授权快照和产品会话，并记录认领、启动、等待、阻塞、产出和终止证据。

优点：能够回答“哪位员工、按哪版配置、为何启动、做了什么、交付到哪里”。

缺点：需要新增跨工作管理、会话编排和执行资产的稳定契约，不能由 Renderer 直接拼接状态。

## 推荐的系统边界

建议由“工作管理”上下文拥有数字员工、工作指派、工作来源、自动化规则和工作执行的业务事实；会话编排只负责建立并驱动产品会话；Agent Runtime 仍只负责 Provider 能力和原生身份；执行与资产保存命令、日志、附件、变更集及交付结果。

优点：复用现有任务、会话、目标、命令和交付链路，避免数字员工成为一个可绕过安全边界的超级 Agent。

缺点：需要版本化命令和领域事件连接多个上下文，不能用一张员工表加后台定时器快速完成。

## 首版范围

首版交付“全局员工模板 + 项目员工配置 + 人工指派 + Zeus 内部任务池 + 已分配项目内自主探索 + 用户显式创建的自动化规则 + 逐动作授权的端到端交付”。外部系统主动捞取作为后续受控工作来源。

优点：覆盖“员工配置、任务自动处理、自动找活、自动化任务、端到端交付”的完整产品主线，并通过项目范围和逐动作授权保持最小权限。

缺点：首版的探索只发生在已分配项目，不能宣称已从外部业务系统自主找活；端到端动作需要分别建设可恢复、可审计的执行门禁，无法用单一“完全自动”开关代替。

## 已确认的产品决策

### 1. 自动找活的工作来源

- A：首版只使用 Zeus 内部任务池和用户显式创建的定时自动化；仓库与外部系统后续接入。推荐，边界最清晰。
- B：首版同时支持 Zeus 任务池、代码仓库探索和已安装连接器；每个来源必须单独授权与配置。
- C：允许员工自行决定从哪里探索工作。自主性最高，但成本、权限与误操作风险不可控，不建议。

已确认：使用“Zeus 内部任务池 + 自主探索”。自主探索仅限员工已分配项目中的任务、代码和文档，并以只读方式发现、提出或创建候选任务；不得扫描其他项目、本机任意目录或未逐项授权的外部系统。

优点：保留员工主动发现工作的能力，同时以项目分配形成最小读取范围和清晰来源证据。

缺点：跨项目问题与外部业务信号不会自动进入任务池，后续需要增加显式连接器来源或跨项目授权。

### 2. 自动交付权限

- A：自动探索、认领、执行和形成交付候选；提交、推送、合入、部署及任务终态仍由用户确认。推荐。
- B：可按员工逐项授权自动提交和推送，但合入、部署及任务终态仍需确认。
- C：可按员工授权端到端自动交付，包括合入、部署和任务终态。需要更强审批、回滚、环境和发布治理。

已确认：首版支持端到端自动交付，但采用逐动作显式授权。数字员工分配到项目时，`提交`、`推送`、`合入`、`部署` 和 `结束任务` 权限默认全部关闭，用户可分别开启；开启后允许员工在满足目标位置、环境与前置门禁时自动执行。

优点：可以真正实现无人值守交付，同时按项目和动作维持最小权限；开发员工无需自然继承部署权限。

缺点：必须为每种副作用定义明确接收位置、幂等身份、前置门禁、结果未知处理、失败停止和回滚/恢复策略，不能复用一个笼统的“完全访问”开关。

### 3. 组织与复用方式

- A：全局员工模板，分配到项目时产生项目配置；项目可覆盖领域、Skill、提示词和权限。推荐。
- B：每个项目独立创建员工。隔离最强，但重复配置多，跨项目员工与统一治理较弱。
- C：只有一套全局员工直接服务所有项目。维护简单，但难以表达项目差异和最小权限。

已确认：采用“全局员工模板 + 项目配置”。模板沉淀可复用的岗位、领域、Skill、提示词、Provider/模型和默认工作策略；分配到项目后形成独立数字员工配置，允许覆盖这些内容，并独立配置探索范围、自动化和逐动作交付权限。

优点：产品/前端/开发/测试/部署等基线可以统一维护，又能组合出“CSS 测试”“PIM 产品”等项目员工；项目权限不会随模板更新被意外放大。

缺点：模板更新与项目覆盖之间必须提供可见的继承、差异和升级语义，不能静默覆盖已经运行的员工配置。

2026-08-25 曾误选“全局员工直接服务”，用户随即明确撤回；该误选不构成产品决策。

### 4. 自动化触发方式

已确认：首版同时支持手动立即运行、一次、每天、每周、固定间隔和项目事件触发。项目事件至少覆盖任务创建、任务状态或内容变化以及项目代码变化；同一来源事件必须以稳定身份去重，并受员工并发上限和风暴抑制约束。

优点：既可表达周期巡检，也能在真实业务事实变化时及时工作；自主探索可以按计划或项目事件启动，而不需要无限后台循环。

缺点：必须持久保存调度水位、事件匹配和去重结果；批量导入或频繁代码变化可能形成触发风暴，需要合并窗口与背压。

## 当前不应假设的内容

- 不把固定岗位写成不可扩展的 Agent 类型枚举。
- 不把 Codex 子线程或目标直接当成员工身份或任务池调度器。
- 不因配置了 Skill 或提示词，就默认获得对应工具、凭据或副作用权限。
- 不把“任务已完成”与代码已提交、已推送、已合入或已部署画等号。
- 不在结果未知或缺少真实执行证据时自动重发、自动交付或标记成功。

## Zeus Skill 结合审查

ZEUS-0351 已提供 Zeus Skill Catalog、安装与删除、稳定 Skill 身份，以及 Codex 结构化输入和 Pi ResourceLoader 的全模型原生投影。它的工作流契约是“每次首发显式选择零或一个已安装 Skill”，不是任意文本标签或隐式工具权限。

数字员工原实现与该契约存在三处断点：模板和项目员工接受逗号/换行自由文本；内置模板保存的是 Skill 名称而不是 32 位稳定身份；调度器只把名称列表写入补充提示词，没有向任务推送提交 `skillId`。因此原展示不能证明 Skill 已加载。

本次结合采用“零或一个数字员工默认 Skill”：

- 全局模板从无项目 Catalog 选择可复用 Skill；项目员工从当前项目 Catalog 选择，允许绑定项目级 Skill。
- 保存时只接受 Zeus Skill 的稳定 ID，不再接受名称或路径文本；内置模板不预绑运行环境相关 ID。
- 工作执行固定员工配置快照，派发时把默认 Skill ID 交给既有任务推送链路；该链路先在项目目录复验，再在最终工作区按同一身份复验，并把解析后的名称、说明和绝对 `SKILL.md` 路径冻结进耐久提交。
- Codex 使用原生 `{ type: "skill", name, path }` 输入，Pi 使用同一 Skill 的 ResourceLoader 与显式展开；数字员工不再自行拼接 Skill 正文。
- Skill 只改变执行说明和资源投影；员工代码/验证权限、提交、推送、合入、部署和任务完结授权仍独立取交集。

优点：配置可发现、不可拼错，全模型真实生效，项目 Worktree、重试和 Runtime 切换沿用 ZEUS-0351 的稳定恢复语义，也不会让 Skill 绕过数字员工授权。

缺点：首版一次工作执行只能激活一个默认 Skill；多个 Skill 的顺序、冲突、上下文预算和 Pi 展开协议尚未定义。后续若需要多 Skill，应扩展工作执行的显式编排协议，不能恢复为逗号文本列表或静默只取第一项。

## 阶段交付、数字员工与 Skill 结合审查

三者应保持不同职责：任务阶段描述“当前要完成什么、输入输出契约和何时验收”；数字员工描述“由谁在什么项目范围、能力和逐动作授权下工作”；Skill 描述“某次阶段尝试加载哪份执行说明与资源”。阶段交付物是正式结果，产品会话只是阶段尝试的运行载体。

### 已经打通的链路

- `stageId` 与 `skillId` 可以进入同一条任务首发请求；Renderer 的耐久请求校验同时保留二者，重连不会丢失任一身份。
- 计划和实施阶段仍冻结模型、推理强度、服务等级、工作模式与权限；启动时可另外选择零或一个 Skill。服务端先在项目目录复验 Skill，再在最终 Worktree 复验同一稳定 ID，并把解析结果传入创建阶段尝试的会话计划。
- 代码审查的服务端阶段包装也能接收已经解析的 Skill，并继续保持精确实施来源和只读工作区；普通任务推送、普通代码审查和冲突处理原有 Skill 链路未被阶段功能覆盖。
- 任务详情同时保留数字员工指派面板和“阶段交付”区域；存储权威与生命周期矩阵同时登记 5 张数字员工表和 4 张阶段表，合计 97 张 Core 表、11 张可重建辅助表。

### 尚未打通的真实断点

1. `digitalEmployeeOrchestrator` 仍直接创建普通 `task_push` 会话，不读取任务工作流、当前可执行阶段或 `stageId`；因此把任务指派给员工不会自动形成阶段尝试。
2. 阶段和阶段尝试只冻结模型、权限、工作区及上游交付物，没有数字员工、数字员工执行或 Skill 快照字段。Skill 虽可在原生会话提交中追溯，却不能仅从阶段尝试回答“哪位员工按哪个 Skill 产生了此版本”。
3. 数字员工当前以“会话 completed”作为提交、推送、合入、部署和结束任务的起点；阶段工作流则要求先沉淀交付物并按阶段人工或自动验收。若仅给数字员工请求补一个 `stageId`，会在交付物尚未验收时提前执行外部副作用。
4. 计划/实施阶段的任务推送弹窗可以选择 Skill，但阶段配置没有 Skill 覆盖项；阶段代码审查从任务详情直接启动时也没有传入代码审查 Skill。三种入口尚未形成一致的继承和冻结语义。
5. ZEUS-0263 新增的 7 个阶段写接口直接调用阶段应用服务，没有接收 Work Management Command Envelope。全仓公开命令副作用盘点因此从既有 31 个待迁移入口增加到 38 个，其中新增 7 个全部来自 `taskStageRoutes.ts`。内部副作用登记完整，但公开 actor、命令幂等与统一审计边界尚未建立。

### 推荐的组合契约

- **执行主体**：每个阶段可显式绑定一个项目数字员工；任务级员工只作为未单独配置阶段的默认值。阶段尝试同时引用数字员工执行和员工配置快照。
  - 优点：计划、开发、测试、审查、部署可以由不同岗位/领域员工负责，权限和责任清楚；简单任务仍可由一个员工贯穿。
  - 缺点：需要阶段级指派 UI、配置继承提示、员工停用/删除处理和跨员工交接审计。
- **执行配置**：阶段冻结的 Agent、模型、推理强度、服务等级、工作模式和权限要求优先；数字员工配置只用于初始化默认值及形成权限上限，不能在启动时静默改写已冻结阶段。
  - 优点：阶段可重复、可验收，换员工不会改变既有工作契约。
  - 缺点：员工偏好模型与阶段指定模型冲突时必须显式提示，不再能“自动挑一个可用模型”。
- **Skill 继承**：阶段可选 Skill 覆盖优先，其次继承阶段执行员工的默认 Skill；两者都为空则不加载。稳定 ID、解析名称与内容身份随阶段尝试冻结；绝对路径只保留在会话编排和 Runtime 的原生提交证据中。Skill 仍不扩大权限。
  - 优点：既能让“CSS 测试员工”携带领域 Skill，也能让某个代码审查阶段显式使用专门审查 Skill。
  - 缺点：必须新增可见的“继承/覆盖/不可用”状态，并定义员工模板或 Skill 删除后的历史展示。
- **权限计算**：有效权限取任务权限、数字员工授权和阶段权限的最小交集；Skill 不参与权限计算。计划、自主探索和代码审查继续固定只读。
  - 优点：任一层收紧都会生效，不会因阶段或 Skill 放大员工权限。
  - 缺点：被收紧时需要展示具体来源，否则用户只会看到“为什么不能执行”。
- **推进与交付**：会话完成只产生“可沉淀交付物”；交付物提交并按阶段策略验收后才推进。默认在最终阶段验收、工作流完成后，数字员工才进入提交、推送、合入、部署和任务完结编排；未来如需阶段后交付，必须为每个动作配置明确验收检查点。
  - 优点：不会把一次模型回复误当任务或代码已交付，返工链和外部副作用顺序可审计。
  - 缺点：无人值守链路必须自动生成符合输出契约的阶段交付物，并处理自动验收失败、人工阶段等待和恢复。

不推荐把一个任务级数字员工当隐式“主管”自动选择所有阶段员工。优点是入口简单，但委派决策、权限来源、成本和失败恢复不可解释；若未来需要主管模式，应新增显式的阶段指派命令和可审计决策，不应从提示词自行推断。

用户已确认“每阶段员工 + 任务默认员工”作为正式产品语义。本次方案据此继续设计，但不把确认方案等同于业务代码已经实现。

## Harness Engineering 完整方案

完整交互图见：[ZEUS-0352 Harness Engineering 交互图册](./ZEUS-0352_Harness_Engineering_交互图册.html)。图册以一张业务总流程和九张交互时序分别覆盖人工指派、自动找活、阶段员工/Skill/能力解析、上下文与 Runtime、交付物验收、代码审查、最终交付、结果未知恢复及配置生命周期，并明确区分当前事实、拟议整合和当前断点。

### 1. 定义与目标

Zeus 的 Harness 不是新的 Provider、Agent 类型或万能对话框，而是由 Zeus 产品拥有的一套任务执行控制面：它把工作来源、任务、数字员工、阶段、Skill、产品会话、交付物、验收、代码审查和外部交付动作组织成一条可恢复、可审计、可授权的闭环。

[OpenAI《Codex as a platform: build on the open agent harness》](https://learn.chatgpt.com/blog/codex-as-a-platform)把 Harness 描述为模型之外负责上下文、工具、进度、失败、审批和结果的系统，并明确宿主应用应继续拥有业务上下文、规则、界面和记录系统。Zeus 因此拥有任务工作流、阶段门禁和交付事实；Codex/Pi 及其 Runtime Adapter 只拥有单次 Agent loop、原生会话和 Provider 协议。

目标闭环如下：

```text
工作来源/人工指派
    → 工作执行
    → 任务工作流
    → 阶段执行指派
    → 阶段上下文编译
    → 独立产品会话与 Agent Runtime
    → 交付物候选
    → 阶段交付物与验收门
    → 下一阶段 / 返工
    → 最终交付检查点
    → 提交、推送、合入、部署、结束任务
```

优点：业务状态不依赖某个模型或一条长会话；任一结果都能追溯到员工、配置、Skill、上下文、代码现场和授权；自动化与人工操作共用同一套状态机。

缺点：需要补齐跨上下文命令、阶段快照、验收策略和交付恢复，短期复杂度高于让数字员工直接启动会话并在完成后执行 Git 动作。

### 2. 不可破坏的架构约束

1. 任务及其工作流是业务记录系统；产品会话只是阶段尝试的运行载体。
2. 会话 `completed` 只表示本次 Agent loop 结束，最多产生交付物候选；它不等于阶段验收、任务完成或允许外部交付。
3. 已验收的阶段交付物是跨阶段唯一正式契约；下游不得扫描上游完整聊天来猜结果。
4. 数字员工决定“谁负责”和能力上限；阶段决定“本次做什么”和输出契约；Skill 决定“本次采用哪套执行说明与资源”。三者不得互相替代。
5. 有效能力取任务、员工快照、阶段策略和 Runtime 能力的最小交集；逐动作交付还必须通过对应检查点。Skill 永不扩大工具、凭据或副作用权限。
6. 计划、自主探索、验证和代码审查默认不修改代码；代码审查始终使用独立会话和只读工作区。
7. 所有工作流、阶段、交付物、验收和外部动作写入都必须走版本化 Command Envelope，带稳定幂等身份、主体、作用域和预期版本。
8. 写出后结果未知必须失败关闭并等待对账；不得盲目重发会话、Git、部署或任务终态命令。
9. Renderer 只提交命令和展示投影，不直接选择 Provider、推进阶段或执行 Git/部署副作用。
10. 运行中的员工、Skill、阶段、权限和上下文均按尝试冻结；后续配置变更只影响新尝试。

### 3. 逻辑分层与所有权

| 层 | 主要职责 | 权威上下文 | 不负责 |
| --- | --- | --- | --- |
| 工作入口 | 人工指派、任务池候选、自主探索、日历与项目事件触发 | 工作管理 | 直接启动 Provider 或执行副作用 |
| 任务控制面 | 工作执行、工作流、阶段指派、推进、返工、验收策略、交付检查点 | 工作管理 | 保存 Provider 内部历史 |
| 上下文编译 | 在固定水位选择任务事实、交付物、代码现场、会话证据与 Skill | 会话编排 | 改写引用来源或绕过预算 |
| Agent loop | 原生 Skill 投影、模型调用、工具循环、流式事件和原生恢复 | Agent Runtime | 决定阶段已验收或任务已交付 |
| 证据与质量 | 资产、命令回执、变更集、验证记录、结构化审查报告 | 执行与资产；业务引用由工作管理持有 | 直接推进工作流 |
| 交付控制 | 根据检查点逐项执行提交、推送、合入、部署和结束任务 | 工作管理发令；执行与资产落命令事实 | 从模型回复推断授权 |

这种分层保留现有本地优先模块化单体，不要求把每一层拆成独立服务。优点是可渐进落地并复用现有会话、命令和资产能力；缺点是物理包暂时仍跨上下文，必须靠应用服务、命令和事件守住逻辑边界。

### 4. 统一领域模型

| 实体 | 回答的问题 | 目标语义 |
| --- | --- | --- |
| 任务 | 为什么做 | 保存目标、约束、代码位置、目标分支、任务权限和状态 |
| 工作执行 | 为什么现在开始 | 一次人工指派、认领或自动化触发产生的父执行，跨越一个任务工作流 |
| 任务工作流 | 按什么路线做 | 固定阶段顺序、返工边、验收与交付策略 |
| 任务阶段 | 当前做什么 | 保存目的、输入/输出契约、执行配置和验收策略 |
| 阶段执行指派 | 谁来做 | 显式员工优先，否则继承任务级工作指派；模型不得隐式选人 |
| 阶段尝试 | 这一次如何做 | 冻结员工、Skill、模型、权限、上下文和工作区；拥有独立产品会话 |
| Skill 选择 | 用哪套方法做 | 阶段覆盖优先，其次员工默认，最后为空；一次尝试最多一个稳定 Skill |
| 阶段交付物 | 产出了什么 | 版本化稳定资产，可提交、验收、驳回或被新版本取代 |
| 阶段验收 | 是否可进入下一步 | 人工或显式策略形成的业务事实，不能由会话完成替代 |
| 代码审查报告 | 变更是否满足要求 | 结构化、只读、可定位的阶段交付物；可放行或请求返工 |
| 交付检查点 | 允许哪些外部动作 | 绑定已完成工作流、权限快照、目标位置和放行动作 |
| 交付动作 | 实际做了什么 | 引用现有 Command ledger 的提交、推送、合入、部署或任务终态执行 |

现有 `digital_employee_executions` 可先保持物理表名，但领域语义应提升为跨阶段的“工作执行”，不再与一条普通会话一一等同。其员工身份表示触发或任务默认员工，不表示所有阶段都由该员工执行；每个阶段尝试各自冻结实际负责员工、建立产品会话并引用父工作执行。

优点：最大化复用现有数据与执行记录；员工自动化、人工阶段启动和代码审查最终汇入一条链路。

缺点：旧记录只有普通会话级语义，迁移后需要明确 `legacy_single_conversation` 来源，不能伪造其缺失的阶段、Skill 或验收证据。

### 5. 目标数据契约

首轮采用向前兼容扩展，不先进行破坏性表重命名：

- `task_stages` 增加员工选择模式、显式员工 ID、Skill 选择模式、显式 Skill ID、验收策略与配置修订号。`inherit`、`explicit`、`none` 必须可区分，不能用 `null` 同时表达三种语义。
- `task_stage_attempts` 增加父工作执行 ID、员工 ID/修订号/快照资产引用、Skill ID/内容摘要、有效能力清单资产引用、上下文清单资产引用及指纹。绝对 Skill 路径只留在会话编排/Runtime 的原生提交证据中，不成为跨上下文契约。
- `task_stage_deliverables` 继续承载计划、实现摘要、验证报告、代码审查报告和发布就绪报告；完整正文放稳定资产，表内保存种类、版本、摘要、摘要哈希、状态和来源尝试。
- 新增工作管理拥有的交付动作记录；每条记录只描述动作种类、授权检查点、目标、状态和关联 Command ID，实际命令、日志与回执继续由现有执行与资产能力拥有。
- 现有工作执行继续固定员工配置、来源、自动化、逐动作授权和并发租约，并增加工作流 ID、当前阶段和最终检查点引用。

每次尝试必须能只依赖耐久事实回答：哪项工作触发、哪位员工负责、采用哪版阶段配置、解析了哪个 Skill、允许哪些能力、读取了哪些权威输入、使用哪个工作区和代码水位、产生哪个交付物、由什么规则验收。

优点：运行复现和故障对账有完整证据，配置删除或更新后仍可解释历史。

缺点：快照和资产引用增加存储及迁移成本；必须定义脱敏、保留期和旧记录缺失字段的展示语义。

### 6. 阶段编排

工程任务推荐模板为：

1. **计划**：产品、架构或领域员工负责；只读；输出目标、范围、约束、风险、验收条件和实施顺序。
2. **实施**：前端或开发员工负责；按最小交集获得代码修改与检查能力；输出变更摘要、文件范围、真实检查证据和残余风险。
3. **验证**：测试员工负责；默认只运行允许的验证命令、不修改实现；输出可重复的验证步骤、结果、失败证据与覆盖缺口。
4. **代码审查**：独立审查员工负责；固定只读并精确复用实施工作区；输出结构化发现和 `pass`、`changes_requested` 或 `blocked` 结论。
5. **发布就绪（可选）**：部署员工负责；检查目标、版本、配置、迁移、回滚和环境前置条件，但不自行绕过交付控制器执行部署。
6. **交付动作**：不是模型阶段，由交付控制器依据最终检查点逐项执行已授权动作。

工作流模板允许省略或增加阶段，例如纯调研可只有计划和审查，文档任务可不设验证，业务发布可新增安全或合规阶段；岗位和阶段种类不写成固定 Agent 枚举。

优点：产品、前端、开发、测试、审查和部署员工都能承担清晰责任，同时简单任务仍可裁剪。

缺点：阶段越多，等待时间和成本越高；项目必须维护适合自身风险的模板，不能把最长模板强制用于所有任务。

### 7. 阶段解析与启动算法

每次开始阶段尝试时，服务端按固定顺序执行：

1. 读取任务、工作执行、工作流和当前可执行阶段，校验版本、前置阶段和并发租约。
2. 解析员工：阶段显式员工优先，否则继承任务级员工；员工必须启用、属于当前项目且未超过并发上限。
3. 解析 Skill：阶段 `explicit` 覆盖优先，`inherit` 使用员工默认，`none` 明确禁用；在项目目录和最终工作区复验同一稳定 ID。
4. 解析模型与运行参数：阶段冻结配置权威，员工偏好只用于创建或编辑阶段时填充默认值。能力不兼容时在启动前阻塞并展示冲突，不静默换模型。
5. 计算有效能力：任务权限 ∩ 员工快照 ∩ 阶段策略 ∩ Runtime 可用能力；计划、探索、验证、审查的硬只读约束最后收紧，并生成 `CapabilityManifestV1`。
6. 编译阶段上下文清单，冻结输入身份、版本、哈希、预算、裁剪和缺失项。
7. 通过 `stage_attempt.start` 命令原子创建尝试与派发意图，再建立独立产品会话；写出后未知进入 `outcome_unknown`，不创建第二条会话。
8. Runtime Adapter 按冻结结果建立原生 Skill 投影并驱动 Agent loop，不接管阶段推进。

优点：所有入口得到相同员工、Skill、权限和恢复语义。

缺点：启动不再是一次简单 HTTP 调用；任何配置冲突都会提前显式阻塞，需要相应的修复入口。

`CapabilityManifestV1` 明确列出可见工具、命令中心命令、连接器作用域、凭据槽位引用、网络策略、可写根、验证能力和逐动作交付许可。Runtime 只暴露清单允许的工具面；员工提示词或 Skill 即使要求额外工具，也只能得到明确的“能力不可用”，不能把文字指令当授权。优点是工具和权限可证明；缺点是每个 Runtime Adapter 都必须维护稳定能力键与真实工具投影的映射。

### 8. 阶段上下文编译

上下文编译按以下权威级别和预算选择输入：

1. 系统/开发策略、项目 `AGENTS.md`、安全边界和有效能力清单。
2. 冻结的阶段目的、输入/输出契约、验收策略和工作模式。
3. 员工岗位/领域提示词，以及本次 Skill 的结构化说明和资源投影；二者都不得覆盖前两层或获得额外能力。
4. 当前任务事实和最新主任务文档。
5. 已验收的上游阶段交付物及交接摘要。
6. 精确工作区、Git 基线、当前提交/暂存/未暂存/未跟踪变更和目标分支事实。
7. 已确认的来源会话需求、用户决策和运行证据。

第 4 至 7 层的正文以及代码、日志和外部内容全部标记为不可信数据，只提供事实，不能反向覆盖策略、阶段契约、员工边界或 Skill 选择。最终输入按“策略 → 阶段契约 → 员工角色 → Skill → 任务与证据 → 输出契约”分区编译，不把它们拼成一段来源不明的超级提示词。

编译结果形成不可变“阶段上下文清单”，记录每个来源的稳定 ID、修订号、内容哈希、选择原因、预算、裁剪方式和缺失原因；完整资产按需读取，不复制为第三份会话历史。

优点：同一水位可重建输入，审查能够同时覆盖真实需求和真实代码现场；提示注入和上下文漂移更容易定位。

缺点：需要统一任务文档、会话证据、Git 事实、资产与 Skill 的选择协议；内容哈希相同也不代表语义等价，仍需正确来源分级。

### 9. 交付物、验收与返工

Agent loop 结束后只进入 `output_candidate`。Harness 依次执行输出契约校验、资产固化、摘要/哈希生成和 `deliverable.submit`；只有阶段验收事实才能推进工作流。

验收策略分为三类：

- `manual`：用户显式接受或请求修改，默认用于计划、主观产品结论和高风险发布。
- `deterministic`：输出结构、必填资产、命令回执和确定性检查全部满足后自动接受，适用于机器可证明的阶段。
- `reviewer_plus_policy`：独立只读审查结论为通过、确定性检查通过且无未解决阻断项后自动接受；必须由项目显式开启，自动外部交付时至少采用此策略。

同一阶段的执行会话不能自我验收。请求修改时保留原交付物与审查报告，按返工边重新打开上游阶段并创建新尝试；新尝试只接收已验收交付物和明确的修改请求，不覆盖历史。

优点：无人值守和人工控制可以按风险组合，返工原因与版本链完整保留。

缺点：确定性门禁覆盖不了主观质量；独立模型审查仍是概率判断，显式启用自动验收的项目必须接受残余风险。

### 10. 代码审查 Harness

现有服务端代码审查保留为执行适配器，但审查输入与放行结论提升为正式阶段契约。每次审查必须冻结三份清单：

- **需求清单**：当前主任务文档、已确认的来源会话需求与决策、已验收计划交付物、项目规则和验收标准。
- **变更清单**：精确仓库/工作区、基线 SHA、来源头 SHA，以及基线之后已提交、已暂存、未暂存和未跟踪文件。
- **验证清单**：真实执行过的检查命令、退出状态、日志/产物引用、未执行项和环境缺口；不得把编译通过推断成 GUI 或 Provider 验收通过。

审查会话必须独立于实施会话，固定 `writableRoots=[]`，并精确复用产生已验收实施交付物的工作区。结构化 `CodeReviewReportV1` 至少包含总体结论、范围覆盖、发现列表、残余风险和缺失证据；每条发现包含严重度、置信度、文件/行号、证据、影响和建议。`changes_requested` 通过正式返工边回到实施阶段；`blocked` 不得被当作失败重试或通过。

为自动外部交付启用代码审查时，至少要求不同产品会话；推荐使用不同数字员工配置或不同审查模型，降低同源盲区。强制不同员工的优点是职责独立，缺点是成本和配置负担更高，因此只作为自动合入/部署和高风险项目的默认门禁，不强制所有人工任务。

### 11. 交付控制器

最终阶段验收且工作流完成后，Harness 才创建交付检查点。检查点冻结目标仓库/分支/环境、工作流修订、已验收交付物、验证与审查结论、员工逐动作授权和任务权限，然后按配置执行：

```text
提交 → 推送 → 合入 → 部署 → 结束任务
```

每个动作独立授权、独立状态、独立稳定操作身份，并引用现有 Command ledger。前一动作缺少已接纳回执、目标不一致、工作区出现计划外变化、权限被收紧或结果未知时，后续动作全部停止。确认完成的外部副作用不会因取消而自动回滚；恢复必须从耐久回执和目标系统对账后继续。

部署数字员工可以产出发布就绪报告和建议命令，但不能凭提示词直接获得部署权。实际部署只能调用已启用、作用域匹配、参数完整且已通过检查点的命令中心命令。

优点：满足逐动作自动交付，同时避免“会话完成即推送/部署”。

缺点：交付失败可能需要人工对账，完整自动化依赖目标 Git/部署系统提供可靠幂等或可查询回执。

### 12. 状态机与恢复

目标状态机保持四层独立：

- 工作执行：`queued → dispatching → active ↔ waiting_gate → workflow_completed`；没有外部动作时进入 `completed`，否则 `delivery_pending → delivered`，旁路终态为 `blocked`、`failed`、`cancelled`。
- 阶段尝试：`prepared → dispatching → active → runtime_completed`，分支为 `blocked`、`failed`、`outcome_unknown`、`cancelled`；运行完成不表达交付物已提交或已验收。
- 阶段交付物：`candidate → submitted → accepted`，分支为 `changes_requested`、`superseded`；验收决定属于交付物和工作流，不属于 Agent Runtime。
- 交付动作：`planned → authorized → executing → accepted`，分支为 `explicit_rejected`、`failed_before_write`、`outcome_unknown`。

关键恢复规则：

- 员工停用或配置变化：运行中尝试继续使用快照；新尝试阻塞并要求重新指派。
- Skill 更新或删除：运行中原生会话按冻结投影继续；新尝试必须重新解析或显式改选，历史只展示原稳定 ID 和摘要，不伪装为当前可用。
- 模型或 Runtime 不可用：启动前阻塞，不静默降级；已写出后只依据原生证据恢复。
- 工作区丢失或代码水位变化：阻塞并对账，不在另一 Checkout 冒充原现场。
- 取消：阻止新阶段和后续动作，已确认的外部副作用保持事实，不自动反向执行。
- 会话或命令结果未知：保持未知状态；只有查询到原生身份、命令回执或目标系统事实后才能追加结论。

### 13. 命令与领域事件

优先把 ZEUS-0263 的 7 个阶段写接口迁移到 Work Management Command Envelope，再允许数字员工自动调用阶段链。目标命令至少包括：

- `work_execution.create`、`work_execution.claim`、`work_execution.cancel`、`work_execution.retry`；
- `task_workflow.initialize`、`task_workflow.revise`；
- `task_stage.configure`、`task_stage.assign_employee`、`task_stage.start_attempt`；
- `stage_deliverable.submit`、`stage_deliverable.accept`、`stage_deliverable.request_changes`；
- `delivery_checkpoint.create`、`delivery_action.start`、`delivery_action.reconcile`。

主体显式区分 `user`、`worker` 和受控 `system`，作用域至少包含项目、任务、工作执行、阶段、尝试、交付物或交付动作，所有修改带 `expectedRevision`。命令接纳后用事务 Outbox 发布 `work_execution_started`、`stage_attempt_started`、`deliverable_submitted`、`stage_accepted`、`changes_requested`、`workflow_completed`、`delivery_action_outcome_unknown` 等有序领域事件。

优点：桌面、API、自动化和恢复共用同一条可审计入口；重复事件不会形成重复阶段或重复交付。

缺点：迁移期间必须兼容旧接口并逐项登记副作用；只有命令结构化而没有目标系统幂等，仍不能解决所有外部未知结果。

### 14. 自动化与运行治理

调度器只负责把时间或项目事件转成候选 `work_execution.create` 命令，不直接建立会话、推进阶段或执行交付。沿用现有来源身份去重、事件水位、租约、并发上限、链式触发深度和风暴抑制，并补充：

- 项目/员工/自动化规则三级时间、Token、工具调用和外部动作预算；超限进入 `blocked`，不得把成本推测为零。
- 静默时段、最大连续工作时长、失败冷却和同一任务单活跃工作执行约束。
- 自动认领时记录候选评分与规则命中证据；模型探索只能提出候选，认领仍通过确定性规则和命令。
- 自动推进只能使用阶段自身的验收策略；一个全局 `auto` 开关不能跳过交付物、代码审查或交付检查点。
- 高风险动作支持审批收件箱；用户批准的是具体动作、目标和冻结输入，不是无限期“完全访问”。

### 15. 任务详情体验

任务详情应以一个统一的“执行编排”区域取代彼此割裂的数字员工面板、阶段区和交付状态：

- 顶部展示任务默认员工、工作流模板、当前工作执行、总体状态、预算和阻塞原因。
- 阶段时间线逐项展示目的、负责员工及继承来源、Skill 的继承/覆盖/禁用状态、模型、有效权限、尝试、交付物和验收门。
- 每次尝试可展开上下文清单、会话、资产、验证和代码变更证据；历史版本不可被当前配置覆盖。
- 审查报告按严重度、文件和状态呈现，可一键形成正式修改请求，但不能在只读审查会话里直接改代码。
- 交付区展示每个动作的授权、目标、前置条件、Command 回执和未知结果对账入口。
- 统一审批收件箱聚合人工验收、权限冲突、未知结果与高风险动作，不让用户在多个页面寻找阻塞点。

优点：用户围绕任务、阶段和证据工作，不必理解 Provider thread 或多个内部状态表。

缺点：信息密度高，需要默认折叠运行细节、突出当前阻塞点，并通过真实 GUI 验收打磨布局，不能只以字段齐全判定可用。

### 16. 可观测、安全与度量

所有日志、事件和界面投影应贯穿 `projectId → taskId → workExecutionId → workflowId → stageId → attemptId → conversationId → submissionId → commandId/deliverableId`。审计记录包含触发来源、主体、配置修订、Skill 摘要、权限计算来源、上下文指纹、工作区水位、验收决定和交付回执。

安全上，凭据只引用受控槽位，不进入员工提示词或快照；任务文本、仓库内容、会话证据和外部资产均作为不可信数据；Skill 是显式说明资源而不是安全边界；任何工具和外部动作继续由确定性授权控制。

建议度量：工作流完成率、阶段一次通过率、返工次数、代码审查阻断/漏出率、人工门等待时长、未知结果数量与对账时长、自动交付成功率、每个已验收交付物的真实模型/工具用量、不同员工与 Skill 组合的通过率。无真实 timing 或价格覆盖时显示缺失，不推算 Token 速率或伪造费用。

### 18. 完整方案验收标准

1. 给任务指派默认员工后，Harness 能按工作流为每个阶段解析负责人；阶段覆盖员工时责任和权限来源清晰可见。
2. 员工默认 Skill、阶段 Skill 覆盖和明确禁用三种状态进入同一解析链，并在阶段尝试中冻结稳定身份和内容摘要。
3. 每个阶段尝试都能追溯员工修订、Skill、模型、有效能力清单、上下文清单、工作区水位、会话和交付物。
4. 会话完成只产生候选；交付物提交并通过阶段验收后才推进，修改请求会创建新的上游尝试并保留旧版本。
5. 代码审查在独立只读会话中同时读取确认需求、已验收计划、完整代码变更和真实验证证据，并输出可定位的结构化结论。
6. 最终工作流未验收、审查存在阻断项或验证证据缺失时，不会开始任何自动外部交付。
7. 提交、推送、合入、部署和结束任务分别校验授权与检查点；重复命令不重复执行，结果未知停止后续动作并提供对账入口。
8. 人工指派、任务池、自动化和恢复入口共用相同命令、状态机和审计事实，不存在 Renderer 或调度器旁路。
9. 任务详情能在一处展示当前阶段、员工、Skill、尝试、交付物、验收、代码审查、交付动作和阻塞原因。
10. 在独立 Test Profile、独立资料根和非主外接屏上的真实 `Zeus Test.app` 完成关键路径交互验收；正式 Zeus 实例和数据不被读取、复用或关闭。

### 19. 明确不采用的路径

- 不创建一个隐式主管 Agent 通过提示词自行选择员工、验收结果和交付动作。
- 不让一个长会话跨越全部阶段并把最后一条回复当正式交付物。
- 不以 Skill 名称、自由文本列表或提示词模拟真实 Skill 激活，也不让 Skill 获得权限。
- 不让测试或代码审查员工一边审查一边静默修复同一尝试。
- 不在会话完成后直接提交、推送、合入、部署或结束任务。
- 不在结果未知时自动重试，不用另一工作区或另一 Provider 会话冒充原执行现场。
- 不以固定产品/前端/开发/测试/部署枚举限制自定义岗位和业务领域组合。

## 首版已知边界

- 默认 Skill 必须来自真实 Zeus Skill Catalog，并由 Runtime Adapter 原生投影；它仍不是工具访问控制列表，不能因选择 Skill 就假设获得工具、凭据或额外副作用权限。
- 首版每个数字员工只有零或一个默认 Skill；多 Skill 顺序、冲突与预算编排尚未定义，不支持以文本列表替代真实激活。
- 自主探索由服务端固定为只读、关闭 Runtime 网络并只选择当前项目的任务上下文和工作区；当前 Provider 沙箱没有“仅允许读取某个项目目录”的独立文件读取 ACL，因此还需依赖数字员工指令禁止扫描其他本机目录。不能把这一点描述成操作系统级读取隔离。
- 首版不读取外部业务系统或未授权连接器；跨项目找活、连接器来源、静默时段、预算上限和自动生成独立候选任务仍属于后续扩展。
- 桌面端首版可创建、启停、立即运行和删除自动化；底层接口支持带版本的规则更新，但界面尚未提供已有规则的完整编辑器。
