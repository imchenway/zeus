## 目标

以 Codex Scheduled tasks 的产品心智为参照，把 Zeus 的自动化升级为独立、可集中管理的产品能力，同时保留 Zeus 已有的项目事件、数字员工、命令接纳和审批治理优势。本任务不是只换界面，也不接入 Gmail、Slack 或其他外部连接器。

## 已确认领域边界

### 自动化任务与员工自动化规则分开

- **自动化任务**是用户创建并长期持有的独立产品对象，保存工作内容、目标项目、触发器、会话去向、运行配置和权限边界；创建它不要求先配置数字员工。
- **员工自动化规则**继续表达“由哪个数字员工按什么条件处理什么工作”，兼容现有项目数字员工数据。
- 两者共享调度、幂等、运行账本、并发、恢复和通知基础能力，但不合并为大量可空字段组成的万能实体。

优点：用户可以获得 Codex 式独立自动化，现有数字员工语义也不会被稀释；共享底座避免复制两套可靠调度能力。

缺点：需要维护两个上层配置模型、各自的命令转换和清晰入口；迁移期比直接复用旧表更复杂。

### 两类自动化产品共享领域事件

- Zeus 只存在两类上层自动化对象：平台级独立**自动化任务**与项目内**员工自动化规则**。
- “工作流状态变更的自动化”不是第三类自动化；任务工作流、阶段、交付物、工作执行或自动化运行的状态变化都是 Zeus 领域事件，可被两类自动化对象订阅。
- 首版事件目录在现有任务创建、任务更新、任务状态变化和代码变化基础上，纳入工作流状态、阶段状态、阶段交付物验收、工作执行终态和自动化运行终态；数字员工只作为事件 actor 或后续执行主体。

优点：自动化对象数量稳定，工作流接力仍能通过确定性事件表达；同一事件水位、去重和循环治理可被两类产品复用。

缺点：事件目录与筛选字段成为正式产品契约，需要版本治理，不能直接暴露任意内部事件名或原始 JSON。

### 任务与工作流状态触发完全由用户配置

- Zeus 不预设任何任务状态或工作流状态必须触发自动化，也不按状态名称推断“开发完成”“待审查”等业务含义。
- 用户为自动化选择精确的项目状态稳定 ID、可选来源状态，以及到达该状态后执行的提示词或数字员工动作；每项规则保存状态名称快照用于审计，但匹配只使用稳定 ID。
- 自定义状态改名不改变匹配身份；状态被删除、停用或不再属于目标项目时，对应自动化进入可见阻塞，不能退回按旧名称模糊匹配。
- 运行时只执行已确认并冻结的条件与内容，不先触发所有状态事件再让模型判断是否需要工作。

优点：完全适配项目自定义状态，触发是否必要和具体内容都由用户控制，成本与因果可预测。

缺点：用户需要逐项配置业务状态；跨项目复用时必须映射各项目自己的稳定状态身份，不能假设同名即同义。

### 事件初始水位

- 新事件规则启用时把当前最新事件序号保存为初始水位，只消费确认启用之后发生的新领域事件。
- 已经处于匹配状态的历史任务、阶段、工作执行或自动化运行不自动补跑；需要处理历史集合时由用户发起独立、可预览的明确操作，不伪造成新状态变化。

优点：启用一条规则不会突然对历史项目产生批量副作用，首次运行数量可预测。

缺点：用户若确实需要历史回填，必须使用单独入口，不能依赖启用规则自动补齐。

### 自动化事件默认接力

- 自动化运行或数字员工工作执行造成的 Zeus 领域事件，默认可继续触发下一条匹配的自动化，不要求每条规则额外开启“允许接力”。
- 每次接力必须固定根因事件、父运行、actor、触发规则修订和因果深度；同一事件与规则身份仍只允许接纳一次。
- 检测到因果链中同一自动化任务与目标项目重复出现时，应形成可见循环阻塞而不是再次执行。
- 不设置最大接力段数；只要后续命中的是因果链中尚未出现的自动化，就允许继续。事件幂等、队列容量、Runtime 超时、权限和项目并发边界仍分别生效，不能把“不限段数”解释为绕过其他治理。

优点：平台自动化、数字员工和工作流状态可以真正自动接力，不需要人工逐段启动。

缺点：规则新增或修改会立刻影响后续事件链；即使重复规则循环被拦截，大量不同规则仍可能形成很长的成本与副作用链。

### 触发权威与执行主体正交

- Zeus 是唯一触发接纳权威。触发器只能是人工操作、确定性时间计划或 Zeus 领域事件。
- 数字员工可以是造成领域事件的 actor，也可以被用户选为后续执行主体，但不能绕过 Zeus 直接制造一次长期自动运行。
- 自动化的创建、修改、启用、停用和删除由用户控制；Agent 最多生成结构化草稿或变更建议。

优点：能够记录真实因果、统一去重和抑制循环触发，也不会让一次 Agent 运行自行取得长期驻留权。

缺点：所有入口都必须先形成耐久命令或领域事件，链路比 Agent 直接调用下一次运行更长。

### 自动化运行与工作执行分开

- 每次触发对每个目标项目创建一条**自动化运行**，它是计划时间、实际接纳、漏跑合并、幂等身份、权限快照、状态、结果与未读语义的权威实例。
- 直接执行模式由自动化运行关联产品会话；未来选择数字员工为执行主体时，自动化运行再关联数字员工的**工作执行**。
- 现有工作执行继续表示一次指派或员工规则触发后、跨任务工作流并冻结数字员工配置的实例，不改成数字员工、任务与工作流均可为空的万能记录。

优点：独立自动化与员工工作流各自保持真实语义，同时可以通过稳定关联共享调度和审计链。

缺点：员工执行场景会同时存在自动化运行与工作执行两层身份，查询和界面必须清楚展示两者关系。

### 项目与会话边界

- 一项自动化任务可选择一个或多个 Zeus 项目。
- 每次触发按项目分别建立运行；每个项目拥有独立会话、工作区、权限、状态和结果，不允许一个会话跨项目执行。
- 首版同时支持“每次新建独立产品会话”和“回到创建它的原产品会话”。
- 回到原会话模式只能绑定该会话所属的单个项目；多项目自动化必须按项目新建独立会话。
- 原会话被归档时，绑定它的自动化暂停并进入可见提示；不得自动取消归档或在归档会话中继续隐藏运行。用户恢复原会话或显式改为独立会话模式后才可重新启用。
- 原会话被删除、丢失或无法按 Provider 证据恢复时，自动化阻塞且不自动改建新会话，避免冒充原上下文续接。
- 自动化到期时若原会话正在执行或已有用户提交排队，自动化提交以稳定身份排在现有用户提交之后；不得抢占用户工作或并行写入同一产品会话。自动化运行保持排队状态，系统级 Runtime 超时从提交真正派发时开始计算。
- 独立会话模式创建的正式产品会话只在顶级“自动化”收件箱及对应运行详情中展示，不进入普通会话列表。自动化收件箱因此必须提供完整搜索、状态、打开、归档和历史访问能力，不能只保存一条通知摘要。
- 用户打开独立自动化运行的会话后可以正常手动追问；该会话仍留在自动化收件箱，不转入普通会话列表，也不因人工提交改变自动化来源或后续调度配置。
- 回到原会话模式沿用产品会话的正常模型历史、上下文整理和运行分段恢复语义；Provider 原生线程无法继续时可在同一产品会话内建立新运行分段，但不得偷偷切换成一条新产品会话。无法安全编译便携上下文时本次运行阻塞。

优点：自动化定义可复用，失败、权限和文件现场仍按项目隔离。

缺点：多项目会产生多条运行与结果，集中汇总需要额外投影，不能用一个长会话承载全部项目。

### 调度与恢复

- 时间调度提供常用预设和高级 RFC 5545 RRULE，并显式保存 IANA 时区。
- 自然语言只用于生成可预览、可编辑的确定性计划，不在运行时临时解释时间。
- 应用离线错过多个计划点后，按目标项目合并补跑一次；运行记录保存原计划时间、实际接纳时间和错过次数，再推进到下一个未来发生点。
- 同一自动化任务与同一项目已有活动运行时，阻塞处理策略由用户按自动化配置，不写死为一个全局行为。参考 XXL-JOB 官方模型提供“串行排队”“丢弃后续”“覆盖旧运行”三类产品选项，但按 Zeus 的会话、工作区和副作用语义重新定义状态与门禁。
- 新建自动化默认选择“串行排队”，与 XXL-JOB 默认值一致；同一自动化任务与目标项目按每个到期点正常建立 FIFO 待运行记录。
- 串行队列不是固定单槽，也不是无限队列。每项自动化配置最大堆积数量；此前“只保留一个待运行”的选择已由用户随后给出的具体规则替代。
- 最大堆积数量默认是每个“自动化任务 × 目标项目”10 条待运行，多项目队列彼此独立。
- 配置控件提供 1、3、5、10、20、50、100 快捷值并允许自定义 1–10000 的正整数；10000 是前后端共同执行的资源安全上限，不表示推荐用户形成万条积压。
- 保留在串行队列中的运行不另设最长等待时间或自动过期；轮到后正常执行。队列新鲜度只由最大堆积数量及“满时淘汰最早、保留最新”治理，不再增加第二套时效配置。
- 调度过期策略与阻塞处理策略必须分开：前者处理应用离线或调度器未及时接纳，后者处理运行实例已经活动时的新触发。官方参考：[XXL-JOB 官方文档](https://github.com/xuxueli/xxl-job/blob/master/doc/XXL-JOB%E5%AE%98%E6%96%B9%E6%96%87%E6%A1%A3.md)。
- “串行排队”达到所配最大堆积数量后，接纳最新触发并移除最早尚未开始的待运行；保留下来的队列继续按 FIFO 执行。被移除运行进入 `superseded_queue_capacity` 终态并引用替换它的新运行，不能静默删除。
- “丢弃后续”仍记录被丢弃的触发及原因，不能让计划点无声消失；“覆盖旧运行”要求先终止旧运行并清理其待运行队列，再接纳最新触发。
- “覆盖旧运行”允许用于所有权限模式，包括完全访问；不能因权限高、使用原会话或工作区不可丢弃而隐藏该选项。
- 覆盖只表示向旧运行发出终止并使最新触发取得后续执行资格，不表示撤销旧运行已经发生的文件、Git、网络或其他外部副作用。旧运行及其终止、未知结果和部分副作用证据必须保留，不得被新运行覆盖。
- 用户选择“覆盖旧运行”后，即使无法确认旧 Provider 或外部命令已经停止，也立即启动最新运行。旧运行转为结果未知并保留潜在副作用证据，新运行记录 `supersedesRunId`、终止请求身份和“可能与旧实例重叠”的明确风险事实。
- 该行为是用户为这项自动化配置的并发授权，不得把新运行已启动投影成旧运行已成功终止，也不得自动重写、删除或合并旧运行记录；此前用于讨论的“运行 24 小时等待用户”场景已作废。
- “立即运行”形成来源为人工的自动化运行，但仍服从该自动化当前冻结的串行排队、丢弃后续或覆盖旧运行策略；按钮不得隐式并发或绕过既有策略。

优点：计划可预测、可审计，并避免应用恢复时逐次补齐造成运行风暴。

缺点：RRULE、时区、耐久水位与合并补跑显著高于普通本机定时器的实现复杂度。

### Runtime 执行超时

- 自动化不增加独立超时字段，派发时读取并冻结系统级 Runtime 执行超时。
- 系统设置中的裸“执行超时秒数”应改成数值加单位的可见时长控件；单位支持分钟、小时、天，数量支持快捷值和自定义。
- 用户已确认移除当前固定 24 小时最大值。长于单次 Node 定时器能力的等待必须以绝对截止时间和分段唤醒实现，不能把整数溢出当成产品上限。
- 当前代码中的该设置并不统一约束普通 Codex 产品会话；它实际约束部分有界 Runtime 调用。后续设计不得再把它描述为“所有会话寿命上限”。

优点：全系统只保留一个可见的有界 Runtime 超时权威，自动化不会再复制一套同义配置。

缺点：移除 24 小时上限会影响所有真实消费该设置的路径，必须同时治理长期截止、重启恢复、系统休眠、资源租约和数值安全；不能只改输入框。

### 对话式创建

- 用户在产品会话中提出“定时做 X”后，模型只能生成结构化自动化草稿。
- 用户在预览中确认后才持久化并启用；修改也先显示差异预览，停用和删除仍需显式确认。
- 正式写入继续通过 Zeus 命令信封、幂等接纳和版本校验，不解析助手自然语言来冒充已创建。

优点：保留对话式创建效率，同时避免模型误解一次就形成长期后台副作用。

缺点：比 Codex 式直接创建多一个确认步骤；草稿、正式对象和过期草稿需要独立状态语义。

### Runtime 与能力配置由自动化固定

- 平台自动化任务自身固定 Provider、精确模型身份、推理等级、Fast/Standard、Skill 和 Plugin 选择，不继承目标项目默认值。
- 一项自动化覆盖多个项目时使用同一组自动化配置；项目模型或 Skill 默认值后来变化，不得静默改变后续自动化运行。
- 自动化固定的是 Skill 稳定身份，不固定旧内容副本；每次运行接纳时解析该 Skill 当前最新的已安装内容。更新 Skill 会自动影响所有后续运行，不要求逐项重新确认自动化。
- 自动化同样固定 Plugin 身份并在运行时使用当前已安装版本。Plugin 更新后若权限与连接范围没有扩大则自动生效；新增账号权限、数据范围或可写能力时，旧自动化授权失效，本次运行配置失败并通知，用户重新确认后才允许后续执行。
- 每次自动化运行接纳时仍冻结实际解析到的模型来源、能力目录事实、服务档位、Skill/Plugin 身份与内容版本/哈希证据，历史运行不被当前配置或 Skill 更新覆盖。
- 固定的精确模型被下架或当前账号无权使用时，不回退到同 Provider 或项目默认模型；该次运行以明确的模型配置失败终态结束，并发送运行失败通知。
- 固定 Fast 但模型不支持或 Provider 拒绝该档位时同样直接失败，不降为 Standard，也不永久修改自动化配置；运行保存 Provider/能力校验的真实错误并发送失败通知。
- 此类不可恢复配置失败不自动暂停自动化；后续每个到期点仍建立独立失败运行并发送通知，直到用户修改配置或手动停用。通知可以聚合展示，但不得省略各次运行事实。

优点：长期自动化跨项目行为稳定，项目设置变化不会意外扩大成本、权限或改变执行方法。

缺点：用户需要在自动化中重复配置这些字段；Skill 更新会批量改变后续运行行为，模型、Skill 或 Plugin 被移除或失效时还必须有明确阻塞或迁移语义。

### 自动化修订与已排队运行

- 正在运行的自动化运行始终使用其接纳时冻结的自动化修订，编辑自动化不得改变活动实例。
- 保存自动化修改时，如果已有未开始的排队运行，用户必须明确选择：保留这些运行并继续使用旧修订，或取消全部未开始运行，让新修订只处理之后的新触发。
- 不提供“把既有排队运行原地改用新修订”的隐式选项；取消记录保存原运行、旧修订和配置变更身份。

优点：用户可以阻止已知错误的旧配置继续排队，也不会破坏已经接纳运行的不可变审计事实。

缺点：修改表单增加一次队列处置决策；选择取消后不会自动为旧触发补建新修订运行。

### 产品入口与工作区默认

- 侧栏新增顶级“自动化”入口，承担集中收件箱、搜索、启用或暂停、下一次运行、未读结果和按项目运行记录；新能力不继续埋在单个项目设置中。
- 独立会话模式处理 Git 项目时，只读任务默认使用项目目录；允许写入时默认每次运行使用隔离 Worktree，用户可显式改为项目目录。
- 非 Git 项目无法创建 Worktree，只能使用项目目录并展示冲突风险。
- 独立写运行复用 Zeus 现有项目、环境、来源分支和任务 Worktree 契约，不新增“固定旧提交”或“沿用上一运行分支”选项。
- 每次运行按目标项目当前配置的来源分支创建新的隔离 Worktree，并冻结接纳时的本地 HEAD SHA；不自动拉取远端，也不复用上一运行尚未交付的分支或修改。
- 来源分支不存在、现场不可审计或 Worktree 创建失败时，本次运行失败并通知，不退回另一个 Checkout 冒充目标现场。
- 无变更且已终态的临时 Worktree 可走现有安全回收；存在变更、结果未知或交付未处置时必须保留并在运行详情提供明确交付/放弃入口，禁止后台直接删除。

优点：多项目自动化有稳定全局入口；写任务默认隔离，纯只读任务又不会制造大量临时 Worktree。

缺点：运行前必须可靠判定写能力和 Git 可用性；允许用户改用项目目录时仍需处理未提交修改冲突。

### 无人值守权限

- 首版独立自动化允许用户选择只读、工作区写入或完全访问；完全访问不是排除项。
- 默认权限为只读。完全访问必须由用户对每项自动化单独确认并持久授权，不能继承全局默认后静默扩大能力。
- 完全访问授权绑定自动化的提示词、项目范围、工作区策略、执行主体和权限配置；任一项变化后旧授权失效，必须重新确认。已经接纳的运行继续使用其冻结授权快照。
- 当前会话运行链中的 `full-access` 会映射为 Codex `danger-full-access` 且不逐次审批，实际覆盖本机文件、任意命令与网络能力。
- Zeus 自己编排提交、推送、合入、部署等动作时可以执行独立门禁；但完全访问会话直接运行 Shell 命令时，现有代码没有等价的强制拦截层。需求不得声称一个真正无限制的沙箱仍能被同层逐动作开关完全约束。

优点：可信的长期自动化可完成跨工作区、系统工具和网络调用，不会因后台审批卡住。

缺点：配置错误、提示词注入或模型误判可能形成任意本机与外部副作用；一旦启用，就不能依靠运行中弹窗或普通交付开关补救。

### 阻塞终态与人工恢复

- 自动化运行遇到必须由用户回答或确认的事项、缺少权限、项目不可用或其他无法无人值守推进的边界时，进入可见的 `blocked` 终态。
- 阻塞运行释放活动会话、工作区与并发租约，进入自动化收件箱并保留问题、目标、冻结输入和已发生副作用证据。
- 用户处理阻塞项后，显式创建一条引用原运行的新运行；不得复活旧运行、覆盖旧结果或自动重发结果未知的动作。

优点：活动资源有明确释放点，历史状态不可变，跨重启和升级不需要恢复一个无限期暂停的进程。

缺点：新运行需要重新编译当前现场，上次会话上下文只能通过稳定引用与摘要继承，不能假装是同一原生执行。

### 失败重试

- 每项自动化可配置安全失败的重试次数和固定间隔，默认重试 0 次；数值与单位在创建/编辑预览中显式展示。
- 只有能够证明 Provider/外部命令写出前失败，且模型和副作用均未开始的派发尝试才可自动重试。
- 写出后结果未知、明确业务失败、完全访问下可能已经发生外部副作用，或目标系统没有可审计幂等身份时，永不自动重试。
- 重试是同一自动化运行下的新派发尝试，引用失败尝试和相同冻结输入；计划运行身份、队列占位和未读结果不重复创建。

优点：短暂启动或连接故障可以自动恢复，同时不会把“任何失败”误当作可安全重发。

缺点：安全分类必须由真实写出标记与回执证明；无法证明时即使用户配置了重试次数也不会自动重试。

### 收件箱与通知

- 每项自动化分别配置成功、失败和阻塞三类系统通知开关；默认开启失败与阻塞通知，成功默认不发系统通知。
- 所有终态自动化运行无论通知开关或系统通知权限如何，都进入自动化收件箱并形成独立未读结果；支持逐条和批量标记已读。
- 通知可以按自动化聚合以降低噪音，但必须保留每条运行身份、状态和直接打开入口，不能用聚合摘要替代运行事实。

优点：高频成功任务不会默认轰炸系统通知，失败与待处理项仍能主动提醒；用户可按任务重要性覆盖默认值。

缺点：关闭某类系统通知后需要依赖收件箱未读管理；通知聚合与运行明细必须保持一致。

### 暂停、取消与删除

- 暂停自动化只阻止之后的新触发接纳，不中断活动运行，也不取消已经排队的运行；恢复后从新的调度水位继续，不补造暂停期间事件。
- 排队运行可独立取消并形成不可变取消终态。活动运行的“取消”先形成终止请求；只有取得 Provider/命令终止证据后才记为已取消，结果未知时保留未知状态。
- 删除自动化先停止未来触发并软删除配置；活动与排队运行继续按暂停语义处理，历史运行、会话、授权修订和配置墓碑不随入口删除而级联消失。

优点：调度控制与执行控制语义分开，暂停/删除不会突然制造外部结果未知。

缺点：用户若要彻底停止所有既有工作，需要在运行列表另行批量取消；删除后仍需保留可审计历史与占用空间。

### 历史保留

- 每项自动化配置运行与会话历史保留期，提供 7、30、90、180、365 天和永久，默认 90 天。
- 结果未知、未读、仍有未处置代码变更、活动 Worktree、待处理阻塞或审计保留标记的运行不参与自动清理。
- 到期清理先释放符合条件的会话大型内容与资产，再保留最小运行墓碑、触发身份、终态、时间和汇总计数，避免事件去重、因果链和报表断裂。

优点：高频自动化不会无限占用本机空间，重要自动化又可选择永久保留。

缺点：保留例外可能使实际占用超过所选天数；用户需要在收件箱处理未读、变更和阻塞项后才能完成清理。

### Token 与运行次数预算

- 每项自动化可配置单次 Token 预算、每日/月运行次数上限和每日/月 Token 预算；预算窗口使用自动化显式 IANA 时区。
- 定时、事件、自动接力和“立即运行”都计入同一自动化与目标项目的真实运行次数；安全派发重试仍属于同一运行，不重复计数。
- Token 只采用 Provider 实际报告的用量。单次模型请求可能在回报用量时已经超过阈值，因此门禁在后续模型请求或工具续跑前停止，不承诺对单次 Provider 请求做不可实现的精确截断。
- 达到预算后不派发模型或工具，建立可见的 `blocked_budget` 运行并按阻塞通知规则提醒；预算窗口恢复后只处理新的触发，不自动补跑全部被预算挡住的历史运行。
- 美元费用仅在真实价格覆盖完整时作为估算展示，并同时显示 `priceCoverage`；价格未知时显示“暂无价格”，首版不以猜测美元金额执行硬门禁。

优点：高频、长上下文和自动接力都有可配置的成本边界，且不依赖不完整价格表。

缺点：Token 预算无法在 Provider 单次请求内部精确中止，用户仍可能看到少量越界；预算配置增加创建自动化的复杂度。

## 已排除范围

- Gmail、Slack、GitHub 或其他外部连接器事件。
- 数字员工自行创建并启用长期自动化。
- 单次会话跨多个项目工作区执行。
- 依赖模型在每次运行时重新解释自然语言时间。
- 用 Renderer 本地定时器、Agent 直接调用或助手文字绕过 Core 命令接纳。

配套的产品经理优先可视化见 [ZEUS-0374 自动化开发设计](./ZEUS-0374_自动化开发设计.html)。图示帮助理解主链路和状态，不替代本文档中的字段、事务与失败语义。

### 当前实现基线与必须拆开的边界

当前代码已经具备可复用基础，但没有独立自动化任务这一领域对象：

- `packages/storage/src/digitalEmployeeStore.ts` 的 `digital_employee_automations` 强制绑定单个 `project_id` 和 `employee_id`；触发后创建的 `digital_employee_executions` 又强制绑定 `task_id`。它只能继续表示**员工自动化规则**，不能被扩成项目、员工和任务均可为空的万能表。
- `packages/local-server/src/digitalEmployeeOrchestrator.ts` 已有 10 秒轮询、租约、计划点和事件回执，但当前硬编码最大自动化链深度 4，且触发动作最终都落为任务与员工工作执行。新能力只能复用其耐久调度经验，不能照搬对象语义。
- `packages/storage/src/conversationStore.ts` 的产品会话没有来源归属字段，普通未归档列表会读出所有会话。独立自动化会话若只靠标题或前端临时过滤，必然可能泄漏进普通会话列表。
- `packages/local-server/src/codexDynamicToolApplication.ts` 当前只处理完整工具结果读取和内置浏览器。对话式创建自动化需要新增 Zeus 所有的草稿工具，但该工具只能形成草稿，不能启用正式自动化。
- `packages/local-server/src/localServerSettingsNormalization.ts` 将 Runtime 执行超时限制在 60–86400 秒，`WorkspaceView.tsx` 仍展示裸秒数并以 24 小时裁剪；这与已确认的长时运行语义冲突。
- `packages/storage/src/conversationExecutionStore.ts` 已按模型请求保存 Provider 实际 Token 用量，可作为自动化预算的事实来源；预算不能另造一套估算 Token 真相。
- `apps/desktop/src/main/systemNotifications.ts` 已有本机实时事件转系统通知的桥，自动化只需增加运行终态事件映射和稳定去重键。

设计结论：新增独立自动化领域模型和共享调度内核，保留现有数字员工对象；两者共享触发接纳、事件游标、因果去重和调度唤醒能力，但分别写入自动化运行与员工工作执行。

### 目标架构

按权威边界拆成六层：

1. **命令接纳层**：所有创建、修改、启停、删除、立即运行、取消、已读和人工恢复动作先通过 Work Management 命令信封、幂等键与 `expectedRevision`。
2. **定义与修订层**：自动化任务保存当前状态，任何执行配置变化都生成不可变修订；已接纳运行永远引用旧修订。
3. **触发与调度层**：统一接纳人工、RRULE 时间点和 Zeus 领域事件，维护每个“定义 × 项目”的 lane、水位、计划点、回执和因果链。
4. **运行编排层**：按阻塞策略和预算原子创建自动化运行，再解析模型、Skill、Plugin、权限、工作区和会话现场。
5. **执行适配层**：独立自动化直接派发产品会话；员工规则适配器继续创建 `digital_employee_execution`。适配器不能自行制造触发事实。
6. **投影层**：顶级自动化工作区、自动化收件箱、运行详情、未读计数、系统通知与保留清理只读权威表或其可重建投影。

优点：调度、幂等和因果规则只有一个实现，同时保持两类产品对象的真实语义。

缺点：共享调度层需要稳定的目标适配协议，迁移期会同时存在旧数字员工扫描逻辑和新调度内核，必须按阶段切换唯一 owner，不能双触发。

### 存储模型

#### 独立自动化领域表

新增表由 `work_management` 拥有，并登记到 `packages/storage/src/tableOwnership.ts`：

| 表 | 关键字段 | 权威语义 |
| --- | --- | --- |
| `automation_tasks` | `id`、`name`、`state`、`current_revision_id`、`revision`、`deleted_at`、创建/更新时间 | 当前可编辑入口、启用/暂停/软删除状态，不保存可变执行快照 |
| `automation_task_targets` | `id`、`automation_id`、`project_id`、`source_branch`、`workspace_policy`、`original_conversation_id`、`next_occurrence_at`、`event_cursor`、`enabled_watermark` | 每项目 lane 与现场选择；`UNIQUE(automation_id, project_id)` |
| `automation_task_revisions` | `id`、`automation_id`、`revision_number`、`config_json`、`config_sha256`、`created_by_command_id`、`created_at` | 归一化后的不可变完整配置，队列与历史只引用它 |
| `automation_full_access_grants` | `id`、`automation_id`、`bound_config_sha256`、`permission_fingerprint`、`granted_by`、`granted_at`、`revoked_at` | 每项自动化的持久完全访问授权；配置指纹变化立即失效 |
| `automation_runs` | 见下方运行字段 | 每次触发 × 项目的产品运行事实，也是收件箱条目 |
| `automation_run_attempts` | `id`、`run_id`、`attempt_number`、`status`、`write_state`、`provider_request_identity`、开始/结束/错误 | 同一运行下的安全派发重试与写出证据 |
| `automation_run_observations` | `id`、`run_id`、`kind`、外部操作/Provider 身份、`payload_json`、`observed_at` | 运行终态后的迟到回执、残留进程和终止证据；只追加，不改写原终态 |
| `automation_run_usage` | `run_id`、`model_request_id`、Token 分项、`estimated_usd`、`price_coverage`、`occurred_at` | 从 `conversation_model_requests` 事实投影；`model_request_id` 唯一，禁止重复计费 |
| `automation_notification_outbox` | `id`、`run_id`、`kind`、`dedupe_key`、`eligible`、`status`、时间 | 系统通知可恢复投递；收件箱未读不依赖通知是否成功 |

`automation_task_revisions.config_json` 使用版本化严格结构，至少包含：提示词、目标项目稳定身份、触发定义与 IANA 时区、会话模式、执行主体、Provider/精确模型/推理等级/Fast、Skill 与 Plugin 稳定身份、权限、工作区策略、阻塞策略与最大堆积、重试、预算、通知和保留期。服务端归一化后再计算 `config_sha256`，不对 Renderer 原始 JSON 直接哈希。

`automation_runs` 至少保存：

- 身份：`id`、`automation_id`、`automation_revision_id`、`target_id`、`project_id`。
- 触发：`trigger_kind`、`trigger_identity`、`scheduled_for`、`accepted_at`、`missed_count`、`manual_actor`。
- 因果：`causal_chain_id`、`parent_run_id`、`root_event_id`、`supersedes_run_id`。
- 冻结配置：`runtime_snapshot_json`、`permission_snapshot_json`、`capability_snapshot_json`、`source_head_sha`、`deadline_at`。
- 执行关联：`conversation_id`、`work_execution_id`、`workspace_id`、`environment_id`、`active_attempt_id`。
- 状态：`status`、`terminal_reason`、`error_code`、`error_message`、`termination_request_id`、`may_overlap_previous`、开始/完成时间。
- 收件箱与保留：`read_at`、`audit_hold`、`retention_eligible_at`、`large_assets_released_at`、`tombstoned_at`。

关键索引与约束：

- `UNIQUE(automation_id, project_id, trigger_identity)` 保证同一触发不会重复建运行。
- `INDEX(status, accepted_at)` 支持队列恢复；`INDEX(automation_id, project_id, status, accepted_at)` 支持 lane 内 FIFO 和容量淘汰。
- `INDEX(read_at, completed_at)` 支持收件箱未读；`INDEX(retention_eligible_at)` 支持清理。
- 原会话模式数据库约束或事务校验必须保证恰好一个 target，且 `original_conversation_id` 属于同一项目。
- 独立会话通过会话来源字段关联运行，不允许靠可变标题反查。

#### 会话来源归属

为 `conversations` 增加：

- `origin_kind`：`ordinary | automation_run | digital_employee_execution | system`，历史数据迁移为 `ordinary`。
- `origin_id`：自动化运行或工作执行稳定身份。
- `listing_scope`：`ordinary | automation_inbox | hidden_system`。

普通会话查询必须显式限定 `listing_scope = 'ordinary'`；自动化收件箱按 `origin_kind = 'automation_run'` 与运行表读取。用户在自动化会话手动追问只新增提交，不修改 `origin_kind`、`origin_id` 或 `listing_scope`。会话归档同样只改变归档状态，不改变来源归属。

优点：来源归属是可审计事实，所有入口、搜索和通知都能使用同一规则。

缺点：所有旧会话列表与归档查询都必须补显式 scope，否则迁移后可能漏显或混显。

#### 共享调度基础表

共享调度基础设施不把两类产品对象合并：

| 表 | 作用 |
| --- | --- |
| `automation_domain_events` | 版本化统一事件流：`sequence`、`event_id`、`event_type`、项目/资源、actor、payload、`causal_chain_id`、来源事实身份；来源身份唯一 |
| `automation_scheduler_lanes` | `owner_kind`、`owner_id`、`project_id`、下一计划点、事件游标、租约与恢复水位；owner 为 `automation_task` 或 `employee_rule` |
| `automation_trigger_receipts` | 触发接纳幂等账：owner、项目、触发身份、接纳结果、目标类型与目标 ID |
| `automation_causal_chain_members` | `chain_id`、`automation_id`、`project_id`；唯一约束用于无深度上限的循环拦截 |

`automation_domain_events` 是从现有 `task_events`、工作流/阶段事实、工作执行终态、代码变更事实与自动化运行终态构建的耐久调度事件流。每个来源适配器以稳定 `source_kind + source_id` 写入；先写来源事实、后投影的链路允许延迟但不能丢失。自动化运行终态与其事件可在同一数据库事务写入。

不直接复用现有 `event_log`：它目前只有类型、payload、source 和时间，缺少项目、资源、全局顺序、来源唯一键、因果链及版本，无法承担调度游标和循环检测权威。

### 自动化运行状态机

主状态集合：

- 非终态：`queued`、`dispatching`、`running`、`cancelling`。
- 成功终态：`succeeded`。
- 失败或人工处理终态：`failed`、`blocked`、`outcome_unknown`、`cancelled`。
- 未执行终态：`discarded_busy`、`superseded_queue_capacity`、`superseded_cover`。

预算阻塞使用 `status = 'blocked'` 与 `terminal_reason = 'blocked_budget'`，界面标签仍展示“预算阻塞”。配置、权限、原会话、项目或用户输入阻塞分别使用稳定 `terminal_reason`，避免为每种原因不断扩大状态枚举。

允许迁移：

- `queued → dispatching → running → succeeded | failed | blocked | cancelling | outcome_unknown`。
- `dispatching → queued` 只允许发生在写出前可证明安全且仍有重试额度时，并创建新 attempt；否则进入终态。
- `queued → cancelled | discarded_busy | superseded_queue_capacity | superseded_cover`。
- `cancelling → cancelled` 需要终止证据；无法确认则 `cancelling → outcome_unknown`。
- 所有终态不可逆。人工解决阻塞、人工重跑或恢复只创建引用旧运行的新运行。

运行终态与会话轮次终态不是同义：一次会话请求结束后，编排器还需核对工作区、Token、阻塞请求和交付现场，再以单一事务结算自动化运行。

`outcome_unknown` 只释放 scheduler lane 的活动占位，不等于底层 Provider、Shell 或外部进程已经退出。执行宿主继续按原外部操作身份观察残留实例；之后到达的退出码、Provider 完成事件或终止确认追加到 `automation_run_observations`，但不把原运行从未知改写成成功、失败或已取消。运行详情同时展示原终态与迟到证据。

### 触发接纳事务

#### 时间触发

1. 解析并校验 RFC 5545 RRULE 与 IANA 时区，预先计算每个 target 的 `next_occurrence_at`。
2. 唤醒时以 lane 租约重新读取当前水位，不相信内存定时器。
3. 如果当前时间跨过多个计划点，只生成一个 `trigger_identity` 为 `schedule:<first-missed>:<last-missed>` 的补跑，保存 `scheduled_for` 和 `missed_count`。
4. 在同一事务推进 `next_occurrence_at` 到严格大于当前时间的下一点、写回执并按阻塞策略处理运行。
5. 应用重启、休眠唤醒或系统时间跳变都走相同的水位重算，不使用“错过一次就循环补齐”的内存逻辑。

#### 事件触发

1. 启用或恢复时将 target 的 `enabled_watermark` 和 `event_cursor` 指向当前事件流尾部，只消费之后的事件。
2. 读取游标后的有界批次，按事件类型、稳定状态 ID、from/to、项目和用户配置过滤。
3. `trigger_identity = event:<event_id>:<automation_id>:<project_id>`；插入回执和运行必须在同一事务。
4. 由自动化运行产生的事件沿用 `causal_chain_id`。尝试插入 `automation_causal_chain_members` 时若 `(chain_id, automation_id, project_id)` 已存在，则记录循环拦截回执和 `blocked` 运行，不再派发。
5. 不设置链深上限；不同自动化可继续接力，但每次仍受预算、队列、超时和幂等门禁。

#### 人工立即运行

由命令生成稳定 `manual:<command_id>:<project_id>` 触发身份，使用当前修订并服从同一阻塞策略。多项目立即运行在一个命令内为每个项目独立接纳，返回逐项目结果，不用一个 HTTP 成功掩盖局部失败。

### 队列与阻塞策略算法

策略在 `automation_id + project_id` lane 的数据库事务内串行计算：

- **串行排队**：若无活动运行则入队并可派发；有活动运行则 FIFO 入队。若待运行数已达上限，先把最早 `queued` 运行更新为 `superseded_queue_capacity` 并引用新运行，再接纳最新运行。活动运行不计入最大堆积数量。
- **丢弃后续**：存在 `dispatching | running | cancelling` 或 `queued` 时仍创建运行事实，但直接终态 `discarded_busy`；没有活动或队列才正常接纳。
- **覆盖旧运行**：把所有 `queued` 更新为 `superseded_cover`，向每个活动运行写入终止请求并尝试停止。最新运行立即取得派发资格；不能确认旧实例停止时，将旧运行结算为 `outcome_unknown`，新运行置 `may_overlap_previous = 1` 后照常启动。

覆盖策略有意允许旧实例与最新实例重叠，尤其在完全访问下风险最高。UI、通知和详情必须显示“旧运行未确认停止”，不得用绿色“已覆盖”掩盖结果未知。

### 配置修订与授权

- 每次创建或编辑都先构造规范化草稿与差异预览；用户确认后以一个 Core 命令写入新修订并切换 `current_revision_id`。
- 若有未开始运行，保存命令必须携带 `queuedRunDisposition = keep_old_revision | cancel_unstarted`；缺失即拒绝。
- `keep_old_revision` 不改队列；`cancel_unstarted` 在同一事务把旧队列终态化，再切换修订。
- 完全访问授权的绑定指纹由提示词、项目范围、工作区策略、执行主体和权限配置的规范化子集计算。任何子集变化都使旧 grant 不匹配。
- Skill 修订只保存稳定 Skill ID；派发时解析最新安装内容并把版本/哈希写入运行快照。
- Plugin 保存稳定身份；派发时比较当前权限与连接范围指纹。能力不扩大时使用新版本；扩大时本次运行 `blocked`，直到用户重新确认。
- 精确模型、Fast 或账号能力不可用时运行 `failed`，不回退、不自动暂停定义。

### 会话与派发设计

#### 独立会话模式

1. 运行派发前完成项目、来源分支、工作区、模型、Skill/Plugin、授权和预算预检。
2. 使用由 `run_id` 派生的稳定 `conversation_id` 和 `submission_id`，通过现有会话命令/Provider 写出生命周期接纳；重启恢复不得生成第二条会话。
3. 新会话写入 `origin_kind = automation_run`、`origin_id = run_id`、`listing_scope = automation_inbox`。
4. 会话允许用户手动追问；所有后续提交仍在原产品会话排队，但不会改变来源归属、运行事实或自动化定义。
5. 自动化运行只覆盖首次自动派发及其结算；用户在运行已终态后追问形成普通会话轮次，不复活旧运行。运行详情展示“自动化结果”与“后续人工对话”的边界。

#### 回到原会话模式

1. 定义保存时校验单项目和会话归属；运行接纳时再次校验未归档、未删除和可恢复证据。
2. 使用现有 `conversation_submissions` 队列，把自动化提交排在已接纳用户提交之后；自动化 `deadline_at` 从 submission 实际转为 `dispatching` 时计算。
3. Provider thread 不可续用时走现有同一产品会话的新 runtime segment；便携上下文不完整则运行 `blocked`。
4. 会话归档导致定义暂停并提示，恢复会话后由用户显式恢复自动化；删除或不可恢复导致每次运行阻塞，不偷偷改用独立会话。

#### 等待用户输入与审批

自动化派发不允许长期悬挂 `request_user_input`、文件审批或权限审批。Provider 一旦请求人工动作，编排器保存问题与已发生副作用证据，终止或释放当前执行，结算运行为 `blocked`。用户从收件箱解决后显式创建新运行，引用旧运行和回答摘要。

### 工作区与 Git 生命周期

- 只读独立自动化默认使用项目目录，权限仍由只读沙箱约束。
- Git 项目的工作区写入或完全访问默认创建每次运行独立 Worktree。运行目标冻结来源分支当前本地 HEAD；不得自动拉远端。
- 自动化 Worktree 使用独立记录，不能伪造 `task_id` 写入 `task_workspaces`。新增 `automation_run_workspaces`，字段复用现有 workspace 身份、来源分支、SHA、仓库、路径、状态和清理证据；底层继续调用 `@zeus/git-core` 的安全 worktree 能力。
- 多仓项目为同一运行建立 environment 与逐仓 workspace，保持现有相对布局和 writable roots 校验。
- 用户明确选择项目目录时，派发前记录 Git 状态摘要和风险确认；运行不能把既有用户改动算成自己的成果。
- 无变更且终态明确时可进入安全回收；有变更、交付未完成、结果未知或审计 hold 时保留。交付/放弃继续走显式 Work Management 命令，不在后台自动 commit、push、merge 或删除。

优点：复用成熟的 Git 准备与恢复实现，又不污染任务工作区语义。

缺点：需要新增自动化 workspace 记录与现有 Git 核心的适配层，不能仅给任务表塞一个虚拟任务 ID。

### Runtime 超时实现

- 系统设置仍持久化规范化的 `executionTimeoutSeconds`，以保持现有消费者兼容；Renderer 改为“数值 + 分钟/小时/天”并提供快捷值和自定义值。
- 后端移除 86400 秒产品上限，要求正整数、安全整数并在实际派发时校验 `now + duration` 可表示；极端不可表示值返回明确校验错误，不伪装成固定天数上限。
- 自动化运行在真正派发时保存绝对 `deadline_at`。所有恢复、休眠唤醒和取消判断都比较当前时间与截止时间。
- 内存等待采用分段唤醒，每段不超过当前 Node 计时器安全范围；每次唤醒重新读耐久状态。不得将一个超长 `setTimeout` 当作权威。
- 同时审计 `taskRuntimeOperations.ts`、`conversationApplicationOperations.ts` 和环境变量 `ZEUS_RUNTIME_TIMEOUT_SECONDS` 的真实消费者；没有使用该设置的普通产品会话不得在文案中声称受此超时控制。

### Token 与次数预算实现

- 接纳触发时，以自动化时区计算日/月窗口，在同一事务统计已接纳运行次数；超过次数预算仍写 `blocked_budget` 运行，不派发。
- 派发前读取本运行及窗口内已确认 Provider Token；达到阈值时阻塞。每个模型请求完成后，从 `conversation_model_requests` 以唯一 `model_request_id` 投影到 `automation_run_usage`。
- 在下一次模型请求或工具续跑门禁重新检查预算。单个正在进行的 Provider 请求可能越界，记录实际超额但不谎称精确截断。
- 安全 retry 不增加运行次数，但其模型请求若真实发生仍计 Token；理论上的“写出前失败”通常没有 Token 事实。
- USD 仅聚合 `usage_complete` 且价格覆盖完整的记录；同时返回 `priceCoverage`，不完整时显示“暂无价格”，不参与硬门禁。

### 对话式草稿工具

新增命名空间为 `zeus` 的动态工具 `propose_automation_task`：

- 输入是版本化结构：名称、提示词、项目、触发、会话模式、Runtime、权限、队列、预算等；服务端严格校验并创建短期草稿。
- 工具返回 `draft_id`、规范化预览、警告和缺失字段，不返回“已创建/已启用”。
- Renderer 在对应会话显示正式预览；用户点击确认后才发送 `automation_task.create` 命令。
- 草稿绑定来源会话、turn、tool call、配置哈希和过期时间；重复工具调用按稳定 call identity 幂等。
- 修改建议同样只创建 diff 草稿。Agent 无直接 pause/delete/enable 动态工具。

需要把工具 spec 注入 Codex 和其他支持结构化工具的 Agent 路由；不支持时保留普通 UI 创建，不从助手正文正则解析。

### 顶级自动化工作区

为 `MainNavTarget` 增加 `automations`，hash/deep link、query state、Workspace chrome 和初始化路由同步扩展。界面采用两个主视图：

1. **自动化任务**：列表显示启用状态、触发摘要、目标项目、阻塞策略、下一次运行、最近结果和未读数；详情页分为目标与提示词、触发、会话与工作区、Runtime 与能力、权限、队列与重试、预算、通知与保留八组。
2. **运行收件箱**：默认未读优先，支持搜索、项目/状态/来源过滤、批量已读；一行代表一个运行，不把多项目结果合成无身份摘要。运行详情可打开自动化会话并继续追问，但会话始终留在收件箱。

现有项目设置中的 `ProjectDigitalEmployeesPanel` 保留，并把“自动化”文案明确改为“员工自动化规则”；首版不把规则编辑器迁入顶级入口。顶级入口可提供“员工规则结果”来源过滤或跳转，但不能把两类定义混成一个编辑表单。

关键可访问性要求：

- 所有状态不能只靠颜色，必须有文本与图标；未知结果和完全访问使用明确风险文案。
- 队列策略、覆盖风险、完全访问授权和队列修订处置使用可聚焦说明并关联 `aria-describedby`。
- 列表、筛选、批量已读、对话打开和对话返回支持键盘；焦点从详情关闭后回到原运行行。
- 时间同时展示自动化时区和用户本地相对时间，屏幕阅读器获得完整绝对时间。

### Scheduler 与进程生命周期

新增 `AutomationSchedulerApplication`，由 `localServerPlatformRoutes.ts` 组合根在非 `readOnlyValidation` 模式启动，并在服务关闭时 await `close()`：

- 单实例进程内最多一个 active tick，但数据库 lane 租约仍是跨重启权威。
- 唤醒来源为短周期兜底 tick、mutation `kick()`、事件投影完成和活动运行终态；不得只依赖 10 秒轮询。
- 每个 tick 依次完成：恢复过期租约、投影事件、接纳到期触发、按 lane 派发、结算 attempt、生成通知、执行有界保留清理。
- 外部 Provider、Git 或命令调用必须继续通过带 write marker 的外部操作；数据库只凭超时不能推断外部写未发生。
- 旧数字员工调度迁移时使用 feature-state 单一切换：先让共享内核只观测对账，再停止旧 rule 扫描 owner，最后启用 employee adapter。任何阶段都不能两边同时创建 execution。

### 失败、恢复与可观测性

每次触发和派发至少记录以下身份：automation、revision、target/project、trigger、run、attempt、conversation/submission、workspace、command/outbox、Provider thread/turn/request、causal chain。日志与 UI 错误码使用稳定前缀：

- `ZEUS_AUTOMATION_CONFIG_*`
- `ZEUS_AUTOMATION_TRIGGER_*`
- `ZEUS_AUTOMATION_QUEUE_*`
- `ZEUS_AUTOMATION_PERMISSION_*`
- `ZEUS_AUTOMATION_WORKSPACE_*`
- `ZEUS_AUTOMATION_DISPATCH_*`
- `ZEUS_AUTOMATION_BUDGET_*`

关键指标：到期接纳延迟、漏跑合并数、队列深度/淘汰数、覆盖重叠数、循环拦截数、配置失败率、预写安全重试数、未知结果数、未读数、保留例外占用和 Token 预算阻塞数。

启动恢复顺序：先冻结/核对 in-flight 外部操作和 Provider 状态，再恢复 lane 租约与队列。无法确认写出结果的 attempt 进入 `outcome_unknown`，不得因重启自动重发。

### 数据迁移与分阶段实现

#### 阶段 A：存储与只读投影

- 新增 schema、repository、严格归一化、table ownership 与读取 API。
- 为历史会话补 `origin_kind = ordinary`、`listing_scope = ordinary`，先对普通列表做双读对账，再切成显式 scope。
- 建立统一事件投影和 scheduler lane，但不派发新自动化。

退出条件：迁移可重复执行；旧会话数量、归档数量和项目归属对账一致；事件来源唯一且游标可重建。

#### 阶段 B：命令与独立自动化手动运行
