# ZEUS-0376 长消息完整展示

## 目标

会话中的长消息不能把 Snapshot V2 的有界预览伪装成最终回答。可见消息存在完整正文句柄时，应自动按页读取并展示全文；只有完整性可确认后，才把消息标记为已完整加载。

- 分支：`zeus/ZEUS-0376-task-01`
- 基线：`4772d9b57b13661db4386325dca885fb11a6a532`
- 用户截图对应会话 `conversation_c944a3f347120499f1daec1e`、轮次 `01a0481d-0d1d-7f50-b95f-3f80dca1f5b2`。Provider 最终消息共 5,635 个字符、6,517 个 UTF-8 字节，内容完整；正式数据库中的模型历史和 Provider 投影也保存了完整正文。
- 正式会话热缓存只保存了前 2,048 个字符的 Snapshot V2 预览，截断位置正好停在截图中的“4. 精确定位”。因此不是模型提前停止，而是客户端把预览当成了最终展示。
- 现场正式应用为 0.3.69；其包内没有当前长消息续载状态与完整正文句柄逻辑。当前分支已经包含 ZEUS-0369 的后续修复，因此本任务不重复实现第二条长消息加载链路。

以上正式数据与应用包仅做只读检查，没有修改、复制或续接正式会话。

## 方案与取舍

### 采用：保留有界预览，按句柄读取全文

- 优点：首屏快照体积仍受控；正文按需加载；现有加载、失败重试、同句柄去重和缓存保全语义都可复用。
- 缺点：长消息首次可见时存在一次额外读取；读取失败时需要保留预览并明确提示用户重试。

### 不采用：直接扩大或取消 2,048 字符预览上限

- 优点：实现表面上更简单，短期内减少一次正文请求。
- 缺点：会放大每次快照、热缓存和 IPC 负担，长会话首屏成本不可控，而且仍不能证明任意长度消息一定完整。

### 阶段 2：完整性收口

- 在未发生脱敏替换的正文上，分页结束后重新计算拼接文本的 Unicode 码点数和 UTF-8 字节数；任一结果与存储端声明不一致时拒绝写入完整正文状态。
- 发生脱敏替换时不使用原文总长度校验脱敏后的展示文本，因为替换会合法改变字符数和字节数；仍保留原有的句柄 revision、结构代次、逐页总量一致性和 offset 前进校验。
- 为已有长消息真实 DOM fixture 增加独立查询入口，避免整套动效 QA 同时挂载造成浏览器控制面过载；该入口只影响开发态视觉验收，不进入正式产品导航。
- 本次不调整 2,048 字符预览预算，不修改数据库、Local Server 协议或 Markdown 渲染上限。
