## 已确认现场根因

### 全局消息发送失败

1. 正式 Zeus Provider 使用 Codex CLI `0.150.1`，模型预算回退要求 `models_cache.json.client_version` 与当前 CLI 版本完全一致。
2. Computer Use 的 `node_repl` 配置把正式 `/Users/david/.zeus/providers/codex` 作为 `CODEX_HOME` 传给工具子进程。
3. `node_repl` 启动了 ChatGPT 内置 Codex `0.150.0-alpha.8`；该进程打开正式 Provider 的状态、日志、队列数据库，并持续用 `client_version=0.150.0` 覆盖共享模型缓存。
4. 2026-08-28 19:45 的三条消息均在 Provider 写入前以 `ZEUS_CONTEXT_MODEL_WINDOW_UNAVAILABLE` 失败。重启只暂时由正式 CLI 刷新缓存，不能消除后续再次覆盖。

### 重启后部分会话无法继续

1. “自动化需求”会话原 turn 停在 `request_user_input`，Provider JSONL 没有终态。
2. 19:46:39 的完整重启流程执行 `execution_host.stop_active`，停止一个活动 turn 并关闭一个等待回答请求；这不是用户点击会话内停止按钮。
3. 正式 0.3.69 的 `app.asar` 尚未包含主线 ZEUS-0371 的 `provider_stop_pending` 恢复状态机，因此重启后新消息被保存为本地 `recovery_required`，没有写入 Provider。
4. 现场已经积累 `继续` 和三条 `？？？`，均无 `providerTurnId`；这些历史消息不得自动全部重放。

### `v0.3.70` 后“自动化需求”仍无法继续

1. 正式数据库中的会话 `conversation_00cbecfa03dced4f0293afcb` 绑定 Provider thread `01a047cf-cce1-75e1-be63-59b2280770b3`。原 turn 已在 Zeus 本地记为 `interrupted`，但对应 `request_user_input` 的最后一个问题仍完整持久化：独立会话模式处理 Git 项目时默认使用哪个工作区。
2. Remote Control app-server daemon 跨 Zeus Core 重启继续存活，并继续打开原 thread 的 JSONL。权威 `thread/read` 返回 `active + waitingOnUserInput`；Provider JSONL 没有该问题的 `function_call_output`，证明 Provider 仍在等待旧请求。
3. 旧 Core 退出时把请求标为 `ZEUS_FORCED_QUIT_INTERRUPTED`，新 Core 因此不再拥有原 server request 的连接内身份。Codex 官方 App Server 协议说明 `thread/read` 只读线程状态，`thread/resume` 才加载线程；`item/tool/requestUserInput` 的答复属于原 server request，原请求被中断或清除后只能通过新的显式续接恢复，不能把普通聊天消息冒充为旧请求答复：<https://learn.chatgpt.com/docs/app-server>。
4. 运行管理器的 `interruptTurn` 只在当前连接观察过 `turn/started` 时才真正发 `turn/interrupt`；重启后的新连接没有该内存记录，于是只登记 `pendingInterrupt` 就返回成功。停止恢复层随后把“没有实际发出的中断”误判为已接纳。
5. 后续 `thread/resume` 重新碰到 daemon 内仍未解决的询问，daemon 因线程已有 writer 拒绝新连接。现场后续三条 `继续`、`继续`、`？？？` 均无 `providerTurnId`，分别停在 `interrupted` 或 `runtime_rejected`，没有写入 Provider。

## 实施决策

1. 为受管工具子进程建立独立 Codex Home，不复制或借用正式 Provider 的认证、会话、状态数据库和模型缓存。
2. 模型上下文预算在 Codex generation 初始化时一次性解析并绑定，不在每次发送时重新读取可被其他进程改写的共享文件。
3. 完整重启发现活动工作时必须显示精确数量和中断影响，默认取消；只有用户明确确认后才调用停止命令并安排重启接力。
4. 沿用主线 ZEUS-0371 的原 thread/turn 停止核对。单条、明确未写入 Provider 的恢复消息可在确认终态后续发一次；多条消息保持暂停，逐条由用户重试或取消。
5. 已有 Provider 写入或送达结果不确定的消息继续禁止自动重发。
6. 跨重启连接执行精确 turn 中断时，若当前连接没有观察到 `turn/started`，先用 `thread/read` 核对 daemon 权威状态；线程确为活动态时立即发送 `turn/interrupt`，仅在线程非活动且本地 `turn/start` 可能仍在途时保留原有 `pendingInterrupt` 竞态处理。
7. 只在“最新失败请求为 `request_user_input`、属于最新 Provider turn、同一 thread 返回 `waitingOnUserInput`、且没有其他活动 turn”时识别遗留交互。先真正中断并确认原 turn 终态，再把原问题恢复为交互恢复检查点；用户作答后由现有机制生成一条明确的新续接消息。
8. 遗留期间明确未送达的多条普通消息继续进入 `recovered_unsent`，逐条重试或取消；恢复原问题卡不消费、不重排、也不自动发送这些消息。

### 优缺点

- 工具 Home 隔离可以消除跨进程写污染；代价是依赖共享 Provider 认证的旧工具会独立失败，不能再以污染正式状态作为隐式回退。
- generation 级预算让活动世代不受外部缓存变化影响；代价是模型能力变化需要激活新世代。
- 重启确认消除静默中断；代价是存在活动工作时完整重启多一步确认，且不承诺活动 Core 的无损热替换。
- 多条未发送消息逐条处理可以避免重复催问；代价是用户需要手动处理队首消息。
- 先停止遗留 turn、再恢复问题卡，避免跨连接伪造 JSON-RPC 答复；代价是续接会形成一个新的 Provider turn，审计记录会明确标注它来自交互恢复，而不是伪装原 turn 从未中断。
- `thread/read` 增加一次控制面读取，可以区分“本地 start 竞态”和“旧连接活动 turn”；代价是中断路径多一次有界只读 RPC，但不会扩大普通发送热路径。
