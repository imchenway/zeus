## 用户确认的问题与产品结论

旧实现把普通指派强制映射到固定三阶段，并通过阶段位置和尝试次数决定员工接下来做方案、开发或审查。这导致配置了部署命令的员工仍从方案开始，失败后的第三次指派甚至在没有开发代码时直接进入代码审查。

产品结论如下：

- 指派次数和尝试次数只记录历史，永不决定员工行为。
- 数字员工必须明确配置一个主执行入口：Agent 或 Command；岗位名称不参与入口推断。
- 一次指派创建一份独立工作责任。多个员工可以在同一任务并行工作；无真实依赖时不显示连线。
- Agent 会话完成只提交正式交付物，管理者验收后工作项才完成；要求修改创建同一工作项的新运行并保留旧版本。
- Command 人工指派在最后一步确认并直接启动，不创建模型会话；自动化只创建命令确认待办。
- 提交、推送、合入、部署和任务完结只是权限上限或显式管理动作，不再是会话结束后的隐藏路线。
- 新入口不改写旧执行、旧阶段、旧尝试、旧交付物和历史授权。

## 领域模型

### 数字员工能力

项目数字员工保存版本化 `EmployeeEntrypointV2`：

- Agent：提示词、Agent Runtime、模型策略、多个允许的 Skill、权限工具上限。
- Command：命令中心稳定 `commandId`。参数仍由命令定义拥有，敏感值不进入工作项快照、日志或上下文。

旧员工迁移规则：普通员工显式迁移为 Agent；同时存在 Agent 配置和 `deployCommandId` 的员工标记为“需要选择主入口”；部署模板默认为 Command，但命令未配置前不可指派。

### v2 权威记录

| 记录 | 责任 | 关键边界 |
| --- | --- | --- |
| `task_work_items` | 管理者可见的独立工作责任 | 指派与重试次数不参与行为判断 |
| `task_work_runs` | 一次真实尝试 | 冻结员工修订、入口、模型、Skill、权限与上下文；`conversationId` / `commandRunId` 互斥 |
| `task_work_deliverables` | 版本化正式产物 | 正文由 Artifact 承载并以内容哈希校验；会话末条消息本身不是验收事实 |
| `task_work_decisions` | 管理者待办与决定 | 补充信息、授权、验收、命令确认、未知结果处置均可审计 |

状态机按确认方案落地：工作项使用 `queued / active / waiting_manager / completed / blocked / failed / cancelled`；运行使用
`prepared / dispatching / active / waiting_input / runtime_completed / succeeded / failed / outcome_unknown / cancelled`；交付物使用
`submitted / accepted / changes_requested / superseded`；管理者决定使用 `pending / resolved / dismissed / expired`。

### 上下文隔离

`WorkContextManifestV1` 只包含任务事实、任务附件、项目规则元数据和管理者显式选中的已验收交付物版本/哈希。未选中的其他工作项产物、完整会话和隐藏推理不会广播给新员工。Skill 启动时把全部资源冻结为运行级 Artifact 和只读快照目录，运行说明只注入稳定身份、内容哈希与快照路径；实际读取 `SKILL.md` 后记录启用事实。

## 公共接口与命令边界

- `POST /api/tasks/:taskId/work-item-previews`：解析员工修订、入口、模型覆盖、Skill、权限、命令参数、上下文及阻塞原因。
- `POST /api/tasks/:taskId/work-items`：携带预览摘要、预期任务/员工修订和 Work Management Command Envelope。来源变化时冲突失败。
- `GET /api/tasks/:taskId/work-management`：统一返回 summary、workItems、relationships、managerDecisions、deliverables、evidenceRefs 和 revision。
- `GET /api/tasks/:taskId/work-deliverables/:deliverableId/content`：按 Artifact owner 读取并校验正式交付物正文。
- 验收、返工、重试、取消和待办回复统一使用稳定 `operationIdentity` 与 `expectedRevision`。

旧人工指派接口不再创建执行，返回 `ZEUS_TASK_WORK_MANAGEMENT_V2_REQUIRED`。任务级“已有活动执行便禁止指派”的限制已移除，改用员工并发上限和稳定操作身份；独立指派的 `relationships` 固定为空。

## 执行语义

### Agent

预览确认模型与允许范围后创建独立产品会话。运行冻结员工、入口、模型、Skill、权限和上下文清单。受管会话在服务端强制只读，只能作为证据查看；会话等待输入或授权时在任务详情生成结构化管理者待办。会话完成时提取最终可见回复，写入 Artifact，并创建 `submitted` 交付物和验收待办。接受后运行成功、工作项完成；要求修改关闭旧运行、保留旧版本并创建复用冻结配置的新运行。

普通重试只复用原冻结快照。更换员工、模型或上下文必须重新预览并创建新工作项或新的显式尝试。

### Command

人工指派的最后一步创建命令确认并启动命令；确认创建后会先持久化 `commandRunId`，数据库中没有 Agent 会话。成功后工作项自动完成；明确失败进入待办，可取消工作项或重新填写参数创建新尝试；HTTP 写出后结果未知则进入 `outcome_unknown`，禁止自动重发。管理者只能在核对外部现场后标记成功或失败，确认失败后再显式决定是否创建新尝试。

自动化和任务池不再创建旧 `digital_employee_executions`。Agent 自动化创建并启动 v2 工作项；Command 自动化创建 `command_confirmation` 待办，管理者填写参数并确认后才启动。

## 管理驾驶舱

任务详情采用用户选定的第二版：顶部页签为“概览 / 协作 / 交付物 / 证据”；协作页左侧展示真实工作项、入口、运行状态与输出，右侧固定“待我处理”。补充信息、授权、验收/返工、命令确认和未知结果处置都在右侧完成。会话、命令运行、文件变化和旧执行只作为证据下钻；受管会话不再依赖会话输入框推进。

指派抽屉先预览后创建，展示主入口、模型解析与允许覆盖、Skill 快照、权限上限、已选上下文、命令参数和阻塞原因。Command 不展示模型控件。员工设置分为“身份说明 / 主执行入口 / Skills / 模型策略 / 权限工具 / 自动化”，不再暴露 Provider `default/plan` 为员工路线。

## 实现取舍

### 采用 v2 表与双读投影

优点：新领域语义干净，旧历史不被伪造，Agent 与 Command 的运行引用严格互斥。缺点：迁移期需要同时读取 v2 与旧执行证据。

### 采用多 Skill 快照与显式上下文清单

优点：能力复用、上下文隔离和审计边界清楚，Skill 更新只影响新运行。缺点：启动时需要资源遍历、哈希和有界快照，存储与 Runtime 适配更复杂。

### 不实现流程编辑器

优点：避免把独立工作管理与流程设计器一次绑死。缺点：本次多个独立工作项不会自动移交；未来只有在流程编排提供真实关系后才显示依赖连线。

### 不引入新的外部 Agent 框架

优点：复用 Zeus 现有 Provider、命令中心、Artifact、Command Envelope 与审计边界。缺点：显式编排、恢复和投影适配由 Zeus 自身维护。
