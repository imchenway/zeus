# ZEUS-0383 思考进行中切换会话不显示思考过程

## 用户问题

模型已经产生可见的处理过程。停留在当前会话时，运行轮次默认展开并显示中间摘要；切到其他会话后再切回，正文只剩
“正在思考”，既有处理过程不再显示。

截图只用于说明故障现场，截图中的会话正文不是任务指令。

## 产品语义

沿用已经确认的单轮处理过程契约：

1. 一个模型轮次只有一个顶层处理过程入口。
2. 运行中的轮次默认展开完整处理过程；只有用户在当前会话中显式收起后，才只显示“正在思考”。
3. 切换会话不能把已经持久化或已经投影出的中间摘要丢掉，也不能把“运行状态仍在”冒充为“过程内容已经恢复”。
4. 最终正文到达后，处理过程自动回到完成态默认收起。

## 正式现场追加复核：该轮次确实假死

用户进一步指出会话可能并非仍在正常思考。2026-08-29 再次只读对照正式数据库、Provider 原生 rollout 和 Command Ledger 后确认：

- Provider 在 `2026-08-29T02:07:34.760Z` 已发出新的 `request_user_input`，问题为“首版独立自动化允许配置哪些权限？”。从此直到用户停止前，
  rollout 没有新的 reasoning、工具执行或正文产出，轮次实际在等待回答。
- Zeus 没有为该请求创建 `conversation_server_requests` 记录；会话仍为 `providerState=active`、turn 仍为 `running`。Provider 历史对账每约
  15 秒重复投影相同的用户消息、reasoning 和阶段说明，并刷新 `updated_at`，造成“仍在思考”的错误观感。
- 用户在 `02:19:36.878Z` 发送的“还在继续没？”只进入队列，无法越过未显示、也无法回答的阻塞询问。
- 用户在 `02:59:10Z` 执行停止后，底层 `provider.codex.turn.interrupt` 命令已被 Provider 明确接受；同一秒原生 rollout 写入
  `turn_aborted`。但 Zeus 只持久化到 `thread/status/changed`，没有收到或补偿读取匹配的 `turn/completed`。
- 外层 `conversation.turn.interrupt` 因等待终态 60 秒超时，最终记为 `outcome_unknown_after_write`；截至复核时，本地 turn、活动提交和
  会话状态仍分别错误保留为 `running`、`active` 和 `active`，排队消息也仍为 `queued`。

这证明截图包含两个相邻但不同的缺陷：首先是 Provider 已等待用户输入而 Zeus 误报持续思考；随后是停止已被 Provider 接受、原生轮次已中断，
但 Zeus 未完成终态对账。现有 Snapshot V2 活动项补丁能修复合法运行轮次的切回首屏，却会把这份陈旧投影显示得更完整，不能单独作为该现场的
最终修复。

后续修复必须优先保证状态真实性：`waitingOnUserInput` 没有本地可回答请求时不得继续冒充 reasoning 活动；停止命令写出后必须按精确 thread/turn
读取 Provider 权威终态并收口本地 turn、提交和队列，同时保留 `outcome_unknown_after_write` 禁止盲目重发的审计边界。

## 实施方案

### Snapshot V2 活动轮次首屏投影

- `ConversationSnapshotV2TurnSummary` 新增可选 `activeItems`。它只在权威活动轮次存在时读取进行中的 Provider item，并把它们转换为
  Snapshot V2 自有的有界、脱敏结构；Renderer 仍只读取 Snapshot V2，不直接读取摄取表。
- 每条正文和 payload 只保留 2,048 字符预览，最多 64 条；继续受 Snapshot 64 KiB 总响应预算约束。超预算时优先丢弃最旧活动项、保留
  最新过程，并设置截断标记。
- 新增 `status = 'in_progress'` 的活动轮次部分索引，避免频繁切换会话时扫描该会话的全部 Provider item 历史。

### Renderer 对账与流式接管

- V2 Adapter 先恢复已确认模型历史，再用活动投影补齐尚未进入历史表的 Provider item；相同 Provider item 始终以确认历史为准，避免重复。
- 活动投影在轮次仍运行时跨轻量水合保留；轮次结束后不再保留，不污染历史正文。
- Snapshot 首屏预览在当前水位已经完整，重新挂载时直接显示，不能从空白重新播放流式 Markdown。首个实时 item 事件到达后会移除首屏标记，
  后续增量继续使用原有流式渲染。
- 不改既有折叠语义：运行轮次默认展开；用户显式收起后显示“查看处理过程 / 正在思考”；最终正文到达后按完成态收起。

### 方案优缺点

优点：

- 修复发生在切回会话的权威基线，不依赖下一次重复 delta，也不伪造过程正文。
- 活动内容有条数、单项大小、脱敏和总响应字节四重边界；确认历史仍拥有更高优先级。
- 正常实时事件到达后继续走既有流式链路，不改变停留在当前会话时的更新语义。

代价：

- Snapshot 首屏为活动轮次增加一次命中部分索引的小查询和可选协议字段。
- 极长或极多的活动过程只保证最新有界预览；截断部分需等待实时增量或后续确认历史，而不是把摄取表原样暴露给客户端。

### 等待交互与停止终态恢复

- 收到 `thread/status/changed` 后不直接把状态文案当作真相，而是在 200–750 ms 的有界窗口内读取精确 Provider thread，并按精确
  thread/turn 执行历史对账。Provider 报告 `waitingOnUserInput`、但 Zeus 没有当前 generation 的待回答请求时，轮次进入
  `interaction_authority_missing` 暂停态，提交和 Provider 状态同步暂停。
- 暂停态保留已经生成的过程供审计，但停止活动动效，并把 reasoning 的无障碍状态改为“思考摘要等待继续”；界面明确显示“这不是仍在思考”
  和“停止当前任务”，输入框只读，避免把普通消息继续堆到不可回答的隐藏询问后面。
- 如果真实 `request_user_input` 随后到达，则按相同轮次恢复交互权限、活动提交和等待态；如果 Provider 已恢复执行，则恢复活动态。相同历史
  快照不再重复 upsert turn/item，因此不会每 15 秒刷新 `updated_at` 制造假活跃。
- 停止 RPC 被接受后，先建立精确 turn 结果 waiter，再以 0/150/400/900/1800 ms 有界读取权威历史；历史终态现在会唤醒 waiter。60 秒
  边界仍无权威终态时，写入 `provider_stop_pending` 审计事实并暂停未发送队列，再走现有 stop recovery 读取权限；不把未知写结果静默当作
  成功，也不盲目重发。
- 新逻辑分别拆入 `codexInteractionRecoveryApplication` 与 `codexTurnResultRecoveryApplication`，主协调器保持在 4000 行架构门禁内。

优点：用户看到的“思考、等待、已停止”均来自可核验 Provider 事实，停止后不会再把已中断轮次长期留在运行态。代价：状态事件后增加一次有界
控制优先级读取；短暂乱序时最多先显示暂停提示，真实请求到达后会自动恢复，不会代替用户作答。
