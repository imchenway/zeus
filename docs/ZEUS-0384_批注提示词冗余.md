# ZEUS-0384 批注提示词冗余

## 任务目标

回答批注与代码评论发送后，会话记录只展示用户可见正文和一份结构化批注卡片；Codex、Pi 的 Provider 输入只包含一份可读批注。结构化 `conversationContext` 继续用于本地锚点、草稿恢复、历史回显和审计，不修改接口或数据库结构。

## 真实现场

- 用户截图中的同一条回答批注先以 `# 对会话回答的注释`、回答项、选中文字和用户评论显示，随后又由“回答批注”卡片显示一次。
- 只读核对正式数据中的目标消息后确认：本地 `conversation_messages.content` 已是“回答批注”，结构化引用与评论完整保存在 `metadata_json.conversationContext`；没有数据丢失。
- 对应 Snapshot V2 历史项把 `displayText: "回答批注"` 保存在 `payload.content.displayText`，顶层只有 `conversationContext`。Renderer 只读取顶层 `payload.displayText`，因而错误展示 Provider 可读正文并叠加批注卡片。
- 对应 Codex 原生 JSONL 只有一份可读批注。Pi 派发则在已经包含可读批注的 `prompt` 后再次追加完整 `conversationContext` JSON，模型输入存在第二份同义内容。

## 根因

1. Snapshot V2 的历史用户消息适配只恢复附件、任务推送布局和 `conversationContext`，遗漏同级的 `displayText`。
2. 已持久化的旧 `session-view-cache-v1` 仍可能保留嵌套 `payload.content.displayText`，只修适配层不能保证升级后的首帧立即正确。
3. Pi 的上下文拼装没有识别上游正文已经包含共享序列化结果，无条件追加结构化 JSON。
4. 上下文规模预估既计算已序列化进 `content` 的批注，又计算 `conversationContext` JSON，形成重复估算。

## 实施方案

- Snapshot V2 历史适配把有效的嵌套 `displayText` 恢复到统一顶层展示字段。
- 消息正文读取增加旧缓存兼容：顶层字段缺失时读取 `payload.content.displayText`，不要求清缓存或迁移数据。
- 纯批注消息继续通过既有占位识别隐藏“回答批注”正文，只显示结构化卡片；存在普通用户输入时显示普通输入和卡片各一次。
- Pi 使用共享 `serializeConversationContext` 生成稳定可读块。正文已包含该块时不再追加；缺失时只补一份可读块，不再发送第二份结构化 JSON。
- Provider 上下文预估只计算 `content` 中已有的可读批注，不重复计算本地结构化副本。
- 网页批注属于独立协议，本任务不改变其拼装和展示行为。

## 取舍

优点：用户界面和模型输入都只保留一份批注语义，同时兼容历史记录、旧热缓存和缺少上游可读序列化的 Pi 调用。

代价：持久化记录仍同时保留 Provider 可读正文与本地结构化元数据。两者分别服务模型理解和精确锚点恢复，不属于界面或提示词重复。
