## 用户反馈

用户在重启会话后回答恢复出来的询问，回答气泡已经出现，但界面继续显示“当前操作未完成，请稍后重试”。用户要求修复同步操作、后台恢复和界面反馈之间的语义错位，并避免重复续接。

## 已确认现场证据

1. 正式 `0.3.72` 数据库中，目标询问已经在 2026-08-29 11:54:29 持久化为 `resolved`，用户回答没有丢失。
2. 原 Provider turn 同时被终止为 `interrupted`，符合跨连接恢复时不伪造旧请求答复的边界。
3. Zeus 已创建唯一的 `interaction-recovery-response:` 续接提交；该提交没有 `providerTurnId`，证明没有把续接内容写入 Provider。
4. 续接在约 30 秒后进入 `paused + recovery_required`，持久错误为 `ZEUS_CODEX_RPC_TIMEOUT: thread/resume`。
5. 目标 Provider JSONL 约 5.1 MB；新 Core 恢复完整线程超过通用 30 秒 RPC 窗口。
6. Renderer 把所有未专门识别的队列错误交给统一低噪音错误组件，因此错误地显示为“当前操作未完成”，没有说明回答已保存，也没有提供安全恢复入口。

## 根因与修复决策

### 根因

交互恢复入口在同一个 HTTP 操作中依次执行回答持久化、旧轮次收口、`thread/resume` 和续接派发。回答虽然已经成功保存，但同步 `thread/resume` 超时仍让界面把整个操作解释为失败。

### 决策

1. 回答入口只负责耐久解析请求、收口旧轮次和创建唯一续接提交；完成持久化与事件广播后立即返回 `queued`。
2. 续接由既有统一队列排空器后台派发，继续使用原 submission、Provider command 和 outbox，不新建第二条消息。
3. `thread/resume` 使用独立的 120 秒单次加载窗口；该 RPC 不加入安全只读重试白名单，也不自动重复调用。
4. 新续接在提交 JSON 中保存 `recoveryKind: interaction_response`；旧版本记录只通过内部幂等键前缀 `interaction-recovery-response:` 兼容识别，不新增数据库字段。
5. 排队时显示“回答已保存，正在恢复原会话…”；恢复超时或失败时明确说明续接尚未发送，并提供“重新恢复”和“取消续接”。
6. “重新恢复”使用会先核对 Provider 权威状态的 `recoverQueue()`；“取消续接”仅作用于队列投影中尚无 `providerTurnId` 的提交。已经保存的询问回答不被撤销。
7. 升级后不自动重发旧事故记录；旧记录只获得明确的手动恢复或取消入口。

### 优缺点

- 优点：回答成功不再依赖大线程加载速度；错误反馈与持久状态一致；每次恢复仍只有一次 resume 和至多一次 Provider 写入。
- 代价：异常慢的恢复最多占用当前线程的恢复租约 120 秒；旧版已经暂停的续接需要用户显式点击一次“重新恢复”。

## 实现记录

- `codexNativeConversationCoordinator` 已把交互恢复改成持久化后调用后台队列排空，并立即返回已排队操作。
- `codexAppServerManager` 已为 `thread/resume` 设置生产默认 120 秒的专用硬超时，同时保留可缩短的探针参数；普通 RPC 超时和安全只读 RPC 重试策略未变。
- 队列契约、持久提交输入和 Renderer 会话类型已增加可选 `recoveryKind`；队列快照同时识别新版字段和旧版幂等键。

- Core 删除接口会在写入前再次拒绝任何已经绑定 `providerTurnId` 的提交，避免界面快照与后台派发竞态时误删已进入 Provider 的续接。
