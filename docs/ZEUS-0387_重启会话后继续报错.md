## v0.3.80 部署后第三层根因（2026-08-30）

### 用户现象

升级并重启到 v0.3.80 后，旧会话中的新用户消息气泡可见，但仍显示“当前操作未完成，请稍后重试”，Provider 没有开始新轮次。

### 正式现场只读证据

1. 目标消息已由 Core 耐久接纳：submission `conversation_submission_gGumQXo01htm` 为 `queued`，具有冻结执行快照、当前运行分段和已接受的外层 command receipt；故障不是 Renderer 气泡伪接纳，也不是消息丢失。
2. 所有旧 turn、server request、计划操作和切换操作均已终结；会话 `provider_state=ready`，无活动轮次、无等待交互、无结果未知写入，所以不存在“为防重复而应当停止”的 Provider 边界。
3. 内层 `conversation.submission.dispatch` 命令在 Provider 写入前终止：outbox 结果为 `failed_before_write`、`auto_retry_permitted=1`，receipt 精确错误为 `ZEUS_PLUGIN_CONVERSATION_CONTEXT_MISSING`（“Plugin Host 尚未绑定该 Zeus 会话”）。
4. 目标提交没有 `providerTurnId`，Provider 账本也没有本次 turn；因此使用原 command/submission 安全重试不会重复发送。

### 根因

`ZeusConversationPluginRuntime` 的会话上下文是 Execution Host 进程内状态，应用冷重启后必然清空。新会话会在 `thread/start` 前调用 Plugin `prepare()`，但已有 Provider thread 的旧会话续聊直接进入 `beforeUserPrompt()`；启动恢复又只为 active/waiting/dispatching 会话重建 Plugin 上下文，漏掉了 `ready + queued` 的旧会话。因此本地队列已保存，但 UserPromptSubmit Hook 在 Provider RPC 前失败。

### 修复决策与权衡

1. 每次 Codex 提交派发都在 Plugin Hook 和 Provider 写入前调用幂等 `prepare()`；新 thread 使用 `source=startup` 并解析首次显式引用，已有 thread 使用 `source=resume` 按持久化的冻结激活集恢复进程内上下文。
2. 保留现有 Command Delivery 边界：只有 `failed_before_write`/明确拒绝可复用原 command 生成下一次 outbox；`outcome_unknown_after_write` 仍禁止自动重发。
3. 优点：修复不依赖启动扫描刚好覆盖某种会话状态，也不更新或重新冻结 Plugin 版本；升级后现存 queued 提交可由原身份自动继续。
4. 代价：每次派发多一次进程内 `prepare()` 检查；同一会话命中已缓存 Promise，没有重复执行 Hook 或重建 MCP 连接的实质开销。

### 真实冷启动回归发现的重试信封缺口

1. 在独立数据根中以未修改的 v0.3.80 包冷启动旧 Provider thread，原地复现 `ZEUS_PLUGIN_CONVERSATION_CONTEXT_MISSING`；对应 attempt 1 为 `failed_before_write`，没有 Provider turn，界面显示同一通用错误。
2. Plugin 上下文修复后，新建提交可在同一旧 thread 完成；完整退出应用并再次冷启动后，新提交仍可完成，证明进程级 Plugin 绑定已经恢复。
3. 对第 1 条失败提交执行现有 `recoverQueue()`，保持同一 submission、client message、command 和 idempotency key。下一次冷启动尚未创建 attempt 2 就被 `ZEUS_COMMAND_DELIVERY_IDEMPOTENCY_CONFLICT` 拒绝。
4. Inbox 的 `request_sha256` 与 submission 请求摘要完全一致；持久信封和冷启动重建信封的业务字段也完全一致，唯一变化是来自当前数据库性能上下文的 `traceIdentity`。该字段是短期观测身份，不是业务或 Provider 幂等身份。

### 重试信封修复决策与权衡

1. 会话 Submission 与项目内既有 Codex/Pi Provider 派发采用同一规则：首次接纳保存完整 Command Envelope；安全重试先读取并校验持久信封的全部业务身份，校验通过后原样复用，包括首次 `traceIdentity`。
2. 不放宽 `CommandDeliveryRepository` 的全局信封摘要校验；任何 command、scope、actor、issuedAt、submission/client message、请求摘要、投递方式或类型不一致仍直接拒绝重放。
3. 优点：已由 v0.3.80 写入 `failed_before_write` 的现存记录升级后即可生成 attempt 2，且保留原审计链，不需要改写正式数据库或创建第二条用户消息。
4. 代价：安全重试继续关联首次接纳时的性能 trace，而不是新进程 trace；这与“同一命令的后续 attempt”语义一致，新 attempt 仍由独立 outbox 序号和时间戳区分。

## v0.3.78 复现证据与二次根因

1. 目标 Provider rollout `01a04e90-6adf-7b80-be4c-7a971b9826ce` 在 2026-08-30 01:35 左右已经正常结束，01:43 的新消息完全不存在于 Provider JSONL；故障发生在 `thread/resume`、`turn/start` 和模型执行之前。
2. 对用户明确授权的目标正式记录执行只读核对：对应会话在 01:43 之后没有 `conversation_submissions`、`conversation_turns`、`command_inbox`、`command_outbox` 或 `conversation.message.submit` delivery receipt。消息没有进入 Zeus Core 的耐久接纳账本。
3. Execution Host 日志显示 v0.3.77 在 01:43:00 开始升级退出、01:43:04 完成关闭，v0.3.78 在 01:43:07 就绪。截图中的发送与这 7 秒交接窗口精确重合。
4. Renderer 会在 HTTP 接纳前持久化 `PendingSendEnvelope` 和耐久 command envelope，但失败后只投影本地 `failed/unconfirmed` 气泡；重启后不会自动核对并重放同一个 command。历史工作面还会在调用 `send()` 前提前切换为续聊态，造成“看起来已经发送”的错觉。
5. 普通 `delivery=queue` 当前仍在同一 HTTP 操作中执行慢速 Provider 恢复和派发。即使 Renderer 请求已经抵达 Core，Core 接纳仍与 `thread/resume`、Pi session resume 或 `turn/start` 的耗时与生命周期耦合。
6. v0.3.78 的修复本身没有被本次证据推翻：它解决的是“询问回答和续接 submission 已经耐久保存，但后台恢复失败”；本次暴露的是更早的“Core 接纳前进程退出”窗口，以及普通队列消息没有统一先接纳的结构缺口。

## 二次修复决策

1. 所有原生运行时的 `delivery=queue` 统一先完成 submission、执行快照、用户消息投影、幂等接纳检查点和数据库保存，再返回 HTTP 202；Provider 恢复与写入只由后台统一队列调度器执行。
2. Core 启动后扫描所有仍为 `queued` 且具有冻结执行快照的可派发队首；派发失败进入可见的恢复状态，由现有恢复入口重新核对。同一会话保持单租约，`turn/start` 或等价写请求结果未知时继续 fail-closed，禁止盲目重发。
3. Renderer 重启后先按 `clientUserMessageId` 读取权威 Snapshot；明确不存在时，把自动续发次数先落盘，再用原 `idempotencyKey`、`clientUserMessageId` 和耐久 command ID 自动续发一次。无法确认或再次失败则停止自动动作。
4. 草稿与待恢复信封分离；编辑草稿不得删除待恢复身份。若上一条仍无法确认，新的不同正文不得覆盖旧信封，必须先核对、同身份重试或安全取消。
5. 界面明确区分“Zeus 尚未接收”“Core 已保存、Provider 待恢复”“Provider 写入结果待确认”，并提供与证据边界匹配的核对、重试、取消入口，不再统一显示通用错误。

### 优缺点

- 优点：应用升级、Core 重启和 Provider 慢恢复不再决定消息是否丢失；Codex 与 Pi/第三方模型获得相同队列语义；同身份续发可借助现有 command ledger 消除重复 Provider 写入。
- 代价：Provider 离线时消息会更明确地停留在“已保存、待派发”，需要维护启动扫描、退避恢复和分层 UI；自动续发严格限制为一次，结果未知仍需要保守核对。

## 根因与修复决策

### 根因

交互恢复入口在同一个 HTTP 操作中依次执行回答持久化、旧轮次收口、`thread/resume` 和续接派发。回答虽然已经成功保存，但同步 `thread/resume` 超时仍让界面把整个操作解释为失败。

### 决策

1. 回答入口只负责耐久解析请求、收口旧轮次和创建唯一续接提交；完成持久化与事件广播后立即返回 `queued`。
2. 续接由既有统一队列排空器后台派发，继续使用原 submission、Provider command 和 outbox，不新建第二条消息。
3. `thread/resume` 使用独立的 120 秒单次加载窗口；该 RPC 不加入安全只读重试白名单，也不自动重复调用。
4. 新续接在提交 JSON 中保存 `recoveryKind: interaction_response`；旧版本记录只通过内部幂等键前缀 `interaction-recovery-response:` 兼容识别，不新增数据库字段。
5. 排队时显示“回答已保存，正在恢复原会话…”；恢复超时或失败时明确说明续接尚未发送，并提供“重新恢复”和“取消续接”。
6. “重新恢复”使用会先核对 Provider 权威状态的 `recoverQueue()`；“取消续接”仅作用于队列投影中尚无 `providerTurnId` 的提交。已经保存的询问回答不被撤销。
7. 升级后不自动重发旧事故记录；旧记录只获得明确的手动恢复或取消入口。

### 优缺点

- 优点：回答成功不再依赖大线程加载速度；错误反馈与持久状态一致；每次恢复仍只有一次 resume 和至多一次 Provider 写入。
- 代价：异常慢的恢复最多占用当前线程的恢复租约 120 秒；旧版已经暂停的续接需要用户显式点击一次“重新恢复”。
