## 用户现象

Plan 回合已经在正文底部显示“实施此计划？”阻塞卡片，但对应会话在项目侧边栏没有任何状态提示。用户需要进入每条会话才能发现待处理事项。

## 已确认产品语义

- 待处理计划确认属于“等待用户回复”，单条会话行显示既有琥珀色气泡图标。
- 图标悬停提示和辅助名称均为“等待用户回复”；颜色不是唯一状态线索。
- 蓝色小点继续只表示“有未读回复”，不与必须处理后才能继续的计划确认混用。
- 打开或选中会话不会清除提示；只有计划动作进入非 `pending` 终态才清除。
- 只修改单条会话行，不恢复项目级聚合红点、数量角标或折叠项目提示，不新增桌面通知。

## 已确认根因

1. “实施此计划？”持久化在 `conversation_plan_actions`，Renderer 投影在 `planImplementationRequests`；普通询问和审批则使用 `conversation_server_requests` 与 `pendingRequests`。
2. 会话阶段投影已经把待处理计划动作写成 `stage=waiting_user`，但 Local Server 的侧边栏摘要只检查普通待处理请求、活动轮次和提交，没有把该阶段映射为 `pending_user_input / waiting_user`。
3. 当前打开会话的 Renderer 状态映射只检查 `pendingRequests`，忽略 `planImplementationRequests`，因此实时计划事件到达后仍会覆盖为 `ready`。
4. `conversation.plan_implementation_request.changed` 没有列入会话列表生命周期刷新事件，后台会话创建或解决计划动作时不能精确刷新轻量摘要。
5. `ProjectConversationTree` 已经具备琥珀色 `ChatCircle`、完整悬停提示和辅助名称，不需要新增图标、CSS 或状态枚举。

## 实施方案与取舍

- Local Server 复用已持久化的 `waiting_user / waiting_approval` 阶段投影，向列表返回既有运行状态枚举。
  - 优点：不增加数据库查询、接口字段或另一套事实源，冷启动与后台列表共用同一权威阶段。
  - 代价：列表状态依赖存储层继续在计划动作创建和解决事务中同步阶段；现有仓储已保证该行为。
- Renderer 在会话、完整快照和轻量摘要三个入口统一识别待处理计划动作。
  - 优点：当前会话、切换后会话和旧 Core 缺少列表运行态字段时都能收敛。
  - 代价：三个既有状态适配入口必须保持同一优先级，不能只修当前页面。
- 计划动作实时事件触发目标会话轻量摘要刷新，继续复用现有去重和迟到请求保护。
  - 优点：创建与解决都能即时更新图标和 `stageUpdatedAt` 排序。
  - 代价：每次计划动作状态变化增加一次小型会话摘要读取，不加载完整历史。

## 接口与数据边界

- 不新增公开 API、IPC、数据库迁移、持久字段或状态枚举。
- `conversation_plan_actions.status=pending` 是计划确认是否仍待处理的权威业务事实。
- `stage=waiting_user`、`listRuntimeState=pending_user_input` 和 `taskRunStatus=waiting_user` 都是可重建投影，不能反向改写计划动作。
- 计划确认与普通 `request_user_input` 共用“等待用户回复”展示；命令或文件授权继续使用“等待授权”。
