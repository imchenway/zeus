# ZEUS-0397 新会话通用附件未进入模型上下文

## 任务结论

Zeus 已经成功收集、授权、持久化并展示 JSON 附件，但 Codex Provider 组装把所有非图片资源仅映射为 `mention`。`mention` 会出现在 Codex 的 `UserMessage` 事件中，却不会进入真正交给模型的 `response_item`；因此模型只能看到正文，错误回答“没有收到附件”。图片使用 `localImage`，会继续投影为 `input_image`，所以同一会话中 PNG 可以正常到达模型。

本次按“通用附件必须至少让模型知道资源存在并能按需读取”的既有产品语义修复，不把任意文件内容无边界内联进提示词。

## 现场证据

- 当前分支为 `zeus/ZEUS-0397-task-01`，调查开始时工作区干净。
- 目标 Codex rollout：`/Users/david/.zeus/providers/codex/sessions/2026/08/31/rollout-2026-08-31T01-08-43-01a053a5-18a3-7d70-a3f3-d4f08a05aa75.jsonl`。
- 用户附加的 140631 字节 JSONL 与原始 `rollout-2026-08-30T19-25-46-01a0526b-1db4-75a1-a465-b71067da8304.jsonl` 逐字节一致；内容记录了用户两次要求“看附件内容”、模型两次只收到正文并要求重传的旧故障。
- 首轮用户消息的 Codex `UserMessage` 事件同时包含正文和 JSON 文件 `mention`，路径为 `/Users/david/.zeus/artifacts/task-attachments/command-699c7e54f1d4843d80613fd5-1-rollout-2026-08-30T19-25-46-01a0526b-1db4-75a1-a465-b71067da8304.jsonl`。
- 同一轮交给模型的 `response_item` 只有 `input_text`“新会话缺陷 / 现状：”，没有文件名、路径或文件内容。
- 后续纯附件提交的 `UserMessage` 事件只有相同 JSON 的 `mention`；模型上下文仍没有附件信息。
- 再次发送 PNG 后，`response_item` 同时出现图片路径提示和 `input_image`，模型能够看到截图。
- `packages/local-server/src/codexNativeConversationCoordinator.ts` 对支持图片生成 `localImage`，对其他文件或目录只生成 `mention`。
- Pi Provider 已显式把非图片附件路径追加到真实提示词，Codex 路径缺少同等的模型可见语义。

## 根因

2026-07-28 的通用附件设计把“非图片资源映射为 `mention`”当成了 Provider 可读附件能力，但当时真实打包验收明确没有点击发送，也没有验证真实 Provider 回执。当前现场证明该假设不成立：

1. `mention` 是 Codex 原生用户消息中的资源展示/引用项；
2. 当前 Codex 运行链不会把独立 `mention` 转成模型可见的 Responses 输入；
3. Zeus 又没有为非图片资源补充任何正文路径引用；
4. 因而 UI、持久化和 Provider 事件都“看起来有附件”，模型却完全不知道附件存在。

## 修复设计

对每个已经通过 canonical path、精确授权和文件类型复验的非图片附件，按原顺序生成两个 Codex 输入项：

1. 模型可见的结构化 `text`，包含资源类型、原始文件名和 canonical path；
2. 原有 `mention`，继续服务 Codex 原生事件、历史和 Zeus 资源投影。

支持图片仍只使用 `localImage`，不重复增加文字引用。新会话、既有会话续发、纯附件消息、排队/转向消息和任务首发都复用同一个 `submissionProviderInput()`，因此不在 Renderer 或路由层逐入口打补丁。

结构化文本格式为：

```text
<zeus_attachment>
{"kind":"file|directory","name":"...","path":"..."}
</zeus_attachment>
```

### 优点

- 模型明确知道附件存在、名称、类型和可读取路径；
- 不读取或内联任意大文件，避免请求大小和上下文用量失控；
- 保留原生 `mention`，不破坏资源卡、Provider 事件和历史投影；
- 文件与目录继续经过既有 exact authorization 和可信根校验；
- 单点修复覆盖全部 Codex 消息入口，并保留任务首发的附件位置顺序。

### 缺点

- 模型仍需主动调用读文件或目录工具，附件内容不会在请求前自动展开；
- 若运行时文件在发送后被删除、权限变化或 Provider 工具拒绝读取，会得到明确读取失败，而不是预先缓存全文；
- 每个非图片附件会增加一小段路径元数据 token。

## 安全与范围边界

- 不放宽 Renderer 任意本地路径权限；只处理已经由 Main 签发 capability、并在服务端重新解析通过的路径。
- 不自动重发本次已经错误完成的两轮消息，不修改正式数据库或 Provider rollout。
- 不新增或恢复单元测试体系。
- 不执行 Git commit、push、merge、revert 或正式发布。
- 静态检查、构建和打包不等于真实 Provider/GUI 验收；验证结果按证据等级分别记录。

## 实施结果

- `submissionProviderInput()` 在路径 canonicalize、资源类型和精确授权复验通过后，为非图片文件或目录生成结构化 `text` 与原生 `mention` 两个相邻输入项。
- 结构化输入使用 `JSON.stringify()` 保存 `kind/name/path`，文件名或路径中的引号、换行等字符不会突破字段边界。
- 图片继续只生成 `localImage`，没有重复注入路径正文。
- 普通消息与任务首发都改为展开附件输入数组，任务首发仍按 `TaskPushMessageLayout` 中的资源位置输出。
- Provider 回显后的 Zeus 用户气泡仍由精确匹配的 submission 正文或 `displayText` 决定，不会把内部结构化路径标签展示成用户输入正文；资源卡继续来自 submission 附件元数据。
