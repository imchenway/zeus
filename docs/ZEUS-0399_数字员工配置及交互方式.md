# ZEUS-0399 数字员工配置与任务执行交互

## 当前阶段

2026-09-01 已完成补充需求的代码调整和静态、构建、打包验证。当前有另一任务 ZEUS-0431 正在占用唯一的 `dev.hypha.zeus.test` 测试身份，因此未启动、借用或检查其 GUI；本任务的真实 GUI 与 Provider 验收仍待独立测试身份可用后执行。本任务未执行 commit、push、merge 或 revert。

## 最终产品语义

- 系统模板、项目员工和单次 Agent 执行共用同一类基础配置：供应商分组模型、推理级别、服务速率、工作模式、权限模式、多个 Skill 和员工提示词。
- 员工配置是单次运行的默认值，不是治理上限。单次运行可在当前正常会话实际可用的范围内自由选择模型、推理级别、服务速率、权限模式和 Skill。
- Skill 仍校验稳定身份、项目可用性和冻结资源，但不再要求属于员工预设集合。
- 数字员工不再有配置型并发上限，同一员工可创建多个独立工作项；Provider 限流、运行资源与实际可写代码现场冲突仍是真实运行边界。
- 同一任务可保留多个独立活动工作项。新指派不会隐式停止、替换或修改已有运行。
- 任务详情“执行者”列的下拉只展示当前项目已启用且 Agent 主入口完整的员工。选择员工后直接进入单一运行配置弹窗，最终以一次“开始执行”创建工作项。
- 保留最后一次显式开始，是因为本次需求同时要求运行可以改写员工默认模型、权限和 Skill。若下拉选中即时执行，这些本次配置将无处输入，也会把普通选择变成不可预期的外部副作。
- 数字员工只有 Agent 身份；执行命令是 Agent 的运行能力，不存在单独的 Command 员工或 Command 主入口。

## 实现结果

### 共用配置与项目员工

`AgentExecutionConfigFields` 继续由系统模板、项目员工和单次执行共用。单次执行现在直接使用完整能力模型目录和项目 Skill 目录，仅根据所选模型的真实支持集合筛选推理级别和服务速率。

项目员工页已删除“允许覆盖模型/推理/速率”治理上限和 `1–20` 并发数输入。代码修改、验证和交付动作仍作为员工默认能力显示，不会因会话完成而隐式提交、推送、合入、部署或完结任务。

底层历史 `max_concurrency` 列暂不删除，写入时固定为 `1`，业务路径不再读取它做并发判断。这避免了一次只为删除已失效字段的数据库迁移。

### 任务详情交互

任务基本信息区的“执行者”下拉始终作为新建指派入口，已有运行以“N 个执行者运行中”反馈，不再把下拉锁定为某个当前员工。原有协作、交付物、待办、证据和历史工作项保留。

单次执行弹窗提供完整模型、推理、速率、工作模式、权限、Skill、本次提示词、已验收交付物上下文和代码现场选择。配置变化后以 250 毫秒合并刷新服务端权威预览，丢弃陈旧响应。

任务详情继续使用现有 `WorkspaceDrawer` 的 `wide` 能力，侧边与居中详情最大内宽约 920px；执行弹窗同样为 920px，窄屏回落为单列并限制在视口内。

### 服务端运行边界

预览和创建仍是服务端权威路径，会重新解析并冻结员工、任务、模型、Skill、权限、上下文和代码现场快照。服务端仍拒绝当前不可用模型、模型不支持的推理级别/速率、无效 Skill 身份、陈旧预览和不安全的共享可写现场，但不再对照员工预设集合或权限等级做上限判断。

`POST /api/tasks/:taskId/work-items` 不再接收或处理 `replaceActiveWorkItems`，也不再要求单任务只有一个活动工作项。人工新建、自动化、失败重试和要求修改均不再受员工并发配额或同任务活动项限制。

单次权限模式高于员工默认值时，“是否可写”也按本次冻结权限判断，以保证直接工作区的并行写入冲突不会因员工默认值较低而被漏过。已有任务分支只在当前真实可继续时允许选择；否则创建独立任务分支。

## 取舍与上限

- **员工配置作为默认值**：优点是单次运行与正常会话能力一致，无需先去项目设置扩容；缺点是员工配置不再承担组织强制策略。未来确有组织级硬约束时，应新建明确的策略层，不应重用员工默认值。
- **不设员工并发上限**：优点是人工与自动化指派没有人为配额；缺点是运行量直接受 Provider、机器资源和代码现场限制，这些超限将以真实错误反馈。
- **独立工作项不隐式替换**：优点是新指派不破坏已有运行和证据；缺点是同任务并行结果需要管理者自行验收和取舍。
- **保留显式“开始执行”**：优点是可配置本次覆盖且不会因误选立即产生外部副作；缺点是相比“选中即运行”多一次点击。如后续明确放弃所有本次覆盖，再改为纯默认值的即时执行。
- **保留历史并发列**：优点是没有额外迁移风险；缺点是原始数据库结构仍会看到已失效的字段。只有在未来专门清理表结构时再删除。
