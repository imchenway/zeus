# ZEUS-0405 Telegram 端任务交互优化

## 需求

优化 Telegram 中的任务浏览与操作体验。参考 Vibego 的真实任务列表交互，但继续遵守 Zeus 的单项目绑定、动态项目状态、一次性 capability 和任务/会话身份校验边界。

## 调研结论（2026-08-31）

- Zeus 当前任务列表一次展示全部项目状态，并按任务创建时间正序取前 8 条；任务多时首屏优先出现最老任务，完成任务也会持续占位。
- 列表没有状态筛选入口；状态文字放在任务按钮末尾，长标题或自定义长状态会使关键信息被 Telegram 的 64 字符按钮上限截断。
- 当前 capability 只保存页码。新增筛选后，如果不把筛选上下文贯穿列表、详情、编辑、状态修改、推送和返回动作，用户从详情返回时会丢失筛选位置。
- Vibego 的有效做法是列表顶部直接筛选、筛选后回到第一页、任务按最近更新时间倒序，并在详情返回时恢复列表上下文。其状态只有固定三项，不能原样套用到 Zeus 的项目自定义状态。

## 本期决策

1. `/tasks`、首页“任务列表”默认展示“未完成”，定义为排除当前项目配置中的完成与取消终态；同时提供“全部”和每个真实项目状态。
2. 状态按钮直接位于任务列表顶部，每行最多三个；切换状态从第一页开始。
3. 任务按 `updatedAt` 倒序展示；任务按钮把状态放到编码和标题之前，确保状态优先可见。
4. capability 继续使用一次性安全令牌，并在任务列表全链路中携带筛选与页码；旧的无筛选 capability 仍按“未完成”解析，避免升级后短时按钮全部失效。
5. 新建任务统一回到“未完成”上下文，使创建完成后的任务从详情返回时仍可见。

优点：移动端默认聚焦可推进任务，状态筛选可发现，详情往返不丢位置，且不引入第二套项目状态定义。

代价：项目自定义状态很多时，列表顶部会多占几行；本期不增加折叠筛选菜单，因为默认上限下仍远低于 Telegram 的按钮数量边界，先保留一步直达。

## 明确不做

- 不复制 Vibego 的批量推送、批量改状态、Excel 导入和固定三状态模型；这些能力涉及更大的副作用与桌面端治理边界。
- 不把 Telegram 筛选写入桌面端的任务页偏好；两端是独立操作现场，避免远程点击静默改变桌面布局。
- 不新增 Vitest 或其他单元测试文件；按项目规则使用静态检查、构建和必要的真实运行验收。

## 当前阶段

代码与静态、构建、打包验证完成；真实 Telegram 往返仍待独立测试 Bot 验收。

## 实现记录（2026-08-31）

- `taskListView` 现在按项目动态状态生成“全部 / 未完成 / 各项目状态”按钮，每行最多三个；选择状态会回到第一页。
- “未完成”根据项目状态配置中的终态角色计算，不硬编码 `completed` / `cancelled`；列表按 `updatedAt`、`createdAt` 倒序。
- 任务按钮调整为“项目状态 · 任务编码 · 标题”，状态和编码优先保留在 Telegram 64 字符限制内。
- 列表筛选通过 `task.*` capability action 编码，贯穿详情、编辑等待态、项目状态修改、运行控制、任务会话选择、取消确认与返回列表；旧 action 缺少筛选字段时兼容为“未完成”。
- 新建任务入口统一携带“未完成 / 第 1 页”上下文；进程恢复后的新建和编辑等待态也恢复原筛选。
- `/help` 与 `/task` 帮助同步说明 `/tasks` 默认浏览未完成任务并可按状态筛选。

本轮只修改共享 Telegram 服务和本文档，没有新增依赖、测试文件或桌面端偏好字段。
