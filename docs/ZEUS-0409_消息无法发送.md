# ZEUS-0409 消息无法发送

## 2026-08-31 诊断阶段

### 用户现象

- 会话输入框可以输入文字，发送按钮可见。
- 按回车与点击发送按钮均无反应。
- 附件截图中的草稿为“不是网络问题？”，问题发生在一个已完成轮次之后。

### 目标流程

会话底部输入内容后，按 Enter 或点击发送按钮都必须进入同一提交链路，并把消息投影到当前会话。

### 排查边界

- 先检查 `ConversationComposer` 的发送资格、键盘判定和共享提交函数，再追踪其所有调用方。
- 不分别增加回车和按钮补丁，避免两个入口继续漂移。
- 不把静态检查、构建或截图等同于真实 Provider 已接纳消息。
- 不执行 commit、push、merge 或发布。

### 方案权衡

- 在共享提交门禁修复：优点是同时覆盖回车和按钮及其他调用方；缺点是必须确认活动轮次、目标模式、附件和待批注等分支不被放宽。
- 在 UI 入口分别兜底：优点是改动直观；缺点是重复逻辑且容易绕过真实发送状态，本任务不采用。

### 当前状态

- 分支：`zeus/ZEUS-0409-task-01`。
- 初始工作区干净。
- 正式数据库中该会话最后一次 `conversation.message.submit` 已完成；用户本次两次尝试都没有新的 Core 提交记录。
- Execution Host 在两次操作时间点记录了 Renderer 运行错误，故障位于 Renderer 到 Core 之前，不是网络或 Provider 失败。

## 2026-08-31 实现阶段

### 根因

- 应用重启后，冷历史会话的首屏水合故意不处理发送账本，避免只读浏览产生实时副作用。
- 上一条消息的本地 `pendingSend` 已是 `accepted`，但还没有用耐久快照清理。
- 用户续聊时，新消息与旧 envelope 指纹不同，共享 `send()` 门禁直接拒绝；因为回车和按钮共用该路径，两者同时表现为无反应。

### 修复

- 遇到与新消息不同的 `accepted` envelope 时，先调用已有 `reconcileAcceptedSend()` 读取权威快照并销账。
- 只有确认旧 envelope 已清除后才重进共享 `send()` 继续当前消息；未对账成功仍保持阻断。
- 不重发旧消息，不放宽未接受或不确定 envelope 的安全门禁。

### 优缺点

- 优点：只修改一个共享门禁，同时覆盖回车、按钮和其他发送调用方；复用已有权威对账逻辑和幂等身份。
- 缺点：冷历史首次续聊需额外一次快照读取；该成本只在存在未销账 `accepted` envelope 时发生。
