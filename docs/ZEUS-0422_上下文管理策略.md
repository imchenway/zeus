# ZEUS-0422 上下文管理策略

## 一、任务结论

最近 30 个 Zeus/Codex 原生会话 JSONL 显示，当前最需要修复的不是圆环展示，也不是 `/docs` 或长期记忆预算，而是**派发前 Context Compiler 没有拿到“下一次完整 Provider 请求”的已有上下文规模**。

当前 Codex 派发把 `JSON.stringify(providerInput).length` 作为 `currentInputCharacters`，再按一字符一 Token 传给编译器；这个值只覆盖本次新输入，不覆盖：

- Provider 原生 thread 已有历史；
- Provider 基础指令、Developer 指令和动态工具 schema；
- `segmentLifecycle` 便携上下文；
- `context.additionalContext`；
- Plugin 的 `beforeUserPrompt` / `PostCompact` 上下文；
- 本轮编译后最终合并的完整 `additionalContext`。

因此 `zeus_context_manifest.availableTokens` 目前只是一个建立在不完整基线上的“编译器可选片段额度”，不能代表真实剩余上下文。样本中 28 次续聊 Manifest 的可用额度相对下一次 Provider 真实请求，**中位虚高 91,962 Token，P90 虚高 190,189 Token，最大虚高 202,049 Token**。

截图中的 `238K / 258K = 92.2%` 则来自最后一次真实模型请求，当前 UI 口径是正确的。它与样本 22 次自动压缩前的中位占用 `91.2%` 一致，说明截图处于 Provider 常见的自动压缩危险区间。

只读分析和策略设计已经完成；第一阶段运行代码现已落地完整请求估算账本和 Codex 文本工具结果投影。没有修改正式数据库、Provider JSONL 或 Git 历史，也尚未执行真实 Provider 或 GUI 验收。

## 二、样本与口径

### 2.1 选择规则

- 数据根：`/Users/david/.zeus/providers/codex/sessions` 与 `archived_sessions`。
- 排序：读取每个 JSONL 首行 `session_meta.payload.timestamp`，按会话创建时间倒序，不使用文件 mtime。
- 样本：排除本次尚在生成的 ZEUS-0422 会话 `01a0569b-d9be-7a03-b821-5ac1d2bb97c5` 后，取最近 30 个文件。
- 时间范围：`2026-08-30T17:11:00.518Z` ～ `2026-08-31T06:57:55.697Z`。
- 快照时间：`2026-08-31T07:13:37Z`；样本含 27 个普通 sessions 文件与 3 个 archived 文件，最新 ZEUS-0421 文件仍在增长，因此所有总量都是该时点快照。
- 隐私边界：只统计事件类型、字符/字节规模、Token usage、工具类别和压缩水位，不把对话正文复制进报告。

### 2.2 Token 口径

- 当前上下文占用：`last_token_usage.total_tokens / model_context_window`。
- 累计吞吐：每个会话最后一个最大 `total_token_usage`；它用于观察重复请求规模，不代表当前上下文，也不直接等于计费量。
- 模型请求近似数：按累计 `total_token_usage.total_tokens` 变化去重后的 `token_count` 快照；不把重复广播算成新请求。
- 压缩前水位：`compacted` 事件之前最近一个去重 `token_count`。
- 压缩后水位：`compacted` 事件之后第一个去重 `token_count`。
- 字符/文件 MiB 只表示序列化规模；图片 Base64 字符数不能换算为图片 Token。

## 四、上下文从哪里长出来

### 4.1 首请求固定税

30 个会话的首请求中位数为 29,286 Token。JSONL 中下列序列化字符规模的中位数为：

| 固定来源 | 中位字符数 |
| --- | ---: |
| Provider `base_instructions` | 17,972 |
| 动态工具 schema | 20,915 |
| Developer 消息 | 38,304 |
| 推荐插件、AGENTS、环境启动信封 | 5,478 |
| 合计 | 82,669 |

作为对照，30 个会话所有真实用户文本合计只有 20,444 字符。字符数不能精确换算 Token，但首请求真实 usage 已证明固定启动内容是显著成本。

本次被排除的 ZEUS-0422 当前会话结构与样本一致，其中 Developer 消息包含约 12,198 字符的 Memory 说明/摘要与约 13,640 字符的 Skills 目录；推荐插件目录另占约 3,275 字符。它们适合改成按需发现，不适合每个新会话完整热注入。

### 4.2 工具结果与图片

30 个样本含 2,681 个 `custom_tool_call_output/function_call_output`：

- 558 个序列化结果超过 16K 字符；
- 44 个超过 100K 字符；
- 12 个超过 1M 字符；
- 55 个图片块共 31.17 MiB Base64；
- `view_image` 占 22.03 MiB，文本型 `exec_command` 占 18.90 MiB；
- 只检测到 3 个结果含 `conversation_tool_result` 分页句柄标识。

项目已经有 `ManagedConversationToolResultStore`：完整文本 gzip 保存，模型只接收最多 16,384 字符的头尾投影和不可猜测句柄。但当前 Codex Dynamic Tool 路径对 Plugin 结果直接返回全文，对 Zeus Browser/Computer 结果直接返回 `contentItems`；现有 `.store()` 投影主要接在 Pi 路径。优先复用这一现成能力，不需要再造一套摘要/Blob 系统。

图片不能简单按 Base64 字符截断。合适的热上下文策略是默认低细节/缩略图，只保留最近且仍被引用的 1～2 张视觉证据；原图继续由 Artifact 持有，需要精确检查时再显式读取。

### 4.3 原生 JSONL 体积不是上下文

361.94 MiB 中：

| 顶层事件 | 体积 |
| --- | ---: |
| `event_msg` | 275.54 MiB |
| `response_item` | 76.45 MiB |
| `compacted` | 7.67 MiB |
| `session_meta` | 1.13 MiB |
| `world_state` | 0.99 MiB |

最大的单条 `event_msg/item_completed` 约 3.12 MiB。抽查发现同一个 `CommandExecution` 在一条事件里同时保存约 1.05M 字符的 `stdout` 和同量 `aggregated_output`，另有 `formatted_output`。这是 Provider 原生审计/存储冗余，不等于模型再次接收 3.12 MiB。

因此产品必须分开显示：

1. 当前热上下文 Token；
2. 累计/缓存/输出 usage；
3. Provider 原生日志磁盘占用。

不要为了降低上下文而删除原生 JSONL，也不要复制第三份完整 Zeus JSONL。冷索引继续只保存元数据与锚点。

## 五、P0 根因：派发预算没有完整请求基线

### 5.1 代码链路

1. `codexNativeConversationCoordinator.ts` 只把 `JSON.stringify(providerInput).length` 传为 `currentInputCharacters`。
2. `index.ts` 把这个字符数按一字符一 Token 直接命名为 `currentInputTokens`。
3. `contextCompiler.ts` 用 `contextWindow - reservedOutput - currentInput` 计算 `availableTokens`。
4. 编译完成后，Coordinator 才把 portable context、编译结果、调用方 additional context、Plugin prompt context 与 compact context 合并，再调用 `turn/start`。

编译器算法本身没有问题，问题在调用点给了错误语义的数据：**“本次新输入”被当成了“完整请求已有输入”**。

### 5.2 JSONL 对账

30 个会话共有 58 个 `zeus_context_manifest`：

| 对账项 | 结果 |
| --- | ---: |
| `usedTokens = 0` / `sources = []` | 38 次 |
| 有来源的 Manifest | 20 次，全部是 `task_document` |
| 有来源时 `usedTokens` 中位 / 最大 | 1,073 / 2,360 |
| 30 次首轮可用额度虚高，中位 / 最大 | 9,822 / 11,338 Token |
| 28 次续聊可用额度虚高，中位 / P90 / 最大 | 91,962 / 190,189 / 202,049 Token |
| 续聊虚高超过 50K / 100K | 23 / 13 次 |

这也说明当前压力不是长期记忆造成的：样本没有 `long_term_memory` 进入 Manifest；任务文档实际只占 571～2,360 个估算 Token。此时去缩小 `/docs` 或 Memory 默认预算，收益很小且会损害任务事实权威性。

## 六、优化优先级

### P0-1：把编译预算改为完整请求闭环

最小改法：复用已经落库的 `ConversationUsageSnapshot.latestModelRequest`，不要新增第二套用量存储。

建议把现有含混的 `currentInputTokens` 拆为：

- `providerHistoryBaselineTokens`：续聊取上一条真实 `latestModelRequest.totalTokens`；新会话取按模型、CLI、Developer 指令 hash、动态工具 hash 分组的保守启动基线；
- `pendingInputTokens`：本次用户文本、附件和浏览器批注的估算；
- `knownAdditionalContextTokens`：portable、caller、Plugin prompt/compact 等已知附加上下文；
- `compiledContextTokens`：Context Compiler 本轮选择的片段；
- `reservedOutputTokens`：模型执行配置的输出预留；
- `estimatedFullRequestTokens`：上述输入合计；若 Provider 以后提供 exact preflight，再用真实完整请求计数覆盖估算。

执行顺序应是：

1. 计算 Provider 历史基线与所有已知非编译上下文；
2. 用剩余额度编译 `/docs`、Memory 等片段；
3. 合并最终 `additionalContext`；
4. 对最终序列化请求做第二次 estimate 门禁；有 exact RPC 时调用现成的 `verifyExactProviderContextBudget`；
5. 不满足窗口与输出预留时，在任何 Provider 写出前失败关闭或先进入明确的压缩/新分段流程。

优点：修复真正的安全边界；Manifest、审计与 UI 可以对上；长会话不会在只剩 20K 时仍认为可注入 239K。

缺点：上一请求 usage 是滞后观测；Provider 即将自动压缩时会偏保守，可能少注入部分有用资料。必须给基线记录 `source/confidence/observedAt`，不能把估算包装成 exact。

### P0-2：UI 展示“安全余量”，而不只展示物理余量

保留当前 `latestModelRequest.totalTokens / contextWindow` 口径；它是正确的。新增：

- 物理剩余：`capacity - latestRequest.totalTokens`；
- 输出预留；
- 待发送输入/上下文估算；
- 安全余量：`capacity - baseline - pending - compiled - reservedOutput`；
- 当前窗口编号、累计压缩次数、压缩进行中/已完成状态；
- 安全余量不足时的可点击动作：“等待自动整理”或“生成任务检查点并在新分段继续”。

截图的“剩余 20K”并不等于还能安全生成 20K 输出；只有扣除输出预留与下一次新增输入后才是可用余量。

优点：用户知道为什么 92.2% 仍能继续、什么时候不能继续，以及压缩后发生了什么。

缺点：若估算来源未标明，第二个数字会制造新的伪精确；UI 必须显示“实测/估算”状态。

### P1-1：复用现有句柄投影，收紧 Codex 热工具结果

- 把 `ManagedConversationToolResultStore.store()` 接到 Zeus 可控的 Codex Plugin、Browser、Computer 文本结果路径；
- 维持现有 16,384 字符上限，命令结果保留 12,288 字符头部 + 4,096 字符尾部；
- 模型需要中间段时只调用 `read_conversation_tool_result` 分页读取；
- 对 Provider 内建、Zeus 无法拦截的工具，收紧宿主默认输出上限，并优先使用 `rg`、范围读取和结构化摘要；
- 图片默认低细节/缩略图，原图 Artifact 可回读；真实视觉验收需要原图时不得降质。

优点：直接命中 558 个超过 16K 的结果和图片长尾，减少增长速度与压缩频率；复用现有存储、Artifact、完整性校验和分页工具。

缺点：需要额外分页回合；错误出现在被省略的中间段时，模型可能先得出不完整判断。投影必须明确标记截断，原文必须可取回。

### P1-2：降低首请求固定税，但不削弱安全指令

- 推荐插件目录改为用户明确请求插件或能力缺失时再查；
- Skills 首轮只提供名称、短描述和启用状态，选中后再读完整 `SKILL.md`；
- 动态工具 schema 按冻结的项目/任务能力集选择，不把本轮不可能使用的 namespace 全量注入；
- 明确 Codex Native Memory 与 Zeus Memory 的所有权：同一事实只允许一个热注入版本，外部 Context 生效时避免双份摘要；
- AGENTS、安全边界、权限和用户显式启用的 Plugin 规则继续完整保留。

优点：每个新会话可回收一段稳定窗口，减少无关指令冲突；固定内容虽然大多命中缓存，仍会真实占用上下文。

缺点：按需发现增加一次工具回合；路由器误判可能漏掉能力。必须保留确定性的冻结快照与失败时的显式发现入口。

### P1-3：按阶段续接，不无限递归压缩

建议在以下任一条件出现时提供“新分段继续”而不是继续堆叠当前窗口：

- 同一 Provider thread 已完成 2 次自动压缩；
- 当前任务进入明确阶段切换；
- 安全余量不足且 Provider 没有可控的压缩 RPC；
- 大量 GUI/图片证据已经完成验收，只需保留结论与证据锚点。

新分段只携带：当前 `/docs` 主任务文档、受治理 Memory、最近未完成事项、必要工具句柄和原生 session/turn 锚点。精确历史继续在 Provider JSONL 冷查，不把摘要当权威原文。

优点：限制 summary-of-summary 漂移；4～5 次压缩的超长任务会明显受益。

缺点：每个新会话有约 29K 首请求固定税，也会丢失未写入检查点的隐性语境。因此不能按普通轮次频繁拆分，只在阶段边界或第 2 次压缩后做。

### P2：把 Context Manifest 升级为可对账账本

每次派发记录并展示：

- Provider 原生历史基线与观测时间；
- 固定指令/工具 schema 快照 hash；
- 本次用户输入、附件、Plugin/portable/caller context；
- `/docs`、Memory、运行证据各自的请求/纳入/排除 Token；
- 输出预留；
- estimate 与下一次真实 `token_count` 的偏差；
- 压缩前后窗口 ID、Token 和来源。

Manifest 字段建议把当前 `availableTokens` 改名为 `compilerBudgetTokens`，另增 `estimatedRequestHeadroomTokens`，避免把“片段预算”误读成“真实剩余上下文”。

优点：能按模型、CLI、工具快照做 P50/P90 校准，也能解释某次为何压缩或拒绝注入。

缺点：审计字段会增加少量存储和产品复杂度；正文仍不能复制进审计，只保存数值、hash、来源和决策。

## 七、建议验收指标

1. 续聊 Manifest 的 `estimatedRequestHeadroomTokens` 与下一次真实 `token_count` 对账：P90 绝对误差从当前 190,189 降到 10,000 Token 以内。
2. 新会话首请求基线误差：P90 绝对误差不超过 4,000 Token，并按模型/CLI/工具快照分别校准。
3. `safeHeadroom < 0` 时，Context Compiler 不再继续纳入普通 task document/Memory 片段；安全边界放不下时失败关闭。
4. Zeus 可控的文本工具结果超过 16,384 字符时，模型热历史只保存投影和句柄；完整 Artifact 可分页恢复且 SHA-256 一致。
5. 默认视觉工具结果使用低细节/缩略图；请求原图时可显式恢复，不降低真实 GUI 验收质量。
6. UI 同时区分当前上下文、累计 usage、缓存占比和原生日志体积；任何一项不能冒充另一项。
7. 同一会话第 2 次压缩后出现新分段建议；用户拒绝后可继续，不自动丢失工作。

## 八、不建议优先做的事

- 不先缩小 `/docs` 或长期 Memory 预算：样本只有 20 次任务文档注入，中位 1,073、最大 2,360 个估算 Token，且没有长期 Memory 入选。
- 不把累计 360M input 当成当前上下文或账单：其中 96.78% 是 cached input。
- 不删除或复制 Provider 原生 JSONL 来“节省上下文”：JSONL 磁盘占用和模型热上下文是两类问题。
- 不把每轮都拆成新会话：29K 首请求固定税会反向增加开销。
- 不隐藏真实压缩/截断：投影、估算、自动压缩和新分段都必须可见、可审计。

## 十一、Codex 原生处理方式对照

Codex 的核心策略不是把整个 JSONL 每轮重放给模型，而是由 Provider 维护活动历史窗口；本地 JSONL 保留完整事件用于恢复和审计，模型请求只消费当前活动历史、压缩替代项和本轮输入。最近 30 个会话中的 22 次 `compacted` 事件证明该机制已实际运行。

| 问题 | Codex 当前处理 | 优点 | 局限与 Zeus 责任 |
| --- | --- | --- | --- |
| 长对话持续增长 | 接近窗口上限时生成原生压缩替代历史；样本压缩前占用中位数 91.2%，压缩后 8.8% | 不需要 Zeus 解析或重写 Provider 历史，压缩后可继续原线程 | 压缩通常发生在高水位，不能替代 Zeus 对本轮 additional context 的发送前预算 |
| 原始日志很大 | JSONL 保存原始事件、工具调用和压缩事件，活动模型历史与磁盘日志分离 | 可恢复、可审计，不因压缩丢失原始证据 | 大图片和重复工具输出仍占磁盘；Zeus 不应通过删 JSONL 解决模型上下文问题 |
| 重复前缀开销 | 使用 Prompt Caching；样本累计 input 中 96.78% 命中缓存 | 显著降低重复静态前缀的延迟和输入成本 | cached input 仍占模型上下文窗口；缓存不能修复 29K 首请求固定税或错误 headroom |
| 上下文占用观测 | 每次请求完成后写入 `token_count`，包含最近请求与累计 usage、上下文窗口 | UI 可基于真实最近请求显示占用，当前 92.2% 属于真实事后值 | 这是请求后事实，不是 Zeus 编译 additional context 前的精确预检 |
| 超窗保护 | Responses API 可选择自动丢弃最早输入，或在禁用截断时返回错误；Codex Agent 的本地样本优先表现为原生压缩 | 最终仍有 Provider 级边界保护 | 自动截断可能牺牲关键事实；Zeus 不应依赖 Provider 兜底后才发现本轮注入过量 |
| 大工具目录 | 官方建议把稳定前缀放前、动态内容放后，并用 tool search/延迟加载只暴露相关工具 | 可减少首轮固定成本并提高缓存复用 | 当前本地首请求仍有约 20.9K 字符动态工具 schema，Zeus 需要实际做工具按需暴露 |
| 大工具结果和图片 | 平台支持低细节图像输入，工具结果可由调用方投影为摘要或句柄 | 能控制单次观察结果对热历史的冲击 | 当前 Zeus Codex 动态工具路径尚未统一接入既有 16K 投影/Artifact 句柄能力，仍需补齐 |

因此边界应当明确：Codex 负责 Provider 活动历史的压缩、缓存、最终窗口约束和请求后 usage；Zeus 负责在请求发出前，把 Provider 基线、本轮用户输入、所有 additional context、工具 schema 和输出预留合并成同一本账。两层都需要，不能用其中一层替代另一层。

对截图中 92.2% 的直接解释是：这是最近一次已完成模型请求的真实占用；下一轮 Codex 可能触发原生压缩并明显降低活动窗口，但在压缩发生前，Zeus 仍不应继续按当前 `Context Compiler` 的虚高 headroom 注入普通任务文档或 Memory。

官方参考：

- OpenAI 模型指南建议缩短稳定前缀、把动态上下文后置、利用 Prompt Caching、tool search 和有意压缩，并保留已完成动作、活动假设、标识符、工具结果、未决阻塞与下一目标：<https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.5>。
- Responses Compact API 返回用户消息加单个压缩项的替代输出，说明压缩结果应作为 Provider 原生项继续传递，而不是由 Zeus 猜测其内部摘要语义：<https://developers.openai.com/api/reference/java/resources/responses/methods/compact>。
- Responses Create API 的 `truncation` 可配置为自动删除最早项目或在默认禁用时超窗失败，`usage` 则是响应后的输入、输出与总量事实：<https://developers.openai.com/api/reference/cli/resources/responses/methods/create>。

## 十二、Codex app-server 与 Pi SDK 的优化边界

### 12.1 结论

**目标和账本一致，Adapter 实现不一致。**

两者都应在 Provider 写出前用同一口径计算：Provider 活动历史、固定指令与工具、本轮输入、所有 Zeus/Plugin 上下文、编译片段和输出预留。UI 也应统一显示实测占用、估算安全余量、估算来源和压缩状态。

但不能用同一个“字符换算 Token”实现同时覆盖两者：app-server 把活动历史和最终模型请求封装在 Provider 内；Pi 则由 Zeus 持有 `AgentSession`、`ResourceLoader` 和模型传输适配层，能在网络写出前观察最终序列化 payload。

### 12.2 哪些相同，哪些不同

| 优化项 | Codex app-server | Pi SDK | 结论 |
| --- | --- | --- | --- |
| 完整请求账本 | 第一阶段已计入最近真实请求基线、冻结的 Developer/动态工具、当前输入和全部待合并附加上下文 | 第一阶段已计入最近真实请求基线、Provider metadata、序列化内容与图片和待合并附加上下文 | P0 已在现有 Compiler 收口；两端仍是保守估算而非精确 tokenizer 结果 |
| 历史基线 | 续聊使用已落库 `latestModelRequest`；新 thread 使用冻结的启动载荷估算，避免把临时压缩 thread 的 usage 当成主 thread 基线 | 续聊使用最近真实请求；新 session 使用启动载荷估算 | 字段语义共享，证据来源由 Adapter 明确标注 |
| 精确 Token 预检 | 官方 app-server 当前没有完整待发请求的 token-count RPC | Pi SDK 0.83.0 也没有公共精确计数端口；不同连接还可走 Responses、Completions 或 Anthropic 协议 | 两者都不得标记 exact；Pi 可以做完整 payload 估算，但不得伪装成 tokenizer 真值 |
| 压缩 | app-server 自动压缩，也提供 `thread/compact/start`；当前 Zeus Manager 未暴露该方法，现有临时 thread 只压缩 portable context，不是主 thread 活动历史 | 已配置 SDK 自动压缩，且 Zeus Driver 已封装 `AgentSession.compact()`，可返回 `tokensBefore` 和 `estimatedTokensAfter` | 统一触发政策与 UI 状态，分别调用原生压缩能力 |
| 附加上下文 | 通过 `turn/start.additionalContext` 的 application/untrusted 分区合并 | application 通过 ResourceLoader reload，untrusted 显式附加到当轮用户内容 | 信任分区规则共享，协议映射分开 |
| 大工具结果 | 第一阶段已把 Plugin/Browser/Computer 文本接入 `ManagedConversationToolResultStore`，返回 16K 投影和句柄；图片仍保留原调用链 | Pi 文本工具结果已统一走同一存储，返回 16K 投影和句柄 | 文本契约已统一；图片策略仍需单独收紧 |
| 首请求固定税 | 30 个样本已实测中位约 29K Token，可按 Developer/动态工具 hash 建基线 | 本次没有取 Pi 真实请求样本，不能沿用 29K、91.2% 或 258.4K 参数 | Pi 必须独立采样、按协议/模型/工具快照校准 |

### 12.3 最小实施顺序

1. 扩展现有 `ProviderDispatchContextInput` 和 Manifest，统一记录 `providerHistoryBaselineTokens`、`pendingInputTokens`、`knownAdditionalContextTokens`、`compiledContextTokens`、`reservedOutputTokens`、`estimatedFullRequestTokens` 及每项 `source/confidence/observedAt`。
2. Codex 先复用 `ConversationUsageSnapshot.latestModelRequest`，在最终 `additionalContext` 合并后再做一次保守 estimate 门禁；只有安全余量不足时才考虑接入原生 `thread/compact/start`，不在每轮强制压缩。
3. Pi 使用同一账本做前置筛选，再在既有 `onPayload` 边界根据最终请求长度、消息数、system/tools 分区和已校准偏差做第二道门禁；当 Provider 通知了真实 usage，再回填估算误差。
4. 只给 Codex 动态工具补齐已有的 16K 文本投影与分页句柄；Pi 保持现有文本路径。两者共享图片缩略图/原图 Artifact 策略。
5. Renderer 只保留一套用户语义：“最近请求实测占用”、“下一请求估算安全余量”和“Provider 原生压缩状态”；证据来源由 Adapter 展示，不暴露内部协议差异为两套产品。

共享账本的优点是 UI、审计、防溢出和验收口径一致，不会出现 Codex 和 Pi 各自解释“剩余 Token”。缺点是共享字段只能表达语义，不能掩盖证据精度差异。Adapter 分开实现的优点是能利用 Pi 的 payload 边界和两者各自的原生压缩；缺点是需要两组校准数据和真实 Provider 验收。

## 十三、第一阶段开发结果

### 13.1 已实现

- 共享派发账本不再把含义模糊的字符数当作完整请求。Adapter 现在显式提供历史基线、基线来源、固定输入和估算安全余量；Compiler 额外计入自身 envelope/Manifest 开销，并输出 `estimatedRequestHeadroomTokens`。

- 审计与 Provider snapshot 保留同一份 request accounting，Manifest 使用 `compilerBudgetTokens` 与 `estimatedRequestHeadroomTokens`，不再把 `availableTokens` 暗示为物理剩余窗口。

优点：最危险的虚高 headroom 已在共享入口收口，Codex/Pi 产品语义一致，大工具文本不会继续无界进入 Codex 热历史。缺点：当前仍是带安全余量的保守估算，不能替代 Provider tokenizer；Pi 的极少数同轮 `PostCompact` 追加内容仍在编译后发生，需要后续纳入最终 payload 门禁。

## 十四、第二阶段完整实现设计与开发记录

### 14.1 统一触发政策

- 共享 `ContextPressurePolicy` 只在完整请求估算的安全余量小于零时触发有损压缩；首轮 bootstrap 没有可压缩热历史，不误触发。
- 安全余量已经扣除 Provider 历史基线、本轮固定输入、Compiler envelope、编译片段、输出预留和 2%（上下限 2,048/8,192 Token）的估算保护量。
- 压缩模型请求本身计入累计 usage，但不得覆盖 UI 和下一轮编译使用的“最近产品会话模型请求”基线。

优点：Codex 与 Pi 共享同一产品语义，只有真正越过安全预算才承担有损压缩成本。缺点：两端都没有完整请求的精确 tokenizer 预检，策略仍可能偏保守；界面必须明确标记为估算。

### 14.2 Codex app-server 主 thread 压缩

- `CodexAppServerManager` 与多世代路由层新增 `compactThread()`，调用官方 `thread/compact/start`。
- 压缩作为独立 `provider.codex.thread.compact` 耐久命令，不借用父用户轮次的写标记。订阅在 RPC 前建立，RPC 接纳后才消费新通知，避免把 replay/history 误认作本次终态。
- 以 `turn/started`、`contextCompaction` item started/completed 和 terminal turn 联合收口；重启恢复只接受 Provider history 中可证明完成的压缩轮次，无法证明时 fail-closed，不盲目再压缩。
- 压缩前后执行 Plugin `PreCompact`、`PostCompact` 和 `SessionStart(source=compact)`；PostCompact 固定输入重新纳入请求估算。

优点：保留原 thread 身份和 Provider 原生压缩语义，不由 Zeus 猜测摘要结构。缺点：app-server 不返回压缩后精确 Token，本轮仍必须用旧基线做保守预算，等待下一次真实 usage 校准。官方协议依据：<https://learn.chatgpt.com/docs/app-server>。

### 14.3 Pi 同 session 主动压缩

- 续聊在 Provider 写出前调用既有 `AgentSession.compact()`；要求 session 空闲，并携带稳定 trace identity。
- 新增 `provider.pi.session.compact` 耐久命令。完成进程项、压缩模型请求 usage 与 command accepted receipt 在同一个 `durableTransactionSync` 中提交。
- 只看到 `in_progress`、`failed` 或写后不确定记录时拒绝自动重放；只看到已完成进程项时复用完成事实并恢复 PostCompact Hook。
- `estimatedTokensAfter` 只作为 Provider 估算证据，不冒充精确窗口计数。
- 压缩完成后必须用 `estimatedTokensAfter` 作为显式历史基线重新编译完整请求；若重新计算的安全余量仍为负，则以 `ZEUS_PI_CONTEXT_COMPACTION_INSUFFICIENT` 停止 Provider 写出，下一次队首调度改走新分段。

优点：比等待 SDK 自动阈值更早地为本轮固定输入和输出预留腾出空间。缺点：压缩本身产生一次模型请求、延迟和摘要漂移；因此不在安全余量仍为正时主动执行。

### 14.4 图片 Artifact 与热投影

- Codex Browser/Computer 和 Pi 原生工具的图片结果均解析为受限 data URL，原图以 `conversation_tool_image` owner 写入内容寻址 Artifact，大小上限 20 MiB并绑定活动会话保留策略。
- 当前 Provider 调用链只内联不超过 768 KiB 的热投影；更大图片只返回句柄与明确占位。`read_conversation_tool_image` 默认 `low`，只有显式 `detail=original` 才回读大原图。
- Pi JSONL 继续只持久化受控引用，不保留 base64；Codex 动态工具响应在进入 app-server 历史前已替换为热投影/句柄。
- 文本分页工具拒绝读取图片 MIME，图片读取同时校验会话所有权、Artifact owner、双哈希和解码预算。

优点：原始视觉证据可恢复，热历史和 Provider JSONL 不再无界复制 base64。缺点：当前没有对大图生成降采样缩略图；超过 768 KiB 时默认只给引用，需要模型显式请求原图，多一次工具回合。

### 14.5 工具按需加载

- Codex Plugin MCP 和 Computer 长尾工具使用 app-server 原生 `deferLoading`；`list_apps`、`get_app_state` 等高频观察工具保持直接可见。
- Pi 对 Plugin、长尾原生工具和图片读取器只暴露 `zeus_tool_catalog`/`zeus_tool_invoke`。目录普通搜索最多返回 20 项，精确名称才返回完整 schema；invoke 只能访问当前 session 已冻结目录中的精确工具名。
- 文件读取、搜索、编辑、命令和完整文本结果分页保持直接工具，避免核心开发路径每次先发现。

优点：降低每个请求重复携带的工具 schema 固定税，Plugin 数量增多时收益更明显。缺点：首次调用冷工具多一次发现回合；目录误用会增加延迟，因此保留确定性精确名称、冻结快照和显式不存在错误。

### 14.6 多次压缩后的自动新分段

- 当前运行分段完成两次原生 `context_compaction` 后，下一条队首提交自动创建同路由新分段；旧分段以 `context_pressure_rollover` 封存。
- portable 临时压缩的 `context-compaction:*` 进程项不计入次数，避免“为跨分段摘要做一次压缩”反过来再次触发滚动。
- 新分段继续携带已确认 model history、必要工具句柄、主任务文档和 Memory；Provider 原始 JSONL 保持冷事实源。

优点：限制 summary-of-summary 漂移，不让同一热窗口无限递归压缩。缺点：新 thread/session 重新承担启动固定税，且依赖已确认历史；未落库的隐性语境不会被猜测恢复。

### 14.7 UI 与对账证据

- 每次上下文编译把 `context_request_estimate` 作为 `adapter_serialized` 配置证据落库，记录窗口、输出预留、历史基线与来源、固定输入、Compiler envelope、编译片段、安全量和估算 headroom。
- 圆环继续只显示最近一次真实 inference/tool-continuation 的 `totalTokens/contextWindow`；压缩请求用量只进入累计账本。
