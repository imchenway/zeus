# ZEUS-0428 目标模式恢复附件入口

## 原始需求

- 目标输入状态没有显示附件图标。
- 附件截图中，输入框已进入“创建目标”，左侧工具栏从权限入口开始，缺少普通输入状态已有的附件入口。

## 当前阶段

实现、验证与差异复核已完成，交付物将随本次提交进入当前分支。

## 代码现场与根因

- 当前 worktree：`/Users/david/hypha/.zeus-worktrees/zeus-e2e-oBLuqT/dc824e99f594120f0d34/ZEUS-0428`。
- 当前分支：`zeus/ZEUS-0428-task-01`；开始处理时工作树干净。
- `ConversationComposer` 和 `NewConversationComposer` 都使用 `!goalInputActive` 条件直接移除附件按钮，同时隐藏已选附件。
- 这不是图标资源、模型能力或 CSS 问题，而是 ZEUS-0290 目标输入改造时明确加入的渲染门禁；该门禁把“目标正文单独编辑”扩大成了“目标输入不允许使用附件入口”。

## 本次契约与取舍

1. 新会话和已有会话进入目标输入后都继续显示附件图标，文件选择能力与普通输入一致。
2. 已选附件在目标输入期间保持可见、可移除，避免点击后没有反馈。
3. 不修改原生目标协议：新会话附件继续随首轮消息提交；已有会话的 `goal/set` 只保存目标正文，附件继续留在共享会话草稿，创建目标后可随下一条普通消息提交。
4. 本次只恢复用户指出的显式附件入口，不扩大到目标输入中的粘贴、拖放、浏览器批注、代码批注或 Skill 插入；这些输入的归属语义不同，不能借本缺陷隐式放开。

优点：改动只落在错误的条件渲染处，不新增状态、协议或依赖；两种 composer 的入口和反馈一致。

缺点：目标输入仍不接收附件粘贴与拖放；已有会话中附件不会成为 `goal/set` 的一部分，而是在创建目标后保留给下一条消息。这是现有原生协议的真实边界。
