# ZEUS-0429 会话内容展示缺陷

## 现象

- 活动轮次中，“搜索文件”会脱离原本的过程时间线，单独出现在会话最底部，位于当前处理摘要之后。
- 最近已完成轮次仍显示用户消息、“查看处理过程”和“已处理”，但最终回答正文消失。

## 既有产品约束

- 一个模型轮次只显示一个“查看处理过程”入口；阶段摘要、命令、工具和文件操作都属于该入口内部的真实过程。
- 活动轮次的当前处理摘要必须位于本轮全部命令、工具和文件活动之后。
- 最终正文到达后，完成态顺序是“查看处理过程”入口、最终正文及交付物、处理耗时；正文不能因首屏有界加载而消失。

## 现场证据

- 截图对应生产会话 `conversation_1a5ebca2c3d1616819d82d9a`，Provider 原始记录和本地只读数据库中均存在缺失的最终正文，内容没有在摄取或持久化阶段丢失。
- 截图中的三个轮次分别占 46、110、166 条模型历史；首屏尾部只读取 48 条，因此全部名额都被当前轮次占用。
- Snapshot V2 只为最近轮次额外携带 `openingUserMessage`。这会补回旧轮次的用户气泡，但没有补回同轮最终正文，于是界面只剩开场、过程入口和耗时。
- 活动尾部包含已完成的 prework 项；模型历史中的工具配对会在 Renderer 过滤。现有 `mergeActiveTurnItems` 把未能按 Provider 身份匹配的活动项直接追加到历史末尾，破坏了真实时间线和“当前摘要在过程底部”的既有语义。

## 根因与修复边界

1. 在 Snapshot V2 的轮次摘要中，沿用既有 2,048 字符有界正文投影，增加最终输出锚点；Renderer 将开场和最终输出一并补入首屏历史。这样不提高 48 条尾页上限，也不全量加载长会话。
2. 活动尾部与模型历史复用现有 Provider 身份合并函数，并按原时间排序，不再维护一套“历史后直接追加”的特殊规则。
3. Snapshot V2 结构代际同步升级，防止新旧协议缓存混用。

优点：修复位于共享恢复边界，覆盖冷启动、切换会话和长工具轮次；首屏仍有固定条数与字节上限。代价：每个摘要轮次增加一次有索引范围的最终输出查询和最多 2,048 字符投影。单纯提高历史尾页条数改动更小，但工具密集轮次仍会再次挤掉旧轮正文，因此不采用。

## 修复实现

- `ConversationSnapshotV2TurnSummary` 新增 `completionOutput`，Storage 用与模型历史相同的 phase、reasoning 和正式 Plan 判定，读取每轮最后一个最终输出；正文仍复用 2,048 字符预览和按需完整内容句柄。
- Renderer 的首屏历史锚点由“只补开场消息”改为“补开场消息和最终输出”，再按模型历史序号去重排序。
- 活动尾部复用现有 `mergeItemsByProviderIdentity`，相同 Provider 项只保留一份；排序统一使用首次开始时间，避免完成时间把长命令或文件搜索挪到后续摘要之后。
- 权威轮次只要声明 `process.available`，即使过程详情尚未分页，也直接生成同一个 `turn_work` 占位并紧跟开场用户消息；不再等到最终正文或交付物末尾才补“查看处理过程”。
- Snapshot V2 结构代际升级为 `2026-09-01-conversation-snapshot-v2-turn-output-anchors`；Renderer 类型、身份校验和既有 QA 夹具同步更新。
- 恢复 QA 夹具将历史尾页置空，最终正文只由 `completionOutput` 恢复，用于覆盖本次“用户气泡仍在但旧轮正文被尾页挤出”的实际路径。
