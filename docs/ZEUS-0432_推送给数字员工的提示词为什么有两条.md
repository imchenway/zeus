# ZEUS-0432 推送给数字员工的提示词为什么有两条

已完成正式 Zeus v0.3.92 现场、Provider JSONL、正式 SQLite、Snapshot V2 接口与 Renderer 投影代码的只读诊断，并完成 Snapshot V2 稳定身份修复、真实数据只读投影检查、整仓门禁和独立测试身份打包。
本轮没有重放消息、没有修改正式数据或续接正式 Provider thread。

## 结论

数字员工只收到了一次提示词。界面上的两张用户卡片是同一条持久消息的两个 Snapshot V2 投影未能按稳定身份合并，不是重复派发、重复创建会话或数字员工重复执行。

## 权威事实

1. Provider JSONL 只有一条 `role=user` 的输入，位于第 10 行；用户消息 ID 为
   `msg_01a05a87-afed-7ca2-af97-47da496b333e`。
2. 正式 SQLite 对该会话只有：
   - 1 条 `conversation_submissions` 记录；
   - 1 条 `conversation_messages.role=user` 记录；
   - 1 条 `conversation_model_history.role=user` 记录。
3. 三者均指向同一客户端消息身份
   `native-client-bcb8d211efc36810684637c8`，同一 submission
   `conversation_submission_be9193c24299b19d51d6ec8c`。
4. 正式 Snapshot V2 的 `activeTurn.openingUserMessage` 已返回该条模型历史，但
   `providerItemId=null`。
5. Provider 同一用户项的真实 `providerItemId` 为
   `01a05a87-afee-7643-a5ba-905afe77e68f`；其完整 `payload_projection_json` 为 4,002 字节，
   Snapshot V2 首屏只取前 2,048 字符，截断结果不是合法 JSON，因此 Renderer 无法从该投影中解出
   `clientId=native-client-bcb8d211efc36810684637c8`。
6. 该 Provider item 同时带有真实图片 resource；这解释了截图中一张卡无图片、另一张卡有图片。

## 根因链

### 1. 活动轮次尾部开始携带已完成的 prework 条目

`ZEUS-0418` 为了让活动会话冷开时恢复最近过程，将 `activeTurnItems()` 的查询从只返回
`status = 'in_progress'` 放宽为：

```sql
phase = 'prework' OR status = 'in_progress'
```

因此，已经进入 model history 的完成态 `userMessage` 也再次进入活动尾部。

### 2. opening user history 没有解析到 Provider item 身份

`modelHistoryProviderItemSql` 对普通消息依赖以下精确关联：

- 角色相同；
- 正文完全相同；
- `conversation_messages.created_at = conversation_model_history.confirmed_at`。

当前现场正文完全一致，但本地首帧消息创建于 `01:13:53.801Z`，model history 确认于
`01:13:54.783Z`，时间不相等，因此 `openingUserMessage.providerItemId` 被投影为 `null`。

### 3. 活动 Provider item 的 client 身份被有界预览截断掉

Provider item 的完整 payload 里确实有 `clientId`，但 Snapshot V2 把结构化 JSON 直接按字符截断。
Renderer 只能将完整合法 JSON 解析为结构字段；当前 2,048 字符预览不合法，因此活动条目只剩
`providerItemId`，没有 `clientUserMessageId`。

### 4. Renderer 的合并器没有任何可交汇的身份

`coalesceTranscriptUserMessages()` 只会按以下稳定身份合并：

- client message ID；
- submission ID；
- Provider item ID。

当前两条投影分别只剩：

- model history：`client:native-client-bcb8d211efc36810684637c8` +
  `submission:conversation_submission_be9193c24299b19d51d6ec8c`；
- active item：`provider:01a05a87-afee-7643-a5ba-905afe77e68f`。

两组身份没有交集，同一条消息被当成两条。两条投影的时间线入口不同，所以第二张卡还可能落在已出现的助手消息之后。

## 与历史重复问题的区别

`TASK_20260825_005` 处理的是兼容 `item-N` 跨轮碰撞和旧版 interrupted submission 接管；本次不是跨轮碰撞，
而是同一轮的 `openingUserMessage` 与 `activeTurn.activeItems` 同时返回后丢失共同身份。
历史的“正文指纹 + 5 秒”兼容隐藏明确排除了附件和 `taskPushLayout`，不会、也不应命中本次结构化任务推送。

## 修复实现与取舍

### 已实施：用 submission/client 身份给 user model history 补齐 Provider item ID

用 `conversation_model_history.submission_id -> conversation_submissions.client_message_id` 与
`conversation_messages.client_message_id` 关联用户消息，不再用完全相等的时间戳关联。

实现位于 `packages/storage/src/conversationSnapshotV2.ts` 的共享 `modelHistoryProviderItemSql`：

1. 用户模型历史先按同会话的 submission/client message 稳定身份查找已确认的 `provider_item_id`；
2. 没有稳定身份的旧数据继续使用原有时间戳、角色和正文精确匹配；
3. reasoning source 中的原生 item ID 仍作为最后回退。

- 优点：在 Snapshot 存储边界一次补齐稳定身份；既能让 active/history 去重，也能让附件 resource
  继续按同一 Provider item 落到唯一用户卡片；不依赖正文相似度。
- 缺点：历史消息若既没有 submission/client 身份，也不满足旧精确关联，仍只能依赖 reasoning source；本次不扩展 Snapshot 协议。

### 可选防御：把 clientUserMessageId 作为 active item 的顶层有界字段

不再让关键身份依赖可被截断的 `payload.preview`。

- 优点：长 `taskPushLayout`、长工具载荷和其他结构化长消息都不会再因 JSON 截断丢身份。
- 缺点：扩展 Snapshot V2 协议和 Renderer 类型；单独使用它仍未修复 model history 的 Provider item/resource 关联。

### 不推荐：按正文相同隐藏第二张卡

- 优点：Renderer 改动很小。
- 缺点：会误吞用户真正连续发送的相同消息，附件和结构化上下文还可能被错配；只掩盖症状，不修复身份链。
