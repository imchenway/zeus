# ZEUS-0438 执行命令时 Zeus 经常卡死诊断

## 当前阶段

- 状态：第一、二阶段实现完成；静态检查、构建、命令行为探针和 Test 打包通过，真实 GUI 受本机 Electron 启动故障阻塞并已如实记录。
- 目标：区分命令自身阻塞、外部依赖失败与 Zeus 命令功能失去响应。

## 结论

截图中的发布命令没有卡在“同步远程 main 与稳定标签”。它在启动约 24 秒后因无法连接 GitHub 443 端口而退出，退出码为 1。命令失败属于外部网络问题；终端仍停留在旧日志、运行状态未及时刷新，以及同一时刻本地控制心跳超时并重新连接，属于 Zeus 命令功能的可靠性问题。

因此需要分开归因：

- “这次发布为什么失败”：GitHub 网络不可达，不是发布脚本无限等待。
- “为什么用户看到 Zeus 卡住”：Zeus 在命令继续执行并退出时没有保持日志和状态视图同步，这是产品问题。

## 分层证据

### 命令层

- 发布脚本使用隔离副本完成依赖安装后进入远端校验。
- 失败原因明确为 GitHub 连接失败，且在短重试后退出。
- 3600 秒超时上限没有被触发，不存在本次命令运行一小时或无限等待的证据。

### Zeus 层

- 命令详情页按秒轮询增量日志；截图对应的日志量约 14 KB，不足以单独支持“日志太多拖死渲染器”的判断。
- 同一次运行中，Execution Host 出现唯一一个与活跃命令重叠的重复 UI attach，说明本地控制链路短暂失去响应。
- ZEUS-0407 已在截图所用的 v0.3.92 中将 UI lease 容忍期提高到 120 秒，并把恢复改为非阻塞；这避免了立即过期，但没有消除本次 5 秒控制心跳失败和视图陈旧。

### 数据库与系统负载

- 当前 `zeus.db` 约 9.92 GB（9.24 GiB），全库扫描代价很高，可能放大磁盘与事件循环压力。
- 命令日志查询实际命中 `idx_terminal_events_session_seq` 和主键索引；当前诊断接口与索引查询响应正常。
- 因此数据库体积只能列为风险放大因素，不能据此认定为本次卡顿的直接根因。

## 已确认与尚未确认

已确认：

- 子进程没有停在截图所示阶段，而是继续运行并在 23.7 秒后退出。
- 发布失败的直接原因是 GitHub 网络不可达。
- 命令运行期间 Zeus 控制心跳失败并发生重连，界面未及时投影后续日志与最终状态。

尚未确认：

- 没有该时刻的 macOS hang report、spindump 或 JavaScript 堆栈，无法把瞬时阻塞精确归到某一个 Main/Core 回调。
- 旧 Execution Host 在命令结束约 18 秒后收到 `SIGTERM`；现有证据不能判断是用户重启、强制退出还是其他生命周期动作，不将其作为根因。

## 后续方案取舍

1. 先补充控制心跳超时、Core 事件循环延迟和命令游标的关联诊断。优点是改动小、能精确定位下一次卡顿；缺点是只增强取证，不能直接避免卡顿。
2. 将 UI lease 心跳从可能被命令持久化和日志处理拖慢的 Core 路径中隔离，并让命令输出使用事件推送、轮询兜底。优点是可以从结构上避免命令工作负载拖死控制面；缺点是涉及 Main、Core、Execution Host 协议和恢复语义，修改面较大。
3. 只继续提高超时时间。优点是实现最简单；缺点是会延长陈旧界面的存活时间、掩盖故障，不建议作为修复。

## 建议实施顺序

### 第一阶段：让命令窗口失联可见并自动追平

- `CommandCenterPanel` 复用 `DashboardClient.subscribeEvents`：收到当前 Runtime 的 `runtime.session.output`、`runtime.session.error`、`runtime.session.ended` 或对应 `command.run.*` 事件后，合并触发一次增量读取。
- 实时事件触发即时增量读取，同时保留每秒轮询作为可靠探针，仍沿用既有日志游标、4 MiB 展示预算和终态尾页读取。没有放宽为 5 秒：在实时连接无事件但已失效时，5 秒兜底无法满足 3 秒失联提示目标。
- 记录最近一次成功同步时间；读取超过 3 秒未返回或实时连接进入重连时，把“运行中”改为“连接中断，命令可能仍在执行”，恢复连接后强制增量追平并读取权威终态。
- 失联期间禁用“停止”动作，避免把未送达的停止请求展示为已经生效。

优点：复用现有实时通道和恢复机制，改动集中，不增加依赖；即使 Core 再次阻塞，也不会继续用陈旧日志伪装正常运行。缺点：它改善真实性和恢复体验，但不能消除 Core 自身的瞬时阻塞。

### 第二阶段：复用现有诊断能力定位阻塞回调

- 不新增通用性能系统；复用 `LocalApiPerformanceCollector`、`DatabasePerformanceCollector` 和现有事件循环延迟统计。
- Main 的两处心跳调用统一经过同一个观测入口：只记录每轮故障的首次失败与首次恢复，包含 Main/Core 进程身份、故障起止和耗时，不记录 URL、token、请求体或业务正文。
- 心跳恢复后异步读取既有健康状态和性能诊断，只保留工作数量、事件循环、内存、数据库体积，以及最近最多 10 条超过 100ms 的 API/SQLite 样本；诊断失败不阻塞续租或恢复。

优点：改动小，下一次故障可以直接定位共享阻塞点。缺点：需要再次捕获现场，单独实施不会减少阻塞。

### 第三阶段：只修被证实的热点

- 若证据指向 Runtime 日志写入：将两份 `appendFileSync` 改为按 session 串行的异步追加，并给日志持久化设置有字节和条数上限的批次；终态仍等待最后批次落盘。
- 若证据指向 SQLite：在现有 100ms 提交窗口内批量镜像日志，避免每个 chunk 重复查询 session 与 `MAX(seq)`；关键运行状态继续同步提交，不能牺牲退出状态的耐久性。
- 若证据指向其他慢路由：修该共享路由，不为命令中心单独建立第二套 Core 或数据库连接。

优点：根因只修一次且保持单写者边界。缺点：需要第二阶段证据，不能现在假定 9.92 GB 数据库或日志写入就是直接根因。

不建议只提高心跳、读取或命令超时：实现虽简单，但只会延长陈旧状态，不能改善交互或定位阻塞。

## 实现结果

- `CommandCenterPanel` 复用现有实时事件流；匹配当前 `runId` 或 Runtime `sessionId` 的事件会合并触发增量读取，轮询期间发生的新事件只排队一次，避免重复并发请求。
- 运行中详情读取超过 3 秒、读取遇到本地连接错误或事件流进入重连时，状态显示“连接中断，命令可能仍在执行”，并禁用停止；权威读取恢复后自动回到“运行中”并按原游标追平。
- 连接错误不再弹出业务错误框；真正的 API/业务错误仍沿用全局错误处理。
- Main 的 `refreshConfig` 和 `maintainLease` 已复用同一心跳观测入口；恢复快照写入既有 `runtime/execution-host/host.log`，不新增诊断服务或依赖。
- 未修改数据库、日志持久化和 Execution Host 协议。优点是最小化风险；缺点是本轮先解决陈旧界面和取证缺口，尚未声称消除了没有堆栈证据的瞬时 Core 阻塞。
