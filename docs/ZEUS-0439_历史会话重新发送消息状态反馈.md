# ZEUS-0439 历史会话重新发送消息状态反馈

## 任务目标

用户在空闲历史会话中发送新消息后，必须立即看到与真实阶段一致的连续反馈：恢复实时会话 → 启动处理 → 模型思考。不得把建立连接前的本地暂存消息误画为普通“排队中”，也不得在 Provider 尚未接纳时提前声称“正在思考”。

## 现场与根因

- 用户截图中上一轮已显示“处理已中断”，新消息“继续处理”长时间只显示“排队中”。
- 空闲历史会话按既有产品语义使用 `lazy` Controller；用户首次真实发送后才切换为交互态，并通过 `ensureRealtimeConnection()` 执行 required hydration。
- 连接尚未就绪时，Controller 已正确使用 `queuedUntilHydrated=true` 暂存本次发送；但 `sessionReducer` 只把条目状态投影为 `queued`，没有把“等待恢复实时会话”传给消息展示层。
- 这个阶段会话仍保留上一轮的 `native_idle` 或 `turn_failed`，因此现有“正在启动处理 / 正在思考”也不会显示。

## 实施边界与取舍

1. 保留 `queuedUntilHydrated` 的本地阶段身份，在唯一的用户消息气泡上显示“正在恢复对话”。
2. 实时连接就绪并真正提交后，现有 `send_started` 会清除该暂存阶段，由“正在启动处理”和“正在思考”继续接管。
3. 不恢复已删除的全局连接卡，不将 transport 瞬时状态泄漏到历史会话长期状态，不为了提前显示“思考”而伪造 Provider 已接纳。
4. 不预连接所有历史会话，不绕过安全对账来压缩首次续发延迟。

优点：反馈与真实恢复阶段一致，复用现有消息状态和可访问的 `role=status`，不新增二套进度面板。

缺点：空闲历史的首次续发仍需完成必要的快照和 Provider 权威边界对账；本任务修复“长时间无反馈”，不用跳过对账换取表面速度。

## 验收目标

- 空闲历史会话提交后，本地用户消息立即可见，并显示“正在恢复对话”。
- 连接就绪后不再显示恢复文案；Provider 尚未建立轮次时显示“正在启动处理”，轮次运行后显示真实思考或当前活动。
- 普通活动轮次中发送的下一轮排队消息仍显示“排队中”，不被误标为恢复对话。
- 恢复阶段文案通过现有 `aria-live=polite` 公告，不只依赖动画或颜色。
- 通过 `pnpm lint`、`pnpm typecheck`、`pnpm build`、`git diff --check`；真实渲染验收使用现有 Renderer QA 页面和 Zeus 内置浏览器。

## 操作边界

- 不新增或恢复单元测试体系。
- 未经用户明确要求，不执行 commit、push、merge、revert 或正式发布。
- 不启动、替换或修改 `/Applications/Zeus.app` 与正式用户数据。
