## 用户现象

1. 在创建任务或会话输入框中粘贴截图后，缩略图有时正常，有时显示裂图或只显示图片文件图标。
2. 同一类现象中，有的附件实际可以到达模型，但 Zeus 本地缩略图不可见，用户无法判断模型是否收到。

## 现场证据

### TIFF 样本

- 正常样本 `pasted-task-screenshot-1788242899703.png` 是 `1144×1390` PNG。
- 异常样本 `Zeus 2026-09-01 14.06.58.tiff` 是可被 macOS 正常解析的 `1822×1016` TIFF，文件本身没有损坏。
- 正常样本文件名包含内容摘要和 `pasted-task-screenshot-*.png`，对应剪贴板位图经 Electron `nativeImage.toPNG()` 后的二进制物化路径。
- 异常样本保留原始 `.tiff` 文件名且没有内容摘要，对应 macOS 剪贴板 `furl` 文件引用优先进入 `saveTaskResourcePaths()` 的路径复制流程。

### PNG 样本

- 会话附件 `command-aa62c24c8ef1926915f78b6f-1-2aca0f4e69598b96-image.png` 是可正常解码的 `1744×1702` PNG。
- 本轮模型实际看到了该图片的像素内容，能够读取标题“会话内容显示错误”和左侧“当前操作未完成，请稍后重试”，证明这一次附件发送成功，故障只发生在 Zeus 预览层。

## 根因一：剪贴板文件引用压过 PNG 位图回退

`readTaskClipboardResourcesFromNativeClipboard()` 与会话资源 broker 都先读取本地文件引用，只要存在路径就直接返回；只有没有文件引用时才调用 `clipboard.readImage().toPNG()`。

macOS 的截图来源并不总是只提供 PNG 位图：有时还会暴露指向 TIFF 的 `furl`。Zeus 当前优先保留这个 TIFF 路径，于是同一个“粘贴截图”动作会出现两种结果：

- 没有可读文件引用：走 `nativeImage.toPNG()`，保存为 PNG，预览正常；
- 存在 TIFF 文件引用：直接复制 TIFF，后续把任意 `image/*` 拼成 `data:image/tiff;base64,...`，Chromium 无法直接渲染，显示裂图。

同时，Codex Provider 的本地图片判定把 TIFF 标记为 `localImage`，但 OpenAI 官方图片输入要求只列出 PNG、JPEG、WEBP 和非动图 GIF。因此 TIFF 不仅是预览风险，也不能作为可靠的模型图片输入。

## 根因二：有效 PNG 的共享附件卡预览请求被反复取消

`ConversationComposerAttachments` 每次渲染都会重新创建资源对象数组和内联 `onLoadPreview` 函数。`PendingResourceCard` 的 effect 又同时依赖整个 `props.resource` 对象和 `props.onLoadPreview`：

1. 父组件任意重渲染都会清理当前预览请求；
2. effect 立即清空已加载预览和失败状态并重新请求；
3. 会话状态持续更新时，请求可能在完成前反复失效，卡片最终只显示图片文件图标。

附件发送不依赖该缩略图。提交时服务端会重新解析已持久化附件路径；支持的 PNG 会被组装为 Codex `localImage`。因此“Zeus 看不见”和“模型看不见”当前不是同一事实。本轮 PNG 已由模型实收；其他历史消息仍应以实际 Provider 输入或模型回执核对，不能仅看卡片外观推断。

## 最小修复建议

### 建议一：粘贴图片在 Main 边界规范化为受支持格式

对粘贴来源的 TIFF、HEIC 等非网页/模型通用图片，使用 Electron 已有 `nativeImage` 解码并统一输出 PNG；Finder 明确复制的普通文件仍保留原文件语义。

优点：一次解决任务预览、会话预览和模型输入格式漂移；不新增依赖，复用 Electron 原生能力。

缺点：需要准确区分“粘贴截图/图片内容”和“用户把 TIFF 当普通文件复制”，避免擅自改变后者的文件格式与名称。

### 建议二：共享预览 effect 只由稳定资源身份驱动

参照已经修复过相同竞态的 `TaskAttachmentPreviewList`，让 `PendingResourceCard` 使用稳定 loader 引用，并只依赖资源 ID、类型和已有预览 URL，不依赖每次渲染产生的新对象和新函数。

优点：单点覆盖会话输入、本次推送附件等所有共享资源卡；不改变附件存储和发送协议。

缺点：修复后仍需为真实读取失败保留明确失败态；不能把“尚未加载”永久伪装成文件图标。

### 建议三：Provider 图片白名单与官方格式对齐

只有 PNG、JPEG、WEBP 和非动图 GIF 直接进入模型图片输入；其他格式应先转换，转换失败则按普通文件发送并明确提示，而不是继续声称图片已送达。

优点：界面可见性、Provider 发送意图与模型真实能力一致。

缺点：历史 TIFF/HEIC 附件若要恢复为图片，需要发送前转换或迁移；仅收紧白名单会让其退化为普通文件。

## 推荐落地顺序

1. 先修 `PendingResourceCard` 的预览竞态：复用 `TaskAttachmentPreviewList` 已有的稳定 loader/request token 做法，effect 只由资源 ID、类型和内存预览 URL 驱动；父级普通重渲染不再清空成功预览或取消同一资源的有效请求。
2. 再统一粘贴语义：文本输入区粘贴到单张、存在位图表示的 TIFF/HEIC 等非通用图片时，优先用 Electron `nativeImage.toPNG()` 物化；文件选择与拖放继续保留原文件。这样不需要为每种图片格式扩展 Renderer。
3. 最后收紧 Provider：PNG、JPEG、WEBP、非动图 GIF 才直接发送为模型图片；其他格式转换失败时按普通文件发送并显示“已作为文件添加”，不再以裂图或图片图标暗示模型已收到像素。
4. 为已有 TIFF/HEIC 只补按需预览转换，不批量迁移历史文件；用户再次发送时再按上述 Provider 规则处理。

整体优点：两处共享根因修复覆盖创建任务、任务详情、会话输入和本次推送附件；不新增依赖，不改数据库，不批量重写历史资源。

整体缺点：单张 TIFF 从文本框粘贴时会按图片内容转为 PNG；若用户要保留 TIFF 原文件，应使用文件选择或拖放。历史不支持格式首次预览会多一次本机解码。

不建议增加“模型已看见”状态。Zeus 最多只能确认附件已提交给 Provider，不能替模型声明已理解图片；应把“预览成功”“已作为图片提交”“已作为文件提交”分开表达。

## 实施结果

1. `taskClipboard` 增加统一图片输入白名单。只有 PNG、JPEG、GIF、WEBP 可直接生成 Renderer 预览和标记为模型图片。
2. 剪贴板只有一个 TIFF、HEIC、HEIF 或 BMP 文件引用且 Electron 同时能读到位图时，优先使用已有 `nativeImage.toPNG()` 物化为 PNG；位图不可读时仍保留原文件，不丢失用户输入。
3. preload 对文本框粘贴的单张非通用图片优先调用上述原生剪贴板链路；拖放和文件选择不转换，继续保留原文件格式与名称。
4. 任务与会话资源的 `kind` 改为依照同一白名单判定。转换失败的 TIFF/HEIC/BMP 以文件呈现，不再生成浏览器不可靠的 `data:image/tiff` 等预览。
5. 已保存的历史 TIFF/HEIC 仍可在任务和会话的本机预览入口按需通过 Electron 转成 PNG，不做数据库迁移或批量重写。
6. `PendingResourceCard` 使用稳定的资源和预览 loader 引用，effect 只由资源 ID、类型和内存预览 URL 驱动；父组件普通重渲染不再取消有效 PNG 预览请求。
7. Codex 本地图片白名单移除 BMP、HEIC、TIFF；新粘贴内容在 Main 边界转成 PNG，转换失败或历史不支持格式按普通文件进入 Provider。Pi 保留其独立格式策略，本任务没有无证据收紧其他 Provider。

优点：任务创建、任务详情、会话输入和共享附件卡沿用同一格式边界；不新增依赖、不改数据库，也不会把无法可靠发送给 Codex 的文件伪装成图片。

缺点：GIF 是否为动图仍未在本地解析；当前沿用既有 GIF 支持，不为本缺陷新增图片解析器。历史 TIFF 若作为文件发送，模型不一定读取其像素，但 UI 不再宣称它已作为图片提交。
