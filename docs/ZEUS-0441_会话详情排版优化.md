# ZEUS-0441 会话详情排版优化

## 2026-09-01 现场诊断

### 用户现场

- 图一是从任务详情直接推送的新会话，只包含任务正文，页面显示“当前操作未完成，请稍后重试”。
- 图二是把同一任务指派给“产品数字员工”后创建的独立工作会话，包含任务正文、员工提示、冻结上下文清单和 Skill 元数据；会话没有产生任何回复。
- 两张图来自两个独立入口，不是同一推送后的重试。

### 只读证据

- 任务：`task_4f560090f172ccfad99f1dcd1e76ff07`，任务号 `ZEUS-0441`。
- 数字员工指派会话：`conversation_59ffdd053fbcea0798b0def7`，消息正文 1913 字，提交
  `conversation_submission_355f354bd7020332de097492`；关联工作项 `task_work_item_4562b07b00a9451f91d560ce5adfc35b` 和运行
  `task_work_run_1f41597fce0059ba309c30419aaf206a`。
- 直接推送会话：`conversation_e7216e28f8b7e6e97eb83c72`，消息正文 230 字，提交
  `conversation_submission_d1bf0fc592efd595dcbe5936`。
- 两条会话都处于 `starting / unbound / queued`，没有 Provider Thread、没有 Turn，`provider_token_usage_json` 均为 `{}`。截图中的
  6.1M、5.9M、8.2K 是任务“预期”字段里的文字，不是真实会话统计。
- 两次提交都暂停为 `runtime_rejected`，精确错误一致：
  `deferred dynamic tool must include a namespace: read_conversation_tool_image`。
- v0.3.94 合入的 `d14519ef6` 在 `conversationToolResultDynamicTools()` 中新增顶层动态工具 `read_conversation_tool_image`
  并设置 `deferLoading: true`。Codex App Server 要求延迟加载工具必须位于命名空间内，因此新 Codex 线程在 `thread/start`
  阶段被拒绝；已有 Provider Thread 的续聊不走这次新建线程校验，影响面主要是新会话。

### 根因与影响

1. **首要根因**：图片回读动态工具的延迟加载定义缺少命名空间，导致所有携带该工具定义的新 Codex 会话无法启动，不是 ZEUS-0441
   提示词本身的问题。
2. **直接推送反馈降级**：普通任务推送能看到提交已暂停，但 Renderer 只显示通用错误，没有暴露 Provider 的精确拒绝原因。
3. **数字员工状态投影缺陷**：`dispatchAgent()` 在本地会话和提交耐久创建后立即把 Task Work Run 标为 `active`；后台 Provider
   拒绝后，会话仍为 `starting / unbound / queued`，只有提交变为 `paused / runtime_rejected`。`processAgentRun()` 只检查
   `conversation.stage/providerState`，不检查提交队列的 `runtime_rejected`，因此 Work Item 和 Run 永久保持 `active`，
   `error_code/error_message` 为空，界面表现为“指派成功但无反应”。

### 为什么刚发布的修复没有拦住

- ZEUS-0441 的数字员工没有进入真实模型轮次：关联会话没有 Provider Thread 和 Turn，任务分支 `zeus/ZEUS-0441-task-01` 仍停在
  `main` 的 `a3189a36`，工作树无代码差异，因此不存在已经完成但未生效的 ZEUS-0441 修复。
- 触发本次故障的 `read_conversation_tool_image` 来自 v0.3.94 合入的 ZEUS-0422。该任务记录明确写明：独立测试数据根没有真实
  Provider 凭据，没有执行真实 Codex/Pi 请求；GUI 只验证了空数据首屏。最终合入阶段也只执行 lint、typecheck、build、脚本验证和打包，没有启动
  GUI 或真实 Provider。
- 现有验证器覆盖了派发/恢复状态机和一次性探针，但没有把新动态工具清单真正发给 Codex App Server 执行一次 `thread/start`
  。TypeScript 类型允许顶层函数设置 `deferLoading`，Provider 的“延迟工具必须位于命名空间”约束只在运行时返回，因此所有静态门禁均可通过。

### 系统性架构结论

- Codex App Server 与 Pi 已经拥有原生 session/thread/turn、上下文、工具和恢复能力；Zeus 当前不只是适配这些能力，还在产品层并行维护
  Conversation、Submission、Turn、Segment、Receipt、Task Work Run、Digital Employee Execution 等多套状态机。
- 任务归属、工作区、权限、交付物和审计属于 Zeus 的必要产品能力；重复解释 Provider 是否启动、运行、等待或失败则产生双重事实。此次同一个
  `runtime_rejected` 在普通会话显示失败、在数字员工运行中保持 `active`，就是状态投影漂移的直接证据。
- 后续不能只修通用错误文案。Runtime Adapter 应成为 Provider 生命周期的唯一翻译边界；Task Work
  只消费统一的已接纳/运行/等待/完成/明确拒绝/结果未知事件，不再自行从 `conversation.stage` 的部分字段猜运行状态。发布门禁必须启动真实
  Codex 与 Pi 临时会话执行原生协议 smoke，静态结构断言不能替代。

### 建议修复边界（未执行）

- 正式修复：将图片回读工具放入稳定的 `zeus` 命名空间并保留延迟加载；现有动态工具路由已经接受 `namespace === 'zeus'`
  。优点是保持上下文优化目标且改动集中；缺点是必须真实验证新建 Codex 会话和图片句柄回读协议。
- 临时止血：去掉该工具的 `deferLoading`。优点是改动最小、可立即恢复新会话；缺点是工具定义会常驻上下文，背离 ZEUS-0422
  的按需加载目标。
- Task Work 运行必须把首条提交的 `runtime_rejected`
  投影为运行失败，并保存真实错误码与错误信息。优点是数字员工不会假装持续运行，管理者可以明确重试或重新指派；缺点是需要区分可安全重试的“Provider
  明确拒绝”和外部写入结果未知，不能把两者统一处理。
