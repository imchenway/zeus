# ZEUS-0444 推送会话报错

## 当前阶段

- 状态：根因修复、定向行为探针、全量静态/架构门禁和独立测试身份打包已完成
- 日期：2026-09-02
- 范围：Pi Provider 新会话首轮直接派发与统一队列调度竞态
- 边界：不放宽 Command Delivery 身份校验，不删除或改写正式数据，不执行 git commit/push/merge/revert

## 用户现象

推送会话时弹出：

```text
ZEUS_PI_PROVIDER_COMMAND_IDENTITY_CONFLICT:
既有 Pi Provider 命令与当前请求身份不一致，拒绝重放。
```

## 现场证据

- 正式 Execution Host 日志在 `2026-09-02T01:14:50.093Z` 和 `2026-09-02T01:15:26.892Z`
  记录了两次相同错误。
- 正式 SQLite 只读账本显示，两次推送对应的 `provider.pi.session.open` 和
  `provider.pi.run.start` 都在同一时刻成功记录为 `accepted`，并各自保存了真实
  `nativeSessionId` 与 `nativeTurnId`。
- 第一次报错发生在 session 命令建立后 7ms，但原 owner 继续并于 321ms 后成功接纳；
  这排除了 Provider 拒绝，证明是第二个并发 owner 在本地身份校验处失败。
- 两条 submission 最终都是 `completed/terminal`；用户看到的“操作未完成”与耐久真相相反。

## 根因

Pi 直接派发在 submission 仍为 `queued` 时调用 `projectLocallyAcceptedUserMessage()`。该函数为了刷新
用户消息同时发布 `conversation.queue.changed`。全局事件出口把所有该事件都视为队列派发请求，
因此在原调用完成 Provider 预备前，统一队列调度器又对同一 submission 启动了一次 Pi 派发。

两个 owner 使用相同 submission/command 身份，但第二个 lifecycle 在用户消息已投影后重建了
portable context，请求摘要不同，因而严格的 Pi Command Delivery 校验正确失败关闭。

## 修复设计与取舍

- 做法：保留 `conversation.queue.changed` 作为 Renderer 刷新事件；对已由当前调用直接派发的 Pi
  submission 标记“不再请求队列派发”，全局事件出口不启动第二个 owner。
- 优点：不改变用户消息投影、submission 状态、实际派发时序和严格幂等校验；真正的排队、
  回合终态续发和恢复唤醒仍按原路径工作。
- 缺点：队列事件多一个内部布尔语义；后续若新增“先投影、再直接派发”的 Provider 路径，也必须明确标记。
- 不采用：放宽或删除 `ZEUS_PI_PROVIDER_COMMAND_IDENTITY_CONFLICT` 校验。这会把真实的正文、模型或
  portable context 篡改错认为安全重放，可能导致重复发送或错会话派发。

## 实施结果

- Pi 新会话首轮和既有会话续轮在调用 `projectLocallyAcceptedUserMessage()` 时显式设置
  `requestQueueDispatch: false`。用户消息和 `conversation.queue.changed` 仍正常投影，但不会与当前
  直接派发 owner 竞争。
- `shouldRequestConversationQueueDispatch()` 集中保留两条语义：普通 `conversation.queue.changed`
  仍唤醒队列；`conversation.turn.completed` 无论载荷如何都唤醒后续队列。
- Pi Command Delivery 的严格命令身份、请求摘要、unknown 禁重放和 accepted 原子回执均未改动。
