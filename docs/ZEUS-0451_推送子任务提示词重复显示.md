# ZEUS-0451 推送子任务提示词重复显示

## 当前阶段

- 已完成正式 Provider JSONL、正式 SQLite 和当前会话投影代码的只读诊断。
- 已按稳定身份修复活动用户项覆盖历史用户项时的信息丢失，不按正文相同合并。
- 本轮不修改正式数据或 Provider 会话，不执行 Git 历史或远端操作。

## 现场结论

Provider 实际只收到一次首发业务输入。界面上的两张用户卡片来自同一条持久消息的两个投影，不是子任务被重复派发。

本次现场会话 `conversation_7da61e6e75b0f9cd24690f22` 的首发稳定身份链只读对账结果：

- `conversation_submissions`：1 条。
- `conversation_messages.role=user`：1 条。
- `conversation_model_history.role=user`：1 条。
- `conversation_provider_item_states.item_type=userMessage`：1 条。
- Provider JSONL 业务用户输入：1 条。

上述数量只针对已固定的首发 `submissionId`、`clientUserMessageId` 和 `providerItemId` 统计；会话后续已有新消息，不把整个会话当前总量误报为 1。

## 根因

历史用户项已有稳定的 `clientUserMessageId`、`submissionId` 和 `providerItemId`。同一 Provider 活动用户项的载荷长度为 2,348 字节，首屏只保留了被截断的 JSON 预览，Renderer 无法从中解出客户端身份。

`mergeActiveTurnItems()` 虽然用共同 `providerItemId` 识别出两个投影，但活动项会整体覆盖历史项，也把历史项中的客户端和提交身份一起丢掉。后续水合因此无法把原始任务卡与 Provider 卡识别为同一条消息。

## 修复与取舍

- 只在活动项和历史项均为用户消息、且 `providerItemId` 相同时，用历史载荷补齐稳定身份和可用的结构化展示信息。
- 活动项继续拥有最新状态、正文和时间，不影响进行中投影。
- 不改通用工具或过程项合并，不改存储、协议、数据库或公开类型。
- 不按正文相同隐藏卡片；不同客户端或 Provider 身份的相同正文仍然是两条真实消息。

优点：在身份丢失的共享入口一次修复，改动集中，不增加协议字段和兼容分支。

代价：没有稳定 Provider 身份的历史脏数据仍不会被猜测合并，以避免误吞用户有意重复发送的内容。
