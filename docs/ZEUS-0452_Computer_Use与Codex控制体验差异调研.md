# ZEUS-0452 Computer Use 与 Codex 控制体验差异调研

当前进度：已落地控制会话、持续窗口采集、后台语义操作和坐标约束。用户明确要求将预览放在对应会话的环境信息下方；独立桌面预览窗口已删除，画面及停止、继续入口改为会话内展示，见第 11.6 节。前一轮真机检查已确认系统窗口图标、后台中文输入和停止撤销；新的会话内呈现需要单独验收。通用后台键鼠与独立菜单栏图标可见性仍有差距，不能标记为完全对齐 Codex。第 1–10 节保留开发前的调研证据。

## 1. 调研阶段结论

Zeus 与当前 Codex 的桌面控制实现存在实质差异。Zeus 已实现读取界面、点击和输入等基本操作，但没有实现与 Codex 对等的后台焦点管理、可见虚拟光标、持续控制预览和控制会话生命周期。

用户提出的体验差距有实现证据支持。其中，“缺少持续控制展示”和“缺少专门的防抢焦点机制”可以由当前代码确认；“物理鼠标为何移动、哪一次动作使窗口切到前台”仍需同场景运行记录才能锁定，不能仅根据一个系统接口或变量名称断言根因。

用户随后明确：Codex 操作时，菜单栏和被控应用窗口左上角同时出现“屏幕控制中”的小图标。该形态与 macOS 原生屏幕共享/采集指示一致，调研重点应是系统采集会话及其可见状态；画中画属于另一个功能，不能代替这一反馈的解释或验收。

调研阶段只完成本文档，没有修改产品代码或执行桌面点击、输入、拖拽；用户随后已授权第 11 节的开发。

## 4. 鼠标与窗口焦点的差异

### 4.1 Zeus 的“虚拟指针”只有坐标记录

`ComputerService.swift:40` 定义 `virtualPointers: [pid_t: CGPoint]`。全文及调用方搜索发现它仅在点击、拖拽、滚动后赋值，没有读取路径，没有创建光标窗口、绘制光标或隔离用户输入。

坐标点击最终进入 `postMouse`（`627` 行），创建带坐标的 `CGEvent`，只设置点击次数，然后 `postToPid(pid)`。拖拽也复用此函数；键盘和文本输入分别在 `643`、`541` 行直接向目标进程投递事件。

这能证明实现意图是定向投递，不能据此证明用户的鼠标、按键和桌面焦点已经隔离。反过来，当前 Helper 没有发现 `CGWarpMouseCursorPosition` 或全局 `post(tap:)`，也不能将用户观察到的物理鼠标位移直接归咎于全局鼠标移动调用。

所有事件源目前使用 `.hidSystemState`。[Apple 文档](https://developer.apple.com/documentation/coregraphics/cgeventsourcestateid/hidsystemstate)说明它使用硬件输入的合并状态；独立事件状态 `.privateState` 是另一选项。但“独立事件状态”也不等于“目标窗口一定不会激活”，只替换这一参数不能作为完整修复。

### 4.2 Codex 有专门的焦点和交互组件

对当前安装包执行只读符号检查，可见：

| 组件或方法 | 可以确认的实现差异 | 不能据此推断 |
| --- | --- | --- |
| `SyntheticAppFocusEnforcer.enforceActiveState`、`deactivateFocusEnforcer` | 存在专门的合成应用焦点管理及退出方法 | 具体使用何种系统内部机制 |
| `SystemFocusStealPreventer`、`targetLostFocusHandler`、`targetGainedFocusHandler` | 存在专门处理系统焦点抢占和焦点变化的组件 | 所有目标应用都绝不会抢焦点 |
| `syntheticallyActivateIfNeededForSendingClick` | 点击前有专门的应用激活状态处理，并考虑窗口及网页控件 | 它等价于简单调用应用的前台激活接口 |
| `target(forMouseEventAt:)`、`sendClick(...focusEnforcer:virtualCursor:)` | 点击路径同时考虑目标窗口、焦点管理和虚拟光标 | 单靠传入进程编号就能复制其行为 |
| `ComputerUseCursor`、`targetWindowID`、`createVirtualCursorIfNeeded` | 存在带目标窗口、位置及可见状态的光标组件 | 系统提供了一个公开、通用的“第二只鼠标”接口 |
| `ComputerUseUserInteractionMonitor` | 存在用户交互监听组件 | 普通模式下的精确暂停阈值和恢复策略 |

这与官方描述的“macOS 下后台工作时，用户可以继续使用其他应用”相互支持。该描述是 macOS 的能力，官方同时说明 Windows 会占用前台，不能混用两种平台的实现结论。[OpenAI Computer Use 文档](https://learn.chatgpt.com/docs/computer-use)

### 4.3 Zeus 焦点路径的具体边界

- 普通控件点击先尝试 `AXPress`，成功就直接返回；目标应用如何处理该动作仍由应用决定。
- `focus()`（`563` 行）会设置控件的 `AXFocused` 属性。它的两个调用方是 `paste` 和 `typeText` 的元素分支，但目前公开工具参数没有给这两个方法暴露 `element_index`。因此不能把这段分支当成本次抢桌面焦点的已证实原因。
- 当前原生输入路径没有前台应用变化的监听，也没有与 Codex 上述组件对应的防抢焦点处理。
- `ComputerHost.ensureSensitiveActionApproval()` 会在敏感或目标不明时打开 Electron 模态确认框（`488–499` 行）。如果用户看到的是 Zeus 自己跳到前台，审批框是需要单独核查的触发路径；不能和目标应用点击造成的激活混为一谈。

这说明应分别记录“物理指针位置”“桌面前台应用”“目标窗口内部输入焦点”，三者不能用一个“focus”变量替代。

### 4.4 坐标路径另有可确认缺口

Codex 随包 `sky-window-api.md` 将点击坐标定义为应用窗口截图中的坐标；原生包也包含窗口和鼠标目标解析方法。

Zeus 的工具参数明确要求桌面全局坐标，但 `captureWindow()` 返回的是目标窗口截图，并按所有显示器中的最大缩放倍数确定图片尺寸。截图结果没有统一返回该窗口的桌面原点与实际缩放转换；点击则直接将收到的数值传给 `CGPoint`。

因此 Zeus 没有统一的“截图坐标到目标窗口/桌面坐标”转换。在多显示器、窗口移动、不同缩放比例或目标窗口被遮挡时，这会增加误定位与操作失败的风险。AX 树中的控件位置可以为部分语义操作提供坐标，但并未补齐截图坐标回退的契约。此项是独立缺口，不是物理鼠标位移的既定原因。

## 5. 为什么没有同样的“屏幕控制”展示

### 5.1 Codex 的应用预览是独立产品能力

OpenAI 官方说明：macOS 后台操作时，画中画预览展示当前应用，用户可以打开或移动预览。本机包内同时存在 `CUAServiceRemoteHostedPIPController`、`RemoteHostedPIPContentStream` 和 `setComputerUseCursorLocation` 等组件，说明它包含预览与光标位置同步这一层。[OpenAI 使用说明](https://learn.chatgpt.com/use-cases/use-your-computer-with-codex)

Zeus 当前只有：

- `ZeusComputerSettings` 中的 `enabled`、`serviceState` 和系统权限字段；
- 设置页的“立即停止控制”按钮；
- 会话栏的“停止控制”按钮，其显示条件并不是“当前正在控制”；
- `get_app_state` 调用期间的一次窗口截图，随后作为工具图片交给模型。

没有当前控制应用/窗口、控制归属会话、开始与结束事件所驱动的持续桌面提示或画中画。`serviceState=ready` 只表示服务可用；服务还会在最后一次调用后空闲保留两分钟，不能将它直接显示成“正在控制屏幕”。

`configuration.showsCursor=false` 只决定截图里是否包含光标，不会生成独立光标，也不负责显示或隐藏用户桌面上的控制提示。

### 5.2 用户已确认：菜单栏与被控窗口左上角的状态图标

2026-09-05 用户补充：Codex 使用 Computer Use 时，菜单栏和被控制应用的左上角都会显示“屏幕控制中”的小图标。提示位置已经明确，本段替换此前“尚未收到区分信息”的记录；该事实来自用户观察，本次没有把它表述为代理已现场截图验证。

继续读取 Apple 的 [WWDC23 ScreenCaptureKit 说明](https://developer.apple.com/videos/play/wwdc2023/10136/)后，得到如下对应关系：

- `SCStream` 表示持续接收屏幕画面的采集流。Apple 说明系统会将活动流接入菜单栏展示，并提供预览、变更共享内容和结束共享的控件。
- 系统还提供从窗口直接选择共享内容的入口；`SCContentSharingPicker` 用于接收内容选择、变更等通知。系统展示与应用自己的画中画是不同层次。
- `SCScreenshotManager` 是获取静止画面的接口，使用它时以截图调用代替创建 `SCStream`；创建 `SCStreamConfiguration` 这个配置对象本身不代表已启动采集流。

当前实现证据：

| 项目 | 当前证据 |
| --- | --- |
| Codex 安装包 | 可见 `SCStream`、`SCStreamOutput`、`SCStreamDelegate`、`startCaptureWithCompletionHandler:`、`stopCaptureWithCompletionHandler:` 以及 `ScreenCaptureWorker`，说明包含采集流及其启动/停止能力；仅凭符号不能确定用户现场每一次动作使用的分支 |
| Zeus 当前源码 | `captureWindow()` 只调用 `SCScreenshotManager.captureImage`；没有创建 `SCStream`、启动/停止持续采集或接收系统停止采集通知的路径 |
| 用户观察 | 菜单栏与目标窗口左上角同时出现小图标，符合系统共享/采集状态的形态；精确图形、系统文案和运行中的归属进程尚未由代理现场检查 |

据此，主要判断是：Codex 的活动采集会话接入了 macOS 原生共享展示，而 Zeus 当前的单次截图模式没有等价的持续会话。这比“缺少自画悬浮图标”更贴近用户所指的差异。该判断结合了用户观察、Apple 文档和安装包证据，仍不应扩大为“截图 API 在所有系统版本都不产生任何提示”或“一个公开 API 就能解决全部后台控制问题”。

原生共享图标表示屏幕内容正在被采集/共享，不直接证明鼠标或键盘已经隔离。系统结束共享后，控制工具是否立即停止也取决于宿主如何处理通知，因此采集生命周期与输入控制生命周期必须联动。

## 6. “停止控制”目前不是完整的用户接管

共享停止入口调用 `stop('user')`，会终止当前 Helper、清空未完成请求及快照，这部分确实已实现。

但它保留 `settings.enabled=true`，不会撤销当前轮次的控制资格。后续 `invoke()` 再通过启用检查，就可以在 `ensureService()` 重新启动 Helper。因此当前按钮的真实语义是“中止当前服务请求”，还不能保证用户停止后本轮不会自动继续控制。

同时，工具转发入口知道 `conversationId`、`threadId`、`turnId`，而 Helper 请求只收到随机请求编号、方法和参数；目前没有与这些身份绑定的控制会话开始、结束或撤销协议。Codex 包内则存在应用使用会话、`onCodexTurnEnded` 和预览结束接口；其具体内部策略未执行验证。

这也是需要与可见提示一起处理的根因：用户应能知道谁在控制哪个应用，并在停止后真正保留接管权。

## 7. 建议的后续实施边界与优缺点

| 优先事项 | 建议 | 优点 | 代价与限制 |
| --- | --- | --- | --- |
| 先定位实际桌面干扰 | 在隔离实例中，对照记录动作前后的用户指针、前台应用、目标窗口和所走输入分支 | 可以区分事件投递、应用自激活、审批框与坐标错误，避免修错位置 | 需要真实双应用及多屏场景，静态检查不能替代 |
| 修复共享原生输入路径 | 在现有 Helper 中统一处理目标窗口、截图坐标转换、独立事件状态及非前台交互边界；不支持安全后台操作时明确返回限制 | 一次覆盖点击、拖拽、滚动和输入的共同问题，保留现有无障碍语义操作 | 跨应用兼容性必须实测；不能承诺几个公开 API 就完全复制 Codex 的内部实现 |
| 建立最小控制会话 | 在现有 `ComputerHost` 上绑定会话、轮次及目标；停止时撤销当前控制资格，拒绝同轮后续动作，并复用现有 Helper 回收 | 用户停止后不会被自动重新接管；控制展示可以使用真实状态 | 必须处理并发会话归属以及停止与新请求相遇的情况 |
| 接入原生共享状态 | 优先验证受控窗口的 `SCStream` 能否自然呈现用户指出的菜单栏及窗口图标；采集限于当前目标，并把系统停止通知连接到控制撤销 | 复用 macOS 对采集范围、应用归属和停止共享的展示，不需要模拟系统图标 | 持续采集增加资源消耗，需限制帧率和生命周期；仅有图标不会解决输入抢占 |
| 显示真实控制状态 | 由控制会话驱动不抢焦点的桌面状态入口，显示目标应用和停止操作；如需 Codex 同类预览，再增加画中画 | 用户切到其他应用仍能看到控制状态；改动可以复用当前原生宿主与截图能力 | 画中画有额外截图开销；状态入口不能以服务存活代替实际控制 |

建议先把共享输入、真实停止与可见状态作为一个完整交付边界。完整预览动画、复杂光标动效和锁屏工作不属于本次反馈的必要前置条件。

不建议只补一个悬浮提示就宣称体验对齐：它的优点是改动小，缺点是鼠标与焦点干扰仍然存在。也不建议操作后强行把用户鼠标和前台窗口切回：看似恢复现场，实际会制造第二次抢占并与用户正在进行的操作竞争。

不建议重新引入旧 Codex 私有插件运行时作为兼容补丁：短期可能获得部分现成行为，但再次依赖另一个应用的缓存、路径、安装身份和升级节奏，重新带回旧任务已记录的桥接故障。当前自有能力应以可观察行为验收，而不是以工具名称与参数数量相同判定完成。

## 8. 后续真实验收标准

1. 用户持续在应用甲输入，Agent 操作应用乙时，用户物理鼠标位置和应用甲的桌面前台归属不被切换；应用乙内部输入正确。
2. 语义点击、坐标点击、文本输入、按键、滚动和拖拽分别核对，不以其中一个成功推断全部通过。
3. 窗口移动、遮挡、负坐标显示器和不同缩放比例下，截图与实际操作落点一致。
4. 控制前出现状态，目标变化时更新；结束、失败、取消和 Helper 回收后正确消失，提示自身不抢焦点。
5. 点击停止后，当前及同轮后续请求都不会恢复控制；新控制须由用户明确恢复或另起已授权任务。
6. 菜单栏与被控窗口左上角的系统状态图标分别留证，核对开始、目标切换、系统停止和任务结束；应用自有预览另行记录，不代替这些图标的验收。

## 10. 推荐的对齐方案

用户本轮询问“应该如何与 Codex Computer Use 对齐”。本节是基于前述证据的实施建议，尚未变成产品实现或验收结果。

### 10.1 对齐目标

建议用以下可观察行为定义完成，而不以内部类名、工具数量或变量名称判定：

1. 用户在应用甲继续打字和移动鼠标时，Zeus 能在应用乙执行正确操作，用户的鼠标和桌面前台归属保持自主。
2. 控制目标明确，截图、点击、输入和可见光标都指向同一个有效窗口；窗口移动及多屏缩放不造成误点。
3. 菜单栏和被控窗口左上角出现真实系统状态，目标切换、停止和结束时正确变化。
4. 用户点击 Zeus 停止或系统停止共享后，控制立即进入撤销流程；同轮后续请求不能自动恢复。
5. 用户能查看操作过程；预览及虚拟光标自身不获得用户的鼠标或键盘焦点。

后台交互是最难、目前证据最少的一项。Codex 的相关符号提供了实现方向，但没有公开其全部算法，不能承诺仅换事件源或补一个采集接口就能对齐所有 macOS 应用。

### 10.2 第一步：先验证两个关键技术前提

在本任务隔离的 Test 实例中先验证：

- 原生控件、Electron 界面以及应用内菜单/网页控件能否正确接受后台语义与坐标操作，同时不改变用户的指针和前台应用。分别记录操作分支、目标窗口和焦点变化，不记录用户实际输入内容。
- 对单个目标窗口建立持续采集流后，菜单栏和窗口左上角能否出现用户要求的系统图标，以及用户从系统入口结束采集时如何通知服务。

优点是尽早暴露真正的技术限制，避免先花时间做预览样式；代价是需要真实桌面交互，构建成功不能代替结论。任一目标应用达不到后台交互要求，应记录具体限制，该项不计作对齐完成，也不自动切换为占用用户前台的控制。

系统共享展示按实际系统能力验证。Apple 的相关系统体验从 macOS Sonoma 引入；项目原有 macOS 13 支持边界需要明确记录，不能承诺旧系统具备相同原生图标，也不在本轮擅自改变最低支持版本。

### 10.3 第二步：在现有宿主和 Helper 中完成核心行为

| 改动 | 推荐做法 | 优点 | 代价与边界 |
| --- | --- | --- | --- |
| 统一控制归属 | 由现有 `ComputerHost` 持有当前会话、轮次、目标应用/窗口和控制代次；原生服务执行前校验归属 | 截图、输入、停止和 UI 使用同一个事实来源；Codex、Pi 等共用行为 | 需要将已有轮次结束/取消信号接到宿主，并防止旧进程通知影响新会话 |
| 限制操作冲突 | 同一 Zeus 实例先只允许一个活动桌面控制会话；其他桌面控制请求明确返回占用状态 | 避免多 Agent 互相改窗口与输入焦点，实现范围较小 | 桌面控制暂不能并行；文件、命令和已有浏览器能力不受此限制。只有真实需求证明需要时，再扩展按应用划分的控制归属 |
| 修复共享输入 | 保留现有无障碍语义操作，在共同事件投递路径补齐目标窗口、坐标转换、独立事件状态和经过验证的非前台交互机制 | 一次覆盖点击、拖拽、滚动和输入；减少多个工具各自修补 | 不支持后台操作的路径要明确失败；不能自动移动物理鼠标、强制切前台或事后抢回焦点 |
| 统一屏幕采集 | 以当前受控窗口的 `SCStream` 作为采集来源；现有 `get_app_state` 从有效帧生成模型图片，并保留目标、坐标变换和观察时刻 | 系统共享状态与模型实际看到的内容一致；后续预览可以复用同一来源 | 持续采集会增加耗电和内存占用，应限制帧率、只保留有界帧缓存，避免持续写入视频；切窗和动作后的观察不能冒用旧目标/旧状态的图片 |
| 可靠停止 | 首先撤销当前控制资格，使尚未执行和同轮后续动作被拒绝，再关闭采集、光标并中止/回收 Helper；全局启用设置可以保留 | 停止不会被下一次工具调用悄悄撤销，用户保持接管权 | 已进入目标应用的动作无法保证回滚；复用现有 `ZEUS_COMPUTER_EFFECT_UNKNOWN` 结果，不自动重试 |
| 正确释放资源 | 系统停止共享、用户停止、轮次结束/取消、目标退出及 Helper 故障统一进入结束流程；正常结束后只允许新授权任务建立新会话 | 不留下“任务结束但仍采集”或“没有画面还在点击”的状态 | 要处理停止和新请求同时到达的情况；Helper 的空闲保留与采集会话的结束必须分开 |

Apple 提供采集停止通知 `stream(_:didStopWithError:)`。宿主应将系统停止与控制撤销联动；具体系统版本的错误分类在实施时按所用 SDK 和实际系统核对，不把用户主动停止当成应自动重连的故障。[Apple 停止通知文档](https://developer.apple.com/documentation/screencapturekit/scstreamdelegate/stream%28_%3Adidstopwitherror%3A%29)

保留现有总开关、系统权限和敏感动作审批；新增控制归属不能成为每次点击都重新授权的理由。暂停、停止和结束也不能由 `serviceState=ready` 推断，服务可用与某个任务正在控制是两种不同状态。

用户在其他应用操作是正常并行使用，不应因此全局暂停 Computer Use。只有用户进入同一个受控窗口、显式接管或出现共享输入冲突时，才暂停当前目标的自动操作；恢复前重新观察目标状态，不续用暂停前的元素定位。

### 10.4 第三步：补齐观察体验

- 可见虚拟光标必须反映真正的目标和操作落点，先提供清楚的指向与点击反馈；绘制层不接收用户输入，不压到用户正在操作的无关窗口上。
- 画中画复用已经建立的采集流，显示目标应用、当前任务及停止入口，保持不抢焦点；复杂光标动效和锁屏工作可在核心行为验收后单独扩展。
- Zeus 自有提示用于解释“谁正在操作什么”，macOS 原生图标用于表达系统采集状态，两者都由真实控制/采集生命周期驱动。

优点是用户可以确认操作范围和进度；代价是新增显示层与资源开销。先交付简洁可用的光标和预览，复杂动画没有必要成为本次问题的前置工作。

### 10.5 首次交付的判断标准

一个完整场景是：用户始终在应用甲输入，Zeus 操作应用乙；菜单栏和应用乙窗口显示系统状态，操作落点可观察；用户按下任一停止入口后，同轮继续发出的控制请求均被拒绝，状态正确消失。该场景还需覆盖窗口切换、多屏缩放及服务异常。

实施后按项目要求执行 `pnpm lint`、`pnpm typecheck`、`pnpm build`、`pnpm package:mac`，再完成本任务隔离 Test 应用的真实交互验收。两类证据分别记录；未完成后台输入和双位置系统图标的真实验证，就不标记为已与 Codex 对齐。

### 11.2 最终实现与取舍

| 范围 | 已落地行为 | 优点与限制 |
| --- | --- | --- |
| 控制归属 | 同一宿主只允许一个轮次控制桌面；入队前占位，在启动、审批、调用与结果投影之后复核撤销状态 | 防止并发抢占与停止后复活；桌面控制暂不并行，撤销轮次记录保留至宿主退出 |
| 生命周期 | 用户停止、原生采集停止、目标退出、锁屏、轮次结束和中断都进入撤销；桥断线不重放 Computer 调用 | 旧轮次的迟到通知不能杀掉新轮次；Provider 中断与桌面撤销同时发起，桥故障不会挡住模型停止，撤销失败仍报告 |
| 截图和坐标 | 一条受控窗口采集流提供截图及预览；每秒最多两帧、两帧队列，缓存最新图像；输出窗口编号、逻辑边界、像素比例与采集时刻 | 消除多屏最大比例猜测；动作后的截图等待原始帧时间戳更新，窗口变动必须重新观察；持续采集仍有资源开销 |
| 真实提示 | AppKit 主线程负责非激活画中画、Zeus 菜单栏入口、虚拟光标和用户停止；macOS 共享入口与采集流相连 | 提示与实际控制同源；系统图标样式及菜单布局由 macOS 管理，Zeus 自有菜单项不冒充系统图标 |
| 输入与接管 | 语义点击、单行文字插入优先；原始事件携带目标窗口及独立事件状态，仅向目标进程投递；用户进入受控窗口时暂停 | 实测标准控件可后台操作；自绘控件的原始键鼠仍需观察确认。暂停只能由用户在预览继续，模型重新观察不能自动恢复 |
| 中途清理 | 输入检查与投递在同一短锁内；保存本服务尚未释放的虚拟按键，接管、停止和终止信号时发送清理用的抬起事件 | 防止停止与按下事件交错；已进入目标应用的动作无法撤回，中断返回“结果未知”并禁止重试 |

没有加入新的依赖、测试体系、前台激活兜底、物理鼠标恢复逻辑或对用户菜单栏配置的修改。现有敏感动作审批与 Zeus 自身控制隔离继续生效。

### 11.5 用户指出预览形态错误（2026-09-05）

用户指出“你这个画中画不对啊，你做的这个是个独立的窗口一样”。当前实现确实使用带标题栏的非激活 `NSPanel`，画面四周有留白、底部另设说明与按钮区域。它虽然不获取前台焦点，却仍表现为一扇普通浮动窗口，不能把此前“能显示画面、不抢焦点”的功能检查当作画中画呈现已经通过。
