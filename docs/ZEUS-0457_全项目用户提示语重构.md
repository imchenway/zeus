# ZEUS-0457 全项目用户提示语重构

## 目标与约定

- 当前阶段：`zeus/ZEUS-0457-task-03` 已按用户明确规则修正 Computer Use：全局开关打开后会话即可使用，重复的每轮启用限制已删除，工程检查、隔离运行检查及独立打包通过。运行中的正式应用尚未更新，真实订阅登录、发送及归档仍待验，以文末最新记录为准；此前阶段事实保留。
- 用户已确认：全项目面向用户的提示语，中英文同步。重点解释为什么操作受阻，不能以“消息已保存”“操作未完成”或无依据的“重试”代替原因。
- 覆盖桌面页面、原生弹窗、通知、Telegram，以及到达这些界面的服务端错误。用户内容、AI 正文、第三方网页、诊断日志和模型指令保持原意。
- 文案遵循“具体情况、实际原因、影响、有效操作”；内容按需要出现，不强制每条提示包含四句话。
- 按场景解释必要名称；保留 Codex、Git、API 等准确身份，去掉内部实现过程与自我辩护。
- 没有证据时不得猜测登录、网络、权限或服务状态。按钮只调用场景已有能力，不能凭文案决定重发、取消或归档。
- 不修改历史数据，不执行提交、合并、推送或发布。

## 已确认的代码问题

1. `formatVisibleApplicationError` 只识别少量错误，其他已知错误也统一丢弃原因；`errorToLocalUiMessage` 固定传入中文。
2. 队首失败包装仅保留通用错误码和消息；部分命令、接口与会话投影继续丢失底层错误身份。
3. 通知、原生对话框和 Telegram 存在固定中文；模型失败直接展示英文服务原文，缺少与应用语言一致的解释。
4. 设置、插件、自动化和会话提示混入“权威、派发、运行世代、真实、不伪造”等实现用语。

## 实施取舍

- 复用现有模块文案和错误展示；只对跨入口共享的原因和脱敏逻辑建立共用函数，不引入翻译框架或在线翻译服务。
- 原始错误信息通过可选原因字段保留；摘要与详情分开。优点是原因可读且可追溯；代价是需要同步检查传输与展示两端。
- 原生窗口、通知和 Telegram 跟随现有应用语言；设置未就绪时默认中文。
- 全量清单记录来源、原文、最终文案、触发入口、操作与处理结论；明确区分改写、合理保留和非产品文案。

### 错误链与取舍

- 现有错误对象只增加可选 `cause`。命令包装、HTTP 返回、前端接口、查询缓存与会话投影保留原错误码和底层原因；原因对象限制深度和长度，补充上下文只保留有界标量。
- 历史会话从现有错误 JSON 中只读提取可选原因，无数据库迁移、历史重写或业务状态调整。历史记录本身没保存的原因无法补造。
- 详情隐藏访问密钥、登录令牌、密码、认证与 Cookie 头、URL 查询参数、个人目录和堆栈。未知原因如实说明，不用网络问题代替所有错误。
- 普通模块继续使用原有双语组织；共用错误原因集中维护。优点是不同入口对同一原因表达一致；代价是错误码新增时也要更新原因目录。没有引入翻译框架、在线翻译、测试依赖或新的测试体系。
- 删除 AI 连接状态旁重复的内部检查说明；终端按已有能力说明“命令输出”或“交互式终端”。缺省数据不再向普通用户解释内部事件为什么尚未同步。

## 新用户任务流程与精致原生设计（2026-09-07）

### 电脑使用拦截原因复核（2026-09-07）

- 用户追问原因后核对源码：`StructuredComposerInput.tsx` 的 `/` 命令菜单包含 `Computer Use`，选择后建立结构化标签并随消息提交 `computerUseRequested=true`；全局开启仅决定此选项是否可选，普通文字授权不生成该标记。
- `nativeTurnComputerUseRequested` 只检查当前模型轮次所关联的原始发送记录；记录缺失、关联缺失或标记不为真都返回否。`codexDynamicToolApplication.ts` 因此在调用原生操作宿主前返回 `ZEUS_COMPUTER_NOT_REQUESTED`，这条错误不能单独证明是用户漏操作。
- 现有会话提示明确要求启用后开始新轮次。此前“开启后回复已开启”的指引不完整：应从输入框 `/` 菜单选择 `Computer Use`，随新消息开始新轮次；不能依靠当前轮次中的普通文字引导补上该标记。
- 该设计的优点是电脑控制授权限定在单次工作内；缺点是自然语言请求与功能标记分离，当前错误原文没有说明具体入口及新轮次要求，容易造成已授权却持续受阻的困惑。本次仅说明原因，未修改控制权限或应用代码。
