# ZEUS-0879 会话发送与切换性能及弱网一致性

## 结论

2026-10-19 复核结论：不能确认原始问题已解决。三项资源整改已进入共享实现，但调用链仍有等待、当前权限交接和冷切换显示缺口；大消息会话仍可能重复序列化。此前“已全部改完”只能表示上一轮代码修改结束，不能表示完整修复或验收通过。最新证据和范围见文末“调用链复核”。

本次问题由三条链路共同造成，不是单一网络问题：

1. Codex 每次发送都会冻结完整 Skill 目录。录屏对应提交没有选择 Skill，但仍复制了 39 MB、1085 个文件。发送因此在 `thread/resume` 完成后停顿约 95 秒。
2. Renderer 每次会话状态变化都会同步 `JSON.stringify` 整段热缓存。流式事件和弱网恢复时的集中事件会放大主线程阻塞，导致切换和正文显示卡顿。
3. 本地消息在队列回执到达后会先从时间线状态移除，再依赖排队区或权威消息重建。队列、Provider 消息和界面可见性不是同一个原子状态，因此弱网或事件乱序时存在消息短暂消失的空档。

- 提交：`conversation_submission_6DYWlepu35mL`。

## 修改

### 发送链路

- 无论是否明确选择，普通会话都不再冻结或复制 Skill 目录。
- Codex 直接使用提交时解析到的当前 Skill 路径；源文件后续修改或删除，按执行时实际状态生效。
- Pi 每次从当前目录读取 Skill catalog，用于自动发现和显式选择；不再把 catalog 复制到提交级产物目录。
- 发送和显式 Skill 解析只扫描本地目录，不等待 Codex Provider 元数据；弱网不会进入消息派发关键路径。
- 子代理按自己的工作目录重新解析当前 Skill，不再继承父消息的 Skill 文件副本。
- 旧的普通会话 Skill 副本不再进入新消息或恢复执行链路。数字员工旧物化目录在服务启动时删除；数据库迁移会统一解除全部历史 Skill Artifact 的持有者和保留锁，并裁剪旧运行记录中的可执行副本字段。

优点：彻底移除发送前递归复制，Skill 数量和目录体积不再形成提交级等待；修改和删除语义与用户看到的当前目录一致。

代价：会话不再保存 Skill 内容版本。发送后修改文件可能影响尚未读取该文件的执行；文件被删除后，恢复或继续执行不能取回旧内容。

边界：员工、权限、上下文和正式交付物仍保留审计快照；Skill 可执行正文不再冻结。两类数据不能混为一谈。

### 会话切换与渲染

- 热缓存首次接管时计算体积，流式更新只替换最新状态引用。
- 会话安静 2.5 秒进入持久化边界时，再重新计算精确体积并执行原有淘汰策略。
- 正文使用现有 140ms 透明度接管动画，不移动滚动位置，不延后交互，并遵守 `prefers-reduced-motion`。

优点：流式事件不再反复序列化完整会话；切换先显示本地缓存，后台网络更新不遮住已有正文。

代价：流式活动期间缓存字节估算是上一轮值；活动停止后的持久化边界会重新计算并淘汰超限条目。缓存仅保存对象引用，不复制业务数据。

### 弱网与消息一致性

- 队列水合和发送接纳只补充调度状态与稳定身份，不再删除本地用户消息。
- 本地发送消息持续保留到同一 Provider 消息在一次状态更新中原位接管。
- 只有底部排队区实际挂载且能够显示同一消息时，正文才做互斥展示；Provider 关闭、失败或输入区被抑制时，消息保留在正文。
- 渐进水合保留未被权威条目接管的本地用户消息；相同持久身份到达后原位合并，不产生交接空档。
- 未知送达仍按现有规则只核对，不自动重发。

预期收益：减少网络慢、断开或事件集中到达时的消息交接空档，并保留未知送达不重复写入的约束。2026-10-19 复核发现冷切换恢复仍有显示缺口，不能把该预期写成全场景保证。

代价：Provider 接管前会持续保留本地状态标识；如果 Provider 永远没有返回稳定消息，该记录也不会被后台清理，只能由用户明确删除。它只影响展示，不会被当作服务端已执行证据。

## 平台影响

- Windows：使用相同 Local Server、Reducer、热缓存和 CSS 代码路径，代码修改与本次发现的问题都适用于该端；实际行为尚未验证。未增加平台专属文件系统调用或动画能力。

## 同类设计整改

三项已完成上一轮代码修改，但本次调用链复核未通过完整交付判断。判断标准不是名称中是否包含“快照”或“冻结”，而是它是否复制可执行资源、阻塞消息派发，或让已删除资源继续生效。

### 已整改：Codex 每轮发送前后全量读取工作区

- 发送前同步等待 `beginWorkspace`，再进入 Provider 写入。该入口会用 Git 枚举工作区全部已跟踪文件和未忽略新文件，并逐个读取、计算 SHA-256；轮次完成时再全量读取一次。
- 默认上限为 2 万个文件、单文件 20 MiB、整轮保留正文 100 MiB。当前工作区静态统计为 1251 个文件、约 34.8 MiB；这些文件即使本轮完全不会修改，也会进入枚举和内容读取。
- 注释写的是“扫描故障不阻断用户发送”，但实际调用使用 `await`，因此只有扫描报错不会阻断；扫描耗时仍在 Provider 写入前完整等待。
- 该机制只出现在 Codex 派发链路，Pi 没有同一工作区基线入口。

优点：能够捕获脚本和命令行产生、但 Provider 没有上报的文件变化，也能保留发送前已有的脏文件内容，用于准确审阅和撤销。

代价：发送延迟与仓库文件总数、磁盘速度、杀毒软件扫描和文件系统开销相关，而不是与本轮实际修改相关。Windows Defender 等环境可能放大这项成本，但本次没有 Windows 实测数据。

实施结果：已删除 `beginWorkspace`、`bindWorkspace`、`finishWorkspace` 及其四个调用入口。消息本地接纳后直接进入 Provider 派发，变更集只接纳 Provider 明确上报的文件事件。

优点：仓库规模、磁盘速度和杀毒软件不再进入发送关键路径。代价：命令或脚本修改文件但 Provider 没有上报时，Zeus 不再保证该文件进入变更卡片或自动撤销。

### 已整改：Plugin 按会话冻结全部启用项，并在派发前预连接 MCP

- 新会话第一次准备时，会把项目中全部已启用 Plugin 写入会话激活快照，不只包含用户明确选择或本轮实际使用的 Plugin。
- Plugin 更新、停用或删除后，旧会话仍读取原激活记录；被会话引用的旧安装修订也会继续保留。该行为与“没了就没了”的产品语义冲突。
- 会话准备会先为全部激活 Plugin 建立 MCP 工具目录。MCP Server 按 Plugin 和 Server 顺序连接，并在 `client.connect` 与 `client.listTools` 返回后才继续。
- Zeus 这一层没有为连接和工具枚举传入明确超时。底层 SDK 或 transport 是否最终超时，本次没有运行验证；但本层已经确认会在 Provider 派发前等待。
- Codex 恢复、新 Pi 会话和 Pi 恢复均使用这条共享链路，因此不是单个 Provider 的问题。

优点：同一会话中的工具 schema、Hook 和权限策略保持稳定，旧会话不会因 Plugin 更新而出现结构漂移。

代价：停用或删除不能立即生效；未使用的 Plugin 也增加启动与发送成本；远程 MCP 和 Connector 把网络可用性带入消息发送关键路径。

实施结果：会话不再写入、继承或读取 Plugin 激活快照；数据库迁移会清空旧激活记录。派发、Hook、工具目录和调用均读取当前安装、启用、修订和权限状态。Codex 与 Pi 只预注册稳定的 `catalog`、`invoke` 入口，MCP 到实际发现或调用时才并行连接，目录连接上限为 5 秒。

预期收益：后续发现读取当前状态，移除无条件 MCP 预连接。限制：发送前同步 Hook 仍可调用 MCP；工具调用跨审批或 Hook 等待期间也未完整绑定原修订与审批身份。不能保证所有权限变更立即安全接管，或所有旧调用都会因修订变化失败。代价：会话内工具和 Skill 会随当前 Plugin 状态变化。

### 已整改：数字团队把 Skill 重复读取、Artifact 化并再次落盘

- 数字团队和任务工作预览会递归读取所选 Skill，计算每个文件的摘要；正式创建运行前又完整读取一次，确认预览没有变化。
- 创建运行时把所有文件编码为 Base64，保存到 JSON Artifact，再解码到运行专属只读目录。重试和恢复时还会重新校验或重新物化。
- 单个 Skill 上限为 2000 个文件、32 MiB。Base64 还会增加约三分之一的正文体积。
- 该链路不影响普通会话，只影响正式数字团队、自动工作项和任务运行创建。

优点：正式工作可以证明使用了哪一份 Skill，重试时输入稳定，并能检测运行目录被篡改。

代价：同一资源被多次读取并保存两份，创建延迟和存储成本都随 Skill 体积增长；Skill 删除后仍可从 Artifact 恢复，也与统一的“没了就没了”语义不一致。

实施结果：预览的摘要函数只读取 `SKILL.md` 并记录来源、身份、当前路径和摘要；创建、重试和恢复不再递归读取全部文件正文、不再 Base64 Artifact 化，也不再物化只读目录。目录解析仍会递归枚举和读取文件元数据，详见复核。派发前重新解析当前 Skill；删除或停用后明确失败。旧物化目录在启动时删除；数据库迁移统一解除全部历史 Skill Artifact 的持有者和保留锁，并将旧运行记录裁剪为审计引用。

优点：移除重复读取、双份存储和恢复旧资源的行为，删除语义一致。代价：正式工作不再保证 Skill 内容完全复现；Skill 在接纳后、派发前变化时，实际执行使用当前内容，并以派发时摘要更新审计记录。

### 不属于同类问题

- 会话执行快照只保存模型、连接、权限、工作区身份等少量元数据，用于未知送达和幂等恢复，不复制 Skill 或工作区文件。保留它能防止重试时换模型或扩大权限。
- Plugin 安装时复制到内容寻址目录，是安装边界和完整性校验；它不是每次发送复制。需要修改的是会话长期引用旧修订，不是删除安全安装过程。
- 用户明确添加的任务附件需要进入 Zeus 自管目录，否则源文件移动后会丢失。它是显式输入持久化，不是推测性全量冻结。
- 助手明确交付的本地图片会归档，目的是避免临时目录清理后图片消失。它发生在交付完成阶段，不阻塞初始发送。
- 数据库恢复包、Git 提交身份和正式交付物属于备份、代码版本或业务证据。删除这些快照会破坏恢复和审计，不应与运行时资源冻结混为一谈。

### 需要补齐的缺口

1. **消息可见性：本地已接纳消息仍可能在冷切换时暂时消失。**

   - 服务端 `localUserSubmissionProjection.ts:21` 已保存本地用户消息；Codex 在 `codexNativeConversationCoordinator.ts:1111` 创建提交后持久化。该缺口是本地显示恢复不完整，不能直接称为数据库消息丢失。

2. **Plugin 当前态：审批与最终调用未绑定同一工具身份。**

## 2026-10-19 会话切换卡顿复查与修复

### 用户期望

- 会话选择应立即响应。
- 冷会话读取时应像任务列表和源码页一样保留稳定结构，并显示连续加载动效。
- 正文、图片和目录应按优先级渐进出现，不能长时间空白后整块跳出。
- 热会话来回切换应直接显示已读内容，不应反复进入冷读取。

### 录屏与生产只读证据

- 补充录屏在约 `22.35s` 已完成侧栏选中、标题和输入区切换，但正文仍显示“正在加载会话”；约 `25.50s` 正文才出现。本次冷切换的可见等待约为 `3.1s`。
- 录屏中的目标会话显示缓存约为 `1.3 MiB`，来源会话约为 `2.7 MiB`，都未超过单会话 `8 MiB` 限制。因此，问题不是缓存文件过大被直接拒绝。
- 对同一生产数据执行只读接口计时：可读快照约 `46–107ms`；完整会话目录约 `0.22–1.98s`，长会话稳定出现约 `1.8–2.0s` 的目录读取。
- 可读快照在读取会话前先等待 Git 环境信息。该读取通常为几十毫秒，但观测到一次约 `669ms`。Git 环境不属于正文首帧，不能占用正文关键路径。
- 正文组件挂载后立即并行请求完整目录。目录读取在 Core 的同一事件循环内执行同步 SQLite 查询，因此慢目录会阻塞已经开始的可读快照继续处理。录屏中“目录刻度先出现、正文后出现”与该调用顺序一致。
- 目录实现对同一批模型历史先构建发言，再构建过程边界；两个阶段都逐条读取来源别名和显示位置。长会话会形成数百次重复位置读取，是目录耗时的主要代码原因。
- 普通会话进程内热缓存只保留最近 `6` 个会话。补充录屏连续切换超过该数量后，较早会话会退回磁盘缓存或服务端读取，无法保持类似源码标签的即时切换体验。
- 性能跟踪仍关联旧快照路径，实际使用的可读快照请求没有继承会话点击身份，导致现有指标无法准确反映录屏中的点击到正文时间。

### 实施内容

1. 正文优先于完整目录
   - `ConversationTranscript` 只在正文已水合后读取完整目录。
   - 目录仍覆盖深历史和过程分组，但不再与冷会话首屏争抢 Core。
   - 优点：正文快照可以先提交到 Renderer；代价：左侧会话刻度会在正文后渐进出现。

2. Git 环境退出正文关键路径
   - 可读快照不再等待分支和工作目录查询。
   - 正文接管后通过既有独立环境接口补齐；热切换期间先保留已有环境，避免右侧信息闪空。
   - 优点：Git 慢盘或命令异常不再拖住消息；代价：冷打开时环境信息可能比正文晚一个读取周期。

3. 目录位置一次联查
   - 模型历史、来源别名和显示位置在同一批 SQL 中读取。
   - 发言目录和过程边界复用同一份位置结果；已回答询问也在原查询中取得位置。
   - 仍保留缺失位置时拒绝损坏目录的原契约，不用时间戳或消息文本猜测顺序。
   - 优点：删除逐条位置查询，长会话目录不再产生数百次重复读取；代价：目录 SQL 增加两个有主键支撑的联接。

4. 扩大热切换覆盖
   - 普通会话热缓存数量由 `6` 调整为 `12`。
   - 总内存估算上限仍为 `32 MiB`，单会话上限仍为 `8 MiB`，超过字节预算时继续按最近使用顺序淘汰。
   - 优点：补充录屏中的连续切换范围可更多命中内存；代价：小会话较多时可保留更多对象，但不会突破既有总字节上限。

5. 与任务列表一致的渐进加载
   - 冷会话加载层改为用户消息和助手正文形状的脉冲骨架，不再只显示两条居中短线。
   - 加载层淡出与正文淡入在同一位置交叉接管；标题和正文沿用现有短促落位动效。
   - `prefers-reduced-motion` 下关闭新增过渡，保留稳定结构和可读状态。
   - 不保留上一会话正文做跨会话叠化，避免选中目标已经变化时短暂显示错误会话内容。
   - 优点：冷读取过程连续、结构稳定；代价：真实冷读取仍会显示骨架，动效不能代替后端性能修复。

6. 恢复真实性能关联
   - 会话点击性能跟踪改为关联实际使用的可读快照请求。
   - 后续可以区分网络快照完成和 React 正文接管，不再记录到未使用的请求路径。
