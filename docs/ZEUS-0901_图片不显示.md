# ZEUS-0901 图片不显示

## 需求与依据

- 修复截图所示会话图片加载失败，覆盖 macOS 和 Windows 的共享入口。
- 已通读当前仓库的 `PROJECT-STYLE.md`，规则文件扫描未发现其他 AGENTS.md、CODE-GUIDELINES.md、DESIGN.md；同时遵守本次提供的 AGENTS.md。未发现本任务历史文档。
- 只读查询正式数据库，定位到 2026-10-21 19:21:21（北京时间）的用户消息“这个回复的产生逻辑是？”。该消息、提交和资源均指向 `/Users/david/Library/Caches/WeType/dsclp/1792581619212.png`。文件系统确认此文件已不存在。
- 原生附件代理 `describePaths` 只签发源路径授权；剪贴板文件引用、拖入文件和选图共用此入口。无路径图片则已走 `materialize` 保存到 Zeus 附件目录。
- 资源预览再次读取原路径时抛出 ENOENT，共享错误映射显示“找不到需要的文件或程序”，与截图一致。不是图片布局或解码问题。

## 实施方案与取舍

- 图片添加时复用现有 `materialize` 和原子文件发布，保存受管副本，再将受管路径交给草稿、服务端和 Provider；非图片文件与目录继续使用现有精确路径授权。
- 选择与拖入入口新增落盘行为，接入现有 Main Command 账本；剪贴板继续沿用已有命令。每次添加保留独立命令身份，避免草稿清理删除另一条消息的副本。
- 优点：覆盖三类图片路径入口，不依赖来源缓存生命周期，也不增加数据库结构或后台扫描。
- 代价：增加图片读取、写入和磁盘占用；沿用现有单文件 100 MiB、单批 256 MiB 限制。
- 不采用“仅改报错”或“发送时才复制”：前者不能保存图片，后者仍可能在草稿等待时丢失来源。
- 已丢失且没有受管副本的历史图片不能凭路径重建；本任务不写正式数据库、不猜测替换图片。后续找到原会话的完整图片数据，恢复情况见下文。

### 后续方案取舍

- 建议普通“文件附件”在导入时固定内容，并在统一接纳入口保证所有调用方提交的是持久副本；桌面导入仍需尽早保存，避免草稿期间来源清理。已有持久副本应直接复用，不能每层重复复制。
- 图片格式识别应复用共享能力，避免输入与预览维护不一致的格式表；正式助手图片交付应统一归档规则，覆盖 Markdown 和结构化卡片。
- 优点：来源生命周期与历史消息分离，跨入口行为一致。代价：增加磁盘与读写成本，还需明确容量、归属和清理策略。
- 目录、源码链接和工具查看记录需要保留其实际业务语义，不能一律递归复制。当前引用的优点是始终读取最新文件且成本低；代价是历史内容可能变化或失效。是否保留工具当时看到的图片，应与“打开当前文件”分别定义。

### Codex

- 本地图片输入会实际读取文件，转换成内嵌图片数据，不只记录路径。见 [models.rs:2175](https://github.com/openai/codex/blob/b4ad33d1a3c10c9652dd57f7afd7a949f8f26895/codex-rs/protocol/src/models.rs#L2175)。读取发生前原文件仍须存在。
- 默认图片存储使用 `InlineAttachmentStore`，保留图片字节；统一处理也支持由注入的存储返回 `file_id`，不能把接口存在说成默认上传到云。见 [默认存储](https://github.com/openai/codex/blob/b4ad33d1a3c10c9652dd57f7afd7a949f8f26895/codex-rs/core/src/thread_manager.rs#L549)、[图片准备](https://github.com/openai/codex/blob/b4ad33d1a3c10c9652dd57f7afd7a949f8f26895/codex-rs/core/src/image_preparation.rs#L355)。图片可能缩放或重新编码，历史保存的是实际处理后的内容，不保证原文件逐字节不变。
- 会话记录先准备图片，再把 ResponseItem 持久化到 rollout。见 [历史写入](https://github.com/openai/codex/blob/b4ad33d1a3c10c9652dd57f7afd7a949f8f26895/codex-rs/core/src/session/mod.rs#L3652)、[rollout 持久化](https://github.com/openai/codex/blob/b4ad33d1a3c10c9652dd57f7afd7a949f8f26895/codex-rs/core/src/session/mod.rs#L3795)。本任务的原 PNG 确实在原会话 `input_image` 中完整保存，是此链路的现场证据。
- `view_image` 同时产生“查看了哪个路径”的事件和含图片字节的工具输出；只取路径事件会丢失另一份内容证据。见 [view_image.rs:171](https://github.com/openai/codex/blob/b4ad33d1a3c10c9652dd57f7afd7a949f8f26895/codex-rs/core/src/tools/handlers/view_image.rs#L171)。生成图类型也区分内嵌结果和持久 `file_id`，另有可选本地保存路径。
- 普通文件的路径、文本提及或工具读取不能视为自动归档整个文件；公开 `UserInput` 的本地图片专用处理不能推广到所有文档。
- 优点：已记录的图片内容可独立于原始缓存恢复；代价：内嵌数据增大会话记录，也不能保证操作系统里的原文件一直存在。

- 优点：避免来源缓存消失造成历史丢图，并可复用相同内容；代价：引用登记、回收及失败恢复比独立副本复杂。普通路径附件仍承担源文件变化和消失的风险。

### OpenCode

- 当前 App 根据模型输入能力、类型和大小区分内嵌媒体与路径附件。可内嵌的受支持图片/PDF 保存 Blob，提交时转为 data URL；普通本地文件保存路径，无本地路径或远程场景上传到服务端临时目录。见 [附件分类](https://github.com/anomalyco/opencode/blob/c93aaae37157d785f76a8e9a9243a6560e286468/packages/app/src/composer/attachments/attachments.ts#L59)、[临时上传](https://github.com/anomalyco/opencode/blob/c93aaae37157d785f76a8e9a9243a6560e286468/packages/app/src/composer/attachments/destination.ts#L13)。
- 浏览器草稿驱动使用 IndexedDB 保存 Blob，展示用 object URL 与持久 Blob 身份分离。见 [草稿存储](https://github.com/anomalyco/opencode/blob/c93aaae37157d785f76a8e9a9243a6560e286468/packages/app/src/runtime/persistence/drafts.ts#L442)。不能把每次创建 object URL 本身当作持久化完成。
- 真正发送在 `files` 字段里的附件由服务端读取/解码、按内容判断 MIME、生成 Base64 数据，进入持久消息输入；图片元数据不只保留原文件路径。见 [附件接纳](https://github.com/anomalyco/opencode/blob/c93aaae37157d785f76a8e9a9243a6560e286468/packages/core/src/session/prompt.ts#L91)、[队列入库](https://github.com/anomalyco/opencode/blob/c93aaae37157d785f76a8e9a9243a6560e286468/packages/core/src/session/inbox.ts#L303)。
- 普通 `path` 附件是另一条链路：序列化为提示文字及展示元数据，不进入上述 `files` 内容快照。这一分支仍依赖源文件或临时上传文件。见 [请求组装](https://github.com/anomalyco/opencode/blob/c93aaae37157d785f76a8e9a9243a6560e286468/packages/app/src/composer/request.ts#L167)。
- TUI 粘贴附件入口读取受支持图片/PDF并转成 data URL，SVG按文本处理；与 App 的格式和能力选择不完全相同。工具读取受支持媒体时也返回 Base64 内容。见 [TUI 读取](https://github.com/anomalyco/opencode/blob/c93aaae37157d785f76a8e9a9243a6560e286468/packages/tui/src/component/prompt/local-attachment.ts#L29)、[工具读取媒体](https://github.com/anomalyco/opencode/blob/c93aaae37157d785f76a8e9a9243a6560e286468/packages/core/src/tool/read-filesystem.ts#L136)。
- 优点：图片输入独立于原路径，普通文件可以按需读取、避免无条件复制；代价：草稿 Blob、消息数据、路径附件的生命周期不同，路径附件仍可能失效。

### 对 Zeus 审计结论的修正

- 三家都区分媒体内容与文件引用，并未统一把所有文件和目录永久复制。因此，“保存了原路径”不能单独证明有 bug；需要结合界面承诺判断它是历史附件还是当前文件引用。
- 本任务用户粘贴的截图应作为当时提交的内容保存。Zeus 自己的历史预览不能只使用第三方缓存路径；Codex 已保存图片数据，也不代表 Zeus 的资源读取会自动使用那份数据。
- 建议优先统一图片和明确交付媒体的内容持久化、元数据及消息归属，复用已有存储；普通文档是否固定发送时内容须按附件语义定义，目录及源码引用保留当前文件语义。不要因为竞品存在媒体仓就新建第二套存储。
- 优点：对准已确认的丢图问题并覆盖同类入口，避免重复复制已有受管文件；代价：需要区分展示/归档内容与“打开当前原文件”的行为。前文“所有普通文件附件都固定内容”的建议不应直接作为无条件实施要求。
- macOS 与 Windows：以上主要逻辑分别复用 Rust/Node/浏览器存储实现；OpenCode 请求组装显式识别 Windows 盘符与 UNC 路径。此次仅核查源码，没有安装这些源码快照、执行两端测试或验证各产品实际 UI，也不据此保证两端完全无差异。

### 结论与用户语义

推荐采用“两种语义、一个内容存储、一套授权读取”：需要固定内容的附件复用 ArtifactStore；需要操作当前文件的入口保留路径引用。统一的是身份、授权、归属和状态，不是把所有入口都改成递归复制。术语记录在 [执行与资产](contexts/execution-assets/CONTEXT.md)。

| 用户操作或预期 | 推荐语义 | 内容固定时点和边界 |
| --- | --- | --- |
| 在会话中选择“添加附件”、粘贴截图，或把文档拖入附件区 | 附件内容副本 | 加入草稿前保存。发送提交绑定草稿里已保存的那份内容；文件在等待期间改变不会被偷偷重新读取。需要最新内容时明确替换附件。PDF、Office、压缩包与图片遵守同一规则，不按扩展名猜测是否需要留存。 |
| 从文件树、源码位置链接、引用文件动作向模型提供当前工作文件 | 当前文件引用 | 每次使用都重新核对路径和授权，读取当前内容。界面使用“引用文件”，与“添加附件”区分；即使引用的是图片，也不因此自动改成副本。 |
| 引用工作目录，让助手继续查看或修改项目 | 当前文件引用 | 不递归复制，不把项目目录转换成附件包。需要交付目录时，使用明确的目录提交或打包动作。 |
| 助手明确交付报告、图片、表格等文件 | 附件内容副本 | 文件交付完成时固定内容；源码定位链接、网站链接仍保留各自引用语义。卡片样式本身不能决定是否归档。 |
| 查看助手某次工具实际看到的图片 | 所见图片记录，使用内容副本 | 优先绑定该次调用已经保存的图片字节；只拿到路径时仍是路径记录，不能承诺历史还原。 |
| 任务表单中显式添加文件或目录 | 保留现有内容副本语义 | 现有任务入口已经复制文件和目录。不能为了统一而改回当前路径；也不据此扩展为所有目录入口都复制。 |

“添加附件默认固定内容”是根据用户预期提出的产品建议，不是已核实的现行完整契约。实施时应把动作名称和协议语义一起落地；不能只有后端改变行为，而界面仍把“引用文件”和“发送文件”混在一起。

### 本轮核实的复用条件与限制

1. [ArtifactStore](../packages/storage/src/artifactStore.ts) 已有内容哈希、不可变对象约定、稳定 owner 关系、staging 恢复、保留锁、容量诊断和两阶段回收。`putFile` 在复制前后比较来源身份、大小和修改时间；`resolveAuthorized/readAuthorized` 要求 owner 并校验对象。可复用这些能力，不另建媒体库或独立引用计数系统。以上是源码事实，不等于并发和崩溃行为已经运行验证。
2. `artifact_owners` 以 owner 种类、owner ID、对象哈希共同唯一；不同会话可以引用同一内容而保有独立关系。GC 候选要求没有 owner、没有活动保留锁，隔离前重新核对关系。不能把文件的最后访问时间当作是否可删的依据。
3. 现有保留策略包含活动会话、归档会话和删除归属等分类，但 GC 查询依据保留锁状态；到达时间不会自动把活动保留锁变成已释放。附件接入必须包含关系解除和保留锁释放，不能只调用入仓。
4. [工具图片存储](../packages/local-server/src/conversationPortableContext.ts) 的 `storeImage` 已将图片字节放入 ArtifactStore，记录会话、轮次、运行分段和调用配对身份；Codex 动态工具与 Pi 工具图片已有调用方。它不证明 Codex 原生 `imageView` 路径事件也已经关联这些内容。此处主要需要补关联与投影，而非再保存一份相同图片。
5. [服务端附件接纳](../packages/local-server/src/conversationApplicationOperations.ts) 目前验证 `localPath/uploadRef` 和精确路径授权，不持久保存内容；创建、续聊、提问回复、计划执行、排队编辑、任务推送补充附件均需接入同一接纳规则。仅修改桌面选择器无法覆盖服务端直接提交。
6. [资源预览](../packages/local-server/src/conversationResourcePreview.ts) 目前按真实路径和授权根读取；[资源投影](../packages/local-server/src/conversationResources.ts) 的目标与授权记录主要保存路径。因此接入内容引用时，必须同时调整读取与投影，不能只替换写入位置。
7. 原生草稿 `discard` 当前直接删除会话受管目录中的文件；采用共享内容后必须改为解除草稿关系，否则同一内容被多处使用时会误删。受管目录路径本身也不能证明文件不可变、已登记归属或已获得长期保留。
8. ArtifactStore 当前要求相同存储哈希的 MIME 等元数据一致。统一接纳应规范内容识别结果，文件名和调用方声明类型留在附件关系中；复用已有对象时沿用已核验的对象类型。类型冲突需要复核，不能因不同扩展名重复存储相同内容，也不能静默覆盖对象元数据。

### 统一设计与接纳流程

沿用现有命令、应用服务和 ArtifactStore 边界：桌面负责原生选择、剪贴板读取和用户授权；Core 负责内容接纳、归属提交、读取授权与回收；Renderer 只拿稳定资源身份和展示信息。文件路径可以作为受信宿主的导入参数，不作为跨上下文长期内容身份。

每个附件关系至少表达以下事实，优先扩展现有提交附件和资源元数据，不先建一套通用附件数据库：

| 信息 | 保存与读取规则 |
| --- | --- |
| 稳定附件 ID、所属提交或消息、附件顺序 | 同名文件也能区分；不同消息引用相同内容仍有不同附件身份。名称和内容哈希均不能单独作为消息附件身份。 |
| 语义 | 明确为内容副本或当前文件引用；新写入不得靠路径位置或 MIME 推断。 |
| 内容引用 | 副本绑定 ArtifactRef 与合法 owner；只向调用方暴露受控资源 ID，不暴露对象目录作为编辑目标。 |
| 当前文件引用 | 保存项目或工作区身份及相对位置；项目外引用保存精确授权。原路径只在受信宿主解析，不因复制到新位置而扩大权限。 |
| 名称、字节数、内容识别类型、来源说明 | 来源路径供解释和“打开原文件”使用，不是副本丢失时的静默替代来源。名字相同也不能据此认定内容相同。 |
| 保存结果及证据 | 区分保存中、可用、失败，以及历史记录是否具有当时内容证据；文件不可预览与内容没有保存是两种状态。 |
| 图片表示 | 原件与模型实际输入、预览派生图分别关联。转换或缩放不能覆盖原件，所见记录指向实际获得的表示。 |

接纳流程如下：

1. **明确语义并校验权限。** 复用精确文件授权、可信根和真实路径校验。服务端不接受客户端自报的“已经保存”、owner 或任意哈希作为访问凭据。路径引用只登记合法引用；目录默认走引用语义。
2. **草稿阶段保存内容。** 原生路径附件由桌面发起受控 Core 导入并等待完成，再把“可用附件”加入草稿；无路径字节直接进入同一入仓流程。复用命令 ID 和附件序号作为幂等身份。较大文件沿用流式文件写入；每项返回明确成功或失败，不能部分失败后无提示地少发附件。
3. **优先复用。** 已有合法 ArtifactRef 只增加对应关系，不再读取来源或复制字节；只有既有受管路径的历史内容按后述接管流程处理。新路径附件只完成一次持久保存，避免桌面永久副本再被服务端永久复制。
4. **提交归属。** 内容对象完成提升后，提交记录、附件关系和正式 owner 在 Core 持久事务内一致提交。先保护内容，再解除草稿 owner；不能出现消息已接纳但没有可用内容，或草稿先删除、消息还未提交的空档。现有 owner 方法各自开事务，实施时需在现有应用服务中补齐组合事务能力，不能声称当前已经原子完成这些步骤。
5. **保留未知结果。** 发送响应丢失时按同一命令身份查询接纳结果；草稿关系和内容继续保护，不能自动重发消息或清理。排队提交即获得持久 owner，不等到 Provider 开始运行才保护内容。重试复用原提交附件；主动替换文件产生新的提交关系。
6. **统一读取。** 历史预览、下载、Provider 输入、结构化卡片和恢复都从同一内容引用解析。资源投影可以重建，正式内容关系必须存在于提交、消息、工具结果或交付事实中，不能只存在 Renderer 或可重建资源列表里。

给 Provider 的普通路径参数、系统默认应用和编辑器不能直接指向内容仓中的权威对象，避免外部程序原地改写归档。优先传字节；只能用路径时提供有生命周期的工作副本，禁止用可写硬链接连接权威对象。用户需要编辑时使用“打开原文件”或“另存为”；历史预览继续读固定内容。工作副本是可重建输出，不是第二份永久事实。

### 各入口的具体接法

| 入口 | 推荐接入点与行为 | 复用及边界 |
| --- | --- | --- |
| 会话普通文件 | `conversationInputResources`、Preload 和 Core 接纳统一传递语义；选择、拖入附件区按内容副本保存，引用文件动作保留路径。 | 覆盖普通聊天、提问回复、计划反馈、排队消息编辑、任务模型推送补充附件；复用现有附件组件与命令账本，不复制多套发送逻辑。 |

| 服务端直接提交本地附件 | 在统一异步接纳步骤处理授权、保存、owner 和输入记录；现有归一化函数保留纯校验职责。所有同步调用方随接纳契约调整。 | 新命令明确语义；合法路径仍须保存才能承诺内容副本。历史或旧调用方未声明语义时维持原引用并标记，不偷偷复制；内部调用方切换完成后新写入强制声明。 |

| 结构化交付卡片 | `deliverables`、`presentation.deliverables`、明确交付的 `resources/artifacts` 共用文件交付接纳；支持图片及普通文件。 | 已有正式成果引用直接关联；普通源码卡片和网站卡片保持引用。文件必须保存成功才显示可用交付；保存失败保留正文与明确失败状态，不把路径卡片当作已归档。 |
| 任务表单附件 | 保留文件和明确目录上传已有的复制行为；普通文件的新写入复用内容仓，任务与会话分别拥有关系。 | 从任务带入会话只增加引用；移除任务附件关联不删除已被会话或正式成果持有的内容。目录继续由现有任务服务负责清单、复制限制和生命周期，不新增通用目录内容仓。 |
| 剪贴板图片、长文本 | 无路径内容直接进入统一保存步骤；剪贴板文件路径按用户的附件动作处理。 | 复用原生剪贴板解析和格式转换，去掉下游重复持久化；不是再增加一层截图缓存。 |
| Telegram 入站 | 下载校验后的内容直接进入统一保存步骤，连接与入站操作身份保持幂等；任务或提交增加正式归属。 | 不再次从发送者取文件，不对现有持久文件逐层复制。另行修正硬编码 `/` 的路径校验，复用同文件已有 `isPathInside`；这与历史附件留存是不同缺陷。 |
| 正式发布成果 | 保留 `WorkArtifactDelivery → ArtifactStore` 的冻结和授权规则。 | 会话卡片只关联正式成果，不重新发布、不改变其冻结身份，不重复复制 docs 阅读副本。 |
| 助手最终图片 | Markdown 图片、标准生成图与结构化图片交付使用同一结果接纳规则；已有归档内容直接复用。 | 复用现有归档请求和恢复行为，逐步把内容身份接入 ArtifactStore。归档失败仍是未完成保存，不能靠首次打开时重试来保证留存。 |
| 浏览器批注截图 | 保留现有 draft/sent 保护，关联统一内容身份和归属。 | 已发送图片只增加关系，不新建截图副本；提交期间的并发移除仍需后续验证。 |

对于助手最终交付，Zeus 自身的工作树清理应等待明确交付的保存完成；待保存状态需有可重试凭证和有限重试，不能无限重放模型或永久占用来源。若内容已被外部程序删除，记录失败并允许用户重新提供文件，不能把后来的同名文件自动替换进历史。

### 历史记录与已有副本接管

- **新记录：** 提交或交付事实保存稳定附件关系；资源表保存可重建展示投影；ArtifactStore 保存内容与 owner。内存 object URL、缩略图和 Provider 临时路径不作为持久身份。
- **已有 Artifact：** 验证现有 owner 的访问权后增加新关系，绝不让“知道哈希”变成读取权限。跨会话去重只共享字节，不共享授权。
- **已有受管文件：** 先盘点任务、会话、Telegram、批注、最终图片的现有引用和清理规则。读取继续复用现有受管副本；通过明确接管操作将单个文件导入内容仓、核对哈希、提交全部关系后，才允许释放旧位置。每个来源只接管一次；期间短暂双份占用属于迁移成本，不是永久双写方案。接管完成条件是保留记录均已切换且旧位置没有活跃引用；目录保留在既有任务服务边界内。
- **历史原路径仍存在：** 继续标为旧路径引用。现在读取到的字节不能证明等于发送时内容；若用户选择保存当前内容，记录当前捕获时间与来源，不伪造历史快照。不能在打开历史时自动全盘复制。
- **历史原路径已消失：** 有精确会话、消息或工具调用与字节证据时才恢复并登记来源。原任务恢复的 PNG 可作为候选，但本轮不改写原消息。没有证据时显示“原文件已不存在，未保存历史副本”，不按同名搜索猜图。
- **导出和恢复：** 副本导出带内容及引用清单；路径引用导出的是引用说明，不承诺在另一台机器可打开。备份需同时覆盖关系数据库、对象仓及必要的任务目录副本，仅备份 SQLite 不够。缩略图与工作副本可重建。

新增业务事实优先放在现有提交与资源契约，复用现有 Artifact 关系表。若实施时现有草稿或接管记录不能表达持久归属和状态，只补足这些实际缺口；任何结构变更须另行核对 SQLite 实际版本、迁移入口与存量关系。本方案不附 DDL，也未执行数据库操作。

### 来源变化、删除与失败时的行为

| 情况 | 内容副本 | 当前文件引用 |
| --- | --- | --- |
| 来源改名、移动或删除 | 历史预览和下载保持不变；“打开原文件”可失效。 | 明确提示原位置不可用；重新定位需要新授权，不按同名自动替换。 |
| 来源内容改变 | 历史保持原内容；主动替换附件产生新关系。 | 打开和助手读取时得到当前内容。若需提示“已变化”，依据已有摘要或文件状态判断；大小和时间只能作线索。 |
| 导入期间来源变化 | 拒绝提交这份副本，保留明确失败状态；需要重新导入。 | 使用时重新做授权和实际路径校验；不能沿用失效链接授权。 |
| 存储不足、格式无法预览 | 保存失败时阻止该附件被当作成功提交；已保存但无法预览时仍可下载原件。 | 路径可以保留，但必须标明未保存副本；不能在副本保存失败时自动降级为引用。 |
| 归档对象缺失或损坏 | 显示“保存的附件不可用”，走证据恢复；不静默读取已变化的原文件。 | 按当前路径状态报错，不承诺恢复旧内容。 |
| 移除草稿或取消发送 | 解除该草稿关系；发送结果未知时先保留，确认接纳结果后处理。 | 仅移除引用，永不删除用户原文件。 |
| 删除消息、任务或会话 | 解除被删除实体自己的关系及对应保留锁；其他消息、正式成果和恢复保留仍有效。 | 删除关系，不删除源文件或目录。 |

### 存储增长、关系与清理

1. **以关系为准，不维护易漂移的裸计数。** 复用 `artifact_owners` 的唯一关系；引用数由关系派生。owner 应能定位到具体附件或稳定业务记录，重试不得重复增加关系。删除一条消息只解除它的关系，不能按内容哈希批量解除别人的 owner。
2. **草稿保护必须持久。** 保存成功先绑定草稿或导入命令 owner；不能只靠 Renderer 内存保护。提交后绑定正式 owner，再释放草稿关系。建议无活跃编辑、无排队提交、无未知发送结果的废弃草稿在最后活动七天后进入可清理范围；七天是待确认的产品默认建议，不是已核实的现行策略。现有草稿机制若不能记录这些状态，需补最小持久记录。
3. **保留与回收分开。** 消息保留期间不因图片很久没打开而清理。沿用当前保留策略和 GC：关系解除、保留期及锁处理、生成清单、再次核对、隔离、延迟删除。删除业务关系时先落实适用的删除保留期，再释放对应活动锁，不能顺手释放恢复或导出保护。接纳关系和隔离状态须在同一 Core 写入边界裁定，并在变更事务中复核对象状态。现有活动会话三十天、归档会话三百六十五天是策略下限，不是到期删除有 owner 内容的时间表。
4. **先接齐关系，再允许自动回收。** 迁移中的文件、仍被旧记录引用的受管路径、运行中的工具图片、队列附件、正式成果和未知接纳结果都受保护。旧目录不能仅按 mtime 扫描删除。已有通用磁盘清理脚本不能替代内容仓的 owner 检查。
5. **统一计量，不重复计费。** 内容仓按唯一对象统计物理字节，同时分列 staging、隔离区、旧受管目录、任务目录副本和可重建工作副本；逻辑附件数与实际存储量分别显示。复用已有容量诊断、增长采样和大对象列表，不增加第二个容量统计系统。
6. **容量不足不牺牲已发送记录。** 复用剩余空间和配额预检；已知内容引用直接复用。现有预检在去重前按请求大小预算，导入和接管还会有 staging 峰值，不能承诺“相同内容永远零额外空间”。并发接纳需约束峰值，真实写入失败保持可恢复记录。配额不足时拒绝新导入并提供现有清理入口，不自动删除仍有关系的旧消息内容。
7. **限制按用途区分。** 保留已有导入、Telegram、图片归档和预览预算，实施时统一解释并核对差异，不为统一接口直接放宽。保存原件、生成缩略图和发给模型是三种预算；不能为了模型输入限制删除原件，也不能把任意大图完整放进热会话数据。
8. **修复一致性，不猜测归属。** 维护时核对业务记录与 owner、未完成 staging、孤立导入、活动保留锁和对象完整性。可重建关系只从权威记录恢复；来源不明先保留并报告。逻辑删除和隔离不等于安全擦除，备份与用户导出属于独立保留范围。

### 必要方案取舍及竞品借鉴

| 方案 | 优点 | 代价与适用边界 | 结论 |
| --- | --- | --- | --- |
| 全部保存原路径 | 磁盘开销小，适合继续编辑当前工作文件。 | 临时来源会消失，内容会变化；不能兑现发送内容的历史留存。 | 仅用于明确的当前文件引用。 |
| 所有文件和目录无条件复制 | 实现表面统一，容易获得单次目录快照。 | 复制整个项目、依赖与构建目录；增加存储、泄露无关内容风险，也改变助手操作当前工作区的语义。 | 不采用。仅保留已有显式任务目录上传或明确交付。 |
| 各入口独立复制 | 可以局部修复丢图，短期改动较小。 | 不能统一直连服务端、引用释放和共享清理；重复内容占用与规则漂移持续存在。 | 现有保护继续有效，但不是长期目标。 |
| 所有内容内嵌会话记录 | 单份历史容易携带字节，Codex 图片历史证明其可恢复价值。 | Base64 和重复正文增大日志、读取与传输成本；不适合把普通大文件都塞进热记录。 | 仅作为 Provider 协议或导出表示，不作为 Zeus 主要附件仓。 |
| 显式语义 + 现有 ArtifactStore | 对准用户预期；内容可去重、独立授权、统一维护，复用已有正式成果和工具图片能力。 | 需要接齐关系事务、读取适配、旧副本接管及清理；不是只多调用一次 copy。 | 推荐。目录继续留在已有任务服务边界。 |

对比采用前一节固定源码快照，不把它们说成当前安装产品的运行结果。借鉴 Codex 保存实际图片表示及工具输出证据；借鉴 Cindy 的消息归属与媒体内容分离；借鉴 OpenCode 区分内容附件和路径引用。三者都不能作为“所有附件必须复制”的依据。Zeus 已有 ArtifactStore 和工具图片原件，不需要照搬另一套媒体协议或重建存储引擎。

### 实施顺序与完成条件

顺序只安排依赖，不减少覆盖范围。当前轮次不实施以下步骤。

1. **固定契约和读取边界。** 明确添加附件、引用文件、文件交付与所见记录的语义；扩展稳定引用与保存状态；统一内容识别和读取授权。完成条件是同一附件可以从提交事实重建历史预览，不依赖来源路径或 Renderer 状态。
2. **接齐输入与归属。** 接入桌面、全部服务端调用、草稿、排队、反馈和任务推送；复用任务、剪贴板、Telegram 已有保护。完成条件是新增内容副本不能绕过接纳，草稿取消不能删掉正式内容，未知接纳结果不被清理。
3. **接齐过程与交付。** 关联工具图片现有 Artifact、适配原生 imageView 证据，统一最终 Markdown 图片和结构化文件卡片；正式成果直接引用。完成条件是路径事件与有内容证据的记录明确区分，文件卡片保存状态真实可见。
4. **接管存量与维护。** 提供可审阅盘点和接管计划，处理历史失效引用、关系释放、容量和隔离回收；旧写入停用后完成旧引用收敛，禁止永久双写。完成条件是所有保留入口都有明确内容或引用身份，清理能说明每个候选为何无主、哪些关系仍阻止删除。
5. **分别完成平台验收。** 在获得实施授权后按下面范围验证实际行为；不能用编译结果或单端记录代替。既有源码修复尚未完成这项验收。

### 覆盖范围、未解决事项与假设

- **方案覆盖：** 会话普通文件、SVG/AVIF/ICO、服务端直接提交、所有共享发送调用方、imageView、结构化交付；同时覆盖任务表单、剪贴板、Telegram、正式成果、最终图片及批注截图的复用、归属和维护。
- **仍未解决的实际问题：** 原失效消息尚未改写；前阶段图片修复仍有格式和入口遗漏；普通附件未实现显式语义；过程与卡片尚未接入统一内容关系；Telegram Windows 路径问题未修复；本方案所有新增行为尚未实施。
- **需在实施中查明的技术事实：** 每个 Provider 的原生查看图片事件能否提供可精确配对的内容；现有草稿是否足以持久表达 owner 活跃状态；同内容并发导入、事务组合、MIME 元数据冲突、既有引用接管和两端文件系统故障的实际行为。不能只凭 API 存在认定这些已安全。
- **建议默认但未确认的产品选择：** 添加附件默认内容副本、引用文件默认当前内容；废弃草稿建议七天宽限。磁盘总配额和具体保留期应沿用已确认产品策略，缺少使用规模数据时不编造容量收益或自行承诺保留上限。这些选择不阻塞本轮方案交付。
- **不作承诺：** 没有历史内容证据时无法还原当时文件；只保存本机副本不等于防磁盘损坏或云备份；任意格式的模型输入、网页完整离线归档、项目目录自动快照、跨机器路径自动修复不在本方案承诺内。显式任务目录上传的现有能力继续保留。
