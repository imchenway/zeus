## 原因判断与方案

源码确认：`PendingRequestSurface` 中的自定义回答每次文本变化都会调用共享 `autosizeTextarea`。该函数先将真实输入框的高度设为 `auto`，随后读取 `scrollHeight` 强制布局，再写回计算高度。临时收缩会改变底部交互区与正文区域的可用高度，也可能触发浏览器滚动位置钳制和光标可见性调整。中文组合输入会反复经过该路径。

这是与录屏现象一致的代码原因判断，尚未通过修改前后原生应用对照确认全部触发条件；没有将静态分析写成实机复现结论。

采用项目自由回答和计划反馈框已经使用的 `field-sizing: content`，让浏览器直接按内容计算高度，删除临时收缩、读取、恢复的 JavaScript 流程。Chrome 官方说明该能力自 Chromium 123 起支持；当前项目依赖 Electron 42.11.10。参考：[CSS field-sizing](https://developer.chrome.com/docs/css-ui/css-field-sizing)。

- 优点：消除每次输入强制布局的中间尺寸，复用现有技术；换行、删除、宽度变化和输入法组合文本均由浏览器计算尺寸。
- 代价：依赖项目当前 Electron 的 CSS 能力，不提供旧浏览器兼容分支。文本真实换行时输入区仍会自然增高；修复目标不是冻结所有布局变化。
- 未采用固定输入区高度，因为它会缩小长回答的可见范围；未采用记录后恢复外层 scrollTop，因为它会与正文跟随和用户滚动竞争。

## 修改与调用入口

已移除全部旧函数调用、无用导入和仅服务于该函数的窗口尺寸监听，并删除无人调用的 `textareaAutosize.ts`。

| 入口 | 调用链与处理 |
| --- | --- |
| 同步询问、自定义回答 | SessionWorkspace → PendingRequestSurface → RequestUserInputPanel；复用自由回答框的原生尺寸方式，最小 30px、最大 24vh |
| 异步询问、自定义回答 | SessionWorkspace → AsyncQuestionPanel → RequestUserInputPanel；与同步入口使用同一修复 |
| 自由回答、计划反馈 | 已有原生自适应实现；自由回答与自定义回答共享样式，计划反馈维持既有实现 |
| 已有会话目标输入 | SessionComposerProjection → ConversationComposer；原生伸缩，保留 48px 最小高度、34vh 上限和内部滚动 |
| 新会话目标输入 | SessionWorkspace 内新会话输入；复用同一输入区样式 |
| 历史消息编辑 | ConversationTranscript → ThreadItemView；保留 72px 最小高度和 48vh 上限 |
| 排队消息编辑 | SessionQueueProjection → QueuedConversationMessages；保留样式中有效的 84px 最小高度及 min(28vh, 180px) 上限 |
