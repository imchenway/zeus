# ZEUS-0922 多仓库交付与冲突保全

## 需求与边界

- 用户进一步明确：代码交付必须将当前工作目录下所有 Git 仓库的代码全部合入各自来源分支。单仓冲突处理结束不等于整次交付结束。
- 修复代码交付进入冲突会话后遗漏同一任务其他仓库的问题。
- 冲突处理覆盖当前仓库全部冲突及自动合并文件，结合任务会话意图、共同祖先和双方提交历史保留有效修改。
- 提交时间仅作为证据，不能按时间或 ours/theirs 整体覆盖。分支推进后继续使用既有 SHA 校验和重新合并机制。
- 本轮修改 Zeus 当前工作区，不自动补合历史业务仓库，不推送、不修改生产数据库。

## 规则与现场

- 项目实际规范文件为 PROJECT-STYLE.md，已通读；其余三类规范文件未发现，AGENTS.md 使用会话提供的完整规则。
- 已核对当前 docs 中 ZEUS-0921 的多仓库入口修复和 ZEUS-0892 的冲突交付记录，当前 Git 初始干净。
- deliveryWorkspacesForConversationBranch 按当前会话工作区的 branchName 过滤。冲突分支名称独立，因此原任务其他仓库被排除。此函数同时供环境卡片和任务交付文件树使用。
- 交付执行器本身按已选仓库分别推进，单仓失败不阻塞其他仓库；只有全部步骤成功才更新任务状态。前端范围丢失发生在交付请求建立前。
- 只读核对今日 CCKG 记录：任务 task_417e1f4bc4e3be7ee07ddf47cced7ef1（ZEUS-0110）有四个原任务仓库及一个 SDK 冲突工作区，合入记录仅涉及 SDK；该记录证明范围结构，不单独证明其余仓库存在遗漏提交。任务 task_b33b9280b2f398a41a185f73ea803810（ZEUS-0107）还有二级冲突工作区，需要沿 baseWorkspaceId 逐级回溯。任务编号跨项目重复，核对使用真实任务 ID。

## 方案与取舍

- 复用原任务工作区关系和 environmentId 恢复同一开发环境的仓库范围；当前仓库保留确切的冲突开发线，避免重复交付其祖先工作区。旧记录无环境身份时才沿用原分支范围，失效关系不扩大范围。
- 复用既有会话消息仓储，向冲突处理提供有界的本任务用户消息、时间及来源身份；明确截断和缺失。结合真实 Git 历史判断，不能把旧会话文本当成新的执行授权。
- 初次冲突、准备重试、普通会话交付及冲突继续入口采用一致的保全要求，来源草稿仍保持未提交语义。
- 优点：修复共享范围根因，沿用现有文件树、原生窗口和逐仓执行能力，不增加交付状态机或数据库结构。
- 代价：冲突会话的交付页会加载同一任务环境其他仓库；会话摘录有长度上限，需要 AI 根据任务文档和 Git 补充证据。多仓库合入仍不是跨仓事务，逐仓成功与失败必须保留。

2. 任务冲突初次接纳、准备恢复、普通会话交付都注入需求与用户消息摘录。普通目录会话若确属当前项目任务，也读取本任务意图；无任务关联时仅读取原会话。消息带会话 ID、消息 ID 和时间，最多提供最近 12 条、每条 1000 字符，任务描述最多 4000 字符，省略处明确标记。
3. 初次处理和继续处理共用保全要求：读取 docs、共同祖先、双方提交 SHA、作者时间及提交时间，检查全仓冲突与自动合并文件；时间不能决定整侧覆盖，替代或删除必须说明需求和代码依据。以上为后续 AI 执行要求，不代表本轮已经完成历史业务代码的语义验收。
4. 共享 completeTaskIntegrationCommit 拒绝未暂存或未跟踪的新修改；普通 merge 丢失合并状态却仍有暂存内容时也拒绝收尾。来源草稿仍复用原有专门路径，不混入正式任务提交。
5. 发现并删除分支推进后的自动强制清理、重建路径。原流程会经 worktree remove --force 删除尚未提交的冲突处理成果；现保留原工作区与错误原因，由原会话代码交付重新审阅并同步。其他过期尝试仅允许回收干净现场。

优点：同一任务环境的其他仓库不再因冲突分支名不同而消失；分支并发推进、漏暂存和合并状态异常不会直接忽略已有修改。

代价：分支推进后不能自动沿用过期候选完成交付，需要用户在原会话重新审阅；业务语义仍需要结合真实代码判断，提示词和提交时间都不能证明所有新逻辑必然保留。

- 执行器接管已有的唯一、精确匹配候选的 AI 会话；多个有效尝试时明确停下核对。整批冲突接管将同一权限设置应用于本次全部待处理仓库，手工草稿仅应用于其所属步骤；已有会话和结果未知步骤不盲目重发。
- 原会话继续处理时，若只有一条关联的未完成整批运行，则恢复该运行；成功仓库不重做，其他仓库继续推进。旧待办没有整批授权快照时不自动扩大原范围。
- 新交付核对过期候选时，只有当前 Git 包含关系证明任务提交已进入来源分支，才关闭旧记录并重新记录本次合入事实；原冲突目录仍保留。无法证明时要求在原冲突会话继续，不能按时间或旧状态猜测成功。Git 包含关系是合并历史证据，不代替后续业务语义核验。
- 单仓成功事件明确显示仓库名称。只有整批所有步骤 succeeded 才出现整体成功，冲突、待同步、读取失败和 unknown 均不算完成；已接纳清单固定，运行中出现范围外提交仍要求重新审阅。

优点：代码交付的目录范围、各仓库来源、冲突续办和完成状态采用同一口径；不再需要用户从第一个冲突页逐仓寻找剩余工作。

代价：完整交付会读取和处理更多仓库，独立 AI 会话的并发与模型用量随冲突仓库数量增加；未登记仓库和证据不足会阻止整体完成。仓库发现不会扫描依赖缓存、其他任务工作树或符号链接指向的外部目录。
