# ZEUS-0933 发送消息即时状态反馈

## 需求与现场

发送后立即显示“正在执行”；发生网络恢复时，由已有“正在连接… (1/5)”组件接管；明确失败或恢复耗尽时显示已有错误组件。沿用原消息身份与重试、查看原因操作。

当前工作树初始无改动。已读仓库内 PROJECT-STYLE.md；文件定位未发现其他 AGENTS.md、CODE-GUIDELINES.md、DESIGN.md。会话提供的全局规则同样适用。历史依据优先核对 docs/ZEUS-0879_会话发送与切换性能及弱网一致性.md，独立消息发送边界再以现有代码核实。

## 原因与取舍

`send_started` 已立即插入本地用户消息并清空输入，但不会设置权威会话运行状态。正文仅依据服务端轮次决定是否显示运行提示，输入框也只在活动轮次中显示停止按钮，因此服务端接纳前出现无反馈窗口。

方案：用现有消息状态补充展示层判断，复用 TranscriptActiveStatus、MessageDeliveryOutcomeFeedback 和 ConversationNotice。连接次数来自现有只读核对循环，不新增网络重试、不重放发送、不建立会话级锁。

优点：发送立即可见，明确失败与结果未知仍归属各自消息，后续消息不被阻塞；正文、输入框共用判断，继续隔离流式正文的输入区订阅。

代价与边界：“正在执行”覆盖本地发送到模型接手的整个请求阶段，并不表示模型已经开始生成。停止按钮立即切换，但仍须取得真实、匹配的已开始轮次才能启用。原题回答沿用问题组件，排队消息沿用排队区域。

## 入口与平台

- 普通会话、任务会话：SessionWorkspace → 分区状态投影 → ConversationTranscript / ConversationComposer → useSessionController。
- 侧栏已建立的对话：正文与发送继续复用会话工作区。SideQuestionWorkspace 首次创建草稿使用独立创建流程，本次未修改该流程，也未做该入口的实机观察。
- 子智能体详情：SubagentWorkspace 复用正文组件；历史只读模式不显示活动状态。
- macOS、Windows 共用 Renderer 与控制器。本次没有新增平台专属逻辑。
- 任务首发另有 SessionCreationNotice，创建阶段改用同一“正在执行”组件，继续保留它的重试和错误接管规则；本次仅核对调用代码。

## 追加：录屏中的反复闪烁

用户提供 29.53 秒、4096×2334 的原生录屏。逐帧查看确认，约 21–24.1 秒同一位置在“正在执行”和多段英文思考摘要之间反复切换，正文与答题卡随高度变化上下位移；不是单纯文字扫光。20 Hz 抽帧显示最明显的相邻帧变化集中在此区间。

只读核对运行现场：进程 19239 使用 `/Applications/Zeus.app`，启动于 13:43:28，安装目录的 app.asar 修改时间为 13:18。实际打包代码 `session-workspace-CO8HwTyl.js` 仍存在 `jt===executing && Mt ? 摘要组件 : 运行提示组件` 的互斥分支，且 Mt 来自 `state.currentReasoningItem`。这与录屏中的交替呈现相符。当前任务工作树及其 Renderer 构建已经移除该分支，但没有更新安装目录，不能将代码完成描述为用户正在使用的应用已修好。

本轮补充同一预览入口的“连续摘要”：交替输入空摘要、不同长度的多行摘要，共推进 120 次。实际记录 121 个样本，均只有一处“正在执行”；状态节点替换 0 次，状态顶部恒为 275 px、用户消息顶部恒为 176 px、滚动高度恒为 320 px、scrollTop 恒为 0。改动文件 ESLint 与差异空白检查通过。

边界：浏览器报告 `document.visibilityState=hidden`，计时受到后台调度影响，因此这些结果只证明连续更新下的 DOM 身份和布局稳定，不能证明原生可见帧已经无闪烁。没有替换安装包、重启用户应用或改变实际会话。macOS 录屏仅作为故障证据；Windows 尚无实机结果。

取舍：继续使用前一阶段已完成的单一执行状态，不增加延时、防抖、固定高度或摘要缓存来掩盖旧分支。优点是直接消除两种组件交替占位；代价是当前运行应用必须更新到包含该修复的构建后，才具备现场复验条件。

## 恢复实时摘要：已确认规则与实现

用户确认：有摘要时替换“正在执行”，无摘要时显示“正在执行”；同一轮次的更新没带摘要时，保留最近有效摘要。重连、错误和等待交互仍优先接管，本轮结束或切换会话、轮次后不沿用旧摘要。不同模型共用规则。

本次修改：

- `TranscriptActiveStatus` 始终保留同一个状态节点和扫光组件，只切换实际文字。没有新增摘要折叠、固定高度、延时或防抖。
- `SessionReasoningSummary` 的原摘要提取方法移至纯函数文件 `reasoningSummary.ts`，活动状态与历史过程共用原有摘要提取规则，不删除模型提供的内容。
- 快照水合和实时事件共用 `reconcileCurrentReasoningItem`。无摘要、空条目不会清空本轮最近有效内容；不同条目按持久位置选择最新摘要，同一条目继续复用现有内容修订合并。普通正文事件不再清空摘要；结束事件和终态快照仍清理临时状态。
- 多行摘要沿用原状态样式，补充窄窗口换行。原界面仅在 `.session-transcript-thinking` 存在时使用 6 px 行间距；以前替换成摘要组件会改变整段消息区的间距。现在该节点保持不变，不再触发这项布局切换。

代码可确认的原因：快照缺少摘要时旧代码直接置空；快照把不同摘要条目交给只适用于同一条目的修订合并；实时最终正文会清空摘要。这些路径都可能引发显示回退。录屏能确认来回替换及位移，但没有原会话事件序列，不能据此断言每次闪烁分别由哪条路径触发。

优点：实时摘要保留；空更新和旧更新不会引发摘要与占位反复切换；不新增 Provider 特判。代价：同轮暂停生成摘要时仍显示最近有效内容；真正的新摘要变长、换行时高度仍自然变化，不承诺内容变化时高度恒定。

### Provider 与入口核对

- Codex：`codexProviderEventProjection` 接收 `summaryTextDelta` / `summaryPartAdded`，`reasoningSummaryProjection` 形成已有 `presentation.summarySegments`，之后进入共享事件归约与状态展示。空分段不覆盖已有可读摘要。
- Pi 接入的模型：`TurnProcessProjector` 将消息结束时的 `thinking` / `reasoning` 块转换为 reasoning 过程；`publishPiProcessItems` 发往同一事件归约。现有 `thinking_delta` 路径只记首字时间，并未逐片发布摘要。本次复用已经提供的可读内容，不扩展 Provider 的传输协议；未发布摘要时显示“正在执行”。重开会话时仅从现有活动投影恢复，不把历史过程冒充当前摘要。
- 不提供思考内容的模型：活动期间继续显示“正在执行”，不生成或推测摘要。
- Provider 的重连次数来自现有进度字段；本地未知发送的只读核对仍使用已有五次上限，两者没有混用。
- 普通会话、任务会话和已建立的侧栏会话复用 SessionWorkspace；子智能体详情复用 ConversationTranscript；只读历史不显示活动状态。首次创建阶段在没有摘要时继续显示执行状态。
- macOS 与 Windows 共用 Renderer。本次没有修改平台服务，也没有真实模型、多端原生发送或侧栏首次创建的实机结果。
