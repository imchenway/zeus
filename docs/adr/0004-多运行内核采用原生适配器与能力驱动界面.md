# 多运行内核采用原生适配器与能力驱动界面

Zeus 采用多运行内核架构：Codex 继续通过 Codex App Server 保留原生 harness；Grok、Kimi、DeepSeek 与经真实目录验证的 ZAI/GLM
优先通过 Pi adapter 接入；Claude Code 未来作为独立原生 adapter，优先级最低。Zeus 保持统一会话主路径，但由 adapter
声明真实能力并驱动界面，不把所有运行内核压成最低公共功能，也不把 Pi 能调用的模型误称为 Codex 或其他原生 harness。

## 选择原因

全部改走 Pi 能降低适配器数量，但会失去已经实现的 Codex thread、turn、item、审批、账号和恢复语义；每个模型都开发独立 agent
又会重复工具、会话、安全与运维体系。保留少量原生运行内核适配器，并让 Pi 承载通用模型供应源，可以同时保住 Codex 原生能力与多模型扩展效率。

## 结果

- Zeus 产品会话与运行内核原生会话采用双层身份并保持明确绑定。
- 已有会话不能静默更换运行内核；跨内核使用时创建新会话并显式承接必要上下文。
- Codex、Pi 与未来 Claude adapter 分别维护协议、权限、恢复和能力证据，共享 Zeus 的会话主干与产品级状态语言。
- Zeus 只拥有产品编排层，不重写 Codex core 或 Pi agent core 的模型驱动工具循环；承接工具和审批请求不等于自研内层 harness。
- UI 只展示当前 adapter 已声明且完成真实验证的功能；模型名称、provider 配置或静态功能清单不构成支持证据。
- Pi provider 目录中的 xAI、DeepSeek、Kimi For Coding 和 ZAI 只是接入候选；Zeus 支持状态必须由账号、模型目录、真实会话、工具、安全和恢复验收决定。

优点是兼顾 Codex 原生保真与多模型扩展，并允许不同运行内核发挥各自高级能力。代价是需要维护 capability
contract、双层会话身份、跨内核承接流程和多 adapter 验收矩阵。

首个公共框架里程碑不接真实 Pi 模型且默认隐藏 Pi；Pi 的独立进程、安全和能力证据约束见
`docs/adr/0005-Pi采用独立进程且公共框架默认隐藏.md`。

## ZEUS-0311 修订

“跨运行内核创建新产品会话”已由 ADR 0014 替代。产品会话现在持有统一时间线、队列和确认模型历史，Codex thread 与 Pi session 降为可封存运行分段。适配器继续分别维护原生 session/thread、turn、事件、审批、输入和中断，但不再各自拥有产品队列、模型切换事务或业务恢复状态。跨内核切换只有在目标首个真实 turn 被接纳后才提升运行分段。
