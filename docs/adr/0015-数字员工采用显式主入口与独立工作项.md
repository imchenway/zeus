# 数字员工采用显式主入口与独立工作项

> 0016 已取代本文中“同一任务允许多个并行活动工作项”和旧“预览 → 创建”指派交互的约定；0017 已取代 Agent/Command 员工二分和 Command 主入口。独立工作项、冻结运行、正式交付物、上下文隔离和历史保留继续有效。

数字员工由版本化能力配置拥有唯一 Agent 或 Command 主执行入口。普通指派通过“预览 → 创建”形成独立工作项和冻结运行；指派次数、尝试次数、岗位名称与旧阶段位置均不得决定行为。Agent 会话、Command 运行、正式交付物和管理者决定相互分离；任务工作流只有在真实关系被显式提供时才参与编排。

## Considered Options

- 保留固定“方案规划 → 实施 → 代码审查”三阶段，并按指派或尝试次数推进：实现简单，但次数没有业务语义，员工配置失去权威，失败会错误推进到不存在事实的阶段。
- 根据“开发”“部署”等岗位文本推断 Agent、Command 或阶段：配置成本低，但岗位是可编辑说明，不是稳定行为枚举，无法安全推导模型、命令、参数和权限。
- 在既有单会话执行上继续补丁，完成后自动提交、部署或完结：复用代码多，但消息、产物、权限与外部副作用仍混为一体，无法可靠验收和恢复。
- 建立显式主入口、独立工作项、冻结运行、上下文清单、正式交付物和管理者决定：迁移成本较高，但领域事实清楚，可并行、可审计且能复用未来流程关系。

## Consequences

- 新增 `task_work_items`、`task_work_runs`、`task_work_deliverables`、`task_work_decisions` 四类 v2 权威记录；旧 `digital_employee_executions`、阶段和交付物不迁写，只在兼容编排与证据投影中保留。
- Agent 运行只能引用 `conversationId`，Command 运行只能引用 `commandRunId`；两者互斥。Command 人工指派直接确认并启动，自动化只创建确认待办。
- 会话完成只提交 `submitted` 交付物。接受使工作项完成；要求修改保留旧版本并创建同一工作项的新运行。
- `deliveryGrants` 降级为权限上限；提交、推送、合入、部署和任务完结必须来自显式管理动作或未来流程节点，不再由会话终态自动触发。
- `WorkContextManifestV1` 只允许任务事实、附件、项目规则和显式选中的已验收交付物；完整会话与未选产物不得隐式泄漏。
- Skill 的全部资源按运行写入 Artifact 并物化为只读快照目录；提示只暴露精简元数据和快照路径，实际读取另记启用证据。
- 受管 Agent 会话由服务端拒绝普通消息，只允许在任务驾驶舱通过管理者决定回复请求；会话页面只保留证据查看和返回任务入口。
- 独立工作项的 `relationships` 为空。未来流程编辑器或编排器复用同一执行接口，并且只有持久化真实依赖后页面才显示连线。
- 管理驾驶舱成为受管工作的主控制面；会话、命令日志、文件变化和旧执行只作为证据下钻。

## 优缺点

优点：员工配置成为唯一行为来源；多个员工可真实并行；Agent 与 Command 边界明确；上下文、模型、Skill、权限和产物均可审计；失败和未知结果只影响相关工作项。

缺点：迁移期需要双读；Skill 资源快照和 Context Manifest 增加存储与 Runtime 适配复杂度；任务详情信息密度提高；未来流程编排仍需单独设计。
