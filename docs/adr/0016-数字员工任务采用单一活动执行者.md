# 数字员工任务采用单一活动执行者

## Context

ADR 0015 把每次指派建模为独立工作项，并允许同一任务并行运行多个数字员工。任务详情随后需要一个直接可编辑的“执行者”字段，但并行活动工作项会使该字段没有唯一值，也无法清楚表达切换、自动化竞争和停止失败后的真实状态。

## Decision

每个任务同时只允许一个实际运行中的数字员工。活动运行定义为 `prepared / dispatching / active / waiting_input`；`runtime_completed`、已完成、待验收、失败、阻塞、取消和历史工作项不删除，也不占用执行者。

选择新的执行者只打开单次执行配置弹窗。最终确认时，客户端提交当前全部活动工作项的稳定身份和预期修订；服务端重新校验精确集合，并在所有旧运行得到真实停止确认后才创建新运行：

- 当前数字员工运行使用已有 turn interrupt；
- 若历史工作项仍引用独立 Command run，则仅为兼容停止而使用已有 run stop；
- 未外发的 `prepared` 运行可以本地取消；
- 派发、停止或外部写入结果未知时禁止新启动；
- 多个历史异常活动项逐个停止，每个成功结果立即持久化，任一失败都会终止切换。

自动化不得抢占活动执行者。重试和要求修改也必须先满足同任务没有其他活动运行。

## Considered Options

- 保留同任务并行活动项，并把执行者显示为多选或列表：保留并行能力，但“执行者”不再是单值，切换和自动化抢占仍无唯一语义。
- 客户端先调用取消接口，再单独创建新员工：实现直观，但两次请求之间存在竞争窗口，无法权威校验活动集合，也难以保证停止失败时不启动。
- 只把旧工作项标记取消，不停止真实 Provider/Command：界面变化快，但会留下后台真实运行和外部副作用，状态不可审计。
- 采用服务端原子语义的“精确活动集合 + 真实停止 + 新建”：实现需要兼容历史运行的停止链路，但状态、并发和故障边界清晰。

## Consequences

- ADR 0015 的显式主入口、冻结运行、正式交付物、管理者决定、上下文隔离和历史保留继续有效；仅“同一任务允许多个并行活动工作项”被本 ADR 取代。
- 新工作项仍是独立历史责任，`relationships` 只有在未来存在真实依赖时才使用。
- 服务端必须对人工创建、自动化、重试和返工使用同一活动运行判定，不能只依赖页面状态。
- 用户取消切换时旧运行不变；停止失败、结果未知或活动集合陈旧时新员工不创建。

## 优缺点

优点：任务执行者唯一；切换行为可审计；自动化不会静默抢占；停止失败和未知结果默认保护真实运行；历史工作项与交付物不丢失。

缺点：同一任务不能再并行启动多个数字员工；跨多个真实运行的异常历史数据需要逐个停止；用户需要拆分任务才能表达真正并行的工作责任。
