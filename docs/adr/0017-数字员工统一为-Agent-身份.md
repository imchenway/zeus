# 数字员工统一为 Agent 身份

## Context

旧能力迁移把 Agent 会话和命令中心运行建模成数字员工的两种主入口，导致项目设置出现“Command 员工”，任务执行弹窗也需要两套互斥流程。这个模型混淆了员工身份与执行能力：数字员工需要通过模型会话理解任务、选择工具并接受权限治理，执行命令只是 Agent 在运行中可能调用的能力。

## Decision

- 数字员工始终通过 Agent 会话执行，不再提供员工入口类型选择，也不允许创建新的 `command` 入口。
- 普通命令调用沿用会话运行时能力，由员工权限模式、沙箱和审批链路统一约束，不新增第二套命令权限模型。
- 项目固定部署命令继续作为 `allowDeploy` 下的项目专属能力；它不改变员工身份，也不会因任务开始或 Agent 完成而自动执行。
- 旧数据库中的 `command`、`requires_selection` 和 `requires_configuration` 员工读取时按其已保存的提示词、模型、Skill 和权限投影为 Agent；原 `deploy_command_id` 继续作为部署能力保留。员工下次保存时写回 Agent 入口，不新增数据库迁移。
- 历史任务工作项中的独立 Command run 只保留展示、证据、停止和失败处置兼容；新建和自动化路径只能创建 Agent 工作项。

## Considered Options

- 保留 Agent/Command 员工二分：可以直接运行固定命令，但员工身份、任务理解、权限与切换交互被分裂为两套模型。
- 为员工新增“允许执行命令”布尔开关：界面直观，但会与既有 `read-only / auto / full-access`、沙箱及审批规则重叠，容易产生矛盾授权。
- 统一为 Agent，并复用会话权限治理：改动最小，命令、文件和工具能力使用同一安全边界；固定部署命令仍可作为显式项目能力配置。

## Consequences

优点：员工身份唯一；系统模板、项目配置和单次执行不再分叉；命令调用复用成熟的会话权限与审批链路；历史部署能力不丢失。

缺点：不能把固定命令伪装成员工后绕过模型会话直接启动；历史独立 Command 工作项仍需保留兼容代码，待数据生命周期结束后才能删除。
