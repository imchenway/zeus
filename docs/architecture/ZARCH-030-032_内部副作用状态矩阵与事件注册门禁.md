# ZARCH-030～032 内部副作用、状态矩阵与事件注册门禁

## 本轮结论

公共 Command 清单仍由 `scripts/audit-command-side-effect-entries.mjs` 负责，当前动态结果保持为 203 项：183 个 `integrated`、6 个 `read_only`、1 个 `handoff_control_capability`、10 个 `ephemeral_capability`、2 个 `read_only_external_probe`、1 个 `diagnostic_capability`，`pending=0`。Electron Main 继续使用自己的独立分母，本文件不改变 Main 的 108/9/26/65/0 口径。

此前公共清单明确排除的 Git/Core/后台 Worker 内部调用现在由独立门禁接管，不再写成“待审计排除”。同时新增 Command/Provider/Recovery 状态转移矩阵，以及会话事件耐久级别的精确注册表。这三项都已接入 `pnpm verify:zarch-gates`。

## 1. 内部副作用机器清单

### 动态结果

`scripts/audit-internal-side-effect-entries.ts --require-complete` 当前声明 72 个 capability、10 个恢复/回执 policy，并从源码动态发现 128 个调用点：

| 类别 | 调用点 |
| --- | ---: |
| `@zeus/git-core` 写能力 | 35 |
| Core 提交后调度、投影、恢复与轮询 | 50 |
| Heavy Worker 创建、派发、IPC 与关闭 | 10 |
| OS 进程、PTY、Provider IPC/socket 与信号 | 33 |

机器声明位于 `scripts/internal-side-effect-registry.mjs`。每项 policy 必须同时说明稳定身份、真正写入边界、恢复规则、回执位置和源码证据，不能只贴“已覆盖”标签。审计执行以下失败关闭规则：

- `packages/git-core/src/index.ts` 的 `gitMutatingCapabilityNames` 是 Git 写能力的运行时单一来源；它与审计清单必须精确同集合，每个名字还必须仍是 exported function。
- Local Server 对 Git 写能力、Heavy Worker runtime export、受管 Core receiver、轮询器和进程/Worker 原语的调用点均由 TypeScript AST 重新发现；未知 capability 或缺失 policy 立即失败。
- `projectionDatabases.snapshot()` 是精确只读诊断排除；同一 receiver 新增其他方法不会继承该排除。
- 每个 policy 的证据文件和 marker 都必须存在；已删除但仍留在声明中的 Core/Worker/进程 capability 也会按 stale entry 失败。
- `afterCommit` 只负责在事务提交成功后唤醒消费者，事实和恢复游标必须位于 SQLite/outbox；内存 callback 不被伪造成完成回执。

### 审计范围

纳入范围包括：已登记 Git 写能力、Core `afterCommit`、投影数据库、TaskEvent 文件投影、任务 Telegram effect、Provider recovery/close、Heavy Worker、AI Runtime/Provider child process 与 IPC/socket，以及 Telegram/Handoff polling lifecycle。

不纳入本分母的内容包括：203 个公共 HTTP/Provider Command、Electron Main IPC/OS bridge、普通读查询、HTTP/WebSocket `reply.send` 和纯内存计算。前两类分别由既有公共清单与 Main 清单管理。该门禁不访问真实 Git、Provider、正式数据库或云，也不证明跨 SQLite、文件系统和远端系统的 exactly-once。

## 2. Command/Provider/Recovery 状态转移矩阵

`packages/shared/src/commandGovernance.ts` 当前登记 10 个主要状态机：

| 类别 | 状态机 | 运行时状态类型 |
| --- | --- | --- |
| Command | `command_delivery_attempt` | `CommandDeliveryAttemptState` |
| Command | `command_run` | `CommandRunStatus` |
| Provider | `conversation_submission` | `ConversationSubmissionStatus` |
| Provider | `conversation_turn` | `ConversationTurnStatus` |
| Provider | `conversation_provider` | `ConversationProviderState` |
| Provider | `provider_native_operation` | `NativeOperationStatus` |
| Provider | `runtime_session` | `RuntimeSessionStatus` |
| Recovery | `execution_host_handoff` | `ExecutionHostHandoffStatus` |
| Recovery | `storage_health` | `ZeusStorageHealthState` |
| Recovery | `recovery_promotion` | `RecoveryPromotionPhase` |

同一文件另登记 8 项并发语义：不可变 Command identity、Command Delivery state CAS、expected revision、Task `expectedUpdatedAt`、Provider generation CAS、Handoff snapshot CAS、Storage restart revalidation，以及恢复提升的离线 lease+hash。

`scripts/verify-command-governance-registry.ts` 会用 TypeScript AST 抽取 10 个运行时 string-union，要求状态集合与矩阵精确一致；同时检查每个终态无出边、所有转移目标存在、所有并发 policy 有真实文件和 marker。新增运行时状态而未决定允许转移，或删除 CAS 证据，都会失败。

此矩阵是治理契约，不是对所有领域服务的自动 runtime interceptor。当前它能防止状态词汇和 CAS 证据静默漂移，但不能仅凭静态 marker 证明真实 Provider/断电时序，也不覆盖产品自定义任务看板的全部业务状态。

## 3. 会话事件耐久级别注册表

`packages/local-server/src/eventFlowControl.ts` 是耐久分类的运行时单一来源。当前精确登记 38 个事件类型：

- `critical_fact`：32 个；包含 turn/submission/request/thread/goal/attention/warning、Provider 设置、任务 change-set 和所有失败/恢复边界。
- `coalescible_process`：6 个；仅 `conversation.item.delta`、`conversation.item.updated`、`conversation.turn.plan.updated`、`conversation.tokenUsage.changed`、`conversation.rateLimits.changed`、`conversation.mcpStartup.changed`。
- `ephemeral_ui`：0 个；空集合也是受门禁保护的明确产品事实。

运行时真正来自未来 Provider 版本的未知动态字符串保守提升为 `critical_fact`。源码中的字面量事件则必须先精确登记；不能再通过 `conversation.ui.*` 前缀或 `.progress/.delta` 后缀静默降级。

`scripts/audit-conversation-event-durability-registry.ts` 当前从 Coordinator、publish/broadcast、Provider 映射与事件对象中动态发现 36 个字面量类型，并与 38 项注册表核对。注册表允许预先保留尚无字面量发送点的已知协议事件，但发现的新字面量没有登记时立即失败。

## 4. 门禁命令

```bash
pnpm audit:internal-side-effects
pnpm verify:command-governance
pnpm audit:conversation-event-durability
node scripts/audit-command-side-effect-entries.mjs --require-complete
pnpm verify:zarch-gates
```

这些脚本是审计/行为 verifier，不是单元测试，也不启动正式 Provider、正式数据库或云服务。

## 收益

- 公共 203 清单的排除项现在有独立、动态、可失败关闭的分母，新 Git 写能力、Worker export 或受管 Core 方法不能靠默认分支进入产品。
- 状态词汇、终态和 CAS/revision 证据形成机读契约，代码重构时能尽早发现恢复语义漂移。
- 高频事件只有精确登记的六类可以合并，新增事件默认保留关键事实，降低误丢终态和恢复事件的风险。
- 三项门禁输出有界 JSON，可供 CI 和后续架构审计复用，不依赖文档中的手工数量。

## 缺点与剩余风险

- 内部副作用 registry 需要随新 capability 更新；精确失败关闭会增加改动时的登记成本。
- AST 审计覆盖已声明的边界模式，不是通用污点分析；新增完全不同的底层库时必须同步扩展 discovery rule，不能假设自动识别任意 I/O。
- 状态矩阵目前验证类型、允许边和并发证据，不会自动拦截每一次运行时转移；高风险路径仍需行为 verifier 与真实故障注入。
- 未知动态事件按关键事实持久化更安全，但可能增加 WAL/网络压力；只有形成明确产品语义后才能把它降为 coalescible 或 ephemeral。
- 本轮没有验证真实 Git、Provider、打包应用、正式静止副本或长流 SLO；构建和门禁通过不能替代这些最终证据。
