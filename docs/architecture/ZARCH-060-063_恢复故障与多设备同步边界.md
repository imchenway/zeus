# ZARCH-060～063：恢复、存储故障、宿主交接与多设备同步边界

## 1. 领域边界

本批次必须区分三类能力，不能使用同一“备份/同步”名称互相替代：

1. **灾备恢复包**：把某一时刻的数据库、获授权资产和 Provider 恢复能力封装为客户端加密、不可覆盖的恢复点；主要处理磁盘损坏、误迁移和设备丢失。
2. **本机高可用**：由唯一 Core 写入者、Execution Host 监督、故障关闭和无损交接保证窗口或进程故障不会制造双写；不依赖云端。
3. **多设备用户数据同步**：在多台设备间传播设置、任务等可编辑产品数据；需要逐类定义权威、冲突、删除、离线和密钥语义。用户已明确 iCloud / Google 指这一能力，不是恢复包双目的地复制。

多设备同步需求尚未定义，ZARCH-063 本轮暂停。不得因为存在加密恢复包或 File Provider 本地目录，就声称已实现设置/任务同步或真实云端提交。

### 收益与缺点

收益：运行中数据库不会被裸复制；受控 Test 根、规范 bootstrap、来源/目标树分离和 Storage open/close 身份复验会对正式根冒充、alternate root、符号链接、硬链接、过宽权限、超预算 bootstrap 与常见 rename-swap 失败关闭；隔离候选、正式提升和回退各有可审计身份；进程中断不产生空库或静默半恢复。

缺点：完整包耗时且需要额外磁盘；scrypt 增加 CPU/内存成本；在线复制允许正式 writer 合法前进，因此只能声称“副本为一致时间点快照”，不能声称来源目录完全未变化；只读验证仍需反复核验目标全库摘要，首启与退出时间随库大小线性增长；旧的任意临时 validation root/v1 manifest 不再兼容，无效 bootstrap 也不会向未受信目录写日志；项目总览不能显示实时 Git，副本里的“活动”记录也只作为历史诊断，不代表对应 Provider/Runtime 仍然存活；原子数据库替换无法自动解决多目录资产一致性，因此需要版本化 managed-data 代次或拒绝提升。

## 3. ZARCH-061：磁盘与 I/O 故障关闭

Core 对关键写入、checkpoint、Artifact staging 和命令耐久提交的 ENOSPC、EROFS 与 I/O 失败进入统一只读故障态。已提交数据继续可读；新副作用命令被拒绝；已写出 Provider 但回执未知的请求保持 `outcome_unknown/recovery_required`，不自动重发。

最终打包现场补充了 Provider 负向证据：Pi SDK 的 Agent 设置关闭运行时和 provider 两层 retry，能力目录不再宣告 retry；本机失败 Provider 对同一 turn 的直接断开只观察到一次网络请求。另一次请求保持活动后终止 Test Pi Worker，业务 turn 收口为 `ZEUS_PROVIDER_WORKER_RESULT_UNKNOWN`、`resultUnknown=true`，原生会话中用户输入只出现一次；显式 recovery 使用旧 generation CAS 切换新 Worker，`replayedCommandCount=0`，随后新的真实 1xm Haiku 会话成功。该链证明网络失败和 Worker 崩溃不会自动重发，但统一故障弹窗仍缺 Computer Use 可视证据。

进入故障态时必须先立即尝试回滚当前 SQLite 事务并丢弃其 `afterCommit` 回调；只有 `no_open_transaction` 或 `rolled_back` 且故障不是 `integrity_error` 时才能继续提供已提交数据读取。若回滚无法证明成功或已知数据库完整性损坏，health 明确返回 `readsAvailable=false`，所有 Repository `select/get` 与写入一起失败关闭，避免未提交或已损坏事实被当作安全历史。恢复前置检查必须覆盖 SQLite `quick_check`、WAL、外键、Artifact staging、Inbox/Outbox/receipt 语义一致性和剩余空间；只有显式恢复动作及新 Core generation 才能重新开放写入。外键检查只读取首条违规而不把损坏大库的全部违规物化进内存。预检分别返回 `preparedCommands`、`providerWritesAwaitingReconciliation` 和 `recoveryRequiredCommands`，未决 Provider 写出只进入对账清单，不自动重发或清零。Main IPC 会再次逐字段核对事务、数据库、外键、Command Ledger、Artifact staging/空间和非负有界计数，任一字段缺失或矛盾都不退出当前 Core。预检一旦通过，Main 先固化内存重启意图，再由 `finally` 幂等安装 timer；即使 Main receipt 的 fsync/rename 再次失败也不会留下“已安排但没有重启”的假状态。临时受限文件系统探针已验证磁盘满后第一次和后续写入都失败关闭、旧数据仍可读、活动 reader 阻断 WAL 时拒绝恢复，以及空间恢复并释放 reader 后预检可收敛；独立负向场景证明未提交行和通知在故障切换后均不可见、完整性错误禁止读取、Command Ledger 状态矛盾和外键违规即使 `quick_check=ok` 也会阻断重启，fake receipt 故障后仍恰好安排一次重启。

收益：恢复判定同时覆盖结构完整性和命令语义，不会把已写出但未确认的 Provider 动作误当成可重发；首条外键探测让内存占用有界。缺点：预检只报告是否存在外键违规，不返回完整违规列表；深入诊断需要独立离线工具，且保守重启闸机会延长故障期的只读时间。

收益：最危险的存储故障不会继续扩大数据库与外部副作用分叉。

缺点：故障期间只能只读；完整核对比简单重试慢，并需要清晰的维护页和用户恢复入口。

## 4. ZARCH-062：Execution Host 与升级交接

Detached Core 通过单实例锁、generation、rendezvous、启动状态、租约、心跳和能力版本保持唯一有效写入宿主。Renderer/Main 退出只解除 UI 租约；活动工作继续由原宿主持有。升级交接不再由 Main 捕获、携带或回写内存 checkpoint：旧 Core 在业务 SQLite 内以同一耐久事务创建唯一 active handoff、写入 Codex pending 请求的最小身份/CAS 条件与 hash，并关闭 `dispatch_enabled`；新 Core 在 Coordinator 恢复和队列派发前幂等 claim。只有仍匹配且可证明属于 `codex + codex_native + app_server` 的请求会写入 `interactionRecoveryCheckpoint`；任一 journal 自校验、总 hash、请求身份、turn 或 conversation CAS 漂移都会进入 `recovery_required + paused`，绝不把 Pi 绑定为 Codex。

### 数据根持久身份与协议 v2

每个 canonical 数据根现在以 0600 普通文件 `.zeus-root-identity.json` 持久绑定 `rootId + production/test/development profile + bundleId + bundleIdentityKind + schemaGeneration + canonicalRoot + Keychain service 身份摘要`。production/Test 的 `bundleIdentityKind=code_sign_bundle_id`，对应打包产物必须核验的 bundle ID；development 通常实际运行在共享 Electron.app，所以 `dev.hypha.zeus.development` 被明示标记为 `development_distribution_label`，它不是、也不得被描述为 Zeus code-sign bundle 身份。标记使用根内私有临时文件、`fsync`、硬链接 no-replace 发布和目录 `fsync`；读取时以 `O_NOFOLLOW` 的同一文件描述符限制大小，核对 owner、精确 0600、普通文件、`nlink=1` 和前后 dev/inode/size/mtime/ctime。完整性 SHA-256 只用于发现损坏、拷贝和误配，不是签名，也不是能抵抗同 UID 进程篡改的安全信任根。

空数据根可在任何 Core、Browser profile 或业务文件写入前原子认领。非空无标记自定义根固定返回 `ZEUS_DATA_ROOT_OFFLINE_ADOPTION_REQUIRED`，启动链不猜测 profile。既有自定义 production/Test 根只能由显式 CLI `pnpm data-root:adopt-offline` 两阶段认领：操作者必须逐字提供 canonical `--data-root`、`--profile production|test` 和匹配的 `--distribution-label`，先执行 `--plan`，再把绑定 root dev/inode、布局、SQLite 路径、inventory 摘要和 Keychain service 摘要的 64 位 `confirmationToken` 回传。脚本没有默认根，不读取 `ZEUS_USER_DATA_DIR`，无参数、帮助、缺参或未知参数都在动态加载身份模块和创建 preparation lock 前退出；development 不进入该迁移边界。

离线 CLI 只接受至少具有分层或 legacy-flat `zeus.db/zeus.config.json` 权威证据的非空根；两种布局并存、主库头无效、任意 nested symlink/特殊文件/业务 hardlink、Execution Host 目录任意残留、SQLite `-wal/-shm/-journal`、已有 marker 或目录 inventory 漂移都会失败关闭。Test 不能与系统账号 home 下的正式默认/历史 Application Support 根相同或互为父子目录，production 也不能认领 `.zeus-test`/`.zeus-development`。plan/apply 与 Main 共用根同级 preparation SQLite lease；apply 在锁内重新生成计划，并以 `lsof +D` 三次确认未观察到根内打开句柄后才原子 no-replace 发布唯一 0600 marker，不清理、不 checkpoint、不迁移业务文件。只有已知的正式默认/legacy 根仍可由启动链在唯一准备锁和无声明 writer 条件下补标为 production。

Execution Host 协议升为 v2。同一根身份的紧凑摘要现在必填贯穿 bootstrap、`host.lock`、startup、rendezvous、kernel lease 读写边界、capability 与 Browser bridge attach；Main 在 Browser bridge、Core、配置文件和 lease 产生副作用前先做只读对比，已存在但不可解析的宿主元数据也不降级为“无 Host”。普通 Test 与 production 宿主双向拒绝；`read_only_validation` 仍保留 manifest v2 全链校验，并额外要求数据根 profile 必须为 `test`。旧协议 v1 宿主不做热附着，会在任何新 Browser/Core 写入前进入结构化维护态；需待旧 writer 排空、安全退出后再由 v2 Main 启动。

v2 Host 若在发布 `host.lock` 后被 SIGKILL，OS 会释放 kernel lease，但诊断 lock/startup/rendezvous 可能残留。Main 只把“安全可解析的当前 v2 + `ownershipMode=kernel_lease_v1` + 相同 root/validation 身份 + lease 已释放”视为可恢复候选；PID 可能复用，不能代替 lease。Main 本身不删除 lock，只启动竞争 Child；只有实际取得相同 rootId kernel lease 的 Child 才能用同一 fd 安全读取旧 lock，记录 dev/inode/content，hard-link 到 0700 quarantine 中的确定性 0600 证据文件，再次核对 target inode/content 后以 `rename(temp, host.lock)` 原子替换并 `fsync` 目录。旧 lock 全程有 target 或 quarantine 名称，不出现 check-then-unlink 空窗；多个 Child 中只有 lease 赢家可替换，其余等待并附着赢家。legacy、未声明 ownership mode、相反 root/validation、非法/unsafe metadata 和路径漂移仍保持原文件并失败关闭。

收益：路径命名和环境变量不再是正式/Test/开发资料的唯一边界；错连宿主在 Browser 调用、SQLite 创建和文件写入前被拒绝，空根初启仍是一次原子快路径；非空自定义旧根有了不可误触、可复验且不改业务内容的离线迁移出口；v2 Host crash 不再因残留 lock 永久进入维护态。

缺点：每次启动与 attach 增加少量安全文件完整性/身份读取；协议 v1、非法身份和不可证根仍会保守停机。离线 adoption 会对大根执行三轮元数据 inventory 和 `lsof +D`，耗时与文件数近似线性，并在根同级留下 preparation-lock SQLite；`lsof` 只证明观察时没有打开句柄，不是持有业务数据库的排他 lease，最后观察到 marker 发布之间仍不能抵抗不遵循准备锁的同 UID writer。marker 的 hard-link no-replace 在 `link` 与临时名删除之间崩溃时可能留下 `nlink=2`/临时文件，后续会安全拒绝但仍需显式维修；因此这里只宣称正常路径的原子 no-replace 与 fsync，不宣称完整 crash-safe。Host quarantine 会保留每次异常接管的旧 lock 证据并增加少量 runtime 磁盘占用；最终 lstat 到 rename 仍不抵抗恶意同 UID path swap。

`verify-data-root-identity-binding.ts` 仅在 `mkdtemp` 合成目录执行，已覆盖空 Test 根 0600 认领、development label/code-sign bundle 语义区分、production/Test 双向互拒、非空无标记自定义根不写 marker、已知正式 legacy 根在真实数据准备锁下安全补标、`host.lock`/rendezvous/已持有 kernel lease 任一存在时不补标、拷贝 marker/rootId 与 symlink 拒绝，以及相反 Host 元数据在 Browser invoke、Core 数据库和 lease/文件写入前失败关闭。`verify-data-root-offline-adoption.ts` 另行覆盖无参数/帮助/缺参/未知参数对合成默认根零触碰、production/Test 分层与 legacy-flat 成功、确认失配、Host 全类残留、WAL/SHM/journal、可观察 writer、已有 marker、symlink/hardlink、普通目录和旧计划拒绝。`verify-execution-host-v2-crash-recovery.ts` 模拟 Host 不 cleanup 释放 lease，证明下一 generation 自动 quarantine/接管、PID 存活不主导、并发只有一个赢家，且 active owner、相反 root/validation/companion 与路径漂移均保持旧 lock。`verify-zeus-test-database-copy.ts` 另行证明预置 profile/config 的 strict root 不会生成数据库或 marker。这些探针不读写真实 `~/.zeus`、正式 Provider、Keychain 或云端，不生成也不启动生产 App。

prepare 先关闭所有 `/api` 业务请求接纳（仅 health、status 和 handoff 控制面保留），暂停 Telegram，等待已接纳 HTTP mutation，阻断活动 turn/runtime/command、Pi waiting、Project scan、Heavy Worker 和 Task Integration；随后停止用量刷新、Heavy Worker、Command Center timer、Legacy Import 与 Codex admission，排空增量/Runtime 保存，再以数据库级业务写 fence 阻止遗漏的 SQLite 写入，只有 handoff repository 获得窄写许可。投影库是独立可重建 SQLite，不属于业务 journal 原子边界，并在宿主关闭时排空。此处“全局”精确定义为业务 SQLite mutation；未经枚举的外部文件系统副作用仍不能据此宣称被同一事务回滚。

`POST /api/execution-host/handoff/prepare` 明确归类为 `handoff_control_capability`，而不是普通 durable Command：它的职责正是冻结并转移通用 Command Ledger 的单写入者，若反过来要求在冻结后向同一 Inbox/Outbox 写 accepted receipt，会形成生命周期自依赖。其耐久幂等性由同库 `execution_host_handoffs` journal、唯一 active 约束、checkpoint hash、状态 CAS 和进程内 single-flight 提供；失败后的 `recovery_required` 也写入该窄控制 journal。收益是交接在通用账本停止接纳后仍能完成且不会产生第二写入者；缺点是它不能复用普通 Command receipt/replay 工具，必须维持独立协议、审计规则和跨版本探针。

当前隔离探针使用构建后的 Desktop/Storage 产物验证：Pi waiting 返回专用 `409 ZEUS_EXECUTION_HOST_PI_WAITING_BLOCKED`，旧 PID 保持存活、journal=`aborted` 且派发重新开放；同一 Codex turn 的两个 pending 请求在旧 Host 退出、Main 不存在且新 Host 尚未启动的故障窗口中保持 journal=`prepared`、恢复数 `0`、`dispatch_enabled=0`，随后新 Core 自动 claim 为 `completed`、恢复数 `2`、`dispatch_enabled=1`，两个请求均保持 `pending + waiting + recoveryReason=host_handoff`。未来协议仍快速进入结构化维护态，最终发现文件清理且 `quick_check=ok`。正式大库 Test 已证明只读 generation 的 Host 启动、退出与发现文件清理；独立可写 Test 又证明 Main 保持时 Core 硬崩溃可在一秒内换代恢复，并在 Pi Provider 请求活动期间终止 Worker 后以 unknown 禁重发、显式换代恢复和真实 Haiku 新会话成功收口。仍待核验的是两个实际打包版本之间的 handoff、真实维护页和 GUI 退出选择；不能用同版本 Worker generation 切换冒充跨版本交接。

Main 本次调用新启动 Detached Core 后，如果初次 Browser bridge 注册或恢复/交接后的 attach 注册失败，不能再只关闭 bridge 并等待 Host 的 30 秒空闲回收。`connectOrLaunchExecutionHost` 现在返回“既有连接”或进程内一次性 cleanup capability；只有 requested generation、已发布 instance、spawn PID、kernel lease、lock、rendezvous、health、控制端点和 validation identity 全部仍匹配，能力才会调用本机 `/shutdown` 并等待 PID 与 SQLite 内核租约同时消失。竞争中由其他窗口赢得的 Host、既有 Host、身份漂移或不可证状态一律不关，也不按陈旧 PID 发信号。`verify-detached-core-attach-cleanup.ts` 以真实临时子进程、控制面和 SQLite lease 证明三条分支：本次新建失败立即收口；既有 Host 失败保持存活；identity mismatch 返回拒绝且保持存活。shutdown 或 45 秒等待失败会与原 attach 错误组成 `AggregateError`，不会伪报已清理。

Execution Host 状态心跳已改为单条数据库聚合，不再每秒调用 `listRecoverable/listInProgress/listPending/listSessions/listActive` 并反序列化全量记录。提交、effectful turn、待回复请求、可能持有进程的 Runtime 和活动命令分别使用只包含活动状态的部分覆盖索引；`running` 与 `orphan_detected` 共享同一进程所有权判定，软删除或归档的孤儿进程也不会被漏算。handoff 捕获不读取 `payload_json`，但会保存请求 ID、Provider request 身份、request/turn/conversation 稳定时间戳、逐项 SHA-256 与总 SHA-256；恢复时先从 journal 行重算逐项与总 hash，再与当前业务表比较。同一 turn 的多个请求先全部预验证、再按唯一 turn 更新一次，避免第二次 CAS 把预期的 `affected=0` 当作成功依据；request、journal request、唯一 turn、conversation 和最终 handoff 每次更新都必须命中恰好一行，任一 `changes() != 1` 会回滚该恢复 SAVEPOINT 并进入 `recovery_required`。迁移 ID 已核对既有 checksum，结构漂移会拒绝启动。临时行为核验在每张表 1,000 条终态历史、Codex/Pi/身份冲突请求及带 512 KiB 请求载荷的现场中验证五类计数、`orphan_detected → lost → orphan_detected` 转换、最小 Codex handoff 身份、五条覆盖索引查询计划和 `quick_check=ok`；250 次聚合读取的本机 P95 约为 0.03 ms，仅作为结构回归证据，不替代正式大库 SLO。

收益：窗口重启和 Main 短暂故障不终止长任务；升级不会产生第二 SQLite 写入者；新建 Host 在 UI attach 失败后不再无意义占用数据库写租约约 30 秒；v2 Host 异常退出后，残留诊断 lock 由下一任真实 lease owner 留证接管，不再形成永久维护环。

缺点：后台生命周期、用户退出语义和跨版本 drain 更复杂；任何无法证明已排空的后台写入都会保守阻断或进入 `recovery_required`，短时可用性低于冒险继续升级。legacy/future/unsafe 或身份冲突 lock 仍必须保守等待；quarantine 证据不会自动删除，需纳入 runtime 保留策略。attach 失败补偿需要额外 health/lock/rendezvous 身份复核，若 shutdown 卡住会最多等待安全退出上限并把启动判为失败；身份不可证时仍宁可等待 Host 自行空闲退出，也不能冒险关闭其他窗口的工作。新增 journal 表、hash 计算和五条部分索引带来少量写放大与磁盘占用，既有大库首次迁移仍须在最终一致副本记录耗时和空间增量。

## 5. ZARCH-063：多设备用户数据同步暂缓

### 未决产品问题

- 哪些对象同步：设置、任务、项目元数据、Memory、归档和删除墓碑需要分别决定；凭据、系统密钥、代码工作区、Provider 原生历史、会话执行和活动命令默认排除。
- 谁是权威：需要逐对象确定单写设备、云端权威或多主模型，不能用“最后写入获胜”覆盖任务状态和删除冲突。
- 如何合并：需要设备 ID、逻辑版本、幂等事件、离线队列、删除墓碑、冲突草稿和用户确认。
- 如何加密与恢复：需要端到端加密、设备加入/吊销、跨设备密钥恢复和密钥丢失语义。
- 如何接云：iCloud 与 Google 必须通过正式适配层返回远端对象版本；本地同步目录出现文件不等于云端提交成功。

在这些问题明确前不安装连接、不写产品代码、不创建云端对象；本轮也没有触碰任何 iCloud 或 Google 数据。

收益：避免跨设备重复执行、错误合并、删除扩散和凭据泄漏。

缺点：本轮没有多设备同步功能；后续需要独立产品设计、迁移协议和真机矩阵。

## 6. 验收边界
